# 需求分析（七步法）与业务调研

对已收集/圈定的需求做分析+调研，产出「范围确认依据」，**不是**产品方案（PRD）。范围锁死才进入 字段清单→业务PRD→DemoPRD 链路。

## 〇、先做真伪鉴定：这条需求该不该由产品做（写方案之前的门）

用户的原话：「先看需求要做什么，然后考虑是否需要产品配合实现，也就是需求的真伪鉴定，如果是组织层就能解决，就不需要做产品的设计。」**这一步排在七步法之前**，跳过它直接进七步法，会把业务没治理完的问题变成开发任务。逐条过五问：

1. **表面诉求 vs 真问题**：需求方写下的往往是方案（加个页面/字段/报表/开关），要还原出他真正要解决的问题（什么现象、谁受影响、拿它做什么决策）。写不出真问题＝还不能进方案。
2. **根因在不在我方系统**：波动/缺失/口径漂移的根因若是上游机制（外部平台黑盒）、业务动作、或指标定义，改我方页面只是掩盖。判据一句话：改完之后那个真问题还会不会发生？会 → 不是产品能解的。**别把需求方给的单一句根因当成定论写进方案——那是替业务接锅**，先核实再引用。
3. **组织层能不能解**：三问——① 它依赖的定义是不是别人还没定（业务自己的标签清单、指标口径、激励规则）？② 换个流程/考核/话术能不能解？③ 这件事现在实际是怎么做的（没人做 = 功能做了也没人用）。
4. **能力是不是真缺**：走本文「新增判定铁律」那两关（生产环境不存在 + 跨系统不可复用）。缺 → 产品做；不缺 → 标增强/对接。
5. **排期逻辑成不成立**：它依赖的那条若排得更晚就是假的（见「排期倒置」条）。

**四档结论，每条都必须落到其中一档**：① 必须产品做（能力缺失/链路断点）② 先组织层解决、产品再定要不要做 ③ 依赖顺序有问题、范围要砍 ④ 后置 + 先试流程。

产出形态：一张「要做什么 / 真伪判定 / 依据 / 结论动作」的表 + 上面的三档归类 + **最多 3 条必须先问业务的问题**（判据同「澄清项三分类」：不答就定不了范围的才算）。正文每段把**事实/推断/待确认**标出来。

**不要对 N 条平均用力**：一批需求里通常只有一两条是真能力缺失，其余是口径、治理、顺序问题。结论要敢写这句——「把整包一起做，等于把业务没治理完的问题变成产品开发任务」。每条的价值口径也要敢质疑：需求方自认「只给定性价值」的条目，验收锚点改成「链路能出数」这类可判定的东西，别挂核销率/打标率这类运营指标。

## 〇之二、再看归属：要的是「数据」还是「能力」（大数据 vs 我方）

真伪鉴定之后接一问：「哪些是大数据的需求，哪些是我们的」。判据一条：**要的「能力」在我方（页面/引擎/配置/发送链路）→ 我方开发；要的「数据」在别人那（大数据/DMP/券系统/VK/账号体系）→ 外部供数，我方提需求并排期；两边都要 → 拆成两张单子分别立项**。逐条出四列表：条目 / 我方要做的 / 大数据（或其他外部）要给的 / 谁主导。

归类只给这四档，不要发明第五档：

- **纯我方**：外部依赖可能有（如 VK 手机号），但不涉大数据。
- **我方为主、个别指标要外部供数**：主体是我方页面/清单，只有一两个指标（如「已注册好友数」）要账号体系供数；供数方没确认就写「未确认」，不要默认它有。
- **大数据是硬前置**：数据不接，交付出来就是空界面/空壳。这类的排期必须写成「以数据接入为前提」，不能只挂在依赖栏里。
- **我方主建、外部供事件数据**：引擎/配置在我方、事件数据在对方；事件表的登记（事件配置）写入方常是数据方而需求入口在我方——写成一条**流程**，不要写成技术对接。

收尾产出一份**只给大数据的问题单，5 条以内**，每条都必须是「不答就排不出期」的桩：有没有这个数据源、接入排期、哪份数据谁供、粒度到哪个 ID、事件配置登记谁落表。

两条提醒：① 外部依赖是 VK / 券系统这类时，**不要统写成「大数据」**——归错团队，诉求会递错人；② 数据缺口未核实前不要拿它当结论写进方案，标「供数方待确认」。

③ **供数方是外部供应商（非内部团队）时，先分清「开通」与「定制」**：标准事件/标准接口往往自己就能订阅，不需要供应商开发；确实要它定制的，也不要写成开工前置——按「先查我方实际能收到什么 → 评估自己接或让对方转发 → 都不行才降级为推断、不写进验收」三档处置，并把该项记为**待确认与风险**。功能按双口径都能算的方式设计，数据到了再校准，不要因为供应商没动静就让需求停摆。

## 〇之三、可用性三问：上线之后会有人用吗

前两节只回答了「该不该我方做」「谁供数」。还差最后一层，不写就会被直接质问：**「就知道满足业务诉求，不知道辩证，做了一堆产品功能没人用，没数据，有什么意义」**。每条需求再过三问，结论写进需求池分析列的第三段「上线后怎么判断有用」。

1. **基线值**：这个指标现在是多少？多数需求原文只写「提升效率/提升准确性」这类定性话，没有基线的需求只能验「功能上线了」，验不了「有没有用」。查不到就写「基线缺」，不要替它编数字。
2. **谁会真的点、凭什么点**：列出使用者角色与使用频率，再问动机——这个动作对使用者本人的指标有没有好处？（导购多打一次标、多分享一次券，若不进他的考核、也没配套任务化/激励，那个「打标率 40%」只是纸面数字，只能算运营承诺，不能进产品验收。）
3. **拿什么数据判成败**：验收锚点按可信度排序——**可量化基线对比 > 链路能出数（分享数/领取数/核销数）> 运营指标（不接受）**。原文自认「只给定性价值」的条目，锚点改成「链路能出数」。

**第四问（数据前提，并进真伪鉴定一起写）**：这条要的数据现在有没有？数据不到，功能做出来就是空壳——空界面、没有事件可触发的计划类型。

落地两条：

- 结论写进需求池「产品分析」列时**三段并行、不混成一段**：真伪复核（要做什么/真伪判定/归属）→ 优先级建议 → 上线后怎么判断有用。
- 对业务的书面问题单**按三槽出题**（基线 / 使用者与频率 / 验收口径），每条需求 3–4 题，一条只问一件事。**判据不写进对外版**——「没有机制支撑这个数就是空的」是我方判断，写出去变成争辩；对外只问「配套机制是什么」。
- **需求池里的优先级常由项目负责人标注，不是产品拍板**：只在分析列写「优先级建议」并注明与子单/原文的差异，**不要去改原优先级列**，也不要问用户「以哪个为准」。

## 七步法（需求分析）
1. **拆子需求**：按业务环节拆（解决什么/给谁/哪个环节），不按技术拆。
2. **分类定性**：标 核心链路（没它闭环断）/ 增值 / 支撑能力。
3. **四维估**：价值 / 成本 / 风险 / 依赖（简单打分或 RICE）。
4. **找依赖串联**：谁是前置，排不出顺序=没理清。
5. **取舍分期**：定 本期 / 二期 / 砍 / 延，砍要有理由。
6. **列待确认**：口径/范围/冲突列出来问业务，不许猜、不许自行定。**澄清项要收敛分类，不许把不确定性全倒成一张长清单**（分类见下「澄清项三分类」）。
7. **产出分析报告**：一张表=子需求|价值|成本|依赖|优先级(本期/二期/砍)|理由 + 待确认清单。给对范围用，不是 PRD。

## 新增判定铁律（防"已有能力被评估成新开发"）
- 标"新开发"前必须过**两关**：① 生产环境 DOM 确证该能力不存在（已抓该模块/页面）；② 跨系统确认也不存在（相邻系统可复用/对接）。两关都过才算新增。
- 有一处已存在或可复用 → 一律标"增强/补指标/对接复用"，不标新开发。
- **默认怀疑已有**：需求池文档没提 ≠ 系统没有，判断以生产系统实测为准，不以文档为准。
- 评估结论若与生产环境证据冲突 → 以生产环境实测为准，列差异清单自修正。

## 多需求批量分析档（一次分析 N 条已圈定需求）

当用户说「把二期/这批 N 条需求分析一下」，产出是**两个文件**，不是一份长文：

- `XX_N条需求分析档.md` —— 论述正文（逐条展开）
- `XX_N条需求总览.tsv` —— 9 列可排序总览：序号 / 需求名称 / 原文优先级 / 期望上线时间 / 涉及端 / 主要依赖 / 源码复核状态 / 建议排期段 / 备注

分工理由：论述塞进 TSV 读不了，可检索字段淹在 md 里对不了表。**两份必须逐行一致**，改一处同步另一处；`源码复核状态` 只许填「本轮已复核」或「沿用旧评估未复核」，不许留空（读者要能一眼分清证据等级）。

每条需求的段落顺序固定，**逐条七段**：① 原文摘要（照抄关键句，不改写）② 业务场景与价值 ③ 现状核查（生产源码 `文件:行号` + 真系统页面证据）④ 实现方案（MVP 优先，分别写清要改哪些端）⑤ 前置依赖（外部数据/系统 + 内部能力）⑥ 优先级建议与理由 ⑦ 待确认项。

分析纪律：

- **同一份产物不要拆给多个执行器分头写**：7 条需求分给 7 个 bot 各写一份方案，合并后**必现**三类不一致——① 同一字段两套互斥定义（一方写「添加/待添加/删除」，另一方拆成「好友动作 / 账号状态 / 待添加」）② 两条需求互相声明对方是前置（循环依赖）③ 术语大小写与菜单名各写一套。切分要按「互不重叠的产出物」，不按「同一条流水线一人一段」；合并后必须再跑一轮**术语 / 字段边界 / 依赖**对齐才能拿去评审。
- **验收对方产出要对着权威源核，不能只看它的自报**：让执行器自查「八节齐全、依赖未动」不够，要另起一轮**对照审查**——把草稿与权威文档逐条比，重点是：依赖有没有漏（尤其「依赖另一期能力先交付」这种排期级前置）、口径有没有与权威源冲突、有没有编造系统实现（接口名/字段名/表名）。
- **审查结果要分「事实 / 自行判断 / 待确认」三档落地**：审查提出的问题里，属于内部文档证据链的（引用了源码行号、内部证据档）**不要删**——那是内部调研档该留的；只把「没出处的断言」改写成待确认，并在文档头部加一行说明证据来源与时效（避免读者拿几个月前的期望上线时间排今天的期）。
- **事实与推断逐条分开标注**；查不到的集中成「源码未命中汇总」一节，**不许用推断顶替事实**——用户会当场抓「这一条你在源码里找到了吗」。
- **不替需求方拍板**：原文写了「此功能和 X 一起上」就按一起上写，能不能拆单这类问题只挂进待确认并**指名需求方**，不进实现方案。
- **工作量拆到「引擎 vs 事件」层**：新建的触发/调度引擎是主成本，事件个数只是挂在引擎上的配置。只数事件数量会让排期严重失真（现有系统可能只有定时型计划，事件源/调度器都是新的）。
- **合并建议必须附一条口径待确认**（谁覆盖谁、冲突如何处理）。写「A+B 合并」会把口径冲突藏起来，读的人以为没风险。
- **整体判断给三档**：建议先做 / 建议合并 / 建议暂缓后置，每条带理由；理由优先引用源码行号这类事实，不用「价值高」这种空话。
- **找「今天不做明天返工」的预留口子（底子 vs 面子）**：评估 MVP 范围时把候选内容分两堆。**底子** = 不预留就要做数据迁移 / 重写模型的：① **中枢化的定义**（行为/事件/标签的定义与属性集中管理，使用处只存引用 + 快照，绝不内联）② **能被独立命名与存取的组合对象**（条件集——将来的「人群/人群包」就是它被存下来命名，界面可以先没有）③ **定义层的语义定死**（主体是谁、时间按哪个字段、是否快照）④ **取数口径**（首次 / 最近 / 每次发生——「第 N 天」类触发都按首次起算）。**面子** = 界面模块（列表页、命名与复用选择器、画布、触发引擎），后加不疼。MVP 只做底子 + 最小使用入口，面子写进后续版本。拍板时给两案边界让用户选（A 只预留数据结构 / B 带最小资产界面），别替他决定。
- 若某条需求要用的定义（如事件配置、行为定义）与本期正在新建的能力同源，就要求本期把该定义做成通用的，写进「本期不做但预留」。否则后面必然出现两套模型、两套 JSON 语义。
- **依赖别的系统才能做的条目，排期建议里先写「确认对接人」**——对接人没定，排期是假的。
- **拆单后以子单正文为唯一权威源，母单原稿整体作废**：需求池里一条母需求被拆成 N 张子单后，子单各自的正文、优先级、期望上线时间、处理人都会脱离母单单独演进。旧分析档常是照母单写的，会出现「文档写 9 月中旬已过期、子单其实写着次年 3 月」这种整表失真。核实顺序：先 `grep '^## 二、详细描述'` 逐份读子单正文 → 用子单的优先级/期望上线时间重置总览 TSV → 再回头改分析档里引母单的段落（尤其「与 X 一起上/不拆单」这类绑定关系，子单里可能已经没了）。**报给用户时把旧的 vs 子单的对照表列出来**，让他一眼看到哪几条被重排。
- **排期倒置检查（每条需求都要对着它依赖的条目比一次日期）**：A 的输入数据由 B 产出、而 B 的期望上线晚于 A 时，A 首期交付必然「功能在、数据空」。这类问题不能只写在依赖栏，要单列成「要么把 B 提前、要么承认 A 首期只做不依赖 B 的那半」，并作为必须向业务拍板的问题之一（不拍，交付内容就是空的）。
- **需求方自报的「仅适用某国/某地区合规」＝投入产出比的硬约束**：单国家单点需求要按「国家单点」单独归一批，别和全局能力混在一个里程碑里排。
- **旧评估要重新核源码再用**：沿用几个月前的评估结论必须在总览里标「未复核」，并要求高相关度的条目必须复核。旧结论可能是错的（原型注释、旧报告都骗过人）。
- **不飘、不脑补、可追责**：产出里三类写法必须分开且显式标注——**事实**（带出处）/ **推断**（写「推断」二字）/ **假设**（写「口径假设（谁拍/何时）：……，待澄清」）。没出处的断言一律改成「待确认（见待确认第 N 条）」。把推断写成事实句，评审时是要被人担责的。
- **澄清项三分类（收敛，不靠数量堆严谨）**：① **A 必须外部答复**（需求方 / 大数据 / 其他团队）——只有「不答就没法开发、或没法判定验收」的才留这里，**每份最多 3 条**，超出先合并同类项；② **B 产品内部能拍的设计选择**——单独成「设计选择（建议 + 待拍）」清单，给建议方案与理由，标注待产品拍板；③ **C 开发实现细节**（接口怎么调、表怎么建、并发怎么处理）——进「留给开发确认」，不占产品澄清位。判据一句话：不答就做不了/判不了验收 → A；只是做法不同 → B；只是怎么实现 → C。**评审会只过 A**。
- **A 类还要再收敛一层：按「谁答」合并成书面问题单**（需求方一份 / 大数据一份 / 开发一份 / 运营一份），**会上只留「不拍就开不了工」的条目**——实测几十条 A 类里真正必须上会的是少数几条“桩”（数据源有没有、两套系统的同一人怎么映射、架构归属、本期范围）+ 跨需求口径组；其余 1:1 问题书面递出、会后回收。用户对“每份 3 条、共 21 条”仍然回“还是感觉不合理”——**可见“数量均摊”不是收敛，按人归并 + 只留卡开工的才是**。
- **澄清项质量五查（bot 产出的清单必查，逐条过）**：① 「问谁」是否落到人或角色——出现“材料未覆盖具体人 / 请某人指定”就是会上拿不出去；② 「影响哪些结论」是否说清影响，而不是堆编号（“③7、⑧5”这种读者判断不了严重度）；③ 一条是否只问一件事（一条塞 6 个子问题必须拆开才能逐条拍）；④ 是否**混装**——**材料缺口**（示意图未转录）与**现状核查**（让开发去查）不属于待确认，应单列「补材料清单」「现状核查清单」；⑤ 优先级是否有理由（“高”给交互细节、“低”给底座问题 = 排序无依据）。
- **最终形态**：一张「会上必拍」小表（问题 / 为什么必须会上拍 / 建议谁答 / 不答的后果）+ 按人分发的书面清单 + 补材料清单，并**显式列出「不进澄清范围」的部分**（设计选择已给默认值、实现细节已交开发）——不写清它们就会回流到会上。
- **待确认项条数失控（几十上百条）说明没做判断，不是严谨**：清单一长，评审会过不完，等于没提。重排后要给出分类统计（A/B/C 各几条）。
- **会议纪要到手后第一件事是回写已有清单，不是再提一轮问题**：纪要里已经定下来的结论（某人说明的机制、已确认可提供的数据、已确定的支持范围）要从「待拍」里移走，改写进对应条目的「理由 / 已确认」栏，并升清单版本、注明依据哪一次会议纪要。留着「这个数据有没有」这类已被纪要回答的问题，等于让会上把已经说过的话重说一遍。真缺口通常只剩两三类：供给方与覆盖率、与既有设计的落地冲突、排期归属。
- **纪要里的已知限制要拿去和已有设计对撞，找出落不了地的条款**：纪要写「某标识无法区分国家」这类限制时，回头扫一遍自己的设计里有没有依赖该属性的固定条件（如受众筛选里那条「国家条件：XX（系统固定，不可修改）」）——对不上就当场列成待确认，写进对应条目理由栏，不要等原型做出来才发现执行不了。
- **引用第三方结论必须带得上原话**：写「X 已确认 / X 说」时手上要能对上原话；记不清是谁讲的，就只写结论不带人名，或标「待核」。把乙的观点安到甲名下、并把「避免 A 造成折损」记成「A 不可用」，结论会整个反过来，而且会一路传进澄清清单和 PRD 被人当场纠正。

## 接手「已做了一半」的需求评估：先盘点交付物谱系，再定真缺口

用户说「把那批需求评估做一下／这条主线今天没推进」时，**不要从零重做评估**——同一批需求往往已经沉淀了四到五件产物，真正卡住的是别的环节。动手前先 `ls -lt` 该需求目录 + `grep '^#' <分析档>` 拉目录树，按下表判断现状：

| 产物 | 存在说明 |
|---|---|
| `XX_N条需求分析档.md` | 逐条七段论述已做，不需要重写 |
| `XX_N条需求总览.tsv` | 优先级/排期段/复核状态已有 |
| `XX_澄清清单_会前版.md` | 澄清项已按「会上必拍 + 按人分发」收敛过 |
| `复核/复核v1-第N类-*.md` | **这轮复核问题没人消化 = 真正未完成的工作** |
| `草稿/` | bot 草稿，非权威源，只做参考 |

判断规则：**「未推进」多半指复核问题未回写，或结论未出，而不是分析没做**。向用户汇报时先报「评估主体已完成到什么程度 + 真缺口在哪」，再动手改，别让他以为要重跑一遍。复核问题按「高严重度必改／中低批量／需业务拍板」分三档，只有第三档才需要打断用户。

## 业务补充四块：背景／目的／价值／运营计划

用户要拿材料找业务（需求方）补需求背景、目的、价值、运营计划时，产出是**一张可分发可回收的收集表**，不是一段论述。做法见 `references/business-supplement-collection.md`，核心四条：

1. **预填「原文可依据」那一栏**（照抄原文/分析档的句子），业务只需补空白，不重写；缺的写成编号问题 ①②③，一条只问一件事。
2. **判据只进内部版，不发给业务**：「不合格的样子」（背景不能是「为了提升效率」、价值不能没有基线、运营计划必须写到执行主体与规模）是用来评回收质量的，**不要放进发给业务的第一版**——用户会直接说「先看她给的第一版，先不指导她如何填」。对外版只留 `原文已写` + `想请补充` 编号问题；判据、状态速览、结论三句真话留着自己看。
3. **一页速览表**用「原文有／部分有／缺／全缺／待量化」标每格的状态，让缺什么一眼可见；再单列一节「回收时要拿到的最小信息」，把最卡排期的 5–6 条拎出来当面问，其余书面回收。
4. **结论要敢说真问题**：常见组合是「运营计划几乎全缺、价值全部未量化、某条排第一批的理由只是‘改动小’」——这三句不写出来，表就只是一张表。
5. **材料发出后就停手，不要替用户跟踪人际沟通**：用户说「我已经发过了，等回复就好」之后，不要再规划怎么催、该怎么跟对方说、还缺哪几句——他负责找人，你只等他的回信再把质量判断拿出来（判据留着用于那一刻）。

## 业务调研问卷（极简格式）
- 回答者**点选不写长文**：每道题下 `- [ ] 选项`（单选只勾一个，多选勾多个）+ 末尾留"回答："输入框。
- 题型字段、细致分区一律不要（用户看不懂复杂格式，宁简勿繁）。
- 问卷只问两件事：业务怎么运转（调研者答）+ 产品怎么定范围（用户拍板）。系统/技术事实不走问卷（自行抓证据）。
- 收回后整理成：已确认事实 / 待确认 / 产品决定 / 后续动作，不把原始回答当 PRD。

## 产出可读性铁律：用需求名字，不用代号
需求分析报告的读者是业务和评审，不是写文档的你自己。
- **禁止 R1–R8、REQ-01 这类型号**：业务看不懂，过两周你自己也记不住哪个 R7 是哪条。用户原话「给业务都看不懂 R1 是什么，我也会忘记」。
- 正确写法：正文、依赖、风险、分期建议里的**交叉引用全部带需求名字**（「导购打标」「好友列表状态」），读者不该为了看懂一句话往回翻表。
- 需要排序时只在一张总表里放**序号 1..N**，并保留原始系统编号（VAPD/需求池编号）做追溯，正文不出现序号。
- 从代号批量改名字要用脚本，改完必查两类坏味：①名字叠词（「导购打标 打标」）②名字被换成句子成分后串在一起（「…营销工具带参分享」）。抽查总表与分期表两处，别只看正文。
- **批量改口径的五条规矩**（当生产端证据推翻了文档里的预设现状——术语叫法、页面结构、步骤序列）：① **版本记录 / 变更日志行保留旧口径**（跳过表头含版本/日期/变更摘要的行）——改了反而断掉追溯；② **术语替换与结构叙述分开跑**：只改术语会留下「术语新、结构旧」的半成品，「第 N 步 X」→「X 区块」、步骤条 → 单页区块、Mermaid 节点名、用例里的操作流程列表要各自处理；③ **落点未定的内容标「（落点待定）」，不删也不断言**——直接删掉会让读者以为这事不存在；④ 逐文件报替换处数，改完 `grep -rn` 验收：要改的归零，**残留只允许出现在版本记录行**；⑤ **文件名含旧术语的一并改**，改前先 grep 引用点再 `git mv`。
- **谁来做**：带判断的口径批量改（哪些是历史行、哪些标待定、结构叙述怎么改）且文件量在十几个以内时，**在仓库里自己跑脚本更快**——不必为了「机械活交给执行器」的教条多开一轮 A2A 指令；纯机械、无判断、上百文件的全仓替换才交给执行器。
- **人名也一律写真实姓名，禁内部昵称**（agent 内部称呼之类）——文档要拿去评审，读者不认识代号，看到先问"这是谁"；项目名保持原口径，只改人名。替换前先 `grep -rln '<昵称>' --include="*.md" .` 扫全项目：需求调研问卷、业务PRD、方案稿往往同时中招，一次改完再交付，改完复查零残留。

## 两个分界（防混淆）
- **需求分析** = 拆解+排序+取舍+定本期范围 → 产出分析报告（决策过程）。
- **产品方案/PRD** = 范围锁死后把选定的细化成字段/流程/页面。范围没定方案必返工。
- 需求仍模糊 → 先澄清，不直接分析。

## 输入侧：需求池维护与内网在线表抓取

把公司内网需求池表完整落到本地、对账、定目录结构，见 `references/requirement-pool-maintenance.md`。三条铁律：

1. **TSV 是唯一事实源，状态/版本是列不是目录**——按状态建目录，状态一变就要搬文件、git 历史断裂。一条记录一个 md + 手写索引表 = 把一张表拆成 N 个文件再手工指回去，纯增熵。
2. **表头会变，指令先抓表头再抓数据**——按预设列名抓会静默漏列；先抄实际表头逐列比对再报增删。内网表只能用户侧 Cursor `@Browser` 只读抓，`?sheetIndex=N` 是定位单表不是限制。
3. **先对账再删旧数据**，对账用唯一编号（VAPD 单号）不用名称模糊匹配；新数据可能抓漏，旧库是唯一基线。

分工铁律：公司电脑只读不推，落文件与 git 一律 VPS 侧做；抓取指令红线必须显式写「禁止任何 git 操作」。

**把分析结论回写进需求池的「产品分析」列**（行号定位、追加不覆盖、验收四项、线上表只能用户自己贴）的做法见同一份 references 的「回写进需求池的某一列」节。

## 把需求填进在线需求 list（功能点拆解）

公司需求表的标准列是 **所在端 / 1级菜单 / 2级菜单 / 3级菜单 / 4级功能点 / 5级功能点 / 功能点描述**（一个需求占一组行，1–3 级菜单是合并单元格，不必每行重复填）。填法：

- **菜单层级取自真实菜单树，不许自造**。从知识宝典的「菜单结构总览」和原型 `src/config/menus.ts` 逐级对。自造分组（如"列表交互"）会在评审时被当场问"指的什么"。
- **粒度到「页面级功能」，不到字段**。一个页面 3–5 行（筛选条件 / 列表页 / 导出 / 权限），字段名放在「功能点描述」里用顿号连写。拆成"每字段一行"必被打回。
- **筛选字段 ≠ 列表字段**。加几列不等于加几个筛选；筛选只挑业务真会用的，其余让业务导出到 Excel 自己筛。
- **明确「不支持」的项不占功能点行**。列头排序这类"不做"的事写进表里会被开发误当成需求，口头说明即可。
- **措辞防反向歧义**："非当前页"会被读成"不含当前页"，要写"含当前页，不受分页限制"；"时间类型下拉二选一"与"两个独立区间筛选"是两种交互，别混着写。
- **有口径风险的字段写在描述里标「待确认」，不要另立一行**。更不要给取数链路凭空立"服务端数据表"这种项——取数不改字段值，字段本来就在表里；用户会直接反问"取数据又不改字段值，为什么要在功能点里单独立项"。
- **先确认这块由谁交付，再决定拆多少行**。同一个模块可能是「对方系统出页面、我方供数据」，照自研功能清单拆十几行会被打回（"报表不是我们做，是大数据那边内嵌页面，不需要我们做功能"）。但也不能反向一刀切成"我们啥也不做"：页面由对方画、数据靠我方落表出接口时，功能点就落在**字段与口径**上。两种搞反，一个白做一套页面需求，一个漏掉真正要写的落库工作。
- **菜单归属与交互位置先查对标系统**。同一能力在参考系统（如内销 CMS）挂在哪个菜单层级、在流程第几步出现，照它的相对关系走，别按自己的语义洁癖重新发明。查证路径：竞品/对照文档里记的菜单路径 + 原型里 steps 的定义。
- **交付形态：发 .tsv 文件，不在聊天里粘制表符长文本**。要求"弄个 tsv 我好快速复制/表格形式"时，把文件发给他（Excel/WPS 双击就是真表格），粘一大段 `\t` 分隔文本会被回一句"你发我的不是表格形式"。文件里列名必须与他在线表实际表头逐字一致（先用截图/导出确认表头，别用自己习惯的列名如"需求名称/4级功能点"代替"所在端/1级…/功能点描述"）。
- **菜单归属不是产品单方面能定的，要分两处看**：①管理侧配置入口（事件配置、标签管理这类）只有总部几个人用，培训成本低，可产品先定；②圈人/操作侧（受众圈选这类）所有国家运营每天都在用，动了就是改操作习惯＋要给业务再培训，必须运营确认。拿不准时给运营三问：现在是否一次配完？页面多一块会不会找不到原来的入口？这件事现在实际是怎么做的（回答"否/没做过"说明功能做了也没人用）？降风险三法：范围先小（只接一个事件）、默认收起不占地方、先灰度一个国家再推。
- **交互细节不写进需求 list，留到出原型**。需求 list 回答"做什么功能"，不回答"控件长什么样"。表头内嵌搜索框、回车触发搜索、有内容显重置按钮、点×清空并恢复默认列表——这些是公司交互规范里已有的约定（需求要审、原型上会标），写进需求 list 只会撑大篇幅。原型阶段直接套公司现有的交互说明档（如 `vX.Y.Z-交互说明` 里「表头交互规则」那一节），不自己设计控件样式；没拿到完整规范时先问用户要，不要凭记忆补。
- **数据侧的口径争执不要撿进自己的功能点**：报表指标该算"首次添加"还是"所有添加动作"这类，是数据方和业务对的事；我们只保证字段都在（两个时间字段都落库），他们怎么定都能算出来。把它写进需求会被回"这是大数据要和业务对的东西

## 内部标杆系统对标：差异清单与汇报口径

领导拿标杆系统（如内销 CMS）衡量本项目时，产出物是**差异清单**，不是论述文章：逐项列 `标杆位置 / 我方现状 / 是否一致 / 差异原因 / 处理`，**三层分开列**：① 菜单位置 ② 菜单与能力命名 ③ 能力有无。他要的是「看差异就能判断两个系统有什么不同」。

**〇 结果口径（不然整个文档方向就是错的）**：**差异可以有，但每条差异必须给出能说服人的缘由。** 不要写自造主张（如「对齐能力骨架、不对齐界面形态」）——那是产品观点，不是领导口径。差异分三类写，读者一眼能判断性质：

- **该改的（多为位置类）**：已确认要动，写明历史缘由 + 调整动作。
- **阶段性差异**：方向一致、我方后续版本已规划（写清是哪个版本，把「没有」变成「什么阶段有」）。
- **以我方为准**：有生产实测证据支撑的口径（如指标层数、按渠道区分的字段），说明为什么不能照搬。

**一、位置/命名对照要单独成表**：同一能力两边叫不同名字（组织管理 vs 组织架构、运营报表 vs 数据报表）最容易被当成「两个系统不一样」，其实是一回事——命名差异也要收进清单并建议统一口径，评审时主动说明。

**二、位置结论不许用二手来源**：原型 `menus.ts`、知识宝典、旧报告都是**二手**，只能当线索。凡涉及「把系统内既有模块搬家」的动作，动手前必须在生产环境只读核实：真实菜单树 + 影响面（菜单资源、角色授权、历史链接、是否有按菜单归属做权限判断的后端逻辑）。

**二之二、核 "标杆有没有这个能力" 必须分清「看到了」与「没观察到」**：没看到 ≠ 没有——把"没看到"写成"标杆没有这个能力"，用户自己一截图/一问人就当场推翻，且据此做掉的功能会变成"不该砍的砍了"。写法固定：「已观察到 X（页路径/截图/字段名）」「未观察到 Y，需再取证」。

**二之三、对标结论要落到"具体形态"，不能停在能力名称**："有没有某能力"决定做不做，"以什么形态存在"决定怎么做。示例：标杆的启用/停用是**列表里一个开关列**，我方做的是"停用按钮 + 二次确认"——两者都叫启停，形态不同，只对齐名称就会做成两套交互，评审时被当成差异。同理：列表列名与列数（标杆可能有"行为维度"这类我方没有的列）、有没有筛选区、操作列有几个按钮，逐项抄进差异清单。

**二之四、菜单位置的分量高于能力名称**：同一能力挂在不同一级菜单下，读者就当成两套系统。查证路径：从标杆真实页面读出**完整菜单路径**（不只当前页，连它的同级兄弟一起抄）——同类能力成组出现在同一配置域时（如"圈人原料类"配置集中挂在一个配置菜单下），我方也应**整组归位**，而不是逐个模块各找地方。

**三、可行性要诚实分层，别一句话说「可行」**：

- **结构可行**：目标一级菜单是否已存在——已存在就是换挂载点，不是新建域；
- **机制可行**：归属到底是配置数据还是写死代码——判据是「生产路径的域与当前菜单位置是否一致」，两者不一致即证明「挂在哪」由菜单数据决定，而不是前端路由；
- **影响面待核实**：角色授权绑定、历史链接、后端权限语义。

前两层有证据才敢说可行，第三层没核实就明说「待核实」，不要用前两层推出第三层。
