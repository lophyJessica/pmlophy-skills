# 需求池维护与内网在线表抓取

需求分析的输入侧：把公司内网的在线需求池表完整、可对账地落到本地。

## 一、内网表只能靠用户侧 Cursor 抓

Hermes 在 VPS 上访问不到公司内网（docs.vivo.xyz / vapd.vivo.xyz），只能给用户公司电脑上的 Cursor 发只读抓取指令，结果回传。

### 指令骨架（顺序不能乱）

1. 首行 `@Browser <完整URL>` —— 声明浏览器控制 + 目标地址
2. Context 第一句写明「该链接已在 Cursor 内置浏览器打开（已登录内网）」——否则它会重新搜索或尝试登录
3. Context 写明执行位置 + 本地项目名
4. Request 分两步：**先读表头，再抓数据**
5. Output format 分两版（见下）
6. 红线：只读 / **禁止任何 git 操作** / 不截断 / 不去重 / 不改列名
7. Checkpoint：页签数、实际列数、行数、与历史基准的差异、文件路径 + 字节数

### URL 写法

- URL 只出现**两处**：`@Browser` 后 + 「数据来源」。写三四次会被理解成多个来源。
- `?sheetIndex=N` 是「定位第 N 个工作表」，**不是「整表」**。只需要一张表时保留它，并写死「只处理当前工作表，其他页签只列名称、不点开」。
- 反面写法：把 sheetIndex 当限制删掉、又要求「遍历所有页签」——等于让 AI 去抓同簿其他产品线的表。

### 先表头、后数据（最容易踩）

- 在线表头会变。实测同一张表从 18 列变 19 列（新增「是否维护」列），某列名被改写。**按预设列名去抓 = 静默漏列**，不会报错。
- 指令必须让 AI：先抄全部物理列表头（多层合并表头记成「上层-下层」）→ 与历史列清单逐列比对 → 报告增删与改名。
- 历史行数作基准写进指令（如「该表历史上 59 条非空、行号 3–13 与 15–62」），数量对不上会强制它解释原因而不是闷头截断。

### 长文本列

「主要场景」「需求价值」「产品分析」「进度跟踪」必须完整读，明写「不得截断、不得概括、不得省略」。唯一允许截断的是附加的**摘要列**，且写死长度（取前 60 字，超出用 …）。

### 读法：文档 API 而非首屏 DOM

让 Cursor 用文档编辑器 API 整段读（`Range().Value` 或等效），不要靠首屏 DOM 快照 / 无障碍树。DOM 有分页、虚拟滚动、合并单元格三大坑；API 一次读完整个区域无截断，还能顺带报 UsedRange 行数与空行行号。指令里写「用文档 API 读取整个数据区域」，比写「滚动到底」有效得多。

### 两版传输

| 版本 | 内容 | 去哪 |
|---|---|---|
| 完整版 | 全列 + 长文本 | 写项目本地文件，用户本地留存 |
| 精简版 | 10–11 列 + 摘要列 | 聊天框贴 TSV 代码块，供远端重建结构 |

原因：飞书机器人收不到文件/附件；完整表贴聊天体积不可控。

## 二、需求池目录怎么摆

- **TSV 就是类 Excel 表格**：Excel 可直接打开、git 能 diff、能 grep、能筛排。在线表转 TSV 即可，不必拆成一个个 md。
- **状态不做成目录**。状态是表里一列，筛选就出来了；按状态建目录 = 状态一变就要搬文件、git 历史断裂、外部引用失效。版本号同理，它是列不是目录。
- 「一条需求一个 md + 手写全量索引表」= 把一张表拆成 N 个文件再手工指回去，纯增熵。
- 推荐形状：
  ```
  需求池/
  ├── README.md             规则说明（十几行，不列全表）
  ├── 需求池-<日期>.tsv     全量导出，唯一事实源
  ├── 需求池导出说明.md     表头确认 + 行数统计，有溯源价值
  └── 需求拆分/             深度分析产物
  ```
- 两类东西分开：**跟踪表**（状态/版本/优先级，TSV 一行一条）vs **分析产物**（拆分稿、PRD、方案，md 放分析目录）。混在一起用户一进目录就觉得重。

## 三、对账：先比对，再动旧数据

- **绝不先删旧数据**。新数据可能抓漏（筛选、隐藏行、分页），旧库是唯一比对基线；先删就无从判断缺哪几条，只能重抓。
- 对账用**唯一编号**（VAPD 单号这类），不要用名称模糊匹配——中文名长度/空格/后缀差异会造成大量假阴性，报出几十条假「新增」。
- 旧库文件名常丢单号，要从**文件内容**取：
  `find . -mindepth 2 -name "*.md" -exec grep -ohE "VR[0-9]{6}-[0-9]{3}" {} \; | sort -u`
- 出两个集合再下结论：`comm -13 old new`（新增）、`comm -23 old new`（可能丢失）。「丢失」必须逐条解释——常见是父单号被拆成子需求独立成行，不是真丢。
- 文件数/体积统计一律递归 `find <dir> -type f | wc -l`；`ls dir/*.md` 只扫顶层，会把 48 个报成 19 个。

## 四、数据质量

- 优先级大小写混用（P2 / p2 / p1）、单元格里挂变更说明（「P2 / 0630调整为P1」）极常见，对外使用前先规范化。
- 空行、以及只有首列有值的行要单独统计，不算有效记录。
- 需求池台账里的「疑似重复」（同一需求单对应两条/两条记录同单号）要列出来让用户核对，别自行合并。

## 五、把分析结论回写进需求池的某一列（产品分析列）

用户说「把分析结果归纳到需求池的分析列」时，按这个顺序做与验：

1. **先看表头定位列号，不按列名猜**：`head -1 需求池-<日期>.tsv | tr '\t' '\n' | nl`，「产品分析」一般是第 11 列。
2. **定位目标行**：`awk -F'\t' 'NR>1{print NR"\t|"$5}' 需求池.tsv` 按需求名称取行号，不凭记忆认行号。
3. **追加，不覆盖**：该列是多人在不同日期写的对话体（「某人：1030 …」「另一人：1106 …」），新结论按同格式追加 `刘龙飞：<MMDD> …`；直接替换会抹掉历史评审意见。
4. **用映射文件回写**：把「行号<TAB>追加文本」写进一个临时文件，再按行号拼进第 N 列输出到新文件；先 `cp` 备份原 TSV，校验通过后再覆盖。
5. **每格写四件**：真伪判断 + 归谁做（我方/大数据/外部）+ 卡在哪 + 待定项。一段话说清，可判定可追溯，不写成流水账。
6. **验眕四项**（只报「已改好」不作数）：
   - 行数不变：`wc -l` 前后一致；
   - 每行列数不变：`awk -F'\t' '{print NF}'` 前后 diff 为空；
   - **其余列零变化**：`diff <(cut -f1-10,12-21 bak) <(cut -f1-10,12-21 new)` 为空——这是唯一能证明没误伤别的列的检查；
   - 目标列非空且尾部与写进去的文字对得上。
7. **线上那份内网表写不了**：只能改本地快照，交付时必须明说「线上要你自己贴进去」，否则用户会以为已同步。
8. **顺手核优先级**：需求池列的 P 级与 VAPD 子单上的 P 级经常不一致（两边各自在改），发现就单独列出来请他定以哪个为准，**不要自行统一**。

## 六、分工：减少 git 频次（防公司监控）

用户明确要求：指令和分析在聊天框走，减少 git 操作。落地——公司电脑只做只读抓取，不 commit 不 push；落文件与 push 一律 VPS 侧完成。指令红线必须显式写「不得执行任何 git 操作（git add / commit / push 一律禁止）」，只写「不要改动文件」拦不住。
