# 需求评审 Skill（两档制）

对已有需求材料做系统评审，提前发现研发看不懂、测试无法验收、业务理解冲突、流程/状态不闭环、异常无规则、范围膨胀的缺陷。

> 版本 v1.2。变更日志见文末。

## 触发条件
用户说「审一下这个PRD」「评审这份需求」「方案能进研发吗」「帮我找逻辑漏洞」「从研发/测试角度看有没有问题」等，且已有需求材料时，启用本 skill。若需求仍模糊→先需求澄清。

## 第一步：定档次（必做，先选档再评审）

| 维度 | 简档 · 快速 | 全档 · 完整 |
|---|---|---|
| 复杂度 | 单模块、流程闭环、角色≤2、字段≤10 | 多模块/多端、跨系统、状态机、角色>2、权限/异常复杂、依赖外部接口 |
| 评审深度 | 扫核心维度，不铺全表 | 全部维度 + 多视角 |
| 输出 | 4 段一页结论 | 标准评审报告 |
| 用时 | 3-5 分钟 | 完整评审 |
| 何时用 | 需求简单/用户只要个判断 | 评审会前自检/重要需求/复杂模块 |

判定铁律：**不确定时往简档降，不往全档升**；先给结论，用户要深再升级。后续可加「标准档」中间档（只增不删）。

## 共享核心（两档共用）

### 严重程度
- **S0 阻塞**：不解决无法评审/设计/开发/测试（核心目标不明、主流程不闭环、核心状态未定义、关键权限缺失、核心规则冲突、范围无法判断、关键依赖未确认、无法确定预期结果）。
- **S1 高风险**：直接开发高返工/线上风险（异常流程缺失、数据口径不一致、消息频率去重缺失、历史数据不明、角色目标冲突、原型与PRD不一致、验收覆盖不完整）。
- **S2 一般**：不阻塞但影响体验/运营/维护（默认排序未定义、反馈不足、字段规则不完整、文档重复不清）。
- **S3 优化**：可执行但有更优（减步骤、优层级、提复用、降扩展成本）。

### 评审视角 → 主看维度（速查）
| 视角 | 主看维度 |
|---|---|
| 业务 | 背景目标、范围、指标验收 |
| 用户 | 用户场景、页面交互、消息通知 |
| 产品 | 流程、对象、规则、状态 |
| 研发 | 字段数据、依赖、异常并发 |
| 测试 | 状态流转、异常边界、验收标准 |
| 设计 | 页面交互 |
| 数据 | 数据字段、指标埋点 |

### 维度（全档全扫；简档只扫「范围/流程/规则/状态/权限/异常/验收/依赖」8核心）
背景目标 / 用户场景 / 范围 / 核心流程 / 核心对象 / 业务规则(对象·前置·触发·判断·动作·系统动作·状态变化·结果·结束·例外) / 状态流转(进入退出·闭环·回退·多规则并发·终态可操作?) / 权限数据范围(看/改·本人到平台·转交·离职调岗·越权漏权) / 数据字段(名称含义·必填默认·来源·枚举·校验·历史·搜索统计·跨系统口径) / 页面交互(入口·默认排序·按钮可用·反馈·空加载失败态·跳转·原型PRD一致) / 消息通知(对象·渠道·时机·频率·去重·重试·点击·关闭) / 异常边界(空数据·重复·并发·状态已变·无权限·删转失效·接口失败·跨天周期·数量上限·历史·新老版本) / 指标埋点 / 验收标准(转用例·正常异常·应该/不应该发生·权限·模糊词)。

### 原则
1. **问题必须有依据**：在哪/为什么/影响什么/严重程度/建议/谁确认。2. **区分问题·建议·待决策**：不把偏好包装成问题。3. **先业务逻辑后页面细节**。4. **优先阻塞研发的**。5. **不替业务和研发决策**（列选项/优缺点/影响/建议决策角色）。6. **结论可执行**。

## 【简档】轻量评审（3-5 分钟）

只拍「能不能进研发」这个板，不做全表。

1. 定对象/版本/重点。2. 扫 8 核心维度，标「已明确/未明确/冲突」。3. 关键验收转 Given/When/Then 看能否测。4. 标 S0/S1。5. 输出简档报告（4 段；「其他发现」只有真多时才补，不凑数）。

**简档输出模板（4 段，3-5 分钟能填完）：**
```markdown
# 评审结论（简档）

## 总体结论
{不建议进入研发 / 补充后重审 / 有条件通过 / 可以进入研发}

## 阻塞项（S0）
- {问题}

## 高风险项（S1）
- {问题}

## 待确认事项
- {问题}（影响范围 + 建议谁确认）

## 其他发现（可选，真多才列）
- {S2/S3/缺失规则/流程状态问题等，可一条一行}
```

**简档示例（对一份 2 页采购订单 PRD）：**
```markdown
# 评审结论（简档）

## 总体结论
有条件通过（补 2 个阻塞后）

## 阻塞项（S0）
- 审批后「退回修改」未定义：退回后单据状态/能否再改/重提流程不明 → 主流程不闭环

## 高风险项（S1）
- 「采购数量」口径：需求里写整数，但现有字段清单兼容小数，两份资料冲突且未核来源

## 待确认事项
- 订单号规则谁定（业务/上游）· 影响编号唯一性校验

## 其他发现
- 无权限/锁定状态下的操作按钮未定义（S2）
```

## 【全档】完整评审

**执行（每步带操作路径）：**
1. **识别对象**：文档类型/版本/阶段/评审范围/用户指定重点——从文档头部、命名、历史版本取。
2. **提取结构**：目标/用户/场景/范围/流程/对象/规则/状态/权限/字段/页面/消息/异常/指标/验收——分段摘，标来源位置。
3. **查内部一致性**：名称↔角色、流程↔状态、页面↔规则、字段↔指标、各章节↔互相、原型↔PRD（A 处说的和 B 处是否冲突）。
4. **查完整性**：每维度标 已明确/部分/未明确/冲突/需决策。
5. **多视角**：业务/用户/产品/研发/测试/数据（涉页面加设计）逐视角过，对着「视角→主看维度」表。
6. **流程状态**：起点→终点→分支→失败处理→闭环；状态进出条件/回退/多规则并发。
7. **规则权限**：每条规则的条件/动作/结果；角色可看可改、数据范围、转交/离职调岗。
8. **补异常**：只补影响业务结果和研发实现的高价值异常，不堆低频。
9. **可验收性**：关键规则转 Given/When/Then，判断能否直接写用例。
10. **定严重度** S0-S3。
11. **形成修改建议**：位置/描述/影响/建议/确认角色/是否阻塞。
12. **输出标准报告** + 结论。

**全档输出 = 标准评审报告。报告头骨架：**
```markdown
# {需求名称}｜需求评审报告

## 1. 评审信息
| 项目 | 内容 |
|---|---|
| 评审对象 | {PRD/需求分析/方案/原型} |
| 文档版本 | {版本} |
| 当前阶段 | {阶段} |
| 评审范围 | {完整评审或重点章节} |
| 评审结论 | {总结论} |

## 2. 结论摘要
### 总体结论
{不建议进入研发 / 补充后重审 / 有条件通过 / 可以进入研发}
### 问题统计
| 等级 | 数量 | 说明 |
|---|---:|---|
| S0 阻塞 | {数量} | … |
| S1 高风险 | {数量} | … |
| S2 一般 | {数量} | … |
| S3 优化 | {数量} | … |
### 优先确认事项
1. {事项}
```

**报告主体 section（接在头后）：**
- 阻塞性问题（逐条 严重程度/位置/描述/影响/建议/角色/是否阻塞）
- 高风险问题（同上）
- 一般问题与优化建议表
- 业务流程/状态流转/权限数据/数据字段/异常边界 评审表
- 验收标准（可直验 / 无法直验给 Given-When-Then 改写）
- 风险与依赖
- 待确认事项表
- 修改任务清单（任务/角色/P0-P2/是否阻塞）
- 最终结论（能否进研发 + 进入前必做 + 可后续优化）

## 常见评审问题速查
目标(问题还是方案？可验证？范围与目标一致?) / 流程(谁发起/哪进/哪结束/失败怎么办/多角色冲突?) / 规则(何时触发/何时不触发/多久一次/重复?/何时失效?) / 状态(有哪些/进出条件/回退?/终态可操作?) / 权限(谁能看改/数据范围/转交离职调岗?) / 数据(来源/必填/默认/历史/口径) / 消息(给谁/何时/几次/去重重试/点击去哪) / 验收(可写用例?覆盖不该发生的?无权限和状态变化?模糊词?)

## 交付前自检（输出前逐项勾）
- [ ] 结论回答了「能不能进研发」这个板？
- [ ] 每个 S0/S1 都有依据（在哪 + 影响）？
- [ ] 修改建议有明确的负责人角色？
- [ ] 区分了 问题(缺失冲突) / 建议(更优) / 待决策(需角色拍)？
- [ ] 优先输出了 S0/S1，S2/S3 没凑数？
- [ ] 没虚构业务规则、保留用户术语？
- [ ] 简档 4 段 / 全档完整报告，两者之一，没混？
- [ ] 是否有真实示例可参考格式（简档见上文示例）？
