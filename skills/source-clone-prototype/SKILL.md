# 搬源码做前端原型

## 何时用
手里有真实系统的源码，要做一个能脱离内网/带 mock 数据也能跑的原型（给评审演示、给研发当基线）。区别于“看截图/设计稿复刻”——那是重画，这里是把原件搬过来。

## 铁律：组件不替换

页面代码原样搬，模板里的组件标签**一个不许换成别的组件库**。

为什么：组件库决定了 DOM 结构、默认尺寸、内部 class 名和样式作用域。把 `nx-search`、`FosButton`、`Tabs` 换成另一个库的 `van-search`、`van-button`、`van-tabs`，等于把原件拆成零件重拼。即使单位换算完全正确，视觉也会全错，而且靠调数值不可收敛。

**判断是否走错了**：换算验证通过了（如设计稿 48px 在窄容器里实测 16.65px、理论 16.67px），但同一元素的字号/圆角/间距两边差很多——那就是组件被换了，不是单位问题。此时不要在数值上继续磨。

## 正确顺序

1. **先验证源码用的组件库能不能装**
   私有组件库走公司内网 registry 验证。验证办法：最小工程装一遍，渲染一个组件，跑一次 build。能装就不要替换。
   验证时顺手确认：包有没有 TypeScript 声明（没有就补 shim）、有没有 postinstall 脚本需审批。
2. **能装 → 页面代码和 scss 原样搬**
   全局样式文件、主题变量、字体、reset 全部一起搬；px 单位照源码写，由 PostCSS 转。
3. **装不上 → 替代要成体系**
   一层薄封装 + 成对的样式覆盖，不能逐组件随手换。这时要向用户说清楚视觉会有差异，不是“已经一致”。

唯一允许保留替换的是原生能力（扫码、剪贴板、保存到相册、拨号、打开外部应用），因为浏览器里没有对应容器，这部分写 mock 层，但组件渲染部分不动。

## 验收：数值相等，不是“接近”

把两边拉到**同一个窄视口**（移动端页面用 375×812）取 computed style 逐项对比。

合格标准是**完全相等**：如头部高度 98.55、搜索框字号 14.5875、Tab 字号 15.6375、Tab 栅高 37.48。两边一致到小数点后两位，才说明组件和样式都是原件。

只看到“大致差不多”不算过；没有真实数据而取不到的区块（如需要登录态才能渲染的卡片），如实标为未验证，不要含糊成“已经一致”。

## 先做样板再繶开

多个页面要改时，先改一个当样板，验收通过再批量。否则一个错的做法会复制到全部页面（尤其组件替换这类错，返工成本最高）。

## 源码能跑就先跑起来

如果源码本身能在本机装上依赖并启动，先跑起来：它是最准的参照物，也是取真实 DOM 和 computed style 的前提，比自己推组件怎么用快得多。

跑不起来或登录态失效也不阻碍——壳层、导航、搜索、Tab 这些静态结极照样能取到；只影响需要数据的卡片和列表，那部分靠源码文件和 scss 对照，并如实标注未验证。

## 常见坑

- **样式覆盖残留**：从替代组件换回原件后，旧组件库的样式覆盖（如 `.van-tabs`、`.van-button` 的固定宽度/尺寸覆盖）必须删干净，否则原件被套一层不适用的约束。
- **fixed 定位跟容器脱节**：原型壳层把页面限宽居中后，页面内 `position: fixed` 的元素会相对浏览器窗口定位，顶部横跨整个窗口。解法是给容器加 `transform: translateZ(0)` 建立包含块，或用绝对定位。
- **窄容器里单位换算**：容器限宽时 `vw` 会按浏览器窗口算而不是容器，得用容器查询单位（`cqw`）并确保容器声明了 `container-type: inline-size`。

## 红线
- 不改源码仓库（只读，用 `git show <branch>:<path>` 取文件，不切分支）。
- 组件替换不默默做，做了要告诉用户视觉会有差异。
- 数值对不上不说“已经一致”。
