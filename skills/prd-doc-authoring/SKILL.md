# 评审PRD 编写工作流

## 定位（用户2026-09定）
评审PRD = **评审用完整档**：把主PRD(规则) + Demo(页面) 合并成一份，**评审人读它就能审、开发按它就能做**，不用切换多份PRD。
- 评审现场：在原型图上打开原型标注逐个讲角标；评审PRD是把现场固化下来，评审后凭它回看（别人/以后看不到原型标注）。
- **自包含交付件，全文零外引**：评审PRD = 唯一交付件，评审人/开发只看这一份就能干活，**不出现任何 TSV / 字段清单详细稿 / 权威源 / 主PRD 引用**。TSV 是内部梳理工具，交付时删净——用户"谁知道你详细稿啊，我要的是这一个PRD评审后就可以去开发了，全部看这一个PRD"。头部声明写自包含口径（"本件为自包含评审档，覆盖全部需求，评审通过后可直接作为开发依据，无需再查其他文档"）。

## 关键治理三铁律
1. **权限按需**：只有需求分析明确区分了"不同角色所看/所操作不同"、或系统未实现RBAC需页面做角色控制时才写权限；否则标注"由运维/运营/RBAC管控"。AI爱硬加权限，默认不加。
2. **大白话全中文**：目录结构全中文，禁令写 In/Out of Scope、SSOT、RBAC 等英文术语；枚举/代码字段值保留英文给研发对照，但描述必须中文。
3. **功能清单=原型标注角标一一对应**：**功能清单的条数 = 原型标注角标数**，一个角标一个功能一条。

## 铁律：页面说明的每条短句必须带序号（2026-11-17 用户反复强调）

页面内容/交互说明/业务规则/场景举例每一段里的每一条短句，前面必须有序号 `1、2、3、`，一条一句，不得并列成不分号的长句。

这条在**任何压缩版里都不许省**：做 wiki 紧凑版（段内并句、减少换行）时，只许把换行去掉，序号必须保留——正确形态是 `【页面内容】1、启用状态列为开关；2、操作列提供查看与编辑。`，错误形态是把序号剥掉只剩 `启用状态列为开关；操作列提供查看与编辑`。

序号风格统一为中文顿号 `1、`，不用 `1)` 也不用 `1.`（两版 wiki 稿与权威源保持一致）。压缩脚本每轮改完都要回读一行验证序号还在。

### 加粗定界符必须合法（2026-11-18 实测踩坑）

`**【页面内容】**` 这种写法，如果 `**` 后面紧跟数字或汉字（如 `**【页面内容】**1、…`），右定界符在 GFM 里不成立：前面是全角【】属标点，后面必须接空白或标点，接 `1` 就失效，星号被当字面输出，表现为「有的行加粗、有的行满屏星号」。

固定写法：**段名加粗后跟一个空格**——`**【页面内容】** 1、启用状态列为开关。`。不推荐用 `<br>` 顶（会把行距拉开）。批量排查：`re.sub(r'\*\*【([^】]+)】\*\*(?=\d)', …)` 数有几处被替换；验收不看源码看渲染，用 marked 渲一遍，`document.body.innerText` 里出现 `**` 就是没改对。

### 配套两条（同一轮的楔子，2026-11-17 用户点出）

- **多用短句**：一条只讲一件事，超过 40 个字就拆成两条，不要把「条件 + 结果 + 例外」塞进一句话。判据：读完一行不需要回头再看第二遍。
- **层级关系明确、多用陈述短句**：只用两层——段名（【页面内容】这种）→ 条目（1、2、3）；条目内不再套子层。确实需要再分时用「1、…（1）…」，最多两层，不能无限嵌套。层级靠段名与序号体现，不靠缩进、不靠加粗。

## 开工前必做（2026-11-17 教训）

**写或改评审 PRD 之前，必须先 `skill_view(prd-doc-authoring)`，不许凭会话上下文手写。** 2026-11-17 那版就是没加载本 skill 凭记忆写的，结果结构与一期标准不一致，md 表格还被改坏（删列时只改表头没改分隔行、删句子时把行尾 ` | |` 一起删导致整表断行）。

改完必跑本 skill 自带的两支脚本，退出码非零不许交付：

```
python3 <skill>/scripts/structure_check.py <源稿.md>
python3 <skill>/scripts/consistency_check.py <源稿.md> --proto <项目>/99-产品原型prototype/src
```

**改表格行或删句子后单独查一次列数**：逐表比对每行 `|` 个数与表头是否一致。

## 章节结构：固定九章，对齐一期 P0（2026-11-17 用户定）

用户原话：「去看下 03-产品设计\私域2.0一期\04-评审PRD\私域2.0一期_P0评审PRD.md，好好看看标准的PRD结构是什么样的」。

| 章 | 内容 | 要点 |
|---:|---|---|
| 1 | 业务背景 | 两到三段：现在具备什么、暴露什么缺口、本版补哪一块 |
| 2 | 业务目标 | 三条以内，写「让谁在什么地方做什么、替代掉什么」 |
| 3 | 需求范围 | 表：序号｜需求块｜菜单路径｜说明；表下补一句哪些是既有能力本版不改造 |
| 4 | 业务场景 | 三到五条 bullet，具体的人做具体的事 |
| 5 | 功能清单 | 按模块分子节；表列固定 `序号｜功能｜功能描述` |
| 6 | 主要流程 | 固定两节：**6.1 系统流程图**、**6.2 业务流程图** |
| 7 | 页面和操作 | 每页一节，五列表格 + 该页字段清单跟在节尾 |
| 8 | 验收标准 | 输入条件→预期结果；仅源稿保留 |
| 9 | 待确认事项 | 表：序号｜事项｜影响｜处理人 |

**「业务规则」不再单独成章**：全部拆进对应页面的【业务规则】段（用户原话「16 节业务规则全归属到页面说明中」）。**「字段清单」也不再单独成章**：跟到所属页面节尾（用户原话「这是标准，以后都是这样，你不要再搞不一样的出来了」）。

**按需**：状态流转、状态机、异常边界——有才写，无则标"不适用"。

## 业务规则（默认不单独成章，2026-11-17 改口径）
- **默认：不设独立规则章**，规则全部拆进第 7 章各页面的【业务规则】段（见上文九章表）。只有当用户明确要求保留独立章时才按下面写。
- 若保留独立章：每张子表表头 `序号 | 什么情况下 | 结果`，序号**每张子表各自从1开始**；编号列写"序号"，不用 R01/R02 这种内部编码。
- 「什么算一条功能」的归属：一条规则如果只是解释某个字段为什么这么算，它就是页面规则，不升成功能点；反过来能落到一句备注的说明（如「频控由短信中心负责」）只进备注列，不占功能清单行。

## 页面和操作（五列表格，核心）
每页格式：`| 序号 | 操作路径/功能点 | 原型页面 | 页面说明 | 备注 |`
- 表头五列：**序号 | 操作路径/功能点 | 原型页面 | 页面说明 | 备注**。序号每页独立从1开始(列表1..9、新增1..6、详情1..11)，与二章功能清单序号对应。
- **序号用"序号"字样，不用"#"**——用户明确"列头要改成序号，不是#号代替"。功能清单章(序号|功能|**功能描述**)首列同样是"序号"不是"#"；**第三列列名写「功能描述」，禁写「一句话说清」**（那是写作要求不是列名，用户纠正过）；**不再设「本期」列**（2026-11-17 用户：「16 行全是是，这列没有信息量，删掉」）。**第三列列名写「功能描述」，禁写「一句话说清」**——那是描述写作要求，不是列名，用户纠正过。
- 表头列名逐字对齐：第2列操作路径/功能点、第3列"原型页面"(不是"截图")、第4列"页面说明"(不是"说明")——用户对列名敏感。
- **操作路径必须具体到功能点**：`线索管理/线索列表-状态页签`、`线索管理/线索列表-新建与导入`——不能都是粗页面名。
- 原型页面 = **整页截屏 + 红虚线框圈选该功能点所在区域**（一功能一行一图，26角标=26张整页向量红框图）。不是区域小图！
- 页面说明 = 该角标对应原型标注块内容搬运(逐字不脑补)。
- 备注列留空，评审遇待确认时手填。
- **不出现"功能清单（F1-F6 共 6 个角标）："这类带角标计数的副标题**——直接进表格（"功能清单"正文章节标题可留，"（x角标）"计数副标题删）。
- **不要在页面顶部另放一张独立整页大图**——它和表格里 L1/F1/D1 行的整页红框图重复(曾被用户指出"大页面和下面表格重复")。直接进表格，每行自带整页红框图。
- 页面级角标(如页面/权限/本页规则)截整页，弹窗类角标用弹窗截图。

## 流程图与 PRD 套件同源（2026-11-17 用户定，禁自己重画）

用户原话：「系统流程图和 prd 套件里的系统流程图不一样」「业务流程图和之前的又不一样了，应该有配置触发型事件和定时型事件这两个分支」。

- **6.1 系统流程图** 直接取 `01-PRD套件/<版本>_系统流程图.md` 那张时序图原样贴入。套件那张是完整的：提需求建表、配行为、计划新建选触发方式、`alt 【定时型】/【触发型】` 两分支、下单发两条路共用。
- **参与者超过 5 个就拆图**（2026-11-17 实测）：一张时序图塞 7 个参与方，在 Cursor 窄预览里文本全部叠在一起，折行救不回来。按参与方边界拆成多张，每张≤ 5 个，`6.1` 下用粗体图题分开（图一用户行为配置与建表 / 图二触达计划配置与圈人 / 图三下发与结果回传），不重新编章节号。
- **图里只放交互骨架，规则解释不进 Note**：`Note over` 里不写「下游为空时提示什么」这类长句，一句 Note 只给阶段名（如「② 配置行为」）；所有细则回到该页的【业务规则】段——图里每一条在正文都得有依据。
- **6.2 业务流程图** 直接取 `01-PRD套件/<版本>_业务流程推演.md` 那张 flowchart，按「维护层／使用层／执行层」三段展开，使用层与执行层各自要有定时型和触发型两分支。
- 与套件不一致等于错。改流程先改套件再贴回评审PRD；参照源本身错就先改参照源。
- **同源不等于照搬**：套件自己也可能违反 mermaid 硬规则，贴进评审 PRD 前必须扫一遍（Cursor 预览窄，文字长就会压线）：`rect rgb` 着色块必删（连它的 end）、`actor` 改 `participant`、单行消息超 20 汉字用 `<br/>` 折行、连线标签写成 `-->|"文字"|` 带引号、参与者超五个考虑合并或拆图。改完按 420px 与 700px 各渲一次，交视觉模型核「有没有文字压线/相糊」。细规见 skill `mermaid-diagram-authoring`。

## 图的形态与流程图硬规则

**flowchart 首尾必须有开始与结束节点，且开始节点必须在整图最顶端（2026-10-31 用户当场纠正）。**

- 缺开始/结束 = 流程没头没尾，评审会问「从哪里进来、到哪里结束」。
- **开始节点不能在途中**：Mermaid 按连线关系自动布局，把 `STRT(["开始"]) --> 第一个节点` 写在 subgraph **内部**时，它会被自动排到中途（实测跑到判断节点左下方）。正确写法：开始节点写在 `flowchart TD` 之后第一行、**subgraph 外面**，再指向第一个业务节点；结束节点同样写在所有 subgraph 外面、末尾。
- 形状用体育场形 `(["开始"])` / `(["结束"])`（左右半圆的胶囊/椭圆），**不用 `(("开始"))`圆形**；中间业务节点保持方角 `[...]`，评审才分得清出入口。
- 写完不靠想象验收：让用户或 agent 把图渲染出来看一眼开始节点是否真在顶部；Mermaid 自动布局会因回连线（如「不满足则回到提需求」）改变节点位置，出现偏离就把回连线也移到 subgraph 外重排。

**流程图不做清单（踩过才知道，别再试）**
- 不用 `rect rgb(...)` 着色块：旧渲染器不认，整块被当文字输出。
- 不用 `actor`：旧渲染把 actor 名称和第一条消息文字叠在一起，参与方统一写 `participant`。
- 不用短横调表格列宽：Markdown 列宽不可控，纯浪费轮次（曾改三轮 dash 数才承认）。
- 不承诺泳道等高、不做矩阵泳道：subgraph 不能等高，Mermaid 表达不了。

**流程图必做验收（生成后逐条核）**
1. 开始/结束节点存在，且开始节点渲染在整图最顶端。
2. 渲染器能正常解析，无语法被当文字输出（重点查有没有残留的着色块/actor）。
3. 节点文字与正文口径一致（数字、状态名、判断条件不能和图外文字打架）。

## 多形态共存时必须给每种形态独立落位（2026-11-22 教训）

触发型/定时型这类一个页面多种形态的设计，最容易写成「以其中一种为纲、另一种在功能清单里带一句」。用户的判据很直接：**打开评审 PRD 能不能找到另一种形态的页面说明、字段清单、验收标准**——找不到就是漏，哪怕功能清单里有那一行。

做法：
- 「页面和操作」按**共用部分 + 各形态专属**拆节：共用节放触发类型选择、受众筛选/人群筛选这类两态都有的块；专属节按形态各占一节，互不夹杂。章内编号顺延，不要出现两节都叫同一个号。
- 「功能清单」每种形态至少各有自己的一条主功能（如定时型-定时下发、定时型-人群筛选），不要只写「两卡片单选」就算覆盖。
- 「验收标准」每个形态各一节，写形态独有的输入条件（定时型的发送时间必填与时间窗口、人群筛选的组数上限与默认预置组）。
- 「需求范围」表里形态各占一行，说明写清该形态的圈人主体是什么。
- 截图：共用截图 + 每种形态至少一张能体现其专属配置的图，红虚线只圈该形态的专属功能区。

## 截图规范
- **截图前先核目标交互能不能被真实触发（2026-10-30 实测踩坑）**：脚本能跑、图能出，
  不代表图里有所要表达的状态。mock 数据不支撑时截出来的是「空验证」——实测要求交「好友标签超过两个显示 +N」的图，mock 里每行最多两个标签，图出来了但那行只是两个标签、没有 +N，agent 自检写「22/22 图存在且有红框」，验收时发现整张图是假的。
  固定前置动作：逐条问「这个交互要出现在图上，需要什么数据前提」→ 到 mock 里核数据存不存在 → 不存在就**先补 mock 数据再截**，补不了就在交付里写「该交互 mock 不支撑，图待补」，不许交一张看不出该交互的图充数。
  - 验收时看图上有没有那个元素，不看「图文件存在」这个事实。
- **重截图后不能靠 git 看「哪些图受影响」（2026-10-31 实测）**：原型顶栏时钟是 `new Date()` 实时渲染（`components/layout/Shell.tsx`），重跑截图整批图字节都会变，git status 会显示全部 22 张改动。判定影响面只能看样式改动落在哪些页面（diff 文件→路由→该页的图），并接受「整批重出、整批提交」，不要试图只重出几张。
- **Mac 跑截图脚本的依赖坑**：需 playwright + pillow，别装系统 Python，用独立 venv（如 `~/venvs/prd-shots`）；脚本已写死 `/Applications/Google Chrome.app` 路径，所以不需要再跑 `playwright install chromium`。
- **引用图必须开图核画面，文件名和 mtime 都不算证据**：PRD 里挂着名叫「XX失败重试」的图，实际画面可能是两条「生成中」，既没有失败态也没有重试按钮——文件名只说明当时想截什么，不说明图里真有什么；mtime 新也不等于图对。核图固定动作：逐张交给视觉模型问「这张图里能不能看到 XX 元素」，尤其是失败态/空态/置灰/多态这类「看不见就等于没做」的界面。发现不符就用「新文件名另存新图」替换引用（带日期后缀，旧图不覆写），并在图列的引用里同步改成新文件名。
- **准确：截自真实可运行原型，不脑补；图上内容与说明一致。
- 全面：主页面+关键交互(弹窗/Toast/二次确认/批量/空数据)都要截。
- 文件名中文+对应功能，如 `线索列表页-L2-状态页签与线索池视图.png`。
- **整页 + 单角标红虚线框**（用户强调不展示其他角标框）。
- 批量截图分工见 `references/antigravity-ego-screenshot.md`（反重力+ego lite 备用方案；主路径 Playwright+Pillow 本机自动画框省额度）。

## 页面说明固定五段，逐句 `<br>` 分行（2026-11-17 用户定）

用户原话：「页面说明要标题和短句说明要换行 `<br>`，层级关系明确，多用陈述短句」。

每行页面说明固定五段，段与段之间用**一个** `<br>`，段名加粗 `**【页面内容】**`，段内每条用 `<br>`：

```
**【页面内容】**<br>1) …<br>2) …<br>**【交互说明】**<br>1) …<br>**【业务规则】**<br>1) …<br>**【场景举例】**<br>1) …<br>**【待确认】**<br>1) …（@____）
```

**段间不要写 `<br><br>`**（2026-11-17 用户实测）：粘到 Confluence / 语雀等 wiki 后，`<br><br>` 是两次换行，再叠上平台自己对单元格内容的段间距，实际渲染出三四行空白，一篇下来满屏空行。改成单 `<br>` + 段名加粗后，层级还在、空白没了。

- **陈述短句**，一句只说一件事；不写「该功能主要通过……实现」这类叙述句。
- **交付到 wiki 后必看空行**：粘一行就抬眼看，若段间空白明显多于段内，改用「紧凑版」口径。

### wiki 粘贴专用紧凑版（2026-11-17 实测有效）

目标平台把单元格里每个 `<br>` 当**独立段落**，段间距由平台定，所以少写换行才有效，光把 `<br><br>` 降成 `<br>` 只是从两倍空变成空一段。

生成规则：
1. 段内多条 `1) 2) 3)` 并成一句，用 `；` 连接，只留最后一个句号。
2. 段名写成纯文本 `【页面内容】`，**不要加 `**` 加粗**——部分 wiki 不解析 Markdown 粗体，会出现满屏星号。
3. 段与段之间一个 `<br>`，每个单元格总共只留 4 处。
4. **重建表格行时 `|` 前后必须留空格**：写成 `| 单元格 |`，不能写成 `|单元格|`。实测漏空格会让格内**第一个** `**【xx】**` 不被解析、显示成字面星号，后面的却正常，表现为「部分加粗失效」。
5. 成品单独存为 `<名>-wiki紧凑版.md`，不覆盖权威源（权威源保留完整分段 + 加粗，供 Cursor/GitHub 看）。

粘完必须抽一行回截图核：段名是否正常、有没有字面星号、段间空白能否接受。
- **业务规则从这里来**：原先独立成章的规则表拆成本行自己的【业务规则】条目，一条一句，序号在本段内从 1 起。
- **【场景举例】必须有**，用具体的人和具体动作写，如「运营要找预售相关的行为，在名称框输入『预售』即可筛出」。
- **【待确认】有内容才写**，没有整段不出现，不写占位。

## 生成整页红框图的可行做法（Playwright+Pillow）
优先用 `scripts/capture_orm.py` 脚本跑；以下为原理与坑，脚本卡壳时排查用：
- **红框坐标必须截图前现量，不能照上一张图的坐标推算**（实测踩坑）：改过视口宽度、抽屉/弹窗是否展开、侧栏折叠，布局就变了，照旧坐标画出来的框会圈到旁边的表格列上，框和内容对不上而画面里看不出来。固定四步：① 先钉死视口（`Emulation.setDeviceMetricsOverride`，宽高固定，如 1600×1000）② 截图前一刻 `document.querySelector('<锚点>').getBoundingClientRect()` 现取 x/y/w/h ③ 用该值画框，且 `x2 = min(W-6, x+w+6)`——超出画布的部分会被裁掉，出现半框 ④ **截完把 PNG 交给视觉模型问一句「红框是否完整圈住 XX」**，它能把「框圈错位置」直接指出来；只靠坐标数字自查发现不了这类错。
- **要展示的状态得先造出来**：失败态、已删除态这类非常规状态，先往 localStorage / mock 里种一条对应该状态的数据再截图，否则截出来永远是最常见的那个状态（要求「失败重试」的图，图里两条任务全是「生成中」）。
- Playwright 打开页面，对每个角标 `document.querySelector("[data-anno='xxx']")` 拿 bounding box（含 scrollY 偏移）。
- 用 Pillow 在整页图上画红虚线矩形圈住该角标区域（dash=8,gap=4,width=3,padding=6）。每角标一张=底图同(同页)、框位不同。
- 表格高超出视口时整页图=首屏900px(列表是滚动容器，full_page不扩展)；框截到视口底即可。
- 弹窗类角标需触发弹窗后截（如点"转为正式客户"出弹窗——按钮文字可能是"转为正式客户"不是"转客户"）。
- **弹窗触发受业务状态锁定**（商家实测踩坑）：商机合同签订态/赢单/输单终态会锁死推进等动作，弹窗不出现（如"关联合同签署中,商机不可操作"）。此时先识别是"该商机本来就不能触发"（业务正确，换能触发的商机）还是"需要绕过"（用无关联记录、非终态的商机/路由触发）。终态或已关联业务记录不能硬触发——不要靠反复点无用功，改用状态满足条件的对象/页面。
- **双视图/多态页**：页面有看板/列表等视图切换时，不同锚点只在其对应视图渲染（商机看板态取不到列表页签/表格锚点为null）。截图前必须切换到目标视图再取锚点；锚点 null 先判断"是否需切换视图/交互/弹窗"再决定，不直接判定失败。

## 文档头部与修改记录
- **头部分两块**：版本行 + `## 修改记录` 表格。修改记录列 `日期 | 版本 | 修改人 | 修改内容`，在文档最上面（版本行正下方）。
- **命名"修改记录"，不叫"变更台账"**——台账是财务/交易系统术语，评审PRD用它指代文档自身修订史是误称，用户纠正过。
- 修改记录定位 = **这份文档的更新操作记录**，只记"版本/改了什么"。不要把"回写目标/回写完成"这类回写skill字段混进来——那是回写权威源做的事，与文档修订史职责分开。
- **不要擅自往版本记录里加行或改版本号**：版本记录由用户自己维护。改完只在一轮对话里说清「改了哪一节、改了什么」，让他决定要不要记一笔；擅自加行会被当场叫停（「你不要改版本记录」）。同理，用户说「只改这一节」时，改完必须验 `git diff --stat` 确实只 1 文件 1 行，不能顺手把相邻条目、版本号、发布版一起动。

- 需要对齐的 = 功能性口径（有几项、能不能勾、置不置灰、必填与否）——这些必须一致。
- 不需要对齐的 = 展示层措辞与英文标识（英文前缀、字段英文名、枚举英文码）——PRD 写中文即可。
- 发现这类差异时**不要主动提议改原型**，记下来即可；一提议就变成一轮无谓改码，还会跟本地 Cursor 的改动撞车。

## 发布版体积硬上限 5MB（2026-11-02 用户明令）

用户原话：「怎么文件又超5mb了啊，能不能长记性啊」「不能超过5MB」。发布版（base64 内嵌图）**不得超过 5MB**，超过则不得交付。实际控制线定在 3MB：一到 3MB 就压图，不要等撑到 5MB 再救。

### 体积暴涨的根因

截图出来的 PNG 未压缩。UI 截图界面区大片纯色 + 文字，未压缩时单张 150-240KB，20 多张合计 3.8MB，base64 后再膨胀 1.33 倍，发布版直接冲 5MB。且每次重截都会重新生成未压缩图。

### 固定动作

1. **截图脚本保存时就压**（已落在 `09-脚本工具/capture_prd_redbox_private20.py` 的 `capture()` 里）：
   ```python
   quantized = img.convert("RGB").convert("P", palette=Image.ADAPTIVE, colors=256)
   quantized.save(out, optimize=True, compress_level=9)
   ```
   UI 截图转 256 色调色板体积降约 60%，文字与红虚线框不受影响（实测过放大可读）。新建同类截图脚本必须内置这一步，不要等交付前才压。

2. **已有图批量补压**（脚本没内置压缩时，或从别人那接手一批图）：
   ```python
   for p in glob.glob('images/*.png'):
       im = Image.open(p).convert('RGB')
       im.convert('P', palette=Image.ADAPTIVE, colors=256).save(p, optimize=True, compress_level=9)
   ```

3. **压完出发布版要带 `--allow-drop`**：deliver.py 默认把「比上一版缩小超 10%」判为「疑似图片丢失」并阻断。压图必然触发这条，用 `--allow-drop 70` 显式声明这是有意的体积优化，而不是丢图。
   ```
   python3 scripts/deliver.py <源稿.md> --prev <发布版.md> --allow-drop 70
   ```
   注意区分：体积**降**可能是压图，也可能是丢图——传 --allow-drop 前先确认 `① base64 图数 vs 引用数` 那一项是 PASS，图数对得上才敢放行。

4. **交付前必看体积**：`ls -lh <发布版>.md`。超过 3MB 回头压图，不要直接发出去让人导入语雀卡半天。

## 小改直接改源稿，别每改动就跑全套（2026-11-02 用户强烈纠正）

用户原话：「有时候手改一下就行了，不需要截图的时候，非要用 skill 跑一遍干嘛」「每一次都在浪费 token」。skill 的三连（截图 → deliver → 自检）是**交付动作**，不是**编辑动作**。

按改动类型决定动作，不要一律全套：

| 改了什么 | 跑什么 |
|---|---|
| 只改文字措辞、补一段说明、改一条口径、改版本记录 | 直接改源稿 + commit。不跑 deliver，不截图 |
| 加了/删了章节、批量改表格、重排序号 | 跑 structure_check |
| 页面形态变了（新增控件/列/页签/弹窗） | 重截该页的图 + 改图引用 |
| 要交付/发给人看 | 才跑 deliver 生成发布版（且只在图已定稿时跑） |

自检脚本的价值在「一次跑出几百行长表里看不见的错」，不在「每改一行就验一遍」。小改用 read_file / patch 看准了直接改。

## 发布版只在原型定稿后生成一次（2026-11-02 用户定）

源稿（`xxx_P0评审PRD.md`）可以随时改、随时提交；但 `xxx-发布版.md`（base64 内嵌图）**不要跟着每次改稿就重跑**。

为什么：发布版里装的是截图。原型没改完、图没重截，跑 deliver 只会产出一份「新文字 + 旧图」的中间态，看是能看，交付出去就是图文不一致。用户原话：「是不是应该等我 push 上去后再搞自动发版？原型图都没更新上去呢」。

正确节奏：
1. 改稿阶段只改源稿 + 跑 structure_check / consistency_check，发布版不动。
2. 等原型改动 push 到位（或图确认不需重截）后再做一次：重截 → deliver → 核图文一致 → 提交。
3. 交付前必须看一眼发布版里的图是不是当前形态，不能只凭 deliver 的「三项自检 PASS」当验收——自检只看图数对不对、路径残留、字节骤降，看不出图是旧的。

## 产品视角 ≠ 技术视角（2026-11-11 用户定，写作第一判据）

源码取证是用来**倒推内销业务规则**的（他们这么做→推出业务逻辑），但反过来**不能拿技术去定义外销产品怎么实现**。产品文档只回答「要做什么功能」，「怎么实现」是技术侧的问题——写死实现路径既干扰研发，也可能挡掉更好的方案。用户原话：「不要干扰人家，也不要忘了我的视角是产品设计」。

- **禁写**：数据表名、接口名、模块/代码路径、代码分支、「事件分片扫描」「调度框架沿用」这类实现手段，以及「结构对齐 V5.2 / V5.3 旧口径」这类内部文档版本号引用。
- **数据源一律写业务名词**：写「数据源为用户行为管理中的用户行为数据」，不写 `smp_user_event` / `eventId` / 「非前端枚举」。
- **技术事实只存在于我方判断层与开发指令**：表结构、字段、代码行号用于出开发指令和排期，不进功能清单/PRD 正文。
- **自检问句**：这句研发看完，会不会被限定成唯一做法？会 → 删掉，只留业务行为。
- 同一份文档里批量检查，不要只改被点出的那一条（实际出过：删了第 17 条的技术表述，第 19 条的文档版本引用和「异步任务」还在原地）。
