# 评审PRD 编写工作流

## 定位（用户2026-09定）
评审PRD = **评审用完整档**：把主PRD(规则) + Demo(页面) 合并成一份，**评审人读它就能审、开发按它就能做**，不用切换多份PRD。
- 评审现场：在原型图上打开原型标注逐个讲角标；评审PRD是把现场固化下来，评审后凭它回看（别人/以后看不到原型标注）。
- **自包含交付件，全文零外引**：评审PRD = 唯一交付件，评审人/开发只看这一份就能干活，**不出现任何 TSV / 字段清单详细稿 / 权威源 / 主PRD 引用**。TSV 是内部梳理工具，交付时删净——用户"谁知道你详细稿啊，我要的是这一个PRD评审后就可以去开发了，全部看这一个PRD"。头部声明写自包含口径（"本件为自包含评审档，覆盖全部需求，评审通过后可直接作为开发依据，无需再查其他文档"）。

## 关键治理三铁律
1. **权限按需**：只有需求分析明确区分了"不同角色所看/所操作不同"、或系统未实现RBAC需页面做角色控制时才写权限；否则标注"由运维/运营/RBAC管控"。AI爱硬加权限，默认不加。
2. **大白话全中文**：目录结构全中文，禁令写 In/Out of Scope、SSOT、RBAC 等英文术语；枚举/代码字段值保留英文给研发对照，但描述必须中文。
3. **功能清单=原型标注角标一一对应**：**功能清单的条数 = 原型标注角标数**，一个角标一个功能一条。

## 章节结构（必有 + 按需）
**必有**：业务总览(做/不做)｜功能清单(序号+功能+**功能描述**+本期?)｜主要流程(含Mermaid图)｜状态流转(单据有才写)｜业务规则(序号|什么情况下|结果)｜页面和操作(每页功能清单表)｜字段清单｜验收标准(输入条件→预期结果；**仅源稿保留，发布版不写**)。
**按需**：权限(见治理)、状态机、异常边界——有才写，无则标"不适用"。

## 业务规则表（序号跨表重置）
- 业务规则每张子表(5.1/5.2/…)表头 `序号 | 什么情况下 | 结果`，序号**每张子表各自从1开始，跨表不接续**——用户明确"跨表格后要重置序号从1开始"。
- 编号列写"序号"，规则项写普通数字(1、2、3…)，不用 R01/R02 这种内部编码（和功能清单/页面表一致，全文档无"编号"列头、无字母前缀编码）。

## 页面和操作（五列表格，核心）
每页格式：`| 序号 | 操作路径/功能点 | 原型页面 | 页面说明 | 备注 |`
- 表头五列：**序号 | 操作路径/功能点 | 原型页面 | 页面说明 | 备注**。序号每页独立从1开始(列表1..9、新增1..6、详情1..11)，与二章功能清单序号对应。
- **序号用"序号"字样，不用"#"**——用户明确"列头要改成序号，不是#号代替"。功能清单二章(序号|功能|**功能描述**|本期?)首列同样是"序号"不是"#"。**第三列列名写「功能描述」，禁写「一句话说清」**——那是描述写作要求，不是列名，用户纠正过。
- 表头列名逐字对齐：第2列操作路径/功能点、第3列"原型页面"(不是"截图")、第4列"页面说明"(不是"说明")——用户对列名敏感。
- **操作路径必须具体到功能点**：`线索管理/线索列表-状态页签`、`线索管理/线索列表-新建与导入`——不能都是粗页面名。
- 原型页面 = **整页截屏 + 红虚线框圈选该功能点所在区域**（一功能一行一图，26角标=26张整页向量红框图）。不是区域小图！
- 页面说明 = 该角标对应原型标注块内容搬运(逐字不脑补)。
- 备注列留空，评审遇待确认时手填。
- **不出现"功能清单（F1-F6 共 6 个角标）："这类带角标计数的副标题**——直接进表格（"功能清单"正文章节标题可留，"（x角标）"计数副标题删）。
- **不要在页面顶部另放一张独立整页大图**——它和表格里 L1/F1/D1 行的整页红框图重复(曾被用户指出"大页面和下面表格重复")。直接进表格，每行自带整页红框图。
- 页面级角标(如页面/权限/本页规则)截整页，弹窗类角标用弹窗截图。

## 图的形态与流程图硬规则

**flowchart 首尾必须有开始与结束节点，且开始节点必须在整图最顶端（2026-10-31 用户当场纠正）。**

- 缺开始/结束 = 流程没头没尾，评审会问「从哪里进来、到哪里结束」。
- **开始节点不能在途中**：Mermaid 按连线关系自动布局，把 `STRT(["开始"]) --> 第一个节点` 写在 subgraph **内部**时，它会被自动排到中途（实测跑到判断节点左下方）。正确写法：开始节点写在 `flowchart TD` 之后第一行、**subgraph 外面**，再指向第一个业务节点；结束节点同样写在所有 subgraph 外面、末尾。
- 形状用体育场形 `(["开始"])` / `(["结束"])`（左右半圆的胶囊/椭圆），**不用 `(("开始"))`圆形**；中间业务节点保持方角 `[...]`，评审才分得清出入口。
- 写完不靠想象验收：让用户或 agent 把图渲染出来看一眼开始节点是否真在顶部；Mermaid 自动布局会因回连线（如「不满足则回到提需求」）改变节点位置，出现偏离就把回连线也移到 subgraph 外重排。

**流程图不做清单（踩过才知道，别再试）**
- 不用 `rect rgb(...)` 着色块：旧渲染器不认，整块被当文字输出。
- 不用 `actor`：旧渲染把 actor 名称和第一条消息文字叠在一起，参与方统一写 `participant`。
- 不用短横调表格列宽：Markdown 列宽不可控，纯浪费轮次（曾改三轮 dash 数才承认）。
- 不承诺泳道等高、不做矩阵泳道：subgraph 不能等高，Mermaid 表达不了。

**流程图必做验收（生成后逐条核）**
1. 开始/结束节点存在，且开始节点渲染在整图最顶端。
2. 渲染器能正常解析，无语法被当文字输出（重点查有没有残留的着色块/actor）。
3. 节点文字与正文口径一致（数字、状态名、判断条件不能和图外文字打架）。

## 截图规范
- **截图前先核目标交互能不能被真实触发（2026-10-30 实测踩坑）**：脚本能跑、图能出，
  不代表图里有所要表达的状态。mock 数据不支撑时截出来的是「空验证」——实测要求交「好友标签超过两个显示 +N」的图，mock 里每行最多两个标签，图出来了但那行只是两个标签、没有 +N，agent 自检写「22/22 图存在且有红框」，验收时发现整张图是假的。
  固定前置动作：逐条问「这个交互要出现在图上，需要什么数据前提」→ 到 mock 里核数据存不存在 → 不存在就**先补 mock 数据再截**，补不了就在交付里写「该交互 mock 不支撑，图待补」，不许交一张看不出该交互的图充数。
  - 验收时看图上有没有那个元素，不看「图文件存在」这个事实。
- **重截图后不能靠 git 看「哪些图受影响」（2026-10-31 实测）**：原型顶栏时钟是 `new Date()` 实时渲染（`components/layout/Shell.tsx`），重跑截图整批图字节都会变，git status 会显示全部 22 张改动。判定影响面只能看样式改动落在哪些页面（diff 文件→路由→该页的图），并接受「整批重出、整批提交」，不要试图只重出几张。
- **Mac 跑截图脚本的依赖坑**：需 playwright + pillow，别装系统 Python，用独立 venv（如 `~/venvs/prd-shots`）；脚本已写死 `/Applications/Google Chrome.app` 路径，所以不需要再跑 `playwright install chromium`。
- 准确：截自真实可运行原型，不脑补；图上内容与说明一致。
- 全面：主页面+关键交互(弹窗/Toast/二次确认/批量/空数据)都要截。
- 文件名中文+对应功能，如 `线索列表页-L2-状态页签与线索池视图.png`。
- **整页 + 单角标红虚线框**（用户强调不展示其他角标框）。
- 批量截图分工见 `references/antigravity-ego-screenshot.md`（反重力+ego lite 备用方案；主路径 Playwright+Pillow 本机自动画框省额度）。

## 字段清单（六列，标题标页面归属）
- 标题必须标明页面归属：`**线索列表页-字段清单**` / `**线索新增/编辑页-字段清单**` / `**线索详情页-字段清单**`——不写笼统"字段清单（列表展示关键字…）"，评审人一眼知是哪页。
- 六列：`字段名称 | 填写格式 | 是否必填 | 字段来源 | 能不能改 | 字段说明`。
  - 字段来源 = 用户手输/用户选择/系统生成/系统计算（用户明确"是手输还是系统生成"）。
  - 填写格式 = 输入约束，如"文本，限100字符""11位数字"；字段说明 = 补充约束，如"与邮箱至少填一个；全局去重"。
- **值全部取自字段权威源**（字段清单详细稿，**TSV 或 md 均可**——命令行字段清单常是 md，不要只认 .tsv，曾因 skill 写死 .tsv 而误判商机无权威源）——评审PRD只搬运/转译，不脑补不造数。措辞可轻度转译(如TSV"文本,上限100"→"文本，限100字符")，语义必须一致，不加新字段/新规则。md 字段清单的列(字段名称|字段来源|取值说明|必填性|新增页|编辑页|字段说明)可直接映射六列。
- **只列业务可见字段，剔除英文技术字段**——评审PRD是给人看的，`crmCustomerId/erpCustomerId/customerSnapshotVersion/customerSnapshotSyncTime/erpProductId/unitPriceSnapshot` 这类跨系统技术标识符**不单独成行**（用户红框指出"怎么还有英文字段名称"看不懂）。技术细节收进所属业务字段的"字段说明"里隐含交代（如"关联客户"说明写"保存客户标识与快照版本(含CRM和ERP双标识)，不以名称作关联键"）。字段表全程不出现英文小写字段名。

## **发布版不写「验收标准」章节**（2026-11-09 用户定）

即使他临时要求生成发布版，**发布版里不要出现验收标准章节**。源稿里若有验收标准表，生成发布版时删掉。用户原话：「后面发布版的不需要写验收标准这个章节」。

口径补充（同日补充）：**验收标准本来是测试的活，产品侧不再新写**。所以：源稿里已存在的验收标准表保留不动，后续不新增条目；发布版一律不带。

**验收标准章开头必须加用途声明**（防止审计拿「发布版没这一章」报不一致、白烧审计 token）：

> 本节用途说明：本章仅用于产品侧自测与验收核对，不作为评审范围，也不属于开发交付物；发布版不含本章。文档间若出现「发布版缺验收标准」的差异，属于既定口径，不是遗漏。
- **交付前固定三连：`structure_check.py` → `consistency_check.py` → `deliver.py`**，前两个退出码非零不许交付。分工：
  - `structure_check.py` 管**形态**：【字段说明】残留、页面说明缺段、版本号重复。这些是长表里肉眼看不见、每次都靠人擦屁股的错（2026-11-02 一次扫出 15 处残留 + 21 行缺待确认 + V3.2 重号）。
  - `consistency_check.py` 管**数字口径**：输出全文「数字+量词」清单与原型硬上限，**判定归人工**，必看五类主题（追加上限的组/条/个是否同义、字符长度、列数与筛选个数、页签步骤个数、时间数字）。
  - `deliver.py` 管**机器交付**：旧口径扫描、图引用核对、重生成发布版、三项自检。
  ```
  python3 <skill>/scripts/structure_check.py <源稿.md>
  python3 <skill>/scripts/consistency_check.py <源稿.md> --proto <项目>/99-产品原型prototype/src
  python3 <skill>/scripts/deliver.py <源稿.md> --prev <上一版发布版.md>
  ```
- **页面说明段结构硬规则**：主行必须有【页面内容】【交互说明】【业务规则】三段；带 `-1/-2` 后缀的细分行可省【业务规则】。**【字段说明】段一律不写**，字段唯一真源是字段清单 TSV。**【待确认】段有内容才写，没有就整段不出现**——不许写「当前无待确认项」这类占位（用户 2026-11-02 明令：没值就别展示，没意义）。
- **表格一律带序号列**：修改记录、需求范围、功能清单、字段清单、验收标准、待确认，**每张表第一列都是「序号」且右对齐**（`|---:|`），序号在表内从 1 开始、跨表重置。用户 2026-11-02：「表格都要加序号，字段清单也是，标准点」。structure_check 会把没有序号列的表报出来。
- **时间字段默认精确到秒**：首次添加时间、最新添加时间、数据同步时间这类展示型时间一律写 `YYYY-MM-DD HH:mm:ss`，不写到分；只有区间筛选器的输入格式可到分。改则需同时改 mock 数据与展示层格式化，不能只改一处。

## 可执行脚本（本地 agent 照跑，别手写逻辑）

**截图不能推翻已定口径（2026-11-02 翻车）**：用户发参考截图时，图能证明的只是交互形态（控件长什么样、能不能点、置灰不置灰），**不能用来改已拍板的枚举范围**。实测：一张带 DELAY/BEFORE/AT_ONCE 三个勾选框的图，我据此把「两项触达时机」改成三项，而用户只是要确认「新建可勾选、编辑置灰」。正确做法：先查历史版本记录与 `references/legacy-terms.txt`（「三项触达时机」在里面就是已废弃口径），有冲突先问一句「本期口径是两项还是三项」，不自己改枚举。
评审PRD不能靠 agent 每回现写截图/提取逻辑（易卡壳或伪造）。skill 自带两个脚本，agent 只需填参数启动：
- **`scripts/capture_orm.py`**：批量截图整页红框图。读 annotation.config.json 自动构建任务，Playwright 打开线上原型拿 data-anno 锚点坐标 + Pillow 画红虚线框，逐角标出图。用法：`python3 scripts/capture_orm.py --config <项目>/annotations/annotation.config.json --out-dir images --base-url https://pmlophy.com/project/<项目>/# --name-prefix '商机列表页-'`。页面级角标(type=page/page-global)自动截整页无框。
- **`scripts/extract_body.py`**：从标注文件提取页面说明。自动剔除来源行/表格行/待确认段，输出连贯中文说明供评审PRD"页面说明"列。用法：`python3 scripts/extract_body.py annotations/pages/<页>.md...`。
- **`scripts/deliver.py`**：一键交付。扫旧口径（关键词表 `references/legacy-terms.txt`，项目可在 PRD 同目录放 `.prd-legacy-terms.txt` 覆盖）→ 核图引用与 images 目录一一对应 → 调 embed_images 重生成发布版 → 跑三项自检（base64 图数=引用数、相对路径残留=0、字节数不骤降）。修改记录章节内的命中只算历史、不阻断。
- **`scripts/embed_images.py`**：base64 内嵌生成发布版。

## 生成整页红框图的可行做法（Playwright+Pillow）
优先用 `scripts/capture_orm.py` 脚本跑；以下为原理与坑，脚本卡壳时排查用：
- Playwright 打开页面，对每个角标 `document.querySelector("[data-anno='xxx']")` 拿 bounding box（含 scrollY 偏移）。
- 用 Pillow 在整页图上画红虚线矩形圈住该角标区域（dash=8,gap=4,width=3,padding=6）。每角标一张=底图同(同页)、框位不同。
- 表格高超出视口时整页图=首屏900px(列表是滚动容器，full_page不扩展)；框截到视口底即可。
- 弹窗类角标需触发弹窗后截（如点"转为正式客户"出弹窗——按钮文字可能是"转为正式客户"不是"转客户"）。
- **弹窗触发受业务状态锁定**（商家实测踩坑）：商机合同签订态/赢单/输单终态会锁死推进等动作，弹窗不出现（如"关联合同签署中,商机不可操作"）。此时先识别是"该商机本来就不能触发"（业务正确，换能触发的商机）还是"需要绕过"（用无关联记录、非终态的商机/路由触发）。终态或已关联业务记录不能硬触发——不要靠反复点无用功，改用状态满足条件的对象/页面。
- **双视图/多态页**：页面有看板/列表等视图切换时，不同锚点只在其对应视图渲染（商机看板态取不到列表页签/表格锚点为null）。截图前必须切换到目标视图再取锚点；锚点 null 先判断"是否需切换视图/交互/弹窗"再决定，不直接判定失败。

## 文档头部与修改记录
- **头部分两块**：版本行 + `## 修改记录` 表格。修改记录列 `日期 | 版本 | 修改人 | 修改内容`，在文档最上面（版本行正下方）。
- **命名"修改记录"，不叫"变更台账"**——台账是财务/交易系统术语，评审PRD用它指代文档自身修订史是误称，用户纠正过。
- 修改记录定位 = **这份文档的更新操作记录**，只记"版本/改了什么"。不要把"回写目标/回写完成"这类回写skill字段混进来——那是回写权威源做的事，与文档修订史职责分开。

## 原型细节不与 PRD 逐字对齐（2026-11-02 用户定）

评审PRD 只写中文口径，原型上的英文前缀/英文枚举（如触达时机勾选框显示「DELAY-延迟」「AT_ONCE-立即」）**不必回改原型去对上中文**，也不必为对齐去动原型代码。用户原话：「就是展示英文_中文，没必要那么细节，prd里写中文就好，不需要完全对齐」。

判断线：
- 需要对齐的 = 功能性口径（有几项、能不能勾、置不置灰、必填与否）——这些必须一致。
- 不需要对齐的 = 展示层措辞与英文标识（英文前缀、字段英文名、枚举英文码）——PRD 写中文即可。
- 发现这类差异时**不要主动提议改原型**，记下来即可；一提议就变成一轮无谓改码，还会跟本地 Cursor 的改动撞车。

## 发布版体积硬上限 5MB（2026-11-02 用户明令）

用户原话：「怎么文件又超5mb了啊，能不能长记性啊」「不能超过5MB」。发布版（base64 内嵌图）**不得超过 5MB**，超过则不得交付。实际控制线定在 3MB：一到 3MB 就压图，不要等撑到 5MB 再救。

### 体积暴涨的根因

截图出来的 PNG 未压缩。UI 截图界面区大片纯色 + 文字，未压缩时单张 150-240KB，20 多张合计 3.8MB，base64 后再膨胀 1.33 倍，发布版直接冲 5MB。且每次重截都会重新生成未压缩图。

### 固定动作

1. **截图脚本保存时就压**（已落在 `09-脚本工具/capture_prd_redbox_private20.py` 的 `capture()` 里）：
   ```python
   quantized = img.convert("RGB").convert("P", palette=Image.ADAPTIVE, colors=256)
   quantized.save(out, optimize=True, compress_level=9)
   ```
   UI 截图转 256 色调色板体积降约 60%，文字与红虚线框不受影响（实测过放大可读）。新建同类截图脚本必须内置这一步，不要等交付前才压。

2. **已有图批量补压**（脚本没内置压缩时，或从别人那接手一批图）：
   ```python
   for p in glob.glob('images/*.png'):
       im = Image.open(p).convert('RGB')
       im.convert('P', palette=Image.ADAPTIVE, colors=256).save(p, optimize=True, compress_level=9)
   ```

3. **压完出发布版要带 `--allow-drop`**：deliver.py 默认把「比上一版缩小超 10%」判为「疑似图片丢失」并阻断。压图必然触发这条，用 `--allow-drop 70` 显式声明这是有意的体积优化，而不是丢图。
   ```
   python3 scripts/deliver.py <源稿.md> --prev <发布版.md> --allow-drop 70
   ```
   注意区分：体积**降**可能是压图，也可能是丢图——传 --allow-drop 前先确认 `① base64 图数 vs 引用数` 那一项是 PASS，图数对得上才敢放行。

4. **交付前必看体积**：`ls -lh <发布版>.md`。超过 3MB 回头压图，不要直接发出去让人导入语雀卡半天。

## 小改直接改源稿，别每改动就跑全套（2026-11-02 用户强烈纠正）

用户原话：「有时候手改一下就行了，不需要截图的时候，非要用 skill 跑一遍干嘛」「每一次都在浪费 token」。skill 的三连（截图 → deliver → 自检）是**交付动作**，不是**编辑动作**。

按改动类型决定动作，不要一律全套：

| 改了什么 | 跑什么 |
|---|---|
| 只改文字措辞、补一段说明、改一条口径、改版本记录 | 直接改源稿 + commit。不跑 deliver，不截图 |
| 加了/删了章节、批量改表格、重排序号 | 跑 structure_check |
| 页面形态变了（新增控件/列/页签/弹窗） | 重截该页的图 + 改图引用 |
| 要交付/发给人看 | 才跑 deliver 生成发布版（且只在图已定稿时跑） |

自检脚本的价值在「一次跑出几百行长表里看不见的错」，不在「每改一行就验一遍」。小改用 read_file / patch 看准了直接改。

## 发布版只在原型定稿后生成一次（2026-11-02 用户定）

源稿（`xxx_P0评审PRD.md`）可以随时改、随时提交；但 `xxx-发布版.md`（base64 内嵌图）**不要跟着每次改稿就重跑**。

为什么：发布版里装的是截图。原型没改完、图没重截，跑 deliver 只会产出一份「新文字 + 旧图」的中间态，看是能看，交付出去就是图文不一致。用户原话：「是不是应该等我 push 上去后再搞自动发版？原型图都没更新上去呢」。

正确节奏：
1. 改稿阶段只改源稿 + 跑 structure_check / consistency_check，发布版不动。
2. 等原型改动 push 到位（或图确认不需重截）后再做一次：重截 → deliver → 核图文一致 → 提交。
3. 交付前必须看一眼发布版里的图是不是当前形态，不能只凭 deliver 的「三项自检 PASS」当验收——自检只看图数对不对、路径残留、字节骤降，看不出图是旧的。

## 删制作说明句（评审PRD只留业务内容）
用户(2026-09)定：评审PRD的受众是评审人+开发+自己，**不给看"这个内容怎么来的/怎么做出来"**。以下制作过程/来源/how 句一律删，不出现：

- 字段/规则的权威来源在文件头已用"自包含"口径交代（见定位），正文不再指向任何外部文件。

- 用户用 forge-crm 线索管理做验证场（示例即可，不要求其他模块补全）。
- 每版改完 push main，用户 pull 后在 GitHub/语雀看渲染验收。

- 改表(re批次/加列/删行)别手改——用脚本：按页表头重置序号计数、整表替换，改完核验三表序号各自连续、无残留旧表头。

- 清理外部引用/编号改号时，全文黑名单检查再 push：TSV、详细稿、权威源、角标、标注块、编号、R0、`#`列表头，一处都不留。
- **砍掉一个功能块，必须逐处清七处落点**（2026-10-31 摘「计划异常标记与复核」实测：一处需求牵出六处，少清一处它就继续活着）：①需求范围表那行 ②流程图上的判断与异常分支 ③业务规则（并重排剩余序号）④字段表与公共字段整章 ⑤验收标准对应条目 ⑥章节重排（正文章号与子节号跟着改）⑦修改记录补一行。
