# PM 前端审计工作流

当用户有一个 AI 生成的前端原型，需要对照 PRD/context 做深度审计并给出修复指令时使用。

## 触发条件

- 用户说"看前端""审一下前端""检查代码跟 PRD 对不对"
- 前端原型已生成，需要验收
- 之前答应过"深审"但还没做

## 四步工作流

### Step 1: 读全量文档

同时读三套文件：
- **context/** — 业务地基（04功能清单、06业务流程、07边界约束、08术语）
- **PRD 文档** — 主PRD + 字段清单 + Demo PRD
- **前端源码** — 所有页面 + types + API 层

### Step 2: 逐项对照，产出问题清单

按严重度分三级：

| 级别 | 判断标准 | 示例 |
|:--|:--|:--|
| 🔴 阻断 | 配色/状态错、超范围功能、缺列 | 状态Tag颜色全错、不该有的导入按钮 |
| 🟡 中等 | 操作不完整、文案不对、默认值偏差 | 行内按钮缺一半、弹窗文案统一写死 |
| 🟢 低 | 措辞微差、简化实现可接受 | SelectWithSearch用原生select代替 |

对照维度：
1. 状态配色 vs Demo §5.3
2. 列定义 vs Demo §5.2（有无缺/多）
3. 行内操作 vs Demo §5.4（每个状态的按钮是否正确）
4. 筛选条件 vs Demo §3.2
5. 弹窗文案 vs Demo §6/§7
6. 分页默认值 vs Demo §5.1
7. context/04（功能清单）vs PRD 主文档 vs 前端 → 术语一致、范围一致
8. context/06（业务流程）vs 状态机代码 → 流程闭环
9. context/07（边界约束）vs 实际按钮 → 无越界

### Step 3: 做三向对齐审计

context/ → PRD → 前端代码，三向对照。输出：
- ✅ 对齐项
- 🔴/🟡 偏差项
- 总评（各维度打分）

### Step 4: 出反重力修复指令

用五段式模板，每条问题写清：
- 问题描述 + 正确规格 + 当前代码位置（文件名+行号）
- Constraints 段写死红线（不改types、不改API、不加依赖）
- 每一轮指令 4-7 个问题，两轮打完

## 实际案例

2026-07-05 强盛科技采购订单审计：
- 第一轮 6项：配色+导入按钮+缺列+缺筛选+行内操作+弹窗文案
- 第二轮 4项：分页+Mock前缀+context术语+colSpan
- 两轮共 10 项，修完对齐

## 关键坑点

- 不要一上来就改代码——先出问题清单，用户确认再给指令
- Constraints 段比 Request 段更重要——先说不能动什么
- 行号是精确到行的，不是大概范围
- 跨文档不一致时，context/ > PRD 主文档 > Demo PRD > 前端代码
