# 五段式结构化提示词模板

用户（刘龙飞）总结的通用提示词模板。核心价值：一次把"背景—动作—输出格式—红线—汇报时机"全部框死。

**底线原则**：任何操作如可能影响 AI 记忆/进程/状态，必须先向用户预警+等确认，绝不自行执行。

## 四层约束体系

五段曲的红线禁止是第四层，前三层是项目级文件，反重力/Cursor/Codex 读取后天然遵守：

| 层级 | 文件 | 管什么 |
|:--|:--|:--|
| 🏗 业务 | `context/` | 做什么/不做什么/规则/术语 |
| 📋 文档 | `AGENTS.md` | PRD怎么写/已知坑/六维走查 |
| 🎨 视觉 | `DESIGN.md` | 颜色/字体/圆角/间距/组件token |
| 🚦 指令 | 五段曲 红线禁止 | 本次任务边界/不改什么 |

DESIGN.md 用 Google 开源的 design.md 格式——YAML front matter 定义 token + Markdown 正文写设计 rationale。Agent 读到的不只是 `#2563eb`，还有"这是唯一主操作色，不用于装饰"。避免跨会话配色漂移。

## 指令路径规范

跨机器协作时（VPS ⇢ Mac Agent），指令中所有路径只用**项目内相对路径**，不写绝对路径：
- ❌ `/Users/liulongfei/个人文件/进销存Traininng/front-prototype/src/api/`
- ✅ `项目名：进销存Traininng/front-prototype/ → src/api/xxx.ts`

## 指令文件交付命名（多单据 PRD 填充）

给用户发 Codex/反重力填充指令的 .md 文件时，文件名前缀标注执行顺序，让用户**不打开文件就能判断并行还是顺序**：

命名：`链名-NN-单据名_Codex填充指令.md`（如 `入库链-01-收货单`、`出库链-02-拣货单`、`退货链-01-采购退货单`）。

告诉用户的规则：
- **同一条链（相同"链名-"前缀）→ 严格按 NN 顺序跑**，下游引用上游定义
- **不同链之间 → 可并行**，同时封顶 2-3 个（文件隔离，不冲突）
- NN 按业务链真实位置编号（如入库链 收货=01/质检=02/上架=03），跳号即表示该位置单据还没生成

另在每个 `prompt/` 放一个 `00-执行顺序.md` 索引表（链/顺序/文件/状态 + 并行建议），一眼看全。

## 发包检查清单

向用户发送项目压缩包前，必须逐项确认：
1. `zip -rq` 全目录打包（非手动挑文件——这是今天血的教训）
2. `unzip -l` 列文件清单，确认 context/、prd-docs/、templates/、prompt/、提示词/、.cursor/、AGENTS.md、CLAUDE.md、DESIGN.md 全部包含
3. 排 node_modules、dist、.git、__MACOSX、.DS_Store
4. 一个项目一个包，不发"代码包+文档包"拆分的
5. 文件名用项目名（forge-erp.zip），不加 -complete/-full/-docs 后缀
6. Mac 用户只用 .zip，不用 .tar.gz

**⚠️ 高频事故**：手动指定目录（如只打 src/）→ 漏文档 → 用户覆盖本地后丢失 → 多次返工。根因：自以为能记全项目结构。解法：`zip -r .` 全目录一把抓，不手动挑。

## 项目检查指令规范（git 优先）

用户说"检查下 XX 项目,变化有点多"时，**第一步是 git log,不是扫目录**。这条被纠正过——曾跳步直接列目录/扫占位,等于跳过了需求调研直冲应用层。

正确顺序(对齐软件工程方法论):
1. `git log --oneline -15` — 需求调研:先看"发生了什么,谁在什么时候改了啥"
2. `git diff --stat` 对比关键批次 — 需求分析:理解变化范围和影响面
3. 基于变化判断当前状态 — 业务设计
4. 最后才列目录/扫占位/总结 — 应用设计

**git log = 项目的历史访谈记录。模糊指令 → 不直接回答 → 先 git log/diff 调研 → 再分析 → 再输出。**

## Hermes 响应规范:模糊请求自动分层追问

用户给了一个"空壳请求"(如"帮我整理下盘点模块""检查下项目"),**不要直接执行,也不要泛泛反问"你要我做什么"**。按软件工程方法论(需求工程→设计工程)自动判断缺失层级,用分层追问帮用户把需求填实:

| 用户给的 | 缺失层 | 我该追问的方向 |
|---|---|---|
| 一句话需求,无背景 | 需求调研/分析 | "单据链路?本期边界?涉及哪些对象?" |
| 有背景,无范围 | 需求分析 | "一期交付哪些?Out of Scope?验收标准?" |
| 有背景+范围,无规则 | 业务设计 | "状态机?跨单下推规则?异常场景?" |
| 有背景+范围+规则 | 应用设计 | "页面结构?按钮规则?交互方式?" |
| 五段曲式完整 | 不缺 | 直接执行 |

**原则:AI是辅助,判断是你做的——空壳请求时我的价值不是"猜你想干啥然后硬执行",而是"帮你把缺失的结构层补出来,让你做判断"。** 每个追问必须是选择题或定向填空题,不让用户自己从零组织。

- 帮用户起草或打磨要丢给 AI IDE/Agent（Antigravity、Claude Code、Codex、Cursor、国产 IDE 等）的提示词
- 用户要下达一个复杂/多步骤的任务，需要结构化表达
- 用户说"帮我写个提示词""套模板""按这个结构写"

## 交付格式铁律（用户明令 · 2026-07 一天内两次纠正）

给用户的指令**必须是单个纯文本代码块**，让他一次性整段复制去喂 Codex/反重力。**可复制性 > 排版美观。**

- ❌ 别拆成 markdown 加粗标题 + 多个散落的小代码块 + 夹叙夹议——用户没法一次选中复制，会当场恼（原话「你这样我怎么直接复制啊」，同一格式错误一天内被纠正两次）。
- ✅ 整条指令从 `Context:` 到 `Checkpoint:` 放进**一个**围栏代码块；块内不要再嵌套围栏，需插入的目标内容（表格行、markdown 片段、find→replace 的新旧文本）用纯文本原样列出即可。
- 聊天里的解说 / 进度 / 核验结论一律放在代码块**外面**；块内只留能直接喂执行器的内容。
- 纯文件编辑类任务用**精简四段变体**：`Context / Request / 红线禁止 / Checkpoint`（省掉 Output format，把 git 推送要求并进红线禁止），贴合用户示范的模板。

## 版本标识与自查（必加段 · 2026-08 血泪教训）

**背景**：文字版罗宾改了十几轮，语音版多轮返工，多次因「不知道改到哪版、无法回滚、AI 改坏布局」吃大亏。根因：指令里没要求 AI 保留版本标识、没要求它自查。

**铁律**：所有给 Codex/Cursor/反重力的指令（尤其是迭代类），必须包含：

1. **版本标识（会话标识）**——写进 Request 或红线禁止：
   - 轻量快照法（不依赖 git，默认推荐）：每完成一轮修改，把**本轮改动的文件**复制到 `versions/v{n}/` 目录（n 递增），旧版本文件不删除
   - 汇报时给出当前版本号 v{n} + 本轮改动文件清单
   - 回滚 = 把 `versions/v{n-1}/` 的文件复制回源码位置
   - 禁止「只改不记」——没版本标识的迭代 = 盲改
   - 不用 git add/commit（太重，用户明令）；git 仅在有明确需求时用

2. **浏览器自查（代替人工验收）**——写进 Request：
   - 改完必须用内置浏览器（Codex/Cursor 自带）或 Chrome DevTools MCP（反重力）打开目标页面
   - 检查：Console 无报错、关键交互可点、数据展示正常、Network 请求 200
   - 截图保存自查结果
   - 未通过项继续修复直到全通过，再汇报
   - 用户不用再人肉刷新验收

3. **版本标识标准模板段（轻量快照法，不依赖 git）**：
```
版本标识（必须）:
- 项目根目录创建 versions/ 目录
- 每完成一轮修改，把本轮改动的文件复制到 versions/v{n}/（n 递增）
- 旧版本文件不删除，保留完整历史
- 汇报时给出当前版本号 v{n} + 本轮改动文件清单
- 回滚：把 versions/v{n-1}/ 文件复制回源码位置
```

4. **自查标准模板段**：
```
浏览器自查（必须，代替人工检查）:
- 用内置浏览器打开 [URL]
- 验证：页面加载无报错 / 关键交互正常 / 数据展示正确
- 截图保存自查结果
- 未通过项继续修复，直到全通过再汇报
```

## 模板本体（可直接复制）

```
Context:
我正在做 [大任务]。
目标对象是 [谁]。
这个结果要帮助他们 [达成什么结果]。

Request:
请完成 [一个明确动作]。

Output format:
请按照 [具体结构] 输出。
必须包含 [必要模块]。
不要超过 [长度/范围]。

红线禁止:
- 不改已有：不要 [改XX文件/类型/逻辑]
- 不加不该有：不要 [加XX功能/状态/按钮]
- 不越界发挥：不要 [脑补/新增依赖/动其他模块]
如果 [信息不足]，请明确标注不确定性。

Checkpoint:
除非涉及不可逆操作、范围变化，或需要我提供信息，否则请继续完成任务后再汇报。
```

## 五段各管什么

- **Context（背景）**：交代大任务 + 目标对象 + 期望结果。让 AI 知道"为谁、为什么"，产出才不跑偏。
- **Request（动作）**：一句话一个明确动作。别塞多个动作，多任务拆多次。
- **Output format（输出格式）**：结构 + 必含模块 + 长度上限。**不可省略**——这是 Hermes 验收的抓手。要求 executor 交出「逐文件 改前/改后 对照 + 一张自洽表」（如 单号→场景→状态→关联号 的全链对照，或 台账验算表），Hermes 才有东西核。实操中这是我最常漏的段，每次缺了用户验收就少锚点。
- **红线禁止**：不限数量，按类别列禁止项 + 举例。常见三类：不改已有的 / 不加不该有的 / 不越界发挥。这条治 AI 幻觉最有效。
- **Checkpoint（汇报时机）**：给 AI 自主权——除非不可逆/范围变化/缺信息，否则做完再汇报，别频繁打断。

## 用法要点

- 五段不必每次全填，但 **Context + Request + 红线禁止 三段建议每次都有**——这是防猜、防越界的最小组合。
- Checkpoint 段是"自主执行授权"，正好匹配用户偏好：让 AI 一口气把活干完再汇报，而不是每步都停下来问。
- 配合课程"分层喂料"原则：Context 段只放这次任务需要的背景，别把整个项目上下文全倒进去。
- 第一次安装 Hermes CLI 时，应先查官网文档确认最新安装命令。不要凭记忆给 `brew install hermes`——最新 CLI 安装方式可能已变（实际正确方式是 `curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash`）。

### 走查返修指令：三条提速铁律（实战验证）

写"修复/统一/对齐"类返修指令前，先做这三步，Codex/反重力 出错率骤降：

1. **先找参照物（reference model）**：仓库里往往已有一个改对的同类文件（如某个字段清单已是目标风格）。在指令里把它列为"标准范本 / 只读"，让 Codex 照抄而非凭空定标准。本次 `库区字段清单.md` 已是全量 camelCase，直接当 `货位字段清单.md` 的范本，指令瞬间精准。
2. **命名统一先敲口径**：用户说"统一命名 / camelCase"时，先确认是"死板 camelCase"还是"对齐代码/SSOT"。看他给的例子——出现 `area_code→zoneCode`（而非 areaCode）这类语义改名，就说明要的是**对齐代码**，那么 `location_code→code`、`location_barcode→barcode` 也应随前端类型走，不加前缀。写指令前用一个二选一问题定死，避免整篇返工。
3. **诊断 doc↔code 方向**：命名不一致时，先判断该改文档还是改代码。若前端 types 已是 camelCase，问题就在 PRD 文档——指令必须写成"改文档向代码对齐"，并把代码/范本列为**只读红线**，否则 Codex 会反向去改代码。

## 六层约束体系

给 AI 生成代码前，六个文件锁死质量。五段曲之前先确保就位：

| 层级 | 文件 | 管什么 |
|:--|:--|:--|
| 🏗 业务 | `context/` | 做什么/不做什么/规则/术语 |
| 📋 文档 | `AGENTS.md` | PRD怎么写/已知坑/走查标准 |
| 🎨 视觉 | `DESIGN.md` | 颜色/字体/圆角/间距/状态标签配色 |
| 🚦 执行 | 五段曲红线禁止 | 本次任务边界/不改什么 |
| 🛡 底线 | 行为铁律 | 任何可能影响记忆/进程的操作必须先预警 |

DESIGN.md 格式见 Google Labs Code 的 `design.md` 仓库——YAML front matter(token) + Markdown body(rationale)，Agent 可读可 lint。放项目根目录，AGENTS.md 中写明"做 UI 前必读 DESIGN.md"。

展示力金字塔：**文不如表，表不如页，页不如面**。面试优先展示可操作的界面和系统，文档作为底层支撑。

五段曲 = Context → Request → Output format → 红线禁止 → Checkpoint

三原则 = 指令层防跑偏 / 文件层防冲突 / 人脑层防过载

### 三条新增铁律（2026-07 实战验证）

**1. 文档同步和代码改动必须拆成两条独立指令。**
PRD 文档（.md）和前端源码（.tsx）不能混在一条指令里——ManualPage.tsx 是代码不是文档。混在一起会让 Codex 把"禁止碰代码"和"要改手册"互相矛盾，导致两个任务都废掉。拆开：一条"只改 .md 文档"，一条"只改 ManualPage.tsx 源码"。

**2. 多条 Agent 并行改源码时，每条指令加"只改源码，不要 npm run build"。**
多条 Codex/反重力并行跑时，如果每条都执行 `npm run build`，后完成的 dist 会覆盖先完成的 dist，所有改动只剩最后一份。每个 Agent 只改源码，全部改完后用户手动跑一次 `npm run build`，一股脑全带上。

**3. Output format 和 Checkpoint 不能因为"任务简单"就省略。**
五段式的最小组合是 Context + Request + 红线禁止，但 Output format 和 Checkpoint 不可省略——Output format 是验证抓手(让 executor 交出逐文件差异)，Checkpoint 是自主执行授权(做完再汇报)。缺任何一段都会让用户验收少锚点或 Agent 频繁打断。
```

### 三原则详解

| 原则 | 防什么 | 怎么防 |
|:--|:--|:--|
| 指令层 | AI 跑偏 | 红线禁止审查前置，写到指令里 |
| 文件层 | 合并冲突 | 模块隔离，不同Agent操作不同文件 |
| 人脑层 | 审查过载 | 并行封顶 2-3 路，再多排队 |

### 多线程并行铁律

单线程靠人审，多线程靠红线兜底。文件隔离是并行第一原则：不同 Agent 必须操作**物理独立**的文件（API/类型/页面各自独立），不可能产生合并冲突。瓶颈不在 AI，在人脑上下文切换成本。

**走查返修实战三条（2026-07 验证）**：
1. **写指令前先落地到行号**：读真实文件确认「改的到底是哪层」再动笔。曾把「货位命名统一」当成改代码，读 `types/baseData.ts` 才发现代码早已 camelCase/ENABLED，实际是**文档向代码对齐**（只改 .md、一行代码不碰）。假设的修复位点必须先验证——省下一整轮返工。
2. **并行前先比对落点文件**：用户问「④⑤能并行吗」，唯一判据是文件是否重叠。两条返修指令都碰 `交运单_用例数据推演.md` → 必须串行或合并，不能并行。回答并行性时永远先逐条列出落点文件；重叠就建议合并成一条（用户只需盯一次 Codex、审一份报告，正合「人脑防过载」）。
3. **走查项判据丢失时：接地或延后，绝不臆造**：用户给的返修项常是速记（「TR语义」「库存查询裸\|」），过几天两人都忘了细节。能从文件挖到实锤的直接写指令；挖不到的**诚实说找不到、请用户定位**，或延后到「用户 push → 我 git pull → 对着真实内容全面检查」那一步。绝不编造走查判据去浪费对方 Agent 的额度。用户 push 前，先在 VPS 侧 `git status` 预检（分支/干净度），确保随后 pull 不卡冲突。

**实战Agent分工**：
- Codex+GPT5.5 → 批量重构/文档/ER图/Dexie迁移/Swagger
- 反重力+Gemini → 前端页面生成
- 不同 Agent 不碰同一目录（安全审查会拦截冲突写入）

### A2A 执行与复核（大改必读，详见 `references/a2a-large-refactor-and-review.md`）

- **先量爆炸半径再写指令**：动手前用 grep/search 数清「占多少处、几个文件」。几十文件 / 上百处 = 大改，别甩一条会改文件的指令，先出**只读「影响面报告」指令**（扫描 + 提议映射，零改动），审完再**按模块分批执行**（封顶 2-3 并行）。本会话 C 项一扫发现 939 处 snake_case / 55 文件，远超预估——盲改必翻车。
- **指令锚定 SSOT / 范本**：先找到已经是目标态的「金标准」（同族已改好的字段清单、SSOT 文档、前端 seed 种子数据），在指令里当**只读参照物**，别在提示词里凭空定标准。例：库区字段清单已 camelCase → 当货位改造的范本；商品档案 SSOT + 前端 seed 用 `SKU001` 口径 → 才是 SKU 重定基的真目标（出库链 `SKU-A100` 和库存 `SKU10086` 两套其实都跑偏）。
- **反重力也能干文档/审计**（Codex 挂时顶上）：五段式**工具无关**。但反重力本能是「生成前端页面 + 跑得快爱动手」，红线必须加固：明确「只改 .md、绝不碰 front-prototype、先出报告后动手、别图快一把梭全改」。
- **复核 IDE Agent 的产出（A2A 的另一半，不只是发指令）**：Agent 在 Mac 改完 push 后，Hermes 在 VPS 侧走 **fetch(只读) → 确认干净快进(`git merge-base --is-ancestor`) → `diff --stat` 范围核验 → 红线核对只动了该动的文件类型 → `git merge --ff-only`**，**绝不盲 pull**（对齐用户铁律「先检查，再 pull」）。VPS 是只读镜像，别在 VPS 提交/推送；push 会因无凭据失败。

**工具替补（Codex 挂了跑反重力）**：五段曲指令工具无关，文档/mock 审计类反重力也能跑，但必须**加固红线**——反重力本能是「生成前端页面 + 跑得快爱动手」，纯文档任务要：① 明确「本次不做页面，front-prototype/ 下 .tsx/.ts/db/api 一行都不许碰，只读改 .md」；② 逼它「先出差异报告、系统性问题只报告不改」，防它图快一把梭全改。另：反重力当前挂的常是养号主力号，重活别连着压（续 Pro 要紧）。

**路径规范**：指令中只用项目内相对路径（`项目名/front-prototype/src/...`），不给绝对路径（`/Users/xxx/`），跨机器兼容。

**依赖同步**：指令中加一句 `如改了 package.json 依赖必须同步运行 npm install`。

## A2A 大重构执行与验证闭环（规模化返修）

详见 `references/a2a-refactor-execution-loop.md`。要点：
- **拓扑**：用户 → Hermes(VPS,审查+出五段曲指令) → Codex(Mac,只改文件) → 反重力(Mac,负责 push) → Hermes(VPS,pull 验证)。VPS 默认 pull-only，push 由用户 Mac 侧负责；别假设 VPS 能推、别在聊天里索要 PAT。
- **安全拉取铁律**（用户明令"先检查再 pull"）：`fetch → merge-base --is-ancestor(FF判定) → diff --stat/--name-only(范围+红线越界) → merge --ff-only`。⚠️ git 把中文文件名转义+加双引号(结尾 `.md"`)，`grep '\.md$'` 会误报越界，看 raw 清单核对。
- **打样先行**：大批量套约定前先拿 1 模块打样深验，抓约定漏洞（曾抓到"枚举值被误 camelCase，应 UPPER_SNAKE"，省 6 模块返工）。
- **立规范再套用**：跨几十文件且多数字段无代码对应时，是"定命名规范"而非"对齐代码"——先写 `context/NN-规范.md` 治宪，再逐模块套。
- **侵入式改动先出只读"影响面报告"**（列引用+建议映射+风险，零改动），人工批准后再执行；杜绝盲改。
- **并行**：不同模块可并行多 chat，但**禁止各 chat 自行 commit/push**(抢 .git/index 锁)，指令写死"只改文件不碰 git"，全部跑完统一提交一次。
