# 内网数据采集指令（Cursor 内置浏览器 / @Browser）

用户公司的业务数据几乎都在内网（`docs.vivo.xyz` 在线表格、`vapd.vivo.xyz` 需求单、自建 Confluence）。
Hermes 进不去，只能由用户公司电脑上的 Cursor 把数据「读出来」再交给 Hermes。
**所以这条链路的瓶颈不是采集本身，是那份指令写得够不够死。**

## 指令骨架

开头两行先解决「怎么读」：

```
@Browser <链接>

Context:
执行位置：公司电脑，该链接已在 Cursor 内置浏览器中打开（已登录 vivo 内网）。
任务：把 <哪张表/哪份文档> 的 <什么范围> 导出为 TSV，写进 <哪个目录>。
```

`@Browser` + 一句「已在内置浏览器打开」是让 Cursor 走浏览器控制，否则它会去猜内容。

## 七条硬规则

1. **URL 全文只出现两处**（`@Browser` 后 + Context 的数据来源段）。出现三次以上会让 Cursor 当成多个来源，产生歧义。
2. **`?sheetIndex=N` 是范围定义，不许删。** 它指定目标工作表；删掉会把抓取扩到其他页签——在线需求池这类文档里，其他 sheet 往往是别的产品线的表。用户说「抓整表」指的是「这张工作表的全部行」，**改措辞，不改 URL**。
3. **先表头、后数据。** 第一步只确认表头结构：几个页签、单行还是多层合并表头、逐列列名、有没有颜色分区/合并单元格/冻结窗格。第二步才按**实际表头**逐行抓。按印象里的列名写死抓取，必漏列。
4. **历史列清单只作比对基准，不作抓取依据。** 指令写死「以在线表实际表头为准，不要照抄上面的列表」，并要求逐条报告增减与改名。在线表会改版，历史记录只能当核对基线。
5. **长文本列点名不许截断**（主要场景 / 需求价值 / 产品分析 / 进度跟踪），并给出行数基准（如「历史 59 条，数据行位于第 3–13、15–62 行，第 14 行为空」）供核对——数量对不上必须说明原因，否则你不知道是表变了还是它没翻完页。
6. **红线里显式禁 git。** 公司机器上抓取一律只读：`git add / commit / push` 全部禁止；除指定的新文件外不动、不删任何现有文件。用户明确要求降低 git 频次以防公司监控。
7. **Checkpoint 要双输出：** 全量文件落本地 + 聊天里贴一份精简 TSV。全量 18 列带长文本贴不动聊天，精简版（10–11 列，只有摘要列允许截断）才是 Hermes 侧重建结构的输入。

## 分工铁律

| 事 | 谁做 | 走哪 |
|---|---|---|
| 抓取/只读 | 用户公司电脑 Cursor | 不产生 git 动作 |
| 指令、分析、方案 | Hermes | 聊天框直接发，不发文件 |
| 落文件、push | Hermes（VPS→GitHub） | 用户不参与 |

公司网络里只留「读」，不留 push 记录。产物回传优先聊天框贴文本/表格；体积大的落本地文件。

## 采集完落盘：表格用 TSV，不要拆目录

采回来的表格数据（需求池、指标表）**一张表一个 TSV** 当唯一事实源——类 Excel、可 diff 可筛选、可 Excel 直接打开。
不要按状态拆文件夹 + 每条需求复制成一个 md：那是把筛选器做成目录，状态一变就搬家断 git 历史。详见 `pm-project-context-setup` 的「需求池/台账类目录」一节。

删除旧文件前必须逐条比对新数据与旧数据的条目数/名称集合，确认没丢再删——旧数据是判断「新抓的是否漏了」的唯一基线。

## 常见坑

| 坑 | 现象 | 预防 |
|---|---|---|
| 删掉 `?sheetIndex=N` | 以为是在清理 URL，实际扩大到其他产品线的表 | 表选择参数是范围定义，保留 |
| 按预设列名抓 | 漏列（18 列的表抓成 13 列） | 先表头后数据，历史清单只作比对 |
| 只抓首屏 | 行数远少于在线表 | 指令写死行数基准 + 翻页滚动到底 |
| 顺手 git commit | 公司机器产生推送记录 | 红线显式禁 git add/commit/push |
| 全量长文本贴聊天 | 消息超限被截断 | 双输出：全量落文件、精简 TSV 贴聊天 |
