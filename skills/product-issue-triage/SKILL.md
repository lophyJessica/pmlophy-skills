# 线上问题单：产品维度研判与处置

收到研发/测试/运维丢过来的问题单（接口报错、组件异常、上游变更、验收遗漏）时用它。产出是**一段可直接贴进在线文档的处置说明**，不是技术排查报告。

## 一、先判「该不该做」，再谈怎么修

产品经理在这类单子里唯一不可替代的价值是判断，不是找根因——找根因有研发。所以顺序固定：

1. **这个功能本身有没有存在价值**。问用户视角一个问题：用户看到这条信息后，行为会变吗？不会变的（如“你在哪个位置”“当前网络状态”）价值为零，报错只是暴露了它的多余，不是该修的 bug。
2. **修好了会有多少人真的用到**。依赖浏览器定位授权、依赖用户主动开启某开关的功能，即使技术问题解决，绝大多数用户仍不会走到那一步。把这条算进去，很多“修一下就能好”的方案会自动出局。
3. **给出处置三档**：删除 / 保留但降级（关掉展示、不调接口）/ 留作新场景重做。**按价值分档，不按修复难度分档**——用户会明确拒绝从技术难度出发的方案。

用户原话：「不要从技术的维度，从产品的维度」。一出技术修复方案就会被拉回来。

## 二、处置说明的固定五节

直接写进在线文档，让人能拿去回复研发和需求方：

1. **问题性质**——一句话定性。典型写法是「不是接口故障，而是功能本身无产品价值」，或「不是新出现的问题，是从上线起就存在的配置不匹配」。
2. **处置范围**——删什么、留什么，逐项列。留的那部分要写清为什么不受影响（它依赖的是另一条链路）。
3. **影响评估**——用户侧可感知的变化是什么。多数情况是「无可感知变化」，但要说出依据（当前只是多一行提示，该提示本身构成负体验）。
4. **不采纳修复方案的原因**——技术能做，但不是该做的事。这一段写不好，会被反问「那为什么不修」。
5. **后续场景说明**——若将来确有真实需求，怎么做、与本功能无继承关系。

写成技术排查报告（根因/复现/修复建议）用户会退回；他要的是能对外用的结论。

## 三、报错先归类，不要写成「可能是上游调整」

问题单里最常见的糊结论是「初步猜测是上游/厂商调整导致」，它等于没查。凡报错原文印在单子里，就先把它当技术事实读一遍，判断是「最近才坏」还是「一直是错的」：

- 报错指向配置不匹配（如限制类型与调用方式互斥、key 白名单不含调用域名）时，这类错误**从上线的第一天起就会报**，不可能是上游这周改的。单子里写「可能是上游调整」就是没定位。
- 区分方法：去平台侧看该配置项的修改记录。一直没改过 → 属验收遗漏；近期改过 → 才是新出现的问题。

但注意分寸：**产品只负责把这个区分讲清楚，不替研发下最终技术结论**。可以写「更像是上线起就存在、验收未覆盖」，并给出验证方式，不要自己断言根因代码在哪一行。

## 四、顺带沉淀的两条

- **验收清单缺项比本问题更值钱**。这类问题十有八九是验收只看了正常态、没测接口失败时用户看到什么。把它作为一条可沉淀的验收项提出来（每个页面都该测一遍断网/接口报错下的样子），比追责有用。
- **删功能前先确认布局依赖**。去掉一个展示区之前先问一句：删了之后下面的内容会不会留一块空白、有没有固定高度或绝对定位撑着。问一句比上线后看到一片留白便宜。

## 五、不要做的事

- 不要把问题单原样复述一遍再补一句“建议修复”——那是传话筒。
- 不要用「几乎无影响」和「初步猜测」同时收尾——两句放一起读起来像没查清，会被退回。
- 提功能理应砍时，不要顺着“已经做了就留着吧”的和稀泥。多说一句「这个功能本来就不该做」，比跟着算工时有用。
