# vivo 外销 CMS 设计定稿增量（待并入 vivo-project）

> vivo-project 是用户自有 skill（非 curator 管），自动写入被拒。用户在前台会话执行 `hermes curator adopt vivo-project` 后，把本文件并入该 skill 对应位置（references/内销用户行为配置字段.md 与 SKILL.md 第四节）。

## 一、用户行为弹窗字段定稿（复刻内销真实形态，覆盖旧口径）

行为ID 手输≤18、名称≤20、描述≤500。

**数据源不是用户手填**——输入框只读、置灰、不可填，值由服务端按行为ID查事件基础配置（`smp_event_cfg`）补齐，不在保存报文里。旧「手填大数据表名」口径作废（业务不需要知道表名）。

记录本身**不是系统自动生成**的：业务点「新建行为」+ 手填行为ID → 调 `listField` 带出行为名称/表名/属性 → 保存生成定义；**新建即启用**（enable=true），启停走列表开关（带二次确认），表单里没有启用字段。

**事件配置由大数据登记**——链路是「业务提需求 → CMS 提需求给大数据 → 大数据登记后才能新建该行为」，业务不直接找大数据；这条已定，不再是待查 P0（旧文档里「谁维护事件配置」的悬案可关闭）。

**判断该框可不可填不许靠截图**：禁止态提示（悬停显示禁止符号）不进画面，占位符「请输入…」和红色必填报错照常呈现，disabled 与可填在截图里同形；可填性只认源码属性或实机悬停确认。**同一条推广到所有多态控件**：截图只拍到一个状态（选中/未选、允许/不允许、启用/停用）时，另一个状态的形态（隐藏？置灰？换文案？）一律算未取证，写进待取证项并指定取证人，不要用「这种开关一般都是置灰」填空——用户拿内销截图来问联动关系时，问的往往正是另一个状态的样子。

- 行为维度：**openid | imei 两个都做**（用户拍板，覆盖「外销仅 IMEI」与「imei|unionid」两种旧理解）。预售走 openid（非 vivo 用户也能参与）、存量用户只有 imei；已知 openid 无法区分国家，见标识坑。
- 允许限制时间范围：必填 允许|不允许。**它是行为定义上的一个开关，管的不是定义本身，而是圈人时该行为能不能加时间窗口**：落点＝受众筛选 → 行为条件里的「时间范围：开始日期 至 结束日期」那一行。
  - 已取证（内销截图·允许态）：「允许」时该行日期区间显性展示，未选值为灰色占位。
  - **未取证**：「不允许」时是**隐藏**还是**置灰**——单张截图只证明一个状态，内销源码在公司机只读不外传、VPS 没有内销仓库，不许顺着「一般是置灰」下结论。取证只有两条：让用户把该行为切成「不允许」再补一张，或问内销产品（口径仅内销）。
  - **两态不能混**：隐藏＝运营根本不知道有这回事；置灰＝看得到改不了、要去问为什么。给业务的解释与要不要补辅助文案完全不同。
  - 外销现行落地口径＝置灰不可编辑 + 弹窗内辅助说明，新建行为默认「不允许」（与内销预售标签那条一致）。这条口径散落在业务PRD（使用限制条＋时间范围条）、功能清单对应条目、Demo（配置页字段表＋受众筛选条件表）、评审PRD（使用限制小节＋时间范围可编辑性小节＋验收标准）、三份 annotations、原型 `EngageBehaviorTab.tsx`（`timeDisabled` ＋提示文案）——取证结论一变，这几处必须一次改完，别只改原型或只改 PRD。
- **行为触达时机：只有「延迟 / 立即」两项，且按事件类型联动**（1028 定稿，覆盖旧「DELAY/BEFORE/AT_ONCE 三复选默认全选」）。内销新触达应用真实形态（**吴凡是内销 CMS 产品经理，其答复只代表内销，外销口径由我们自定**，不许拿内销结论当外销决策依据）：立即类事件可选「立即」或「延迟」，延迟类事件「立即」置灰、只能选「延迟」。不存在「提前」。定义页管「这条行为允许用哪些时机」（上限由事件类型定），触达应用/计划里管「运营实际选哪个」，两层取交集。
- **「立即」不等于实时**：内销绝大多数事件是 T+1（大数据不做实时，压力大），特殊事件（如生日）也只是按月约定周期写表（每月 1 号写当月生日数据）。产品文案不能写「实时」，否则运营以为秒级发出。
- 数据更新时间：必填，**时间选择器填时刻（如 04:30），不是日期**。定义＝**开发约定好的取数时间**：CMS 按这个点主动去大数据拉当日最新数据（不是大数据回推、不是业务自定调度开关）；字段由 CMS 维护，只约束 CMS 内这个时间的用法（凡哥口径）。
  - **系统不校验数据是否已更新**：CMS 与大数据约定取数时间，默认表里数据是最新的直接取。历史上出过「大数据没写完、CMS 当最新取」导致结果偏，靠两边对齐取数时间解决，这是**运维约定不是系统能力**——PRD 不许写「系统保证数据最新」。
  - 因此结果为空时的提示要写「当前条件无匹配人群，若刚发生行为请次日再试」，**不能写「条件有误」**，否则运营会反复改条件。
  - 建议在结果区/列表回显「本次取数时间 + 该行为数据更新时间」供运营自查（要大数据侧支持则列为数据需求）；这是事实展示，比安慰性提示有效。
- 适用范围：必选单选 全量使用|部分可使用|部分不可使用|无
- 行为属性：列表形式

## 二、标识偏差架构坑（内销血泪教训）

会员用 openid、CMS 标签用 imei，对不上 → 内销一直用不了「用户等级」圈选。规则：

1. 外销行为维度选型前必须先问清 openid↔imei 的 mapping 能力（insight-server 在内销干 ID-Mapping，外销有无对应物）。
2. 一个行为数据表通常只有一种标识字段——跨公域/私域圈选要么表内双写标识、要么分行为定义，单选一个维度会圈不到另一域。
3. 该坑答案决定行为维度是单选、还是「跟随数据源表」或双标识。

## 三、系统交互查证方法（派 Qoder，前后端都要）

- 前端（cms-admin）：控件类型、编辑态置灰、提交报文——只能看出形态。
- 后端（smp / smp-scrm-web）：保存逻辑、从大数据同步行为记录的机制（定时任务/消息监听）、更新属性的元数据接口、圈人查大数据的接口链——才能坐实数据流。
- 产出：字段×来源×证据表（文件:行号+接口），不确定写「未能查证」不许推断顶。
- 源码树：`E:\projects\源码管理\内销\前端\cms-admin` + `内销\后端\{smp, smp-scrm-web}`；指派工具=Qoder IDE（公司免费，已入派活池）。

## 四、好友列表改版定稿：好友主视角（主从方案被业务否决）

> ⚠️ **本节 3–5、7–9 条的抽屉式方案已被业务否决作废，现行形态见第十节「平铺全字段」。** 保留本节只为解释「当初为什么这么做」和抽屉被否的两条硬理由（归属链搞错、业务判断要看的信息被收起）。

1. **主从视图（一级行=账号）被业务否决不要再提**——业务要好友视角；账号视角与 WhatsApp 账号列表（管账号分配/解绑/授权）定位重复。
2. 改法：好友为一行、只留好友侧约 9 列；账号维度收进表头筛选 + 「查看详情」右侧抽屉（上半好友信息、下半灰底「所属账号」区块）。
3. 账号健康度用「账号状态」聚合标签列（绿点正常/红点已删除），完整态在抽屉；形态待用户拍板。
4. **必补字段「Whats账号删除状态」**：好友挂靠账号在账号列表侧的删除状态，枚举＝未删除/已删除；与既有「账号删除状态」（好友记录自带）口径不同、并存展示。
5. 「查看聊天记录」挂好友行级，不挂账号级——账号视角下不知看哪个好友的记录。
6. 同口径改动落点：Demo（布局ASCII+Mock+字段表三处列一致）、字段清单TSV、已出的主从形态截图——一次改完。
7. **线框图一图一态**：列表态与详情抽屉态不要并排画在同一画布——看上去像表格下面又跟了一块，用户会直接说「没看懂」。抽屉必须靠点击才出现，图上标清「点击某行 → 右侧滑出」的切换关系。
8. **同名字段必须点破区别**：列表「所属导购」= 添加该好友的导购，抽屉「账号所属导购」= 账号绑定的导购，二者可能不是同一人；不标注就是设计歧义。
9. **聚合类列标口径待确认**：「账号状态」做聚合标签的前提是一个好友可能对应多个账号；一好友一账号时直接展示账号删除状态即可。好友与账号是一对一还是一对多没查清前，图上写待确认，不许自造业务规则。
10. **原型与 PRD 形态分叉时，不擅自按 PRD 重做原型**：定稿 PRD 是好友主视角，而在用 React 原型可能仍是主从视图——用户可能在等业务拍板用哪个。此时只做与形态无关的修正（列/字段/格式），形态切换等业务鉴定；否则做完一轮又被推翻。
11. **原型 mock 时间格式统一为 `YYYY/MM/DD HH:mm:ss`**（三个时间字段一律到秒、斜杠分隔）。改分隔符或精度必须同步改依赖该格式的比较逻辑：区间筛选是拿值 `slice(0, 10)` 跟 `<input type="date">` 的 `YYYY-MM-DD` 比，换成斜杠就**静默失效**（不报错、筛不出东西）——先 normalize 再比；改完跑 `tsc --noEmit` + lint。原型统一到秒后，PRD/TSV 里仍写「到分」的字段（如数据同步时间）要单独问用户要不要跟，不自行改文档。**1028 定稿：用户答「统一下」→ 三个时间字段全部到秒，文档侧（TSV、Demo PRD）写 `YYYY-MM-DD HH:mm:ss`，原型 mock 用 `YYYY/MM/DD HH:mm:ss`，两套分隔符各自成立，不要互相改平。**
12. **交互改版被业务否决时的退路：退回原交互，只加必要功能，不做二次改造**（1028 用户定）。好友列表抽屉式改版发给业务前，用户先把退路定死：业务觉得不行就按原来的交互，只「加导出和筛选两个功能」即可。理由＝抽屉式只是页面组织方式，不是能力增减，业务不认可就不投入返工。因此这类改版在提交业务前先把退路范围问清并记到看板，别等反馈回来再纠结要不要抢救。
13. **好友列表两条待办的设计口径**：①筛选「xxx 时间添加的所有好友」→ 直接复用既有「首次添加时间」表头区间筛选，不新造字段与控件，遵守既有筛选规范（就地展开、不回显 chip、无确定取消按钮）；「添加」定义＝该好友被任一导购首次添加的时间；一好友多账号时取最早还是分行展示，取决于好友↔账号是一对一还是一对多（未查清前标待确认，不自行定规则）。②导出 → 两个入口（全量导出 / 按当前筛选结果导出，含顶部综合搜索条件），默认只导列表 8 列、不导抽屉字段；超约定行数转异步任务中心 + 站内通知，不卡页面；权限只写「配了导出权限后页面怎么表现」，不枚举谁能拿到该权限。

## 五、产品设计方法论（1027 评审后用户定）

1. **先流程后功能**：系统流程图＋业务流程图双必项，画好过用户审后才动 PRD。
2. 每个字段先考究「用户输入 vs 系统获取」（哪个系统/什么时机同步），不确定反问用户，不默认。
3. 评审意见先归口（A 外部答/B 设计自拍附建议/C 开发排期）再动工；设计被业务否决时回「视角归属」找根因，不许改交互细节。
4. **现有技术实现不是产品设计的边界**（1028 用户定）。产品定完整需求，实现路径（新增枚举/复用现有字段/别的方式）归开发选型；源码取证只作佐证，不是「做不了所以缩需求」的理由。写文档时不许把「源码里没有」写成「所以产品不做」。
5. **降级发生在排期，不在设计**（1028 用户定）。要砍需求必须三条同时成立：①开发给出实现不了的结论与成本量级（不接受口头「做不了」）②业务方确认不急着用 ③拿得出「现有场景用不到」的具体场景。设计阶段先缩需求＝替业务做取舍。
6. **系统流程图＝时序图、业务流程图＝flowchart，且图先发聊天再落项目**——形态细节见本节第 10 条、交付纪律见第 11 条。
7. **需求链路有方向，别画反**：要新行为时是 `业务/运营 → 外销CMS → 大数据`——外销CMS 向大数据提「创建行为表」需求（表名、字段、属性、事件类型），**这一层外销CMS 是大数据的业务方**，不是大数据来找 CMS；图上在该段加 Note 点明这层关系。参与方清单与“不存在哪些系统”见本节第 13 条。
8. **交付形态＝mermaid 源码，不是图片**：用户明确要「给我 mermaid 语法，我去渲染看」——源码放聊天框代码块，不出 PNG 长图；只有用户点名要 PNG 才做图。产品视角图禁技术细节：不写接口名／请求方式／库名／中间件名，参与方只写业务认得的实体（业务/运营、外销CMS、大数据平台、短信中心、牛信云），不写 BFF、insight-server、StarRocks、SMP。
9. **图是双文档，改一处要成套升版**：`01-PRD套件/私域2.0一期_系统流程图.md`（系统链路 + 口径表 + 系统边界）与 `私域2.0一期_业务流程推演.md`（业务视角三条业务）同一轮一起改，各自升版本号并写变更日志；只改一份 = 两份互相打架。升版时对旧口径明确写「作废」（如「最多 5 条 AND」→ 三层组合、好友列表 18 列 → 8 列 + 抽屉），否则后人分不清哪版是现行。
10. **两图的形态不同，不能都画 flowchart**（现行定稿，覆盖旧的「一律流程图、禁时序图」）：
   - **系统流程图 = 时序图**（mermaid `sequenceDiagram`）：讲清谁先谁后、谁向谁要什么给回什么，阶段用 `rect` 分组（事件登记 / 配置 / 圈人固化 / 下发）。
   - **业务流程图 = flowchart LR**：讲业务步骤与判断分支。
   - 时序图里**人和系统必须分开声明**：人用 `actor`，系统用 `participant`；不许混写。
   - **参与方怎么定（1028 用户当场纠正）**：①**「开发」不出现在时序图里**；②业务与运营**合并成一方** `actor 业务/运营`；③CMS 一律写实名 **「外销CMS」**，不写「CMS」；④整体 3–4 个参与方：业务/运营、外销CMS、大数据平台、触达下发服务（实名待查证）。
   - **需求链路有方向，别画反**：要新行为时是 `业务/运营 → 外销CMS → 大数据`——外销CMS 向大数据提「创建行为表」需求（表名、字段、属性、事件类型），**这一层外销CMS 是大数据的业务方**，不是大数据来找 CMS。图上要在该段加 Note 点明这层关系。
   - 不出现接口名、库名、中间件名（BFF / insight-server / StarRocks 一律不写）。
   - 纯页面级增强（加字段/筛选/导出、好友列表）**不画流程图**，只在文档里给数据来源与约束表——凑图会被当场指出来。
11. **图先发聊天框给用户审，审过才落项目文件**：mermaid 源码贴聊天框 → 用户提意见 → 明确认可后才写进 `01-PRD套件/` 并提交。未经审就 commit+push 属于制造返工；已推错就 `git revert <commit>` 推回去并说明「项目已回到原样」，不要留着等下轮覆盖。
12. **断言产物不合规范前先看运行时渲染逻辑**：曾静态 `grep` 搜「14:20:00」断言线框图没做到秒，被用户当场反驳——文件里数据存到分，是 `displayTime()` 在运行时给它补 `:00`。验证要么在浏览器渲染态看，要么读源码里的格式化函数，不能只 grep 字符串就下结论（尤其 HTML 原型、带模板拼接的产物）。
13. **参与方只写真实存在且业务认得的系统，名字要有出处**（参与方清单、六渠道实际出口、牛信双身份见 `references/外销触达下发链路与参与方.md`）：外销触达链路的四参与方＝外销CMS / 大数据平台 / vivo 短信中心 / 牛信云；**外销没有 SMP 外部系统，也没有 BSP**（全仓库检索 SMP 仅 13 处注释、BSP 零命中），旧文档的「SMP 触达引擎」口径作废。遇到用户问「X 是什么」就如实交代来源与未查证边界。
14. **命名存疑时首选源码查证，不要停在「沿用 / 中性词」**：外销源码在公司机 `E:\projects\源码管理\外销\`（前端 `cms-global`、`global-guide`；后端六个微服务），**VPS 上没有外销源码**，所以取证派 Cursor（公司机）做只读检索，我们出五段式指令。服务归口速记：触达下发＝`global-cms-target`，营销＝`global-cms-campaign`，员工组织＝`global-cms-employee`，对外统一 API＝`global-cms-web`（BFF）；`global-cms-docs` 是外销自家架构 / ER / 大数据表规范，可当权威技术底稿。查证指令要写死：只读、禁改文件、禁点会落数据的按钮、查不到写「未在源码中找到」不许推断、不从内销源码推断外销结论。

15. **产品视角＝信息需求清单，不是技术交互方案**（1028 用户纠正：“不需要考虑我们用什么技术和大数据交互，需要想的是他们能提供什么信息给我、我们需要哪些信息”）。写“数据怎么回来”这类环节时只列：向大数据要哪些信息（行为清单、每条行为能筛什么、数据节奏、命中人群与标识、超量时的粒度）、用来干什么、给不给、不给的替代是什么；调用方式、接口粒度、明细还是聚合这类问题而给研发，不进产品文档。我们反向给出去的也只有两样：建表需求、取数时间约定。

16. **回答“这个我们本期能不能支持”时拆三层，不要一句能或不能**：①**CMS 本期能力**（页面能做什么：建行为、圈人、生成名单、下发）②**外部依赖**（谁提供、覆盖率多少——如 idmapping、国家字段）③**场景先天约束**（哪些渠道/圈选方式天然覆盖不到——如富媒体按 imei 下发、非存量用户无组织归属）。结论句式：“页面能力会做；能不能覆盖到人取决于 X 的覆盖率，这不在 CMS 范围；Y 渠道天然覆盖不到。”拆不清就会把外部数据缺口说成 CMS 功能缺失，或反过来替大数据承诺覆盖率。

## 六、行为定义 ≠ 圈人：两条链路（源码实证，详见 references/内销圈人与行为定义链路.md）

1. 保存行为定义只写 CMS（`smp_user_event` / `smp_user_event_field`），**不推大数据**；圈人是 CMS 自己生成 SQL 经 StarRocks JDBC 执行。别设计「发布行为定义给大数据」这类接口。
2. 真正的上游依赖是**事件配置**（表名 + day 分区 + 字段 + 属性可选值快照），CMS 只读不产 → 谁是维护方是外销第一要问清的事，也是流程图的起点。
3. 跨维度圈选靠映射表（IMEI/UNIONID/导购）；没有对应映射表，行为维度与人群维度只能保持一致。
4. 三个必须对外讲清的产品坑：时间条件左闭右开（选「到今天」漏今天）、布尔属性是 `is not null`/`is null`、人数缓存 8 小时 / 分析缓存 12 小时（结果非实时）。
5. 保存人群≠可触达，只有走分析链路才固化明细与门店分配，触达用 `dataId + day`。**这是内销机制，外销 MVP 不照搬**，见下条。
6. **外销 MVP 名单方案（1028 定稿，三档里的中间档）**：人数缓存、异步人群分析任务、day 分区全部砍掉。改为 → 保存人群时**一次性生成名单并落库、记录名单生成时间、生成后冻结**；要新数据就重新保存一次重新生成，不自动刷新；下发与导出都取最近一次名单，页面人数＝名单条数。不选“不落名单、下发时实时算”的理由：名单不可复核，发错发少没法交代。保留人数预估但不做缓存层，只靠前端防重复提交加“正在统计”状态。待研发确认：一次性落库名单的规模上限，超了要不要转后台任务。

## 七、限制类配置：先问底层字段，再谈界面配置

国家/地区、渠道这类「管理限制」，本质是二选一：**只落大数据行为表**（当普通字段属性、圈人时筛）还是 **CMS 再加一层**（行为定义上新增适用国家/地区、适用渠道）。判断依据三条：①谁填（业务在 CMS 勾 vs 大数据建表时定死）②要不要跨行为统一管理、随时可调 ③底层行为表有没有对应字段。

1. **没底层字段支撑的 CMS 配置＝摆设**：配了国家，圈人 SQL 加不出国家条件就根本不过滤。所以讨论顺序固定：先问各事件表（尤其 openid 维度）有没有国家/地区字段（字段名、国家码还是中文名、渠道是表内字段还是登记时标注），再谈 CMS 加不加那一层。
2. **openid 无国家 ≠ 没法定国家归属**（叶灿/李萌已确认外销 DMP 暂不承接 openid 标签，openid 本体区分不了国家）。**别就此下「只能总部发」的结论**：
   - 触达计划里的「所属国家」是**执行口径**——决定模板语言、「8:00–22:00」按谁的时区算、预算归谁、走谁的审批、运营能看哪些组织数据；它不决定发给谁。
   - 行为表里的国家是**圈选条件**——决定这个人算不算目标人群。
   - 两者各管各的，所以只要行为表（或手机号国家码）能给出下单国家，**按国家分开发完全成立**：泰国运营建泰国计划、圈「下单国家=泰国」，用同一张跨国行为表也能跑；非存量用户照样能按某国计划触达。真正覆盖不到的只有两类：用户没留手机号/邮箱，以及富媒体按 imei 下发。
   - 因此向大数据要的是：行为表有没有下单国家/站点国家字段（字段名、国家码还是站点 ID、覆盖率）；跨国混表的按国家过滤查询量能不能接受。
   - 只有行为表无国家字段、手机号国家码也补不齐时，才退到总部级计划——那要新增「一个计划跨多国发送」的能力，模板语言/时区/预算/审批全要另开分支，工作量不是一个下拉值。讨论设计方案前先问清业务：触达是按国家分开发，还是一个计划全球发。
3. **渠道与国家的来源不同**：公域/私域天然由数据源表决定（加好友/发消息类＝私域，浏览官网/App 打开类＝公域），可在登记事件表时贴一次标签，不必每张表加字段；国家不行——同一行为的多国数据混在表里，必须表内有字段才分得开。
4. **越早问越好**：「使用范围」在内销的真实含义就是「行为属性里可配置的字段范围，基于底层表字段实现」——CMS 侧属性列表本来就是底层表字段的映射，所以任何想让业务按某维度筛的需求，都先落到「底层表有没有这个字段」上。
5. **定稿口径（用户 2026-10-28 拍板）**：不做 CMS 那层限制，国家/渠道走行为表属性。预售两个时间段（预售时间段、核销时间段）＝**预售标签表字段属性**，事件配置（`smp_event_cfg` / `smp_event_field_cfg`）登记到位就自动进行为属性列表，CMS 侧不用新增控件；只需确认已登记且字段类型为时间。时间属性照旧有左闭右开坑（选「到今天」漏今天），写进交互说明。
6. **用户拍板只给结论时，按结论落地，不要把已定事项当问题重问**：他说「做好两个配置啊」就是定了（配国家/地区 + 配渠道），此时只把真外部缺口单列（例如 openid 国家字段要大数据答），不再追问已定项的粒度。粒度这类细节先给建议值往下走，被否决再调。

## 八、国家维度定稿（1028 晚，取代「行为定义加国家限制」）

1. **外销 CMS 侧只建一条预售行为定义、不含国家信息**；大数据**一张预售行为表多国共存**，不按国家拆表、也不按国家配多个行为。奥营建奥国的计划就用同一条行为。
2. **强制匹配落在使用侧**：行为定义里指定一个属性作为「国家属性字段」；圈人时系统自动用「该字段 vs 计划所属国家」强制匹配，业务不可改。不是靠字段名约定（字段改名就失效）。
3. **页面必须显性展示**「国家条件：泰国（系统固定，不可修改）」——不改值的条件不写清楚，业务圈不到人会以为条件配错。
4. 匹配规则只要求「计划国家命中该字段任一国家」；表里存单值还是多国码由大数据定；**行为表国家码必须与 CMS 计划国家码同一套编码**（最容易出事，要专项确认）。
5. 表里没有国家字段时：行为定义里选不出国家属性字段，圈人时提示「该行为不支持按国家圈选」，引导业务找大数据加字段。
6. 这比「行为定义加国家管理限制」好：限制由系统在使用时强制，不必业务每建一条行为都勾一遍；新增国家无需改配置。
7. **前提**：预售触达在外销 CMS 上按国家分开发（用户 1028 确认）。计划的国家决定模板语言 / 发送时段 / 预算 / 审批；行为表的国家只做圈选条件。两者不冲突。唯一冲突是「一个计划跳多国发送」——那是新增能力，按国家分开发时不做。

## 九、圈人侧行为条件的组合逻辑（内销实图实证 + 外销现状差距）

内销「筛选条件N(行为)」卡片里同时存在**两个独立的且/或层级**，回答用户问题或写交互说明时必须分层说，别混成一层：

1. **行为与行为之间**：卡片最左侧一条蓝竖线连通多个行为块，线中段一个**竖排大「且/或」**（且=蓝底选中）。吊多条行为才出现，单行为不显示切换器。
2. **同一行为内部、属性条件行之间**：行与行之间一个小号「且/或」。**它是随行出现的**——第一条属性条件没有切换器，点「+ 添加筛选」加出第二条后，两行之间才长出且/或。
3. **「并且满足」是固定文案，不是控件**：它表达「行为发生了、并且满足以下属性条件」，写到 PRD 里不能写成可选的下拉或与/或开关。
4. **时间范围逐行为生效**：每个行为块各自带一行「开始日期 至 结束日期」，各行为的「允许限制时间范围」互不影响——一个行为置灰不会连带另一个。
5. **属性条件之间的且/或已定稿**：同一条行为内属性条件行之间只有 且/或 两档，默认「且」，**没有「非」**；同一个属性**可以重复添加多条**（例如「核销日期 等于 10-21」或「等于 10-25」）。原型现在按「每个属性只能用一次」去重（`addAttrRow` 只找没用过的属性），做不到同属性两行，这条必须跟着改。
6. **外销定稿＝四层对称结构（1029 用户逐条拍板，取代旧的「包含/排除」）**：

   | 层级 | 控件 | 可选项 |
   |---|---|---|
   | 块与块之间（标签筛选块 ↔ 行为筛选块） | 横排三档 | 且 / 或 / 非 |
   | 块内组与组之间 | 竖排两档 | 且 / 或（有非吗？有——按用户口径组间也是且/或/非） |
   | 组内属性条件之间 | 竖排两档 | 且 / 或（**无「非」**，默认且） |

   - **组数上限：标签筛选块最多 4 组、行为筛选块最多 4 组**，两组各算各的。内销可无限加组，外销这期收敛到 4+4（差异清单要写缘由：本期只接预售一条行为）。
   - **「非」是打在组或块上的排除标记，不是连接符**：该层命中人群从最终结果里**全局剔除**，与它在链上第几个位置无关。用户举例：「组1 做非，条件是剔除买苹果4的人群，那就全局生效」——所以 A 且 非B 或 C ＝ (A 或 C) 减去 B。别把它当成顺序求值链上的一环去问「管到哪一组」。
   - **一个组对应一个标签 / 一个行为**（不是一组多条），所以「外部组内条目间」这一层不存在，向下直接到底属性层。
   - **旧「关系＝包含/排除」整条作废**：用户明确「没有包含、排除的说法了」。原来靠排除表达的规避已转化人群，改写成「标签组 且 非（行为组：预售状态=已核销）」，业务场景不变。
   - 落地时必须先把这四层拆准再动文档，务必分清「块 / 组 / 属性」三个词——曾把内销的「组内多条行为之间」当成一层，结果用户说外销根本没这一层（外销一组只有一条）。
7. **线上真实文案是原型与文档的用词基准**：受众筛选区块线上叫「标签筛选」，块内的组叫「条件组」，加组按钮「+ 筛选组」、删组「删除条件组」。文档里用「标签筛选块 / 行为筛选块」讲结构可以，**页面上必须沿用线上文案**，否则评审对照真系统会发现两个名字。线上漏斗第二层文案随渠道变（当前渠道显示「有imei号人数」），PRD 不能写死「有手机号人数」。

## 十二、事件标签的概念定义（写文档、画图、做讲解材料都不许走偏）

**事件标签不是营销标签，它不是贴在人身上的一个名字，而是一组属性条件的组合判定。** 说成「被打上了 xx 标签」是错的口径，一律说「命中 / 未命中 xx 事件标签」。

它是**两层组合**，混为一谈就会讲错：

| 层 | 组合对象 | 关系 |
|---|---|---|
| 第一层 | 属性之间（事件来源、关联商品、时间窗口、统计口径、触发阈值） | **且 / 或**（接一个属性时没有关系控件，从第二个起才出现） |
| 第二层 | 事件标签之间 | **且 / 或 / 非**，系统最多支持 **5 个**事件标签的组合 |

关键差别讲不清楚就白讲：

- **「或」不等于「部分失败」**：或有分支没满足，不代表标签不通过——至少一支点亮规则就导通。演示和文档都要点明这一句，否则受众会以为「有一条没满足＝这个标签没命中」。
- **「非」作用在标签层，不是属性层**：属性条件之间只有且/或、没有非；非是打在标签或组上的**全局排除标记**，与它在链上的位置无关。
- **未命中的标签经「非」翻转后是「符合剔除条件」**，不是「无意义」——「未买过」经过非正好等于「该促单」，这是组合逻辑最容易被讲反的一处。

做讲解材料（视频/汇报/图）时，两层要用**视觉上能区分**的语言与色系分别承载（属性层一套色 + 胶囊/电路造型，标签层另一套色 + 硬朗方块 + 大算子），并在画面上标出「第 1 层 / 第 2 层」，让人一眼看出这是两次组合而不是一次。

## 十一、流程图与分工纪律（1029 补充）

1. **业务流程图必须把「维护」和「使用」串成一条，不能只画使用侧**（用户当场指出：「业务流程图缺少了业务去维护用户行为的动作，你只是描述了如何在触达计划中使用」）。维护＝业务提行为需求 → CMS 向大数据提建表需求 → 大数据建表写入 → 业务在 CMS 新建行为并保存启用；使用＝计划受众筛选配条件 → 生成名单 → 下发。用 `subgraph MAINT` / `subgraph USE` 分两段、中间用一条边串起（配好的行为可被多个计划反复引用）。
2. **改动既有交付物前，先读仓库里的现版本，在原版上做增量**——用户把上一版系统流程图整段贴回来并问「这是昨天你给我最后一版的，在这个基础上做，你忘了吗」。重画一张简化版＝白干，且会丢掉旧版里已经定稿的段落（四方参与方、四段 rect、名单冻结等）。
3. **助手只做判断层：理关系、定地基、写指令、独立核验；改文档/改原型一律出指令交 agent**（用户原话：「你为什么要改？你把关系理清楚，把地基约定好，让agent去实现啊」）。判断层产出长这样：四层结构定稿 + 组数上限 + 非的语义 + 受影响文件清单；执行层交给 Qoder/Cursor。
4. **一个交付物一拍板、拍完再做下一个**：流程图 → 功能清单 → 字段清单 → 主 PRD → Demo PRD → 原型，每步停下等拍板。用户明确要求「节奏慢一点」，不要一次把五份都改完。
5. **给 agent 的指令要提前给「现状冲突的裁决口径」**：agent 会忠实报冲突但不会自己拍（例如本期不做清单与新口径打架、旧字段名残留、加粗风格、标题措辞）；提前写清每条怎么处理，否则每轮都要为格式问题多跑一个来回。
6. **砍功能不留尾巴**：用户明确「取消就取消了，不要再留尾巴，不做，干嘛给自己添工作量」。活动日志只记一句「删除 X」，不写取消原因、不留回看口子、不写替代方案。
7. **待确认项要收敛**：用户「一个问题出来不会立马去问业务」，所以待确认只留真外部阻塞项（每条≤1 行，注明问谁），技术实现类（导出限流分片、编码一致性、大表性能）一律归研发 SE，不进产品待办。
