# 内销 CMS：行为定义与圈人链路（源码实证口径）

> 结论来自内销后端源码只读取证（`insight-server`、`smp-scrm-web`，源码树在用户公司机）。文中表名是**代码默认值、可被配置覆盖**，不是生产实值；结论只覆盖仓库实现，不代表线上部署配置。做外销设计时按「机制」引用，不要按「表名」引用。

## 一、两条链路不要混

| 操作 | 源码确认的处理 | 与大数据的关系 |
|---|---|---|
| 保存行为定义 | 写 `smp_user_event` + `smp_user_event_field`，返回记录主键 id | 保存链未见推送大数据 |
| 人数预估 | 异步任务，执行时生成 SQL 统计人数 | 缓存未命中时经 StarRocks JDBC 查询 |
| 保存人群 | 存筛选条件，需要时异步统计人数 | 只统计，不固化明细 |
| 人群分析／重新分析 | 异步固化明细、门店分配、分析结果 | `INSERT … SELECT` 写结果表，再查结果 |

**对外口径**：内销 CMS 以事件ID 关联已有事件配置、保存业务可用的行为定义；圈人时由 CMS 自己解析条件、生成 SQL、经 StarRocks 执行。「行为定义主动同步大数据」和「大数据建表后自动生成行为记录」都没有源码证据，属未查证项，不许写成已实现机制。

## 二、执行层没有 HTTP 提交

`insight-server → DataSqlEngineService → StarRocksEngineService → StarRocksMapper → MyBatis + starRocksDataSource → JDBC`；Mapper 只有 `count` / `executeInsert` / `search` 三个方法。

- 没有「向大数据 HTTP 接口提交条件 JSON、等回调」的实现。
- 任务完成后是 **CMS → 浏览器** 的 WebSocket 通知（`SMP_CROWD_COUNT`），**不是大数据 → CMS 回调**；前端匹配 `taskId`，一分钟未收到转轮询 `taskResult`（约 2 秒间隔）。
- 字段名叫 `hiveTableName` 不代表直连 Hive API。

## 三、保存行为定义的要点

- 表名不是保存接口的输入：请求 DTO 无表名字段，服务端按 `eventId` 读事件基础配置补齐后落库。
- 保存属性只带 `id / description / enable / orgRestricted`，字段编码、类型、查询类型由基础配置补足——**改属性配置不等于改大数据表结构**。
- 分清两个动作：「更新属性」= 读事件字段配置（有哪些字段）；「查询属性值」= 先读默认配置，无默认则读 `smp_user_event_meta_data` 最新日期分区，**不是**对事件明细表做实时 `DISTINCT`。

## 四、圈人条件怎么变成 SQL

单行为模板：`select <行为主键列> from <事件表> where day='<partition_values>' and event_id='<eventId>'` + 时间条件 + 属性过滤。

- **事件表名与 `day` 分区值都读 `smp_event_cfg`**，不是前端传入、也不是行为定义表里的副本 → 这张配置表是整个圈人链路的上游地基。
- 人群维度 `type` 与单行为维度 `mappingType` 可以不同，跨维度靠 IMEI／UNIONID／导购映射表转换；**没有映射表 = 跨维度圈不到**（openid↔imei 类问题的真正落点）。
- 行为组「且／或／非」= 集合交集 / `union all` / 差集。
- 时间条件：空数组不过滤；一个值 = `event_time = 值`；两个值 = `event_time >= 开始 AND event_time < 结束`（**左闭右开**）。前端按 `YYYY-MM-DD` 提交且结束日不加一天 → 业务选「到今天」会漏今天。
- 布尔属性实际是 `is not null` / `is null`，**不是** `=1` / `=0`。
- 任务类型 10 预估 / 11 保存计算 / 12 分析；状态 0 初始化 → 1 执行中 → 2 成功 / 3 失败。

## 五、缓存与「能不能用」

- 人数缓存：key = MD5(统计 SQL) + 当天日期，默认 8 小时、默认开启 → **同一条件当天重复预估不跑 SQL**，业务会看到「改了条件人数没变」。
- 分析结果缓存默认 12 小时，命中时复用已有固化结果。
- **保存人群≠可触达**：保存只统计人数；只有走分析链路才固化明细、门店分配、分析汇总（三张默认结果表，表名可配置覆盖），触达与导出用固化后的 `dataId + day`。外销若要求「人群能用于触达」，就必须有这条固化链路和结果表。

## 六、产品必须对外说清的三句

1. 人数和结果**非实时**（有缓存），改条件后数字可能不变。
2. 保存人群不等于可触达，要跑分析固化。
3. 事件配置（表名、day 分区、字段、属性可选值快照）由外部系统维护，CMS 只读不产。
