# 方案文档的图与数据

适用：产品方案、迭代计划、上线报告、需求分析这类要给人看的产品文档。目标是让读者三十秒看懂一个机制，而不是读一页大白话。

## 一、先定载体：叙述 → 表格 → 图

优先级从低到高：**能画图就不写段落，能上表格就不写句子**。

自查法：写完一章，把每个自然段问一句“这一段能不能变成一个三列表”。能，就换。典型可以换掉的：

| 原写法 | 换成 |
|---|---|
| “我们有三种情况，第一种……第二种……” | 场景 / 诉求 / 为什么现方案不行 三列对照表 |
| “为什么要加这个能力”长篇论证 | 不做这个能力会出什么事，一行后果 |
| “权限大概是有些人能改有些人只能看” | 角色 × 动作 矩阵表 |

表格还有个副作用：写表时会发现某格填不出来，那就是还没想清楚的地方，正好转成待确认项。

## 二、核心机制必须有图

按机制类型选图，不硬套：

| 要表达的东西 | 图型 |
|---|---|
| 端到端怎么跑（谁触发、经过谁、产出什么） | `flowchart LR` |
| 带状态的实体（草稿/启用/停用/失效） | `stateDiagram-v2` |
| 多角色多方交互的时序与依赖 | `sequenceDiagram` |
| 条件怎么组合（AND / NOT / 排除） | `flowchart TD` 逻辑树 |
| 分期路线 | `flowchart LR` 或甘特 |
| 闭环/飞轮（A 产新数据反哺 B） | `flowchart LR` + 一条回流虚线 |

Mermaid 直接写进 md（公司 wiki 支持 md + mermaid 渲染），不另出图片文件。

**每张图都要配一句它要说的事**，否则读者自己解读，解读错了比没图更糟。图上也要实话：一期只闭合哪一段，就在图下注明“这一段后面几期才做”，不要把设想画成现有能力。

## 三、页面部分：线框，不是选项罗列

只要方案里涉及界面（配置页、弹窗、选择步骤），就要有线框。

**功能还没开发、拿不到真实截图时**，用 HTML/CSS 画线框（一文件多屏，浏览器直接打开），不要用文字描述页面。要点：

- 白底卡片 + 细边框 + slate 灰阶色系，重点元素用品牌色描边（如 `#415FFF`）
- 每屏上方标「线框 N ｜ 页面名」，下方标「谁会用、在什么流程的第几步」
- 关键交互用注释框（浅黄底）解释**为什么这样设计**，而不是解释它是什么
- 文档里必须写明：这是线框示意图，功能开发后补真实截图。不说明，读者会当成设计稿定稿

**真实截图优先于线框**：已有系统/原型的，一定截真图，线框只用于未开发部分。

## 四、数据：能指到出处，才写进文档

- 每个数字都要能指到**源文件 + 页码/页签名**。写不出来源的数字，删掉或标「待确认」，不要用“大约”“业内常见”糊
- 用户追问数据来源是常规动作，答不出就是硬伤；回答时给原文（标题 + 数字 + 同一页的附注），不给自己复述的版本
- **同一指标出现两套数**（不同版本的材料、不同统计窗口）→ 把两组数字并排列给用户判断谁对，**绝不挑一个写进去**。两套数并存时评审现场一定会被问
- 区分「我推断的取值」和「源文件写的取值」。源材料标「取值未知」的，就写未知 + 找谁确认；自己补齐的取值标成已知，是凭空造事实
- 从 PDF/PPTX 里找数字时，先确认工具真的能读到该内容：PDF 用 pymupdf 逐页 `get_text()`；PPTX 除了 `shapes` 还要看 `group shapes`、`ppt/charts/*.xml`、`ppt/embeddings/*`（内嵌 Excel）。
  检索数字用固定串（`grep -F`），不要用未转义的点号——`7.96` 里那个点会匹配任意字符，产生大量假阳性，害你以为找到了出处

## 五、交稿前自检

| 检查 | 怎么做 |
|---|---|
| 章节是否图文并茂 | 数一下全篇几张图、几张表；纯叙述章节超过两章就返工 |
| mermaid 是否能渲染 | 代码围栏数应为偶数，`\`\`\`mermaid` 块数对得上；正文里不应漏出 `participant` 这类图内语法 |
| 待确认是否可执行 | 每条写清「找谁」，并按「卡开发 / 待拍板 / 不卡」分档；混在一起等于没有 |
| 是否把设想写成现状 | 全文搜「已上线」「已支持」，逐条对到证据 |
