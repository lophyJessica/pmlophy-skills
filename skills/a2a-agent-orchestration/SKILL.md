# A2A Agent 编排

## 核心原则

**Hermes 是命令官,不是执行者。** 前端/部署/编译类任务,Hermes 只写五段式指令,不动手改文件/编译/部署。具体执行交给反重力/Codex/Gemini。用户不说"你改"/"你部署",绝不碰文件。

**排查/检查/机械活也交给 agent（0814 用户两次强纠正："你要是个人，我直接给你一巴掌"、"不要检查，这是反重力可以做的事情"）。** 范围比"改文件"更宽——包括：浏览器逐行 debug、批量替换（sed 清品牌名）、代码/功能排查（原型标注为何没效果）、日志深挖。正确流程：**现象 → 我写修复/排查指令（含已知信息+现象+范围）→ agent 排查+修复+build+部署 → 我验证**。我只有判断/指令/验收（少量 token），agent 承担排查/修复/构建/部署（大量 token）。曾犯：ERP 销售订单空白 + CRM 原型标注两个 bug 都亲自浏览器查了 20+ 工具调用——用户明确"这是反重力可以做的事情"。

**报告/日志归档路径按目标仓库的 AGENTS.md 走，不要拿其他项目的约定当默认值。** 写指令前先读那个仓库 AGENTS.md 的报告归档节：有的项目要求 `check-reports/`（forge 系），有的项目明令禁止在根目录建 `check-reports/`、要求统一进 `08-相关资料/审计报告/`（cms-project）。路径写错的结果不是报错，而是 agent 停下来弹确认卡、整轮白跑。

**能用本地 agent 就别用 Hermes 子代理（用户当场质疑过「为什么你做啊，不让 agent 来吗」）。** `delegate_task` 起的子代理烧的是用户自己的 Hermes 额度；只要活落在本地 Cursor/Codex/Qoder 能力圈内（尤其代码已推到 GitHub，本地能 clone），一律派本地 agent，我只留写指令与验收。批量源码/文档提取、逐文件读码、生成清单——都是本地 agent 的活，不是我的。

- **真要用 Hermes 子代理时（本地没 agent、或素材只在 VPS 上）**：每个子代理只给 **2-3 个页面或 1 个模块**。大仓库逐文件读会撞满子代理的迭代上限（50 次工具调用），撞满后拿不到汇总，白烧 token。
- **子代理撞上限不等于全废**：它往往已把中间产物写到磁盘（如 `/root/*.tsv`）。重派之前先去落地目录找它写出的文件，核对覆盖范围再决定补哪一块，别从头重跑。

**AI是执行者,人是判断者。** 指令的刀刃在PM手上——Agent只负责在红线内执行,不替PM做决策。Hermes 不识别图片,视觉类任务让用户直接找 Gemini。

## 工具选择

| 任务类型 | 用谁 | 原因 |
|---|---|---|
| **读 PRD 套件 → 一次性生成前后端（全栈）** | ~~Claude Code~~ → **Codex（或 Cursor 顶替）** | **Claude 已退役（2026-08-24 用户定："后面我不打算用 claude 了，太慢了"）**。历史：forge-scrm 一期落地时用过 Claude Code（Code 标签）成功产出（85API/17表/28路由、MVP 43/45 通过），但用户嫌慢弃用。全栈大活回 Codex Sol（质量优先），额度受限时 Cursor Agent 顶替 |
| 审计、分析、新文件生成 | Cursor Agent | 阅读 `@codebase` 精准,输出结构化报告 |
| 批量修改、从零搭建、梭哈 | 反重力(Antigravity/Gemini，用户称“美国大豆包”) | 优先使用已有套餐额度，原型与批量修改快 |
| 精确修复(单行/单文件) | Cursor Agent | 精确控制,不乱改其他文件 |
| 重推理任务(PRD对齐/状态机审计) | Cursor Agent | 审计统一交 Cursor，不默认消耗 Hermes 的昂贵中转额度 |
| 轻量任务(改按钮/加字段) | 反重力 | 速度优先,天生出原型 |
| **内网页面 DOM/结构取证、纯代码改动(改几文件+跑构建+自查)** | **Qoder** | **自带内置浏览器 + Browser 技能，能直接进公司内网测试环境抓 DOM；额度比 Cursor 宽裕，不需要视觉判断的活一律先派它** |
| 讨论、业务判断、拆任务、写指令 | Hermes | Hermes 做命令官，不和 Cursor/反重力重复劳动 |

**额度分层决定派活顺序（用户明确：Cursor 两个账号额度还是不够用，要多用 Qoder 摸它的能力边界）**：判据是「这活需要视觉判断吗」——不需要的（取证、逐文件读改、跑构建自查）先派 Qoder；需要照着设计稿还原 UI 的留给 Cursor，那才是它的长板。重推理/大规模重构才上 Codex。

**分工法则:** 反重力 = 快枪手(批量子弹),Cursor = 狙击手(一枪一个)。反重力出完代码后,Cursor 交叉审计发现毛糙。

### 浏览器取证类任务：派反重力 + ego lite，不要派 Codex

任务本质是「打开带登录态的页面，把真实数值读出来」（Figma 设计稿取数、内网页面 DOM/表格取证、真系统比对）时，工具选型与改代码完全不同：**派反重力 + ego lite**。

- **实测对照**：同一份 Figma 组件库取证，反重力 30 分钟交齐四份结构化数据且数值准确；Codex 同任务跑得更久仍未交付，且前一轮取错——把标题图层的字号字重当成输入框正文值、把画板尺寸当成组件本体尺寸。
- **原因**：ego 直接操作真实页面，能点进主组件本体读属性面板；Codex 在沙箱里读文本，容易停在画板/实例层。这是工具能力差异，不是指令写得不够细。
- **反重力的硬约束**：推理弱。指令必须是**纯取证**——明写「只抄不归纳、不总结、不给整改建议」。让它归纳设计原则、写结论、提优化方向，就会跑偏或自己编。判断与归纳留给 Codex 或我。
- **多层级页面别让它提炼**：写成「按页面层级原样摘录，标明每块属于哪个分组，不合并、不提炼」，否则它会自作主张编成「原则一/二/三」。
- **每个数值必须带来源**：Output format 里要求新增一列「来源」（读自右侧面板哪个字段 / 哪个图层名 / 哪个样式名）。说不出来源的写「未取得」——这是唯一能拦住它填猜测值的机制。
- **取不到就写「未取得」，禁止按常见规范推断**。设计规范、通用尺寸这类常识最容易被拿来填空，填出来看着合理但全是假的。
- **ego 前提**：ego 应用必须已在运行（报 503/连接失败 = 没启动，不是网络问题）；需要能启动外部应用的权限。卡住就让它先把已完成部分交上来，不要原地空转。
- **别双线重复跑**：同类取证任务一旦反重力已出活，立即停掉另一条 agent 线——同样的活已经有人交付，等就是纯烧额度。

### 终端统计类任务：给脚本文件，不要给管道命令

**反重力这类 agent 在「跑一串 grep/管道做统计」上会卡死在 shell 转义，不在任务本身。** 指令里直接写 `node -e "..."` 或 `sh -c "..."` 再往里套 grep + 管道，引号会被套三四层、每层吃掉一层转义，它会反复试「为什么这条 grep 匹配不到」，十几轮一条数据都没产出。

正确派法：**把全部命令写成一个 `.sh` 脚本（内容在指令里逐字给出），让它只做两件事——创建脚本文件、执行脚本并重定向到输出文件，再按输出填表。** 零转义，一次过。

判据：任务只是「跑一组固定命令 + 按结果填表」时，一律走脚本文件；只有需要它临场判断、逐层探查时才给交互式命令。脚本里也别让它自己"优化"引号或合并命令——指令里写死"逐字照抄，不许改写引号"。

### 文本型产物 vs 前端代码（用户 0809 定稿）

| 产物类型 | 用谁 | 原因 |
|---|---|---|
| 项目结构地基/context、PRD 套件、流程(Mermaid/状态机)、字段清单、功能清单、用例数据推演 | **Agent(Codex/Sol)** | 文本任务=目标明确+文件操作+批处理，Agent 闭环执行最合适（给目标→读文件→生成→交付） |
| 前端开发（页面/组件/交互/审查） | **IDE(Cursor/反重力)** | 代码=可视化+可控制+要迭代（看 Diff/改样式/跑预览/接受拒绝） |

**重要：这是"倾向"不是"铁律"**——突发情况（如 Codex 没额度）可把 Cursor 当 Agent 用（它内置 Agent 模式/Composer，文本任务也能胜任）。**不写进 AGENTS.md**（用户 0809 明确：避免僵化，会有突发情况）。定方向留余地 = 谋定而后动的弹性版。

### Gemini/反重力的 "乱做主张" 问题
反重力会自作主张——让删一行跳转,它能重写整个路由层。**对抗方法:**
- 精确指令: "只删不增、只删不改","最后一条改动是删除代码不是添加代码"
- 小模块分批: 一个模块改完验证再下一个,梭哈有风险
- 事后审计: Cursor @codebase 交叉审计,发现冗余路由树/重复 mock 数据/角色守卫缺失

**反重力能守规矩的模板（2026-09 标签删除实测成功）**：给它**要插入的完整代码块原文**（不是"加个删除功能"，而是后端函数全代码 + 前端操作列全代码，指明精确插入位置），配硬红线（只许新增这两段/禁 commit/禁迁移/禁权限/禁改其它页面），Output format 要求**贴 git diff + build 结果 + 端到端状态码证据**（创建→删除 200→再删 404 全流程）。这样零脑委托的反重力能做得干净利落、零越界。反重力最吃"原样贴代码 + 死红线"，不比它"理解意图"——意图一多它就跑偏，代码一给全它就照抄。


## PRD 产物质量门：颗粒度基线（2026-09 用户定，审 agent 生成的 PRD 时用）

用户对"什么样的 PRD 才算够细"有固定标准——**不是篇幅长，是章节齐 + 细但不啰嗦**。审 agent（Codex/反重力/娜美等）生成/返修的 PRD 时按这基线卡质量，缺章节、三问不过、有啰嗦句都要报：

**必含章节（缺一即不合格）**：概述/背景 · **功能清单**(每功能 ID+名称+作用+是否本期) · **流程**(主流程+分支含异常，谁触发/下一步) · **业务规则**(逐条 R##，条件→结果，含状态流转/权限/口径) · **交互规则**(按钮行为+校验时机+错误反馈+编辑权限) · 字段说明(类型/必填/来源/只读/快照/计算) · **页面路径**(URL/路由+入口+跳转关系) · 异常/边界(并发/重复/缺数/越权) · 验收标准(每条输入条件→预期结果，可测)。只读查询页可豁免部分章节，但须写明哪些"不适用"及原因，不能直接删。

**"够不够细"三问判据**（每章自查）：①边界清了没(谁能用/不能用、什么状态允许/禁止) ②条件全了没(触发→结果→不满足怎么办，正异常都写) ③能不能钉死(字段/状态/按钮/路径有具体名/ID/取值，不用"相关信息""适当提示"代词)。

**"啰嗦"判定（这些是废话要删）**：每字段补"当…则…"防御说明、"系统将自动处理"空承诺、跨章节重复同一条规则（三维度应分开：字段约束/业务规则/页面交互）、死状态/动作矩阵里没用的场景、"后续版本考虑"模糊承诺。**够细的写法口诀**：交互规则写全"交互动作+校验时机+错误反馈+编辑权限"四要素；验收每条"输入条件→预期结果"。

## 五段式指令格式

每次A2A指令必须包含全部五段,缺一段都别跑。**五段之前还要有一行抬头：目标仓库 + 执行者 + 工作区绝对路径。** 缺这一行，用户粘错 agent 或粘错机器时没有任何东西能拦住（→ 见「同一 git 工作区禁止派两个 agent」）。

```
Context:
[项目背景、当前状态、为什么改]

Request:
[具体要做什么,分条列出,精确到文件/行号]

Output format:
[明确输出什么——dist.zip路径/改动了哪些文件/编译成功或失败]

红线禁止:
- [禁止改vite.config/tsconfig/package.json]
- [禁止git commit/push]
- [任务特定的禁止项]

Checkpoint:
[编译通过后的下一步动作,或编译失败时的处理方式]
```

**「禁止 git」是硬性项，写成示例不算要求。** 用户代码提交一律他自己在 Cursor / Qoder 界面点，我方只给 **commit 备注文本**。指令里出现 `git add/commit/push` 即违规，即使项目 AGENTS.md 没写这条也不许加——`git add -A` 会把别人的未提交改动卷进同一个提交，而 agent 只看得见自己改的那几个文件，它编的备注与实际内容对不上，事后无法追溯。完整红线写法见 `a2a-instruction-format`（写任何 agent 指令前先读它；该 skill 已接近体积上限，新规则优先加到本 skill）。

**agent 为演示而造的样例数据，验收时必须问清触发条件。** 常见 seed 写法是「存储为空时才注入」（如 localStorage 无历史记录时补一条失败态样例）——用户本地早跑过、已有历史记录，就根本看不到那条样例，演示当场扑空。验收时让它说明「什么条件下会出现、什么条件下不会出现」，不要只看它自己的描述或它自己机器上的截图。

## Codex 全量诊断模式(调试必杀技)

**触发条件:** 同一个 bug 手工修了 3 轮仍未解决 → 停止猜测,交给 Codex 做全量诊断。

**为什么有效:** 手工 patch 循环受限于母 Agent 的上下文窗口——每轮 grep → patch → verify 保留同一个错误假设。Codex 开新 session 从零读两边代码,能发现母 Agent 6 轮都没发现的根因。

**实战案例:**
- Bug: CRM 转客户后 ERP 客户列表看不到
- 手动 6 轮: erpSync.ts 存在?→DB名 `forge_erp_db`?→Dexie v1 schema?→readTable 缓存?→baseDataApi async?→原生 IndexedDB? 全部基于一个错误假设
- Codex 1 轮: 读 CRM erpSync.ts + ERP db/index.ts → 发现 DB 名是 `qs_inventory_db` 不是 `forge_erp_db`,且需要 v1-v6 全量 schema 对齐

**指令模板:**
```plaintext
Context:[bug描述+症状+已尝试的修复]
Request:1. 读两边代码(A模块+B模块) 2. 对比 schema/名称/类型/版本 3. 找到精确不匹配 4. 从根部修复
红线:先读完两边再改
```

## 并行执行铁律

**多个Agent并行改源码时,每个Agent只改源码不编译(`不要 npm run build`)。全部改完后,人工手动一次性 `npm run build`。**

原因:多个并行Agent各自 build 出的 dist 会互相覆盖——后完成的覆盖先完成的,导致前面的修改丢失。

流程:
1. Agent A: 改盘点审核流(只改源码)
2. Agent B: 改报损审核流(只改源码)
3. Agent C: 改库存查询字段(只改源码)
4. 全部改完 → PM手动 `cd front-prototype && npm run build`
5. 一个完整 dist 部署

## 多项目并行编排：先核对"项目审计/返修状态矩阵"（2026-08-20 教训）

**编排多 Forge 项目（或任何有多轮审计/返修循环的项目）前，必须先逐项核对每个项目的状态——不要凭记忆/旧上下文推断。** 本会话因没核对，把已 P0 返修清零的 CRM/WMS 误判成"还需再审计"，被用户纠正两次（"我们不是完成审计了吗""P1/P2 还没收口"）。

每项目四问（以实际状态为准，别靠猜）：
```
① 审计做了吗（出过 P0/P1/P2 报告）？  ② P0 返修清零+部署了吗？
③ P1/P2 收口了吗？                     ④ 本轮该干什么（只读审计 / 返修 / 不动）？
```
并口径："**两个继续返修，一个先审计**" = 一条 ERP 只读审计 + 两条 CRM/WMS P1/P2 返修，独立目录并行。
开口/出指令前，先把这三个项目的状态矩阵列出来（审计✓/P0✓/P1P2待收口/本轮动作），对不上就先问用户或查线上，而不是顺口说"都还没做"。

## Claude Code 模式选择（2026-08-24 查证；⚠️ Claude 已退役，仅留档参考）

**桌面 App 是三个标签，不是"work/code 模式二选一"**：Chat（对话）/ **Cowork**（长时程 agentic 工作、Dispatch、跨会话协作）/ **Code**（软件开发）。写项目代码用 **Code 标签**（读 CLAUDE.md/AGENTS.md、管理文件、跑命令）；Cowork 偏编排/跑腿，不适合直接写代码。**终端 CLI** 更灵活：大活先 `claude` 进 plan 模式（读文档出方案）→ 用户确认 → Shift+Tab 切 acceptEdits 让它写 → build+自检。别把 Cowork 当 Code 用。

## Agent 修复文档期间用户并行补录 → git 冲突（2026-08-24 forge-scrm 实测）

**风险场景**：Codex/agent 在 Mac 上修复文档（如审计 27 项修复），同时用户把新确认（如问卷第二轮 9 项回复）补录进同一批 draft/context 文件并 push，两边改到同一文件 → pull 时冲突（`<<<<<<< Updated upstream` / `>>>>>>> Stashed changes` 标记），且 agent 的版本常是"不知道新回复"的旧版（会把已确认内容改回"待确认"）。

**防**：派修复指令前先确认所有待确认项已回收完毕（审计前先清问卷）。**解**（优先远端已 push 的权威版）：
- Mac 本地冲突且 agent 改动未提交：`git checkout --theirs <file>...` + `git add` + `git stash drop`，再 `git pull origin main`；或 `git reset --hard origin/main`（只留远端的）。
- 或 VPS 直接重写冲突文件为干净版 + commit + push，用户 Mac 上 `git pull` 同步。
- 判断保留哪边：已确认/已回收的内容（✅ 表格、回复原文、关键结论）优先于"待确认"旧版；冲突标记三行（<<<<<<< / ======= / >>>>>>>）必须删干净，别留半个标记。

## 并行返修后必做跨模块一致性复核（2026-08-13 CRM 6 模块实测）

**并行修多个模块（同仓库不同目录）时，每个 agent 只看到自己的模块——跨模块契约必然对不齐。修完必须加一轮"跨模块一致性复核"，否则等到上线前才发现。**

0813 实测：6 个模块并行返修（线索/商机/客户/合同/拜访/业绩），复核查出 8 项跨模块不一致：
- 同一事件字段命名不一致（合同 `crmContractId+opportunityId` vs 商机 `contractId+crmOpportunityId`）
- 同一同步状态枚举不一致（合同 `NOT_READY/PENDING` vs 商机 `NOT_TRIGGERED/PROCESSING`）
- 金额来源口径不一致（合同说签署金额下推 vs 商机传 `expectedAmount` 预测值）
- 状态枚举不一致（客户 `DISABLED` vs 拜访 `INACTIVE`）
- 业务规则冲突（客户模块"停用阻断执行" vs 拜访"已签到允许完成"）
- 入口冲突（客户详情能建合同 vs 合同必须从商机发起）

**流程：**
1. 并行返修（各模块独立 session，只改自己目录，红线"不碰其他模块"）
2. **返修完成后发一轮"整体复核"指令（第 N+1 个 session，只读）**——对照 audit-reviews/ 基线逐项核对修复状态 + 专项查跨模块一致性（字段名/状态枚举/金额来源/业务规则/入口）
3. 复核发现的跨模块问题 → 合并成一条"补修指令"（统一口径，以权威模块/SSOT 为准）→ 再跑一轮
4. 全部收口后才允许 git 提交/进前端

**复核指令要点：** 只读不改；输出格式"逐模块 P1/P2 状态 + 新发现问题分级 + 跨模块一致性问题 + 总结论（合格/需补修）"。Codex 复核 Codex 有盲区（同类错误看不到）——用户抽审 1-2 个模块兜底。

## 项目隔离

多项目指令必须拆成独立session,各喂各的项目目录:

- **forge-wms指令 → 开在 forge-wms 目录的session里**
- **forge-erp指令 → 开在 forge-erp 目录的session里**

禁止一个session里混喂两个项目的指令——AI会跨目录搜改文件,在wms目录喂erp指令可能跑去改别处的erp文件夹。

## 审计任务拆解

审计类大任务也拆成两个独立session:

```
Session A: forge-wms审计 → cd forge-wms → 喂WMS专用指令
Session B: forge-erp审计 → cd forge-erp → 喂ERP专用指令
```

避免AI读到两个项目的文件产生混淆报告。

## 跨平台多 Agent 团队（Grok Bot 总管+专业角色，2026-09 实测）

用户已用 Grok Bot（xAI，Grok 4.6 模型）组建"一个总管 + 多个专业角色"的 AI 团队（forge 例：Lophy-总管 + 需求调研管家/地基维护管家/PRD撰写助手/文档规范管家/跨模块架构师/原型核对员/PRD评审官），每个角色写进设定、同群协作、总管统一派活收结果。这是用户"多个 Hermes 协助 / 管家安排活,本地 agent 干重活"设想的落地雏形。

**孤岛坑（关键）**：这类外部 agent 团队的产出默认停在它自己的 workspace（如 `/workspace/shared/<项目名>/`），**不会流回你的真实仓库/pipeline**——它忙的是自己的那摊，看似在干活，实际没有接走娜美/Hermes 该干的活，"减压力"是假象。要让产出真正回链，得把它当"外部评审/产出工具"：**产出拿到主链路消化（Hermes 收口 / 落 forge 仓库 / 走自动流转管道）**，不是让它在自己环境里继续"改进闭环"（那个改不动你 VPS 的 pipeline）。

**额度坑**：Grok Bot 单文档计费，周配额默认 Grok 4.6（重模型），配置团队+全量读项目上下文一夜能烧 30%。搭建骨架是一次性高成本（值），但**别因兴奋让它并行跑多个角色继续扩活**——骨架完成后就收手，把剩余额度留给真正干活。跑量日常用轻量模型（deepseek/opencode），Grok 4.6 只留给值得的活。

**治理规则（用户 2026-09 实踩 72% 后定，硬纪律）**：**不主动派活 ≠ 不烧额度**——多角色一拿到上下文就自行往"下一步"跑（调研/评审/核对连环开干），你一不留神额度就呼啦啦烧完。必须：① **总管/队长做唯一派单口径**——所有任务经你→总管→按人分派，其他角色只许接单干活，禁止自己开新活、禁止互相甩活；② **没接到单默认待命**，谁都不许主动发起任务；③ **一单一角色**——一次只派一件事给一个角色，做完收结果再派下一单，别让多个角色并行扩活（并行 = 额度乘数级烧）。开场先给硬指令"没我命令谁都不许自己干"。

**能力边界决定能派什么（派活前先过这三条）**：Grok Bot 只有**远程桌面**——**没有内置浏览器、拿不到登录态、网络不在公司内网**。接单判据三条，缺一不可：① **输入自包含**（文件或粘贴内容，不需它自己登录/点击/抓取）；② **不依赖登录态与内网**；③ **输出是文档或代码**这类可脱机验收的东西。

**盘符权限会变，派活前先问一句能读哪几个盘，不要沿用旧结论。** 曾有“只能读 C 盘、得先把材料复制到 C 盘”的约束，后来用户直接开了 E 盘（`E:\projects\...`）——照旧结论写指令会让它白跑。与用户核实后写进指令的永远是它当下能读的绝对路径。

**派给「另一台机器上的 agent」（公司 VPS / 内网机 / 远程桌面）时，第一轮只能是只读盘点，不许改代码。** 它能不能干活取决于三条**环境前提**，与模型能力无关，猜错就白烧一轮指令：
  1. **拿不拿到代码源**——能否访问 GitHub / 内部 GitLab，鉴权覆盖到目标私有库没有（能 clone org 里 A 仓库不等于能读 B 仓库，`404` 先怀疑鉴权而非仓库不存在）；公司网络常常根本出不去 `github.com:22`，`ssh: connect to host github.com port 22: Connection timed out` 就是这条路走不通。
  2. **装不装得上依赖**——非 root 账号下 `corepack enable` / `npm i -g` 会 `EACCES`；需要内网私有源（如 `npm.vmic.xyz`）的项目只有公司网内机器装得了。
  3. **本地副本是不是最近的**——它报「仓库里没有某目录/某文件」时，先要 `git rev-parse HEAD` + `git remote -v` + `git rev-parse --short origin/main`，再自己核一遍远端。停在几周前的提交上，会得出「仓库里根本没这个模块」这种彻底相反的结论；说「fetch 成功但 origin/main 还是旧提交」属于自相矛盾，多半是 fetch 静默失败或 remote 指向了别的仓。

  三条任一不通就**停手换人**（换能出网的那台机 / 交给在用户自己机器上的 IDE agent），不要让它换个姿势重试第二遍——环境前提不是它能自己解决的。盘点报告本身就要给判据：路由条数、文件数、`pnpm -v`、`git log -1 --oneline` 这类可核的数字，而不是「已完成」三个字。

**插话能力差异决定“能不能中途纠偏”。** 部分执行者（Cursor / Qoder 这类）运行中不接受新消息，指令进去就排队，停不了也改不了；远程类（Grok bot）能接中途指令。推论：① 对不能插话的执行者，**发之前必须把所有约束一次写全**（尤其“同时只动哪些文件”和输出文件名），发现写错时只能等它跑完；② 需要边跑边看边改的活，派能给中途指令的那类；③ 不能插话的执行者正在跑时，**不要再给它发第二条**——它收不到，你以为在纠偏，实际两条指令会变成前后串行跑两遍。

- **可派**：批量文档生成/改写（PRD 章节、验收标准、字段说明）、独立数据加工（表格校验、字段清单转换）、自包含的小工程。**若用户已给这个 agent 开了仓库读权限**（如允许它直接读 `E:\projects\<项目>`），就不必再把材料复制到它的可读目录；但指令里仍要**列全可读文件清单**，并标清哪份是**权威源**、哪份是草稿（不标它会把草稿当结论引用）。
- **不可派**：任何「打开某系统页面看/截/点」的活（内网截图、DOM 取证、真系统比对）、需要访问用户本地仓库的活——这些交**有内置浏览器的 IDE agent（Qoder / Cursor，都在公司机）**。
- **切割方式：按产出物切，不按步骤切。** 每个 bot 一个自包含包（输入 + 输出格式 + 红线 + Checkpoint）；**不让两个 bot 写同一个文件**；**不让 bot 之间有依赖**（它等不了别人）。
- **真并行的分工原则**：一条线给「能进内网、能带登录态」的 IDE agent，另一条线给「只能吃自包含输入」的远程 agent——两类活同时开才叫并行；把内网活派给远程 agent，只会卡在那里白等。

## 把助手接进工作流：角色价值 + 数据放置（2026-10 定）

**角色价值：只会"中转"的 agent 没有价值，别把它排进链路。** 一个 agent 若只做"理解 A 的指令 → 转述给 B"，它**零新增信息、还引入失真**（转述会漏、会改动重点）——这是链路里最该删掉的一环。agent 只该占两种位置之一：**脑**（判断/指挥：定方向、写指令、验收）或**手**（照做：落库、commit、搬文件、跑脚本，不需要理解）。居中做"翻译/派活"的定位注定低价值，也最容易让用户一路填坑。设计多 agent 链路时先问一句：**这一环有没有新增判断或新增动作？没有就从链路里拿掉。**

**数据放置铁律（看数据性质，不看是谁说）：**
- **公司敏感材料绝不进个人 GitHub（含私有库）**——保密义务与竞业限制是两回事，竞业可解除而保密仍有效；把材料复制到个人外部平台本身就是风险。
- **敏感数据的版本管理留在组织侧基建**（公司自建 git / 公司机器）：日常 commit/push 由组织侧的"手"完成，助手不接这个版本库。
- **助手只处理非敏层**：骨架、模板、指令、结构、方法论；具体业务数据由人在组织侧填、在组织侧落库。
- **助手够不到内网时，用 IM 当零安装通道**（用户手机就能收发，受限内网里也不用装东西）——但通道 ≠ 存储：过手的内容默认不长期留存。

## 新工具/新玩法：先查证可行性，再谈草案（2026-09 用户纠正）

接手一个新平台/新 AI 能力时（如 Grok Bot、Muse、多 agent 团队、页面新形态），**不要一上来就画流程草案/设计方案**——先联网查证它的真实形态、技术边界、你能不能真正用上（地区/网络墙/配额），用户明确"不要先这么早做草案，还得继续查证，之前我们做 Jarvis 踩过很多坑"。想当然架构 → 实际跑一堆 403/不同步/loop 的坑。节奏：**验证可行性（能跑通吗）→ 再谈设计（怎么接进主链路）**。要用真实工具实测，别靠官方文档想当然。

## 多会话并行编排：先标归属，同一会话内串行

用户会同时开多个 IDE/外部 agent 会话（如 3 个 Cursor chat + 1 个 Grok bot）。编排规则：

1. **每条指令必须点名归属**：开头写清“发给哪个会话的什么活”（会话按用户自己的命名标，如 chat1 = 好友列表、chat2 = 数据报表、chat3 = 内销采集）。给多轮指令时，回复里先列一张“指令 → 目标会话”的对照表，再逐条给正文——不定归属就会出现“这条到底粘哪”的追问。
2. **同一会话内一次一条，串行**：跑完看它停下再发下一条；两条指令同时粘进去会互相打断或被当成一条。**并行只发生在不同会话之间。**
3. **开工前先查资源冲突**：两条活都占同一个浏览器/dev server 就不能放同一会话盖着跑——典型冲突：出图要起本地 dev server + 扫原型页，抓数要占线上页签。这类要么串行（先纠错类、后出产物类），要么拆到不同会话。
4. **别往同一个 agent 身上堆第三条**：已经跑两条时，第三条活优先分给另一类 agent（纯文档类交给无浏览器/无内网依赖的远程 agent），而不是继续加在同一个人身上。
5. **助手额度紧张时停手**：用户说“额度不够了、你先别做”时，助手只保留判断/写指令/验收，**执行全部派出去**；不要顺手自己开干（他额度信息比你先知道，会当场叫停）。

## 同一 git 工作区禁止派两个 agent 改同一批源码（2026-10 实测撞车）

上面「并行执行铁律」管的是 build 产物互相覆盖，**管不住更狠的一层：文件内容互相覆盖 + 归因彻底丢失**。

**症状**：Agent A 改完一批 CSS 并 `git add`，Agent B 同时在同一个工作区里读同一批文件、整体写回。结果：
- `git status` 里 A 暂存过的文件变成 `MM`（暂存区是 A 的快照，工作区已被 B 改写）；
- A 提交出来的 commit 是干净的（add 时刻快照），但**工作区已经不是 A 那一版**；
- 如果 B 读的是 A 改之前的版本、又整体写回，**A 的改动在工作区里已被抹掉**，后面谁再提交就是倒退还。
- 更糟的是多出几个"没人认领"的文件改动，谁都说不清是谁写的。

**规则：**
1. **一个 git 工作区同一时刻只许一个 agent 写源码。** 要真并行，就各自 clone/独立 worktree，产出回到主干前由人工合。
2. **`git add` 不是隔离手段，只是快照。** 它冻结了 commit 的内容，挡不住后一个 agent 改工作区。别把"我提交的是 add 时刻快照"当成隔离成功。
3. **审计类（只写 md）和改源码类可以并行**；两个都写源码的，排成串行。
4. **并行已发生后的善后顺序**：① 让人把还在跑的 agent 全停掉（这一步只有用户能做，你不能停别人的会话）；② **只留一个 agent 做只读清点**，跑 `git log --oneline -6` / `git status --short` / `git stash list` / `git diff --cached --name-only` / `git diff --stat`，全程不许 add/commit/checkout/reset；③ 拿到清点结果后 push 上来，自己 pull 核，**别根据三方汇报拼事实**。
5. **清点时要专门验"上一刀还在不在"**：重跑该轮的判据扫描（如归并后目标值只剩 4 种），出现旧值 = 被并行改动覆盖，不是"本来就没改"。

**指令抬头要同时标「执行者 + 工作区」，两个都写。** 只写工作区不够——用户手上同时开着 Cursor / ZCode / 反重力，粘错窗口是常事（本会话用户就把给 Cursor 的指令给了 ZCode，两个工具在同一份 cms 源码上撞车）。抬头写成一行，例如「目标：cms 项目 · 执行者 Cursor（公司 Windows 机 E:\projects\cms-project）」——执行者点错了，物标一行就能当场被叫住。

**同一模块同一轮只许一个写手，原型与文档不并行。** 文件不重叠不等于不撞车：改原型的 agent 和改文档的 agent 各自读一次现状，两边对「现在是什么」的理解就会分叉，结果是同一个口径你改一版、它改一版，源头永远落后于用户真正在用的代码。默认串联：一条完整指令 → 一个 agent → 跑完交付 → 用户 push → 我 pull 核代码 → 才开下一轮。只有「一方纯只读」才允许并行。

**我自己动手也算一个写手位。** 上一条看着像是在讲「怎么派 agent」，但同样约束我：用户本地开着 Cursor/Codex 在改同一个仓库时，我在 VPS 侧改同一批文件就是第二个写手，push 后用户 pull 必冲突，而且他本地 agent 的改动和我的改动谁覆盖谁说不清。

所以「回写文档」这类指令的默认边界是**只动文档层，代码一行不碰**：用户说「以原型为口径回写其他文档」的意思是原型已经改完、我只把文档对齐过去，**不是让我顺手把原型也改一遍**。即便看到原型有 bug、编译不过，也不要自己修——那属于用户的写手位；写进回复里告诉他，或写成给本地 agent 的指令。

判据：动手前问自己一句「这批文件用户本地是不是有人在改」。答案是「不确定」就先问，别用「顺手一起改省一轮」说服自己，一行手改换来的是一轮冲突处理加一次信任损耗。

**自己已经改过、用户本地又有改动时，主动给出可回退清单。** 被喊停后不要只是「好的我停手」，直接说清三件：我 push 了什么提交号、改了哪几个文件、要不要我把这部分 revert 掉只留文档层。用户按这个清单决定，比他自己去 diff 快。

**拆两个 agent 通常比一个 agent 全跑更慢——先问「这两半口径互相依赖吗」。** 判据两条：① 两边要不要引用同一个口径（字段名、数据来源、枚举值、页面形态）；② 是不是同一个工作区。任一条成立就串行交一个 agent 做到底。实测代价：原型改三批、文档就追三轮；两个 agent 在同一工作区跑，后跑的 pull 时把前一个未提交的改动卷进去，还得手动恢复一次。

**指令必须写基线提交号，且同一时刻只有一个写手。** 两条指令都写「先 pull 到最新」但 pull 时点不同（一条基于 A 提交、另一条跑完已到 B），两个 agent 就都在按「当前口径」判断，基准不是同一个状态——写出来对不上是必然，不是运气差。做法：指令抬头加一行「基线提交：<hash>」，且前后两轮之间必须等上一轮 push 完、我 pull 核完再发下一条。

**执行层不取交集，交集在编排层取一次。** 不要写「文档以原型为形态权威、原型没有的就删」这种让文档 agent 实时去读原型的条款——原型正在改，等于拿移动靶当基准。正确切法：原型一次改完冻结 → 我把最终形态提炼成一份逐条到文件行的口径清单 → 文档 agent 只按这份清单改，不读原型代码。一致性由我在中间收一次，不让两个 agent 互磨。

## 指令增补纪律与待确认收口（用户当场发火的两种情形）

**1. 主指令在跑时不要再堆增补指令。** 一轮只发一条；能预见的写进首条，写不进的攒到下一轮整包发。用户中途无法叫停重发，只能一条条贴，越贴越乱，agent 每收一条还得重扫一遍现状。只有「再不改就会做错整批」的事实错误才值得中途追一条。

**2. 每次给指令就要写死「改完不要提新的待确认项，其余保持现状不动」。** 文档/编码 agent 每轮交付都会再抛一批待确认，逐轮答复会形成没有尽头的循环（用户原话「这样没完没了了啊」）。处置写成三条：① 首条指令就封口；② 它抛出的每一条我方一次性给结论，包括「保持原样，当作定稿前记录」这种明确不动的判法；③ 无法当场给结论的，就指定它以哪一种默认值先落，不留给下一轮。

**3. 派活依据只认用户拍过板的，不认我们自己写过的东西。** 文档里出现过的结构（菜单归属、层级、字段、命名）很可能是某轮重做时我们写进去的，不等于用户定过。派活前先分开两类：「用户明确说过的」与「文档里写着的」——冲突时以前者为准；两者都拿不到时去问用户，不要拿文档当事实源往下推。反面案例：把某菜单写进一篇重做的 PRD 里，之后又照这份 PRD 派 agent 把菜单整块挪走，评审现场菜单直接消失。

**4. 改路由/菜单这类「全局引用点」的改动，先查引用再动手。** 路由路径会被别处配置引用（标注配置的 routeMatcher、权限资源树、旧链接重定向），改之前先 grep 引用面，能保留旧路径就别改；交付后要验证「旧入口仍可用 + 新入口能进 + 全局引用未失效」三件，不只验证页面能打开。

## 我下发的输入必须实测，不能估

指令里的每一个数字、路径、行号、枚举值，都是 agent 的执行依据。凭会话印象或上一轮输出填进去，错了当场反馈、白跑一轮，而且得让用户替你发现。

- **长数字串绝不从渲染输出里抄**。终端/工具输出会把手机号、unix 时间常数这类长数字打码显示（如 `+861****8295`），照着抄就是把我脑补的值当成仓库原值下发给 agent，agent 照抄后往仓库里写入假数据（实测发生过：误信 git diff 里被打码的号码，让 agent 把带星号的编造值写进源码，返工一轮）。核对号码/常数只读字节：`sed -n 'N,Mp' 文件 | grep -oE "'\+[^']*'" | od -An -c`；SQL 里的时间常数用字符串拼接绕开打码（`CAST('11644'||'473600' AS INTEGER)`）。凡「我给出的原值」，来源必须是 od/hexdump 或本身不含长数字串的证据。
- **计数先跑命令**。说「这份数据有 N 行」「命中了 M 处」，就先 `grep -c` / `awk` 数一遍。相邻数组贴在一起时极易把它们的行数加在一起（实测把 18 行报成 27 行），用户核一遍就发现对不上。不确定就写「以仓库实际为准，你核一遍报数」，不要给一个看起来精确的假数。
- **文案、规则说明、报错语涉及业务语义时，原文照抄已定稿表述，不自己编例子**。用户要求「说明要带一个例如…」时，第一反应不能是编一个听着合理的场景：业务语义一旦写反（把「数据更新后生效」写成「行为发生后实时触发」），原型和文档会一起错，而且下一轮审计才翻出来。没有拿来就用的定稿表述，就把原文用上并向用户说明「例子要你给准确口径，我不编」。
- **同一个口径在多个交付物里落点时，先把落点列全再发指令**。字段名、枚举值这类一改就跨文档、跨代码、跨截图，只改手边一份的后果是下轮被审计逐条翻出来。

## 复核类 bot 产出的回收与归档（跨类通用）

外部复核 agent（只挑毛病、不写方案的那类）交回来的**是线索，不是结论**。回收按这套走：

1. **归档到被审对象同级的 `复核/` 目录**（审某期需求档，就放 `02-需求调研/<期>/复核/`），不要塞进资料/审计目录——跟着被审对象放，以后找的时候不用跳目录。
2. **文件名带类别名，不只留编号**：`复核v1-第3类-遗漏边界情况.md`。只写“第3类”的编号离开上下文就不知道是什么。
3. **文件头加一行来源标注**：`> 来源：外部复核产出，非权威源。结论以 <权威源文件名> 为准。` 不标就会在几轮之后被当成我们的结论引用。
4. **按类分批 + 每条 Checkpoint**：先交一类确认格式与粒度，再放其余类；确认语只回“格式可以，按这个交剩下 N 类”。一次全开会导致格式跑偏后全线返工。
5. **驳回要回权威源核对后书面驳回**：交叉引用冲突的条目（如“A 处说独立配置、B 处说要依赖”）很可能只是两件事被读成一件事——回原文件看上下文，站得住的采纳，站不住的**驳回并让它在该清单标注“已撤回”**，不要默默删。
6. **回收后由我分三档处置，不照单全改**：① 结构性前提（上游能力/外部数据源未交付）→ 回写权威源的依赖节；② 口径错误 → 回原文核实后改权威源；③ 机械可修（外引路径/命名/过期时间）→ 我一次改掉，不占 bot 轮次。同一批问题**攻齐后一次性回写**，不逐条改。

**让复核 bot 优先干哪一类**：先要“遗漏的边界情况”和“漏写的依赖”——这两类直接决定评审能不能过；术语/措辞类放后面。

| 问题 | 根因 | 修复 |

| PRD改了但页面没改 | Codex只改了文档没改前端 | 分清工具:Codex审计不碰代码,反重力改页面 |

## 模型接力接力（2026-08-19 实测——Sol 烧完切 Luna）

Codex 有分层模型（Sol 强但烧额度快，Luna 省但质量略低）。用户策略：**大活/审计/返修用 Sol，Sol 额度见底（如剩 20% 以下）切 Luna 收口**。特征与应对：

- **同一个任务会出两份自检报告（首版 + Luna 收口版）**——不要误判为\"重复提交/又跑了一轮\"。Sol 首版先完成主体，Luna 接力复核/收口补验证（如补供应商门户账号验证）。发现同名/同任务多份报告，按时间先后读最终版，时间戳相近属正常。
- **Sol 烧额度的速度远超预期**（实测 3 小时烧完一天额度：多项目审计+返修+铺量标注同时开）——**用户明确：Sol 要\\\"看着用\\\"，不能当日常流水跑**。分层：Sol 只上关键大活（审计/复杂返修/重点模块），日常跑量（收口/批量标注/轻改动）用 Luna 或普通模型省额度。排活前先问用户额度余量/切模型阈值，按用户节奏分批（而不是默认无限跑），避免再出现\\\"3 小时烧光\\\"。
- **Luna 上线前给足边界**：Luna 质量低于 Sol——指令要更小步、更明确（一次只修几项、每项给期望结果）、验收到位（build 通过 + 浏览器实测重点路径），否则容易糊弄式完成。
- **OpenCode 是备用接力层，不是主力（0819 用户定）**：当 Sol 烧完 + Luna 也不够时，用 OpenCode（另一额度池）接力收口——但它\\\"扛不住大活，只能开小灶\\\"（跑批量标注/自检/收尾这类机械活），别再当主力脑。OpenCode 额度也烧完时，**兜底中转（awesomeai/DS 官方等）接最后一棒**。完整派发链优先级：Sol（关键大活）→ Luna（收口）→ OpenCode（备用接力小灶）→ 兜底中转。排活前先问清楚当前用哪个池、余量多少，按池子能力匹配任务（大活硬塞 OpenCode 体会不到：质量和额度都崩）。

## Codex 换账号接力 = 上下文丢失（2026-08-24 forge-scrm 实测）

**场景**：Codex 账号额度耗尽（被封/次抛号寿命到），用户换另一个账号继续 → **新账号会话是全新上下文，读不到原指令全文**。实测：补四模块 PRD 套件的长指令，换号后 Codex 只执行了第一个模块（资料库），其余三个模块没做（它根本没读到后面的指令部分），用户发现\"只让他跑了资料库？\"。

**规则：**
- **换账号 ≠ 无缝续跑**。长指令（多模块/多步骤）换号后必须**确认 agent 完整读到了指令**（让它复述任务范围/输出计划），或**分段重喂**（每段独立可执行，完成一段确认后再发下一段）——参考五段式里\"复杂任务可拆成分步骤\"原则。
- **多模块任务在设计时就要模块独立可执行**（每模块单独一段指令结构），即使换号丢上下文，重喂某一模块段即可续跑，不用整条重发。
- **验收时机**：agent 说\"跑完了\"不等于全量完成——检查 ai-reports 管道有没有对应自检报告（本会话：ai-reports 无新报告 = 实际上没跑完/没跑），或让 agent 列出\"完成了哪些模块、哪些没做\"，逐模块核对，不要相信笼统的\"完成\"。
- **\"已提交/已 push\"必须 fetch 核实（2026-08-26 两次实证）**：Codex 报告\"已完成，未 commit\"、用户说\"我 git 提交了\"、Codex 说\"我已经 push 了\"——三种说法都出现过**远程实际没动**（只本地 commit 未 push，或压根没 commit）。审查前先 `git fetch origin && git log HEAD..origin/main --oneline` 对比远程真实 HEAD，`git pull` 显示 \"Already up to date\" 不代表远程有新东西。**拿到远程 commit 才算数，口头\"提交了\"一律先 fetch 验证**。同理：**未 push 的 commit 一律不能当已验收**——它只存于对方机器的工作区，你 pull 不到、看不了 diff，任何"我核过了"都只是采信汇报。验收指令的第一句就该是"先 push，我 pull 核"或"把 git log/status 原始输出贴上来"，不要先审后推。
- **Codex 沙箱网络受限的兜底（2026-08-26 定，写进 AGENTS.md）**：Codex 沙箱（workspace-write）默认禁网，`curl: (6) Could not resolve host` 即使 `--noproxy '*'` 也无效（沙箱层禁网，非 Mac 代理）。指令里要求网络操作（上传自检报告）时：①命令带 `--noproxy '*'`（防 Mac 代理层）；②明确写"沙箱网络受限时不要反复重试，报告存 check-reports/ 随 git 提交 + 如实汇报'未上传'，由杰西卡 VPS 侧补传管道"。**沙箱同类症状一次认清（2026-10 复发确认）**：禁网 + 禁监听端口是同一条 seatbelt 策略，别当成三个 bug 分别查——① `npm run dev` 起服务报 `EPERM`（换端口无用）；② `git fetch/pull/push` 失败并报成 `.git/FETCH_HEAD` 写不进去（实为联网被掐）；③ ego lite 等要占端口的工具起不来。以前“没踩过”只是因为那些活不联网、不起服务。**注意：Mac 上改 `~/.codex/config.toml` 的 `[sandbox_workspace_write] network_access = true` 无效**——seatbelt 沙箱会无条件禁网、静默忽略该键（只有 Linux landlock 认）。真要让单个会话联网只能用启动参数 `codex --sandbox danger-full-access`，但等于放开整盘写入加联网，**不要为此改默认**；联网与起服务（`git pull/push`、`npm install`、dev server、ego lite）一律交用户自己终端或 Cursor，Codex 只负责改文件和跑本地构建。**禁止 agent 谎报"已上传"——无网络时诚实报告是验收底线**。

## 指令/文件改动先讨论再 push（2026-08-27 用户定）

写指令文档或改文件后 **不要立刻 push**——先把内容给用户看、讨论清楚，等用户明确说"可以 push / push 吧"再推。当天教训：审核范围我理解错两次（先写成"全部下线"，用户纠正为"人工免审+导入/AI 留审"），指令已推到远程才发现范围不对，只能删文件重写再推——远程历史里留下了错误版本。需求中途变化很正常，push 前确认 = 避免无效提交污染远程。git 先 pull 铁律不变；"讨论确认→push"是在它之前的第二道闸。

## 指令路径写参照目标必须精确（2026-08-27 用户纠正）

给 agent 的指令里引用参照物时**写死唯一准确路径，不写"A 或 B 二选一"**。当时 UI 统一指令写了"参照 ~/个人文件/copy-wms（或 forge-wms）"，用户质疑"这个是啥，为什么或者 forge-wms？"——模糊写法源于我没查证 Mac 实际路径，二选一会让 agent 困惑甚至找错对象。正确做法：不确定路径就先问用户或让 agent 实测确认，然后在指令里只写验证过的那一个。
