# 验收判据的写法与复核（agent 交付阶段验收）

写指令时的判据如果只写「grep X 应为 0」，agent 报 1 条命中时你无法判定算不算过，只能再问一轮。

## 判据写法

- 判据要写「命中位置必须是哪些」而不是「必须 0 条」。例：grep「包含」在筛选组件里应为 0，`ChannelStepForm.tsx` 里 `title="包含线上+线下购机用户"` 属触达用户池说明、与筛选关系无关，允许存在。
- 结构性重写类任务，判据要落到「操作后能看到什么」：切换关系后数字是否变化、第 N 行下拉能否选到同一字段、表头数量与顺序。纯 grep 判据挡不住功能没做。
- 要求 agent 报「实际数字与实测方式」（在哪个页面点了几次得到什么值），不接受「已确认无问题」。

## 复核 agent 自报

- agent 列的「以下是我按现有做法定的，请确认」是最容易埋错的位置，必须逐条质疑而不是整包接受。今天实测一条：标签块第 1 组沿用「不显示关系按钮」，导致第 1 组标不了「非」——而「非」是全局剔除标记、与所在分组无关，沿用旧实现直接把口径破了一半。
- 同类：把「组内条件关系」做成整组一个开关。逐条关系（第 2 行起每行一个且/或）才表达得了 A 且 B 或 C，整组开关表达不了。
- agent 为了编译通过而动了指令清单外的文件（如默认值里硬写了被废弃的枚举），这通常是**指令漏列**而不是 agent 越界。认下改动、限定只改默认值，并在下轮指令里把 mock/默认值文件补进清单。
- 已删除组件的标注残留（annotation-kit 等）不要在本轮顺手清，登记待办，等原型定稿统一处理。

## 阶段节奏

- 结构性改造（状态模型重写、列表重写）阶段一做完全部停下验收，不要让它连跑。一次走错后面阶段全白做。
- 验收时把「要改的三处」一次性给全，让它一轮改完再 push，避免「验收→改→再验收」两轮。
- 按用户实际情况决定验收取证方式：用户视障时，截图对他无效，要求 agent 用文字描述页面元素、默认值、切换后的实际数值。
