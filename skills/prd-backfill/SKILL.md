# PRD 回写（前端/代码改动 → 文档同步）

## 何时用
前端或代码改动已实现上线后，把改动同步回 PRD 及相关文档（含流程图），避免"代码改了、文档还停在旧版"的分裂。用户说"回写 PRD / 回写文档 / 把改动同步进文档"时使用。

## 核心原则
1. **忠实已实现**：只回写真实存在的行为；改动没做到的功能绝不写进文档。
2. **单一事实源**：代码/线上实测 = 已实现的事实源；文档（主PRD 等）是权威记录。两者冲突 → 以代码实测为准回写文档，并在修订记录标注。
3. **最小改动**：只更新本次改动涉及的那几处，不重排、不重构、不顺手修无关内容。
4. **联动一致**：同一处改动影响的多个文档要同步改，禁止只改一张（防文档间互相矛盾）。
5. **每次加修订记录**：日期 + 改了啥 + 来源/依据。

## 改动类型 → 要回写的文件（映射）
| 改动 | 必回写 |
|---|---|
| 新增/删除/改表字段 | 字段清单 + 相关 Demo_页 + 主PRD 功能项（+ 影响数据源则核心字段清单） |
| 改业务规则/状态流转/校验 | 业务规则规格 + 主PRD 规则表 + 流程图 |
| 改页面交互/布局/按钮/列 | 对应 Demo_列表页/详情页/新增编辑页 + 主PRD |
| 改权限/入口/可见性 | 主PRD 权限设计 + 业务规则规格权限段 |
| 新增/删除用户可见功能 | 主PRD 功能清单 + 验收清单勾选项 |
| 改流程/跳转/状态机 | 流程图（流程推演/系统流程）+ 主PRD |
| 通用（任何改动） | 主PRD 修订记录追加 |

**forge 模块套件常见文件**：`prd-docs/modules/<模块>/` 下 —— 主PRD.md、字段清单.md、业务规则规格.md、Demo_列表页/详情页/新增编辑页.md、业务流程推演.md、用例数据推演.md、验收清单.md。

## 先诊断「到底缺什么」：grep 命中不等于已经写好

用户说「这个功能评审版 PRD 里没有对应的原型页面」时，不要直接开工写—先分开查三层，因为他说的「没有」往往是下面三种之一：

1. **原型有没有**：在原型源码里 `grep -nE '<功能名>|重试|失败' <页面目录>`。命中了就说明页已存在，开口先报事实（「原型有，是 11-0X 某提交补的」），不要顺着用户的判断去重做原型。
2. **PRD 有没有**：`grep -nE '<功能名>' <评审PRD>.md`。命中不代表完备——要真读那几行：**条目是否四段齐全**（页面内容/交互说明/业务规则/待确认），只有一两行的条目就是没写完；同一条功能往往还有拆出的子条目（主条目写全了、失败态这种子条目却是两行），漏的总是子条目。
3. **截图是不是跟得上实现**：`ls -lt --time-style=+%m-%d_%H:%M <PRD>/images/` 看那张图的时间戳，与 `git log --format='%ad %h %s' -- <原型源码目录>` 的实现时间对比——**图比实现早就是废图**，不能因为图存在就当成已交付。
   
   **时间戳不老也不代表内容对：必须真看图**。存在一种更隐蔽的废图：文件名写着「失败重试」、时间也不算旧，画面里却只有「生成中」两个任务，既没有失败文案也没有重试按钮——它根本证明不了自己那条目。所以核对截图只有一条验收标准：**读图确认画面里真的出了问题描述的那个界面状态**（`vision_analyze` 问一句「这张图里有没有 X 文案和 Y 按钮」）。图与内容不符时，去查是不是有一张对的新图被挂到了别的条目上（常见：主条目挂对了新图，失败态子条目还挂着旧图）。

第四层常被漏掉：**同一批功能在多份文档里各写一套口径**。业务 PRD 的版本记录可能还写着「xx 机制由技术评估后确定」，而评审 PRD 早已把该机制定稿——`grep -n '<关键词>' *.md` 跨文件扫一遍，两边矛盾也要一并报出去，否则回写完这份、那份依旧是旧口径。

诊断完再向用户报「真缺口是哪一样」并按他的回复决定要做到哪一步，不要自行把「补文档」臆断成「重做原型」。

## 重出「整页红框图」的做法（坐标必须实测，不能估）

补截图时最常见的返工：框圈到了别的区域。因为视口宽度一变（1150→1600）整个布局右移，而框的坐标是上一轮写死的。固定顺序：

1. **先定视口再截图**：`cdp('Emulation.setDeviceMetricsOverride', width=1600, height=1000, deviceScaleFactor=1, mobile=False)`。不设的话浏览器窗口多大就截多大，同一脚本两次跑出两种宽度。
2. **把页面操作到目标状态**（打开抽屉/弹窗、造出失败态等），再**从 DOM 实时取框位**：
   ```js
   (()=>{const r=document.querySelector('<要圈的容器>').getBoundingClientRect();
        return {x:r.x,y:r.y,w:r.width,h:r.height,vw:window.innerWidth,sh:document.documentElement.scrollHeight}})()
   ```
3. **整页截图**：`cdp('Page.captureScreenshot', format='png', captureBeyondViewport=True)`，base64 落盘。
4. **按实测坐标画红色虚线框**（PIL 手画 dash，无虚线 API；框内缩 6px，且 `x2` 必须夹到图像宽度内——右侧抽屉贴边时算出 1591 会越界被裁）。
5. **画完再读一次图确认框对了**，这是唯一能发现「框对不上」的手段，不要凭坐标数字相信。

**要验证「点击后的交互」，就按状态链逐态截**：点重试前（失败+重试按钮）→ 点击瞬间（变「生成中」、重试按钮消失）→ 完成后（「成功」+下载）。三张图各圈同一区域，同一批命名（`05` / `05b` / `05c`）。只截首末两态，读者看不出中间发生了什么。

**原型里的状态是模拟的，PRD 要写真实驱动**：原型常见「种一条失败样例、点重试 2 秒变成功」——这是为了能演示。业务规则里要写「失败状态由服务端返回，用户点重试后任务回到生成中，完成后可下载」，不要把那 2 秒当成真实耗时写进文档。

**新图另存新文件名（带日期），不覆写旧图**：旧图可能已被粘进 wiki 并调好位置，覆写会让两边对不上；替换引用由用户决定。

## 回写步骤
1. **盘点改动**：`git diff` 或对比实现的改动点（改哪些文件、行为、行号）。
2. **定位影响面**：按映射查要改的文档，逐个打开看现状。
3. 只改受影响的那几处；忠实回写，必要时标注（如 "回写 2026-XX-XX"）。
4. 补主PRD修订记录（日期+变更+依据）。
5. `git status` 确认只动了该回写的文档（此时不应有代码文件混进来）。
6. commit + push，回报改了什么、依据是什么。

## 流程图回写要点
- 先分清：**【业务流程】**（业务动作，无状态/接口）vs 【系统流程】（含状态/接口/数据源）。
- 只在图上增删受影响的节点/连线/分支；保持整图结构与既有风格，**不整图重画**。
- 状态流转、库存过账、下推等细节只进系统流程，不污染业务流程图。
- 改完检查连通性：分支、回环、结束态不悬垂。

## 回写检查清单
- [ ] 这次改动有哪些行为变化？（盘点）
- [ ] 受影响文档都列出来、都改了？（映射遍历）
- [ ] 只改了受影响处，没顺手改别的？
- [ ] 有没有写进没实现的功能？（没做的不写）
- [ ] 文档之间无矛盾？
- [ ] 修订记录加了、依据标注了？
- [ ] git status 只有文档、无代码误改？

## 红线
- 不改代码（回写是文档活）。
- 不改未受影响的其他文档。
- 不臆造未实现功能；不加"建议"类内容（那是评审会/需求评审的事）。
- 流程图禁整图重画、禁给已跑通的图添新东西（用户铁律："我没让你加东西，只是把以前跑通的改到跑通就行"）。
