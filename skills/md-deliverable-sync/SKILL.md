# Markdown 交付档同步

## 何时用
交付的文档有「主稿 + 发布版」两份，或者要把它粘进公司 wiki 评审。典型场景：评审 PRD、方案文档、上线材料。

## 双档结构

| | 主稿 | 发布版 |
|---|---|---|
| 图片 | `![](./images/x.png)` 相对路径 | base64 内嵌 |
| 用途 | 唯一真源，日常改都是改它 | 单文件传阅，给评审看 |
| 能不能直接改 | 能 | **不能** |

发布版是派生物。任何时候都从主稿重新生成，不在发布版上做编辑。

## 先按形态认档，别按口头名字猜
用户口语里的「发布版」指 **base64 单文件**（复制到 wiki 给同事看），「评审 PRD / 评审版」常指 **引用版主稿**（自己看、要能改）。两个词在聊天里会被互换着说，而目录里现成的 `-发布版.md` 就是 base64 那一档。
所以接手时按形态判断而不是按名字：`grep -c 'data:image/png;base64' 文件` 有命中就是发布版，只有 `![](./images/…)` 就是主稿。搞反了就会把「先出发布版」理解成先改主稿，白做一轮。
判断不了就问一句「要的是能贴 wiki 的 base64 单文件，还是你自己改的引用版」——这比做错方向便宜得多。

## 铁律一：发布版只能重生成，不能就地改

按主稿的文本去发布版里做替换是个陷阱：主稿里是 `![](./images/x.png)`，发布版里是几千字符的 base64。替换会把内嵌图整段换成相对路径，**图片全丢**。

症状：文件体积骤然降一大截；不查图数发现不了。

生成做法：读主稿，正则 `!\[\]\(\./images/([^)]+)\)` 逐个读图片文件转 base64 写回。生成后必查三项：
- base64 图数 == 主稿图片引用数
- 发布版里 `./images/` 残留为 0
- 字节数量级合理，不会比上一版骤降

## 铁律二：成套交付，不做半套

一次改动 = 正文 + 配图 + 图引用 + 发布版重生成。四样都完成才算交完。

- 只改文字不换图：旧图画的是老交互，正文写成新交互，评审看到的是图文矛盾。
- 只改主稿不重出发布版：目录里两份内容不一致，误取旧版就按废弃口径开发。

**图必须重出**：交互、布局、按钮、弹窗形态改了，截图就得重截；不能用旧图顶替，也不能留着「图待补」交给下一轮。

**图还必须能证明它要表达的那件事（2026-10-30 实测踩坑）**：出了新图、有红框、文件也在，不等于图里有所要表达的状态。mock 数据不支撑时截出来是空验证——要求「标签超过两个显示 +N」，mock 每行最多两个标签，图里就只有两个标签，而交付报告写的是「全部图已重出」。判据：**每张图先问「这张图要证明什么，那东西在图里看得见吗」**，看不见就是没截成，要么补 mock 数据重截，要么明写「mock 不支撑，该交互无图」。

**截图脚本的出图清单是写死的，新交互不会自动进图**：项目里按角标批量出图的脚本（`capture_orm.py`、`capture_prd_redbox_private20.py` 这类）内部是一份固定条目列表，每条写死文件名、页面准备动作和圈选框选择器。本轮新做的交互不在里面，直接重跑只会把**旧条目**重出一遍，新交互全漏，而且图看着都是新的不容易发现。重出前先 `grep -c` 数条目、比对正文里新写的交互，缺的条目先补进列表再跑。

**派活也按成套派**：改文档的活交给 agent 时，一条指令里写全「实现功能 → 截图 → 替换图引用 → 核对正文与截图一致 → 重生成发布版 → 自检」，不要让 agent 只截个图、自己手改文字。人改文字 + agent 截图这种拆分必然留半成品，收尾没人认领。

**重复三次以上的动作必须固化成脚本，不要每轮靠记性。** 一轮交付里发布版会重生成十几次（改一段文字就要重来一次），每次都靠人记得跑 `embed_images.py` 和三项自检，漏一次就图文不一致。用户对这件事的态度很明确：要的是 **skill / 脚本一次生成到位，不是主会话后期加工**。所以：扫旧口径、核图引用与 images 目录、重生成发布版、跑三项自检——这四件应该装进一个脚本（形如 `deliver.py <主稿路径>`，一条命令吐结果），而不是每次手工按顺序敲。发现自己在一轮里手工重复同一个动作超过两次，当场停下来想「这个能不能脚本化」，而不是先把它做完。

**红框越界：坐标里加 `window.scrollY` 是错的（弹窗/抽屉类尤甚）**。给固定定位元素（弹窗、抽屉）算框时，`getBoundingClientRect()` 返回的已经是视口坐标，再加一次滚动量就整体漂移；而 `full_page` 截图里 fixed 元素只按截图那一刻的滚动位置渲染一次，两边坐标系对不上，框就飞到容器外、压在底层页面上。另处一个坑：框的外扩不要左右对称，`x` 不减 pad——弹窗内贴左的内容区再减几像素就顶出弹窗边框。固定写法：截图前 `window.scrollTo(0, 0)` 并等稳定，之后所有坐标一律不加 `scrollY`，宽高只向右下各加 2px（虚线本身有 3px 线宽，不会贴死）。两个算框函数（单个选择器与多选择器合并）要同步改，只改一个会一半好一半环。验收不要只看“图文件存在”，看框有没有完整落在内容区内。

指令分三段下，每段带自己的验收判据、做完停下自检再进下一段：①回写正文口径（逐条列改前改后摘要）②补脚本条目并重出图（列新增与重出的文件名）③脚本生成发布版（报图数、`./images/` 残留数、字节数）。

## 铁律三：先实现，再回写

做功能和回写文档是两件事。先让实现落地并实测验收（能跑通、能看到），再动文档。否则容易把「计划中的行为」写成「已实现的行为」，文档说有的东西代码里没有。

## wiki 粘贴适配（Confluence 等）

**表格列宽在 Markdown 里不可控，不要再改分隔行的短横。** 分隔行写几个短横**不控制列宽**：VS Code / Cursor 预览与语雀、Confluence 导入都按**单元格内容长度**自动分配，只有少数编辑器（Typora 一类）参考短横数量。实测把「页面说明」列短横从 3 个加到 11 个、原型图列加到 9 个，在 Cursor 预览和语雀里观感**完全没变**——先改短横再让用户去验证，等于让用户白等一轮。

用户提出「某列再宽三倍」时，直接给三条路并讲代价，让他选：
1. **在目标平台里手动拖列宽**（推荐）——一次几十秒，但重新导入文档后要重拖。用户实际选的就是这条；
2. **改表格结构**——图与说明从并排改成上下两行，不需要宽列，但行数翻倍、破坏「一功能一行」形态；
3. **换 HTML 表格写死宽度**——浏览器里效果确实好，但 wiki 与语雀都不支持导入 HTML 格式，且无法在上面直接写备注、无法作为存档件，每次改完还要重新生成一份。**结论：HTML 表格不作常设方案**——一旦两套产物，哪份是最新的就会打架。md 是唯一真源与存档件；只有需要好看的一次性展示（评审现场投屏、给领导看）才临时从 md 生成 HTML，看完即弃、不进仓库。


Confluence 这类平台只认 Markdown 原生语法：标题、表格、列表、加粗都正常，但**内联 HTML 的 `<br>` 会被过滤**。表格单元格是内联上下文，Markdown 列表语法也不生效，所以单元格内无法换行。

处理原则：
- **不要为换行问题重构文档结构。** 试过的路子（把页面说明拆成列表版、拆成主表+说明表、转 HTML、转 docx）都被否了：信息密度散了、可读性更差，或者格式不再是能改能回写的 Markdown。
- 保留原有表格和 `<br>` 写法，换行由用户在目标平台手工处理，这是确认过的分工。
- 不要在这上面反复试格式。一句话说清平台限制，然后按用户选定的格式交付。

## 口径要有载体，否则审计会反复判「无依据」
交付档里每一条确定性的结论（数据来源、唯一性规则、枚举值域这类），都要在仓库里有一个它能指回去的地方：全局的术语与口径字典、以及一张统一的待确认清单。
- **用户口头拍的口径就是依据**，但它必须落盘才算。只在聊天里说过、文档里写了结论，审计一 grep 找不到出处，就会判「仓库不能证明」→ 整改一轮 → 下一轮审计再判一次，循环不出去。
- 落地做法：口径写进口径字典（并注明「拍板即为依据」），需要外部方才能闭合的写进待确认清单（逐条写影响范围 / 问谁 / 不答的后果）。审计指令里加一条规则：已登记的口径不接受「无依据」质疑，已登记的待办项不计阻断。
- 这样审计的口子只剩一条：文档有没有按口径和待办如实写。

## 交付档不许出现的内容（逐条被否过）

- **「不纳入范围」整节**：用户原话「prd 不要写不纳入范围的」。范围章只留「纳入范围」表，不列不做清单；想交代边界就写进正文对应条目的说明里。
- **未经确认的业务场景**：业务场景每一条都要能在需求原文或已拍板口径里找到出处。自己补一个「看起来合理」的场景充数，用户会当场回「没有说到过这个，去除」——典型是给某个需求硬凑一个下游玩法（抽奖、赠送之类）当示例。
- **制作过程 / 自加的辅助节**：见下节自检。删完一处要回头补修改记录一行，写清删了什么，否则下次评审会问「怎么少了一块」。

## 改文档内容时的自检

- [ ] 分段标题后的段落，图引用指向的文件都存在？
- [ ] 删掉了某个分段（如空的「待确认」），是否留下多余的 `<br>` 或空表格单元格？
- [ ] 通用交互（弹窗底部取消/确定之类）还在单列成行吗？不需要，前文分节截图里已经能看到，单列是冗余。
- [ ] 主稿与发布版的章节数、图片数一致？
- [ ] 修订记录加了吗？
- [ ] **主稿里每一条功能/范围条目都能在原型上找到落点？** 审阅档是「审过就能开发」的交付件，挂一条原型上没有、功能清单里也没有的功能，评审一问就露。定位手法：拿该功能的关键词全仓 grep——只在交付档命中、原型代码与其他套件文档都 0 命中就是孤立条目。这类脏东西多半是历史评审轮次带过来的（某轮加进范围表、后来被推翻但没删干净），不是本轮新增，所以不能只看本轮 diff。处置两条：本期真要做但原型漏做 → 补原型；根本不该在本期 → 整条摘掉，并把它在范围表 / 业务规则 / 字段表 / 验收标准 / 流程图的所有落点一起清，只删一处它会在其余四处继续活着。
- [ ] **摘除后做了章节重排与留痕？** 删掉一整个章节（比如只挂该功能一个字段的「公共字段」）后，后续章与子节编号要全部前移，再全文搜一遍有没有引用旧编号；修改记录补一行说明摘了什么，历史行的旧表述保留当留痕（评审会问「怎么少了这块」）。最后全仓搜该功能关键词，除修改记录历史行外应全部为 0。
- [ ] **主要流程里系统流程图和业务流程图都在？** 两张图分工不同：系统图讲谁向谁要什么、参与方只到系统级（禁出接口名/库名/中间件名）；业务图讲业务视角全链路。只交一张就是缺项；脚本或旧结构带过来的单张「配置链路」类图不能顶替双必项。图源取项目当前那版流程图文档，不用历史截图；用户说「要重新设计的那版」时先盘点仓库里有几处 flowchart 文件、逐个列给他对号，不要自己挑一份就动手。
- [ ] **业务流程图有开始和结束节点吗？** 流程图规范硬要求：必须起于开始、收于结束。节点画成**椭圆**——`(["开始"])` / `(["结束"])`（stadium 形，左右两端半圆）；`(("开始"))` 是正圆、`["开始"]` 是方角矩形，两个都不对。开始节点接第一个业务动作，最后一个动作接结束节点。系统流程图（时序图）不需要开始/结束，那是流程图才有的。
- [ ] **开始节点在渲染出来的全图最前吗？（源码顺序不等于渲染位置）** 开始节点属于哪条泳道就写在那个 subgraph 内第一行——**不要为迁就布局把它挪到 subgraph 外面**，它本就是泳道内的流程节点。但 Mermaid 按连线自动布局，写在第一行也会被排到中途（典型位置：判断节点左下方），因为回流连线（「不满足则回到提需求」这类）会改变层级。所以验收标准只有一个：渲染出来的开始节点是否在全图最前。偏离时按序调：① 精简或改写回流连线；② 减少跨 subgraph 的连线；③ 还不行就把该泳道拆成独立一张图。用户会直接截图圈出来让你「重新理解开始节点的位置」，别拿源码顺序辩。
- [ ] **图用 mermaid 源码还是图片？** 交付档里放 mermaid 源码随文档走，不嵌 PNG、不引 `./images/` 的静态图。源码里的节点文字逐字照用、不精简不润色，两张图各自一个代码块不合并。
  - **图里写到、正文没写的口径，不要另开一节「流程要点」：用户明确要求去除这类自加小节**。需要补充的说明挂进已有章节（业务规则 / 交互说明）的对应条目里。图已表达的不再复述；实在只能图说、正文无处的风险点，先问一句要不要写，不要自己先加一节再被删。
  - **反方向同样要查：正文与功能清单里定了、图里漏掉的环节，要补成节点。** 用户会直接圈出图上某一块问「这里是不是应该显示 X」——那就是图漏环节的信号，不是他记错。典型：受众筛选中「预估人数」三层漏斗在正文与功能清单里都定了，流程图却从时间范围直接跳到「保存人群并生成名单」。改图时拿对应章节的功能清单逐条对图走一遍，两边都有才算完；只核图→正文单向必漏。
  - 往聊天里贴指令让用户转给 agent 时，**指令本身已经是一个代码块**，里面再放带三反引号的 mermaid 源码会嵌套围栏、把指令截断。做法：源码只给内容、不给围栏，并在指令里写一句「每张各自用一个 mermaid 围栏包裹，围栏你自己加」。

## Mermaid 能力边界（被问「能不能」直接给结论，别硬试）

用户会连续追问排版能力，把下表直接答出来，不要先改了再说不行：

| 需求 | 能不能 | 事实 |
|---|---|---|
| 泳道横向排、自左向右 | **能** | 把 `flowchart TD` 改 `flowchart LR` 即可，subgraph 跟着横排，泳道内节点也从左往右。改方向后开始节点的验收标准从「最顶部」变成「最左侧」 |
| 指定哪条泳道在上/在下 | **不能** | 位置全由布局引擎按连线算。想让单条泳道竖排可给它写 `direction TB`，需 Mermaid 9.0+，语雀/Confluence 内嵌版本要实测 |
| 几条泳道等高 | **不能** | subgraph 高度由内部节点数与层级算，没有设高度或最小高度的语法，`style` 只能改填充与描边。要齐只能把两条泳道层级数做接近（等于为对齐改编排），真要求等高就得换 draw.io 或导出 SVG 手工调，那就不再是能回写、能 diff 的 md |
| 表格列宽稳定控制 | **做不到** | 见本文「wiki 粘贴适配」节：分隔行短横不控制列宽，两条可行路径是平台里手动拖或改结构，HTML 表格不作常设方案 |

说清边界的同时给一条替代路径，比「我试试」有用。

**两个旧渲染器不认的语法，直接用就当场出丑（Cursor 预览与语雀都中招）**：
- **不用 `rect rgb(...)` 着色块**：旧渲染器把 `rect` 当组合片段标签、把颜色值当文字输出，图上直接多出一个写着 `rect [rgb(245,255,245)]` 的框。需要分段就用 `Note over A,B: ① …`，不靠背景色。同源的流程图文档（如 01-PRD套件 里那份系统流程图）也存着同一套语法，改一处要全仓 `grep -rn 'rect rgb'` 扫一遍，只改交付档会漏。
- **时序图不用 `actor`，一律 `participant`**：actor 人形图标比 participant 方框高，旧版渲染不给名称留间距，角色名会和第一条消息文字叠印。想表达「这是人」，在名称后加「（人）」——比如 `participant BIZ as 业务 / 运营（人）`。

## 红线
- 不在发布版上直接改文字。
- 不留图文不一致的半成品。
- 图没重出不说「已完成」。
- 不为迁就某个 wiki 平台改掉文档结构。
