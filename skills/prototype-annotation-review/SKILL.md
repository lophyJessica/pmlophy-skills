# 原型标注检阅（Reviewer 版）

## 角色分工（铁律）
- **执行者**: Codex/Cursor（装项目里，目录名 `prototype-annotation`，实际跑标注工作流）
- **检阅者**: 杰西卡 + 罗宾（我们——审标注质量，不出手改项目代码）
- **验收者**: 用户（最终拍板）
- **命名约定**（用户定，勿搞反）：项目执行侧目录 = `prototype-annotation`；Hermes 检阅侧 skill = `prototype-annotation-review`
- **修复实现交本地 agent，不要在 VPS 上手改代码（用户明确要求）**：我们负责定位、写清现象/范围/预期/验收、出五段式指令、最后独立验证；改 config、runtime、build、部署这类执行动作交 Cursor/Codex。哪怕改动很小、自己动手更快，也不要顺手做——用户会直接叫停（「不要自己做啊，浪费 token」）。例外只有用户当面说「你来」，而且完成后必须 push 并告知提交号 + `pull --rebase`。

## 核心理念
标注 = 外置解释层（左原型右标注，模仿 Axure 传统，AI 自动化）：
- 标注存独立 Markdown（annotations/*.md），不写进 PRD/业务代码
- 编译成 annotation.bundle.json（运行时只读）
- 页面加最小 hook（runtime.js + data-anno 锚点）
- 标注块有"来源"行（指向 PRD 文件/章节）
- 产物路径规范：`annotations/` 跟 PRD 走（如 prd-docs/线索管理/annotations/），编译 bundle 在原型 `public/annotation-kit/`

## 检阅清单（我们审什么）

### 0-b. 两条增量标注铁律（2026-10-23 用户定，与 forge 项目做法不同）

1. **只标增量，不标历史**：本项目（vivo 外销 CMS）标注范围**只包括本需求触及的新增/变更功能点**；既有功能、既有字段、既有列一律不上标注——**不要照搬 forge 项目的“全量标注”做法**。验收时多出来的历史标注项要打回去删。
2. **新增项必须用蓝色区分出来**：新增的菜单、功能点、列表列、字段、按钮，在原型与红框图里用**蓝色标识**（蓝色标签/色块/badge，既有项保持中性灰），否则评审时看不出本次到底加了什么功能、加了哪些字段。蓝色标识与标注块要同步（蓝色标的项必须有对应角标与详情）。

### 0-c. 复杂交互 = 标注模型必须带「作用域层」（检阅必查，缺一条即返工）

只要页面有弹窗、抽屉、多步向导、展开行，标注就不能只靠「一个 URL 对一批标注」——下面每条都是实测踩过的失效模式，规则先行：

1. **page 必须是路由表里真实存在的 pathname，不能是重定向路由**。写成重定向的 path（`<Navigate to=.../>`）永远不匹配，重定向后 pathname 已经变了 → 整页 0 角标、该页所有标注块全丢。
2. **同一 URL 下并存的多个 UI 状态不许各自当成独立 page**。弹窗/抽屉/向导步骤/展开行共用宿主页 URL，把它们写成 `/xxx/modal`、`/xxx/step2` 这类伪路由，要么永远挂不上，要么靠补丁全部命中。正解是「路由 page + 状态 state」两层作用域，runtime 按**当前激活状态**过滤。
3. **编号的单位是「当前屏幕状态」，不是页面**。一个页面上有几个状态（列表态、各弹窗、各抽屉），就是几套独立编号，各自从 1 连续；**同一时刻屏幕上只允许出现一套编号**——弹窗打开时宿主页那组角标隐藏，只显示该弹窗组。
   曾经的做法是「宿主页 1..n、弹窗接着编 n+1..」，实测被用户当场否决：列表态屏幕上是 `1,2,3,4,5,11`——中间跳号 6–10（那些在弹窗里），看到 11 会以为漏了 5 块，用户原话「同一个界面上序号自增，准确应该到 6」。**跳号本身就是一种错**，不是只有重号才错。
   落地要点：config 每块带清属于哪个状态组（`scopeLabel`）；runtime 判断当前有无可见弹窗（`[role=dialog]`、`.cms-modal` 一类），有就只渲染该组、隐掉宿主页那组。校验器要按「同一状态组内 id 连续且无重号」判，不是按 page、也不是按 routeMatcher 分组判。
   **这一条可以纯静态判，不必跑浏览器**：凡是 `scopeLabel` 以「弹窗 / 抽屉 / 弹层」开头却仍挂在 `screenState=host`（或未填）的块，直接判错，不用等线上点角标才发现跳号。实测过的画面是「列表态屏幕上是 1,2,3,4,5,11」——起因就是弹窗那 5 块元素在列表态不存在，整套编号按页面连排时中间空了一截。把它做成校验器的一条判据（按 scopeLabel 前缀 + 屏幕状态归属判），比人工在浏览器里逐页点角标快得多，也拦得住回归。
4. **`routeMatcher` 是覆盖「同一页面的多个等价真实路由」的工具，不是多作用域的替代品**。正当用法：一个表单页同时挂 `create`、`edit/:id`、`look/:id` 多个真实路由 → 写 `engage/(create|edit/|look/)`。两种典型错法都要判死：① 写窄——只写 `create$`，而用户实际从列表点「编辑」进的是 `edit/:id`，整页 0 角标；② 当万能钥匙——给每个作用域（含弹窗）都挂同一条正则硬凑匹配，把所有命中块同时算进同屏，直接制造上一条的撞号。看到「几乎每条都带同一条正则」先查作用域是不是被压平了，再决定是改窄改宽还是删，不要无脑删正则。
5. **编译期双向差集校验（必做，人工肉眼代替不了）**：config 的全部 selector 与源码全部 `data-anno` 取差集，两个方向都必须为空；config 的全部 page 与路由表取差集，两个方向也必须为空。缺锚点、死路由只有这一步能拦——靠人看 bundle 数量永远看不出来。
6. **死代码锚点要清**：旧组件被新实现替换但没删，同名 `data-anno` 留在文件里，一旦重新接上路由就是双份角标。grep 计数，同一 key 出现多次即整改。
7. **检阅按页实测角标，不看 config/bundle 数量自证**：打开线上 → 点入口 → 收集 `.vpa-badge` 的 textContent 列表 → 与该页 config 的 id 集合比对。缺号=锚点在不可见状态或不存在；重复号=多作用域撞车；整页 0 角标=page 与真实路由不一致。
8. **横向溢出会造成假漏标**：runtime 判可见时 `rect.left >= window.innerWidth` 直接跳过该元素，页面横向溢出时右侧按钮的角标会整体消失。检阅时视口要够宽或先滚到可见，别立刻判成标注缺失。

9. **配了 `screenState` 不等于运行时认它——先验 runtime 版本（实测坑）**：config 里给弹窗块配好独立状态后，线上仍可能表现为「列表态 1..n 正常，弹窗一开变成两套编号叠在一起」。根因往往不是 config 写错，而是项目里的 `runtime.js` 是旧版：老版本 `currentPageAnnotations()` 只按路由过滤，全文没有任何 `screenState` 处理，配了等于没配。判定命令：
```bash
grep -c "ScreenState\|resolveActiveScreenState\|visibleScreenStatesOnPage" <项目>/public/annotation-kit/runtime.js   # 0 = 旧版，必须换
diff -u <项目>/public/annotation-kit/runtime.js <skills>/prototype-annotation/assets/annotation-kit/runtime.js    # 看差了多少
```
   唯一真源是 skill 的 `assets/annotation-kit/runtime.js`，项目里那份只是副本。同步前备份项目那份；同步后必须重新 build + 递增 `?v=` 才生效，否则会撞上缓存、又被误判成「改了没效果」。凡是 config 新增了 runtime 要读的字段，落地前都先问一句「项目里的 runtime 认识这个字段吗」。

10. **实测角标必须覆盖四种屏幕状态，只测列表态等于没测**：① 列表态——宿主页组应完整、无跳号；② 点主操作打开表单弹窗——宿主页组必须整体消失，只剩弹窗组；③ 点行内操作打开二次确认类小弹窗——应是另一组编号、从 1 开始；④ 带参数的页面——新建/编辑类页面常要 `?channelType=...` 之类参数才渲染表单，裸 URL 只挂上页级块，看着像「漏标」，先补参数再判。少测一种，「弹窗打开时两套编号并存」这类问题就会漏到评审现场。

11. **虚线框要按「有没有标注」判定，不能按「有没有 data-anno 属性」**：override.css 里那条高亮规则如果写成 `body.vpa-mode-annotate [data-anno]:not(...)`，进入标注模式后**页面上所有带锚点的元素都会画蓝虚线框**，不管它有没有对应的标注条目。标注删了、锚点还留在源码里，就变成一片点开什么都没有的空框——用户的原话是「这是以前的功能，为什么还有标注虚线框」。
   治根分两层，缺一层都会复发：① runtime 在**真正挂上角标之后**给该元素加标记 class（如 `.vpa-anchored`），CSS 选择器改成认这个 class，而不是认 `[data-anno]`；每次 `measureBadges()` 开头先把旧标记全清掉，避免切页残留。② 把已经无标注引用的锚点从源码删掉（只删 `data-anno` 属性，元素和样式不动）。
   只做②不做①，下一个 PRD 换一轮锚点又会冒空框；只做①不做②，源码里会长期堆着没人用的锚点。
   检阅法：源码全部 `data-anno` 与 bundle 实际引用的锚点取差集，有输出就是会画空框的那批：
```bash
grep -rhoE 'data-anno="[^"]+"' --include=*.tsx src/ | sed 's/data-anno="//;s/"//' | sort -u > /tmp/src_anchors.txt
# bundle 侧按 target.selector 里的 data-anno 提一遍，再 comm -23 /tmp/src_anchors.txt /tmp/bundle_anchors.txt
```
   注意 `data-anno` 在 JSX 里也可能写成驼峰属性表达式，字面量 grep 会漏，以 check 脚本的 `--src` 双向差集为准。

实测取证步骤、判定表、校验命令与修复方向见 `references/complex-interaction-scope.md`。

**补充（2026-10-24 实机验证，三条落地细节）**：
1. 状态用 `scopeLabel` 字段标注（如「弹窗：新建/编辑行为」「受众筛选-行为页签」），面板以绿色标签展示——评审才知道这块要点什么操作才看得到。
2. 需要操作才出现的区域，面板要把它列出来并标「需操作后查看」（runtime `annotationTargetExists`）；检阅时**别只看角标数量判漏标**，先开面板看条目数。
3. 发版前固定这两条命令，只跑 compile 不跑 check = 没验收：
```bash
python3 <skills>/prototype-annotation/scripts/compile_annotations.py "<迭代>/annotations/annotation.workspace.json"
python3 <skills>/prototype-annotation/scripts/check_annotation_assets.py <项目>/public/annotation-kit --src <项目>/src --routes <项目>/src/App.tsx
```
4. **人工找锚点时别用字面量 grep 就下结论**：`data-anno` 在 JSX 里常写成表达式（`data-anno={index === 0 ? 'xxx' : undefined}`），`grep 'data-anno="xxx"'` 会漏 → 误判成「锚点不存在」。要么用宽松模式（`grep -rn "data-anno"` 看全部再筛），要么直接交给 check 脚本的 `--src` 做双向差集。

### 0-d. 标注按迭代治理：随迭代生、随上线死（用户口径，铁律）

标注不是原型站的长期资产，是**一次迭代的一次性产物**。按这条治理，就不会出现「历史标注越堆越多、看着像全量标注」：

1. **标注的单元是「一个 PRD」，不是页面、也不是整个原型站**（用户定）：一个 PRD 的范围标一轮，该 PRD 走完就把它那套标注整批撤掉，再进下一个 PRD。做的是「按 PRD 范围标注」，**不是全量原型标注**——全量标注会让历史条目越堆越多，评审看不出本次到底加了什么。多个 PRD 并行时各自的标注共存（按 PRD 目录分开存），互不覆盖，这是允许的正常状态。标注目录跟着 PRD 套件走，新 PRD 新建，不在旧目录上追加。
2. **原型端只有一个「当前迭代」的标注包位置**，编译覆盖式写入（`public/annotation-kit/annotation.bundle.json`）。切下一轮 = 直接覆盖，天然不累积。
3. **`annotation.workspace.json` 只允许一个输入源**，就是本迭代的 `annotation.config.json`。**禁止把原型 `public/annotation-kit/` 下的编译产物再当输入源**——那等于自己复制自己，编译出来的标注直接翻倍，查半天以为是 runtime 重复渲染。
4. **上线即下线**：本轮上线后把原型端 bundle 的 `annotations` 置空并重新构建，原型回到干净状态；PRD 目录里的 `annotations` 源文件**留档不删、也不再部署**（以后复盘还能翻到当时怎么标的，删了只剩 git 历史）。
5. **新迭代开工前先确认上一轮已下线**，否则两轮标注在同一原型上并存，评审对象不干净。

### 0-e. 重做一轮标注的标准流程（实跑通过，顺序不可颠倒）

判定标准：现有标注「显示不出夹」是修复问题，「标得粗/标得偏」是重做问题——前者改 config/runtime，后者必须整轮重来。重做的固定顺序：

1. **盘点先行，不许直接写 config**：让 agent 读本迭代 PRD 套件，只产出三样——① 应标块清单（页面 / 属于哪个状态 / 功能点 / 锚点 / PRD 出处）；② 与现有条目的三分类（已覆盖且够细 / 已覆盖但太粗需拆 / 完全缺失）；③ 每页按 routeMatcher 分组的编号方案。交完停下等用户点头。跳过盘点直接写，必然又按页面大区聚合回去。
2. **块数要收，不能照单全收**：agent 会把页面上每个区域都列成块（分页、通用空态、纯展示列）。判据——**角标的价值是「评委会在这块找不一致」**，无特殊规则的块（分页条数、通用空态、纯展示）并进邻近块，不单独占角标。同理，本期 PRD 写「引用、不展开改造」的页面不按重点页面标（收 4–5 块即可），标多了违反只标增量那条。
3. **锚点先于 config**：config 的 selector 必须指向源码里真实存在的 `data-anno`。缺锚点先补锚点——只加属性，不改 DOM 层级、不动业务逻辑、不改文案样式，改完 build 并在对应页面用 `querySelectorAll('[data-anno="…"]').length` 数一遍。
4. **一个属性只挂一个节点**：同名 `data-anno` 挂多处时 runtime 的 `querySelector` 只取第一个，角标指向哪个节点就说不清了（实测一次挂 3 个）。列级语义（每行操作列）是例外，但要确认页面上仍只出一个角标。
5. **agent 报「源码里没有这个锚点，我不自编选择器」是正确行为**——接受并让它补锚点，不要逼它猜一个 selector 出来；它猜出来的选择器能让编译通过，但线上永远挂不上。
6. **八步全链路**：盘点确认 → 补锚点+build → 写 config/md → compile → `check --src --routes` → build → 部署 → 线上逐页点角标比对 id 集合。每步停一次，别合并。
7. **compile + check 全绿 ≠ 没丢标注**：重写 config 时若只写本次批次，上一版里其它页面的条目会被整体替换掉，而 check 只校验现存内容、**不会报「少了什么」**——它给出 `pages: N`、`annotations: M` 全绿，丢掉的页面一声不响。所以重写后必须自己按页对账：把 bundle 按 `page` 分组数条数，与上一版的「页数 × 每页条数」逐页比对，页数或某页条数变少就是丢了。丢了从 git 历史把原条目**原样恢复**（不许顺手按新规范「优化」），恢复后重编译再校验。
8. **空壳块不该独立占角标**：如果一个块除「待确认」外各 Tab 全是「待产品补充 / PRD 未定义」，说明 PRD 根本没这块的规则，挂个角标等于给评审看一屏「未定义」。处理是把它的待确认并进邻近的实体块（如并进表格块），然后删掉这块并让后续编号顺移。
9. **恢复或保留旧块之前，先拿 PRD 的纳入/不纳入范围逐页核一遍**：为防止丢数据从旧提交恢复整批条目的做法本身对，但恢复的是「上一版有什么」，不是「本期该有什么」。实测恢复后 39 块里有 14 块超出本期范围——两个页面被 PRD 明确写在「不纳入范围」（平台自产报表、权限中心侧标签树配置改造），另一组标的页面 PRD 只写「引用既有能力、本需求不展开改造」。用户一句「这不是以前的功能吗，为什么还有原型标注」就把问题点破了。
   固定加一步：重做/恢复后按 PRD 的「§x.1 纳入范围 / §x.2 不纳入范围」逐块对账，超出范围的整体移除，不要因为「上一版有」就留着。交付时同时报两个数——**PRD 纳入范围的块数**与 **bundle 实际块数**，不等必须逐块说明原因；只报后者等于没有尺子。
   检阅时同理：拿 PRD 范围节当标尺，不要拿「比上一版少了什么」当标尺——后者只能发现丢块，发现不了多块。


### 0-f. 标注产物入库核验：先找对工作区，条数自己数

交付方可能在另一台机器（用户 Windows 工作区）做标注，VPS 仓库里没变化是正常的——**先确认活是在哪台机器的哪个工作区，再谈提交**。下面四条是查证顺序：

1. **被跟踪的源是 `public/annotation-kit/`（`annotation.bundle.json` + 每页 md），`dist/annotation-kit/` 是 build 产物且被 .gitignore**。VPS 上 `git status` 干净只说明这个仓库没改动，不能推出"这轮标注已提交"。
2. **条数自己从 bundle 数，不引用执行方或自己记忆里的报数**：解析 `annotations[]`（每条带 `page` / `routeMatcher` / `order` / `scopeLabel` / `key`），按 `page` 分组计数，与"每页预期块数"逐页对账；总数相等但分布不对同样是错（重做批次常是"两页新细化 + 其余页保留旧粗粒度"，各页条数不一样才是预期）。
3. **发现 bundle 里的条数与对话里报的条数不符时，先判"活根本不在这台机器"**，别急着怀疑编译丢条或 runtime 重复渲染。
4. **提交前问一句并发情况**：同一工作区是否还有另一个 agent（反重力/Cursor）在改文件；有就按路径收窄 `git add`（命令写法见 skill `git-workflow-conventions`），并在 push 后立刻告知提交号 + `pull --rebase`。

### 0. 标注语言规范（产品视角，最重要）
标注是给【业务方/评审】看的，不是给开发看的——必须业务语言：
- **页面标识**: 用面包屑路径（如"线索管理/线索列表"），不用 URL/路由（如 /leads）
- **状态/枚举**: 用中文业务名（待分配/跟进中/已转客户/已作废），英文枚举（PENDING_ASSIGN 等）最多括号附注供开发对照，不能作为主描述
- **规则描述**: 业务语言（"分配后48小时未首次跟进自动回收，回退待分配"），不用代码逻辑
- **字段**: 用中文标签（线索名称/手机号），不用字段名（leadName/phone）
- **Tab/筛选**: 用中文名称（全部/待分配/我的线索/公海）
- **面向读者**: 业务方/评审——开发需要英文枚举去查 PRD（标注不承担开发对照职责）
- 发现英文枚举/技术路径为主描述 = 不合格标注，需返工

### 1. 忠于 PRD（最重要）
- 标注内容是否来自 PRD（业务规则/字段/状态/异常）——不是 AI 脑补
- **内容可追溯**：每块在 config `sourceRefs` 里关联 PRD 文件/章节（compile 校验 REQ 覆盖）；标注 md 里**不写"来源：xxx.md#章节"展示行**（评审看不懂，见 8.0）
- 来源不明确的内容应标"待确认"，不是补写

### 2. 不污染代码（铁律）
- PRD 未被改写（标注不混入 PRD）
- 业务代码未被污染（只加 data-anno 锚点/runtime hook，不改业务逻辑）
- 标注 Markdown 独立存放（annotations/ 目录）

### 3. 覆盖完整
- 本次需求涉及的页面区域都有标注（列表页的状态Tab/筛选/操作列）
- 字段规则/状态流转/异常处理是否覆盖
- 用 coverage.md 检查未覆盖项

### 4. 增量更新正确
- 更新了哪些标注（新增/修改/删除）——只动受影响的，不重写全页
- 旧标注是否保留合理（没乱删）
- id 规则（模块内 1/2/3，补充 A1/A2，嵌套 1a/1b）
- **编号规则以 §0-c 第 3 条为准：按「当前屏幕状态」分组，各自从 1 连续，同屏只出现一组**。三种错法都要判返工：① 每个页面各自从 1、但弹窗也各自从 1 且同屏同时显示 → 屏上两个相同数字；② 宿主页与弹窗共用一个号段（弹窗接 n+1）→ 宿主页跳号（实测出现 `1,2,3,4,5,11`，用户直接判错）；③ 全局累加到两位数。检阅时逐页点角标收集编号列表：既不能有重号，也不能有跳号，且弹窗打开后屏幕上只应剩该弹窗那一组的编号。补充 id（`A1`/`A2`）规则不变。

### 5. 运行时合规
- runtime 只读（无编辑/保存/写回）
- 徽章不改变布局
- 选择器稳定（data-anno > testid > 语义选择器 > class）

### 6. 标注分类与面板 UI（2026-08-08 升级，治根）
标注显示为**面板式 UI**（仿 Axure 标注栏，不是只有页面徽章），每个标注块必须带 `type` 分类供页签过滤：
- type 五类：`page` 页面 / `interaction` 交互 / `rule` 规则 / `field` 字段 / `pending` 待确认
- 存于 annotation.config.json 每个标注 id 的 `type` 字段（compile 会保留进 bundle，无需改编译器）
- 面板 UI 要素（对标参考效果）：页面"原型标注"入口按钮 → 浮层面板（标题+条目总数+关闭+副标题"点击条目定位页面中的对应区域"）→ 页签全部/页面/交互/规则/字段/待确认（当前 tab 品牌绿高亮）→ 条目卡片（序号徽章+标题+类型标签+摘要+展开收起）→ 点击条目滚动/高亮对应 data-anno 区域
- **两个入口按钮的激活态必须对称（2026-08-19 治根，检阅必查）**："标注清单"和"原型标注"两个入口，点开后各自的按钮都要显示"被选中/高亮"。**只修一个、另一个不亮 = 半修**；且"JS 加 class ≠ 视觉生效"——要 **JS 状态 class（如 is-active）+ 对应 CSS 视觉规则成对**，缺一味就是"面板开了但按钮不高亮"。检阅时：①点"标注清单"按钮是否自身高亮（不是只看面板开没开）②点"原型标注"同样③两个按钮的激活态视觉是否一致。排查"按钮不亮"先查 runtime.js 是否给该按钮 classList.toggle(is-active) + runtime.css 是否定义了对应 .is-active 样式（JS 有 CSS 无=白加），再怀疑 CF 缓存/环境——别一上来就推给部署/缓存。
- **入口按钮悬浮可拖（2026-08-08 治根）**："标注清单"+"原型标注"两个入口必须**悬浮 fixed 定位**（不占页面布局流、不遮挡页面控件，曾固定在右上角遮挡"批量导入/新建线索"）；支持鼠标拖移换位，位置存 sessionStorage 刷新保持
- 检阅时核对：type 归类是否合理（状态Tab/筛选=interaction，表格操作/校验=rule，字段约束=field）；页面/待确认页签可为空（无独立块时显示 0 条，合理）；入口是否悬浮可拖、不遮挡业务控件
- **悬浮可拖的经典 bug（2026-08-08 实锤，drag/click 冲突，三轮修复才定位到最终根因）**：给浮动入口加"鼠标拖移"时，按钮点击会失效——表现为"入口能显示、能拖，但点击无效果（无 toast、无徽章）"。两层根因（都踩过）：① 容器级捕获阶段统一拦截 click（`suppressClick` 标记）吞掉子按钮点击；② 更深的最终根因——**`setPointerCapture`**：浮动容器对 pointerdown 调 `setPointerCapture` 后，**click 目标被父容器接管**，子按钮永远收不到点击（且为恢复点击而跳过按钮拖拽，会连带取消拖拽能力）。**最终正确模式（v7 定稿）**：**彻底不用 setPointerCapture**——pointerdown 在容器/手柄，move/up 用 **window 级监听**追踪（不捕获）；移动未超阈值 → 保留原生 click；移动超阈值 → 更新位置并抑制这一次 click（防拖动误触）。同时显式 `pointer-events: auto`（全屏 `.vpa-root` 必须 `pointer-events: none`）+ 工具栏 z-index 高于面板。验证三态：点击按钮生效 / 拖拽换位不误触 / 拖后点击仍正常。检阅/验证时：点击无反应先怀疑这个，不是部署问题。
- **验证点击效果看 DOM 副作用，别只看 JS 状态**：runtime 的 `VPA_STATE` 是模块内部变量（不在 window 上，`typeof window.VPA_STATE === 'undefined'` 是**正常**的，勿误判 runtime 挂了）；验证点击是否生效要看 DOM 变化（`.vpa-badge` 数量、`.vpa-toast` 文本、面板元素出现）。浏览器实测流程：`browser_navigate` 打开线上 → console 查入口元素存在（`.vpa-floating-entries` fixed+高 z-index）→ `document.querySelector('.vpa-entry').click()` → 再查 `.vpa-badge` 数量 + toast 文本。曾实测：点击后 8 个 badge + toast"已显示标注区域序号"= 功能正常（无痕/无登录数据时页面数据 0 行、徽章少是正常的）。
- **"点击没效果"诊断阶梯（2026-08-08 深夜实测，入口 DOM 在但点击无反应时用）**：① 让用户 F12 Console 手动绑事件测试：`document.querySelector('.vpa-entry').addEventListener('click', () => console.log('手动点击成功'))` → 再点按钮。**Console 无输出 = 点击事件根本没到达按钮**（被上层拦截：drag 捕获阶段拦截 click / 透明遮罩 / pointer-events:none / z-index 覆盖）——不是 runtime 绑定问题；**有输出 = 事件能到达**，是 runtime 自己的 addEventListener 没执行（查 renderToolbar 绑定链）。② 拦截场景下一步：让 Codex 查 `makeFloatingEntriesDraggable` 是否在捕获阶段统一拦 click、Elements 面板看按钮上方有无覆盖元素、`getComputedStyle` 查 pointer-events/z-index、`getEventListeners()` 查监听器。③ 同步看 Network：响应头 `Age:` 大 = CF 缓存旧文件（见部署一致性验证第 4 条）；`Remote Address: 127.0.0.1:7897` = 本机 Clash 代理在转发（可能劫持/缓存，可让用户关代理直连排除）。曾实测链路：入口 DOM 在 + Console 无报错 + 手动绑定无输出 = 事件被容器捕获拦截（drag/click 冲突），非部署/缓存/绑定问题。

### 7. 交互流规范（2026-08-08 治根，用户强调"必须准确"）
对标参考效果的交互顺序（用户截图定义，红色 ①②③ 标注）：
1. 页面有"原型标注"入口按钮
2. 点击按钮 → **页面显示各标注区域的序号徽章**（绿圆数字，浮在 data-anno 区域边缘，不遮挡内容）——用户能看到"标注对应哪个区域"
3. 点击某个序号徽章 → 才显示该区域的标注内容（弹窗/面板，含描述行）+ 高亮对应区域
4. 再点按钮 → 清理（回干净页面）
- **CRITICAL 坑**（用户实测踩到）：点击按钮**直接弹说明**= 错误交互（用户"不知道是哪一个区域的说明"）；必须先显示序号层，点序号才看内容
- config `runtime.initialMode` 必须 = `preview`（初始不显示徽章，点按钮才显示），不是 `annotate`
- 检阅时验证：初始页面干净 → 点按钮出徽章 → 点徽章出内容 → 再点清理

### 8. 标注内容展示格式（2026-08-08 已治根，含渲染样式）
标注内容不能是长段落平铺（业务定义/显示样式一大段），要**结构化分组 + 分项列表**（对标参考效果）：
- 顶层：需求描述标题（如【状态页签】）+ 描述行
- 分组小标题（如"页签通用行为"、"状态说明"）
- 分项列表：每项"名称: 描述"（如"全部: 默认选中，显示全部单据"、"数量徽标: 显示对应状态单据数"）
- 长文本可展开/收起

### 8.0 描述自动提取 + 来源不展示 + 默认展开（2026-09 跑通，检阅必查）
**评审视角，不展示制作溯源**——用户纠正："来源于别人看不懂"。这三条是标注对外呈现的定稿：
1. **描述行(`> 描述`)必须自动提取，不手写**：等于该块"### 页面内容"小节首个要点句(`- xxx`)，无要点取首个 #### 标题，再无取块内首个要点。**绝不手写描述**——用执行侧 `scripts/extract_desc.py` 生成（forge-crm 已跑通）。描述永远来自正文(正文来自PRD)，可追溯、可持续；块内容改，重跑脚本即 follow。
2. **`> 来源：xxx.md#章节` 行不展示**：评审看不懂文件章节溯源，标注 md 里不要写来源行。**可追溯靠 config 的 `sourceRefs`**（compile 校验 REQ 覆盖 + 内部溯源用），不靠页面上展示的来源行。**清的时候要连运行时一起清**：旧版 runtime 会在待确认面板里用 `pendingIssueSource()` 把 md 里的 `> 来源` 行单独抽出来渲染（`.vpa-pending-source`），于是 md 删干净了、面板里照样出现「来源：xxx.md#…」。两处都要处理——删 md 里的来源行 + 确认 runtime 已同步到不再渲染来源的版本；改完在页面上搜一次「来源：」字样当作验收，搜得到就是没清完。
3. **点角标/徽章默认展开**：点到页面徽章(角标)弹的内容默认展开全部 tab（runtime `setPopupContent` 的 `syncDetails(wasOpen||true)` + 面板卡片 `expandedCards` 反转成"收起的集合"）。用户点开即看全部，不手动点"展开详细说明"。
**检阅时核对**：① 每块描述是否与"页面内容"小节首要点一致(不手写) ② 标注 md 无 `> 来源` 行 ③ config `sourceRefs` 是否完备(compile REQ 覆盖) ④ 线上点徽章默认展开。
- **模块/表格两增强（2026-09 吸收，来源行见 8.0 已弃用）**：① **模块路径字段**——`模块：{一级}/{二级}(页面)`（如 `销售管理 / 销售订单（列表）`），标注块标明归属，评审可知晓在哪用；② **凡有"展示文案⟷后端枚举/代码值"、"Tab标签⟷过滤逻辑"、"状态⟷文案"这类映射关系，优先用表格列（左侧中文展示值、右侧灰色代码框内英文枚举值），不写成长文字**——把 UI 层到代码层的翻译钉死，研发照抄不错。纯说明性文字才用段落。（注：曾要求"来源行带文档锚点"已废弃——评审看不懂文件溯源，见 8.0。）
- 检阅时核对：内容是否分组结构化（不是大段文字）；每个规则点是列表项不是段落；渲染层级（分组标题加粗/项名加粗/展开收起按钮）是否对齐参考。

### 9. 标注详情 6-Tab 规范 + 粒度拆细（2026-08-08 治根，用户定标准）
每个标注块的**详情内容**必须按 **6 个 tab 页**组织（不是单块平铺正文）：
``` 
全部        ← 各 tab 合并视图（默认 tab）
页面内容    ← 页面级描述：路径/布局/该区域展示什么
交互说明    ← 交互行为：点击/hover/页签切换/状态流转/展开收起
业务规则    ← 业务规则：校验/权限/异常/计算逻辑
字段说明    ← 字段级细节：字段标签/默认值/约束/格式
待确认      ← **评审问题记录（人工输入，见第 12 节）**——不是从 PRD 提取的"未决项"
```
- **空 tab 也必须展示**（作为拓展预留口，如"待确认"无内容显示 0 项）——不能隐藏空 tab
- tab 内内容仍用分组+分项列表格式（见第 8 节）
- **粒度拆细**：标注块按【功能点】拆分（参考 8-10 块：状态页签/筛选查询栏/表格/批量工具/行操作/新建线索/AI评分/权限），**不是按页面大区聚合**（曾只 3 大块太粗，每块只写定义、缺交互/规则/字段细节）；每块对应一个 data-anno 区域，缺锚点补
- 检阅时核对：每块是否 6-tab 齐全（空 tab 也在）；粒度是否功能点级（不是大区聚合）；交互/规则/字段信息是否从 PRD 补全（不脑补）
- **六个 Tab 全显示 0 项 ≠ 内容没写（runtime 计数正则的静默坑）**：线上点角标，弹窗顶部标题和来源都正常渲染，但「全部 / 页面内容 / 交互说明 / 业务规则 / 字段说明」一律显示 0、正文区写「该分组暂无内容（0项）」。这时内容往往**已经在 bundle 里**（`jq -r '.annotations[].markdown'` 能看到完整六 Tab 正文），坏的是 runtime 的 `countMarkdownItems`：它按行正则数条目，只认 `- ` / `* ` / `+ ` / `1. `，**不认 `1)` 和 `1、`** 这类中文编号写法，于是每个 section 判定为 0 条，`detailTabMarkdown('all')` 因计数为 0 把整块跳过。
  排查顺序：① 先 `jq` 看 bundle 里该块 markdown 是否非空——非空就别再改内容；② grep runtime 里统计条目的正则，把编号格式补成 `\d+[.)、]`；③ 修完 build 并递增 `?v=` 版本号再验。
  影响是**全量静默**的：所有用 `1)` 写法的块一起变 0，只有靠表格行数统计的段落侥幸有数，所以会误以为是「个别块内容没写」。修复只需一行正则，但正则在项目 `public/annotation-kit/runtime.js` 和 skill 的 `assets/annotation-kit/runtime.js` 两处，改完两边同步，否则下个项目再踩一遍。
- **字段说明页签必须是表格，不许散文、不许指路（用户定）**：四列固定——`字段名称 / 是否必填 / 是否可编辑 / 约束与校验`。纯动作块（按钮、入口、页脚提交、导出操作这类不承载输入的）写一行「本块不涉及字段」。**禁止「见 §x.x」「参见某章节」这类指路**——标注要自包含，评审点开就要看到内容，让他翻文档等于没标。字段约束只能来自字段清单 TSV 或 PRD 字段段，不自己编长度/格式/默认值，缺的写（待确认）。
  **「已经有表格」不等于合格，最常见的错法是三列把两列并成一列**：实际交上来的表头常是 `字段 / 必填&可编辑 / 核心约束`，合并列里写「选填；可编辑」「必填；不可编辑」这类拼串。评审要求的是两个独立列，因为「必填」和「可编辑」是两个正交属性，拼在一格既不能排序也不能扫读。拆分规则：`选填；可编辑`→否/是、`必填；可编辑`→是/是、`必填；不可编辑`→是/否、`列表只读`/`只读`→`-`/否、无「选填」字样的默认按 否 处理。检阅时直接数表头列数：不是四个就是不合格，不要因为它是个规整表格就放过。
- **待确认页签要分两个来源，界面上分组显示（用户定）**：① 产品未定项——写标注时从 PRD 发现没定的，只读；② 评审问题——评审时在面板输入，可勾选已解决、填解决方法、导出待办。**导出待办只导评审问题那一类**，产品未定项不混进待办。两者混在一起评审就分不清「这是产品没定的」还是「这是他自己提的」，这个页签会变成摆设。

### 10. 面板 tab 状态持久化（2026-08-09 治根——滚动重渲染丢 tab）
用户实踩：点"标注清单"→ 选条目"页面内容"tab → 鼠标滚动页面 → tab 跳回"全部"。
- **根因模式**：滚动触发 `scheduleMeasure`（scroll 监听捕获阶段）→ 面板 `renderAnnotationPanel` 用 `innerHTML` 重建卡片 → 详情 tab 节点被销毁 → 从新 DOM 读不到原 tab → 回退默认 `all`。
- **正确模式**：UI 状态存**重渲染之外**的持久 store（`VPA_STATE.detailTabByCard: Map`，按 `data-annotation-key` 作 key）；切换时保存，重建时恢复——"DOM 只负责呈现，状态不放在 DOM 里"：
  ```js
  const cardKey = container.closest('[data-annotation-key]')?.dataset.annotationKey;
  const savedTab = cardKey ? VPA_STATE.detailTabByCard.get(cardKey) : null;
  const requestedTab = savedTab || container.dataset.detailTab || initialTab;
  if (cardKey) VPA_STATE.detailTabByCard.set(cardKey, currentTab);
  ```
- 检阅/验证：选一个详情 tab（如页面内容）→ 滚动页面 → tab 应保持，不跳回"全部"。
- **通用教训**：凡是"滚动/刷新触发的 DOM 重建"组件（tab/折叠/勾选/筛选），状态必须外置持久化（VPA_STATE 等），DOM 默认值不是状态源。

### 11. 滚动事件不得重建滚动容器（2026-08-09 治根——滚动条死）
用户实踩：标注面板的外层列表/内层详情 tab 滚动条无法滚动（`scrollTop/scrollLeft` 每次回 0）。
- **根因模式**：可滚动容器自身触发 scroll → `scheduleMeasure()` → `renderAnnotationPanel()` **重建了滚动容器** → 新节点 `scrollTop/scrollLeft` 归零 → 滚动条看起来"死了"。
- **正确模式**：滚动事件里**只更新需要跟随业务页面移动的定位元素**（`measureBadges()`），**绝不重建面板**；面板重建只由明确动作触发（tab 切换/展开收起/数据刷新）：
  ```js
  window.requestAnimationFrame(() => {
    VPA_STATE.measureScheduled = false;
    measureBadges();
    // 滚动期间绝不调用 renderAnnotationPanel()
  });
  ```
- **金律**：滚动事件只更新定位；结构更新（重建）由显式动作驱动，绝不由容器自身的滚动事件触发。
- 检阅/验证：面板列表 `scrollTop` 能从 0 正常变化并保持；内层 tab 横向 `scrollLeft` 正常；滚动后 tab 仍保持选中。
- **和第 10 节同源**：两 bug 都是"滚动→重渲染"链——第 10 节解决"状态丢失"（tab 回跳），本节解决"容器被重建"（滚动条死）。凡是 runtime 里 scroll/resize 监听触发的重渲染，先问"这次重渲染真的必要吗"。Codex 最终修复方案：`scheduleMeasure` 只 measureBadges，把重渲染从滚动路径摘除——**比"重建+恢复状态"更优**（从根上避免重建）。

### 12. 待确认 = 评审问题记录系统（2026-08-09 用户定，功能升级）
**用户纠正（重要）**：待确认 tab **不是从 PRD 提取的"未决项"**，而是**评审时人工输入的问题记录器**——评审人看到问题 → 输入待确认 → 变成可执行待办。**来源是手动输入，不是文档**。此前把待确认理解成"标注提取的 PRD 缺口"是错的。

**完整需求（用户逐条定义）**：
- **每条标注块下都有**待确认输入框（问题关联具体区域/标注块）
- **全局"待确认"tab**：所有块的问题汇总（按块分组/可筛选）
- **持久化**：存 `localStorage`（刷新不丢）
- **解决流程**：每条问题有勾选框（open/resolved）+ **"解决方法"文本字段**——解决时写解决方案并展示（不只是打勾）
- **导出功能**：导出为 **PRD 待办 Markdown 块**（不是导出清单文件——是"直接贴待办到 PRD 文件"）
- **双向同步**（用户建议，已接受为浏览器技术限制下的现实方案）：PRD 勾选 ↔ 标注问题状态同步变；**浏览器无法直接写 PRD 文件（沙盒限制）** → 导出 PRD 待办块 → 用户/Codex 合并进 PRD → 解决后写方法+勾选 → 回贴/标注侧读状态。"双向"通过待办块的 Markdown 格式实现（`- [ ]`/`- [x]` 可解析）
- **待办下要有解决方法并体现**（不只是勾选状态）

**数据模型**（每条 issue）：
```
id: 稳定 id（标注块 key + 时间戳）
description: 问题描述（评审输入）
source: 所属标注块/页面区域
status: open / resolved
resolution: 解决方法（解决时填写）
```

**导出格式**（PRD 待办块）：
```
## 待办项
- [ ] 问题描述（来源：标注块X / 页面区域）
  - 解决方法：（待补充）
- [x] 已解决问题（来源：标注块Y）
  - 解决方法：已解决方式描述
```

**导出细化（2026-08-09 用户定，两个新需求）**：
- **单块导出**：每个标注块"待确认"tab 详情内也要有"导出待办"按钮（右上角）→ 只导出该块问题。**单块导出也必须带标题+待办清单**（和全局同格式，只是只含该块）：
  ```
  ## 待办项
  ### 序号 X（该块标题）
  - [ ] 问题描述
    - 解决方法：（待补充）
  ```
- **全局导出分组**：全局"导出待办"按标注块分组，每组前缀 `### 序号 X（块标题）`（序号=徽章号，标题=标注块标题），评审可追溯到具体区域：
  ```
  ## 待办项
  ### 序号 1（线索列表页面）
  - [ ] 问题...
  ### 序号 2（状态页签与线索池视图）
  - [x] 已解决...
    - 解决方法：...
  ```
- **实现模式（Codex 反馈，治根）**：单块与全局**共用一个分组 Markdown writer**——单块传入指定 blockKey，全局传全部问题；导出范围用参数控制，导出格式走同一套"标注块分组 → 待办列表"生成器，**避免单块和全局格式分叉**。分组标题统一由 `pendingIssueGroupHeading()` 生成 `### 序号 X（标题）`。

**滚动性（2026-08-09 治根，用户实踩）**：每块问题列表 + 全局问题列表都是**新增动态容器**，必须可滚动——`overflow-y: auto` + `max-height`（不依赖面板自身滚动，不在自身滚动事件中重建）。曾踩坑：问题多了列表超高被截断、无法滚动查看全部（见第 11 节滚动重建教训）。验证：加多条问题 → 列表可滚；面板滚动/tab 保持仍正常。

**弹窗类固定高度浮层的滚动正确模式（2026-08-09 Codex 修复方案）**：固定高度弹窗（`.vpa-popup`）只负责边界和 header；**body 是唯一纵向滚动容器**——弹窗用纵向 flex 布局，body 设 `flex: 1 1 auto; min-height: 0; max-height: none; overflow-y: auto`（+ `overscroll-behavior: contain`）；详情/问题卡片自然撑开 body 的 `scrollHeight`，滚轮由 body 原生处理。**不要**在内容区用固定 `max-height + overflow: hidden` 裁切长内容（会截断问题列表）。验证：body `scrollHeight/clientHeight` 有差值、滚轮后 `scrollTop` 变化、滚动后 tab 仍 active。

**检阅时核对**：待确认 tab 是可输入的（不是静态空）；问题能持久化（刷新不丢）；勾选解决带解决方法字段；导出块格式正确（可贴 PRD）；全局汇总正常；问题列表可滚动（多条不截断）。

## 8.1 Cron 提醒不等于产物已进入部署通道

自动监控可能先检测到 Codex 自检报告，再检测到 ZIP；两者不是同一事件。收到“已检测到新的 AI 产物提交”时，必须分别核对：

1. 报告文件是否真实存在并可读；
2. 目标项目 incoming 目录是否出现与本轮任务对应的唯一 ZIP；
3. ZIP 文件名、mtime、字节数、hash 是否与报告一致；
4. ZIP 第一层是否为 `index.html`，并包含本轮 annotation runtime/bundle；
5. 在 ZIP 确认上传前，不得部署，也不要把 incoming 中旧的同项目 ZIP 当作本轮产物。

如果只有报告、没有新 ZIP，应明确汇报“报告已到，部署包尚未上传，暂不部署”，等待 Agent 完成上传后再继续。

### 审完/归档的报告必须移出监控目录，否则 cron 反复告警（2026-09 实踩)

**已处理完却仍留在 `/var/lib/jarvis/files/ai-reports/` 的报告，会让每 2 分钟的监控 cron 把它当"新提交"反复提醒**（9/19 的标签管理删除报告一直躺着，用户 9/25 还在收它的重复叮）。规则：**审完/归档一份报告后，把它从 ai-reports/ 移出**（留档到 notes-vault + 挪到 archive/），监控就安静。批处理时顺带扫全目录，把历史已收尾但未移出的报告一并清掉；判断"该不该清"=读内容确认对应活已收尾/不急了就清，活还挂着 pending 的提醒是有意义的，别误删。



当用户说“检查 Codex 提交的修复”时，先区分协作链路，不要把出指令者和执行者混为一谈：

```text
Robin/Hermes：编排、出指令
Codex：执行代码修改、构建、打包、上传、自检
检阅者：独立核验产物与线上状态
用户：最终浏览器验收
```

### 固定审阅顺序

1. **找最新证据**：按时间检查 `/var/lib/jarvis/files/ai-reports/`、项目 incoming 目录和 `/var/log/jarvis-deploy.log`，不要只读用户转述或只凭 Codex 报告。
2. **读自检报告**：提取基线、改动文件、构建/浏览器结果、ZIP 名称/大小/hash、上传与部署状态、遗留风险。
3. **核对 ZIP**：确认文件真实存在、大小/hash一致、第一层有 `index.html`，并检查 `annotation-kit/runtime.js`、`runtime.css`、`annotation.bundle.json` 是否在包内。
4. **核对标注产物**：解析 bundle 的标注数量、页面模板、selector、sourceRefs；检查每页 id 是否从 1 连续、workspace coverage 是否闭环、源码 `data-anno` 是否能覆盖 selector。
5. **区分上传与部署**：incoming 有 ZIP 只代表上传成功；只有正式目录、部署日志、线上 bundle/runtime hash 和 HTTP/浏览器证据同时更新，才能说已部署。
6. **部署后复核**：重点验证本轮修复对应的真实页面，例如 RFQ 参数详情 matcher、SPA 路由切换后清单刷新、待确认数据按项目/路径隔离；不要用“首页 HTTP 200”替代功能验收。
7. **最终结论分级**：使用“修改/构建/浏览器本地验证/上传/正式部署/线上验收”逐项列明；任何缺失都写“待完成”，禁止把 Codex 的“已上传”改述成“已上线”。

### 本轮形成的具体检查点

- RFQ 详情页若复用表单组件，必须检查详情参数路由是否被 form matcher 覆盖；只检查 `new/edit` 不足以证明 `:id` 详情可标注。
- SPA 侧边栏切换路由时，既要检查徽章重新测量，也要检查已打开的标注清单是否刷新为当前页面，不能残留上一页条目。
- 待确认问题的 localStorage key、导出文件名和数据范围必须按项目及页面隔离，禁止复用 CRM 的历史 key。
- 线上新包与正式目录 hash 不一致时，结论只能是“待部署/待线上验收”，即使线上 HTTP 200。

## 部署一致性验证（检阅时必做）
用户会拿"Codex 本地自检截图"对比线上效果；不一致时按序排查（不要先怀疑部署失败）：
1. **查部署日志**：`grep '\[部署\]' /var/log/jarvis-deploy.log | tail`——确认最新 zip 是否部署成功（HTTP 200 ✅）
2. **查线上 runtime 是否含新逻辑**：`grep -c '新特征字符串' /var/www/pmlophy.com/project/<项目>/annotation-kit/runtime.js`（如"已显示标注区域序号"）
3. **查 zip vs 线上 JS 名**：backup 里的 zip `unzip -l | grep index-` vs 线上 index.html 引用——相同=新部署 OK
4. **Cloudflare 缓存根因 + 版本参数治根**（2026-08-08 实锤）：部署新版后用户线上仍看不到新效果，常见根因是 **CF 缓存了旧静态文件**（`curl -sI ... | grep -iE 'cf-cache-status|age'` 出现 `cf-cache-status: HIT` + `age: 4xxx` 秒 = 旧文件被缓存；`DYNAMIC`/`EXPIRED` = 实时取源）。注意 index.html 是 DYNAMIC（不缓存），但 **runtime.js 等静态文件有 max-age=14400（4小时）会被 CF 缓存**——即使部署了新文件，浏览器正常访问仍拿到旧的。**治根**：给 index.html 里 runtime.js/runtime.css 引用加版本参数（`runtime.js?v=2`），并**每次部署递增版本号**（v=2 → v=3），否则 CF 又缓存旧版。验证：`curl -s "...runtime.js?v=N" | grep -c 新特征字符串`。另注意 runtime.js 是 index.html body 里动态注入的 script（`vitaminAnnotationRuntime` 创建），不是静态 `<script src>` 标签——grep 静态标签会漏。
5. **引用从来没版本参数 = 改动永远不生效**（2026-10-24 cms 实锤）：cms 原型 index.html 的 runtime.css / override.css / runtime.js 三处引用一直没加 `?v=`，Cloudflare 按 max-age 缓存旧文件，部署后浏览器跑的还是旧 runtime——表现为"代码改了、build 了、部署了，行为一点没变"。**判定法**：在页面里 `fetch(url,{cache:'no-store'})` 能看到新特征，但页面行为不对 = 一定是缓存，不是代码问题。排查时别先去怀疑逻辑，先确认浏览器实际执行的是哪个版本。
5. **浏览器实测点击验证**（2026-08-08 新技法）：用户报"点击没效果"时，用 `browser_navigate` 打开线上 URL → `browser_console` 检查：入口元素存在（`.vpa-floating-entries`/`.vpa-entry`，fixed+高 z-index 可见）→ 实际 `document.querySelector('.vpa-entry').click()` → 再查 `.vpa-badge` 数量 + `.vpa-toast` 文本。**注意 `VPA_STATE` 是 runtime 模块内部变量（不在 window 上，`typeof window.VPA_STATE` 返回 undefined 是正常的）**——验证点击效果要看 DOM 副作用（badge 数/toast 文本），不要因 VPA_STATE undefined 误判 runtime 挂了。曾实测：点击后 8 个 badge 出现 + toast"已显示标注区域序号"= 功能正常（我浏览器无登录数据所以徽章少/区域少，用户有数据应更多）——先实测再让 Codex 修，避免空跑一轮。
6. **⚠️ 标注页面 URL 是 HashRouter（2026-08-14 实测误判教训）：forge-crm 用 HashRouter（`src/App.tsx` import { HashRouter }），正确 URL 是 `https://pmlophy.com/project/forge-crm/#/leads` 带 `#/`——直接导航 `/leads`（无 #）不匹配任何路由，页面渲染默认 Dashboard（`/`），看起来像"路由失效/页面没反应"。诊断标注/页面功能前先确认 URL 格式（`location.hash` 是否含 `#/`）；用 SPA 内部导航（点菜单）最稳，不要直接拼 pathname URL。另：标注 bundle 是按页面绑定的（如 annotation.bundle.json title="Forge CRM 线索列表页标注"——只有线索页有 9 条标注），在控制台首页点标注按钮"没内容"是正常的（无该页标注）——先确认当前页有对应 bundle 再判异常。
7. **build 产物默认不进 git，别把「pull 到最新源码」当成「dist 是新的」**（实测差点上线事故）：原型的 `dist/assets/index-*.js` 通常被 .gitignore 忽略（仓库里只跟踪了 `dist/index.html` 和图标），交付方在自己机器上 build 的 JS 根本传不到部署机。部署机上那份 dist 还是上一次 build 的，里面**一个新加的 `data-anno` 都没有** → 部署后新标注全挂不上，而 bundle 条数、check 输出全是绿的。**部署前固定两个动作**：① `git ls-files dist` 看 dist 下到底哪些被跟踪；② 在部署机上自己 `npm run build`，然后 grep 新锚点：`grep -c '<新锚点>' dist/assets/*.js`，为 0 就是没 build 成功。
- 部署脚本坑（已修）：deploy-all.sh URL 必须带 `/project/` 前缀（forge 系部署在 /var/www/pmlophy.com/project/）；zip 必须"解压即根"（cd dist && zip -rq，不带 front-prototype/dist 前缀），否则部署验证 404 回滚
- **`rsync -a --delete` 前先比一遍目录差集，标注目录最容易被误删**：原型站里 `annotation-kit/` 是源码目录却被 build 复制进 `dist/`，一旦某次 build 没带上它（或换构建配置），`--delete` 会把线上唯一一份标注资产连同 bundle 一起清掉。部署前固定跑一次差集：
```bash
comm -23 <(ls /var/www/pmlophy.com/project/<项目>/ | sort) <(ls dist/ | sort)   # 有输出 = 有线上独有文件将被删
```
  输出为空再执行 rsync；同时先 `cp -a` 整目录备份，回滚就是覆盖回去。部署后立刻两验：`curl` 首页看引用的 bundle hash 变了；`curl` 具体静态资源路径确认 200（不是 404）。

## 整页红框图验收（评审PRD 的「原型页面」列，2026-10 实测）

标注完成后紧接着就是"把 11 个角标跑成 11 张整页红框图"，这一段是检阅者最容易放过、返工最贵的地方。

**前置链路（顺序不可颠倒）**：PRD 正文收口 → 原型页面到位 → **原型标注** → 跑 `capture_orm.py` 出红框图 → 填回「原型页面」列 → base64 发布版。
- **标注是红框图的硬前置**：截图脚本读的就是 `annotation.config.json`（拿 `data-anno` 坐标），没标注跑不出图。所以"截图还差"通常不是截图这一步慢，而是**上游标注没做**——排期要把标注提前排，别把两步当并行。
- **红框图 doc-与标注内容要同源**：「原型页面」列与标注内容都来自 PRD 的「页面说明」列；若父会话在标注期间改了 PRD，已标的部分会对不上——改动要排在标注之前，或明确告知 agent 哪些行已变。

**验收集清单（不看自报）**：

1. **数量三方一致**：`annotation.config.json` 的 `sourceRequirements` 数 = `annotations` 数 = PRD「页面和操作」表行数。不等 = 漏标或漏配。
2. **非空**：`find <images目录> -type f -size 0` 无输出。
3. **同批互比 md5**：同批不同场景的图 md5 不能相同——agent 重截时会把 A 场景的图写进 B 场景文件名（实测撞过），出现相同值就退回重截。
4. **单框**：每张只圈该角标一个红框，不能同时圈出别的角标。
5. **弹窗类要真打开**：图里能看到弹窗，不是背后列表页（触发后才取锚点）。
6. **命名**：`<页面名>-序号<N>-<功能点>.png`——回填时能直接对上行。
7. **分批节奏**：先只出一页（如 3 张）确认命名与框位，再去其余；脚本用 `--limit` 控制首轮数量。
8. 允许 agent 为适配 config 小改截图脚本（只改读取与坐标部分），但**必须报告改了哪些行**；改了整套逻辑 = 退回。

**角标显示口径顺带校对**：详情六个 tab 名称固定（全部/页面内容/交互说明/业务规则/字段说明/**待确认**）；runtime 旧文案可能把空的待确认 tab 写成"待办 0"，发现即让执行方改回"待确认"（只改文案不改逻辑）。

**PRD 与原型对不上时（标注阶段一定会遇到）**：大多数不是实现缺了，而是 PRD 残留了旧结构或被推翻的口径（典型：分步向导时代的"进入下一步"、已被实调推翻的"此阶段不做 X"）。处置顺序：① 先判文档那一条是否过期；过期 → **父会话改文档那一条**，把修正后的文本原样贴回执行方；② 不过期 → 父会话给明确挂点；③ **绝不为让对方过 Checkpoint 而放宽标准，也不要让它自己判断**——它只会挑一个看起来合理的挂点，然后错一页。

## 治根原则（用户定，重要）
- **标准化不是写文档，是让机制在流程里生效（用户强纠正）**：散在 SKILL.md 各节的规则，下一次换个项目换个 agent 没人从头读，还是各凭理解写。要做成一个可复用的包，四件：① 契约（一页纸：什么内容进标注、块怎么切、六页签各什么形态，不含项目细节）；② 样板块（一个填满的完整块，作者照抄结构，比读二十条规则准）；③ 校验器（所有能机器判的规则都进去，进发版门禁）；④ 参数化指令模板（换项目只填项目路径/PRD 目录/页面清单）。**标准的唯一真源是校验器，不是文档**——文档会被跳过，发版门禁跳不过。
- **见一个冒头就修一个 = 人肉门禁，不算 SOP（用户点名批评）**：上线点到问题才反手修，说明校验层缺这道门。每修一个线上问题，必须回答「这条规则进校验器了吗」，没进就等于下次还会犯。加规则→进校验器，不要只补文档。
- 实践发现问题 → 补进 Skill 本身（执行侧 + 检阅侧同步），**不靠指令临时修正**
- 老师/现成 Skill 是起点，不是终极答案——实践中完善它
- 示例：原版 Skill 未强调产品语言 → 补"Annotation Language Standard"到执行侧 SKILL.md（英文版）+ 本 skill 第 0 条（中文版），两边同步
- **修复方案反馈工作流（2026-08-09 用户定，治根不猜）**：让 Codex 本地修 bug（快）时，指令末尾必须要求它**反馈修复方案**（根因/改动/修复模式/一句话总结），杰西卡**基于真实修法补 Skill**——避免"自己猜修法补错规范"。指令模板："汇报要求（重要）：完成修复后，除了标准自检报告，必须额外详细说明【修复方案】：1. 根因（为什么出现）2. 改动（哪个文件哪个函数）3. 修复模式（关键代码片段/思路）4. 一句话总结（以后实现 X 的正确模式）。用途：杰西卡会基于你的真实修法更新 Skill 治根。"——tab 状态持久化规范（第 10 节）就是靠这个流程拿到的真实修法。

## 校验器自身的边界（独立验证必查，别把「全绿」当「都对」）

把规则写进校验器只是第一步，校验器本身也会失灵。三条实测过的失灵模式，检阅时自己独立验一遍，不能因为它报 valid 就放行：

1. **路由判据会被兜底通配路由废掉**：原型路由表几乎都有 `<Route path="*">`，任何 page 都「能匹配上」，于是「routeMatcher 命中不了」被降级成 warning 而不是 error。后果是最初那个坑——只写 `create$` 漏掉 `edit/:id`——照样拦不住，线上依旧 0 角标。独立验证法：把某条的 routeMatcher 改成明显不存在的值，看它报不报；不报即判据无效，退回到「按页面真实路由清单逐条对账」。
2. **空壳块阈值不能按页签总数写死**：详情实际只有 5 个页签，阈值若写「≥5 个为空」等于只拦「全空」，四个空一个实的块一声不响。判据应基于「有实质内容的页签数 ≤1」。
3. **fail-fast 会遮住后面的判据**：markdown 类判据（来源行、字段说明形态、零条目）先跑，一有错就 raise 退出，锚点/路由/编号/跨 PRD 那几条根本没机会执行。所以「跑了一遍只报 3 条错」≠「只有 3 个问题」——改完前一批必须再跑一次才看得见后一批，别在第一轮就宣布全量清单。

4. **分组输出时第一组会粘在 `Annotation assets invalid:` 同一行**：输出形如 `Annotation assets invalid: 【判据6】共 36 条`，第一组的判据号不在行首，用 `rg '^【判据'` 或肉眼看缩进都**读不到它**。后果是「判据 6 明明报了 36 条，却被判成 0 条消失」，进而误以为刚改的代码把判据改坏了，白查一轮。**读校验结果必须数组数，不是数行首匹配**：`grep -o '【判据[0-9]*】共 [0-9]* 条'` 全量抓，或者让执行方把 `Annotation assets invalid:` 单独换行、每组 `【判据n】` 独占行。以后凡是新加判据，先确认它有没有被这个格式吞掉。
5. **「空页签跳过」会吞掉页签级判据**：`check_annotation_markdown` 里对所有页签统一 `if is_empty_tab_body(body): continue`，于是**字段说明页签为空或只写「暂无」时不进 `check_field_tab`**，该报的不合格一条不报（实测漏掉 3 块全空字段说明）。规则：**页签级判据必须排在「空则跳过」之前**——空字段说明本身就是不合格（除非明确写「本块不涉及字段」），不能因为它是空的就被当成没问题。加任何「这个页签形态对不对」的判据时，先问一句「空的会不会绕过它」。

6. **判据会拿被测对象自证，绕过自己的前置校验**：为了修第 1 条（兜底通配路由），很容易把 matcher 的命中判定改成「扫路由表 + 扫 account 的 page 字符串」，看着更严了，实际多出一个更大的洞——**page 与 routeMatcher 一起写错、但互相自洽时就全放行**（page 写 `/zzz/nope`、matcher 写 `nope$`，matcher 匹配上了 page 自己，于是「page 是否存在于真实路由表」这道独立判定被跳过去）。规则：**一个字段的合法性不能被另一个字段的匹配结果豁免**；page 必须在真实路由表里是独立判据，matcher 命中只用于判断 matcher 本身有效。凡是「A 命中 B 所以都算对」的写法，都要问一句 B 自己有没有被验过。

**独立验证的正确姿势**：不要拿现有脏产物当测试基线——前面的错误会 raise 把后面的判据全挡住，你会误判成「后面几条也能拦」。先手搓一个**完全合规的最小 bundle**（两三条块、六页签齐全、字段说明四列、无来源行、id 连续），跑出 valid 当基线，再一条一条注入违规、每次只破坏一项。注意条目计数判据带最短长度门槛（正文太短的散文本来就判不出来），测试用例要写成够长的段落，否则误判成判据失灵。

**反例要通过 = 别把自己构造的矛盾配置当成判据失灵**：测出来一条报错后，先确认这个配置本身该不该报。典型误判：给 `page: /engage/edit/:id`（参数路由写法，项目里真实存在）配 `routeMatcher: /engage/edit/1$`（写死实值）——两个都对不上就对了，因为参数路由的 matcher 本来就该写正则而不是实值，报错是正确行为。把这类自造矛盾误当成缺陷去改校验器，会把刚修好的门禁改松。凡「新判据报了我没想到的错」，先判配置本身合不合理。

## 标注过程会暴露"原型 vs PRD 不一致"（重要价值）
Codex 做标注时对照 PRD 映射页面，会如实记录原型实现与 Demo PRD 的差异（列在报告"遗留风险"）：
- 原型多了/少了状态（如原型"我的线索"含 DRAFT，Demo 定义是已分配+跟进中）
- 原型没执行 PRD 规则（如 7 天防撞墙保护、超时回收只覆盖部分状态）
- 原型没实现 Demo 的能力（搜索/导出/批量等）
- 校验不严（如放弃原因最少 15 字未执行）

**顺带必查「页面骨架是从别的模块复制来的」这一类（实测）**：标注检阅会打开页面上每个角标，最容易被看见的不是标注本身，而是原型自己的陈旧硬编码。典型症状：用户行为页的面包屑写死成「权限中心 / 用户行为」，而菜单配置里它挂在「触达计划 > 配置管理」下；容器 class 还留着 `permission-page` 这种来源页的名字。根因是页面骨架从别的模块整段复制过来，面包屑、class 名、页面标题这些「看起来不会变」的东西没跟着改。
判据：**页面上显示的位置信息必须与菜单/路由配置里的归属一致**。检阅时拿菜单配置文件（如 `config/menus.ts`）的层级去比页面里硬编码的面包屑；不一致就报，不要因为「标注内容没问题」就放过。修法只改面包屑那一段文本，容器 class 名不要动（改 class 会影响样式，属于另一件事）。
处理：用户拍板（原型改对齐 PRD / PRD 改对齐原型 / 逐个确认）——标注本身没问题，是"标注显示的和原型实际行为不一致"影响评审。

## 标注 = PRD 体检报告（2026-08-09 用户定，下一阶段方向）
标注要写"交互说明/业务规则/字段说明"，PRD 没写就标不准/标不全。所以标注功能变成 **PRD 完整度的探测器**——哪里缺，标注就"卡"在哪。
- **正向循环**：PRD 不完整 → 标注发现缺口 → 补 PRD → 重新编译标注 → 标注更全 → 评审更准
- 用户已定下一阶段 = **微调 PRD**（补齐交互/规则/字段缺口）。工作模式：用户拿标注/评审找"PRD 没写全的规则"→ 补 PRD（对齐实际设计 + 补全细节）→ 重编译标注（标注自动同步新 PRD）
- **补 PRD 范围（用户定）**：主 PRD + Demo PRD + 字段清单（如有缺失）三处都补；**主 PRD 是权威**，但可能写的不够细（Demo PRD 可能同理）
- **检阅时价值**：Codex 标注报告"遗留风险"列出的原型 vs PRD 不一致项 = 现成的 PRD 补丁清单（如 forge-crm 线索：我的线索含 DRAFT 冲突/撤销放弃 vs 7 天保护/关键词多值搜索/AI评分边界/创建时间快捷筛选/导出范围/表格能力/放弃是否清空负责人）——用户拍板每个是"补 PRD"还是"原型欠实现"
- **注意区分**：PRD 缺口来自 **Codex 标注报告/审计**（自动发现，写进报告"遗留风险"）；**待确认 tab 是人工评审输入**（见第 12 节），两者来源不同，不要混为一谈
- **PRD 补全决策清单工作流（2026-08-09 用户拍板流程，forge-crm 线索已跑通）**：① 把标注/审计发现的待确认项整理成**决策清单**（每条含：现状/冲突/建议/拍板项），按类别分组（A 状态定义类/B 查询区类/C 工具表格能力类/D 超时回收类）；② 用户**批量拍板**（可一次全按建议）；③ 写**决策定稿文档**存进项目（prd-docs/线索管理/线索PRD补全决策定稿_20260809.md 为样例：每条含"定稿/理由/修改到哪个文件"）→ push；④ 给 Codex 一次补全三个文件（主PRD权威 + Demo + 字段清单），指令引用决策定稿为唯一依据（红线：严格按定稿不自行改决策）；⑤ 重编译标注 → build → 走部署管道
- **决策定稿文档是给 Codex 的权威输入**：Codex 看不到对话，只有定稿文档——所以文档必须自包含（每条决策写清改哪个文件哪个章节）

## 假警报教训：显示数 ≠ 渲染数先查滚动容器（2026-08-09 实锤）
用户报"全局待确认页签计数 5，但只显示 3 条"（导出有 5 条 = 数据完整）。**当时误判为渲染 bug，补了一条 Skill 规范并 push，用户随后澄清是"没在列表小窗口内滚动、在外层滚动了"——功能正常，不是 bug**，最后 `git revert` 撤回。
- **教训**：计数与可见条数不一致时，**先怀疑滚动容器交互**（列表区独立滚动，外层滚动不动它——用户可能不知道要在列表区内滚），再怀疑渲染丢组。别急着治根补 Skill。
- **已误 push 的撤回方式**：`git revert --no-edit <commit>`（保留历史）→ push origin main，不要 `reset --hard`（会分叉）。
- **治根前置校验**：用户报"问题"先判断是 bug 还是使用习惯（尤其滚动/交互类）——确认是真 bug 再补 Skill 规范，避免为假问题留规范。

## 标注的前置依赖清单（2026-09-11 血泪教训，开工前必查）

**原型标注的输入依赖**（缺任何一项 → 标注只能靠猜）：
1. **PRD 套件（核心）**：主PRD（业务背景/功能范围/单据定位/状态机）+ Demo PRD（字段展示/输入/校验/反馈）+ 业务规则（状态/动作/异常边界）+ 流程（涉及上下游时）
2. **字段清单 TSV**（字段事实源——**是前置输入，不是标注来源**）
3. **前端原型页面 + 锚点**（页面要有 `data-anno` 可挂载）
4. **标注规范**（annotation-scope 边界判断 + 编写规范 + SKILL）

**铁律**：
- **标注的来源始终是 PRD Markdown，不是 TSV**——TSV 是字段事实的前置输入。v2 加了 TSV 不代表标注内容会变，而是字段约束更准；**v1/v2 标注长得一样是正常的**。
- **开工前先做依赖盘点**：这项工作依赖哪些输入？我手上有哪些？缺哪些？——缺的立刻汇报，**绝不用猜测/半套材料硬做**。（2026-09 娜美在只有前端代码、无 PRD 套件的空架子上硬做标注，来回修复浪费用户 2-3 天；"v1/v2 看起来一样""标注没体现 TSV"全是这个根因。）
- 检阅时先问一句：**这套标注是基于完整 PRD 套件生成的吗？** 不是 → 质量无从谈起，先补地基，**别在标注层修补**（层选错了，修不完）。

## 维生素新版（vitamin-prototype-annotation）三能力 + 三步验证法（2026-09 参考）

老师那版比我们多三块能力，值得吸收（包已存 `/root/notes/vitamin-course/vitamin-prototype-annotation/`）：
1. **标注边界判断** `references/annotation-scope.md`——什么时候该标（状态/字段约束/计算/权限/异常），什么时候不该标（布局/尺寸/圆角/Mock数据）。解决"这个要不要标"的纠结。
2. **编译后自动校验** `scripts/check_annotation_assets.py` + `--check`——自动查配置完整性 / sourceRefs 映射 / 重复 ID / 缺失选择器。从"标完人工看"变成"机器先过一遍，人工只查机器报的错"。
3. **可运行示例** `examples/static/`——完整标注项目（config→Markdown→编译→部署可跑通），新项目"直接抄作业"。
- 运行时新特性：`runtime.hideToolbarWhenEmpty`（默认 true）——当前页无匹配标注时不渲染工具栏与贴边样式；workspace 顶层设 false 可全站常驻入口。

**三步验证法（验收标注工具/产物的标准，缺一不可）**：
① 边界判断能指导标注（scope 判断有理由，该标/不该标分得清）
② 编译校验能抓 bug（贴**真实运行输出**，不是摆设）
③ 浏览器真能看到角标（工具栏渲染 + 角标显示 + `data-anno` 选择器匹配真实 DOM）
——"工具链跑通"（compile→check→bundle）≠"页面能看"；只报前两步就宣称完成 = 没验收（2026-09 娜美第一轮就是跳过第③步被退回）。

## 四层校验走查法 + 触发时机（维生素13节吸收，2026-09 补）

走查标注/DemoPRD 的"支撑细节"时要按**出错位置分层**查，避免漏异常：
- **字段级**：单字段取值（为空、格式不合法、超长、超上下限）
- **页面级**：字段联动与明细约束（日期先后、金额联动、必填联动、最少一行、重复行）
- **业务级**：是否符合业务规则（状态是否允许编辑、编码重名、是否查库存/额度）
- **系统级**：操作过程异常（网络失败、超时、重复提交、并发编辑冲突）

**触发时机**：同一条规则挂不同时机体验不同——输入时（边输边限）、失焦时（离开后行内检查）、动作触发时（点保存/提交审核等按钮查哪些规则）。**不能笼统写"提交时校验"**：要说清是哪个按钮、查哪些规则；"保存草稿宽松 vs 提交审核严格"的差异要按项目定义。

**校验后必交代操作结果**：成功提示什么/页面停留哪里/单据进哪个状态；失败怎样提示/保留哪些已填内容；"结果暂不明确"（如网络超时）单独说明后续如何确认。**容易漏的**：用户改正确后（修正输入）错误何时清除、能否恢复操作——提示出现、修正、恢复这一段也要交代。

**检阅时对照**：标注/DemoPRD 是否覆盖四层 + 触发时机 + 操作结果 + 修正恢复；"宽松校验""格式错误"这类模糊词要揪出来（宽松到底允许缺哪些、格式错误包含哪些）。

## 本页规则（page-global 整页规则，维生素13节吸收）

整页通用规则（**防重提交、未保存离开拦截、页面准入/权限、整页加载失败**）不该挂在某个具体按钮/字段角标上，要用 **page-global**（无元素锚点，type=page-global，target=None）作为**页面级规则**独立呈现。区分：
- **组件级规则** → 局部角标（表单字段/按钮动作）
- **整页级规则** → 本页规则（page-global）：状态流转、防重提交、未保存离开、页面准入

**检阅时核对**：
1. 防重提交/未保存离开/页面准入这类整页规则是否做成 page-global（而非硬挂某个按钮）。
2. page-global 块是否存在于 config（type=page-global）、标注 md（target 无 selector）、bundle 中一致；runtime 能识别（`isPageGlobal`）。
3. page-global 块内容是否简明（整页规则，不重复各组件细节）。
4. runtime 是否给 page-global 一个呈现位置（本页规则区/页面顶部/面板顶部）。
