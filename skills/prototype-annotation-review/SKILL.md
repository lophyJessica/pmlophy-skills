# 原型标注检阅（Reviewer 版）

## 角色分工（铁律）
- **执行者**: Codex/Cursor（装项目里，目录名 `prototype-annotation`，实际跑标注工作流）
- **检阅者**: 杰西卡 + 罗宾（我们——审标注质量，不出手改项目代码）
- **验收者**: 用户（最终拍板）
- **命名约定**（用户定，勿搞反）：项目执行侧目录 = `prototype-annotation`；Hermes 检阅侧 skill = `prototype-annotation-review`

## 核心理念
标注 = 外置解释层（左原型右标注，模仿 Axure 传统，AI 自动化）：
- 标注存独立 Markdown（annotations/*.md），不写进 PRD/业务代码
- 编译成 annotation.bundle.json（运行时只读）
- 页面加最小 hook（runtime.js + data-anno 锚点）
- 标注块有"来源"行（指向 PRD 文件/章节）
- 产物路径规范：`annotations/` 跟 PRD 走（如 prd-docs/线索管理/annotations/），编译 bundle 在原型 `public/annotation-kit/`

## 检阅清单（我们审什么）

### 0. 标注语言规范（产品视角，最重要）
标注是给【业务方/评审】看的，不是给开发看的——必须业务语言：
- **页面标识**: 用面包屑路径（如"线索管理/线索列表"），不用 URL/路由（如 /leads）
- **状态/枚举**: 用中文业务名（待分配/跟进中/已转客户/已作废），英文枚举（PENDING_ASSIGN 等）最多括号附注供开发对照，不能作为主描述
- **规则描述**: 业务语言（"分配后48小时未首次跟进自动回收，回退待分配"），不用代码逻辑
- **字段**: 用中文标签（线索名称/手机号），不用字段名（leadName/phone）
- **Tab/筛选**: 用中文名称（全部/待分配/我的线索/公海）
- **面向读者**: 业务方/评审——开发需要英文枚举去查 PRD（标注不承担开发对照职责）
- 发现英文枚举/技术路径为主描述 = 不合格标注，需返工

### 1. 忠于 PRD（最重要）
- 标注内容是否来自 PRD（业务规则/字段/状态/异常）——不是 AI 脑补
- 每个标注块是否有"来源"行（主PRD/字段清单/Demo PRD 的哪个文件/章节）
- 来源未明确的应标"待确认"，不是补写

### 2. 不污染代码（铁律）
- PRD 未被改写（标注不混入 PRD）
- 业务代码未被污染（只加 data-anno 锚点/runtime hook，不改业务逻辑）
- 标注 Markdown 独立存放（annotations/ 目录）

### 3. 覆盖完整
- 本次需求涉及的页面区域都有标注（列表页的状态Tab/筛选/操作列）
- 字段规则/状态流转/异常处理是否覆盖
- 用 coverage.md 检查未覆盖项

### 4. 增量更新正确
- 更新了哪些标注（新增/修改/删除）——只动受影响的，不重写全页
- 旧标注是否保留合理（没乱删）
- id 规则（模块内 1/2/3，补充 A1/A2，嵌套 1a/1b）
- **id 独立计数（2026-08-19 治根）**：每个【页面】的标注块 id 独立从 1 连续编号，不做全局累加。检阅时核对：切到不同页面（如列表→新建→详情），徽章序号都应各自从 1 开始；若某一进页面从 10+/大数字开始，说明 id 跨页全局累加了，返工（runtime 徽章直接显示 annotation.id——所以 id=页面内序号）

### 5. 运行时合规
- runtime 只读（无编辑/保存/写回）
- 徽章不改变布局
- 选择器稳定（data-anno > testid > 语义选择器 > class）

### 6. 标注分类与面板 UI（2026-08-08 升级，治根）
标注显示为**面板式 UI**（仿 Axure 标注栏，不是只有页面徽章），每个标注块必须带 `type` 分类供页签过滤：
- type 五类：`page` 页面 / `interaction` 交互 / `rule` 规则 / `field` 字段 / `pending` 待确认
- 存于 annotation.config.json 每个标注 id 的 `type` 字段（compile 会保留进 bundle，无需改编译器）
- 面板 UI 要素（对标参考效果）：页面"原型标注"入口按钮 → 浮层面板（标题+条目总数+关闭+副标题"点击条目定位页面中的对应区域"）→ 页签全部/页面/交互/规则/字段/待确认（当前 tab 品牌绿高亮）→ 条目卡片（序号徽章+标题+类型标签+摘要+展开收起）→ 点击条目滚动/高亮对应 data-anno 区域
- **两个入口按钮的激活态必须对称（2026-08-19 治根，检阅必查）**："标注清单"和"原型标注"两个入口，点开后各自的按钮都要显示"被选中/高亮"。**只修一个、另一个不亮 = 半修**；且"JS 加 class ≠ 视觉生效"——要 **JS 状态 class（如 is-active）+ 对应 CSS 视觉规则成对**，缺一味就是"面板开了但按钮不高亮"。检阅时：①点"标注清单"按钮是否自身高亮（不是只看面板开没开）②点"原型标注"同样③两个按钮的激活态视觉是否一致。排查"按钮不亮"先查 runtime.js 是否给该按钮 classList.toggle(is-active) + runtime.css 是否定义了对应 .is-active 样式（JS 有 CSS 无=白加），再怀疑 CF 缓存/环境——别一上来就推给部署/缓存。
- **入口按钮悬浮可拖（2026-08-08 治根）**："标注清单"+"原型标注"两个入口必须**悬浮 fixed 定位**（不占页面布局流、不遮挡页面控件，曾固定在右上角遮挡"批量导入/新建线索"）；支持鼠标拖移换位，位置存 sessionStorage 刷新保持
- 检阅时核对：type 归类是否合理（状态Tab/筛选=interaction，表格操作/校验=rule，字段约束=field）；页面/待确认页签可为空（无独立块时显示 0 条，合理）；入口是否悬浮可拖、不遮挡业务控件
- **悬浮可拖的经典 bug（2026-08-08 实锤，drag/click 冲突，三轮修复才定位到最终根因）**：给浮动入口加"鼠标拖移"时，按钮点击会失效——表现为"入口能显示、能拖，但点击无效果（无 toast、无徽章）"。两层根因（都踩过）：① 容器级捕获阶段统一拦截 click（`suppressClick` 标记）吞掉子按钮点击；② 更深的最终根因——**`setPointerCapture`**：浮动容器对 pointerdown 调 `setPointerCapture` 后，**click 目标被父容器接管**，子按钮永远收不到点击（且为恢复点击而跳过按钮拖拽，会连带取消拖拽能力）。**最终正确模式（v7 定稿）**：**彻底不用 setPointerCapture**——pointerdown 在容器/手柄，move/up 用 **window 级监听**追踪（不捕获）；移动未超阈值 → 保留原生 click；移动超阈值 → 更新位置并抑制这一次 click（防拖动误触）。同时显式 `pointer-events: auto`（全屏 `.vpa-root` 必须 `pointer-events: none`）+ 工具栏 z-index 高于面板。验证三态：点击按钮生效 / 拖拽换位不误触 / 拖后点击仍正常。检阅/验证时：点击无反应先怀疑这个，不是部署问题。
- **验证点击效果看 DOM 副作用，别只看 JS 状态**：runtime 的 `VPA_STATE` 是模块内部变量（不在 window 上，`typeof window.VPA_STATE === 'undefined'` 是**正常**的，勿误判 runtime 挂了）；验证点击是否生效要看 DOM 变化（`.vpa-badge` 数量、`.vpa-toast` 文本、面板元素出现）。浏览器实测流程：`browser_navigate` 打开线上 → console 查入口元素存在（`.vpa-floating-entries` fixed+高 z-index）→ `document.querySelector('.vpa-entry').click()` → 再查 `.vpa-badge` 数量 + toast 文本。曾实测：点击后 8 个 badge + toast"已显示标注区域序号"= 功能正常（无痕/无登录数据时页面数据 0 行、徽章少是正常的）。
- **"点击没效果"诊断阶梯（2026-08-08 深夜实测，入口 DOM 在但点击无反应时用）**：① 让用户 F12 Console 手动绑事件测试：`document.querySelector('.vpa-entry').addEventListener('click', () => console.log('手动点击成功'))` → 再点按钮。**Console 无输出 = 点击事件根本没到达按钮**（被上层拦截：drag 捕获阶段拦截 click / 透明遮罩 / pointer-events:none / z-index 覆盖）——不是 runtime 绑定问题；**有输出 = 事件能到达**，是 runtime 自己的 addEventListener 没执行（查 renderToolbar 绑定链）。② 拦截场景下一步：让 Codex 查 `makeFloatingEntriesDraggable` 是否在捕获阶段统一拦 click、Elements 面板看按钮上方有无覆盖元素、`getComputedStyle` 查 pointer-events/z-index、`getEventListeners()` 查监听器。③ 同步看 Network：响应头 `Age:` 大 = CF 缓存旧文件（见部署一致性验证第 4 条）；`Remote Address: 127.0.0.1:7897` = 本机 Clash 代理在转发（可能劫持/缓存，可让用户关代理直连排除）。曾实测链路：入口 DOM 在 + Console 无报错 + 手动绑定无输出 = 事件被容器捕获拦截（drag/click 冲突），非部署/缓存/绑定问题。

### 7. 交互流规范（2026-08-08 治根，用户强调"必须准确"）
对标参考效果的交互顺序（用户截图定义，红色 ①②③ 标注）：
1. 页面有"原型标注"入口按钮
2. 点击按钮 → **页面显示各标注区域的序号徽章**（绿圆数字，浮在 data-anno 区域边缘，不遮挡内容）——用户能看到"标注对应哪个区域"
3. 点击某个序号徽章 → 才显示该区域的标注内容（弹窗/面板，含来源行）+ 高亮对应区域
4. 再点按钮 → 清理（回干净页面）
- **CRITICAL 坑**（用户实测踩到）：点击按钮**直接弹说明**= 错误交互（用户"不知道是哪一个区域的说明"）；必须先显示序号层，点序号才看内容
- config `runtime.initialMode` 必须 = `preview`（初始不显示徽章，点按钮才显示），不是 `annotate`
- 检阅时验证：初始页面干净 → 点按钮出徽章 → 点徽章出内容 → 再点清理

### 8. 标注内容展示格式（2026-08-08 已治根，含渲染样式）
标注内容不能是长段落平铺（业务定义/显示样式一大段），要**结构化分组 + 分项列表**（对标参考效果）：
- 顶层：需求描述标题（如【状态页签】）+ 来源行（灰色代码框）
- 分组小标题（如"页签通用行为"、"状态说明"）
- 分项列表：每项"名称: 描述"（如"全部: 默认选中，显示全部单据"、"数量徽标: 显示对应状态单据数"）
- 长文本可展开/收起（条目卡片里"展开详细说明 (N 项)"，默认收起，点开展开切换"收起详细说明"）
- **渲染样式**（Codex 已实现）：分组标题渲染为加粗独立小标题；列表项冒号前的"项名"渲染为加粗、描述常规（视觉分离）；来源行灰色代码框；弹窗白底圆角卡片+阴影+清爽滚动
- 检阅时核对：内容是否分组结构化（不是大段文字）；每个规则点是列表项不是段落；渲染层级（分组标题加粗/项名加粗/展开收起按钮）是否对齐参考

### 9. 标注详情 6-Tab 规范 + 粒度拆细（2026-08-08 治根，用户定标准）
每个标注块的**详情内容**必须按 **6 个 tab 页**组织（不是单块平铺正文）：
``` 
全部        ← 各 tab 合并视图（默认 tab）
页面内容    ← 页面级描述：路径/布局/该区域展示什么
交互说明    ← 交互行为：点击/hover/页签切换/状态流转/展开收起
业务规则    ← 业务规则：校验/权限/异常/计算逻辑
字段说明    ← 字段级细节：字段标签/默认值/约束/格式
待确认      ← **评审问题记录（人工输入，见第 12 节）**——不是从 PRD 提取的"未决项"
```
- **空 tab 也必须展示**（作为拓展预留口，如"待确认"无内容显示 0 项）——不能隐藏空 tab
- tab 内内容仍用分组+分项列表格式（见第 8 节）
- **粒度拆细**：标注块按【功能点】拆分（参考 8-10 块：状态页签/筛选查询栏/表格/批量工具/行操作/新建线索/AI评分/权限），**不是按页面大区聚合**（曾只 3 大块太粗，每块只写定义、缺交互/规则/字段细节）；每块对应一个 data-anno 区域，缺锚点补
- 检阅时核对：每块是否 6-tab 齐全（空 tab 也在）；粒度是否功能点级（不是大区聚合）；交互/规则/字段信息是否从 PRD 补全（不脑补）

### 10. 面板 tab 状态持久化（2026-08-09 治根——滚动重渲染丢 tab）
用户实踩：点"标注清单"→ 选条目"页面内容"tab → 鼠标滚动页面 → tab 跳回"全部"。
- **根因模式**：滚动触发 `scheduleMeasure`（scroll 监听捕获阶段）→ 面板 `renderAnnotationPanel` 用 `innerHTML` 重建卡片 → 详情 tab 节点被销毁 → 从新 DOM 读不到原 tab → 回退默认 `all`。
- **正确模式**：UI 状态存**重渲染之外**的持久 store（`VPA_STATE.detailTabByCard: Map`，按 `data-annotation-key` 作 key）；切换时保存，重建时恢复——"DOM 只负责呈现，状态不放在 DOM 里"：
  ```js
  const cardKey = container.closest('[data-annotation-key]')?.dataset.annotationKey;
  const savedTab = cardKey ? VPA_STATE.detailTabByCard.get(cardKey) : null;
  const requestedTab = savedTab || container.dataset.detailTab || initialTab;
  if (cardKey) VPA_STATE.detailTabByCard.set(cardKey, currentTab);
  ```
- 检阅/验证：选一个详情 tab（如页面内容）→ 滚动页面 → tab 应保持，不跳回"全部"。
- **通用教训**：凡是"滚动/刷新触发的 DOM 重建"组件（tab/折叠/勾选/筛选），状态必须外置持久化（VPA_STATE 等），DOM 默认值不是状态源。

### 11. 滚动事件不得重建滚动容器（2026-08-09 治根——滚动条死）
用户实踩：标注面板的外层列表/内层详情 tab 滚动条无法滚动（`scrollTop/scrollLeft` 每次回 0）。
- **根因模式**：可滚动容器自身触发 scroll → `scheduleMeasure()` → `renderAnnotationPanel()` **重建了滚动容器** → 新节点 `scrollTop/scrollLeft` 归零 → 滚动条看起来"死了"。
- **正确模式**：滚动事件里**只更新需要跟随业务页面移动的定位元素**（`measureBadges()`），**绝不重建面板**；面板重建只由明确动作触发（tab 切换/展开收起/数据刷新）：
  ```js
  window.requestAnimationFrame(() => {
    VPA_STATE.measureScheduled = false;
    measureBadges();
    // 滚动期间绝不调用 renderAnnotationPanel()
  });
  ```
- **金律**：滚动事件只更新定位；结构更新（重建）由显式动作驱动，绝不由容器自身的滚动事件触发。
- 检阅/验证：面板列表 `scrollTop` 能从 0 正常变化并保持；内层 tab 横向 `scrollLeft` 正常；滚动后 tab 仍保持选中。
- **和第 10 节同源**：两 bug 都是"滚动→重渲染"链——第 10 节解决"状态丢失"（tab 回跳），本节解决"容器被重建"（滚动条死）。凡是 runtime 里 scroll/resize 监听触发的重渲染，先问"这次重渲染真的必要吗"。Codex 最终修复方案：`scheduleMeasure` 只 measureBadges，把重渲染从滚动路径摘除——**比"重建+恢复状态"更优**（从根上避免重建）。

### 12. 待确认 = 评审问题记录系统（2026-08-09 用户定，功能升级）
**用户纠正（重要）**：待确认 tab **不是从 PRD 提取的"未决项"**，而是**评审时人工输入的问题记录器**——评审人看到问题 → 输入待确认 → 变成可执行待办。**来源是手动输入，不是文档**。此前把待确认理解成"标注提取的 PRD 缺口"是错的。

**完整需求（用户逐条定义）**：
- **每条标注块下都有**待确认输入框（问题关联具体区域/标注块）
- **全局"待确认"tab**：所有块的问题汇总（按块分组/可筛选）
- **持久化**：存 `localStorage`（刷新不丢）
- **解决流程**：每条问题有勾选框（open/resolved）+ **"解决方法"文本字段**——解决时写解决方案并展示（不只是打勾）
- **导出功能**：导出为 **PRD 待办 Markdown 块**（不是导出清单文件——是"直接贴待办到 PRD 文件"）
- **双向同步**（用户建议，已接受为浏览器技术限制下的现实方案）：PRD 勾选 ↔ 标注问题状态同步变；**浏览器无法直接写 PRD 文件（沙盒限制）** → 导出 PRD 待办块 → 用户/Codex 合并进 PRD → 解决后写方法+勾选 → 回贴/标注侧读状态。"双向"通过待办块的 Markdown 格式实现（`- [ ]`/`- [x]` 可解析）
- **待办下要有解决方法并体现**（不只是勾选状态）

**数据模型**（每条 issue）：
```
id: 稳定 id（标注块 key + 时间戳）
description: 问题描述（评审输入）
source: 所属标注块/页面区域
status: open / resolved
resolution: 解决方法（解决时填写）
```

**导出格式**（PRD 待办块）：
```
## 待办项
- [ ] 问题描述（来源：标注块X / 页面区域）
  - 解决方法：（待补充）
- [x] 已解决问题（来源：标注块Y）
  - 解决方法：已解决方式描述
```

**导出细化（2026-08-09 用户定，两个新需求）**：
- **单块导出**：每个标注块"待确认"tab 详情内也要有"导出待办"按钮（右上角）→ 只导出该块问题。**单块导出也必须带标题+待办清单**（和全局同格式，只是只含该块）：
  ```
  ## 待办项
  ### 序号 X（该块标题）
  - [ ] 问题描述
    - 解决方法：（待补充）
  ```
- **全局导出分组**：全局"导出待办"按标注块分组，每组前缀 `### 序号 X（块标题）`（序号=徽章号，标题=标注块标题），评审可追溯到具体区域：
  ```
  ## 待办项
  ### 序号 1（线索列表页面）
  - [ ] 问题...
  ### 序号 2（状态页签与线索池视图）
  - [x] 已解决...
    - 解决方法：...
  ```
- **实现模式（Codex 反馈，治根）**：单块与全局**共用一个分组 Markdown writer**——单块传入指定 blockKey，全局传全部问题；导出范围用参数控制，导出格式走同一套"标注块分组 → 待办列表"生成器，**避免单块和全局格式分叉**。分组标题统一由 `pendingIssueGroupHeading()` 生成 `### 序号 X（标题）`。

**滚动性（2026-08-09 治根，用户实踩）**：每块问题列表 + 全局问题列表都是**新增动态容器**，必须可滚动——`overflow-y: auto` + `max-height`（不依赖面板自身滚动，不在自身滚动事件中重建）。曾踩坑：问题多了列表超高被截断、无法滚动查看全部（见第 11 节滚动重建教训）。验证：加多条问题 → 列表可滚；面板滚动/tab 保持仍正常。

**弹窗类固定高度浮层的滚动正确模式（2026-08-09 Codex 修复方案）**：固定高度弹窗（`.vpa-popup`）只负责边界和 header；**body 是唯一纵向滚动容器**——弹窗用纵向 flex 布局，body 设 `flex: 1 1 auto; min-height: 0; max-height: none; overflow-y: auto`（+ `overscroll-behavior: contain`）；详情/问题卡片自然撑开 body 的 `scrollHeight`，滚轮由 body 原生处理。**不要**在内容区用固定 `max-height + overflow: hidden` 裁切长内容（会截断问题列表）。验证：body `scrollHeight/clientHeight` 有差值、滚轮后 `scrollTop` 变化、滚动后 tab 仍 active。

**检阅时核对**：待确认 tab 是可输入的（不是静态空）；问题能持久化（刷新不丢）；勾选解决带解决方法字段；导出块格式正确（可贴 PRD）；全局汇总正常；问题列表可滚动（多条不截断）。

## 8.1 Cron 提醒不等于产物已进入部署通道

自动监控可能先检测到 Codex 自检报告，再检测到 ZIP；两者不是同一事件。收到“已检测到新的 AI 产物提交”时，必须分别核对：

1. 报告文件是否真实存在并可读；
2. 目标项目 incoming 目录是否出现与本轮任务对应的唯一 ZIP；
3. ZIP 文件名、mtime、字节数、hash 是否与报告一致；
4. ZIP 第一层是否为 `index.html`，并包含本轮 annotation runtime/bundle；
5. 在 ZIP 确认上传前，不得部署，也不要把 incoming 中旧的同项目 ZIP 当作本轮产物。

如果只有报告、没有新 ZIP，应明确汇报“报告已到，部署包尚未上传，暂不部署”，等待 Agent 完成上传后再继续。



当用户说“检查 Codex 提交的修复”时，先区分协作链路，不要把出指令者和执行者混为一谈：

```text

Codex：执行代码修改、构建、打包、上传、自检
检阅者：独立核验产物与线上状态
用户：最终浏览器验收
```

### 固定审阅顺序

1. **找最新证据**：按时间检查 `/var/lib/jarvis/files/ai-reports/`、项目 incoming 目录和 `/var/log/jarvis-deploy.log`，不要只读用户转述或只凭 Codex 报告。
2. **读自检报告**：提取基线、改动文件、构建/浏览器结果、ZIP 名称/大小/hash、上传与部署状态、遗留风险。
3. **核对 ZIP**：确认文件真实存在、大小/hash一致、第一层有 `index.html`，并检查 `annotation-kit/runtime.js`、`runtime.css`、`annotation.bundle.json` 是否在包内。
4. **核对标注产物**：解析 bundle 的标注数量、页面模板、selector、sourceRefs；检查每页 id 是否从 1 连续、workspace coverage 是否闭环、源码 `data-anno` 是否能覆盖 selector。
5. **区分上传与部署**：incoming 有 ZIP 只代表上传成功；只有正式目录、部署日志、线上 bundle/runtime hash 和 HTTP/浏览器证据同时更新，才能说已部署。
6. **部署后复核**：重点验证本轮修复对应的真实页面，例如 RFQ 参数详情 matcher、SPA 路由切换后清单刷新、待确认数据按项目/路径隔离；不要用“首页 HTTP 200”替代功能验收。
7. **最终结论分级**：使用“修改/构建/浏览器本地验证/上传/正式部署/线上验收”逐项列明；任何缺失都写“待完成”，禁止把 Codex 的“已上传”改述成“已上线”。

### 本轮形成的具体检查点

## 部署一致性验证（检阅时必做）
用户会拿"Codex 本地自检截图"对比线上效果；不一致时按序排查（不要先怀疑部署失败）：
1. **查部署日志**：`grep '\[部署\]' /var/log/jarvis-deploy.log | tail`——确认最新 zip 是否部署成功（HTTP 200 ✅）
2. **查线上 runtime 是否含新逻辑**：`grep -c '新特征字符串' /var/www/pmlophy.com/project/<项目>/annotation-kit/runtime.js`（如"已显示标注区域序号"）
3. **查 zip vs 线上 JS 名**：backup 里的 zip `unzip -l | grep index-` vs 线上 index.html 引用——相同=新部署 OK
4. **Cloudflare 缓存根因 + 版本参数治根**（2026-08-08 实锤）：部署新版后用户线上仍看不到新效果，常见根因是 **CF 缓存了旧静态文件**（`curl -sI ... | grep -iE 'cf-cache-status|age'` 出现 `cf-cache-status: HIT` + `age: 4xxx` 秒 = 旧文件被缓存；`DYNAMIC`/`EXPIRED` = 实时取源）。注意 index.html 是 DYNAMIC（不缓存），但 **runtime.js 等静态文件有 max-age=14400（4小时）会被 CF 缓存**——即使部署了新文件，浏览器正常访问仍拿到旧的。**治根**：给 index.html 里 runtime.js/runtime.css 引用加版本参数（`runtime.js?v=2`），并**每次部署递增版本号**（v=2 → v=3），否则 CF 又缓存旧版。验证：`curl -s "...runtime.js?v=N" | grep -c 新特征字符串`。另注意 runtime.js 是 index.html body 里动态注入的 script（`vitaminAnnotationRuntime` 创建），不是静态 `<script src>` 标签——grep 静态标签会漏。
5. **浏览器实测点击验证**（2026-08-08 新技法）：用户报"点击没效果"时，用 `browser_navigate` 打开线上 URL → `browser_console` 检查：入口元素存在（`.vpa-floating-entries`/`.vpa-entry`，fixed+高 z-index 可见）→ 实际 `document.querySelector('.vpa-entry').click()` → 再查 `.vpa-badge` 数量 + `.vpa-toast` 文本。**注意 `VPA_STATE` 是 runtime 模块内部变量（不在 window 上，`typeof window.VPA_STATE` 返回 undefined 是正常的）**——验证点击效果要看 DOM 副作用（badge 数/toast 文本），不要因 VPA_STATE undefined 误判 runtime 挂了。曾实测：点击后 8 个 badge 出现 + toast"已显示标注区域序号"= 功能正常（我浏览器无登录数据所以徽章少/区域少，用户有数据应更多）——先实测再让 Codex 修，避免空跑一轮。
6. **⚠️ 标注页面 URL 是 HashRouter（2026-08-14 实测误判教训）：forge-crm 用 HashRouter（`src/App.tsx` import { HashRouter }），正确 URL 是 `https://pmlophy.com/project/forge-crm/#/leads` 带 `#/`——直接导航 `/leads`（无 #）不匹配任何路由，页面渲染默认 Dashboard（`/`），看起来像"路由失效/页面没反应"。诊断标注/页面功能前先确认 URL 格式（`location.hash` 是否含 `#/`）；用 SPA 内部导航（点菜单）最稳，不要直接拼 pathname URL。另：标注 bundle 是按页面绑定的（如 annotation.bundle.json title="Forge CRM 线索列表页标注"——只有线索页有 9 条标注），在控制台首页点标注按钮"没内容"是正常的（无该页标注）——先确认当前页有对应 bundle 再判异常。
- 部署脚本坑（已修）：deploy-all.sh URL 必须带 `/project/` 前缀（forge 系部署在 /var/www/pmlophy.com/project/）；zip 必须"解压即根"（cd dist && zip -rq，不带 front-prototype/dist 前缀），否则部署验证 404 回滚

## 假警报教训：显示数 ≠ 渲染数先查滚动容器（2026-08-09 实锤）
用户报"全局待确认页签计数 5，但只显示 3 条"（导出有 5 条 = 数据完整）。**当时误判为渲染 bug，补了一条 Skill 规范并 push，用户随后澄清是"没在列表小窗口内滚动、在外层滚动了"——功能正常，不是 bug**，最后 `git revert` 撤回。
- **教训**：计数与可见条数不一致时，**先怀疑滚动容器交互**（列表区独立滚动，外层滚动不动它——用户可能不知道要在列表区内滚），再怀疑渲染丢组。别急着治根补 Skill。
- **已误 push 的撤回方式**：`git revert --no-edit <commit>`（保留历史）→ push origin main，不要 `reset --hard`（会分叉）。
- **治根前置校验**：用户报"问题"先判断是 bug 还是使用习惯（尤其滚动/交互类）——确认是真 bug 再补 Skill 规范，避免为假问题留规范。

## 标注的前置依赖清单（2026-09-11 血泪教训，开工前必查）

**原型标注的输入依赖**（缺任何一项 → 标注只能靠猜）：
1. **PRD 套件（核心）**：主PRD（业务背景/功能范围/单据定位/状态机）+ Demo PRD（字段展示/输入/校验/反馈）+ 业务规则（状态/动作/异常边界）+ 流程（涉及上下游时）
2. **字段清单 TSV**（字段事实源——**是前置输入，不是标注来源**）
3. **前端原型页面 + 锚点**（页面要有 `data-anno` 可挂载）
4. **标注规范**（annotation-scope 边界判断 + 编写规范 + SKILL）

**铁律**：
- **标注的来源始终是 PRD Markdown，不是 TSV**——TSV 是字段事实的前置输入。v2 加了 TSV 不代表标注内容会变，而是字段约束更准；**v1/v2 标注长得一样是正常的**。
- **开工前先做依赖盘点**：这项工作依赖哪些输入？我手上有哪些？缺哪些？——缺的立刻汇报，**绝不用猜测/半套材料硬做**。（2026-09 娜美在只有前端代码、无 PRD 套件的空架子上硬做标注，来回修复浪费用户 2-3 天；"v1/v2 看起来一样""标注没体现 TSV"全是这个根因。）
- 检阅时先问一句：**这套标注是基于完整 PRD 套件生成的吗？** 不是 → 质量无从谈起，先补地基，**别在标注层修补**（层选错了，修不完）。

1. **标注边界判断** `references/annotation-scope.md`——什么时候该标（状态/字段约束/计算/权限/异常），什么时候不该标（布局/尺寸/圆角/Mock数据）。解决"这个要不要标"的纠结。
2. **编译后自动校验** `scripts/check_annotation_assets.py` + `--check`——自动查配置完整性 / sourceRefs 映射 / 重复 ID / 缺失选择器。从"标完人工看"变成"机器先过一遍，人工只查机器报的错"。
3. **可运行示例** `examples/static/`——完整标注项目（config→Markdown→编译→部署可跑通），新项目"直接抄作业"。
- 运行时新特性：`runtime.hideToolbarWhenEmpty`（默认 true）——当前页无匹配标注时不渲染工具栏与贴边样式；workspace 顶层设 false 可全站常驻入口。

**三步验证法（验收标注工具/产物的标准，缺一不可）**：
① 边界判断能指导标注（scope 判断有理由，该标/不该标分得清）
② 编译校验能抓 bug（贴**真实运行输出**，不是摆设）
③ 浏览器真能看到角标（工具栏渲染 + 角标显示 + `data-anno` 选择器匹配真实 DOM）
——"工具链跑通"（compile→check→bundle）≠"页面能看"；只报前两步就宣称完成 = 没验收（2026-09 娜美第一轮就是跳过第③步被退回）。

## 四层校验走查法 + 触发时机（维生素13节吸收，2026-09 补）

走查标注/DemoPRD 的"支撑细节"时要按**出错位置分层**查，避免漏异常：
- **字段级**：单字段取值（为空、格式不合法、超长、超上下限）
- **页面级**：字段联动与明细约束（日期先后、金额联动、必填联动、最少一行、重复行）
- **业务级**：是否符合业务规则（状态是否允许编辑、编码重名、是否查库存/额度）
- **系统级**：操作过程异常（网络失败、超时、重复提交、并发编辑冲突）

**触发时机**：同一条规则挂不同时机体验不同——输入时（边输边限）、失焦时（离开后行内检查）、动作触发时（点保存/提交审核等按钮查哪些规则）。**不能笼统写"提交时校验"**：要说清是哪个按钮、查哪些规则；"保存草稿宽松 vs 提交审核严格"的差异要按项目定义。

**校验后必交代操作结果**：成功提示什么/页面停留哪里/单据进哪个状态；失败怎样提示/保留哪些已填内容；"结果暂不明确"（如网络超时）单独说明后续如何确认。**容易漏的**：用户改正确后（修正输入）错误何时清除、能否恢复操作——提示出现、修正、恢复这一段也要交代。

**检阅时对照**：标注/DemoPRD 是否覆盖四层 + 触发时机 + 操作结果 + 修正恢复；"宽松校验""格式错误"这类模糊词要揪出来（宽松到底允许缺哪些、格式错误包含哪些）。

## 本页规则（page-global 整页规则，维生素13节吸收）

整页通用规则（**防重提交、未保存离开拦截、页面准入/权限、整页加载失败**）不该挂在某个具体按钮/字段角标上，要用 **page-global**（无元素锚点，type=page-global，target=None）作为**页面级规则**独立呈现。区分：
- **组件级规则** → 局部角标（表单字段/按钮动作）
- **整页级规则** → 本页规则（page-global）：状态流转、防重提交、未保存离开、页面准入

**检阅时核对**：
1. 防重提交/未保存离开/页面准入这类整页规则是否做成 page-global（而非硬挂某个按钮）。
2. page-global 块是否存在于 config（type=page-global）、标注 md（target 无 selector）、bundle 中一致；runtime 能识别（`isPageGlobal`）。
3. page-global 块内容是否简明（整页规则，不重复各组件细节）。
4. runtime 是否给 page-global 一个呈现位置（本页规则区/页面顶部/面板顶部）。
