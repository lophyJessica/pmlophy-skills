# 内外销功能差异对比

给总裁/领导看的跨市场能力盘点表。核心：**内销做基准，外销只回答有没有**，每一行都要能指回代码。

## 一、口径（先定再动手）

| 项 | 定法 |
|---|---|
| 基准方 | 内销。全量列内销功能点，外销侧只回答「有没有、差在哪」 |
| 粒度 | 一个页面拆 15-30 行子功能项，一条功能一行，**不按整页一行** |
| 功能介绍 | 一句话 20-40 字，讲清解决什么业务问题、服务什么场景 |
| 行来源 | 源码取证，每行带 `文件:行号`；不凭页面名想象 |
| 外销列 | 以线上真机为准填，**不照源码填**（源码常落后线上，会低估现状） |

### 表头自带的八条填写规范（模板原文要点）

1 **截图**：放对应 App 的实际页面截图，用来证明当前页面结构、展示内容、字段位置与交互入口；尽量完整，必要时用标注框对应到具体子功能项。
2 **功能接受**（模板原文即此，实际语义是功能介绍）：说明该功能为何存在、服务什么用户场景、解决什么业务问题。
3 **是否支持该功能**：填内销/该区域当前是否支持，取值为 √ / ×。
4 **内容是否可以在后台配置**：取值为 √ / ×。
5 **展示数量**：前台展示数量，并说明是否可按需增加。
6 **设计规范**：写宽×高。
7 **代表国家选择原因**：普外选印尼（功能在该地区更完善 + 销量最高）、欧洲选西班牙（功能更完善 + 销量最高）、拉美选巴西（功能更完善）。
8 **差异备注**：内外销不一致时写这一列；若代表国家不支持但该区域有其他国家支持，也写在这里，写清是哪个国家。

### 列口径定稿（2026-11-03 用户逐条确认，填表时照这个，不要自己推导）

| 列 | 口径 |
|---|---|
| **是否支持该功能** | 指**该国家/地区有没有这个功能**，不是问“支不支持内销的做法”。因为外销按国家部署，运营也能不一样。例：A 功能泰国有、巴西没上 → 巴西填 × |
| **内容是否可配** | 本质问的是**这是不是通用功能**——能不能靠后台配置开关实现，而不是重新开发。例：外销 CMS 的公域渠道，可以对新加坡开 2 个渠道，也可以开 3 个 |
| **差异备注** | **内外销不一致就写在这一列**，四个区域组都有，只有一个意思。代表国家不支持但区域内其他国家支持，也写在这里并注明是哪个国家。不需要另找地方、也不要塞进功能介绍 |
| **展示数量** | **暂不管**。历史上这列从未填过信息，留空即可 |
| **设计规范（宽*高）** | **产品不管**。这列需要流转给交互/UI 确认，产品表里留空 |

**后台页面同样套用这 32 列**：不是只给 App（导购端/商城 H5）用，后台页面也是同一套列复制过去。区别只是——展示数量与设计规范两列默认不填，原则是「有则填、无则不填」，当前一律不填。

## 三、源码取证流程

### 先知道：国家差异到底藏在哪里（用户 2026-11-03 指出，后续优先走这条路取证）

判「某功能在某国家支不支持」时，不要只找页面上的国家判断代码。因为**外销按国家/租户部署，国家差异通常是用权限控制 + 配置实现的**，代码里可能一行 `if 国家` 都没有。按成本从低到高四条取证路径：

1 **权限与菜单授权代码/配置**（首选）：权限中心、角色授权、菜单资源、数据范围里有没有国家/租户/战区维度；一个菜单项对某国家不可见，表现出来就是「不支持该功能」
2 **租户/多租户配置**：数据库或配置表里的租户表、国家配置表、功能开关表，一个国家一个租户时，开关就存在租户维度
3 **源码路由与条件渲染**：菜单配置、router、`v-if` / 灰度开关，注意路由被注释=未启用
4 **真机逐国验证**：切国家看实际能不能看到、能不能用；成本最高但是最终标准

结论落表时，差异备注里要写清这个结论是靠哪条路径来的（权限配置 / 源码 / 真机），因为三条的证据强度不同。

1. 页面清单唯一来源是 `src/router/index.ts`（或 `router/*.js`），grep `path:` + `meta.title` 列全，别凭 views 目录猜。
2. 逐页读 `.vue`，从 **template 段**取界面文案：文本节点、`label/placeholder/title` 属性、`:label` 绑定的字符串常量。
3. 弹窗、抽屉、下级页各起一行，不算父页的子句。
4. 三类不确定性必须标出来，不许混进结论：**路由被注释（未启用）**、**文案/选项由接口或 `pageElementConfigFn` 下发**、**灰度/权限条件渲染**。

### 「内容是否可配」判定口径

- √：文案、选项、标签、排序、权益项来自接口或后台配置 → 运营可改
- ×：写死在组件里的中文常量 → 改文案要发版
- 判据必须是代码位置，不能凭感觉

## 四、坑

- **package.json 的 version 字段不可信**，它常被忘记同步。判定一份源码是不是最新版，看三个信号：①关键新功能文件（当下版本才有的页面/组件）的最后提交日期是否落在近期；②路由条数是否与线上菜单对得上；③doc 目录里概设文档的版本号。实测外销 global-guide：package.json 写 1.0.0，但 orderList / verify / activityShare 等预售功能文件都是最新提交，代码实为 1.8.0.2。仅凭 version 字段就下「源码是旧版」的结论会误报。
- **原型 ≠ 现状**。原型是设计方案，可能包含还没落地的页面。用原型当「外销现状」会把规划算成存量，给领导的结论直接错。
- **源码版本必须先核对**。查 `package.json` version + 最近提交日期；分支停在几个月前就要怀疑，别拿旧代码下结论。核对方法：仓库文件列表的 Last commit、`git branch -r --sort=-committerdate`。
- **有的团队用版本分支开发、master 根本不合并**（vivo 外销 global-guide 实测：master 停在 v1.5.0，线上跑 1.8.0.2，中间隔四代）。这类仓库按 master 取源码等于取了个古董。规矩：①先看 GitLab 的 Switch branch/tag 列表，找版本号最大的分支；②确认它对应线上哪一版（问研发或看部署记录）；③取完先数路由条数，跟线上菜单对不上就是取错了。
- **拿不到源码时让 agent「复刻原页面」是高风险动作**：agent 会照设计稿重生一份，这份产物不是现状证据；报告里必须标清「竞争原型/重建品，非真实实现」，否则会被当成外销已有能力写进对比表。
- **容器内 H5 无法自动化截图**。企业微信 / v消息 里嵌的应用，Playwright 拿不到登录态；截图只能人工，工具侧只负责出「截图清单」（页面/状态/命名/对应行）。
  实测证据（vivo 内销 qywx-h5 / 外销 global-guide）：内销在非企微/非 v消息 UA 下直接路由到 /notsupport，OAuth 必须在企微客户端完成；外销壳子能开但 token 靠 dsBridge 取 `vchat-uuctoken`，无 token 时接口返 10040004「没有操作权限」。唯一 documented bypass 是本地 development + cookies.json（token 靠人工从已登录环境抄），不是一键。
- **截图不进对比表时也要留证**。复现或原型截的图不能当证据，领导追问就露底。
- **合并单元格别做 Automation**：Excel 里同页面名合并要按组各自合并（每组只合自己那一段），写错会把整列合成一格、值全丢。
- **别自己动手做机械提取**。批量读源码提取这类活派本地 agent（Cursor 公司机免额度），Hermes 子代理只适合小批（并发 3，每个别超过 2-3 页，否则撞 50 轮上限）。

## 五、产出与验收

- 先出 5-6 个核心页的「深度样张」让用户验：粒度、功能介绍写法、多子页页面怎么归。三项定了再铺开。
- 铺开按模块分批，每批 3 个 agent / 每个 agent 2-3 页。
- 验收看三件事：每行有代码依据、粒度 15-30 行/页、没有把「未启用」写成「有」。
- **agent 自报不算验收，必须跑 `scripts/verify_feature_tsv.py <清单.tsv> <源码根目录>`**：它会检列完整性、代码依据的文件是否存在/行号是否越界、每页行数粒度、重复子功能项。实测过 497 行零缺失零越界才敢收。
- 抽查「内容是否可配」的判定：判 × 的应该是写死的界面文案，判 √ 的应该是接口驱动的业务内容；若接口下发项被大面积判成 ×，说明 agent 把「标签写死」当成了「内容不可配」。
- **多批分给不同 agent，判定列会出现口径漂移**。实测：同一套前端，第一批（Hermes 子代理判）可配率 55%，后三批（Cursor 判）只有 23%，差了三十多个百分点。规矩：**可配这种主观列只能由一个 agent 从头判一遍**，或每批次都要求附「判定理由」并比对各批可配率，偏差过大就统一重判。
- **不要中途加列**。第一批做完才想起要「内容是否可配」这一列，结果前 153 行缺列、要补跑一轮。开工前把列口径一次定死，包括以后要不要加「判定理由」。

### 验多少真机：分层，不做全量（用户 2026-11-04 定）

矩阵已经回答「有没有」，再套一遍真机就是重复劳动。规则：

- 矩阵判「没有」→ 采信，证据来源标权限矩阵
- 矩阵判「有」且与内销一致 → 采信，同样标矩阵
- 只有三类上真机：①矩阵判「有」但疑似空壳（菜单授了、数据不通）②区域间有差异要写清具体差在哪 ③触达、卡券、私域、用户行为等核心页挑 8-10 个亲眼验

量级约 40 次真机，其余全走矩阵。代价：边角页面功能层细差异可能漏，但那不是领导会问的。

**每一行必须标证据来源**（权限配置 / 租户配置 / 源码 / 真机）——四种强度不同，领导追问「你怎么知道巴西没这个功能」，答「权限中心巴西角色没授这个菜单」和「拿巴西账号试过」是两回事。

### 铁律：外销侧必须先有正向功能清单，再反推内销（2026-11-05 血泪，320 行返工）

**顺序做反 = 整张表作废。** 2026-11-05 导购工作台实测：只有外销路由表（18 条）+ 页面映射表，**没有一份「外销每个页面到底有哪些功能」的清单**，就直接从内销 1136 行反推外销「有没有」。结果 320 个区块的外销结论全是推出来的、不是查出来的，用户一眼挑出「印度没有销售 tab 却把销售功能填到印度列」，整表退修。

规矩：

1 **先建外销正向功能清单**：逐个页面读源码，列出该页有哪些功能点，带 `文件:行号`。外销页面数通常远少于内销（实测 10 页 vs 内销 61 页），一两小时能做完。这份清单是外销侧唯一事实来源。
2 **再拿它判定内销功能在外销有没有**。有据可查，不是凭「内销有这功能、外销代码里好像没搜到」。
3 **没有外销正向清单之前，不许往表里填外销列的 √/部分/×**。填了就是给返工埋雷。

反向自查：如果说不清某个外销判定是基于「外销某页某行的什么功能」，那就是反推的，不许落表。

### 印度列与印尼列极易看混，核对时必须带列号

「印度」和「印尼」在 Excel 里只差一个字，而且第 14 列（印度-差异备注）紧挨第 15 列（印尼-截图），实测用户和我都把两列看成过对方。沟通或验收时一律写「第 14 列（印度-差异备注）」「第 15 列（印尼-截图）」，不要只说「印度列」。

印度口径本身也有坑：**印度有导购工作台，只是没有销售 tab**，不等于「无导购工作台」。所以印度列不能整列填 ×，只有销售相关功能填 ×，其余按实际填「待核」。西班牙（有商城无 CMS）与巴西（两者都无）才是整列 ×。

### 外销截图必须带壳，与内销截图形态不同属正常

- 外销跑在小程序里：手机状态栏 + 小程序导航栏 + 右上角胶囊（···｜×），总高 100 CSS px。
- 内销跑在企业微信里：手机状态栏 + 企微导航栏（左返回箭头 / 中标题 / 右「更多」三点），**没有胶囊**。
- 两套外壳参数分开写进 openPage.js 的 injectShell 选项，禁止混用。截图前必须隐藏浏览器注入的浮层（`#immersive-translate-popup`、vConsole），那些不是真实环境的东西。
- 图插进 Excel 时，**内销截图列与外销截图列都必须按页做单元格合并**，图锚定在合并区内居中。为了「保住合并区数量不变」而改成逐行锚定，结果是图乱插放，排版全错——合并区多少不是验收标准。
- 同一页的内销图与外销图行高按两张中较高者取；**全表行高统一**，不许个别页面因为多插了外销图就被抬高，否则整张表看起来参差不齐。

## 七、无登录态 H5 的本地 mock 截图流水线（2026-11-05 跑通）

对比表的截图列靠这条跑出来，替代此前「容器内 H5 无法截图、只能人工」的判断。前提：源码快照能在本地 `pnpm dev` 起得来。

**顺序不可颠倒：体检 → 分类修 → 复检清零 → 才截图。** 边截边修会反复返工。

关键实现点：

- **打开逻辑必须抽公共模块**（openPage.js），体检脚本与截图脚本共用。不抽的话体检全绿、截图却退回直开 URL：依赖 query 的导航高亮失效、依赖第三方 SDK 的页面空白、依赖特定 UA 的页面弹窗。
- **底部导航选中态常依赖 `route.query.type` / `pagePath`**，直开 URL 不会高亮。逐页读组件确认参数名写进路由映射表，不改业务代码。
- **「页面无实质内容」不能只看选择器命中**，要算剔除固定文案后的文本长度。必须剔除 `.iframe-footer`、`.tab-bar`、`.van-nav-bar`，以及**防截图水印容器**（水印会把同一句员工姓名重复几十次，直接污染字数统计）。同理克隆 body 取 innerText 前要先剔除 `display:none` 元素，否则 `v-show` 隐藏的弹窗文字会被算进去造成假通过。
- **mock 数据量必须在开工前就定硬指标，不能等截完图再说**。实测踩过：只要求「页面有实质内容」，fixture 给 3-5 条就过了验收，截出来一屏都填不满、大面积留白，图根本不能用，白跑一整轮。规矩：列表类接口一律 20 条、分页 total 200+、字段值必须互有差异（姓名/机型/状态/日期/金额轮流造变体）、头像与封面二维码用 data URI 不许空 src。体检脚本加一项「列表项数 ≥ 10」，与原有项并列，低于 10 且不是本征空态页即不通过。
- **截图必须配空白自检**：非白像素占比 + 文件字节数双信号，占比低于 2% 的逐张人工看。否则「成功 61 张」里混着空白图，插进 Excel 才发现。
- **文件名含 `/`**（如「素材详情（朋友圈/社群）」）在 Windows 写盘会失败，生成前统一替换为 `-`。
- **页面名与截图文件名必须精确匹配**，不许模糊；同一页面在主表里可能被拆成两段，填截图列时按「页面首次出现行」填，不是每段都填（实测出过 63 处 vs 应为 61 处）。

公司环境已知坑：

- **地图类页面**依赖定位成功回调，本地 key 域名白名单失败会让整页 `v-show` 隐藏。用 Playwright route 拦截 SDK 域名 fulfill 本地 stub，不改业务代码。
- **「加载中」类中转页**要改 `waitUntil` 为 `load` 而非 `networkidle`，否则挂起的接口会让 networkidle 等满超时后走到错误分支。
- **页面 JS 用构建期注入的空字符串覆盖 cookie** 时，`addInitScript` 里直接写 cookie 会被覆盖。可靠做法是劫持 `document.cookie` 的 setter，把空值写入替换成 mock 值。
- **公司 DLP 对 .xlsx 做异步透明加密**：生成几分钟后文件头变成 `%TSD-Header-###%`，本机打开无感知，但外发/上传会失败；TSV 不受影响。判断是否被加密看文件头前两字节是否为 `PK`，不要只看能否打开。生成与校验要连跑，利用加密生效前的时间窗。发出去前要么走解密流程，要么改发 TSV 或截图压缩包。

插图规范（Excel）：每页只在「该页首行」填文件名，其余行留空；图片锚定该单元格向下浮动、宽度按 130px 等比缩放；插图行行高要大于图高，避免压住下一处页面首行。
