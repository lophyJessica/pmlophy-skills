# A2A Instruction Format (五段式)

## 原型/前端类指令：必带的两条（2026-10-23 用户定，漏了会被当场指出）

> **实现指令里夹带的 UI 数值会被写进 PRD（实测，用户当场崩「为什么prd的交互说明写UI规范啊」）**：给 agent 派「做某交互 + 回写文档」类活时，指令里列的尺寸/色值/字号/字重/圆角会被照抄进 PRD 的【交互说明】。写数值时**必须紧接一句「这些只用于实现，不许写进文档；文档只写行为」**——不写这句，交付回来的 PRD 就带着 62×32px / #E9EAF1 / 700 这种设计规格，得重做一遍。自查：交付验收时 grep 主 PRD 里 `px`、`#[0-9A-Fa-f]{6}`、`字重`、`圆角`，应为 0。

> **「做功能」与「回写文档」必须分成两个阶段、中门必须停**：把两件事写进一条指令一路跑到底，结果就是功能做了、文档只改一半（正文改了图还是旧图、发布版没重生成）。正确写法：第一阶段只做功能并交验收（build + 点击流程跑通），Checkpoint 停；我确认功能真实存在后，才发第二阶段回写指令。理由：回写的硬规矩是「忠实已实现」，功能没验收就回写 = 把没验证的行为写进文档。

> **设计稿交给 agent 复刻前，形态必须先由 Hermes 用视觉模型逐属性文字化**：agent 自己看设计稿图会走样（小程序胶囊导航栏二次复刻都做错），且聊天里贴的图它读不到。正确流程：Hermes 先 `vision_analyze` 读设计稿（一次只问一个区块的全部属性：控件构成/颜色/圆角/分隔线/显隐条件/交互回退行为），把读到的形态**逐条文字化写进指令 Context**，并写明「全部按此执行，不需要再去看图」；agent 只剩机械落地。验收自查代办：形态若再次做错，升级为 Hermes 直接给完整组件代码让 agent 原样落地，不再第三次靠它读图。
>
• **公用形态看板类功能（导航栏/外壳）走「应用外层统一包装」，不做逐页插桩**：用户直觉是「外面包一层规范样式即可」——小程序导航/TabBar 这类全应用共用的外壳，正确结构是 App 根容器统一提供（状态栏+导航栏常驻、router-view 只换内容、TabBar 钉壳内底部），页面组件不感知导航。逐页插一遍 NavBar 是双倍维护面的错误做法，还会引入「搜索态下哪一层负责隐藏」这类两层协调问题。指令里写「外壳由 App.vue 统一提供，页面组件移除一切导航挂载」。页面内残留的旧导航偏移（top: NNNpx / padding-top 叠加）也要一并清，否则出现「导航栏与内容之间一条多余空白带」——旧层偏移不会因为新层接管就自动消失。
• **图标渲染走纯 CSS/SVG，不走组件库 nx-icon/字体图标（组件不可 import 时）**：本项目 unplugin-vue-components 只配了 VantResolver，vos-ui 组件靠 babel-import 插件（只转 import 语句，不注册全局组件）——组件内直接写 `<nx-icon>` 没 import = DOM 有节点但字形为空 = 用户看到的「返回箭头没有」。且该图标 name 全项目无其他用例可证有效。修复形态：返回箭头用纯 CSS chevron（12px 方块 + 左/下 2px solid #111 边框 + rotate(45deg)），不依赖图标字体与组件注册。验收时区分「DOM 有节点」与「节点可见」——agent 自报「DOM 数量=1」不算修好，用户实测才算。
• **「agent 自检表全过」与「用户实测不符」连续两轮时，下一轮必须收运行时证据**：让 agent 交判断代码片段 + 目标路由下运行时实际取值（route.meta 关键键/console 输出），不再收自检表；同时要求用户 push（agent 完成后不 push 是常态，父会话读不到代码只能靠截图推理），验收通过后主动提醒 push 一次恢复「父会话能读代码核验」的基线。

> **复刻类指令的四条更硬的红线见 `references/frontend-replication-prompt-template.md` 末节**：① 原系统用什么组件库就用什么，不许替换（写「不能用就替代」= agent 会整套换掉，交一个「有源码还样式完全不同」的产物）；② 取不到证据时标注「未取到」，不许静默交简版（用户会问「为什么要做简化」）；③ 真源是现场 DOM / 跑起来的系统，不是仓库文档；④ 手机端原型 375px 容器的 `cqw` 必须有 `container-type: inline-size` 才生效。

1. **标注只做增量，不做历史**：本项目只标**本需求新增/变更的功能点**；既有功能/字段/列不标（forge 当时的全量做法不要照搬）。
2. **新增项必须蓝色标识**：新增的菜单、功能点、列表列、字段、按钮在原型与红框图里用**蓝色**标出（本项目已采用“列头文字变蓝”；既有项保持中性灰），否则评审看不出本次到底加了什么功能、加了哪些字段。写完原型类指令自查一句：“蓝色标识要求写进去了吗？”

## 地基归我、实现归 agent（用户当场纠正：「你为什么要改？你把关系理清楚，把地基约定好，让 agent 去实现啊」）

「我不亲自下场」不只针对代码——**改 PRD 正文、改流程图、改字段清单、改原型，同样归 agent**。我动手写文件就是越界，会被当场叫停。我该交的是：

1. **地基约定**：层级结构、控件形态、可选值、默认值、互斥/边界规则、数据结构（整棵树而不是平铺列表这种约束），写成一屏可拍板的形态；
2. **待拍清单**：我从证据里拿不准的（相邻两个还是每组一个、上限多少、作用域到哪），逐条列出来让他定，**不要替他拍也不要脑补**；
3. **验收判据**：每步交什么、什么算合格。

拍板之后，5 段式指令派出去，我只验收。

## 原型交付没有过程性标记，也不许自造生产端没有的区块

两条原型红线，写进每条给前端 agent 的指令：

1. **原型里不许出现任何进度/过程性标记**——「待改造」「查看态改造留待下一步」「生产端 6 套分支已映射」「TODO」「暂未实现」这类给内部人看的注记，一律不得进交付原型。评审看到「留待下一步」就直接判没做完，解释也挽回不了。自检：交付前在原型仓库 `grep -rn "留待下一步\|待改造\|TODO\|待实现" src/`，必须为零。
2. **原型不得比生产端多オ区块/能力**。实测：原型查看计划页自造了一个「生产端 6 套分支已映射」的渠道卡片区（邮件/富媒体/普通短信/WhatsApp云端直发/导购定向直发/导购转发），而生产端查看页只有一行统计表——一个计划只对应一个渠道。这类「我以为要展示全量」的区块进评审就是送分题。反方向的错更贵：**把生产端真有的区块删掉**。区块存废按两层核，缺一层就会删错：

1. **区块清单以源码取证档为准，不以交接文件、也不以截图为准**。交接里一句「查看页只有一行统计表加活动配置」是**看得见的那一段**，不是完整页面；一张截图里没有受众筛选和内容配置，多半是折叠或首屏之外。完整规格去仓库里的源码取证/差异清单找（形如 `08-相关资料/审计报告/<模块>-生产源码vs复刻原型-差异清单.md`）里那张「区块顺序 + 组件名 + 显示条件」表——它写明每个区块挂在哪个 query 参数下、哪些编辑/查看共用、只读由哪个变量控制。写指令时把**该节标题与行号**引进去，打字员式照抄，别转述。
2. **共用页面的「只读」不等于「不显示」**。生产端常见形态是同一 URL 同一套区块，查看态只把 `readonly` 置真。指令里写「查看态只保留 A 和 B」会被当真删掉；正确写法是「整块保留、全部不可编辑、页脚只留关闭」。补区块时同样要按取证表补齐每个字段（活动配置常是五项而非三项）。
3. 历史文档里记的区块/列名也可能过期（同一张统计表，旧文档写「发送账号/预计发送人数/实际成功发送数/实际触发失败数」，实际已是「渠道/预计发送数/频控数/实际发送成功总数/实际发送失败总数」）。**列名以最新实机截图为准，区块存废以源码取证为准**。

3. **评审讨论本身也不许长在页面上**。除了进度标记，「待确认」徽标、「待确认方案：A / B」、「可编辑字段 / 不可编辑字段」这类把内部讨论搬上页面的卡片同属违规——它们归 PRD 的待确认段，页面只呈现形态。写指令时把这条单独列出来：agent 天然会把“把规则讲清楚”当成贴心。
4. **线上没有的元素一律不加，包括“看起来更清楚”的小增补**。给区块标题加数量角标（如「行为筛选 (1)」）、加计数、加解释句，都算自造，用户会当场问「你加这个是干什么用的」。新增只有两个正当来源：定稿 PRD 写过的、线上本有但要改口径的。指令里直接写「线上没有的元素不加」，否则它会按自己的审美补。
5. **取证前先分清“这块功能在被取证系统里到底存不存在”**。本期新建的功能（如用户行为页面）在存量系统里根本没有，让它去线上取证只会绕圈、甚至拿别的站的材料充数。指令里写死两件事：① 每个区块从哪个站取证（各系统只认自家站，不得互相顶替）；② 哪些区块是本期新建、不用去线上找。取证结论要求标来源站，以便事后分辨哪个权威。

**Output format 里默认写「不截图，用文字描述页面元素、默认值、切换前后的实际数值」**：用户视障，让他拿截图验收等于没有证据，还得再问一轮。它已经截了也不必返工，回一句改成文字即可。

**Hermes 自己用视觉模型读截图，也不能当字符串级证据（实测）**：截图经视觉模型转述后，括号、色值、单位、字序这类细节会被读出文件里并不存在的东西——实测把文件里的 `rect rgb(240,245,255)` 读成 `rect [rgb(240,248,255)]`，据此下了「语法写错了」的错误根因，被用户拿本地文件原文当场证伪。规则：涉及**文件内容、代码语法、字段名、枚举值、列名**的判断，一律先读文件原文，或让 agent 交「行号 + 原文」；截图与视觉转述只用于判断「某控件是否存在、大致布局、有无置灰」，不用于抄字符串。给用户的结论被证伪后，一句「以你本地文件为准 + 我判断错了」就够，不要垫一段解释。

## 改原型前先读原型源码核实「现状」，不要把交接里的改造清单直接翻译成指令

交接/待办里写的「五处改造」是症状清单，不是工作量账本——同一份清单里往往混着「加一个控件」「改一处文案」和「整块结构重写」三种量级。不核实就写指令，会把重写写成改文案，agent 交回一个改了字但结构没动的半成品。

派活前必做三件：

1. **逐项定位实际文件与当前结构**：先用文案关键词 `grep -rn "<页面文案>"` 定位渲染点，再读组件看层级/状态结构（数据里有没有「组」这一层、上限写在哪个常量、关系取值有哪些），把每一项判成「已具备 / 缺什么 / 必须重写」。
2. **结论先报给用户再发指令**：三类分开讲——已具备的不许重复派活（重复派活=让它重做已有的东西，容易改坏）；重写项单独给目标数据结构（层级、可选关系、数量上限、默认值）；并说明它为什么不是改文案。用户据此判断这一轮值不值。
3. **指令按「重写 / 新增 / 删除」分组**：重写项必须给出目标数据结构，因为原结构里可能压根没有那一层（如条件筛选原先只有扁平条件数组、没有「组」），不给结构它会就近改造旧形状。

**旧字段常以注释块形式残留，grep 命中 ≠ 页面渲染**：React 组件里被 `{/* ... */}` 包起来的旧实现照样能被 grep 搜到。核实现状必须确认那段 JSX 是否真的在 return 的渲染分支里（看 `isEdit`/`mode` 等分支实际渲染了什么），注释块只作历史参考。误把注释块当现存实现，会写出「把 A 改成 B」的指令而页面本来就没有 A，或者漏掉真正在渲染的旧控件。

**原型与 PRD 不一致时，先查字段清单 TSV 判谁是过期方**：字段清单是字段口径的唯一事实源。TSV 已删除的字段 = 旧口径，文档和原型都要删（不许因为「原型里有」就加回文档）；TSV 有而原型没渲染的 = 原型漏做。裁决完再决定这一轮改文档还是改原型，不要两头各改一遍。

## 地基阶段四条硬规矩（都是被纠正后长出来的）

1. **只解决他说的那个缺口，不顺手扩能力**。业务诉求是「把授权状态放进列表、能看见能筛选」，我顺手把枚举从三态扩成四态就被打回（「为什么要扩展授权状态？现在就三个枚举」）——扩枚举 / 加字段 / 加配置项都必须先问，不能拿「这样表达得更全」当理由。地基里每多一个值域，开发与数据侧就多一笔成本。
2. **文件数量不写数词，逐一点名**。指令里写「把三个文件一起提交」而实际只有两个，agent 会卡在 Checkpoint 反问你第三个是哪个。写成「A.md 与 B.md 这两个文件」。
3. **事实型口径以实机截图为准，不以历史结论为准**。同一个列表，旧文档写「数据同步时间到分」而实机到秒、旧结论说「接口里没有聊天记录字段」而系统里有独立的「查看聊天记录」入口——派活前先拿截图核一遍，冲突处以实机为准，并在指令里写明本轮改哪条口径。
4. **回报格式固定四件套 + 停在阶段结论**：① 改动文件清单（文件 + 改了哪几段）② `git diff --stat` ③ 关键 diff 片段（改动处前后各 3 行）④ 逐条自检（内容是否与指令逐行一致、几张版本表都加了没、是否动过其他文件），最后一行必须是「停在阶段结论，等我确认」。它顺手提的现状问题（新图方向与原图不同、某处标题与内容不匹配）要逐条裁决，别默认放行——这类提示往往正是漏改的那处。

## 产品流程图与需求交付：先理地基，再分步派 Qoder

当任务涉及系统流程图、业务流程图、功能清单、字段清单、主 PRD、Demo PRD、原型等一组互相引用的产物时，先由父会话完成产品判断，不要直接让 agent 从截图或旧文档自行推导：

1. 先锁业务链路：维护用户行为（业务提需求→CMS向大数据提建表→大数据建表并写入→CMS配置行为）与触达计划使用（标签/行为筛选→生成名单→触达）必须串成一条业务流程；系统流程图保留跨系统时序，业务流程图表达页面操作。
2. 组合规则必须写成层级树，不能写成平铺“条件列表”：标签筛选块、行为筛选块各默认一个；每块最多 4 个组；标签块一组对应一个标签，行为块一组对应一个行为；两个块之间且/或/非；同一块内组与组之间且/或/非；同一组内属性/数据条件之间且/或。非作用于被标记的那一组并从最终结果全局剔除，不是相邻连接符，也不是组内关系。
3. 继承既有定稿图时，先读取仓库现行版本，在原四段时序图（行为需求与建表、配置行为、取数圈人与名单、触达）上做最小增量；不要凭记忆重画一张简化图。
4. 交付顺序固定为：流程图→功能清单→字段清单→主 PRD→Demo PRD→原型。每一步必须单独派给 Qoder（或用户指定的 agent），完成后停止，等用户拍板；不得把后续产物顺手一起改。
5. 流程图先只给用户审阅 Mermaid 源码，不直接落仓库；用户拍板后再给 Qoder 指令落盘。指令必须要求保留未涉及的四段链路与系统参与方，不擅自改图形表达、系统名称或业务责任边界。

### 流程图阶段验收

- 系统流程图必须包含 BIZ、外销 CMS、大数据平台、短信中心、牛信云五方及四段链路；“取数、圈人与生成名单”段须传递完整组合结构，不能平铺丢失关系。
- 业务流程图必须从业务维护用户行为开始，经过建表/配置，再进入触达计划受众筛选、名单生成和触达；只画页面使用、不画维护链路，视为不完整。
- 组合规则、组数上限、非的全局排除语义必须在图注或交互说明中明确；不要用“包含/排除”替代组间且/或/非，除非用户重新拍板。
- 图通过用户拍板后，才进入功能清单；不要把未拍板的算法细节写成事实。

### 派活前先在父会话拍掉的口径（写进指令前自检，逐条都得有结论）

每一步产物派出去之前，这些口径必须先定好并写进指令的「定稿口径」段，不能留给 agent 自行判断，也不该让它们变成产品待确认项：

1. **枚举不因「看不见」而扩**。业务说“列表上看不出情况”时，诉求通常是**把字段放上列表并支持筛选**，不是新增枚举值；扩枚举必须有系统侧取值证据（曾把授权状态三态扩成四态被当场驳回）。
2. **导出类能力合并成一个入口**。全量 / 按筛选是同入口的两个选项，附加导出项（如会话记录）做成勾选框，不拆成两条功能。
3. **字段增减先算列数给用户选**，不要自己默认替换。既有字段是否保留、新增字段是否叠加，把两种列数（A：17 列 = 9 旧 + 8 新；B：18 列 = 再加一个）列给他拍。
4. **技术实现类问题不占产品待确认位**：数据量限流与分片、编码一致性、大表查询性能由对接研发 SE 在架构层承担，文档里写一句归属即可。
5. **不阻塞主流程的问题写进「待确认」节就继续产出**，不停下来等外部答复——用户会攒着统一对，不会一个问题就去问业务。已定设计的条目写成备注式（“本期已按 X 设计，此条为与业务确认的备注”），不等同于开放问题。
6. **功能清单列名写「功能描述」**（不是“一句话说清”）；条目合并/拆分后功能清单与待确认表都要重新从 1 连续排序号，否则会出现重号。
7. **删减类需求：整块删，不留尾巴**。用户说「取消就取消了，不要再留尾巴，不做，啬嘛给自己添工作量」——指令里就要写死「相关章节/表格行/用例全部删除，不留替代说明、不写取消原因、不写‘以后可能要捡回来’的钩子」，变更日志只记一句「删除 X」。只有「领导拍板砍的需求」才需要在修改记录里写一句缘由好交代；普通删减按前者处理。

判断法：一条口径如果会改变产物里的条目数、列数或枚举取值，它就属于父会话该拍的，拍不到就把两种算法摆给用户二选一，不要默认。

## 多交付物任务：按用户给的顺序分步，每步停

交付物超过一件时，**顺序和停止点由用户定**，不按我的效率最大化。项目上已经跑通的固定链路：**流程图 → 功能清单 → 字段清单 → 主 PRD → Demo PRD → 原型**，每完成一步停下等他拍板再开下一步。用户说「今天节奏慢一点」时，就是要把这条摆到明面上——不要「顺手」把下一步的产物也改了，也不要把一步的成果自行打包成下一步的输入。

**链路尾端还有一环：原型定稿 → 重出红框截图 → 回写评审 PRD / 重生成发布版。** 带截图的 PRD 回写必须排在原型之后，不要为了「先清一个小尾巴」提前只改正文：评审 PRD 的页面说明配的是原型整页红框图，原型没定稿就改文本，结果是新文字配旧截图（图和文字打架），加上原型验收后还要再改一遍——两轮返工。用户纠正过按「先改文档、再出原型」排的节奏，正确排法是先出原型给他审，他点头后再一次性回写文本 + 重截图 + 重生成发布版。

**步与步之间会互相卡**：上一步没拍的参数会直接卡死下一步的条目数（比如组合逻辑的层级/上限不定，功能清单就拆不准）。发现这种依赖就当场说「到第 N 步你得先给这几个答案」，并把它们先作为待确认标着，不自己填。

## 改既有交付物前先读仓库现行版，不重画

对已经落过稿的东西（流程图、PRD、字段清单），第一动作是 `read_file` / `grep` 读出仓库里的现版，在它上面做**最小增量**（改哪几行、为什么改要说得出来）。凭印象重画一张「更新的、更简洁的」新图 = 前面的定稿全部作废，用户会直接把上一版贴回来问「在这个基础上做，你忘了吗」。

**派生结论**：用户会把上一版原样粘给你当基准，粘回来的就是权威版；**版本号/页数/条数一律报实测值**（`grep '^| V[0-9]'`、`wc -l`），不报印象值——各文档版本号互相独立，用户记忆里的 3.5 和仓库里的 3.3 经常对不上。

## 铁律：一个写手 + 指令必标基线提交号（2026-10-30 用户实测结论）

用户原话：「分开两个 agent，还不如 cursor 一个 agent 全部跑完更效率」「指令互相打架」「文档干文档的口径，原型做原型的，不应该互相取交集」。

- **判并行还是串行，只看两条**：① 口径是否互相依赖；② 是不是同一个工作区。任一条成立就串起来交给一个 agent 做到底。文档要写「行为维度」，得看原型刚改成什么——这就是口径依赖，不能拆。
- **「文件域不重叠就能并行」是错的**：共享工作区本身就是冲突面。两个 agent 在同一 repo 同时跑，后 pull 的那个会把前者未提交的改动卷进去（实测 Qoder 报告「已恢复工作区原有的 4 个原型代码改动」——那不是协助，那是自己给自己制造脏工作区）。
- **指令第一行写基线提交号**（如「基线应为 51fc129」）。两条并发指令各自写「先 pull 到最新」时，它们 pull 的不是同一时点，两个 agent 对「当前口径」的判断基准不同，产出必然对不上账——这不是运气差，是必然。
- **口径耦合的活由父会话收一次交集**：原型先一次改到冻结 → 父会话把最终形态提炼成口径清单 → 文档按清单改，不让文档 agent 去读原型代码。不取交集的是执行层，取交集的是我这层，且只取一次。

**清单必须父会话先扫全（2026-10-30 一天踩三次）**：给 agent 的「逐处修改清单」若只按上一轮报告的某几段摘，必然漏同节里的其他条目——实测三轮审计、每轮都报「清单之外还有 N 处漏改」（旧枚举 10 处、旧示例 3 处、旧字段名若干），每次都要再开一轮。

- 写清单前用 `grep -rc '<关键词>'` 对每个旧口径词做**全仓计数**，再按文件列出来；不要按段落摘抄报告。
- 清单里逐项写明文件与行号，并补一句「同类表述一并扫，报残留数」。
- 交付验收看它报的残留计数，不看「已全部替换」。

## 并行派活：每条指令必须标「发给谁」（2026-10-23 用户定，原话“指令后面给谁，再清楚点，现在 cursor 跑 3 个 chat，还有 Grok，别乱”）

同时给多个 agent / 多个会话派活时（Cursor 多 chat + Grok bot 并行是常态），**每条指令正文之外必须带两样东西**：

1. 一段**「指令 → 谁」路由表**（谁跑哪条、哪个会话做哪件事），同时交代哪些必须串行、哪些可以并行；
2. 每条指令开头自己带一行**归属标签**（如“发给 Cursor·会话3（内销源码对标）”）。

打包规则：

- **默认不合并指令——合并只能由用户提出（用户原话：「不要随意合并，因为很多时候你给我的第一时间，我已经给agent在跑了，除非我让你帮我合并」）。** 我把两条独立需求"顺手合成一条"时，用户手上那条往往已经贴进 agent 开始跑了：合并版要么覆盖不了在跑的那条，要么让他重贴一遍，等于整轮白跑加返工。所以新冒出来的需求一律**单独成条、开头写明给哪个 agent**，绝不自己缝进上一条；要合并就等他说一句「你帮我合并」。同理，回复里也不要说"这两条我合并一下"，那是替用户做了他已经在做的事。
- **每条指令的归属标签写在正文外第一行**：`【发给 Cursor · 会话 N（干的什么活）】`。一轮里同时在飞的 agent 越多，这一行越是必需——漏了用户就贴错窗口，而且他不会先问，直接跑错一轮再回来找你。
- **同一个 agent 不要堆第三条并行任务**——出图占 dev server、抓数占浏览器页签，再加一条会互相踩；用户自己会说“cursor 可以开第三个会话”，在此之前按 1–2 条排。
- **同一仓库存写动作的指令不并行**；只读型（源码对标 / 抓数 / 出图）可以并行，但要避开共用资源（dev server / 同一个浏览器实例）。
- 回复多条并行指令时，**一条一条分块给、块首写归属**，不要混成一大段——混在一起用户不知道复制哪段给谁。
- 用户在会话中插入新任务时，**先重排路由表再给正文**（谁的手上现在几条、哪条先停）。

## 先分清「用户在派活」还是「用户在叙述」——不确定先一句确认

用户消息常是**分段打字**：前一段是背景，后一段才是真要求（“我先把 cursor 跑起来” / “你先沉淀下记忆” 这类）；也可能一句话里同时在说他**已经让 agent 在做的事**。看到「改一下这个 html，让他加上交互效果」这类话，不要立刻产出一整份五段式指令——它很可能只是在告诉你 Cursor 正在干什么。

- **判断信号**：上一轮他说过「我先让 cursor」「我本地让他做了」→ 本轮的「让他加上 X」九成是叙述，不是委托。
- **处置**：先用一句抹确认（“这条是你要我给指令，还是你已经让 Cursor 做了、只是跟我说一声？”）——一句疑问成本十秒，误判成本是一整份指令加一轮撤回。
- 判据：用户说「你出个指令 / 给你指令 / 这个指令」= 委托；只是描述某个动作正在发生 = 叙述。
- **最常见的误判形态：用户先发来产物（截图／HTML／文件），紧跟一句「改一下这个，给他加上 X」**——那不是要你写指令，是在转述他已经交给 agent 的活。只要上一轮出现过「我先让 cursor／我本地让他做了」，本轮的「让他……」按叙述处理。
- **误判后的处置就一句话撤回**（「那条指令不执行，我撤回」），不要解释自己为什么写错、也不要说是他表达不清——整套指令已经白写了，再垫一段复盘就是第二次浪费。撤回后直接停在等他的产物。

## 铁律：指令里禁止制造“每个交付结尾一句请示”（2026-10-30 用户批）

用户原话：「特别反国内的 agent 设计，总会在做完一句后，说一句 xxx 未动，需要你说一句」——那是把决策成本转回给用户，一次交付十处就是十次打断。

根因在指令自己：**「拿不准就停下来问」写得无限宽**，agent 无法判断什么是真拿不准，于是所有细节都算。改为可判定的两段式，写进**每一条**指令的交付纪律：

1. 只有一类可以停：缺少的信息会使**产物口径出错**，且无法从仓库现状与已定口径推出。
2. 其余一律：按已定口径自行判定并执行，结论写进报告的「处理记录」一节；不反问、不给选项题、不在结尾留「某某未动，需要你定」。

配套：指令的 Output format 里固定要一节「处理记录」，接收这些自行判定的条目——有出口就不必反问；不要只写「待确认节」而不给自主判定出口。

## 铁律：指令一旦发出即冻结，补充一律开新指令（1021 用户定）


> **反面（2026-10-30 用户批）：「不要老是加增补指令」**——发出去的主指令还在跑（跑一半），就又追发 1-3 条增补，用户没法中途停掉重新整合，只能一条条贴，越贴越乱。规矩：**一轮只发一条指令；能预见的都写进首条，写不进的攒到下一轮整包发，不在同一轮里打补丁**。漏项先记在看板，等这轮 agent 交付并停稳后，与下一轮任务合并成一份完整指令再发。判断法：如果我正在写的“增补”只是把口径说清楚，而现在这一轮还没结束，就并到下一轮；只有“再不改就会做错整批”的事实错误才值得立即追一条。

现实场景里指令发出后 agent 很快就开始跑了，**回头修改原指令 = 无效操作**（对方按旧版在跑，改了也看不到）。所以：

- 已发出／已开跑的指令**永不修改**；发现前提错、要补内容、要改红线——一律**新起一条指令**，写明“在上一轮基础上追加／纠正”，并显式说明增量范围与“不重复已完成的部分”。
- 新指令编号连续（如 03 → 04），标题写清本轮增量。
- 原指令前提根本错时（如照错误现状写的），也只发新指令叫停／纠正，不原地改。
- 推论：**首条指令要尽量一次写全**，可预见的补充前置进去，别指望“先跑着，回头再补”。

### 同一口径改了几轮：最后一条必须写「替换之前所有相关补丁」+ 给完整覆盖文本

同一个字段一天内把口径改了四轮（三项 → 两项 → 不出现第三项连说明都不写），最后 agent 落地的是**中间某一版**——它按能对上的那条补丁执行，不会自行判定哪条最新。规矩：

1. 每条新口径开头写「**替换之前所有相关补丁，以此条为准**」；
2. 给**一次性覆盖的完整文本**，不要写「在上一版基础上再改 X」——增量描述链条一断一节，后面全错；
3. 收尾要求它回报「全文扫旧口径 = 0 处」，并在指令里点名扫哪些文件（含红线外目录也要看）。

### 砍选项 / 砍功能：连「不支持 X」这类说明一起删

用户口径是「这个选项根本不存在」时，**留着「不支持提前」「不设提前」等于告诉执行方和评审「这里本该有个字段」**，会引出追问。指令里写死：「凡出现 X 及其实体为空的说明，一律删除，不做不支持说明」。同理「取消某功能」要**整套删**（章节 / 表格行 / 字段 / 用例 / 功能点），不留替代说明、不写取消原因、不写「以后可能要捡回来」的钩子，变更日志只记一句「删除 X」——用户原话「取消就取消了，不要再留尾巴，不做，干么给自己添工作量」。
- 同一仓库不要同时开两条有写操作的指令（会同改文件）；只读取证型指令也应等前一条跑完再开。
- **同一需求重发指令时必须点名「以哪条为准、前一条作废」**：连续发两条内容相近的指令（润色重发、补漏重发），用户分不清哪条该跑，会直接问「到底哪一个指令，你刚刚发了我两个」。重发时开头一句写「用最新这条，前一条作废」；内容完全一样就不用重发，只补差异部分。
- **不同任务的指令连着给时，也必须一句话交代「现在跑哪条、另一条什么时候用」**：一轮里先后发出两条各自独立的指令（一条改文档、一条改原型），用户回头只看到两个代码块，会直接问「两条指令我用哪一个，上还是下」。正确写法：每条指令**块外第一行**标明任务名与先后关系（如「这条是 PRD 收尾的，排在原型验收之后」／「这条是原型的，现在跑」），并在最后一条后面说明另一条的启用时机。尤其当用户中途改过节奏（先文档后原型 → 改成先原型后文档）时，旧那条要么明确标「暂缓」，要么当场重出——留着不标注就是给用户挖坑。

## Agent Role: 指令命令官 (Commander, NOT Executor)

> 方法论背景：AI 四工程框架（提示词→上下文→约束→循环）的实践映射与面试弹药见 `references/ai-four-engineering.md`——本 skill 的五段式/红线/门禁/管道都是"约束工程+循环工程"的具体落地。
>
> **DeepSeek Harness (dsh) 是用户 0814 新装的 agent 工具**（Mac 本地 3080，接 Go 通道免 DS API）——安装/四模式/Go 接入/插件清单见 `references/deepseek-harness.md`。v0.1 预览版定位玩具/研究，生产任务仍走反重力/Codex/Cursor。

Hermes 在 A2A/前端/部署场景中的唯一职责: 写指令,不执行。

**定位红线（2026-10-22 用户纠）：默认派活，不亲自下场。** 凡是**机械性、可脚本化、可交给 agent 或 skill 脚本**的活（填表、批量替换、生成 base64 发布版、渲图、grep 清单式检查、拼档），**一律写成指令交给本地 agent 按 skill 跑**——即便我自己在 VPS 上“顺手”也能做完，也不做。我的产出是：规则、指令、验收结论。
- **唯一例外：用户明确说“很急/快点”。** 那时才可以亲自下场抢时间，并事后说明为什么破例。
- 自检：动手前先问“这活能不能拆成一条指令给 agent？”——能，就住手，写指令。
- 反例（当日发生，已被纠）：自己一句句把 11 处「待补」填成图引用、自己跑 base64 拼发布版——本该是 skill `prd-doc-authoring` + `embed_images.py` 交给 agent 的事。
- **定位即止，不要顺手修（2026-10-24 再次被纠正）**：排查出根因后 **立刻停手写指令**。修复动作会横向扩散——改代码→改脚本→改配置→build→部署，一路做下去就是替 agent 把活干完了。本次自己改完 6 个文件并部署后才被叫停（“你不要自己做啊，浪费 token，让本地 agent 来”）。边界线：**我只交付根因证据 + 五段式指令 + 最后验收**；中间所有写文件/build/部署归 agent。唯一例外仍只有用户明确说“很急”。

| ✅ 做 | ❌ 不做 |
|---|---|
| 写五段式指令给反重力/Codex/Gemini | 不动手改文件(HTML/CSS/JS/TSX) |
| 分析问题 + 给出修复方向 | 不自己跑 cp/rm/chmod 部署 |
| 提供审计清单、产品决策框架 | 不自己写代码修复 bug |
| 写"批量替换/清理"指令给 agent | **不自己跑全仓 sed/批量替换（2026-08-14 用户纠正：品牌清理 22 文件我亲手 sed，被批"以前是要控制你的 token 使用，这些活可以交给其他 agent 来"）** |

**排查/调试/验证也是 agent 的活（2026-08-14 用户再次纠正：「你不要检查，这是反重力可以做的事情！」）**：不仅批量替换，**连现象排查/根因定位/逐行 debug 都该交给 agent**——Hermes 亲自浏览器逐行查 console/DOM/源码（20+ 工具调用）验证功能问题 = 同样的 token 浪费，且用户明确要求"这是反重力可以做的事情"。正确分工：用户报现象（如"原型标注点了没反应"）→ Hermes 写排查+修复指令（Context 里写清**已知现象 + 已观察到的线索**——按钮存在但面板未渲染、annotation-kit 文件在、bundle 无标注代码等，把已查到的证据直接喂给 agent 缩短排查路径）→ agent 排查+修复+build+部署 → Hermes 只做最终验证（curl 200 + grep 归零 + 浏览器看一眼）。曾犯：ERP 销售订单空白页 + CRM 原型标注问题都亲自查了 20+ 工具调用才被用户叫停——这两案例的证据收集法（注入 window.__errs 监听器抓 React 渲染错误；区分 runtime 注入按钮 vs React 组件）见 `references/spa-runtime-blank-page.md`，但**执行主体应是 agent**。

## 执行环境路径与模型分层（2026-08-19 纠正）

### 执行环境路径：Codex 跑在用户 Mac 上，不是 VPS

**给 Codex/agent 的项目路径必须用用户 Mac 路径，绝不写 VPS 路径**（`/root/repos/...`）——Codex/反重力/Cursor 都跑在用户 Mac（`/Users/liulongfei/个人文件/forge-*`），VPS `/root/repos/` 是本地镜像/旧版（Codex 只传 zip 不 push 时 VPS 仓库落后——以 Mac 工作区+线上 zip 为准）。曾犯：把 ERP/WMS 初始化指令的项目路径写成 `/root/repos/forge-wms`，用户纠正"你提供的路径是 vps 的"。部署通道里的 rsync 目标是 VPS（远端），但源码路径/工作目录永远是 Mac 本地。**判断标准：写指令前先想"这个 agent 的进程在哪台机器上跑"——源码在 Mac，部署目标是 VPS。**

#### 先确认「现在哪台机器」（2026-10-24 用户纠正：“我现在用的是 mac，不是公司电脑，给我指令时注意地址”）

用户在两台机之间切换：个人 Mac + 公司 ThinkPad(Windows)。**同一份指令在两台机器上路径完全不同，写错用户一步都跑不了。**

- **动手前先确认当前机器**：从本轮对话找信号（他说了"在公司/在家"、上一轮命令是 PowerShell 还是 zsh、有没有提"公司电脑卡"）；信号不明就直接问一句，**不要默认沿用上一个会话的机器**。
- **已知的仓库路径（用户给过的，直接引用不要重推）**：

| 仓库 | Mac | 公司 Windows |
|---|---|---|
| cms-project | `/Users/liulongfei/个人文件/WorkSpace/vivo/cms-project` | `E:\projects\cms-project` |
| pmlophy-skills（skill 库） | `/Users/liulongfei/个人文件/pmlophy-skills` | `E:\projects\pmlophy-skills` |

- **取证能力按机器分，但不要再派「抓生产 DOM」的取证任务**：Codex 跑在用户 Mac，**没有外销生产站（scrm.vivo.com）与公司内网登录态**。即使换成有登录态的 Cursor 内置浏览器，单点 DOM 抓取也反复取不准（漏掉整个区块与第二层关系控件、把系统固定条件判成自造、把默认预置条件判成没复刻），每次都是用户当场截图纠正。**现行做法：线上长什么样由用户本人核对后告知（截图或口述），我方只接事实**；需要在线状态才能判的条目在指令里标死「未取到证据，待补」，**不许 agent 自行补全或编默认值**——用户会当场追问「他依据什么补」。把「补线上默认值」派给看不到线上的 agent 等于让它编。
- **Codex 只做仓库文件内已有依据的部分**：文档之间互相打架、字段枚举与必填性、控件形态、删多余区块、路由与菜单归位——这些都有文件证据，可派。
- **仓库路径会变（重新克隆 / 换目录），表里的只当默认值，用前先确认**：用户说「我重新克隆了，本地地址是 X」就立即换掉，不要沿用记忆或旧记录。路径错一个字符，用户一步都跑不了，指令就是废纸。

- **命令按平台改写**：Mac 用 `python3`、`/` 路径、zsh 无 `#` 注释；Windows 用 PowerShell/`\` 路径、`python`。交付前扫一遍指令里有没有残留另一台机器的东西。
- **会话要开在承接改动的那个仓库**：指令改的是哪两个仓库的文件，就让用户在哪个仓库目录开 Cursor 会话；只被引用（路径、命令示例）的仓库**不要**当工作目录——会话开错目录时 agent 会跨目录搜改别的项目。
- **指令正文第一行必须写清「执行者 + 目标仓库 + 工作区绝对路径」**（用户原话：「你上一个指令给 skill 库的还是 cms 的，下次标清楚」；后又因指令归属混乱被批「指令不要混乱哈，不然返工麻烦死了」）。固定格式：`【执行者：Cursor｜ZCode｜Codex｜反重力 · 仓库 <仓名> · 工作区 <绝对路径>】`。三样缺一样都不合格：只写仓库不写 agent，用户会贴错窗口；只写 agent 不写仓库，agent 会开错目录。多条指令同时在飞时这条尤其致命——用户手上开着多个 agent 的多个会话，指令归属一混就是整轮白跑加返工。只说「找 SKILL.md 改一下」这类不带仓库地方的写法，agent 会开错目录；多仓库并行时更是必填。格式：`目标仓库：<仓名>（<工作区绝对路径>）；本指令只动这个仓库。` 引用到的其他仓库路径同时注明「只读引用，不要修改」。自检：把指令从头读一遍，如果看不出它应该在哪个目录执行，就是不合格。
- **实例**：改 skill 文本的就开在 pmlophy-skills；只有真要改原型/代码时才开在 cms-project。写指令时就把这句话写进前置段落（用户会直接问“这个指令是在哪个仓库执行”）。

## 铁律：写「对齐/重做某数据」类指令前，先自己核实唯一真源是哪个文件

凡指令要求 agent「让 A 跟 B 对齐」「重做这张表」「按真实结构补全」，**先自己 grep 确认 B 到底是什么文件，再把它写进 Context**。真源写错，agent 会认真地按错的东西做完一整轮，产出看着齐整、结构全错，返工全落在用户身上。

- **同一个概念往往有多份长得像的文件，选错就白做**：路由表（`App.tsx` 的 `<Route path>`）= 代码挂了哪些路径，混着历史别名与兼容入口；菜单定义（如 `src/config/menus.ts` 的 MODULES）= **原型侧**栏渲染的层级。改原型自己的菜单时真源是菜单定义文件、不是路由表——按路由表推出来的必然是生产别名路径、叶子漏一半、分组被压平。
- **但「让原型跟真实系统对齐」时，菜单结构的真源既不是菜单定义文件，也不是仓库里的盘点文档，而是现场 DOM**。理由很硬：真实系统的菜单是**后端配置数据**（`menu/tree` 一类接口按权限过滤后下发），前端源码里根本看不到部署出来的菜单树；仓库里那份「真实系统盘点」md 也可能是照错的取证写的（本项目就有一份被 agent 写错、删了又重抓的）。所以这类任务的**第一条指令永远是「现场只读取证」，不是「照某份文档改」**：
  - 指令要它打开真实系统，逐层读出顶部一级导航 + 每个一级下的左侧分组与叶子，**要 DOM 证据**（容器选择器、层级嵌套关系、「分组标题到底是不是可点菜单项」的判别，如 `em-sub-menu` vs `em-menu-item`），不要它总结。
  - 红线写死「不许参考仓库里任何现成的菜单结构文档或代码，全部以亲眼看到的 DOM 为准」——不写这句，它会去仓库找一份文档照着做，然后在错的基础上再错一遍。
  - 拿到 DOM 之后才写第二条「照这个改代码」的指令。
- **同一个结构被改错过一轮时，先找「最后一个方向对的提交」整文件回滚，不在错的基础上继续叠补丁**。`git log --oneline -- <文件>` 逐条看提交说明，对比现场 DOM 挑出结构对得上的那一个，`git checkout <提交> -- <文件>` 只回滚这一个文件；**配套自动生成的文件不要跟着回滚**（资源表这类从菜单程序化生成的会自动跟上，回滚它会把别的正当改进一起退掉），只把种子版本号加一触发重灌。回滚后必须跑一次 build——联合类型收窄会让旧的判断分支报 `TS2367 comparison appears to be unintentional`，按回滚后仍存在的枚举值改判断即可。
- **写进指令前先跑一遍**：`grep` 出候选文件的层级结构，看清模块/分组/叶子三层各是什么、有多少条，再决定谁是权威。数量对不上（如 27 个叶子写成一个数、14 个分组写成另一个数）说明口径还没统一，此时不许下指令。
- **派「在现有交付物上改」的指令前，先做版本对账（材料版一致性铁律）**：用户手上的稿与仓库/父会话手里的稿可能不同（他本地删过页、改过行且未同步）。做法：① 用 python-pptx（或对应读法）读出仓库版的页数+逐页标题；② 拿用户给的导出/截图数量核对页数；③ 用户提过“我删了几页/改过”时当场确认“你手上那份和仓库这份是不是同一版”——先让用户 push 他改完的版本或明确说与仓库一致，再生成落点清单和下发指令。按旧版算好的文本框号在删过页的版本里全部错位 = 整轮返工；宁可先停一轮对账，不许默认“仓库文件 = 用户手上那份”。
- **派任何「在用户交付物上改」的指令前，先做版本对账（材料版一致性）**：用户手上的文件与仓库里的可能不是同一版（他本地删过页、改过行未同步）。做法：① 用对应读法（python-pptx 页数+逐页标题 / git log / 文件 md5）读出仓库版；② 与用户给的导出物（PNG 页数、截图）核对；③ 用户提过“我删了几页/改过”时，先让用户 push 或明确确认与仓库一致，**再生成落点清单和下发指令**。按旧版算好的文本框号在删过页的版本里全部错位向下平移 = 整轮返工。用户若自己更正「是我看错了，两版一致」，也要先跑一遍页数/标题核对再快进，不凭口头。
- **给 agent 派改页类活时，把可预判的口径问题在指令里预先拍掉**：WorkBuddy 这类 agent 会把可判定的细节弹成逐题确认卡（1/3、2/3、3/3）阻塞等用户。Hermes 先自己用落点清单+渲染图把口径全拍（如「目录印不印页码」「扩展位放哪」「小卡插哪」），Context 写「定稿口径」；agent 仍有题时，父会话能从他给的坐标/渲染图判的当场判，不回问用户。
- **指令点名真源要带文件路径和行号范围**，并写一句「其余文件只读，不许拿来推断」——否则 agent 会自己再找一份看起来更像的当依据。
- **路径口径一并锁定**：真源里写的是短路径就只用短路径，显式红字禁用别名族（如 `/main/channel/channel/...`、`/main/content/...`），并在 Output format 要求它回报「0 条含别名的资源」这种可机器判的结论。

## 派活粒度：大范围盘点指令必然卡住，拆小；输出溢出改走文件

**“读完整整个应用再逐页摘录”是设计错误，不是 agent 不行**。实测让 agent 一次盘完一个多子应用的前端仓库（路由 + 菜单 + 每个页面的筛选/列/按钮/状态），跑到中途就卡住——不是模型能力不够，是单轮任务太大、上下文塞满。

**正确切法**：一次一个模块，每轮范围小、可交付、可验收；上一轮验收过再派下一个。宁可四轮快跑完，也不要一轮卡死白等。

**卡住的判据三条**：超过预期时长仍无阶段交付 / 开始重复相同的读文件动作 / 回复变慢且不提进度。命中就不要再等。

**处置顺序（卡住后）**：

1. **先让它交已完成的部分**，哪怕只有一半——发一条“不要继续跑原任务，把已经产出的内容交出来”的指令，问清做到哪一步、已经盘完哪些模块、有没有输出文件。
2. **不要重跑**：拿到已完成的部分再定下一轮范围，避免重复劳动。
3. **范围减半重跑**，并把上一轮已经查到的结论预先写进新指令的 Context——它就不必重查一遍，也不会因为信息不足而扩张范围。

**输出溢出改走文件（关键）**：agent 盘完的东西太多、往对话里刷屏时，立刻改指令："停止向对话输出，把已产出的内容写成文件"。要求：

- 按模块拆成多个 md，**不要写成一个巨型文件**
- 每份文件头写三行元信息：数据来源仓库路径、代码版本（`git rev-parse --short HEAD` 的结果）、盘点时间
- 每条摘录后面带 `文件:行号`
- 没盘到的写「本次未盘点」，不留空、不推测

然后让用户 push，我方从文件读——**文件比对话可靠，能逐条查行号**；对话里的长输出既占上下文又无法逐条核。

**同理：多章节文档产出（手册、规范、多页报告）也不是我亲自写的**。我只出「格式标准样张 + 章节骨架 + 提炼原则」，然后派 agent 按样张铺完其余章节。用户会直接说「你不用自己动手，让本地agent来」——批量写文档跟批量改代码一样，属于可派活。样张先行仍必要：没定格式就让它铺 8 章，风格不对全部返工。

## 验收：逐项对回 Output format，缺一项即不合格

agent 的交付报告可以很长、很详实、前半部分完全正确，**却整块漏掉 Output format 里的某一项**——它会交自己做到的部分，没做的直接不提，读起来毫无破绽。

- 收到交付**第一动作是把 Output format 的编号项列出来，逐项找对应内容**，找不到的就是缺项，当场判不合格退回，不要替它补、也不要因为其他项都对就放行。
- 缺项往往是「两件事要塞进同一轮」时漏掉的那一半（样式改一半、元数据补一半）——这类分两轮的指令，验收时按两轮的要求分别核。
- 反过来也要防：它可能只交了一个问题的结果就把整条指令报完成。判据是**指令里并列了几个问题，报告里就该有几个对应结论**。

### 模型分层（Sol 烧得快、Luna 省——按任务复杂度分档）

- **Sol（强模型）**：只上关键大活（审计、P0 返修、全模块标注、复杂重构）——质量高但烧额度极快（实测 3 小时烧完一天额度）。
- **Luna（省）**：小活/收口/续跑/低价跑量——便宜但质量低一档，指令边界清晰、任务拆小、验收到位才有效（Luna 需要明确指令+小范围+每步自测）。
- **分层排活**：大活 Sol 打头，额度到警戒线切 Luna 收口——但 Luna 扛不住超大任务（用户实测"opencode 扛不住，只能开小灶的活"）。**切换引擎要告诉 Hermes**——同任务出两份自检报告 = 正常（先行版 + 收口版），不误判为重复。

## 铁律：指令里不出现任何 git 命令（2026-10-22 用户定）

给本地 agent（Cursor/Codex/反重力/WorkBuddy）的指令中，**禁止出现任何 git 命令**——包括 `git pull`、`git checkout`、`git status`、`git stash` 等所有读操作，不只是禁 `commit/push`。

- 需要让 agent 看到仓库最新内容时：**由用户先 pull**，agent 只读本地文件；不要写"先 git pull"。
- 需要它知道某处最新文本时：**把那段文本直接贴在指令里**（或让它照本地文件读），不要让 it 自己去同步仓库。
- 指令里关于 git 的表述只允许出现**禁止性红字**：「不 commit、不 push」。
- 自检：指令发出前 grep 一遍 `git `——出现任何 git 命令就是不合格指令。
- **例外：本地 IDE agent 在用户自己的仓库上干活时，提交与 push 归 agent，不要让用户换工具收尾（用户原话：「为什么要在 cursor 里 push，Qoder 也可以啊」）**。判据是「这台机器能不能推」：Cursor / Qoder / Codex 跑在用户自己的工作机上、远端可达，就让它在改完后 `git pull --rebase` → `commit` → `push` 一路做完，并要求回报 `git log -1 --stat` 与 `git status -sb`（应显示与 origin 齐平）。上面那条禁 git 的规则针对的是**公司内网受监控、要防留痕的抓取类任务**，别套到本地开发仓库上——套错的表现是让用户在两个工具之间搬最后一步，白耗一轮。push 被拒（非快进）让它先 `pull --rebase` 重试一次，仍失败就停下报错，禁止 `--force` / `reset`。

## 铁律：目录边界与破坏性操作（agent 越界删掉其他项目，实测）

**版本对账（材料版一致性，指令要求"在现有交付物上改"时先做）**：用户手上文件与仓库版本可能不同（本地删过页未同步）。做法：① 对应读法读出仓库版现状（页数/标题/md5）；② 与用户导出物核对；③ 用户提过「我删了几页」时，先 push 或确认两版一致再出指令——按旧版算的文本框号在删页版里全部错位向下平移。口头说「两版一致」也要先核对再放行。

**PPTX 删页的三件连带（指令一次给全，不靠 agent 自发）**：① 页脚分母全量重排（27→26）；② 全篇正文「见 Pxx」「(Px)」交叉引用按新页号重算，逐处列「旧→新→所在页」进自检报告；③ 删页连包内 OLE 嵌入对象一起连带删除，验收用 zip 内部件名清单核对。落点文档只写「删 P5 + 重排页脚」时 agent 会漏后面两件，验收才发现「见 P14」还是旧号。

给 agent 派「clone / 新建目录 / 初始化工程」类任务时，只写「只在 X 目录内操作」**不够**——它会顺手清理它认为无关的东西（实际发生：让它 clone 一个新仓库，它删掉了同盘其他几个项目目录）。

- 红线写死三条：**只在 `<目标目录>` 内新建与修改；禁止删除、移动、重命名、覆盖该目录以外的任何文件或目录；禁止执行任何清理类命令（rm -rf / 清空目录 / 批量删除）**。
- 要求它**在交付说明里列出本轮动过的路径清单**，父会话拿清单与预期比对——越界往往发生在没人要它汇报的地方。
- 恢复路径（先查再重建，别急着重做）：① 目标平台回收站与文件历史，逐目录确认有无整目录可还原；② git 项目一律从远端重新 clone——**给用户恢复命令前，先跑 `git remote -v` 逐个确认远端还在、拉得到**；③ 本地未 push 的改动：拿父会话侧镜像或远端最新 commit 做对照，判断差了什么再补，**不要直接重置目录**。
- 长期习惯：**「本地权威源 + 远端仓库 + 父会话镜像」三份对照是硬要求**——用户机器上的每个项目都要有可 clone 的远端；父会话侧保留镜像，专用于本地被误删/损坏时的比对与恢复。

## 验收：替换类交付与声称数字

**「全文统一改」与「某页不许动」的红线会撞车（实测）**：下「全文把所有 X 改成 Y」这类指令时，红线里若还写着「不许动某几页」，agent 会守红线只改其余部分，于是同一份材料里留下两个不同的值——它还会在交付里主动点出这个矛盾等你决定。正确顺序：先让 agent 扫出**全部命中位置列表**（页码 + 原文），逐条判断哪些改、哪些受保护，清单交用户拍板后再下发替换指令。反过来，只授权改某一处时，要主动让它把**同族表述**（同一个量的多种写法）一并扫一遍并在报告里报残留数，避免「改了一处、另两处还是旧值」。

**改单页/单节前先扫全篇：既查重复内容，也查入向引用（用户原话「下次要全盘考虑哈」）。** 用户点名「第 N 页/某节要改」时，不要只盯着那一页想替代方案——先拉一张全篇标题清单，然后两件事必做：① **看后面有没有页已经在讲同一件事**（做个新的很可能跟已有统计页/盘点页撞车，整轮白想）；② **数全篇有多少跨页引用指向它**（那决定改动会不会连带重排一大堆引用）。这两步没做就出指令，用户会先问「后面的统计有没有和这两页重复的」，然后你前面那轮构思全部作废。

**替换类交付（把 N 处占位/旧值换成新值）验收三步**：

1. `grep -c` 残留，并与指令里的目标条数对比——**数量不等就是没做完**，不要看它自报“已全部替换”。
2. 对每一处残留**能给出“为什么这处不能替换”的具体原因**（如该页没有原型所以无图可换、该处是历史记录行有意保留）。讲不出原因的残留 = 漏改，退回去改。
3. 交付前把残留逐条列给用户看，由他决定是补替换还是改写成写实说明（例：无原型可换的格子改写成“本期暂不提供原型”而不是继续留“待补”）。

- **占位符（待补/待定/TODO）清零要跨章节全量核，不按本轮批次数收口**：同一类占位符会散在本批次之外的另1章（那一章没有可供图的原型）——按已完成的批次数收口必漏（实测：以为 11 处全清，另一章还留着 3 处）。收口标准：全文 `grep -c` 归零；不能清零的每一处都要有具体缘由，并改写成写实说明（如“暂缺（缘由…随后补）”），不许留空格子。
- **图类交付三数一致（父会话自己数，不看它自报）**：引用版里 `![](./images/x.png)` 计数 = 发布版 `data:image/png;base64` 段数 = 图片目录实际张数；发布版残留相对引用与残留占位符都为 0。用户怀疑“怎么没生成 12 张”时，直接拿这三个数回答，不靠解释。

**自报“已删除 / 已移除 / 已对齐”必须回代码 grep 核实（2026-10-23 实测）**：agent 报告“某示例项已从侧栏移除”，而 menus.ts 里该项仍在（只是渲染被过滤或根本没改）——**删除类自报一律不信**，按它报的名字 grep 一遍确认代码里真的没了；不一致就当场报给用户（“它报告与代码对不上”），不要替它圆过去。

**「0 命中」的结论必须先跑阳性对照（编码敏感环境必做）**：`grep` 计 0 有两种可能——真没有，或检索链路失效（编码、大小写、文件范围）。做法：同一次检索里带一组**已知存在的对照词**（同语言、同文件范围），对照组有命中才证明链路有效；否则 0 是假阴性。PowerShell 读中文尤其容易整组归零，没有对照的「0 命中」不许当验收证据。

**多轮修复后必须做「声称 vs 落地」对账**：同一批活分几轮修时，逐条回原文核报告里标为已改的条目，**不接受报告自述**——前一轮报告说已改、后一轮可能又覆盖回去或根本没落地。审计报告与真正落地的差异，正是这类活最贵的产出。

**声称数字必须能复算（实测：agent 报“改了 280 处”，行级 diff 是 570 增 / 520 删，口径不明）**：

- 它的“改了 N 处”若没有可复算口径（按行？按改动点？），**不当验收依据，也不对外引用这个数字**；需要量化就用 `git show --stat` / `--numstat` 自己算一遍。
- 同一条纪律适用于“已全部找到/已全部挂载/0 遗留”：凡是数量结论，父会话都要拿可复算的侧面证据（配置数组长度、grep 计数、文件清单）核一遍。

**翻译/改写类交付的验收三件套（实测有效，比看自报可靠）**：让 agent 做“整篇翻译/中文化/改写措辞”时，自报永远说“已完成”，必须用三个机械指标核：

1. **英文词频前后对比**：`grep -oE "[A-Za-z]{4,}" <file> | wc -l`，改前改后各跑一次。降幅不明显 = 没真翻。剩余英文应基本只剩标识符、产品名、代码块内容——把剩下的高频词列一遍就能判断是“专有名词”还是“漏翻的句子”。
2. **围栏代码块 md5 对比**：把 ``` 围栏内的内容单独提出来算 md5（`awk '/^```/{f=!f;next} f' file | md5sum`），与改前版本比，必须完全一致。这是证明“代码块一个字符没动”的唯一硬证据，比让它自己声明可靠。
3. **行数**：翻译通常行数不变或微增（换行位置变了），行数大幅减少 = 删内容了，大幅增加 = 自己加了原文没有的说明。

同一套三件套也适用于任何“重构/去重/改写法”：行数对不上先问是不是删了东西，md5 对不上就是动了不该动的地方。

**agent 会把上一轮任务的报告当本轮交付重发（实测）**：给同一 agent 接连派两轮任务时，它可能把上一轮（尤其是同目录、同文件族）的完成报告原样再交一次，看起来像交差。判据两条：① 它报的行数/字数与**上一个提交**完全一致；② 本轮指令要求的三项输出（前后对照/词频统计/校验结果）一项都没有。命中即判“没做”，重发指令时把验收判据直接写进指令（“改后行数应与 N 不同，如果和 N 完全一样说明你没改”），比事后追问省一轮。

## 交付闭环：改文档/改产物必须一次整套交，不许手工收尾

用户两次点名（「那你干嘛要自己操作改prd，不让cursor成套出全部，你就这样指挥工作的？」「我要是不问你，这事情是不是就糊弄过去」）。交付标准是**一次改到位**，不是改到一半等追问：

1. **“改文档”包含四件：正文 + 截图 + 图片引用 + 发布版**。只改正文不重出图 = 旧图配新文字，图和文字打架；不重出发布版 = 用户拿到的是旧渲染。四件写进同一条指令的四个阶段。
2. **不要自己抢着改一段然后留尾巴**：自己改正文、图留给下一次，比不改更差——下一个人得先搞清哪里改过。要么派 agent 一次整套做完，要么自己一次整套做完。
3. **自检句**：交付前问自己“图跟文字一致吗？发布版重出了吗？”两个都否就是没交付完，不许丢给用户去发现。
4. **先加载对应 skill 再动手**（用户点名「为什么不用skill？」）：改 PRD 类活走 `prd-backfill` / `prd-doc-authoring`，它们的红线（忠实已实现、最小改动、发布版重生成）直接管到这类遗漏。

## Checkpoint 必须分阶段 + 停点 + 验收判据（2026-10-24 用户纠正：「checkpoint 下次不要这么写了，严谨点」）

禁写「两项都交，我一起看」「完成后发我」这类**无停止点**的松句——多步骤任务一路跑到底，中途跑偏没人拦，返工成本全落在用户身上。Checkpoint 的职责不是「让它交作业」，是「在正确的点让它停下来」。

固定三段写法：

1. **阶段划分与顺序**：写明「本指令分 N 个阶段，严格按顺序，每阶段结束必须停下等我确认，不许自行进入下一阶段」；
2. **每阶段交付物**：要它交什么、什么格式（文件清单 / 行号 / 前后对照 / 命令原始输出）；
3. **每阶段通过判据**：什么算完成、什么算不合格、不合格退回重做。

切分原则：按「可机器验证」与「需人判断」分层——机械类（改字号、重排页码、翻译、替换）先做，判据用 MD5 / 行数 / grep 计数即可；需要业务判断的（改叙述、补证据、处理矛盾数据）后做，判据是我方逐条核。阶段数控制在 2–3 个，超过 3 个说明这活该拆成多条指令。

结尾固定一句：**任何一步口径不明、数据缺失、或它想自行新增规则，停下问，不许自行决定。**（不写这句，agent 会自己挑一个看起来合理的做法往下走，然后错一整轮。）

## 交付节奏：Checkpoint 停下的回复 = 本轮的「继续」，不是新一轮

agent 在 Checkpoint 停下等确认时（自报里出现“未生成其余 N 项 / 未改 PRD / 等待确认”），我发出的内容是**这一轮的继续指令**——接着它停下的那一段往下走，措辞写成“继续 / 按下面接着做”，**不要框成“下一轮指令”**（实测：把继续内容写成“下一轮指令”，用户纠正“不对，cursor 还没跑完，还要继续，刚刚只是确认范围，等他跑完上一轮吧”）。判据：自报带“未完成/等待确认” = 本轮未结束 → 回继续；自报“已全部完成” → 才是新一轮。用户说“我 push 了”也要先分清是**本轮产物**还是**上一轮收尾**。

**修正顺序：会被后续文档引用的图，先对齐规范再出图。** 截图/整页图一旦被 PRD 引用，形态错了就要整轮重来（改原型 → 重截图 → 重替换引用 → 重新生成发布版）。所以 agent 交付“先做页面 + 锚点，等确认再出图”时，**放它出图之前先把形态口径核一遍**；用户说“用规范 X 来”时，先去仓库里找到那份规范文件（Demo PRD / 规范文档 / 项目方法论目录），把**出处 + 要点逐条**写进指令，不要自己描述形态——原型里已实现的形态与规范不一致时，先要求改形态再出图。

## 派工判据：远程桌面型 agent（无内置浏览器、无本机登录态）

对只有远程桌面、没有内置浏览器、拿不到本机登录态、网络也不在内网的 agent（如多机器人团队形态的 bot），派工判据三条缺一不可：

1. **输入可自包含**——给它文件或粘贴内容即可开工，不需要它自己去登录、点击、抓取；
2. **不依赖内网**——内网测试环境、内网 GitLab、内网接口一律不能派；
3. **输出可脱机验收**——产物是文档或代码，不依赖你亲眼看到它的屏幕。

**凡需要内网截图 / DOM 取证 / 读本机仓库的活，一律留给跑在用户机器上的 IDE agent。** 多机器人并行时按**产出物**切任务：每个 bot 一个自包含包（输入 + 输出格式 + 红线 + Checkpoint），**不要让 bot 之间有依赖、不要让两个 bot 写同一个文件**；成不成活靠产出物验收，不靠它自报。

**沙箱限制会卡死「让它去读」这类写法（实测）**：这类 bot 往往只能读某个固定盘（如只读 C 盘），它们**读不到用户的仓库路径**。此时**由父会话先给出«复制清单»**：逐份列出要复制的文件、它在仓库里的源路径、大小、以及**哪几个 bot 需要它**（复核型 bot 常要额外的对标/调研材料）——用户按清单把文件拷到 bot 可读的绝对路径（如 `C:\<输入目录>\`），指令里再写死这个绝对路径。清单只给「本次任务真正需要的几份」并注明「只读，不要修改」；材料总量不大时**整份给、不要拆文件**（在指令里限定「只处理第 N 节」即可）。多轮迭代后 bot 产物会变（合稿重新生成、文件位置变），要求它**报出产物在它侧的绝对路径**，避免用旧路径取件。

**迭代交付纪律（大文档多轮修改时）**：要求 bot **只报「改动过的节 + 每节改了哪类东西 + 改动处数量级」，不要重发全文**——全文回贴一次就是几万字符，搬运成本比改动本身高；父会话要全文时会让它发文件。验收时也看这三样：改动是否集中在声明的节里（没顺手改别处）、八节等固定结构是否仍在、声明“未动的部分”是否真的没动（抽一两条旧句在新版里比对）。

## Prompt delivery and execution guard

The instruction is for an external coding agent, not a document-generation task. For any code-change request, start with a direct execution sentence such as: “请直接修改代码，不要把本指令保存成 txt/md，也不要只输出计划。” Put the project path, task, and first action near the top. Keep the five-section structure, but do not let Output format, self-check, or deployment prose dominate the opening; otherwise Codex may interpret the whole prompt as a specification to save as a text file.

## Codex Harness 入口与个人 Agent 的边界

当用户讨论 OpenAI 开源 Codex Harness 时，先区分产品形态，不要把它描述成一个直接安装即可使用的独立 GUI：

- **Codex CLI / `codex exec`**：终端入口，适合一次性工程任务、CI 和后台作业；
- **Codex SDK**：Python/TypeScript 程序接口，用于在自有应用里创建、继续、恢复和流式运行 Codex 线程；
- **Codex app-server**：JSON-RPC Agent Runtime，适合嵌入已有业务界面，提供持久线程、事件流、中断、工具暴露和审批处理。

官方 GUI/IDE 产品是基于 Harness 的成品入口；开源仓库本身主要提供 CLI、SDK 和 app-server，不应直接承诺“安装后出现桌面 GUI”。

### 接入本地模型

Codex 可通过 `config.toml` 的自定义 OpenAI-compatible Provider 接入本地推理服务。官方配置形态包括：

```toml
model = "<local-model-name>"
model_provider = "local_ollama"

[model_providers.local_ollama]
name = "Ollama"
base_url = "http://localhost:11434/v1"
```

Rapid-MLX 等只要提供兼容 OpenAI API 的本地服务，也可以用同样方式接入。给用户的安装/接入建议按小步走：

```text
Mac 安装 Codex CLI
→ 配置本地 Provider
→ 先做只读/小范围代码任务
→ 验证工具调用、上下文和沙箱
→ 再考虑 SDK 或 app-server
```

不要一开始把 app-server 当普通桌面应用安装，也不要直接让本地模型执行长时间、高权限任务；先用小任务验证本地模型是否能稳定完成工具调用。

### 与个人 Agent 的分工

```text
个人 Agent：长期记忆、人格、用户关系、任务理解与编排
Codex Harness：Agent loop、工具、沙箱、审批、续跑与工程执行

```

## Format Rules

1. No emoji or icons. Plain text only.
2. Output as single ```plaintext block.
3. 红线禁止 must include "禁止 git commit 或 push".
4. Checkpoint must distinguish WHO does WHAT and WHERE.
5. VPS-side deployment only when user says "你部署下".
6. **git 指令铁律（2026-08-07 用户严厉纠正）：master 是收口分支，永远最后合并。** 给 agent 的任何 git 指令：
   - 禁止出现 `git push origin master` 直接推 master 的写法（除非用户单独明确要求）
   - "提交到 GitHub 并融合到 master"的指令必须写完整流程：开发分支（如 main/feat/*）commit → push 该分支 → 确认后 `git checkout master && git merge <分支> && git push origin master`
   - 指令发出前自查：有没有可能让 agent 直接 push master？有就重写
   - 误 push master 的回退：`git reset --hard <之前commit> && git push --force origin master`，然后开发分支 cherry-pick 重做，再走正常合并
   - 背景教训：写"提交到 GitHub 融合到 master"指令时漏了 main→merge→master 流程，直接写 `git push origin master`，导致 v156/v157 被误推 master，用户："你脑子坏了？？还带你这样的？"
   - **git 措辞精确性（2026-08-07 用户追问教训）**：汇报 git 动作必须分清 commit（本地）/ push（远端）/ 分支名。VPS /opt 是纯本地基线（无 remote），只能 commit 不能说"已 push GitHub"——用户连续追问"你 push 的是不是到 master？"。被问"提交/推送了什么"时，先跑 `git branch --show-current` + `git remote -v` 再答；说"提交"不含"已 push 到远端"。
   - **分支一致性（2026-08-07）**：VPS 本地基线分支名要与 Mac 开发分支对齐（都 main，`git branch -m master main` 改名保留历史），否则"我在 main 开发、你在 master 提交"永远汇合不了。独立初始化的本地仓库与 GitHub 仓库**无共同祖先**——直接 push 被拒（non-fast-forward）或 --force 覆盖远端历史（灾难）；本地基线代码类型不同（如 VPS 服务 .py vs 前端 React）时不要 push 进前端仓库，云端备份用独立仓库或 git bundle 打包。
6. UI 迭代若用户指定 Mac 本地截图验收，Checkpoint 默认写"本地启动→用户截图→等待下一轮"，禁止每轮打包、上传或 VPS 验证；用户随后明确授权部署时才切换到部署流程。
7. 部署后的审计要区分两类证据：浏览器截图/实际渲染用于视觉结论，源码或构建产物用于组件与路由结论。浏览器不可用时必须如实说明，不能把静态字符串检查包装成“已看过页面”。
7.5 **指令里引用截图/参考图必须文字化（2026-08-08 用户纠正）**：Codex/Cursor 看不到你贴的截图。写"参考格式（第二张图）"它不知道图是什么。凡是要对标某张参考图的效果，必须把交互流/格式/样式**逐项写成文字描述**放进指令（如"点击按钮→显示序号徽章→点徽章才看内容"），不允许写"按第二张图的样式"。参考效果若只有截图无源码，按文字描述的交互/结构/样式复刻，验收时用户拿截图对比。

7.6 **形态类改动要给「落在仓库里的参照图」+ 文字规则双保险（2026-10-22 实测）**：agent 读不到聊天里的图，但**能打开仓库里的图片文件**。所以改形态（列表筛选、面板、交互控件）时：①**产出一张形态参照图放进仓库**（用 HTML 画线框 → 浏览器截图 → 提交进项目 `images/`，命名如 `参考-<形态名>.png`），指令里给**仓库相对路径 + 一句"先打开看再动手"**；②同时把规则**逐条文字化**（控件类型、开合行为、生效提示、重置位置），图定形态、字定细节。只给图会被自由发挥，只给字会被理解偏（实测：给了规范章节号让它"按 §2.1–2.3 做"，它照样做成了另一种形态，重出两轮）。

7.7 **引用"某系统的某页面形态"属于无效参照（2026-10-22 用户质问"你让他参考的，是不是没有图？他能完成吗？"）**：写"参照内销 X 页的形态"而对方无图可看、也无截图可取时，它只能猜。要么补一张参照图（见 7.6），要么把该形态**逐条拆成文字**写进指令；**两者都做不到就不要下这条指令**——先跟用户确认参照物，宁可多问一句，也不要让它摸着黑做一轮。
8. **绝不打断正在跑的 Agent（2026-08-05 用户明确要求）**：Codex/Cursor 正在执行一轮任务时，发现漏项/要加需求 → **等它跑完再发第二轮完整指令**，不追加增量说明、不叫停重跑。用户原话"codex 不停，我怕出问题，我们等他跑完，给第二轮指令"。多轮迭代 = 串行队列：跑完一轮 → 部署验证 → 再发下一轮合并指令。
9. **同一实例的相关改动必须合并成一条指令（2026-08-11 用户纠正："两个指令合并一起，我还没跑第一个指令"）**：给 WorkBuddy/Codex 之前，把当前所有关联改动（如登录默认账号 + localStorage key 隔离 + Dexie 库名隔离 + 全项目残留检查）一次性写进同一条五段式指令，**不要分两条让用户跑两次**。发现新需求就并进待发指令，用户还没跑时就合并；用户已跑完一轮才发下一轮（规则 8）。指令里用"Request: 1/2/3/4 分步"表达多改动，Checkpoint 要求报告各步结果。
10. **增量追加指令（2026-08-23 model-rescue 实战验证）**：对**正在开发中/刚交付的项目**追加小改动（修 bug、加按钮、调逻辑），不需要重发完整五段式——发**增量指令**：Context 里写"给正在开发中的 <项目名> 追加 <功能/修复>，不要重建项目，在现有代码上增量添加"，并点名现有文件路径和**已知现状**（如"backend/main.py 里 VISION_MODEL_OPTIONS 有 3 处..."）；Request 只列本次新增/修改点，每点带"在 <文件> 的 <函数/位置> 做 X"；红线写"禁止改动 <本次范围> 以外的任何代码/文件/配置"；Checkpoint 逐条对应 Request 的验收。优点：Cursor/Codex 不会把项目推倒重来，用户复制成本低（一条小指令）。**节奏配合**：大需求拆阶段（基线→调研→规格→实现）+ 小改动用增量指令，避免"一条巨型指令"或"频繁打断"两个极端。
11. **交付物附提交备注，不替用户起提交标题；备注必须短（2026-08-26 定，2026-10-21 用户两次嫌长）**：用户本地用 Cursor/Antigravity 界面提交代码，**commit 标题（命名）他自己起**。我方交付（指令文件、审查结论、总结）末尾**附一段提交备注文本**（`feat(backend): 一句话改动范围` 风格，供他粘贴进提交框）；git 命令照常给出不受影响。不要强调"我给你起了提交标题"。**长度硬上限：一两行讲清干了什么即可**——不分节、不列多条 bullet、不写交付物清单（用户原话"提交备注这么长？？""太长了，后面提交备注不要这么长"）。详细交付说明放聊天正文，备注只留最短版。
12. **prompt/ 指令目录按时间线加序号，新增自动续号（2026-08-26 用户定，2026-08-28 补充）**：项目 prompt/ 目录的指令文件用 `NN-<名称>-指令.md` 前缀（01/02/...按执行时间线排序）。**每次新增指令文件自动续号（最大号+1）**，forge-scrm 现有 01~25（16最终审计修复/17推送删除规则/18二期收尾/19模板引用资料/20PRD对齐审计/21报告删除与卡片折叠/22推送前端优化/23推送取消删除与卡片全文/24折叠面板收起交互/25PRD对齐修复）。曾犯：从 16 号起丢序号被用户纠正（"我们之前规范好的指令要有序号，现在很乱"），事后批量 `git mv` 补齐（纯 rename 不改内容）。已发出但被后续指令吸收的旧指令要**删除并合并进新指令**（用户 2026-08-26 要求把"下拉展示修复"合并进"全模板化改造"后删掉独立文件；2026-08-28 Badge 角标独立指令同样并入最终修复指令后删除）——避免 Codex 收到两份重叠指令重复跑；合并时把旧指令的关键要求以细化条目写进新指令对应小节。

17. **deploy-all.sh cron 卡住不消费 incoming（2026-08-27 jarvis-voice 实测）**：zip 已上传但日志连报「有新包待部署」而 dist 不更新=管道卡死，不等第三次——手动跑单项部署脚本兜底（如 `bash /root/deploy-jarvis-voice.sh`，输出 "deployed" 即成功），再验 bundle hash/index.html 引用/内容特征三件套。
18. **同一天多轮修复的部署节奏（2026-08-27 forge-scrm 定案）**：用户明确"多个修复累积一次部署"时，逐个修复只 commit+push 到 main（含 prompt/ 指令存档），**不催部署**；累计批次完成后给出一份合并部署命令（git pull + deploy.sh）与完整收尾清单（✅ 逐项列出当天全部改动），由用户执行并贴部署输出后再验线上特征。避免每修一个小点就要求重新 build+部署烧额度。
19. **给用户的"手改服务器配置"命令必须自校验防占位符（2026-08-28 两次实翻车）**：让用户在 VPS 上改 .env/配置文件时，① 绝不在命令里写脱敏占位符（`UtfJy1...4` 这种会被用户原样复制执行——写进去的就是坏值）；② sed/单行替换极易翻车（替换成空/删行），**配置类操作给 nano 交互式步骤**（打开→粘贴三行→Ctrl+O/Ctrl+X→grep -c 验证行数），不再拼单行 sed；③ 命令设计成幂等（先 `grep -q` 判断已配置则跳过），防重复执行写重；④ 用户贴回输出后**必须核对关键值是否完整**（如 Secret 是否还是截断的占位符）再放行下一步。本次 SECRET 被写成 `UtfJy1...4`、又被 sed 删空，连续两轮返工。
19b. **VPS 环境变量配置的用户授权模式（2026-08-28 实测通过）**：用户授权"你去配置好了"时，Hermes 可直接 SSH 远端执行（`ssh -i /root/.ssh/id_ed25519_forge -p 2222 root@45.78.70.160`），用幂等写法（`grep -q KEY .env || printf '...' >> .env`）一次写入 + 重启服务 + journalctl 验证，避免让用户手敲多轮。凭据在会话中已出现过才可直写；写完必须 grep 验证行数并核对 Secret 完整性（不含占位符/截断）。
20. **验收驱动的设计纠偏（用户实测反馈即 PRD 变更）**：用户亲测发现交互设计问题（如"推送入口埋在长文最底部体验差""已推送的任务怎么还有删除按钮，别搞脏数据"）时，这是**验收级反馈**：① 立即盘点同模块所有同类问题（过时文案/误导字段/缺失反馈）打包成一次清理指令，不逐个挤牙膏；② 修复指令里把用户的业务理由写进 Context（"已推送记录=发送凭证必须保留"），防止 agent 按旧 PRD 复刻同样问题；③ 顺手 grep 全项目同类过时文案（`grep -rn "待实测\|暂不可用" frontend/src`）一次清零。
21. **PRD 对齐审计判定必须先查"最新拍板口径"，context 未回写的拍板不等于缺陷（2026-08-28 两次实翻车）**：审计"前端 vs PRD"差异时，凡判定为"缺口/偏差"的条目，先对照**最新的用户拍板记录**（审核流程变更说明.md、draft 待办、会话拍板）——用户口头/指令拍板但 context 未回写的口径（如"二期审核默认通过、审核入口隐藏"）会让 Agent 把**符合最新拍板的代码**误判为缺陷去"修复"（25 号指令 R2 让 Codex 放开成员审核，方向完全反了，被用户抓到后整份重写）。正确姿势：① 写审计指令时把已知拍板口径写进 Context（"审核入口隐藏是拍板行为非缺陷，audit D2 判定作废"）；② 拍板后的正式回写（如 context/04 R1/R3/R6/R8 改二期口径）作为修复项**明确授权改 context**（平时 context 只读，回写拍板口径是例外，需用户点头）；③ 修复轮 Codex 可能没收到 v2 重写版（用户手里还是 v1）——派发前确认用户喂的是最新指令版本，防止"旧口径代码跑完才发现方向反了"整轮作废（本会话实际发生）。

22. **给 Mac zsh 的命令块禁止含 `#`（2026-09-19 实测）**：Mac zsh 默认 `interactive_comments` 关，命令里的 `#`（含行尾注释）会被当参数——`git pull origin main # 注释` → 报 `couldn't find remote ref #`；`&&` 串行 + 行尾注释最易翻车（`parse error near ')'`）。给用户整段粘贴的 shell 命令块**不要放任何 `#`**，注释放代码块外；单行一条命令，并优先用 `ln -sfn` / `mkdir -p` 等幂等命令保证可重复跑不报错。

## 流程化标准：把一次性修法升级成可复用包（2026-10-24 用户铁律）

用户原话：「不要修修补补，然后下一次用的时候，还是走这个老路，要能复用」「这个活后面肯定都是要本地 agent 根据定义好的 skill 或者指令直接 sop 出来的，这不是业务需求，是可以被流程化控制做出的产物」。判据：**换个项目、换个 agent、换个人，不改规则也能跑出同样质量的结果**——做不到就不是 SOP，只是这次碰巧搞定。

1. **标准的唯一真源是校验器，不是文档**。文档会被跳过（没人从头读一遍），发版门禁跳不过。所有能机器判的规则全部写进校验脚本，进发版前置；文档只保留判不了的（边界判断、切块原则），并且从属于校验器（是它的说明书，不是另一套规则）。
2. **见一个雷头修一个 = 人肉门禁，不算 SOP**。上线点到问题才反手修，说明门禁层缺这道口子。每修一个线上问题必须当场回答「这条规则进校验器了吗」——没进就等于下次还会犯；只补文档不算。
3. **可复用包四件，缺一件就会回到老路**：① 契约（一页纸，写清边界/切分原则/产物形态，**不含任何项目细节**）；② 样板块（一个填好的完整样例，作者照拄结构——比读二十条规则准）；③ 校验器（判据全部可执行，报错指到具体哪项）；④ 参数化指令模板（换项目只填 2–3 个参数：项目路径、套件目录、范围清单）。
4. **分工：判断归我，产出归 agent**。我定规格、定判据清单、定流程步骤与每步验收判据；agent 负责写契约文档、写校验器代码、写模板、拿它量修存量内容；我只做独立核验。例外只有一类：线上已坏需要立刻止血——那种情况可以自己动手，但事后必须由 agent 补正式实现并进校验器，不能停在手工修好的状态。
5. **清单类任务先盘点后动手**：盘点（“该有哪些”）是独立一步，产出交人拍板，**不许 agent 直接开写**。跳过盘点直接执行，它必然按自己的粗粒度聚合回去，返工成本远大于多停一轮。

**自报「已修复」与用户实测不符时，下一轮指令要运行时证据，不再收自检表**：agent 的自检表（自查项全打勾）可以和用户实测完全相左——自测路由/环境不同。发现第一次不符时，下一轮指令必须包括「先诊断再修」：交回真实判断代码片段 + 目标路由下 console 实际取值输出，然后才谈修复方案。连续两轮不符即停收自检表，一切以运行时证据为准。同时，本地 agent 完成后不 push 是常态——父会话读不到代码时，所有判断只能靠截图与汇报，验收成本显著升高；多轮任务在验收通过后主动提醒用户让 agent push 一次，恢复「父会话能读代码核验收」的基线。

## 验收确认过的改动必须当场写进待发指令（编排层漏项铁律，2026-10-27 用户连环抓出两处）

用户拍板/确认过的口径（如「四条一句话无标点」「0625 参考做三处吸收」）如果只放在聊天回复里等时机成熟再发，**下一轮新指令时大概率漏掉**——执行层完全收不到，用户翻一轮交付才发现「我说过的两件事都没做」。规矩：

1. 用户拍板任何会改产物的口径时，**当场把该条目写进当前待发（或下一轮）指令的 Request 草稿**——不落在聊天回复就落进一个固定的「待发指令池」段落（可存看板或草稿文件），下一轮发指令前先扫池子。
2. 发指令前自查两问：① 上一轮验收里用户点头/拍了板的每一条，指令里都有对应 Request 条目吗？② 用户提过的参考材料要吸收的点，都进了 Context 或 Request 吗？——两个答案不全是 yes 就不许发。
3. 用户被问到「怎么没做」时，根因先设为**编排层漏项**（我/父会话没传达），其次才是执行层没做——先对账完成过什么再判断。

## Long-Goal Cost Discipline (Codex / Sol)当上游按请求次数、最低消费或重复上下文计费时，Sol 应采用“长目标、少轮次、完整闭环”：

1. 第一轮只读审计，一次摸清代码、PRD、数据层、参照项目和业务边界。
2. 第二轮实现指令一次给全 Context、范围、业务规则、红线、回归清单和 build 验证。
3. 允许 Codex 在单次任务内持续读取、修改、自查、构建；不要把一个模块拆成按钮、字段、间距等多个碎请求。
4. 用户集中截图验收后，把多个问题合并为一轮返修。
5. 成本评估记录任务前后余额、耗时、首轮完成度和返工次数；不要用反复询问模型身份等空跑测试。

## Common Patterns

### 内网系统只读抓取指令（`@Browser` 格式，2026-10 实测）

用户公司内网系统（在线表格 / 知识库 / VAPD）Hermes 进不去，只能由他机器上的 Cursor 内置浏览器抓。沿用五段式，但有五个固定写法：

1. **首行只写 `@Browser <完整URL>`**（链接**交付时写占位符** `<在此粘贴已打开的目标链接>`，用户在 Claude 侧复制粘贴后自己填——不要写死内网/测试环境地址，也不要让他从聊天里另找），Context 里再说一句"该链接已在 Cursor 内置浏览器中打开（已登录内网）"。URL 全文只在 `@Browser` 后和「数据来源」各出现一次——写成三处会被理解成三个不同来源。
2. **保留 URL 里的 `?sheetIndex=N`**：那是目标工作表编号，删掉它 agent 会去遍历所有页签（其他产品线的表全被拖进来）。要限定范围就在 Request 写"只处理当前这张工作表（sheetIndex=N），其他页签只列名称不点开"。
3. **先读表头、再读数据的顺序**（最重要）：不要让 agent 按你预设的列名去抓。第一步要求它把**实际表头原样抄下**（多层合并表头记成「上层-下层」），写出实际列数，并与你手里的历史列结构逐条比对差异；第二步才"按第一步确认的实际表头"逐行取值。预设列名 = 漏列（曾按 13 列写指令，实际表头 19 列，漏掉 6 列）。
4. **给数量基准做交叉校验**：告诉它历史上有多少行/多少条非空记录、数据行范围，让它回报本次抓到多少行、和基准一致不一致、不一致要说明原因。仅一句"全量抓"无法发现翻页漏抓。
5. **红线必须显式禁 git**：写"不得执行任何 git 操作（add/commit/push 一律禁止）"。只写"不改动项目文件"挡不住它顺手 commit——用户在受监控的公司网络里推个人仓库，这是硬要求。

**大表不要指望贴回聊天**：飞书收不到文件，全量 18 列带长文本的 TSV 几万字符贴不进来。Checkpoint 分两段要：① 只读 agent 把**完整表写进项目本地文件**（不 git）；② 聊天里只贴一份**精简清单**（行号 + 名称 + 状态 + 版本 + 链接 + 摘要前 60 字），Hermes 用精简版对账和重建，完整版留在用户机器上备查。

**要先想清楚这次是要「写文件」还是「只贴聊天」，并把后果提前告诉用户**：两种形态用户侧的体感完全不同，不交代就会以为指令出错。

| 指令写法 | 用户本地 | 谁 push | 适用 |
|---|---|---|---|
| 写进项目目录（不 git） | 跑完会多出新文件 | 用户自己 commit + push | 产物要长期留在仓库、内容不大 |
| 不写文件、只贴聊天 | **跑完本地什么都没多** | 不需要任何人 push；Hermes 直接从聊天内容落盘并 push | 防公司监控（公司网络里零 push 记录）、或只是拿数看一眼 |

写「不写文件、只贴聊天」时，**交付说明里必须加一句"所以跑完你本地不会出现新文件，结果直接在聊天里；落盘我来做"**——否则他会在跑完后问"我本地怎么没有新文件让我 push，是指令有问题吗"。此时**不要让他去 push**：由 Hermes 把内容写进 VPS 侧仓库并 push，公司侧只读不推。

**抓在线表格的技术路径**：走 WPS `WPSOpenApi` / `EtApplication` 读 `Range().Value` 一次取整个区域，比 DOM / 无障碍树 snapshot 可靠得多（无障碍树常常根本呈现不出表格内容）。指令里不需要指定实现，但回报里让它写明抓取方式，便于判断是否有分页截断。

**新旧导出对账用业务单号做唯一键**：比对两份需求/工单清单时，先从内容里正则抽业务单号（如 `VR[0-9]{6}-[0-9]{3}`）做集合 diff，**不要按文件名或标题匹配**——同一需求的标题在多版导出里措辞、空格、前缀都不同，按名称比会误报几十条"新增"。父单号被拆成子需求时父单号会"消失"，属正常拆分不是丢失。

### 本地 agent 看得到、我看不到的源码：用"只读比对出差异清单"当第一轮指令

当编码 agent 能访问一份我看不到的权威源码（生产前端源码、客户内部工程），不要让它直接改代码——第一轮必须是**只读比对产差异清单**，并且指令里写死三条：

1. **证据格式**：每条差异必须给“权威源码 文件:行号 + 摘录”与“现有实现 文件:行号 + 摘录”，两列并排；**拿不出行号的条目退回重做**。
2. **单独一节的“源码里找不到”清单**：现有实现里有、权威源码找不到出处的，逐条列出——这些就是当初被“补齐”出来的假货，是清单里最值钱的部分。
3. **禁止反推**：不许用现有实现去反推权威端长什么样，找不到就写“未找到”或“需人工确认”，不许脑补、不许用截图猜。

配套的改造轮次纪律：**一次只改一个页面/区块**，改完 build + 本地预览 + 与权威端**并排截图**，停下等确认；续轮只做下一块。红线固定四条：只读那份权威源码（不改不 git 不外传）、不动本轮范围外页面、命名/字段/控件/顺序一律照权威源码不许自由发挥、**删掉的东西先注释保留不要物理删除**。

**验收必须回代码**：截图只验外观，命名/字段/条件结构要用户 push 后自己 pull 读代码核——只拿 agent 的自报当真会被用户当场退（"不合格"）。另外，agent 自报的“留项”里，凡本期需求要用的（条件结构、筛选项）当场驳回，不算留项。

**指令要同时写“不许写哪里”和“产物最终落在哪里”**：只给范围红线（如“本轮只许写 A 目录”）时，agent 会把产物丢在它自己选的地方（实测：产物被放进 `原型/audit-deliverables/`，而规范位置是 `08-相关资料/产品审计/…/`）——下一轮还得专门发一条“归位”指令。写指令时把**产出路径写进 Output format**（逐项给绝对/仓库相对路径），红线只用来防越界，不用来代替指定产物位置。

**并排对比图的验收标准**：必须左=权威端、右=复刻端，**同一区块、同一交互态**，各自独立截图后脚本拼接；拿一张整体图当另几组图的左半 = 没做（agent 会这样凑，并自称“仅结构参考”）。做不到同态的（如只读不允许触发某个动作）就在文件名/图内标注“仅结构参考”，不要当成验收依据。

- **用「字段映射表 + 逐条渲染规则」代替叙述性字段描述（1028 好友列表三轮返工实测）**：给 agent 派「列表/弹窗/抽屉分配字段」类活时，靠自然语言理解字段归属（哪个字段进列表第N列/进抽屉哪分组）、枚举取值、空值写法会反复错（自造聚合列、漏字段、字段改名、列表与抽屉重复展示）。治本做法：① 先把字段表写成 **TSV 文件提交进仓库**（列：序号/属性分类/字段名/列表列序/抽屉分组/枚举或格式/空值表现/使用说明），指令里把这份 TSV 标为「唯一事实源」，字段名/位置/枚举全从 TSV 机械取，冲突时以 TSV 为准；② 把易分歧的隐含契约写成机械判据：每个字段唯一归属互斥不重复、逐条列「列表不得出现哪些字段名」、不许自造聚合列、聚合类指标（按导购聚合的好友数）同批行同值且不等于列表条数；③ 交付必须带「字段核对表」逐行对回 TSV，一行不少；④ 严禁写「抽屉是完整档案」这类自由度大的规则——归属规则必须互斥、逐字、可 grep 验收。

- **上下文信任门（1028 实测）**：用户说「我 push 了」→ 先在 VPS `git pull --rebase` 实锤（看远端最新提交号与目标文件是否存在），**不存在就直说没拉到 + 问他提交的仓库/分支**，不要顺着话说「看到了」。用户以为自己 push 了但实际推到别的仓库/分支或还没 commit 是常态；凭空说「看到了」后面全盘判断都在替不存在的产物背书。

- **验收先扫空文件**：agent 会把 0 字节截图写进证据链并让 md 引用它 → 证据链静默断裂。验收第一步跑 `find <证据目录> -type f -size 0`（以及核对 md 里引用的每个文件名是否真实存在且非空），发现空文件当场退回重截，不接受“文件在就算交付”。

**同批截图还要互比 md5（0 字节之外的第二种静默坏图）**：agent 重截时会把 A 场景的图顺手写进 B 场景的文件名——实测重截邮件渠道截图时覆盖了"生产整体"那张，两张 `md5sum` 完全相同，于是并排图左半是邮件、右半是 WhatsApp，拿两种渠道比，整张图作废。验收时对**同批、同用途但不同渠道/不同场景**的图跑一次 `md5sum`，出现相同值就退回重截，并要求文件名带上渠道/场景标识（如 `受众筛选-生产-WHATSAPP-整体.png`）；重截后让 agent 在交付说明里报两张图的 md5（必须不同）。

**枚举值 ≠ 展示文案**（比对两版界面时最容易漏）：源码里 `EMAIL` / `SMS` / `SMART_SMS` 是值，界面要显示中文文案（邮件 / 短信 / 富媒体短信）；按钮文案（`确定` vs `提交`）、弹窗标题也逐字比。从源码抄枚举一律取 label/文案字段，并让它**全站扫同类问题**（筛选项、列表列、状态列、类型/推送方式）。

### 只读对齐审计指令：三态逐条 + 四类清单 + 报告落盘 + 聊天只回一屏数

派「原型/代码是否忠实承载 PRD」这类审计时，骨架固定，换项目只换真源清单：

1. **执行者必须是没参与本轮实现的新会话**，指令里写明「不许沿用任何对话记忆，结论只以仓库现行文件为依据」——同一会话审自己刚写的东西等于自证，什么都审不出来。
2. **真源按权威度排序列出且带路径**：功能清单（本期范围）> 业务 PRD > Demo > 字段清单 TSV（字段唯一事实源）> 评审 PRD（仅交叉参考，权威度最低）。权威度不排序，agent 会拿最弱的当依据。
3. **逐条三态**：一致 / 不一致 / 未覆盖，条数必须等于功能清单条数，每条强制带「相对路径:行号」，显式禁「基本一致」「大致符合」这类无证据结论并写明命中即退回；再显式禁「未涉及」「合并处理」。
4. **四类专项清单各自成节**：A 原型有而 PRD 与线上都没有的自创项（逐页扫，最值钱，且要求空表时附已扫页面清单）；B PRD 有原型没有，并区分「确定没做」与「口径未定所以没落地」；C 字段级偏差——原型列/字段逐项对 TSV，TSV 有原型没有=漏做、原型有 TSV 没有=自造，并报「原型列数 vs TSV 应有列数」两个数；D 无法判定项（缺什么证据、需要谁确认）。
5. **报告写文件、聊天只回一屏摘要**：报告落**目标仓库自己规定的报告目录**（唯一允许写入的文件）——写指令前先读该仓库 `AGENTS.md` 的报告归档约定，按它写路径；仓库没写才用默认。已知两种：cms-project 用 `08-相关资料/审计报告/` 且**明令禁止根目录新建 check-reports/**；forge 系用 `check-reports/`。把 forge 的路径套到 cms-project 上会让 agent 当场弹确认卡停下（2026-10-30 复发两次，Codex 与 Qoder 各报一次）。摘要必须带可核的数（三态分布、A/B/C 各几条）+ 前几位不一致项。给视障用户回贴长报告等于没交付。
6. **红线固定几条**：只读（唯一可写是报告文件）；不 build、不跑 dev server、不截图；不做任何 git 操作；不联网登录系统取证，要线上证据处一律写「仓库内无依据，需人工确认」——不写这条它会拿行业常识或别的站的材料补空缺；禁止用截图/OCR 认字段名；禁止把「我没找到」写成「没有实现」，必须写「未定位到 + 已搜关键词与目录」，把不确定性交回来。
7. **禁止读带 `-发布版.md` 的文档**：发布版把截图 base64 内联，一行几万字符，读进来直接撑爆上下文；核对只用不带「发布版」的那份。
8. **审计与修复切成两条指令**：阶段一只交审计并停下；修复另起一条。塞进一轮，agent 会边审边改，审完的结论已经失效。
9. **A 类「自创项」不许直接进删除清单**：审计者看不到线上，它只能证明「仓库真源里找不到依据」，**不能证明「线上没有」**。修复指令之前必须逐条裁决：能回线上取证（有登录态的 agent）的先取证，回不去的交用户拍板。实测一次审计给出几十条自创项，其中预估人数按钮、导出异步任务抽屉、系统固定条件行、默认预置条件全是线上真实形态——照单删就是把线上正确形态删掉，用户会当场指出「这个是默认值，不允许删除」。
10. **修复指令必须带「保留不动」清单**：把裁决为保留的项（线上形态、本期不做但仍显示的控件、系统固定条件）逐条写进 Context 的已定口径段，并写明「不许再反问、不许改」。只写「删哪些」不写「留哪些」，agent 会按「精简」的本能顺手一起删。**系统固定条件类**（不可删、不参与新条件组逻辑、圈人时由系统自动叠加）要单独点名：它不并入本期新枚举与新组合逻辑，形态照线上原样保留。

11. **修改/删除类指令必须给「改前代码原文 + 改后目标代码原文 + 机械判据」，不给行号范围**：写「约在第 249-259 行」「其余保持现状不动」这类模糊定位与软出口，agent 一条都不会动——模糊范围可解释成「已在范围内」，保留项又给了它不做的理由。实测一轮增补指令下去，那个按钮原封不动。固定三件套：① 贴出改前那段代码与改后目标代码（逐字，让它替换而不是理解）；② 给 grep 判据（改完后某字面量只应剩 N 处、应为 0 的写 0）与 build 判据；③ 要求交 git diff 前后各 5 行。验收按这三件收，不看「已删除」「已按您要求处理」这类自报。**首句就写「替换上一条增补指令里的 R-N，以本条为准」**，否则它会按上一条的软措辞执行。

### 原型为准的对齐审计：五部分骨架 + 「报告自述不是落地证据」

当权威关系反过来（原型已定稿、文档来追），而且文档已经过好几轮 agent 改动之后，审计骨架换成五部分，不要沿用上面那套「PRD 为准」的三态骨架：

1. **报告声称 vs 实际落地**：把 N 份改动报告里标为「已改」的条目逐条抽出来，回文件原文核，判三态——确实已改 / 声称改了但没改 / 改了但与已拍板口径不符。
2. **文档 vs 原型一致性**：按功能清单逐条判「一致 / 文档没跟上原型 / 文档写得比原型多」。第三类往往占大头，它比漏做更危险——文档承诺了原型没有的能力，评审照文档问就答不上。
3. **新造口径识别**：文档里出现、但原型与功能清单都找不到依据的规则句、限制条件、枚举、默认值，逐条列出。**每轮文档回写都会长出几条**（典型：「同一租户内名称不重名」「标签最多显示 2 个超出 +N」「失败可重试」），这是最该抓的一类。
4. **跨文档矛盾**：同一件事在不同文档里写法不一致的，列各处原文与行号，指出哪一份与原型一致。
5. **原型 vs 已拍板口径冲突**：只列不判，交用户裁决（改原型还是改口径）。

三条铁律：

- **agent 的报告自述不能当落地证据**，一律回文件原文核。多轮报告叠加时尤其致命：同一条口径被后一轮覆盖掉，前一轮报告仍写着「已改」。
- **回写不要拆成多轮**：把「回写 → 旧口径清理 → 口径修正」拆开做，每拆一轮就重新摸底一次、报告再叠一层，口径越修越散——一轮把条目、矛盾、自造项一起清。
- 审计输出的摘要只回**五个数**（声称条目总数与其中没落地数、文档三态分布、可疑新口径数、矛盾处数、原型冲突处数）+ 最要紧的 5 条各一行；给视障用户回贴长报告等于没交付。
- **报告目录要定期治噪，不然一天就几十份**：回写/清理/修正这类**过程报告用完即删**（结论已经回写进文档了，报告本身不再有信息量），只留独立审计与取证证据；往期结论归到 `历史/<年-月>/` 子目录并按日期命名。git 有历史可回溯，删过程报告不丢东西。治噪前把「删哪些、留哪些」列成清单交用户拍板，删完在根目录写一份归档说明。
- **报告目录不是回收站，也不是证据库**：一份报告只该存在两种状态——还在支撑当前结论（那就留着并让后续审计引用它），或已经被实成写进交付物（那就删）。夹在中间的“我写过”没有保留价值。

### 判断“现有机制能不能扩展”：要机制级证据档，不是差异清单

当本期要新增的能力需要**接进生产已有机制**（如一种新的圈人条件类型接进现有条件模型）时，让 agent 出的不是页面差异表，而是**四节证据档**：

1. **机制事实**：这条链路上现有的枚举 / 参数校验 / 解析器 / 接口分别是什么（文件:行号 + 原文），调用顺序怎么走。
2. **扩展点**：哪些地方是“只认固定取值”的硬编码（枚举白名单、SQL 生成器、字段校验），新增类型要动哪几处。
3. **静默失败点**：只改上层数据、不改下层解析器会怎样。实测：圈选/预估链路的解析器会**移除非白名单的条件类型**——前端塞进去的新条件类型被后端悄悄丢掉，页面不报错但人数算错。这类“不报错但结果错”的路径必须专门写出来。
4. **未确认项**：读源码读不出的（如名字暗示“历史上支持过、后来被移除”的方法），列出来给开发确认——这类残留方法的答案往往直接决定工作量。

铁律：**“能不能做”要答成“要扩哪几处”**——“可以做”三个字对排期没用。证据档全程标注**事实 / 推断**，推断必须写“推断”二字，查不到写“未在源码中找到”，不许拿看起来合理的设计补空缺；源码里不存在的模块（本期要新建的能力）一律按“本期新增”表述，不要让 agent 去找一个不存在的实现。

### 需求分析档指令模板

给本地 agent 写“对 N 条需求做可交付分析档”这类指令时，逐条固定七段（原文摘要 / 场景与价值 / 现状核查带源码行号 / MVP 实现方案分端 / 前置依赖 / 优先级与理由 / 待确认项），要点与坑见 `references/requirements-analysis-instruction-template.md`——**该文件同时写了多 bot 并行拆法（按产出物切、附文件清单、无源码权的 bot 立“不许编造实现”规矩）、复核岗（找问题不写方案）的六类问题清单，以及复核结果的分层处置（结构性前提回写权威源、机械可修父会话自己改、已处理的告诉对方不用补）**。

**回答 agent 的 Checkpoint 提问 = 一条可粘贴的口径回复，不是一段分析**：本地 agent 交付时反问的“口径点”（是否同意某顺序 / 是否允许拆分 / 是否接受沿用旧评估）要**逐条编号答复、整段放一个 plaintext 代码块**，用户是直接复制回给 agent 的——把"我建议…因为…"的论证留在聊天正文（或干脆先给用户看），代码块里只放结论式指令（含"补一句 X""不接受 Y，要求 Z"这类可执行要求）。**用户先拍板再由我转成口径**：产品决策（先做哪条、能不能拆、要不要跟标杆）由用户定，我只给一句话建议；我负责把拍板结果翻译成 agent 能照做的条目，并写清"确认后继续哪一段"。

**agent 的「待确认」必须一次答完并显式收口（否则永远收不了尾）**：本地 agent 每轮交付都长出一批新的待确认项，逐条答完下轮又冒新的，用户会直接说「这样没完没了」。答复里除了逐条结论，必带两句收口：① 「**回完即收口，不要再提新的待确认项**」；② 「**其余一律保持现状不动**」——不写第二句，它会为“看起来不完整”的地方自行补一条。已答过的条目不再重开；确实只能是外部答复的（等别人回），写成备注式挂账，不阻塞本轮。

**派活前先溯源：文档里“看起来像定稿”的句子不等于用户迟到拍过的口径**：把某条写进指令 Context 当作依据前，先分清它来自哪——① 用户当场说过/拍板；② 线上真实形态；③ 只是某轮文档里写成那样。第③类拿它派活就是把自己的笔误当权威执行（实测：PRD 重做时把入口写成“权限中心”，后来据此派活真去挖了菜单，评审现场菜单当场消失，用户当场问责“我什么时候约束过”）。做法：写进指令前跑一遍 `git log -S "<那句话>" -- <文件>` 看它哪次进来，没有用户拍板记录就不当依据，先问一句。

**父会话手里的代码镜像可能落后于用户本地，不要拿它判“现状”**：agent 在用户机器上改、没 push 时，VPS/父会话读到的永远是旧版——据此说“这个没改/改好了”必错。规矩：① 派活前不拿镜像断言代码现状；② 用户说“我 push 了”就 `git pull` 实锤到具体提交再下结论；③ 代码变动频繁的时期，Hermes 只负责口径与文档，核验统一排到 push 之后。

**验收对方的"已落实口径"要逐条对回原要求**：agent 回"口径已落实"时，逐条核对它是否真的改了（如要求"相关内容必须标证据等级"→ 检查那一列是否真存在、是否留空），并单独看"未在源码中找到/这条我没做"那节——**那节才是它真正没能力的部分**，不许拿它的自报总结当验收结论。

**对方报“文档与实现对不上”时，先判文档是不是过期（不要让它自己挑挂点）**：这类冲突（"PRD 写 X，页面里没有 X"）大多数不是实现缺了，而是文档残留了旧结构或被推翻的口径（典型：分步向导时代的"进入下一步"、已被实调推翻的"此阶段不做 X"）。裁决顺序固定：

1. 先判文档那一条是否过期；过期 → **父会话改文档那一条**，把修正后的文本原样贴给对方并说明"文档已改，按新文本执行"；
2. 不过期 → 由父会话给出明确裁决并写明挂点（如"这个角标挂在页脚操作区"）；
3. **绝不为让对方过 Checkpoint 而临时放宽标准，也不要让它自己判断**——它判断不了业务口径，只会挑一个看起来合理的挂点，然后错一页。

**验收截图/角标类交付先数数量**：配置里"来源"与"产物"两个数组的条数必须等于文档里的目标行数；再抽查组件 diff 是否只含锚点/属性新增（diff 里"删一行又加回带锚点的同一行"属正常）。数量对不上就不进入下一轮。

### 前端重构/换组件库指令：必须列"保留层"（2026-08-14 CRM Shadcn 重构实测）

**用户明确拒绝"复制项目再重构"**（"我不想再做一次项目的备份，之前我们做个 CRM 客户自动同步到 ERP 的操作的"）——集成逻辑（erpSync.ts/Dexie schema/路由结构）是宝贵资产，复制一份=集成要重做。**直接在现有仓库重构 + git commit 打基线**（commit 就是备份，可回滚，不用物理复制）。

**重构指令必须显式列出保留层 vs 换掉层**（不列反重力会全重写）：
```plaintext

- 保留 src/api/erpSync.ts（CRM→ERP 客户自动同步集成——绝对不能动/删/重写）
```

**⚠️ 重构后注入式功能会失效（标注 runtime 实测）**：annotation-kit 这类由 `index.html` 动态注入 `<script>` 的标注 runtime，依赖页面 DOM 上的**锚点属性**（如 `data-anno`）定位标注目标——反重力重构页面时**丢了全部 data-anno 锚点** → runtime 能加载（按钮在、bundle 数据在）但**找不到目标 → 点击无效果/面板不渲染**。症状特征：按钮存在 + annotation-kit 文件都在 + console 无报错 + 但面板不渲染。**预防**：重构/换组件库指令的红线加"保留页面 DOM 锚点属性（data-anno/data-testid 等）"；验收时点一次标注按钮验证注入功能，不只是看页面渲染。修复路径：恢复锚点属性（git 旧版 diff 出缺失的 data-anno）→ rebuild 部署。

### 小功能新增："只新增这两段"最小侵入框定（防反gravity乱跑，2026-09 标签删除实测通过）

给 scope-prone 的 agent（反gravity/Gemini）派**小功能新增**（加删除按钮/加字段/加单个接口）时，别只描述改动——把整份指令框成**纯增量**，并自己先摸清全部范围再写：

1. **出指令前先自己摸清（agent 的活变成了纯机械插入）**：grep 后端路由表确认缺哪个端点、读模型确认约束（如 FK `ondelete=CASCADE` → 删标签自动解除关联，不用写拦截逻辑/迁移）、照抄现有惯例（删除端点 = `OkResult + not_found + 权限依赖` 样式、前端删除列 = `Popconfirm + http.delete` 先例）。把这些"已核实事实"写进 Context，并明说"已帮你摸清，按下面给的改，不要自己再去翻别的地方"——agent 说"让我自己翻一遍"或补翻别处都是浪费。
2. **给出可原样粘贴的两段完整代码 + 精确插入点**：后端 `在 <函数> 之后原样插入下面这个函数（一字不改）`；前端 `在 <columns 数组> 末尾加这个对象`。缺的 import 逐项列出"只补这 N 个"，并注明"不要重排 import 顺序"。
3. **红线收死（多条）**："只允许新增上面两段，禁止改动/删除/重排/重写/格式化文件里任何已有行；禁止动 import 区（缺的按所列补）；禁止新增权限枚举/改 functional_permissions/数据库迁移；禁止新建项目/目录/文件；禁止 git add/commit/push".
4. **Output 要真实证据，禁空口**："必须贴 git diff（应只两处新增）+ build 通过 + E2E 结果，禁止报'完成/无风险/0 遗留风险'之类空话"。scope-prone 的 agent 若拿自报完成照收，下一步就是把整仓改乱。

已实测（两次）：反gravity 按此框定，交付了**干净的两处新增**（git status 只两文件、E2E 创建 200/删除 200/再删 404）+ git diff + npm build 全过，零越界——证明"最小侵入框定 + 喂已摸清事实 + 要真实 diff 证据"能压住它的乱跑倾向。

### 前后端接口契约：给前端指令前必须核对后端路由表（2026-08-25 用户严厉批评）

**接口契约 = 后端定义（权威），前端适配调用——"后面端缺失就让前端用静态数据兜底"是错误规范，用户原话："凭什么前端开发不用管后端接口了，这个规范是最基本的吧"。** 曾犯：给 Cursor 的方向联动指令写"没有接口就用前端静态数据 + 标注待后端接口"，Cursor 照做 → 前端调 `/directions/*` 后端没有 → 页面内 404 toast（`/topics/generate` 打开报 "Not Found"，不是路由 404 而是页面内 API 请求 404）。用户质询时才发现：后端（Opus 早期搭的）路由表根本没有 directions 接口，前端按 PRD 做了、后端没跟上——**前后端开发不同步，而我在出指令前没核对后端路由表，还亲手给了"静态数据兜底"这条偷懒合法路径**。

铁律：
1. **给任何前端/agent 指令前，先核对后端路由表**（`grep -rn "@router." backend/app/routers/`），确认前端要调的接口后端都有；缺失 = 指令里写"该模块后端接口未实现，**任务 blocked**，先补后端（列接口清单）再让前端适配"，**绝不允许"静态数据先顶着"假装完成**
2. **页面内 404 的排查法**：页面能打开但弹 "Not Found" toast = 某个 API 请求 404 → 读前端页面源码找 `http.get/post` 路径 → 与后端路由表对比，缺失即根因；不是前端路由问题也不是 nginx 问题
3. PRD 已确认的模块（如业务方向"即建即用"）后端必须同步实现——前后端派工不同步时，**编排者（Hermes）负责在对齐前把缺口暴露出来**，而不是让前端先做半成品

**✅ 正确范本：方案 B（后端补齐接口使前后端一致，2026-08-25 directions 实测通过）**：前端已按 PRD 实现（Cursor 交付）、后端缺接口时，给后端 agent 的补齐指令五要素：
1. **先从前端源码提取完整接口协议**：`grep -nE "http\.(get|post)"` 前端页面 → 列出每个 URL + 请求 body 字段 + 响应字段（如 `GET /api/directions` 返回 `{business_directions, specialties}`、`POST /api/directions/business` body `{name}`——字段名必须与前端类型定义严格一致，`grep` 前端 `interface` 拿字段）
2. **PRD 表定义引用**：字段清单/主PRD 里表的字段、类型、唯一约束（如 `(business_direction_id, name)` 联合唯一），照抄进指令
3. **后端范式文件点名**：`models/<同模块>.py`、`schemas/<同模块>.py`、`routers/<同模块>.py`、`main.py` 的 include_router 注册方式、`models/__init__.py` 导出、alembic versions 迁移风格——让 agent 照葫芦画瓢不发明新写法；同时写明**每个接口的权限级别**（成员级 vs 管理员，照参考模块）
4. **明确"前端零改动"**：前端已是最新正确实现，后端补齐后前端自动可用（静态 dist 无需重构建）；若前端有"接口失败静态兜底"逻辑，说明补齐后会自动走真实接口
5. **部署通道必须含 .env 与 DB 迁移保护**：deploy.sh 后端 rsync 加 `--exclude='.env'`（防开发版覆盖生产，见 forge-deployment）；alembic 用 `.venv/bin/alembic upgrade head`（venv 内的可执行文件，裸命令找不到）；验证用真实登录 token curl 新接口（token 存文件防脱敏）+ 浏览器确认页面不再报 Not Found

### 三方 API/SDK 对接：协议先行（2026-08-05 用户总结，最高优先级方法论）

用户原话：\"后面有这种对接三方的，你一定要先去把 API 或者 SDK 跑通，然后用标准格式给到 agent 指令，低模型也能达到不错的效果\"。适用于任何接第三方服务（语音/支付/云 API/IM 等）的 AI 协作任务。

**流程（四步，顺序不可颠倒）**：
1. **自己先把协议跑通**（判断层，Hermes 的活）：读官方文档 → 拿官方 demo/SDK → 本地/服务器实测调通（鉴权、请求格式、响应解析、错误码）。**禁止直接甩给 agent 对接**——agent 也会盲试协议，顶配模型才可能啃动，低模型直接废，且往返烧钱。
2. **验证成功**（真实调通，不猜）：用真实请求确认能拿到预期结果（如音频/数据），记录错误码 → 根因速查（如 55000000 = body 结构错、45000010 = App/服务绑定错）。
3. **把已验证的调用方式以标准格式写进 agent 指令**：完整 URL、鉴权头（含 key 格式坑如\"只传值不传名称:值\"）、请求 body 结构（贴正确 JSON 示例）、响应解析方式、已知错误码含义。**指令给\"已验证的标准格式\"，不给\"去研究协议\"**。
4. **低模型（Luna 极高模式）执行也能达到不错效果**：用户实测\"luna 开极高模式是真的省，还比较准，只要指令和边界准确\"——协议跑通 + 边界写清 = 不用顶配。顶配留给协议未通/架构级重构。

**后端锚点原则（用户 2026-08-05 明确认可）**：\"今天你 vps 侧一直不需要配合前端怎么去调整修改，都是围着你来改的\"——**服务端（代理/API）先定契约并保持稳定，前端/调用方单向适配**。契约清晰 → agent 改前端时边界明确 → 低模型可干 → 返工少（用户对比：协议盲试日返工 n 轮 vs 协议先行日几乎不返工）。

**验证锚点**：代理日志三行齐全（识别→思考→合成）即链路通；改前端后对照代理契约验收，不回改代理。

## 上下文投放纪律：知识库/源码是"可查文件"，不是"随身行李"（2026-09-02 用户 569k token 教训）

**症状**：给 agent 派"建整个项目/复刻整个系统"这种大活时，把**整个知识宝典 + 整个前端源码**一次全塞进会话 → 单会话 token 冲到 **569k**，agent 回复变得极慢、理解稀释、前后矛盾，最后慢到用户没等到回复就放弃。用户自查确认两个根因：①知识宝典太大占大头；②把**前端源码散文件全文**扔进上下文（而非 dist 压缩包/仓库路径）。

**根因**：把"本该留在文件/仓库里的库存"当"塞进 agent 脑子的随身行李"。大上下文 = 物理上慢（每次回复都要在几十万 token 里找）+ 稀释 + 烧钱。

**正确姿势（铁律）**：
1. **知识宝典/产品架构/接口文档 = 可查的库，不是常驻记忆**：建好后放文件，agent 处理某件事时**只让它去读那一个文件/章节**（按需加载），用完就放下。绝不让 agent 时刻背着整个库。
2. **前端/源码 = 让 agent 读文件/仓库，或给 dist 压缩包，绝不把源码全文粘进上下文**：agent 能访问目录 → 给路径让它自己读；不能访问 → 给精简的/必要的（dist 产物），几十万行源码永远不该全文进会话。
3. **大活按模块拆会话，别一次搓成型项目**：成型项目是 context→单模块 PRD→单模块前端一步步建的（Forge 流程本来就如此），不是把全模块一次堆一起搓。
4. **会话一长就 /new 分段**，别硬扛。
5. **判断标准一句话**：让 agent"读文件/查库"，而不是"把文件内容塞给它"。上下文只放当前这步要用的少量信息，大的东西让它去文件里读。
6. **止损**：一旦发现会话已到几十万 token（如 5 位数 token 起步的巨型会话 + 回复明显变慢），**别救，直接 /new**——地基/知识库/文档都在文件里不会丢，新开会话按模块小步重来比在巨型上下文里挣扎强。
