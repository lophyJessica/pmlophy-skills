# UI 复刻四方案

> 来源:2026-07-18 杰西卡总结,Codex @chrome 实测验证

## 四方案矩阵

| 方案 | 数据源 | 适合场景 | 工具 | 
|------|--------|---------|------|
| **A 源码** | 研发给代码 | 自己公司老系统改造 | 反重力/Codex 直接改 |
| **B 设计稿** | UI 给 Figma+组件库 | 新项目从设计稿还原 | Codex 看图生成 |
| **C 截屏** | 截图→Agent 看→改 | 竞品/无登录/UI 微调 | Gemini(有视觉) |
| **D 浏览器自动化** | @chrome 直接抓 DOM+样式 | 公开页/有 Demo 账号/自己老系统 | Codex @chrome |

## 交叉组合

| 组合 | 场景 |
|------|------|
| **A + B** | 老系统改造——源码打底,新设计稿定风格 |
| **A + D** | 给老系统加功能——@chrome 看现状,源码精准改 |
| **B + C** | UED 走查——设计稿截图 vs 开发还原截图,让 Agent 对齐 |
| **C + D** | 竞品分析——@chrome 打开竞品首页(公开),截图参考;内页只截图 |

## 硬限制

- 竞品后台需登录 → 方案 D 不可用(没凭据进不去)
- Agent 无视觉能力 → 方案 C 不可用(截图给它也看不懂)
- 非公开页面无 Demo 账号 → 只能靠方案 C

## 实战案例

- **copy-wms**: Codex @chrome 打开参考 WMS 页面,直接克隆布局+配色+交互,生成 React 代码
- **forge UI 微调**: Gemini 截图看页面,文字描述问题,反重力改代码

## 整系统复刻（built-in 浏览器 → 本地 React 项目迭代）——2026-09-02 实测坑

场景：只能访问目标系统测试环境（无源码/无设计稿），用户想把**整个系统复刻到本地 React 项目**，再用 Forge 方法论在本地迭代设计（CMS 复刻案例）。

**两个必踩坑（避免重犯）**：
1. **菜单/路由层级即使"一层层照着复刻"也会复刻错**——AI 逐层读仍可能理解偏结构（把子菜单归错级/漏层级）。**复刻产物 ≠ 权威标准**，只能当草稿/参考；权威始终是目标系统真实页面（你点出来的）。先拿**真实菜单层级**（一级→二级→三级）钉进指令"菜单按这个层级，禁止 AI 自己发挥"，别让 AI 猜；或先只复刻 1-2 个菜单分支验证结构对，再扩，别整系统梭哈（容易结构飘）。
2. **整系统复刻 + 整知识宝典一起喂 = 上下文爆炸（569k token）**：见 SKILL.md「上下文投放纪律」——知识宝典/源码/架构放文件里按需查，别一次全塞进 agent 会话。

**整系统复刻的推荐路径**：先建**真实系统菜单地图**（维生素第 10 课"抓菜单"法）→ 用地图对齐复刻的骨架 → 逐模块（每模块一个小会话）→ 每模块本地验收 → 文档对齐到复刻项目（文档与复刻冲突时以真实系统为准，复刻不彻底时更不能以复刻为准）。
