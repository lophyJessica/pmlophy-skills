# 前端页面复刻 A2A 指令模板

> 来源: 用户实战打磨的 "资深前端还原工程师" 角色指令
> 适用场景: 根据参考页面 URL/截图/描述，从零生成可运行 React 页面
> 与五段式指令互补: 五段式用于修改已有代码，此模板用于生成新页面

## 完整模板

Context:
你是资深前端还原工程师，把老旧后台系统页面复刻成可运行可扩展的React项目。

本次目标：根据参考页面URL/截图/描述，复刻指定页面。不生成孤立单页面HTML，要识别并沉淀同一系统的公共布局。

技术要求：
1. 遵循现有技术栈(React+Vite+Tailwind CSS)
2. 拆分复用AppShell/TopNav/Sidebar/FilterForm/DataTable/Pagination/Modal等公共组件
3. Tailwind负责布局颜色间距；老系统特殊尺寸用少量自定义CSS
4. 图标优先复用项目内SVG/iconfont，禁止用Emoji或随机Unicode替代
5. 默认Mock数据+本地状态，不接入真实接口
6. 不引入不必要依赖，不擅自改变原页面结构

执行流程：
1. 检查项目结构+分析参考页面(布局/字体/颜色/间距/表格列/交互)
2. 区分公共布局与独有内容，优先复用已有组件
3. 先输出简短实现计划+关键假设，再修改项目文件
4. 完成页面后启动本地项目检查实际渲染
5. 修复最明显的3-5个视觉差异
6. 验证主要交互和控制台，确保无错误

还原原则：
- 优先还原整体布局、尺寸比例、视觉密度和信息层级
- 保留老系统常见的固定顶部栏、侧栏、窄表格、横向滚动、中文字体
- 无业务逻辑时用Mock交互表达
- 不确定内容用低风险假设并在结果中说明
- 只有遇到改变实现方向的关键歧义时才提一个问题

完成后输出：已完成页面和公共组件、修改/新增文件、本地运行命令、已验证的交互和视觉效果、未实现/需确认项

## 四类复刻方案(来源:用户 2026-07-22 实战矩阵)

| 方案 | 数据源 | 适用场景 | 工具 |
|---|---|---|---|
| **A. 源码** | 研发给代码 | 自己公司老系统改造 | 反重力 |
| **B. 设计稿** | UI 给 Figma+组件库 | 新项目从设计稿还原 | Gemini/Antigravity |
| **C. 截屏** | 截图→Agent 看→改 | 竞品/无登录/UI 微调 | Gemini |
| **D. 浏览器自动化** | @chrome 直接抓 DOM | 公开页/有 Demo 账号 | Codex @chrome |

四个方案可交叉使用: A+B(老系统改造)、A+D(精准定位修改)、B+C(UED 走查)、C+D(竞品分析)。

**Codex @chrome** (方案 D): 原生浏览器操控,自动识别布局/配色/交互,直接生成 React 代码。比截屏→描述快 10 倍,但需登录凭据才能访问内页——竞品内部页面不可用。

## 实战要点

- 提供参考页面URL+登录账号让Agent直接看真实布局
- "识别并沉淀公共布局"=为系统搭脚手架，后续页面扩展零成本
- "只提一个关键问题"减少来回沟通，类似Checkpoint

## 四条必写红线（漏了必返工，复刻类指令最贵的几个坑）

### 一、原系统用什么组件库就用什么，不许替换

复刻指令里千万不能写「XX 组件用 YY 替代」，哪怕两者风格接近。写「能用就用，不能用就替代」，agent 会把**整套都替代掉**，然后交付一个「有源码还样式完全不一样」的产物，用户判断「完全是两个产物」。

私有组件库先验证能不能装（内部 registry），能装就必须用真的。唯一允许替换的是平台能力层（原生桥、扫码、剪贴板、保存到相册）——换成浏览器 mock。

指令里的固定写法：

```
组件一律照源码原组件，组件名和全部属性逐字照抄，不许用任何其他组件库替代。
发现某个组件确实装不上时，停下来告诉我，不许自己挑一个近似的替代。
```

### 二、取不到证据时如实标注，不许静默简化

agent 取证不完整时就开工，会把没取到的部分**悄悄删成简版**交差（详情页只剩名称和链接、展开态筛选直接不做、状态标签颜色自己配）。用户只会问「为什么要做简化」。

指令里三句必须都写：

```
取不到的字段/区块/样式值，在该处标注「线上未取到」，不许静默删掉；
交付时单独一节列出「哪些没取到、尝试了什么」；
体积/复杂度不是理由，不许以「简版」交差。
```

取证顺序也写死：**先把该点的点完（展开收起、Tab、下拉选项、弹窗）再动手写代码**，别一边写一边取。

### 三、真源是现场 DOM / 跑起来的系统，不是仓库文档

「让原型跟真实系统对齐」时，菜单结构、筛选项、列、状态色的真源是**现场页面**（内置浏览器打开的已登录系统），不是仓库里的盘点 md，也不是路由表代码——真实系统的菜单是后端配置数据下发的，前端源码里根本看不到部署出来的菜单树。指令第一条永远是「现场只读取证」，不是「照某份文档改」。

更彻底的一条：如果源码能在本地跑起来（装得上依赖、能起 dev server），**跑起来的真实渲染比“照代码搬”准**——直接对 computed style 和 DOM 取值。缺登录态也不影响看布局与控件形态，只是数据空态。

### 四、手机端原型在桌面看：375px 容器的 `cqw` 坑

容器 `max-width: 375px` + **必须声明 `container-type: inline-size`**，PostCSS 才能用 `cqw` 按容器换算；没这个声明 `cqw` 退回按浏览器窗口算（940px 窗口下 16.67cqw = 157px，页面巨字）。验收一行：`getComputedStyle(document.querySelector('.mobile-viewport')).containerType` 要返回 `inline-size`。配套：页面里的 `position: fixed` 会相对浏览器窗口而不是容器（顶部横跨全屏），TabBar 用 `absolute` 钉在容器底部。

### 五、共用外壳（导航/状态栏/胶囊/TabBar）挂在应用根，不逐页插

小程序类移动端复刻的导航栏、状态栏、胶囊按钮、底部 TabBar 是**全体页面共用的外壳**，应在 App.vue/App.tsx 的根容器统一包一层（状态栏 + 导航栏 + router-view + TabBar），页面组件不引入也不渲染导航。逐页插入 = 重复实现，且路由切换时导航会重建/闪烁；二级页返回箭头显隐、搜索态隐藏导航这类**全局态**只在外壳里判断一次（按 `route.meta.homeTab`），不用每页面写。

已知反模式（都实测过）：① agent 第一轮逐页插 NavBar，用户原话「样式很简单，外面包一层不就好了」→ 指令应直接定外壳方案；② 外壳方案落地时 agent 忘把页面里已插的 NavBar 摘除（双重导航）；③ 外壳里的胶囊被加了真实行为（更多弹菜单、关闭跳首页）——定稿口径是纯静态展示；④ 二级页返回箭头渲染失败（图标被全局 reset 吃掉/判断条件写反），交付截图里标题左侧空白——验收必须带二级页截图且箭头可见才算过，只看自报「已接入」不算。

## 只取证不开发时，交付物是结论不是改法

用户说「只是取证」「我们又不是开发」时，**不要顺手给修复方案或改动建议**——那些属于研发的活。交付物就是：现状是什么、机制是什么、对产品意味着什么。给了改法反而被判跑题（原话：「管怎么修改干嘛？」）。
