# 一次给全：范围要盖满，检查点分在指令内部

不要把一个任务拆成多轮指令，一页一页、一步一页地给。用户会直接说「给我一个全量的指令」。

## 正确形状

一份指令内部分成多个阶段（第一部分/第二部分/第三部分），每部分写清范围与要求，Checkpoint 写在指令末尾统一收束。而不是今天发一页的指令、等它跑完、明天再发下一页。

例外：当任务的成功依赖前一阶段的产物格式时（比如先出一份样板 TSV 确认列定义，再铺其余三套源码），这时才阶段一停下等确认。判据是「格式错会全返工」，不是「页数多」。

## 范围盖满的三件检查

交出去之前逐项问自己：

1. 目标对象的全部数量都列上了吗？（说「剩下三页」就要把三页全列出来，不是只写第一页）
2. 每一步的验收判据写了吗？（不说「检查一下」，要说「用基线脚本生成对照稿、逐页比 XML，只允许这三页变化」）
3. 需要用户拍板的取舍点提前标了吗？（标在指令里让它遇到就停下问，而不是跑完才暴露）

## 配套：交付备注

用户自己用 IDE 提交，不需要给 git 命令，只需要给提交备注文本，且备注要短——一两行讲清干了什么就够，不要分节长清单。
