# PRD 根因排查：先问 context 再修 PRD

2026-07-29 实战教训：供应商报价模块经历 4 轮前端 + 3 轮 PRD + 2 轮 context 修改才定版。

## 事件链

1. 初始 PRD: "供应商报价单 BJ-prefix" (采购员录入版)
2. 前端实现: 反重力写了列表+新增编辑
3. 用户发现: 面包屑不对、询价单没同步、这是供应商用的不是采购员用的
4. 第一反应: 给前端修正指令 → 修了 2 轮还是不对
5. 用户指出: "PRD 本身估计就是问题"
6. 重写 PRD → 还是带了 BJ 前缀和错误定位
7. 用户问: "context 有没有要先修改的"
8. 改 context/04 (模块名+定位) + context/05 (删除 BJ 前缀) → PRD 重写 → 前端重写

## 正确流程

```
发现 PRD 核心定位错误 → 
  先问: context/04 (模块定义) 和 context/05 (编码规则) 要不要改? →
  改 context →
  重写 PRD (主PRD + 字段清单 + Demo) →
  用户评审确认 →
  再出前端指令
```

## 判断标准：什么算"核心定位错误"

必须回溯 context 的信号:
- 用户角色变了 (采购员→供应商)
- 单据编码前缀需要新增/删除 (BJ 前缀)
- 模块名称变了 ("供应商报价单" → "供应商报价工作台")
- 状态机根基变了 (草稿/已报价 → 待报价/已报价)
- 数据层级变了 (独立单据 → 挂接在询价单下,无独立单号)

## 什么情况下只修 PRD 不改 context

- 字段增删(不涉及编码规则)
- UI 交互调整(面包屑/布局/按钮文案)
- 业务规则微调(超期策略从"宽松"改"严格",前提是状态机不变)
