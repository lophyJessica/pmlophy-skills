# 验收 agent 产物：三类失败与识别方法

agent 自报“已完成/已重判/已按要求”都不算数。这三类失败各出现过，识别成本很低，但只看汇报会直接采信错的结果。

## 一、抄旧值冒充重判

**现象**：让它“重新判定某一列”，交回来的文件行数对、格式对、统计也对，但内容是上一轮的值。《实测：1136 行重判，与旧结果的判定逐行相同，0 处差异。》

**成因**：工作目录里存着上一轮的结果文件，agent 直接读旧值搬回来，没有回源码重判。

**指令侧预防**：重判一律换一个只放输入文件的干净目录，并在指令里写死「不许读取或引用任何其他历史结果文件」。输入文件也不要带旧判定列——带着列等于把答案递到它面前。

**验收动作**：新旧结果逐行 diff（按「页面 + 子功能项」为键）。全等即未重判，直接退回。

## 二、卡在上一轮，反复吐旧产出物

**现象**：连着几次交回的都是上一步的文件，文件名和统计完全一样；加语气、重申需求都没用。《实测：连续三次交回同一份外销清单。》

**成因**：上下文串了，或没读懂任务边界——它把新任务当成了继续上一轮。

**指令侧预防（三条一起写，缺一不可）**：
1. 开头先写任务边界：「这是全新任务」+「上一轮产出已完成，不要再生成、不要覆盖、不要重新输出」。
2. 写死唯一产出物：「本次唯一允许的产出文件名是 X，最终文件名不是 X 即视为失败」。
3. 要求交付自检数字：行数（含/不含表头）、各类计数相加必须等于总行数、所有中间态行的清单。对不上就停下报告，不许硬交。

仍不行就开新会话重投，不要在同一会话里继续加码。

## 三、主观列口径漂移

**现象**：同一套代码、同一个判定列，分给不同 agent/不同批次后，可配率差出三十多个百分点。

**成因**：「标签写死但内容接口驱动」这类边界情况，两边取法不同。

**处理**：
- 主观列（是否可配、是否有对应能力、是否等价）只能由一个 agent 从头判一遍；或每批都要求附「判定理由」，并比对各批比例。
- 已漂移时不要全量返工：从两版结果里各取一半行（如 20 页 × 3 行）做**盲判仲裁**，分别算与两版的一致率。两版一致率接近时（如 79% / 78%），看**错的方向**：集中在「旧× → 盲判√」说明那批判严，反向则判松。只重判错的那一批。
- 盲判样本要放进干净目录、只带中性列（页面/子功能项/介绍/依据），不带任何旧判定。

## 四、脚本自动匹配的结果只能当对照

按页面配对 + 文案相似度自动映射，会把「刷新按钮」匹到「去处理按钮」、「打标签弹窗」匹到「修改备注弹窗」——机械初版与人工判定的一致率只有六成多，且错的方式是硬凑匹配。

它的正确用途只有两个：给审阅者一个底盘；把下一轮 agent 的任务从「从零做」降级成「审初版、判错就改并给理由」。最终结论必须由能读代码的一侧判，不能把相似度分数写成结论。
