# 需求分析档指令模板（给 agent 批量分析 N 条需求）

场景：有一批已圈定的需求（来自需求池/VAPD 单号），要让 agent 产出一份可交付的分析档。已有调研/评估文件必须先读，本轮的增量是**源码级现状核查 + 实现方案 + 依赖 + 优先级**。

## 逐条固定七段（顺序不许变）

1. **需求原文摘要**：照抄关键句，不改写、不加解释（改写了后面就没法回对原文）。
2. **业务场景与价值**：谁、什么情况下遇到什么问题、解决后带来什么。
3. **现状核查**：现在系统有没有相关能力？在哪个模块、哪个文件、哪一行（生产源码 文件:行号）；缺什么。页面上能看到的给页面证据。
4. **实现方案（MVP 优先）**：分别要改哪些端（后台 / 员工端 / 消息工作台 / 大数据），最小可实现范围是什么。
5. **前置依赖**：外部（大数据表与字段、订单数据、合规）与内部（哪些能力要先做）。
6. **优先级建议 + 理由**。
7. **待确认项**：需要问需求方 / 开发 / 大数据的。

## 硬规则

- **事实与推断分开**：事实必须带证据（源码 文件:行号 / 页面截图 / 原文摘录）；推断一律标注“推断”；源码里查不到的写“未在源码中找到”，**不许用推断顶替事实**。
- **产出路径写进 Output format**（一个主文件），红线只用来防越界，不用来代替指定产物位置。
- **Checkpoint 分段**：先做完前 2~3 条并停下，把总览表 + 这几条发回来确认口径，确认后再做剩余——一次性全量输出，口径错了整份返工。
- **总览表要标“是否已复核源码”**：不能把上一轮（或上个月的）旧评估原样沿用——旧结论可能已被证伪，写清哪几条本轮真的核过源码。
- 红线固定：只读生产源码与测试环境（禁点 发布/保存/提交/预估人数），**只许写自己的目录、严禁改同仓库其他任务的目录**（并行时不写这条必然互串），不 commit/push。
- 需要它“写细一点”的条目点名列出（通常是：时间敏感与版本绑定的那条、跨端链路最长的那条、与本期新建能力有复用关系的那条）。
- **时效要标**：原文写的“期望上线时间”往往已过期，别让它变成别人拿来排期的依据——逐条标「已过期，需重排」，并在文档头部写一句时效说明。
- **依赖要覆盖两类常见漏项**：①本能力的上游能力还没交付（如“沿用本期新建的 X”，而 X 还是下一期的事）；②外部数据源还没接入（如按某类标签筛选，而该标签体系本身尚未接入）。这两类不写进依赖节，排期就是空的。

## 常见坑

- **原文里的绑定句必须先回原文确认它挂在哪一个子项下**。“与 X 功能一起上”这类句子常常只写在某个子项（如 a）底下，不是整条需求——先定位这句话在原文里的位置，再决定它约束谁；把整条都按“绑在一起”写，就等于替需求方扩了范围。只对确实被绑的子项写绑定，其余子项写独立排期，并把“能否先行”列成待确认去问需求方。
- agent 报告“生产源码里没有 XX 实现”时，先核它看的是不是旧分支：本项目若正在做该功能的发布上线，结论可能相反。
- 本期新建的能力（生产源码里当然不存在）只许表述为“本期新增 / 将来可复用”，不许让 agent 去对照一个不存在的模块。
- **内部证据引用不是缺陷**：分析档是内部件，保留「文件:行号」与证据档引用是对的；但要在头部加一行「内部证据文件」写明来源类型——否则复核方（尤其是看不到这些文件的 agent）会把它们当“无出处”报上来。

## 多 bot 并行：任务包 + 复核岗

批量分析适合拆给多个 bot（各自独立跑一条需求）。拆法与红线：

- **按产出物切，不按步骤切**：一条需求一个 bot，互不依赖、不写同一个文件；每个 bot 一个自包含包（输入 + 八节输出格式 + 八节固定标题 + 红线 + Checkpoint）。
- **输入必须自包含并可列举**：给它的材料就是几份文档，**在交付说明里附一张文件清单（文件 → 源路径 → 大小 → 谁需要）**，让用户把文件复制到 bot 能读的位置（沙盒常只允许读某个盘）。同一条需求只喂它需要的那几份，别把无关材料一起堆进去。
- **无源码访问权的 bot 必须先立规矩**：输入材料之外一律写「材料未覆盖」，不许推断系统现有实现，不许编接口/字段/表名——否则产出会“看起来合理但全是编的”。
- **每条需求只要求先出最关键的三节**（原文摘要 / 功能点拆解 / 待确认），确认口径后再补全其余节：一次铺满等于口径错了整份重写。

**复核岗（挑毛病 bot）**：另起一个 bot，喂**全部对照材料**（分析档 + 原文 + 总览 + 对标文档 + 调研清单），任务只是“找问题不写方案”，固定六类：

1. 无出处的事实（把推断写成事实、引用材料里没有的依据）
2. 自相矛盾（同一份文档前后冲突）
3. 遗漏场景与边界（空数据、失败、超时、权限不足、批量、并发、数据缺失兜底）
4. 依赖漏项（做这条实际还要什么，文档没写）
5. 优先级理由站不住（理由与结论不匹配、与其它条目判断标准不一致）
6. 术语不一致（同一事物不同叫法）

输出一张问题清单：序号 / 位置（章节＋小节）/ 问题 / 依据（引用原句或标“材料未覆盖”）/ 严重度 / 建议；按严重度排序，只列问题、不重写文档、不提新需求、不给排期。先要高优先级前 5 条，确认后再要中低。

复核的输入要**尽量完整**：只通读部分材料时它自己会声明“只按关键词抽查了其余几份”，这时它报出的“无出处”里有相当比例其实是它没读到——把材料给全，它的误报会明显下降。

## 澄清项要收敛，不能倒垃圾（否则只是一堆未判断的不确定性）

多 bot 分头写时，每个 bot 都会把「所有不确定」倾到待确认节（几十数百条、且每条里裹着 3–6 个子问题），那不是严谨，是没做判断。收到后父会话要做的第一件事是**按“谁答 + 不答的后果”三刀切**：

- **会上必拍**：不答就**开不了工**的（架构归属、外部数据源到底有没有、核心口径定义、本期范围）。通常只剩个位数；每条写清「为什么必须会上拍 / 建议谁答 / 不答的后果」。
- **书面按人问**：只能外部答复、但不阻塞开工的 → **按人合并**（需求方 / 数据方 / 开发 / 对接方 / 运维 各一份清单），会后回收。**不要按需求分**——同一个问题影响多条需求时，按人问一次能解多条。
- **自己定**：做法多样、不影响能否开工的设计选择 → 让 bot **给默认值**，不要列成待拍；只把「两种做法改造量差一截」的挑出来送用户。
- 实现细节（接口怎么调、表怎么建、并发怎么处理）单列给开发，不占产品时间。
- 材料缺口（原文示意图未转录之类）单独成「补材料清单」——混在待确认里只会虚高条数、拉低优先级含金量。
- **判据一句话**：不答就开不了工 → 会上；只能外部答 → 书面按人；做得不一样 → 给默认值。
- 同类问题按**词**合并而不是按需求合并（“已删除 / 待添加 / 交叉 / 某口径从什么时候算”这几个词各自一次问完）。

**交付形态**：一份《澄清清单·会前版》，四节——①会上必拍（含理由/谁答/不答的后果）②按人分发的书面问题 ③材料缺口 ④不进清单的部分及其去向。**第④节必写**，否则被压下去的条目会再流回会上。

**归档 bot 草稿要标“非权威源”**并在头部指向收敛版：草稿与权威源（分析档）并存时，后来人极容易拿草稿当依据——文件里写清“事实与口径以《XX 分析档》为准，本稿仅作方案推演与澄清项来源”。

## 复核结果的分层处置（父会话做，不要转发给 bot 自己决定）

复核报回问题后按四类处理，**不要照单全改**：

| 类别 | 例子 | 处置 |
|---|---|---|
| 结构性前提（影响排期） | “依赖的上游能力还没交付”“外部数据源未接入” | **父会话回写权威源**（分析档依赖节），再让方案 bot 同步——只写在草稿里等于没写 |
| 口径错误（原文被过度解读） | “这句话只挂在 a 底下，不是整条” | **父会话去原文核实**，改权威源里的那段结论 |
| 机械可修（文档自身） | 外引路径、过期时间、名称不一致 | 父会话一次性改掉，不必占用 bot 轮次 |
| 已由父会话处理过 | 复核要求的补充其实已经做了 | **明确告诉 bot 不用补**，避免重复劳动和二次口径漂移 |
