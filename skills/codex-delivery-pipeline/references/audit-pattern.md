# 审计型子任务的标准打法（delegate_task 两线并行）

## 适用场景
长迭代收尾、多轮修复后的收口：用户要"最后来一轮审计和修复"。

## 实测有效模式（2026-08-28 forge-scrm）

**两线并行**，一次 batch 两个 leaf 子代理：
- **A 功能审计**：只读走查近期全部代码改动，按 P0（状态机洞/安全）/P1（功能缺陷）/P2（质量）分级，强制"已核通过的方面"也列出来（防止报告全是问题、没有基线）。限制条数（≤15）防凑数。
- **B 标准审计**：先【起草标准文本】再按标准走查——用户说"UI 很丑很随意"时，根因往往是**标准没成文**（只在讨论中存在），先立标准再查违规，修完顺便把标准沉淀进仓库（AGENTS.md 指针 + 独立规范文件，单一来源解耦）。

**指令关键要素**：
- "不要修改任何文件，只输出报告"（只读审计）
- 每条问题含【级别】+ 文件:行号 + 建议修法（可直接转成修复指令）
- "宁缺毋滥"上限（15-20 条）
- 用户提供截图标注的 bug 优先纳入

**汇总动作**：两份报告 → 合并为**一条**编号修复指令（P0→P2→UI 顺序）→ 用户跑 Codex → 核验报告 + VPS grep 实锤 → 部署 → 用户抽查。修复指令里写明"已核通过不要动"清单，防 Codex 越界重构。

## 反面教训
- 单份大报告直接怼主上下文：让子代理返回结构化摘要（全量存盘，只读需要的段落）
- 审计只报问题不给"已通过"基线：用户无法判断改动面是否失控
