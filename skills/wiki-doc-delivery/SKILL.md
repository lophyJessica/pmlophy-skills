# Markdown 文档交付到 wiki 平台

本地渲染正常 ≠ 粘过去正常。交付失败几乎都在三处：**平台不认的语法标签**、**相对路径图片**、**用本地预览当验收**。

## 第一步：先问平台，别先改文档

用户报「换行没生效」时，**先问是哪个 wiki、以及标题/表格/加粗/列表认不认**——不同答案对应完全不同的改法，猜错就是白改一轮。

| 平台表现 | 处置 |
|---|---|
| 标题/表格/加粗/列表都认，只有换行不对 | 不认内联 HTML `<br>`。把内容从表格单元格拆成 Markdown 列表（见下） |
| 连标题、表格都不认 | 跟文档写法无关，是粘贴方式问题。转 HTML 用浏览器复制，或走平台自带的 Markdown 宏 |
| 全部正常 | 只剩图片问题，做 base64 内嵌 |

实测 Confluence：认 Markdown 的标题、表格、加粗、有序/无序列表，**不认 `<br>`**。

## `<br>` 是 HTML 标签，不是 Markdown 语法

表格单元格里用 `【页面内容】<br>1) xxx<br>2) xxx` 分行是常见写法，在支持内联 HTML 的渲染器（VS Code / GitHub / Typora）里没问题，**但这不能当验收标准**——Cursor/VS Code 预览支持内联 HTML，粘到过滤 HTML 的平台就会挤成一团。

**解法：把成段内容从表格单元格里拆出来，改成 Markdown 列表。** 列表是原生语法，只要平台认 Markdown 就一定渲染成多行，不依赖任何标签。

**⚠ 但结构性改写必须先经用户同意，不能当成默认动作。** 把表格拆成列表会改变整份文档的阅读形态——表格一行一页、横向扫；列表一页一节、纵向排，页数一多文档会变得很长。实测这份改写被用户直接退回：「可读性太差」「还是得需要表格，不然很乱很乱」。

可接受的几种降级，按代价从低到高：

1. **保留五列表格和 `<br>`，换行由用户手动处理**（最常用的收尾）。用户在 Confluence 里逐格回车，或者接受它挤成一段。原话：「br那个你不用管了，我自己手动换行处理吧，不折腾了」。
2. **表格单元格内换成带编号的分隔符**：`【页面内容】1) xxx ｜ 2) xxx ｜ 3) xxx`——不换行，但每条编号清楚，比句号连写可读。
3. **主表 + 说明表两张表**：主表一行一页放图（序号/路径/图/备注），紧跟一张「分段 | 内容」两列表，一条说明一行。每条自解释、不靠单元格内换行，但分段名要重复写，看着啰嗦。
4. **拆成列表**（本文件上面的形态）——只在用户明确同意改结构时用。

决策顺序：默认先问「表格换行还是拆结构」；用户没明确说改结构，就走 1。

**产出一律保持 md，不要为了迁就平台换格式**。用户明确：「我都说了，不想换其他格式的，我们产出的就是md，改也会很方便」。docx / HTML / PDF 只在你提出来后他明确说要时才做——他要的是能回写、能 git diff 的源文件。

转换后的单块形态：

```
**序号. 操作路径/功能点**

![](data:image/png;base64,...)

**页面内容**

1. 第一条
2. 第二条

**交互说明**

1. ...
```

转换规则：
- `【页面内容】<br>1) xxx` → `**页面内容**` + 空行 + `1. xxx`
- 条目自带的 `1)` 编号换成 Markdown 的 `1. `
- 备注列非空时用 `> 备注：xxx` 收尾
- **其他表格（字段清单、状态枚举、待确认事项）原样保留不动**——它们不靠 `<br>` 分行，拆了反而丢结构

## 图片交付：默认给「按序号命名的截图文件夹」，不做 base64 发布版

相对路径的图 `![](./images/x.png)` 粘到 wiki 一定是破图（粘贴只带文本，不带附件目录）——这个事实不变，但**解决办法已经换了**：用户明确不要再出 base64 内嵌的发布版（原话「后面不要出 base64 的图片了，太麻烦了」），改成他自己上传图片。

固定做法：在 PRD 目录下建一个截图文件夹（如 `04-评审PRD/wiki截图/`），**按页面分组建子目录、按 PRD 表格里的序号命名**，并写一份 `索引.md`（序号 / 文件路径 / 说明）让他对着贴：

```
wiki截图/
├── 01-<页面A>/
│   ├── 1-<功能名>.png
│   └── 2-1-<功能名>.png        # 子序号用连字符，与 PRD 的 2-1 一一对应
├── 02-<页面B>/
└── 索引.md
```

- **序号必须等于 PRD 表格里的序号**，不要另起一套；分组目录用「NN-页面名」保证排序稳定。
- 图片本体仍留在 `images/`（PRD 的相对路径引用指向它），`wiki截图/` 只是给他上传用的整理版；两边文件名不同是正常的。
- 源稿的 `![](./images/...)` 引用照旧维护，**发布版（base64）不再默认生成**——只有他明确说要发整份发布版时才做一次。
- 生成工具：项目里有 `embed_images.py` 之类脚本就复用；只在真要出发布版时跑，跑完确认 base64 图数 = 源文件图片数。

## 截图必须先看画面内容，再谈文件名

截图是 PRD 的证据，文件名叫什么都不算数。**交付或审计截图时必须真看图（`vision_analyze`）**，核对画面里的状态是否就是这一条要讲的状态——实测遇到过：PRD 里名为「导出失败重试」的图，画面里两条任务全是「生成中」，既没有失败态也没有重试按钮，等于这条说明没有任何证据；而真正含失败态+重试的图反而挂在相邻的另一条上。

- 一条说明需要一个状态的证据时，**把该状态的要素逐个点名核对**（状态文案、按钮、入口是否出现），画面里缺一个就是图不对。
- **多状态的功能给多张图，一图一态**（失败态 / 点击后中间态 / 完成态），不要指望一张图说明整条流转。
- 截图要来自**当前正在运行的原型**，并记下生成时间；改了原型之后旧图就是过期证据，要重截而不是复用。

## 转换后必查四项

少一项就是丢内容：

```bash
# 1. 标签残留必须为 0
grep -c '<br>' 新文件.md

# 2. 相对路径残留必须为 0
grep -c '\./images/' 新文件.md

# 3. 章节标题数与源文件一致
grep -c '^#' 源文件.md 新文件.md

# 4. 图片数与源文件一致
grep -o '!\[' 源文件.md | wc -l   vs   新文件
```

再逐条比对源文件的每个 `#` 标题、每个图片引用是否都能在新文件里 `grep -qF` 命中——比只看数量更可靠。

## 诊断：标签数差异不一定是缺标签

新版比旧版少几十个 `<br>` 时，先数「`【】` 分段数」——差的是**段落数**（旧版没跟到新版新增的段），不是格式漏了。

判据：把「缺 br」的两种典型形态各 grep 一遍，命中为 0 就说明格式完整、问题在内容版本：

```bash
# 段标题后直接跟数字（缺 br）
grep -oE '【[^】]{2,8}】[0-9]' 文件.md
# 条目之间无 br 直接接下一个编号
grep -oE '。(?=[0-9]\) )' 文件.md
```

两处都 0 命中 → 该重新生成内容版本，不要去补标签。

## 用户已在 wiki 里排好版：只能增量交付

一旦用户在 wiki 里手工调过样式，他会直接说「我没办法全量复制替换」。这时**不要再发整份发布版、也不要发 md 文件**（原话：「我不要md的文件，你在聊天框告诉我就行，哪个标题下的哪个值要修改」）。做法固定为：

1. **在聊天框里按「章节标题 → 条目 → 改成什么值」逐条给**。每条带一个定位锚点（行号 + 开头一串原文），他用锚点在 wiki 里搜得到位置。不要让他自己对 diff。
2. **批量改动单列成一条可批量执行的规则**，不要逐行贴。例如「所有缺【待确认】的页面说明行，末尾补一句：1) 当前无待确认项。」——逐行列 20 行他没法用。
3. **行数会变的块要提前提醒**：删段/补段会让表格行数增减，告诉他「按行内容替换，别按行数对齐」。
4. **含 base64 内嵌图的表格行**：不要让他复制那一大串。单独把图文件发到聊天，让他上传后换成 wiki 自己的图片地址，文字部分照拄。
5. **版本记录/修改记录这类内部痕迹可以标「可选」**，让他自己决定贴不贴。
6. **要换图时另存新文件名（带日期），不要覆写旧图**。旧图可能已经被他粘进 wiki 并调好位置，覆写会让两边对不上；交付时说清「这张是新文件，替换还是新增你定」。
7. **不要因为「顺手重出一下发布版」就全量重生成**：他没要求的重生成等于逼他重贴一遍整篇。改什么就只给什么，其余不动。

反过来，如果他还没在 wiki 里调格式，就走本文前面的整份交付路径——先问一句「wiki 里那份你改过样式没有」，两种做法完全不同。

## 交付边界

- 转换是**格式层动作，不许改内容**。文字、编号、规则语义一字不动。
- **改结构前先确认**：拆表格、拆章节、改条目编号方式都属于改变阅读形态，先问一句再动手（见上文「结构性改写必须先经用户同意」）。
- 保留一份「引用版」（md + images/）在仓库维护，wiki 版只在交付时生成——两份结构不同是正常的，别回头用 wiki 版覆盖引用版。
- **发布版（base64）已默认停用**：用户现在的做法是自己把截图上传到 wiki，我方只维护源稿 + 截图文件夹。若他明确要求某次要发整份发布版，才从主稿整体重生成并核版本号、章节数、`<br>` 数、base64 图数四项一致。
- **不要因为「顺手重出一下发布版」就全量重生成**：他没要求的重生成等于逼他重贴一遍整篇，而且会让他在 wiki 上已经调好的图片位置与新版脱节。改什么就只给什么，其余不动。
- **旧版发布版文件头的「已过时」标注要随重生成一起清掉**，别让新文件还挂着旧警告。
- 图片粘过去后通常还需手动上传附件或插附件宏，这一步提前告知用户，别让它以为粘贴就完整了。
