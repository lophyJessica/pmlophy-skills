# 原型复刻保真纪律

复刻存量系统页面时，原型的第一职责是**呈现真实环境长什么样**。任何"我觉得应该这样"的设计都会在下一次评审或用户点检时变成返工，而返工比新建贵——新建是加法，返工要先拆错、再重对一遍底。

## 一、真源顺序（不可颠倒）

1. **真实运行系统的 DOM 文本**——唯一权威。让能开浏览器的 executor（Cursor 内置浏览器等）读 `innerText` / accessibility 树，抄原文。
2. **生产前端源码**——线上页面拿不到时的次选，只读参照。
3. **PRD / Demo 演示块 / 历史审计文档**——只用于判断业务口径，**不能当页面形态依据**。
4. **自己的记忆与推断**——只能用来提问，不能写成结论。

**取证一律靠点界面，不得拼路由（用户 2026-11-03 明确要求）。** 顺序：点左侧菜单进模块 → 在页面内点按钮/链接/页签 → 用内容变化判断到了哪一页。禁止改地址栏、禁止改 iframe src 直达目标页。两个典型翻车：① 嵌入型后台（iframe 内 SPA）**外层地址栏不随内部页面切换**，列表进新建后 URL 不变，若拿地址栏当判据就会误判“进不去”，随后去试 `/new`、`/add` 必然 404；② 裸坐标点击在跨域 iframe 里容易点到外层壳或 div，改用 CDP 按按钮文案定位实际元素再点（Element 体系用 `button.el-button` 文案定位可靠）。

**环境站点必须分清、不得互相顶替。** 同一个系统常有生产站、测试站、内销版、外销版，域名只差 `.com` / `.com.cn` 就会落到另一套系统上。写指令前先确认这次要对齐的是哪个站，取证的每条结论都标来源站。测试站的结论不能当生产依据，内销版的结论不能当外销依据。

## 二、页面形态：线上没有的，一个都不加

原型页面上只允许出现真实环境本来就有的东西。以下是**默认禁止**（除非已取证确认线上也有）：

- 辅助说明句、段落、提示条（例如"标签筛选与行为筛选同时生效：……"）
- 待确认标记、"待确认方案"、"留待下一步"、TODO 类过程性文案
- 字段下方的小字注（"系统生成，只读""DMP 维护"等）——只读用置灰表达，不加文字
- 状态徽标、计数角标、"新增"标记（用户未点名要的一律不加）
- tooltip / 悬浮提示 / 折叠说明

**说明、规则、待确认、字段读写性全部进原型标注或评审 PRD 的待确认段，不进页面。** 页面和标注是两层东西：页面给人看长相，标注给人看逻辑。写进页面会同时污染真实性和标注体系，评审也分不清哪句是系统原文、哪句是产品注释。

**文案照抄真实环境，哪怕语义怪。** 线上区块标题用了复用组件的错名字，原型也用同一个名字——"真实环境怎么写就怎么写"优先于"这样写更合理"。

用户口述的字段名、占位符、选项值同样可能记偏（"全部使用" vs "全量使用"），交付前回线上对一遍。

## 三、截图不做字段级取证

截图只能判断版式（谁在左谁在右、分几栏、区块先后）。**字段名、列名、数量、上限、占位符一律走 DOM。** 视觉模型会凭版式"补全"不存在的字段——把裁切边缘读成"组合计划""频控明细"这类线上根本没有的词，且语气笃定。一旦这种结论进了指令，executor 会照做，返工成本翻几倍。

需要判断视觉形态时，优先看区域裁剪图而不是整张长截图；长截图分辨率摊薄后错读率更高。

**仓库里已归档的真实系统整页截图（验收截图目录）是另一种情况**：比手机翻拍清楚得多，可以读出列名、筛选项、页签名、空态文案、分页形态，用来给 executor 写形态说明。**但它只能当基线，不能当现状**——归档截图往往比今天的环境旧几天，而恰恰是最容易做错的细节会变：实测两张归档图各漏一处，一张漏掉表格最左侧无列名的展开列和分页的每页条数下拉，另一张把 9 列读成 8 列（漏了「库存」）。硬规矩：**先现场点开核一遍再动手**，现场与归档不一致时以现场为准；只拿归档截图开工，等于把上周的形态当今天的需求。两条其余约束照旧：①指令里写明「截图仅作辅助，以文字条目为准」，把读到的形态逐条文字化，不让 executor 自己看图；②读不出来的部分（典型是空数据下的操作列按钮、下拉枚举）标“无取证”，在指令里要求只渲染占位符，不许 executor 自行发明。

## 四、写指令前的自检（做不到就不发指令）

- 页面每一处形态，有对应取证吗？没有的，在指令里明写 `未取证`，不填内容、也不让 executor 猜。
- 引用的文案是从 DOM 抄的原文，还是凭记忆写的？凭记忆的一律回去核。
- 线上有 / 线上无 分类清楚了吗？线上有的以线上为准；线上没有的本期新建功能，参考同类系统形态，但**与定稿冲突处以定稿为准**。
- 用户口述与取证冲突时，先报冲突再动手，不自行选一个。
- 用户已经明确拍过的口径，线上取证**不自动取胜**。取证只证明线上怎么长，不证明本期要怎么定；两者冲突时把差异报给用户拍，不拿取证去覆盖已定稿的口径。
- 指令里把本次要对齐的站 URL 原样写进去，不让 executor 自己选站。

## 五、多轮返工的唯一止损办法

不要一轮一轮去线上抓页面（单轮成本高、容易卡额度）。改成**按需抓、抓完沉淀**：每轮只取当前要改的那一页，立刻写进仓库里同一份取证文档（按页分节、标注来源站与取证时间），以后所有复刻、回写、指令都以这份文档为准，不再重复抓。

取证时该抄什么，见 `references/线上取证清单.md`。

原型定稿后回写 PRD 时，哪些文档必须一起动，见 `references/PRD回写连带检查.md`。

## 六、验收

- 不认 executor 自报"已完成/已对齐"，拉下来按代码逐项核；判据只认 `src` 与线上 DOM，不认历史审计文档的记述。
- 用户是视障或不便看图时，验收反馈一律用文字描述页面元素、默认值、切换后的实际值，不要求他看图。
- 点检"原型是否与 PRD 一致"时，基准是定稿的 PRD 套件（业务PRD + 功能清单 + 字段清单），不是还在旧口径的评审 PRD；两边冲突逐条列出让用户拍，不替他选。

**审计要由没参与实现的一方做**，实现方自审只会顺着自己的实现说"符合"。逐条给三态，缺证据不算通过：

1. 一致——附文件行号证据；
2. 不一致——写清文档怎么要求、代码实际怎么做、差在哪个文件哪一行；
3. 文档未覆盖——分"原型做了文档没写"与"文档写了原型没做"两类。

另必扫一类：**文档与线上都没有、但原型里有**的自创内容，这是自创的唯一可靠检出方式，只能逐页扫，不靠记忆。禁止接受"基本一致""总体符合"这类无证据结论。审计不通过，不放行到评审材料。

**逻辑对但点不出来，等于没做完。** 原型里任何“按系统字典做过滤/收敛”的功能（按组织层级收敛门店、按国家码过滤行为、按租户过滤列表），都要当场核一遍 **mock 数据的取值是否落在字典的真实取值域内**。典型死法：mock 用的是另一套系统抄来的数据（国内站的国家、内销的租户名），而字典只含本系统的取值，于是过滤后候选集直接为空——代码写得没错，页面上却什么都看不到，审计和用户都无法验收。

修复优先级：**改 mock 数据，不改过滤逻辑，也不扩字典**（往字典里补一个本系统根本不存在的取值，等于造假）。改 mock 时保持行数与各列取值分布不变（授权态、删除态、有值/无值、脱敏格式都要原样），只改落在字典外的那几列。

**字典本身也必须只有一个定义处。** 上面讲的是 mock 越出字典域，反面同样常见：字典自己分叉——同一个下拉的候选值在多个文件里各抄一份，改了用户截图上的那一处，别的入口照样冒出错误取值（外销原型里同一个国家列表就同时存在五份：渠道选择、标签管理、计划 mock、行为 mock、权限中心组织树）。排查「选项里出现了不该有的值」时，**第一步是全仓 grep 这个值的字面量**，把所有硬编码列表一次性列出来，而不是只改报出来的那一个下拉：

```bash
grep -rn "'中国'\|'印尼'\|巴布亚新几内亚" --include=*.ts --include=*.tsx src
```

修法固定两步：①在字典文件里收口成两个导出（按上级维度取、取全部），调用方一律引用，不再各自 flatMap 或写死数组；②改完再全仓扫一遍禁止值，逐条区分「本次该清」与「属于另一套数据源」（组织架构 mock、模板/券默认值等）——后者单独列清单报给用户拍，不顺手一起改。

**表单默认值最容易漏。** `country: '中国'` 这类切始化默认值不在「下拉候选」里，扫候选值扫不到，要单独 grep 字段切始化处（`emptyRow`、`INITIAL_FORM`、语言版本映射）。默认值同样只能取字典内的值，取不到就留空必填，不得编造——外销场景里区号、国家码这类字典没收录的字段，宁可留空进待确认清单，也不自己填一个看起来合理的值。

## 七、模块闭环：先数菜单叶子，再谈完成

被问到「这块是不是还没完成 / 我没看到闭环结果」时，不要凭会话记忆回答，也不要拿“页面文件在不在”当判据。按菜单配置数叶子，逐项核：

1. 读菜单配置文件（`config/menus.ts` 之类），列出该模块全部叶子项及其 `implemented` 标记；
2. 对每个 `implemented: true` 的项，确认页面源文件与路由同时存在（只有标记没路由、只有路由没页面，都算没做完）；
3. 输出「已做 N / 共 M + 剩余项清单」，不写“基本完成”“大致对齐”。

**页面做完 ≠ 模块闭环。** 一条功能要同时满足六项才算闭环，缺一项即未闭环：

1. 页面实现——路由 + 菜单 `implemented: true` + 能打开；
2. 字段清单覆盖——详细稿 TSV 有对应行（只留 TSV，不留 md 双份）；
3. 交付 PRD 对应章节——页面内容 / 交互说明 / 业务规则 / 待确认，逐条编号；
4. 原型标注——交互与规则，跟 PRD 走；
5. 流程图与页面对得上——外部系统引用类页面（服务宝这类中台引用的），流程图里的参与方与数据来源要能在页面上对应；
6. 实测开页——线上原型能打开，不只本地 dev 跑通。

汇报闭环状态时按这六项列缺项，不按页面数量报——用户问的是闭环，答“还剩两个页面”等于答错了题。用户手上没有这份清单时，主动提一次要不要挂上看板逐条对照。

## 八、分工与指令交付

- **UI 复刻/造型类改动，优先让用户自己带 Cursor 对话做。** 用户手上有浏览器登录态、有截图、能即时纠偏，一轮对话就能改到位；助手隔一层转述只会失真，往往要来回好几轮。助手不写工序级别的改 UI 指令。
- **助手留的活**：业务口径判断、取证结论归档、出文档回写指令、独立核验、对外材料。**文档改动（PRD / 功能清单 / 字段清单 / 需求表）一律出指令交给 executor 执行，助手不自己改文件、更不自己 commit+push**——判断和执行混在一双手上，出错时分不清是口径判错还是抄错。用户说"原型差不多了，你去点检"时才动验收。
- 确需下发指令时，**多条改动合并成一条可直接粘贴的指令**，不拆成几条分次发；指令正文放在代码块里方便整段复制，说明文字放块外。
- 用户自己改完的代码也可能留尾巴（口径只改一半、只加计数没改交互），仍然要拉下来逐项核，不能因为他自己动过手就假定没问题。
