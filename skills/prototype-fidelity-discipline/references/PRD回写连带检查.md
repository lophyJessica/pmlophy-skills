# 单点变更的 PRD 连带检查

改动一个功能点或一个字段口径时，PRD 套件里往往有五处要一起动。只改一处，下一轮对账就会把"文档与原型不一致"当成新问题重新报一次。

## 功能点增删（含"移出本期又恢复"这类翻案）

按顺序全部检查：

1. **功能清单**：条目本身 + 总数（"共 N 条"）+ 分组小计 + 末尾「功能点对应关系」表
2. **功能清单版本记录与变更日志**：写清这版做了什么调整，翻案的写清"恢复"及新形态
3. **业务PRD 范围对照表**：旧版/新版那一行改成当前口径，并标注是哪一版恢复的
4. **业务PRD「本期做」**：没条目的补一条
5. **业务PRD「本期不做」与「职责边界」表**：从整块不做收窄为"只不做哪一部分"，职责改成分工句式（我方做什么 / 对方做什么），不留"不负责"这种一刀切

## 字段口径变更

1. **字段清单详细稿（TSV）**：字段来源（用户输入 / 系统生成 / 外部同步）+ 取值说明两列同时改，只改一列等于没改
2. **业务PRD 对应功能节**：字段来源与可编辑性句式
3. **交互说明**：谁填、什么时候填、能不能改

## 交互规则变更

功能清单里的关系层级要写全三层，漏一层就会出现两套理解：

- 筛选块之间（标签块 ↔ 行为块）：且 / 或 / 非
- 块内条件组之间：且 / 或 / 非
- 组内条件之间：只有且 / 或，没有非

写清"块""组""条件"分别指什么。标签与行为的粒度不同（一个标签就是一个属性；一个行为带多个属性列），不要用同一句"一组一个 X"盖两种对象。

## 验收

改完做一次反向验证：拿原型实际形态反向对文档，确认每一条都能在两边找到对应；与前一版对比看 diff，不要把自己刚写的内容读回来跟原文比。
