# 内网数据只读抓取（Cursor @Browser）

助手访问不了公司内网系统，只能让用户公司电脑上的 Cursor 用内置浏览器**只读**抓取，结果回传（写本地文件 + 聊天里贴精简清单）。本 skill 管这一类活的指令写法、校验方式和对账口径。

**取证就走 Cursor 内置浏览器，不要为内网活去配别的浏览器 agent**：内置浏览器复用 Cursor 里已登录的会话，零安装、零配置。给别的 agent（反重力等）配 ego lite 这类浏览器 skill 是一条独立的技术债——skill 目录位置、frontmatter、各 agent 自己的加载机制都要逐个趟，且对「打开内网页面读 DOM」这件事没有任何额外帮助。评估一个取活方案时先问：它比内置浏览器多解决了什么？答不出来就别绕。

## 先同步、再深挖：需求池类任务的链式取数

「同步在线表 → 在同步结果里圈定子集 → 逐条点开关联链接深挖正文」是需求池类任务的标准链路。写指令时的关键点：

1. **同步与深挖是两条独立管道，分别写红红线**：同步段防“用旧快照补新缺口”（当前没有的只许记缺），深挖段防“漏掉嵌套内容”（正文里内嵌图片和超链接是独立产物，不打开就丢）。
2. **圈定范围必须显式排除项**：凡排除某条需求（如属上一期的不在本次范围），要写成命名的排除条目并在红线重申一条「不得把排除项抓成范围内」；圈定结果单独停一道 checkpoint 交人确认「没漏没多」再放量。
3. **链接钻取写死深度上限 + 去重**：正文里可能嵌套链接，逐层打开最长两层、同一链接不重复打开，防死循环与重复抓取。连不通的链接报 URL + 失败原因，不许静默跳过。
4. **先查本地已有材料再定本次新增量**：之前只抓过中心页正文、没打开过内嵌图片/链接的，本次新增的就是这些深层内容——指令里写清“哪些已抓过、哪些是本轮新增量”，agent 才不会重复劳动或偷想拿旧产物顶数。既有材料只作“差异界定”用，内容本身仍以在线为准重抓。

## 局部同步与状态过滤（增量更新的轻量姿势）

重抓整张几百行的大表既慢又容易在翻页链上出错，多数迭代场景只需要一部分。两种轻量策略，写指令前问清用户要哪种：

- **行号窗口同步**：只同步在线表顶部活跃区。新需求都排最前面，顶部就是活跃区；但「行号 ≤N」这个窗口在两次抓取之间会漂移——在线表可能加了表头行、顶部插了新需求，同一批内容的行号整体后移。所以给 agent 的窗口指令必须带一道 **checkpoint：报行号规律（起始行/是否跳号/最大行号）+「旧基线锚点行现在落到哪一行」**，由人在几个口径里拍板（按当前物理行号截 N 条 / 按旧基线对齐漂移后的范围 / 其他），不要让 agent 自己猜。
- **合并键不用行号**：行号是会漂移的物理位置，两次抓取之间必然变。合并回本地时按**稳定的业务键**匹配（需求名称 + 关联链接、单号、唯一编号，对账用单号优先于名称），物理行号只保留作展示列、不作匹配键。同条原则：本地 TSV 里自加的辅助列（如导出时写的「行号」列）要明确告诉 agent「这列是本地加的，在线没有」，否则它会拿别的内容列硬套或报结构错误。
- **按状态圈深挖范围**：状态列（K 列）为「需求上线 / 需求拒绝」这类终态的条目正文不再变化，深挖只圈非终态的活跃条目——量大时这是最大的减量项。圈定清单单独停一道 checkpoint，排除项（如上一期已单独立档的需求）要单独点名。

## 短链重定向到同一中心页：先探落点再分段抓

行内链接（`vapd.vivo.xyz/s/xxx` 这类短链）可能**全部重定向到同一个母需求单的不同视图/锚点**，而不是各自独立页面。指令里必须写两步，不许直接开抓：

1. 逐条点开，先报“实际落到哪个页面/URL”交人确认。若多条落到同一中心页，**中心页只抓一次**（头部/公共区不重复抓），再按各条的视图/锚点位置分别转录专属正文段。
2. 直接开抓的代价：同一页重复七遍、后续跟踪分不清是哪一条的记录。

## 与用户的分工（不变，硬规矩）

用户明确要求「减少 git 操作频次，防止公司监控」。所以：

| 事 | 谁做 | 走哪 |
|---|---|---|
| 抓取 / 只读 | 用户公司电脑 Cursor | 只读，不产生 git 动作 |
| 指令、分析、方案 | 助手 | 聊天框直接发，不发文件 |
| 落文件、push | 助手（VPS→GitHub） | 用户不参与，公司网络看不到 push 记录 |

## 翻页抓取的必做防护（2026-10-23 实测踩坑）

**症状**：样品统计出「大量重复行」，重复行号呈**固定间隔（等于每页条数，如 100）**、且重复行的其他字段完全相同。真因是**翻页后表格尚未刷新就读取了上一页的数据**，不是业务数据重复。

**必做三条**（写抓取指令时直接写进去）：
1. **翻页后等表格刷新再读**：先等 loading 消失，并校验「本页首行 ≠ 上一页首行」；不满足就重试，最多 N 次。
2. **每页存首行/末行指纹**：落盘时附带页码 + 首行/末行哈希，事后可快速查“哪两页内容相同”。
3. **重复行的自检口径**：抓完后先跑一遍「重复行的行号间隔是不是每页条数的倍数」——是，就判定为抓取误差，**数据作废重抓，不得拿去写业务结论**（曾据此阻止了一次错误的重复率结论）。

**结论口径纪律**：样品里出现的“跨账号重复”例子必须**回线上逐一定位复现**才能当证据（本次 3 个例子全部未复现）——未复现的就写“不能作为证据”。

## canvas 渲染的在线表格（WPS/类在线文档）：三条路按顺序探

部分在线表格（WPS 等）把单元格**画在 canvas 上**，DOM 里读不到全文——拦路的是它的渲染方式，不是权限。可行路线三条，按成本从低到高探：

1. **iframe 内的 WPS JSAPI**（agent 可程序化用）：WPS 在线表格的 iframe 里常挂有 `WPSOpenApi` / `EtApplication` 对象，`Range(...).Value2`、`GetCell(row,col)`、`ActiveSheet` 等能直接读单元格文本（含 canvas 渲染的表），比人肉剪贴板顺。先 `Object.keys` 摸 API 形状再批量读；注意方法签名与印象可能不一致（如 GetCell 要数字参数）。大区域一次读会截断，分段读再拼，或先落 TemporaryFile 再整体读。
2. **剪贴板**（用户一秒能做的）：先用名称框/Ctrl+End 确定真实范围（如 `A1:I165`，别信光标所在位置），整块选中 → Ctrl+C，粘进记事本（列间自动是 Tab、行间是换行，存成 .txt 就是 TSV）或直接粘进聊天框。**能两秒解决就别上脚本**——「选中复制、粘到记事本」这步用户自己就能做，助手不用写指令。拷完自检：行数对得上、首尾各抽一行核对、**单元格内含换行会把一行拆成两行**（入库前转义或替换成空格）。
3. **导出按钮**：目标表有导出按钮 → 优先导出（最省、不易漏行）。

判断顺序：JSAPI 探得到 → 程序化读；探不到但用户在场 → 剪贴板；有导出 → 导出；都不行才逐屏读（并预期数据不完整，必须标注）。**不要一上来就写「读不出 canvas，请用户导出」**——用户会反问「直接在线抓就行了啊」。

## BI 看板取数：日期靠顶栏筛选器，不靠 URL 参数

BI 看板（`bi-xxx/dashboard/3719` 这类）的 KPI 卡片和图表常是 Canvas 渲染，点格子改不动，但**不代表整页都动不了**——真正的日期筛选器在顶栏，是普通 DOM 输入框 + 确认按钮。

**先分清三类区域，判断“哪能动”**：

1. 顶栏筛选器（战区 / 国家 / 计划 / 发送日期）：普通表单元素，可输入可确认——日期区间就从这里改。
2. KPI 卡片区：Canvas，只读，改不了也不用改。
3. 明细表：DOM 里没有 `<table>` 就说明这张看板只给汇总，压根没有逐行明细，别指望它拆到国家。

**URL 参数通常无效，别先花时间试**：实测 `?startDate=&endDate=`、`?beginDate=`、`?dateRange=`、`?start_time=` 四组全不生效——参数留在地址栏、页面不报错、KPI 和筛选文案一个没变，日期存在前端状态里不进 URL。**正确做法是在顶栏筛选器填起止日期后点确认，等数据刷新**。

**默认窗口是大陷阱：多数看板默认「最近 30 天」而不是全周期累计**。实测同一张富媒体看板，默认区间发送人数 9707 万，改成半年区间后变成 7.02 亿——差一个数量级。**报数字前先报「页面当前显示的时间范围」**，否则拿 30 天数字去填「累计」口径的报表。

**改完日期必须报改前／改后两组 KPI 对照**：数字没变就说明筛选没生效（没点确认，或该筛选不影响这张卡片），不能默认成功。

**系统里没有的维度要当场判死，不要让 agent 反复找**：实测要「各国 × 渠道开通状态」矩阵，翻遍配置中心、预算规则、白名单——预算 0 条、白名单 0 条，这张表压根不存在。这时应该报「页面上无此项」。**Output format 和红线里写死：页面上没有的写「页面上无此项」，不许估算、推算、补全**——取数 agent 天然倾向“把格子填满”，不写死就一定给你编一个看起来合理的数。

**维度选项少得反常时，先查上层筛选而不是怀疑数据不存在**：国家下拉只列出 5 个国家、而线下表有 13 个时，不要立刻断言“系统里没有这些国家”。常见真因是**上一级维度（战区 / 租户 / 组织）把范围限死了**——明细行的「战区」列会直接暴露（东南亚战区的数据里自然看不到南亚国家）。查法：把战区改成全部/多选，确认后重看国家选项列表有没有变长；没变才判死，变了说明是筛选限制。拉长日期区间也会改变选项列表（选项=该区间内有数据的对象），但**拉长日期不等于放开战区**，两个要分开试。

**战区也放开后国家选项仍不变，先别判死「系统缺数据」——回去核线下表的原始范围**：实测战区从「无限制」改成两战区全选，国家列表和 KPI 一个没变，说明这张看板的数据集本身就只有这 5 国。回头看线下统计表才发现：孟加拉等国的富媒体那一行本来就写着「未上线（手机版本不支持）」、使用情况是「——」，那 5 国正是该渠道有数据的全部国家，两边严丝合缝。**「工具里少了几项」优先怀疑线下表的统计范围，而不是系统缺失**——这正是能白折腾一整轮的地方。核实方法：拿工具里的国家清单去对线下表同一渠道的非空行，数量能对上就是对的。

**明细表是 DOM 表格时优先用它，但注意分页**：KPI 卡片是 Canvas 读不到，不代表整页都是 Canvas——看板底部的明细区常是真 `<table>`，带完整字段（含国家这类 KPI 没有的维度）。区别方法：能 `querySelectorAll('tbody tr')` 拿到行就是真表。真表可以整页批量读，但**只有当前页在 DOM 里**，换页后旧行消失，要循环点分页控件逐页抓再合并。抓完用「页数 × 每页条数 ≈ 总行数」对账，中间页未必满页。

**「创建计划数」这类业务指标 BI 常常没有**：明细一行 = 一次发送任务，不是一份计划——同一计划id 会在不同日期/不同任务上出现多行。要出计划数得按 `计划id` **去重计数**，不能拿总行数顶替。找不到对应指标就报「页面上无此项」，并说明能用什么替代口径。

## 抓取类交付标准（2026-10-23 用户认可的样板，写指令直接照抄）

用户把一次抓取的 Checkpoint 当作“后续交付标准与落点重点方向”展示——以后内部抓取类任务的**小样核对阶段必须交这五项**：

1. **列名原文**（逐列编号列出，不按自己的描述预设）
2. **分页与总量**：每页条数 / 列表总条数 / 总页数 / 已覆盖页数与行数
3. **关键列索引**（第 N 列 = 什么字段，供后续按索引取数）
4. **原始值示例**（每页抽 1 行真实值，证明确实读到了数据）
5. **“确认后再继续”的显式停机请求**

**全量抓取的落点与工程规范**：

- 落盘固定到 `08-相关资料/产品审计/<主题>/`，文件名带范围（如 `账号好友关系-全量.tsv`）；
- **每页追加写入**，不要内存积完再写（防中断全丢）；同目录维护 `抓取进度.txt`（已完成页码区间 + 已写行数），支持断点续抓；
- **行数对账**：每 N 页跑一次「已写行数 == 已完成页数 × 每页条数」，不等就记页码继续；
- 每页**一次性读全页行**（页面内脚本批量取列文本），不要逐格点读；
- 先抓 N 页出**中间结论**再铺开全量——早期就有信号，比跑完几百页才知道划算。

**先确认目标页有没有导出按钮再定方案**：有导出就优先导出（最省、不易漏行）；没有才翻页抓（vivo 账号对应好友列表就没有导出，只能翻页）。注意：**不要让 agent 点导出按钮**代替只读翻页，除非用户明确同意——导出会在后台留下导出记录与文件。

## 覆盖式导入的合并纪律（把外部数据回填进系统时）

当任务从“拓数据”变成“把外部整理好的数据合并回系统并导入”（典型：翻译文档 → 导入模板 → 导入平台），先向用户/文档确认**导入是不是覆盖式**，然后按这套走：

1. **只填空缺、绝不写空**。覆盖式导入里，文件里的非空值会覆盖线上；**把已有的非空单元格写成空 = 清空线上数据**。所以合并时“保留原模板所有非空值 + 只补缺口”是唯一安全姿势。
2. **冲突单独列、不自动覆盖**。原模板已有值 ≠ 新数据时，先出「现值 vs 新值」对照，交用户拍；用户要求“用新值更新”时才覆盖。
3. **导入前备份原导出**，导入后抽查几条（新值已填、旧值没被清空）——导入常不可逆（即生效/即审核通过）。
4. **先出匹配明细再写文件**：按唯一键（key / 单号）**精确匹配**（去首尾空格），逐条标“存在 / 不存在”，不存在的按前缀归类，并列出“仅大小写/单复数/前缀不同”的成对项交用户确认——**不要用模糊匹配自行纠正 key**。
5. **不改目标的形状**：不删列、不改列名、不排序；产物另存新文件，不动原模板。列里的隐藏语义要问清（如某列看似“标签”其实是“版本号”，留空有前提条件）。
6. **自检报告**要能对账：新增条目数 / 逐列补了多少格 / 冲突清单 / 最终行数列数与原模板是否完全一致。

**“新增数量少得反常”先查三件事，别急着怀疑合并逻辑**：① 原导出是不是在**别人已导入过之后**才导的（看数据的“最近更新时间/操作人”，整批同一天同一工号 = 已导过一轮）；② 源文档是否**不止一个 sheet/页签**（只抓一个就会漏）；③ 导出时**项目/环境/筛选条件**是否选错（用“系统页面显示的总记录数 == 导出文件行数”反证）。

## 两阶段：先摸结构，再全量

在线表列数多、长文本多时，别一上来就全量抓。第一阶段只摸结构：页签名、总行列数、表头层数、逐列列名与取值类型、分区/分组标题行号、前 3 行样本（长文本截 40 字）。看完结构再决定全量抓哪几列。

## 富文本报告（BPM / 知识库正文）：文字读 iframe DOM，图片取 img 原图

内网 BPM、知识库、门户里的「上线报告」「复盘」这类页面，正文通常渲染在 **Rich Text iframe** 里，带图片与表格。抓这类要分两条管道，不要混：

1. **文字与表格**：定位正文 iframe，按只读 DOM 顺序取标题层级、段落、列表缩进；表格按行原样转 Markdown，不合并跨行、不精简列。先摸结构（章节树、段落数、表格数、图数）再全文抄，跟在线表格一个节奏。
2. **图片**：`img` 元素带 `src`，直接用当前登录态把原图逐个下载，**不要标「图表内容未取到」交差**。落 `images/` 子目录，按「章节号-序号-主题.png」命名，并报每张的像素尺寸与字节数。

**页面上点开放大不清晰 ≠ 原图不清晰**：正文里图片常按容器宽度缩略显示（如 863×427），原图分辨率往往高得多，直接从 `src` 取就能拿到清晰版。拿「页面打开也模糊」当理由放弃，会被用户一句「截图不行吗」问回来。

只在真的取不到时（401/403、地址失效、非图片格式）才写失败原因；**禁止用截图替代原图而不标注**。图片里的数据交给视觉模型逐张读，读不清的标「模糊存疑」，不当结论写。

抓完自检四项：正文段落数、表格数、图片数与页面实际一致；每张图字节数非 0；失败项逐条有原因；报告文件头记来源 URL、抓取时间、页面标题。

产物落 `08-相关资料/产品审计/<主题>/`：`<主题>-原文.md` + `images/`。

### 在线文档（vivo docs / 飞书类富文本）按「三件套」产出，不只交一份原文

这类文档通常是「章节 + 矩阵表 + 若干示意图」的混合体。只交一份 `innerText` 原文没用——大表在 `innerText` 里是**逐格换行**的，读不出矩阵结构。要求三件套：

1. **原文 md**：章节层级 + 段落 + 列表原样，长文本一字不删；文件头记来源 URL、抓取时间、文档标题。
2. **表格 Markdown（单独一份）**：每张表按行原样转，不合并跨行、不精简列。矩阵信息以这份为准，不以 innerText 为准。
3. **结构化提取 TSV**：按**使用方的分类口径**建列（例如「没按时使用 / 没使用 / 近期没有计划 / 正常使用 / 未部署」），每行必须带**逐字摘录的原文依据句 + 来源章节**，以及「页面上无此项」占位——文档没有的维度（如分季度动作）一律写这四个字，不许推演。

**分类必须由原文措辞决定，不许 agent 自己归纳。** 原文里「暂不建设」与「未上线（不用 WhatsApp）」「未上线（CMS 未对接）」性质不同：前者是**没有计划**，后者是**客观条件不具备**，混成一类会在汇报时被问「凭什么归这里」。验收时逐条对原文，把归纳过头的条目单独拆出来。

**图片抓不下来时交「手工另存清单」，不要截图冒充。** 在线文档正文图片走 iframe 内 `fetch`/canvas 常失败，这是常态而非权限问题：报出失败的张数与地址，列出命名清单让用户按 `src` 手工另存。与结论无关的示意图、头像、产品图标可以不追，但要写清哪些没抓、为什么可以不要。

**消费端铁律：聊天里的精简清单不等于数据到手。** agent 往往本地落了全量文件、聊天里只贴一段样例（实测：本地 37 行，聊天里 27 行）。拿样例去改报告/PRD/PPT，漏掉的那几行恰好就是会改变分类的原话。固定顺序：**先要全量文件 → `git pull` 拉到本地逐行核 → 列出原稿哪些对、哪些错 → 再动手改**；改完把「核过哪些、改了什么、原文依据」一并回报。跳过这一步的代价是整轮作废重来，且会被问「你为什么不等我把数据给你」。

## 指令骶架（五段式 + @Browser 首行）

**指令交付只走聊天框代码块，不落盘**：给 agent 的抓取指令一律聊天框直接贴，不写成 md 存进项目仓库——仓库是产物与资料的家，指令文件堆进去就是垃圾文档。本地参考路径可以写进指令 Context，但指令本身不进仓库。

```plaintext
@Browser <完整URL>

Context:
执行位置：公司电脑，该链接已在 Cursor 内置浏览器中打开（已登录内网），本地项目为 XXX。
任务：把这张工作表的数据完整导出为 TSV，写进项目目录 / 输出到桌面。
现有本地材料不全，以在线为准做一次全量抓取。

Request:
第一步：先读表头，不要先读数据
第二步：按实际表头逐行抓全量（翻页滚动到底）
第三步：不做任何加工（不去重、不合并、不排序、不改写、不补全）

Output format:
1. 主产物：<路径>/<文件名>.tsv —— 制表符分隔、UTF-8 无 BOM
2. 附带说明：表头确认结果 / 行数统计 / 异常记录

红线禁止:
- 全程只读，不得修改、编辑、提交在线数据
- 不得执行任何 git 操作（git add / commit / push 一律禁止）
- 不得只抓首屏、不得截断长文本、不得省略任何一列
- 不得去重或合并重复项、不得自己改列名
- 遇登录墙或权限不足立即停止并告知

Checkpoint:
1. 文字回报：页签数、实际列数、行数、与历史基准的差异、文件绝对路径与字节数
2. 在聊天里另贴一份精简清单 TSV（见下）
```

## 七条硬规则

1. **首行 `@Browser <url>`** 是触发浏览器控制的开关；Context 里再补一句「该链接已在 Cursor 内置浏览器中打开」，agent 才不会另开窗口或要求重新登录。

1b. **链接一律写成占位符交付（1021 用户要求）**：给用户的指令模板里链接位置写 `<在此粘贴已打开的目标链接>`，用户直接复制粘贴后自己填。不要让我猜内网地址、也不要写死过期地址。

2. **URL 带 `?sheetIndex=N` 时保留**。这个参数是「指定第 N 张工作表」，不是脏参数——去掉会让 agent 去翻所有页签、抓错表。要改的是措辞：把「所有工作表」改成「当前这张表（sheetIndex=N），其他页签只列名称不点开」。

3. **URL 只出现两处**（`@Browser` 后 + 「数据来源」）。写三四处会让 agent 当成多个来源。

4. **先读表头，再读数据**，并明确「以在线表实际表头为准，不要照抄下面给的历史列结构」。表头会漂移——照抄历史列名必然漏列。要求它把差异逐条列出来。

5. **红线必须显式写「禁止任何 git 操作」**。抓取全程不能产生 push 记录；写本地文件可以，git 一律不碰。

6. **点名不许截断的长文本列**（主要场景 / 需求价值 / 产品分析 / 进度跟踪之类），否则 agent 会概括成一句话。

7. **Checkpoint 分两段**：①文字回报（页签数 / 实际列数 / 行数 / 与历史基准的差异 / 文件绝对路径与字节数）；②在聊天里贴一份**精简清单 TSV**，只留重建结构必需的 10–11 列，唯一允许截断的是摘要列（如「取主要场景前 60 字」）。完整列留本地文件——全量 TSV 含长文本、上百 KB，贴聊天不现实。

## 需求单正文抓取的盲区：正文区可能藏在 iframe 或折叠点里

VAPD 这类需求管理平台是微前端外壳 + iframe 架构：主文档 `body` 几乎为空，实际内容在第一个内层 iframe 的子域页面里。配正文抓取指令前先让它探测一轮：主文档是否为空、内层 iframe 的数量与实际 URL。确认后**直接打开内层 URL 再抓**，在外壳主页面上只会抓到空白；抓不到正文时，先判断是「外层空」还是「确实没有内容」，不许两种情况混为一句「正文为空」。

三个容易丢内容的点，写抓取指令时逐条写死：
- **正文可能有折叠点**：「展示更多...」折叠区块要点开展开后再重新读取全文，落盘后验一次没有折叠态残留。
- **动态 / 状态变更 tab 不在正文流里**：要单独点开才见得到；谁在何时从什么状态改成什么状态逐条存——改名、优先级提升这类变更，正是后续做需求分析时的关键信号。
- **评论区通常为空也不许跳过记录**：写了「页面上无评论」才能让后台的人知道这区是被查过而不是被忽略。

## 需求池拆单后的父子结构：旧参考只覆盖母单

同步需求池时用「需求名称 + 链接」做匹配，但**旧时点的原文材料可能是在母单页面抓的**；需求池里的链接日后可能拆成独立子需求单（各自有自己的 requireId）。落点探测那一步比「打开是否成功」多报一个信息：每条链接对应的 requireId 与旧材料里的母单 requireId 是否一致。一旦发现「子单 requireId ≠ 母单」，升列为重大发现交人确认：旧参考只有原稿口径，拆单后子单里的正文才是当前真实口径，本次抓取不得拿旧参考顶数。同时在每部新档案的元信息里写好「关联母单 = <母单号（原稿）>，正文以本单为准」的注脚，后续追溯时才有入口。

## 另一类活：抓页面结构（DOM）做证据，不只截图

当任务不是「导出数据」而是「核对我方页面/复刻件与真系统是否一致」（复刻对齐、口径核对、控件文案对照）时，**截图不够**——截图只能看外观，命名、字段、条件结构看不到。做法：同样用 @Browser 打开目标页，**把目标区块的 DOM 也抓下来当证据**。

要抓的：区块容器标签与 class / data-* 属性；每个分组的标题文案；控件类型（input/select/checkbox/radio/button）、占位符、默认值、必填标记；**下拉展开后的全部选项文案与 value**；按钮文案与禁用状态；「已选 N 个 / 清空」这类状态文案。产物两份：精简 HTML（只留该区块子树）+ 结构化整理稿（.md）。

四条必写进指令：

1. **证据顶层是「源码 + DOM + 截图」三条，缺一标「单证据·待核」**，不得写成完成；源码与页面冲突时**以源码为准**，冲突另列一节。
2. **锁定语言与地区再比对**：文案随右上角语言/地区设置变——先记录当前设置，两端在同一设置下取图取 DOM；文案不一致时先排除语言因素，再判定是对错。
3. **i18n 坑**：DOM 里可能只有国际化 key 没有中文，**key 与实际渲染文案两个都要记**。
4. **每份证据文件头部记元信息**：抓取时间 / 完整 URL（含全部 query）/ 视口宽度 / 语言与地区设置。后面追溯“这份证据是哪个页面哪个状态”全靠它。

只读边界比表格导出更严：允许查看、展开下拉这类无副作用交互；**严禁点 保存 / 提交 / 发布**，严禁修改已有记录的字段；优先打开**已有记录**进入查看/编辑态，而不是走完整新建流程。

### 什么时候别派 DOM 取证：要「整块形态 + 默认值 + 全部枚举」时改由用户口述

单点取证 agent 能做（这个按钮叫什么、这列有哪些取值）；**整块形态取证反复做不准**——一个筛选区块里默认几个组、每组的默认条件与判定值、快捷条件控件到底是独立控件还是预置值、有没有折叠控件、组间关系从第几组开始出现：这类活每次只抓回其中几项，漏掉的自己也不知道，报告看着齐全，拿它改代码仍与真实页面对不上。

判据：指令里出现「把这一块的所有控件、默认值、全部枚举都抓回来」就属于这一类，**不要派**。改法：让用户自己打开页面按清单口述，他给的就是事实，直接当权威写进文档与指令；截图只用来定位版式与字段位置，不做字段级结论。根本原因：缺项无法自检——agent 不知道自己漏了什么，你也无法从它的报告里看出来，只会一轮轮补。

并排对比图**让 agent 用脚本拼**（同区块左右拼、高度对齐、固定视口）——不要指望用户手工拼：滚动长截图高度对不齐，用户会直接说做不到。

## 菜单 / 信息架构：只认实时 DOM，不认自己仓库里的结构

菜单层级、分组归属、页面挂在哪一级——这类事实**必须现场取 DOM**，不能从任何现成文档或代码推导。原型仓库的 `menus.ts`、历史盘点 md、上一轮 agent 的报告都可能是错的、或已因有误被删；拿它们当基准去下指令，改完会发现白名单、权限中心、Demo 这些位置全错，且下游（资源表、路由、页面归属）跟着整套返工。给 agent 下结构改动指令前，先问自己：这个结构的证据是**今天在真系统里看到的**，还是**从我自己产物里读出来的**？后者不算证据。

抓法：定位菜单容器（如 `#mainMenu`）与顶部导航容器，按元素语义分层——可展开分组通常是带 `aria-haspopup=true` 的标题节点且**自身没有 href**（不是路由项），叶子是独立可点节点。两类要分开报，否则会把分组标题当菜单项。

必问清楚的五件事，缺一条就可能白改：

1. **顶部一级导航的完整顺序**（不只是有哪些，还要顺序——位置错就要整排顺移）。
2. **每个一级下的分组数 + 每组的叶子及顺序**，用缩进表示层级。
3. **分组标题本身是否可点击**、是否对应路由，还是纯展开标题。
4. **明确回答「有 / 没有」**：问「某模块下有没有白名单分组」时，要能直接答「没有」并指出同名叶子实际挂在别处。只报「看到了什么」而不回答否定命题，等于没取到证。
5. **一次抓全所有一级 tab，不要只抓当前 tab**：切换后有约 1s 仍显示上一模块菜单的残留，要等 DOM 稳定再读。

菜单接口往往不可用：路由树接口（如 `menu/tree`）在页面内 `fetch` 重放多半返回 `No permission to operate`，**别把接口当唯一出路**，DOM 才是能用的证据；接口只报「曾发起过、拿不到响应体」。

**基准错了导致多轮改动后，先回滚到最后一个正确提交再重做，不要在错的基础上继续修**。定位法：`git log --oneline -- <受影响的配置文件>` 看该文件的历史，用 `git show <commit>:<path>` 逐条核对候选版本的完整结构，挑出与真系统吻合的那一版；然后 `git checkout <commit> -- <path>` 只回滚这一个文件，**不要整体 reset**——同一区间里往往还有该保留的正当改动（例如资源表改成从菜单文件程序化生成）。回滚后必须跑两项检查再交给 agent 继续：一是结构逐项对真系统对照，二是“相关页面、路由、组件文件是否还在”——菜单回滚容易误伤上一期已验收的原型（私域类页面常靠菜单 key 挂载），要显式列出菜单里的关键叶子与 `App.tsx` 里的路由、`pages/` 下的组件三重确认仍在，并确认 `git status` 只动了目标文件。

**回滚配置文件/类型定义后必须跑一次构建，不能只看结构对了就交。** 菜单文件里的模块 key 往往同时是 TS 联合类型的成员，回滚后其它文件里还在判断已被删掉的 key（`mod.key === 'config'`），编译器直接报 `TS2367: This comparison appears to be unintentional because the types ... have no overlap`——构建挂掉，用户拉下来一片红。做法：回滚后立即 `npm run build`（或项目的类型检查命令），报错就顺手改掉那处分支判断，再把构建成功的末几行附在交付里。同一提交里带上这个修，否则回滚本身就是不可用的。

**回滚菜单配置必须同时提种子版本号**：原型把菜单树镜像进浏览器本地库（IndexedDB / Dexie），靠一个版本常量（如 `RESOURCES_SEED_VERSION`）决定要不要重灌。只改 `menus.ts` 不提这个常量，页面会继续用库里的旧菜单——用户看到“还是乱的”，你却在代码里找不到错，白白多查一轮。做法：回滚菜单文件时一并把种子版本 +1，同一个提交里带上；验证时以用户刷新后的实际菜单为准，不看源码推断。

**撤本地改动时，agent 新建但未跟踪的文件不在 `git restore .` 的清除范围内。** 它只能恢复已跟踪文件，agent 新造的页面 / mock / 样式会作为 `??` 项残留。菜单回滚后这批文件往往 import 着旧菜单 key、或挂在已不存在的路由上，属于隐形雷；要显式把 `git status` 里的未跟踪项列出来，逐项问“留还是删”再动手，不要默认它们会被一并清掉。

**归属类结论必须由用户拍板，文档措辞推不出归属**：需求单里写「A 权限中心顶部增 B 菜单」这类句子，读不出模块到底驻留在哪——同一句话可以读成「模块新增到 A」也可以读成「B 的页面被 A 嵌入」。写架构归属前先问用户一句「这块的能力页面在哪边」，拿用户口径当权威写进文档；凭文档自查推导归属容易把方向写反并纸面自洽（同一会话里连错两轮的典型：把「菜单嵌入」读成「模块自营」，第一次修完又写反第二次，直到用户用「agenta只做权限管理+统一入口」的因果链才钉死）。高效问法不是问「归属是谁」，而是让用户讲「为什么这么放」——归属方向会包含在因果句里，且因果句用户一次就能给你。修文档归属时先清掉旧表述，不要在旧句子上追加补丁，否则同一文档里新旧两套口径并存。

**「对齐真系统」不等于「照抄现状」——本期设计决议优先。** 新版本会故意偏离老结构：把标签能力从权限中心搬到触达计划下与内销保持一致、合并或拆分分组、新增菜单项。这类偏离是设计决策，不是需要被纠正的偏差。动结构前先分两件事：这一处是**复刻现状**还是**本期改造**？属于本期改造的，设计文档 / 评审 PRD 才是权威，真系统只用来确认叶子页面长什么样、字段长什么样；属于复刻的，才以真系统为准。判据很硬：这个归属在 PRD 或评审稿里明确写过吗？写过就按 PRD，没写过才按真系统。把已经设计好的新结构“矫正”回老系统形态，比结构写错更严重——它推翻的是已定稿的设计决议，而且回滚会把下游（资源表、路由）一起带歪。拿不准时先问用户“这块是本期改的还是照老系统的”，一句话就能省掉一整轮返工。

**派给用户去系统里找页面的清单（截图清单 / 走查清单 / 取数清单），路径必须来自源码路由表或现场 DOM，不能写中文页面名。** 凭印象写「任务中心」「内容库」「AI 助手」这类名字，用户打开系统根本找不到，只能一条条问回来。固定做法：先在源码路由文件里 `grep` 出真实 path → 用路由的 `meta.title` 当页面名 → 两者成对写进清单（序号 / 侧别 / 路由 / 页面名 / 要截的状态 / 文件名 / 入口说明）。同时把**入口在哪**写清楚：内销导购端是 `qywx-h5`（企业微信里的 H5，真实路由形如 `/home` `/workTask` `/manager` `/customer-detail` `/customer-detail/user-dynamics` `/group` `/lead-square` `/lead-follow` `/mediahub/task` `/quick-reply` `/training`），入口在企业微信、**不在 CMS 后台菜单里**——不写这句，人会去后台翻一遍然后回来问。路由表里查不到的项整条删掉，不要留着「可能叫这个名字」的占位。

## 读截图取证：视觉识读的证据等级

截图里的内容是用来看的，但**视觉识读只能当线索，不能当验收依据**：

1. **步骤名 / 字段名 / 按钮文案必须裁出该区域放大再读**——整图一次识读会把关键字读错（历史两次把「受众筛选」读成「受众圈选」，结论直接错在根上）。拿不准就先裁图放大，或直接用源码 / DOM 去核。
1b. **代码标识符、英文 key、配置键、英文列名绝对不能用 OCR 当依据**：一个字母的差异（`guide.` vs `guides.`、`in_ID` vs `id_ID`）就是完全不同的命名空间。曾根据截图 OCR 断言“两边 key 命名空间不一致、合并会白添两套词条”，实际是 OCR 多读了一个 `s`——被全量机器比对推翻，白制造一场假警报。规则：涉 key/字段/枚举值这类**机器可读字符串**，只认机器比对结果（导出文件 / DOM / 源码），OCR 读到的一律不写进结论。

1c. **中文业务备注同样不能拿 OCR 当原文，一个字就能反义**：进度备注、审批意见这类密集文字里，「拿孟加拉作为灰度实验」被识读成「舍弃孟加拉作为灰度实验」——动词一错，整条判断反了（一个是选定试点，一个是放弃试点），据此得出的「两边表述矛盾」结论整段作废。规则：要引用**备注、意见、说明**类文字做判断时，直接请用户复制文本过来（他从在线表 Ctrl+C 就得到干净原文），图片只用来定位版式和字段位置。已经拿 OCR 结果下过结论的，回核原文后必须显式声明哪句判断作废。
2. **装饰性文字一律不引用**：水印、侧边栏 / 菜单重复项、页脚小字这类界面装饰最容易被幻觉化或错读（同一张图三次读出三个不同的水印人名；侧边栏项被重复列举十几次）。凡与结论无关的装饰文字不要写进结论；**同一张图两次识读不一致 → 该处结论作废**，改用源码 / DOM 交叉证据。
3. **用户给的截图链路要先回述再校验**：他说「图1→图2→图3」时，先把这条链路用文字复述一遍并逐项核对，对不上的当场指出（他自己也可能记反哪张是哪张）；不要让“顺着说”掩盖错位。
4. **面向视障用户的复述要结构化**：页面归属（系统/菜单/面包屑）、区块顺序、字段与取值、按钮文案、层级关系——不能只回「看到了」。他是靠这段文字“看”界面的，描述完整度就是交付质量。
5. **局部/裁切截图不能用来定布局结构**：只有左侧列表的截图，推不出“右侧没有表单”或“是单栏布局”——很可能只是没截到。**单栏 vs 双栏、有没有右侧面板、页面分几块，只能靠整页截图或 DOM 定**，拿局部图下这类结论会连累后面一整轮返工（曾据此断言真系统是单栏无表单，实际是左树右表单）。

## 取证模式的边界：只出事实，不治方案

用户说「取证 / 核对 / 搞清楚现在是怎么实现的」时，**交付物是事实，不是修复建议**。把现状说清楚就停：三层逻辑分别是什么、代码在哪里判断、条件为假时界面表现如何、哪些情况没有被区分。不要顺着写“应该怎么改”“建议下沉到哪一层”“要不要动手”——用户会直接反问「我们只是取证，又不是开发，管怎么修改干嘛」。

例外只有一个：用户明确问「能不能改 / 该怎么改」。这时先给现状，再给选项，不替他定实现方案。

### 取证「某功能是不是被隐藏了」时，要看渲染层级，不是看控件还在不在

「入口还在」不等于「功能没被拦」。前端常见把同一份判断挂在不同层级：底部导航容器在 `v-if` **外面**（永远渲染），内容容器在 `v-if` **里面**（条件满足才渲染）。只看 Tab 图标还在就回答「Tab 没隐藏」，会漏掉真正的事实——**四个 Tab 的内容区全被同一个判断拦掉**，表现是任务、列表、个人中心一起空白，而不是只有那一个 Tab 没数据。

取证时必须分开回答三个问题：① 入口从哪里渲染、受什么条件约束；② 内容区从哪里渲染、受什么条件约束；③ 被拦时展示的是哪个层级的提示文案（页面级「未分配」还是列表级「暂无数据」）。这三问混在一起回答，结论会错一层，而下一次讨论要重新证一遍。

### 门禁逻辑写成三层，并确认代码有没有把它们混成一层

当一个 App 同时存在「客户端鉴权」「身份鉴权」「业务数据分配」三件事时，**它们是三个独立判断，不能用一个代替另外两个**。判断依据往往长得像：客户端 token 有效、员工编码有效、账号列表接口非空——但最后一层只能决定「某功能入口显不显示」，不该当成前两层的门。代码里把三层写成一个 `if` 的典型信号：某个接口返回空数组，整个页面内容就被替换成一句空态，连带本来与这份数据无关的功能一起不可用。

取证时要输出：三层各自的判断字段是什么、同一个字段被几处消费、以及「某层为假时影响了哪些范围」——是单页、单 Tab，还是整块内容区。

### 底部导航的顺序与文案以真机截图为准

路由的 `name`、语言包的 key、仓库里的目录名都不等于界面上显示的名字和顺序（实测某 Tab 路由叫 `userManager`、需求口头叫「用户管理」，真机底部显示的是「用户」；四个 Tab 在版本迭代里新增了一个并插在第二位，而按代码目录顺序理解会排到最后）。有真机截图时，**拿截图目测顺序 + 文案，再回头对代码**，不要用代码结构反推界面。

## 抓回来的数据怎么归档（月度台账）

报表类抓取不是一次性动作，要按时间点存成台账，后续做年度汇总才不用重抓。归档纪律跟抓取本身一样重要：

- **一个时点一个文件，文件名带截止日期**（如 `2026年1015.tsv`），不用 `latest` / `final` 这种会被覆盖的名字。
- **历史时点的文件不再修改**，新月份只新增文件。改历史 = 趋势分析失去可信度，也没法证明当时引用的是哪个版本。
- **原始明细和人工汇总分开命名，不要混一个文件**：从工具逐行抓的明细（`BI富媒体明细-20260108至20261015.tsv`）是机器可复算的底稿；从在线表复制的多维快照（`2026年1015.tsv`）是人工口径的成品。两者覆盖的维度和可信度不同，合并就分不清哪个数能重算。
## 取数脚本单独入库**（`09-脚本工具/bi_scrape_*.py`），与产物同仓库——台账每月重跑靠它，换人接手能复现。临时探针脚本和中间 JSON 不入库。

## 全量快照合并的三条收尾纪律

把旧快照拍快车进新快照、转成全量（一部分在线重抓、一部分沿用旧值）时：

1. **双版本 TSV 并存是有意的形态，不要删旧**：旧快照（如 `需求池-20261019.tsv`）是历史基准，用来对账；新快照是当前权威。合并完成后，产物直接覆盖同名新日期文件而不是汇总成一个「latest」——见上一节台账纪律。合并说明写进导出说明里，没直措哪个段落是重抓、哪个是沿用、行数净增多少，后来人才能分清两段的时效性。
2. **给大文件加「行性质」分类列再做统计**：在线表里常混着无名称的占位行、未填行——不望图一眼就把总行数当需求条数，报表一定虚。在 TSV 末尾加一列「行性质」（有效需求 / 占位行），判定写在导出说明里；统计和后续分析只筛「有效需求」行。同名同链接的双行在线池本身就存在（同一条需求拆两个子场景录入），这种是**在线原生多行，保留不动并在说明里注明**；不要和同步误差的重复行混为一谈。防重叠校验报出来的重叠先判断「在线源本身就是这样」还是「同步过程造出来的」，前者保留并注记，后者才删。
3. **大 xlsx 源文件入库后有体积天花板**：GitHub 超过 50MB 出警告、100MB 硬禁止，而且 git 历史每版都保留全量——每次同步都会堆一份几十 MB。ubectl源头 xlsx 只在首次入库，后续同步只更新 TSV、不再重传 xlsx（除非结构级变化）；要彻底避免就用 Git LFS。推上 GitHub 后若收到 GH001 大文件警告，说明已经在限线下——当轮还能推，但要在下一轮里做出 LFS 或移出仓库的决定，不要当成无关警告忽略。

### 任务结束必做：清理本轮临时脚本

agent 在项目目录里写的临时探测脚本、合并脚本、中间 JSON、调试日志，任务收尾时**必须盘点并删除**，不要留在仓库里变垃圾。动作：列一批清单（临时产物 / 用户或历史的既有文件），只删前者；被 git 跟踪过的临时文件还要 `git rm` 并纳入收尾提交。这个动作写进任务的收尾检查，而不是等用户提。
- **多维度多时点取数先验单点**：13 国 × 4 渠道 × 2 时点 = 上百次查询，先选一个国家一个渠道试一次，确认能取到且格式可用，再决定逐点跑还是**取全量后本地按日期切片**。后者往往只跑一次：抓完整明细（含发送日期列）回本地，任意截止日的累计都在本地算出来。

## 抓回来先验三项

1. **字段数一致性**：`awk -F'\t' '{print NF}' file.tsv | sort -n | uniq -c` 应只输出一个数（如 20 = 1 列行号 + 19 列数据）。出现多个数说明某些单元格里混进了制表符。
2. **行数与历史基准对比**：agent 报的行数/非空条数若与历史清单不同，差值必须逐条解释（新增、拆分子需求、空行、行号漂移），不能一句「口径不同」放过去。
3. **跨版本对账用单号做唯一键**（VR 号/工单号等），**不要用名称**——名称里的空格、【】、标点、前缀在不同来源里都不一致，按名称前缀匹配会把大量老条目误判成「新增」。
4. **统计数字必须跑自洽校验**（见下节）——从在线表/截图抄回来的数字不验就用，错在哪里你永远不知道。

## 抄回来的统计数字：用自洽关系验，不要靠直觉

从在线表、截图、手工复制里拿到的指标数字，**先算一遍内部关系再入库**。运营报表里的每个比率都是自己算出来的，比率与分子分母对不上就是抄错，这是不需要外部基准的免费校验。

三条通用关系（换成你的业务同构形式）：

1. **比率回算**：阅读率 = 阅读人数 ÷ 发送成功人数，点击率 = 点击人数 ÷ 阅读人数。注意分母是哪个——同一张表里点击率可能除以阅读人数而不是发送成功人数，先拿一行已知数据反推清楚再用。
2. **分层加总**：各国家/各分组合计应等于渠道总数。**汇总值能从系统另拿一处（如 BI 的渠道 KPI）时，两边必须对得上**——实测各国富媒体发送人数合计 702,122,559 与 BI 渠道卡片一字不差，这一次对账同时反向修正了一个少一位数的错值。
3. **量级与单调性**：发送人数 ≥ 发送成功人数 ≥ 阅读人数，任何一条逆序就是错。

**三个高频错型，看到就停下来核**：

- **两个不同对象出现了完全相同的长数字**——手工复制或提取稿整理时行/列串位，不是巧合。
- **某个数字位数跟同行其他项差一位**、或千分位位置异常（如 `5,7005492`）。**但先还原再判定**：把 `5,7005492` 还原成 `57,005,492` 之后套「发送 ≥ 成功 ≥ 阅读」再算一遍，成立就说明只是分隔符丢了、数据本身没问题。直接把错位值当兵值去套逻辑，会得出「成功数大于发送数、数据错」的假警报，并被用户当场纠正。
- **同一字段在两份产物里归属反了（串列）**：结构化提取 TSV 里的「马来的授权数」可能其实是印尼的。判法：不 TSV 里对，而是回**表格还原稿的列头顺序**逐列对齐，再拿该数字 grep 原文行，看它前面紧跟的是哪一国。**两个来源冲突时永远以原文表格列序为准**，TSV 只当作已归类的线索。实测一份 37 行提取稿把马来与印尼的私域授权数据整段反了，而原文表格里写得清清楚楚。

**口径不能混用：某一项改了统计范围，汇总必须同步重算**。同一份材料里，分项渠道按“明细口径”（如邮件只算实际有数据的 5 国）更新了，而总合计还停在旧的“手工矩阵口径”（只有 3 国）——两个数各自都“有据可依”，但放在同一页里报告自相矛盾，对外发出去就是硬伤。规则：汇总数字必须与各分项用**同一个数据源、同一套筛选**重新加总，不能拿两处现成数字直接相加；改完把「分项逐项 → 合计」的计算过程写进交付，并标明数据源文件。发现两个口径都存在时，向用户挑明差异量级再定用哪个，不要默默选一个。

发现疑点后**不要自己猜着改**：把「原值 / 按比率反推的应有值 / 判定理由」三条列给用户，让他回在线表看一眼。改数这件事永远归数据所有者。

## 常见误判

| 现象 | 真因 |
|---|---|
| 「老库有、新导出没有」的某条父单号 | 在线表已把父需求拆成多条子需求独立成行，父单号自然不再单独成行，不是丢失 |
| 按名称匹配出现一堆「新增」 | 名称里空格、【】、标点、前缀不一致；改用单号对账 |
| 某列 `P2` / `p2` / `P1` 混用 | 手工录入不统一。导出后统一规范为大写，并把规范化动作写进导出说明 |
| 用户不希望留 git 痕迹，但指令让它「写进项目目录」 | 写本地文件没问题，但红线里要同时禁止 git 操作，两件事分开说清 |
| 拿到的 Excel/PPTX/PDF 打不开，文件头是 `%TSD-Header-###%` | 公司 DLP（天锐绿盾）加密，离开公司电脑即不可读。让用户在公司电脑解密后重传，或改用截图 |
| 仓库里的 PPTX/XLSX 突然变小、`unzip` 报 `End-of-central-directory signature not found` | 公司 DLP 在 Office 打开文件时**静默加密**，文件头从 `PK` 变成 `%TSD-Header-###%`，照常 commit 上去就污染了云端。这类二进制只能在 Mac 上改；已污染的从历史提交恢复未加密版本，提交前用 `file <路径>` 验证输出含 `PowerPoint`/`Excel` 而不是 `data` |

## 飞书收不到文件

机器人收不到飞书**文件/附件**消息（日志里 `media=0`，只有图片 `media=1` 正常）。所以材料一律走：GitHub 仓库 push、聊天里贴文本、或截图。别指望用户把 Excel/PPT 直接丢飞书。
