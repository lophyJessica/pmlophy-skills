# PM PRD ↔ 代码对齐审计

当 AI 生成了前端原型代码后，需要系统性地审核代码是否与规格文档一致。
本技能定义了审计方法和输出标准。

## Trigger

- 用户说"看前端""审一下前端""对齐 PRD""走查前端代码"
- AI 刚生成完一批前端页面，需要质量把关
- 用户给了 PRD 文档 + 前端代码，要求对照检查

## 审计三原则

1. **逐页逐字段逐状态** — 不是泛读，是对着规格表一行行核对
2. **三重权威源** — context/ > PRD 主文档 > Demo PRD。冲突时取高优先级
3. **改代码不改规格** — 审计结果是指向代码的修复指令，不是去改 PRD（除非规格本身有术语不一致）

## 审计流程

### 第一步：读全量规格

并行读取：
- `context/` 地基文档（至少 04功能清单、06业务流程、07项目边界）
- PRD 主文档（业务规则、状态机、动作矩阵）
- 字段清单（SSOT，所有字段的唯一定义）
- Demo PRD（列表页、新增编辑页、详情页的页面规格）

### 第二步：读前端代码

按页面读：列表页 → 表单页 → 详情页 → API层 → 类型定义。
重点关注：状态流转逻辑、字段显隐条件、按钮可见性矩阵、校验规则。

### 第三步：分三档出报告

| 级别 | 标准 | 示例 |
|:--|:--|:--|
| 🔴 阻断 | 违反 PRD 硬约束、超出 Scope、状态机错误 | 导入按钮在一期 Out Scope、状态配色全错 |
| 🟡 中等 | 遗漏列/按钮/筛选条件、文案不对、默认值偏差 | 行内操作不完整、弹窗按钮文案不对 |
| 🟢 低 | 措辞微差、简化实现可接受、不影响功能 | 原生 select 代替 SelectWithSearch |

### 第四步：三向对齐（context → PRD → code）

对照 context/ 的业务约束，确认 PRD 规则是否全部落地到代码：
- 数量公式（三口径、库存三口径）
- 状态流转（有无到不了的态、执行层是否误加审核流）
- 锁定规则（审核后哪些字段锁定、哪些仍可编辑）
- 校验规则（超收阻断、必填校验、未来日期拦截）

### 第五步：出修复指令

按五段式模板输出给 AI IDE（Antigravity/Claude Code 等）的修复指令。
优先级：阻断 > 中等 > 低。每轮 5-7 项，不要一次塞太多。

## 常见审计发现清单

参考 `references/audit-checklist.md`——包含逐页检查清单（列表/表单/详情/跨页面）和采购订单实战案例（13项审计发现 + 三向对齐结果 + 两轮修复指令）。

## 代码修完后必做：反向同步 PRD

**2026-07-12 踩坑：** 审计发现 5 个 P0 流程不一致（盘点/报损/调拨缺审核驳回、包裹/交运过账反了），代码修完后用户指出 PRD 文档没同步——状态机新增了 PENDING_REVIEW/REJECTED，但主 PRD 的 mermaid 流程图和 Demo PRD 的按钮矩阵还停在旧版。

修复完成后必须逐模块检查并同步：
- 主 PRD 的状态机段落（新增状态 + 流转动作）
- Demo PRD 的按钮矩阵（新增审核通过/驳回操作）
- mermaid 流程图（新增审核节点）
- 字段清单（如有新字段如驳回原因）
- context/（如有模块范围变化）
- 功能清单 context/03（如有模块期次/范围变化）
- 用户手册 ManualPage.tsx（如有操作步骤变化）
- **PRD 全篇的菜单路径引用**（如「工具中心 > 账号对应好友列表」这类操作路径）——菜单层级一改，这类引用全部失效，是审计时最容易漏的连带影响。**只改源稿，发布版一律用 `prd-doc-authoring/scripts/deliver.py` 从源稿重生成，禁止手改发布版里 base64 内嵌的图片数据**；重生成会跑三项自检（base64 图数=引用数、相对路径残留 0、字节不骤降），纯文字改动走一遍字节数应几乎不变，变了就说明动到了图。路径类替换用 `grep -c` 定数量：带箭头的两段写法、不带箭头的口语写法（如「工具中心账号对应好友列表」）各扫一遍再改，改完在版本记录补一行并写明处数，否则下一轮按旧数字派活会漏改。

注意 ManualPage.tsx 是前端源码不是文档——同步指令里不能混写"只改文档不碰代码"。PRD 文档同步和手册同步必须拆成两条独立指令。

## PRD 文档自身审计（AI 审计师只读模式——2026-08-12 CRM 实测）

当审计对象是 **PRD 文档套件本身**（非代码）——核查 主PRD + 字段清单 + Demo 三者一致性——用这个模式：

### 固定审计框架（每轮同——AI 审计师可批量执行）

1. 主PRD 行数（≥300 质量下限——行数是门槛不是质量本身）
2. 章节完整性（痛点/In-Out含原因/链路图/场景编号/状态机/规则编号/权限矩阵/验收条件）
3. 状态机闭环（所有状态入口/出口/失败处理——不只看 happy path）
4. 字段清单 SSOT（下游主PRD/Demo 是否重复定义枚举/必填/校验）
5. 通用规范对照（context/07：Tag配色/列表约定/二次确认/主数据不删除）
6. 上下游一致性（跨系统 SSOT 归属——客户档案在 ERP、订单在 ERP 等）
7. 用例推演是否存在+覆盖（方法论第6步强关卡——缺异常/逆向/跨系统路径=不达标）

### 分级标准

- **P0**：阻断性（功能不可用/状态机断）——必须清零才部署
- **P1**：重要（规则不符/SSOT 破坏/跨系统契约缺失）——应修
- **P2**：优化（列宽/笔误/术语）——可延后

### 执行纪律

- **全程只读**：绝不修改任何文件（用户铁律——审计不是返修）
- 审计产出：`audit-reviews/{模块}模块审计报告.md` + README 汇总表（模块/P1数/P2数/核心问题/跨模块共性发现）——沉淀进项目 git
- 可交给本地 AI（贾维斯/35B）：先喂方法论文档→复述验证→逐模块审计→报告→纠正→记忆沉淀——实测 35B+结构化喂养能达到接近资深 PM 的审计质量（能抓跨系统契约/双标识/生命周期状态等深坑）
- **返修是独立阶段**：审计完→按 P1 清单发返修指令（不同模块独立目录可并行 2-3 个 Codex 会话）——审计与返修分开，避免"审着改着"污染判断

### 跨项目并行审计（2026-08-19 WMS+CRM 实测）

- **不同项目（不同仓库目录）可并行审计/并行铺标注**：WMS 审计 + CRM 审计 + ERP 标注可同时开 3 个独立 Codex 会话（用户明确要并行，避免串行等死）——各自独立目录互不冲突。同一项目内审计与标注铺排是串行关系（都动同一仓库），跨项目才是并行关系。
- **审计/铺标注必须基于 Mac 工作区，不以 VPS 仓库为准**：Codex 在用户 Mac 上跑，项目路径必须用 `/Users/liulongfei/个人文件/forge-*`（绝不能写 VPS 的 `/root/repos/forge-*`——2026-08-19 用户纠正过）。VPS 的 `/root/repos/` 仓库常滞后（Codex 只传 zip 不 push Git 时仓库不同步，线上已更新但仓库旧——例如 CRM bundle 线上 144 块、VPS 仓库仍 9 块）。判断代码现状以 Mac 工作区 + 线上页面为准；给 Codex 指令里写"以 Mac 工作区为准，VPS 仓库旧版不看"。
- **已有 PRD 文档审计 ≠ 已做代码对齐审计**：PRD 文档自身审计（2026-08-12 6 模块）和 PRD↔前端代码对齐审计是两个维度——前者审文档套件内部一致性，后者审代码是否落地规格。用户要后者时不能拿前者搪塞；指令里可让 Codex 参考已有审计报告避免重复，但重点核对代码实际实现。

### 审计→拍板→返修闭环节奏（2026-08-19 双审计实测——关键闸门）

审计报告出来**不能直接丢返修指令**——中间有必经的**用户拍板闸门**（口径冲突是决策项，不是返修项）：

1. **先出 digest 给用户拍板**（不是丢全文）：分级计数汇总表 + 每模块 P0 摘要 + 需用户决策的**权威源冲突清单**。用户只拍板关键冲突，不读全文。
2. **口径冲突拍板案例（2026-08-19 定案）**：
   - 业绩金额口径：context 用 CRM WON 金额 vs 主PRD/字段清单用 ERP 确认订单金额 → 用户拍板**用 CRM 自己的 WON**。理由：CRM↔ERP 串联未打通（Mock 阶段），按 ERP 口径无数据来源。**通用规则：跨系统串联未完成时，用有数据来源的系统自己的口径，别硬关联未接通的系统。**
   - 公海保护规则：context 公海主PRD 与线索主PRD/决策稿反向描述 → 拍板 **context 为最高权威**（符合审计三原则第2条）。
3. **定案口径写进返修指令的红线区**（"业绩金额只用 CRM WON、公海按 context"）——防止 Codex 修时被审计报告里的矛盾表述带偏。
4. 返修指令让 Codex **自读完整审计报告**（报告在 Mac 工作区；VPS 副本常没有）——指令只列 P0 摘要 + 定案口径，细节由 Codex 读报告，不把 46/48 项全抄进指令。

### 审计规模基准与 P0 模式（2026-08-19 实测）

- **规模参考**：CRM 18 页审计 46 项（12 P0 / 26 P1 / 8 P2）；WMS 44 业务页审计 48 项（22 P0 / 22 P1 / 4 P2）。审计报告必须带文件+行号证据；Codex 自检报告机器复核分级计数（标题计数 vs 汇总表一致）。
- **P0 重灾区模式（跨模块共性，WMS 补强）**：①库存冻结缺失（盘点/报损/调拨期间未冻结、可能改错货位）②状态机硬约束被绕过（手工赢单/伪造签署/伪造 ERP 结果/浏览器即时结算）③跨单据回传重复/错账（分批上架重复回传、包装重复/错仓扣库）④越权操作未阻断（已签到无权限取消、停用客户仍可操作）。
- **审计执行偏差必须主动披露**（2026-08-19 WMS 实踩）：审计时运行标注规范附带的校验脚本，会因 workspace 配置重生成了 `annotation.bundle.json` / `annotation-coverage.md`——它们是审计前就未跟踪的文件（Git 无基线，无法证明字节是否变化）。Codex 自检报告必须披露这个偏差并声明未擅自删除/回滚。**给审计指令的红线里明确"不 build / 不跑校验脚本 / 不部署 / 不 commit"**——审计是纯静默读码 + 写报告，任何会写文件的命令都要在红线里排除。

### PRD↔代码双向对齐审计（2026-08-28 forge-scrm 实测——三分类 diff 框架）

前端多轮迭代后用户要求"PRD 和前端页面对齐审计：前端有点超前了，PRD 有的也没实现"。这不是代码质量审计，是**产品层双向 diff**，用三分类框架：

| 分类 | 判定 | 处置建议 |
|---|---|---|
| 【超前】 | 前端有、PRD 无 | 回退 或 补 PRD 待确认（按风险分级：引入新业务概念/写操作=高风险） |
| 【缺口】 | PRD 承诺了、前端没有 | 排期实现，**mvp验收清单内的优先** |
| 【偏差】 | 都有但口径不一致 | 字段/状态/流程对照 context/05 判以谁为准 |

**防糊纪律（关键）**：
- 每个"缺口"判定必须引用 PRD 原文位置（文件:章节）——PRD 没写的不许算缺口
- draft/、requirements/ 不算依据（权威层级 context/ > prd-docs/）
- 交付报告按三类各一张表：页面/模块、PRD 依据、代码位置（文件:行号）、建议处置 + Top5 优先项
- **给 Codex 的审计指令要校准"最新已拍板状态"**：多轮迭代后 PRD 常滞后于代码（如推送状态机新增"已取消"、报告删除已上线），指令里要预先标注"此项记为 PRD 回写待办，不算前端超前"——否则审计会产出已知偏差当新发现
- **拍板处置框架**（审计报告出来后给用户的三档视图）：🔴 必修（MVP 阻塞/context 明确冲突，清零）→ 🟡 文档回写（代码领先文档的拍板项，半小时防未来 Agent 拆家）→ 🟢 排期待办（大功能缺口进 draft 待办池）。三类分开拍板，不混一轮修

**最重要甄别：context 未回写的拍板口径——Agent 读 context 会得出相反结论（2026-08-28 重犯）**。审核流程有用户拍板（"二期默认通过，审核入口暂时隐藏不使用"，依据 审核流程变更说明.md + requirements/09），但 context/04 的 R1/R3/R6/R8 仍是一期审核口径未回写。后果：Agent 审计时把"审核入口隐藏"判成缺陷去"修复"（放开成员审核），方向完全反了——被用户当场抓到，整条指令作废重写。**规则：凡涉审核/流程类判定，先查项目内是否有"变更说明/拍板依据"类文档（审核流程变更说明.md 等），其时间戳晚于 context 时以拍板为准，并在指令里显式标注口径与依据，禁止让 Codex 拿 context 旧口径反推。** 治本 = 授权一次性回写 context（对齐拍板口径），消灭陷阱源头。

**拍板口径的回写粒度与"口子保留"原则（2026-08-28 实测——回写 context 后前端处理）**：context/04 回写"审核默认通过"后，前端不要删能力——用户明确"先把口子留着，前端先做字样上的隐藏"：①按钮字样收敛（"提交审核"按钮删除 → "保存(直接生效)/存为草稿"两键，UI 不再出现审核字样）；②菜单入口注释隐藏（路由+页面+后端接口全保留，直输 URL 仍可达=重启审核能力的预留）；③message 文案去审核词（"保存成功，资料已生效"）；④状态枚举/接口参数/状态机判断零改动。**改字样不改逻辑 = 拍板可逆的最低成本实现**。

**重要甄别：用户说"没有删除功能"≠缺口**。先 grep PRD 确认——本次实测 PRD 明确写「删除报告 ❌ 默认不提供（策略待确认）」，这是**按 PRD 正确实现**，不是缺口。处置选项：A 尊重 PRD 不加 / B 用户拍板修订 PRD 口径后补功能（本次 B：报告删除=有推送记录不可删保对账完整）。若用户选 B，PRD 回写属受保护目录时**记入遗留**由用户手动回写，agent 不代改——或用户明确授权范围后让 Codex 顺带回写（本轮实测：回写范围必须逐文件逐段列白名单，其余 PRD 文件禁改）。

### 复刻件 / 原型 ↔ 真实生产系统结构对齐（真源选择与三分类）

对象不是 PRD ↔ 代码，而是「自己做的复刻原型 ↔ 线上真实系统」。这类对齐最容易错在**真源选错**，而不是能力不够。

**菜单 / 路由 / 层级类对齐，真源只能是侧栏实际渲染的菜单定义文件**（如 `config/menus.ts` 的 MODULES），**不是 `App.tsx` 的路由表**。路由表里混着历史兼容别名（`/main/channel/channel/resource` 这类生产长路径与 `/auth/resources` 短路径并存），按它推会同时错三处：路径全填成生产别名、漏掉一半菜单叶子、把带 children 的分组压平成同级。给 agent 的指令里要写死「不许出现 `/main/...` `/main/content/...` 这类生产别名路径」，验收时反 grep 一遍。

**差异必须三分类，不能笼统说「不一致」**：

| 类 | 判据 | 处置 |
|---|---|---|
| 原型放错了 | 真实系统有明确归属，原型挂到了别处 | 改原型对齐真实 |
| 本次新增 | 真实系统还没有，PRD 里是本轮要做的 | 保留，并**在 PRD 里标明是新增**——否则评审时被问「真实系统怎么没有这项」 |
| 真实有原型缺 | 真实系统的功能原型漏了 | 补，或在 PRD 里写明本期不做 |

判别动作：拿到真实菜单树后逐项问「这是本期要做的吗」——功能清单里有就是新增，没有就是缺口。**「原型跟真实系统不一样」本身不是错误**，错的是没在文档里说清它属于哪一类。

**别用「一级菜单数量对齐」当验收标准**：真实系统六个一级菜单、原型五个，不代表改一个就对了。本次实测差异分布在层级归属（权限中心是一级还是组织架构下的分组）、分组拆分（标签管理独立还是挂在配置管理下）、模块归属（whats 管理工具在触达计划还是工具中心）三种形态上，逐个对层级才有意义。

**同名节点不要合并**：真实系统里「白名单」可能有两处（触达计划下的富媒体短信白名单、配置中心下的白名单配置），是两个不同页面。看到同名就当成一处搬走，等于删掉一个页面。判别动作：同名节点的路径不同就不是同一个东西，各自保留；原型暂时只有一页就写进 PRD 标「本次不拆」。

**盘点类交付先核行数，别信报告的「已补齐」**：把「逐模块盘页面」交给 agent 时，它可能只写元信息加一句「本次未盘点」就交付——四个文件各七行，报告里却写着补齐四个模块。收到后先 `wc -l`，正文不足二十行的按空壳退回。对策是范围压到一个模块一条指令，指令里写死「只盘这个模块，盘完就交，不许往下扩」；一次派四个模块的结果通常是四个都空。

**长报告让它写成仓库文件，不要在聊天里贴**：差距诊断、逐页对比这类报告动辄两三千行，聊天粘贴必被截断，接到半截报告无法判断完整性。指令里直接要求「写成 `02-需求调研/<主题>-<日期>.md` 提交到仓库」，我拉下来读文件；同时要求它回报文件路径、字节数、行数、一级标题清单，用这四项定完整性。

**派活时就写上「改完 commit 到本地分支」**：外部 agent 默认在报告里写「未 commit、未 push」，改动只在它本地盘上。不写这句，我每次核验拉下来还是旧文件——字节数、行数一点没变，得让它再跑一轮提交，一晚上能白绕好几回。push 由我执行，commit 归它。

### 判断「这个功能到底做没做」的取证顺序（别在错的分支/仓库上下结论）

当要确认某功能（如预售）到底有没有开发、代码在哪时，按这个顺序取证，每一步都不会白跑：

1. **先查所有分支，不要只看当前分支**。主分支没有 ≠ 功能没做。产品功能往往落在版本分支上（`1.8.0`、`release-v1.x`、`feature-v1.x-xxx`）。只读取不切换：`git ls-tree origin/<branch> --name-only`、`git diff --name-only main...origin/1.8.0`。指令里要写死「不许 checkout，用 ls-tree / show / diff 读其他分支」。
   **按目录变更找，不要只靠关键词搜**。功能名和文件名经常对不上——一个叫「预售」的模块，页面文件可能叫 `sales/index.vue` / `orderList.vue` / `verify.vue` / `setFollower.vue`，`grep 预售|presale` 一个都命中不了，据此断言「没做」是错的。正确做法：先 `git diff --name-only main...origin/<版本分支>` 把整个新增目录树扫一遍，再逐目录判断它是干什么的；关键词只当补充手段。
2. **再查是不是 iframe / 外链嵌入的外部系统**。搜 `iframe`、`srcdoc`、`embed`、`URL_MAP`、`pageId`，以及外部域名和 `/spa/` 这类路径。B 端系统很常把某个业务模块整块挂在兄弟系统上，本地只有壳：菜单 + 容器 + 登录态 + `postMessage` 传语言/国家，业务表格表单全在对方系统里。
3. **前端没有就反查后端 Controller**。后端也没有对应接口，才能下「真没做」的结论；后端有接口而前端没页面，结论是「页面还没做」——这两者对排期和原型的含义完全不同。

**「本地只有一个 iframe 壳」是常见且合法的架构**，不是缺陷。定位到这种结构后，产品侧的真实职责边界是「提供入口 + 壳 + 权限 + 登录态」，不是自己画业务页面。这时原型该画 iframe 占位页还是画完整业务界面，是产品决策，要单独拿出来问用户，别默认照 PRD 把业务页全画一遍。

**同类先例可复用**：同一个项目里导购端和后台端往往是同一套版本节奏。一端查到代码在 `1.8.0` 分支，另一端大概率也在同一个版本分支上，直接按这个假设去查能减少一轮往返。

### 真源优先级：在线系统 DOM > 仓库代码 > 历史盘点文档

菜单 / 层级 / 字段这类「真实系统到底长什么样」的问题，三级真源可信度递减：

1. **在线系统实际渲染的 DOM**（最高）。让 agent 用内置浏览器进测试或生产环境，直接抓 `#mainMenu`、顶部导航、表单字段的 DOM，连层级嵌套和元素文字一起拿。
2. **仓库里的菜单配置文件**（次之，如 `config/menus.ts`）。它反映的是「上一次改到哪」，可能已在多轮基于错误数据的改动中跑偏。
3. **历史盘点文档 / 上一轮 agent 报告**（最低）。上一轮基线错的话，文档会把错误固化成「权威」。

**铁律：要 agent 对齐真实系统时，第一条指令就是「去抓 DOM，不许参考仓库里任何菜单结构文档或代码」，而不是自己先按文档列一套结构再让它照着改。** 用文档当基线再让 agent 执行，等于把错误放大成多轮返工，而且每一步看起来都合理——直到用户发现真实系统里压根没有那个分组。

盘点类 agent 产出的结构文档尤其不可信：正文常常只有元信息加一句「本次未盘点」，或者层级判断直接错。收到后先 `wc -l`，同时拿真实 DOM 回检。

### 原型 ↔ PRD 点检：基准选谁、冲突怎么裁

点检「原型是否和 PRD 一致」时，**基准不是评审 PRD**。评审 PRD 常滞后于定稿口径（可能整篇还是旧字段名），拿它当基准会把已改对的原型判成错。正确基准是：**功能清单（条数与描述）+ 字段清单详细稿（字段事实）+ 业务 PRD**三件。

执行方式：把基准文档逐条拆成可 grep 的断言，再对代码核，例如「列表要展示行为ID、名称、维度、数据源表、属性数、状态、更新时间、操作」→ 直接 `grep -n '<th>' 列表页组件` 数表头数量与文字，不靠读代码叙述。每条差异写四栏：**基准原文 / 代码实际 / 严重度 / 改哪一边**。

**冲突处不许自行选边。** 典型场景：功能清单写「一组对应一个标签」，而线上真实系统支持组内多条；或定稿口径写「触达时机两项」，线上还有第三项。这类要列出两个基准各自怎么说，然后让用户拍「跟线上还是跟清单」。自作主张选一个再改，结果往往是改了原型又要改回来。

**页面形态只能来自线上 DOM。** 截图 OCR 会编名字（实测把「富媒体短信」读成「鲁班体短信」，把裁切边缘读成页面上根本不存在的「组合计划」「频控明细」），二手描述也会骗人——PRD/交接文件里一句「查看页只有一行统计表加活动配置」当全貌用，会让整块受众筛选和内容配置被误删。规则：要改某页之前，先让带浏览器的 agent 抓该页 DOM；没抓到形态的地方在指令里标「未取证」，不填内容也不允许 agent 猜。

**取证按页累积、不要重复抓**：每轮只抓这次要改的那页，抓完立刻写进同一份取证文档（按页分节，标注来源站与日期），后续直接读文档。**不要提议「把全套页面一次性取证一遍」**——那是要烧掉一个 agent 全部额度的方案，用户会当场否掉。

**内销与外销是两个站，取错站结论全错**：先确认这次要对的究竟是哪个环境的页面（外销生产 / 内销测试），每条结论标明来源站。拿内销站当外销依据是硬错——反过来，「外销线上没有这个页面（本期新建功能）」的情况只能参考内销，而且要在文档里写明「仅参考，冲突以定稿为准」。

### 派独立审计 agent 做「原型 vs PRD」审计：报告怎么下、怎么收

把整轮审计交给没参与实现的 agent（只读、产出带 `文件:行号` 的报告）是对的做法，但报告不等于结论，交付前按下面四条处理。

**① 指令里把「自创」的判定边界写死，并要求单独成节。** 输出固定四块：逐条三态（一致 / 不一致 / PRD 未覆盖-原型未实现）、A「原型有而各真源都没有」的自创项、B「PRD 写了原型没有」（再分「确定没做」与「口径未定所以没落地」）、C 字段级偏差（每张表给「原型列数 vs TSV 应有列数」两个数，字段名与枚举逐项对）。三态必须条条有证据，禁止「基本一致」这类无证据结论，禁读内嵌 base64 的发布版 md（一行几万字符会撑爆上下文）。

**② 不能让审计 agent 上网时，「自创」只等于「各真源里找不到依据」，不等于「线上没有」。** 无登录态就拿不到线上形态，报告自己会写明这点，但下游极易把 A 节整节当返修清单——实际里面常混着一批「照线上复刻的真实控件」（异步任务抽屉、默认预置条件、估数按钮）。父会话必须把 A 节**二分**：真自创（删/改）与疑似线上形态（单独列出来让用户拍板），不许直接下发给执行 agent。判定口径永远是「先取证再定」，不是「文档没写就删」。

**③ 父会话验收先抽查硬结论，再看全表。** 收到报告后随机挑 5–6 条可 `grep` 验证的结论回源码核对（枚举取值、该列在不在、文案 `grep -c` 是否为 0、路由是否还可达、页面是不是静态图占位）。抽查全过才逐条读表；任何一条抽查就不符，整份报告的其余判定都要打折，先退回。

**④ 修复范围按「是否需要线上证据」两档切。** 有仓库内依据的（文档互相打架的口径、字段枚举、必填性、状态文案与控件形态、菜单归属、列数增减、时间格式、写死的自造区块）本轮直接改；只能靠线上 DOM 才能判的（默认预置条件要补哪些、某控件线上有没有、整块折叠控件存废）一律标「未取到证据，待补」并**从本轮范围里摘出去**，改成「先派带登录态的 agent 取证 → 再按清单补」。让执行 agent 在缺证据时自己补 = 它必然编，编完还要返工删。

**执行者按机器可用性选，不是按谁质量好选。** 派审计/修复前先确认这台机器上哪些 agent 真的能用：公司网络下走 OpenAI 的 CLI 不可用，公司机上的活归 IDE agent（Cursor 带登录态内置浏览器做 DOM 取证 + 改原型）与内网可用的编码 IDE（文档回写）；家机才用外部 CLI。原型与文档文件域不重叠可以并行，同一份原型内部的连续改动必须串行同一个 agent。

### 审计报告里的「文档与原型不一致」：先分三态再动手，不准一律删文档

审计会把文档与原型的所有差异都记成「不一致」，但一类是文档自己乱写、一类是原型漏做，处置完全相反：

| 差异性质 | 判据 | 处置 |
|---|---|---|
| 文档自造 | 原型没有，也没有定稿口径撑腰 | 删该表述 |
| 已定口径、原型漏做 | 之前定过要做的规则，原型没实现 | 补原型，**不删文档** |
| 两份文档矛盾 | 同一事实在两个文件里说法不同 | 统一成一个口径，取用户已拍板那版 |

一律按「文档跟原型、多余就删」处理，会把已定的业务规则连同文档一起删掉（典型：「触达时机下方固定说明」「重名阻断」这类之前拍过要做而原型没做的规则，在审计表里长得和自造项一模一样）；反过来把自造项补成代码，就是给原型加没人要的功能。派活前逐条归态，把第二类**单独列举给用户确认**——它要改代码，不是改文档。

判态时一个很实用的区分：这条差异在**功能清单 / 已拍板交付物**里能不能找到依据。找不到依据 = 自造，删；有依据 = 原型漏做，补。

**回写前先全量重扫旧口径并计数，不要用上一轮报告里的数字。** 交接里那句「还有 N 处旧口径」只是当时手边看到的几处；同一个废弃术语散在版本记录、功能清单、页面内容、交互说明、字段说明表、用例推演里，据那个数字派活必然漏改一半。做法：每个废弃术语单独 `grep -c`，再 `grep -o -E '.{0,30}(词1|词2).{0,40}'` 截窗看上下文，按实际命中派活；扫描时排除 base64 内嵌的发布版只扫源稿（整行输出一次就能打满上下文）。

**废弃术语替换要连带核结构，不只换词。** 字段改名常伴随列结构变化（某字段废弃后列表九列变八列、三项枚举变两项、列表里重复的同义列要合并），只做词汇替换，文档和原型的列数/枚举数仍然对不上，下一轮审计会原样再报一次。

### 页面级改动的分工：用户直接带 IDE agent 比经我转述快

逐项复刻/微调单个页面的形态时，用户自己对着屏幕跟 IDE agent（Cursor 等）对话、即时纠正，比我把形态写成文字指令再转过去更快更准——他看得见、能当场喊停，我的转述只会引入失真。这类活不要抢着写工序指令。

该由我承担的：口径裁决（两个基准冲突时该跟谁）、文档侧回写（评审 PRD / 功能清单 / 字段清单）、取证结论归档、以及**独立点检**（不看 agent 自报，直接读代码和文档核）。分工讲清楚，双方都省时间。

### 本期产品设计优先于真实系统结构

真实系统的结构是「现状」，不等于「应然」。本期需求明确要改结构时（例如把标签能力从权限中心挪到触达计划下的配置管理分组、跟内销对齐），照真实系统对齐就是往回改。

判别动作：动手前先问「这块本期是要对齐真实系统，还是要改造它」。问不清就问用户，别默认对齐。上面三分类里的「本次新增」类差异，一律不动。

### 复刻样式：同栈搬代码，不跨框架重画

有源码时，「用另一个框架重画一遍」是做原型最贵的错。源码 Vue3 + 移动端组件库，原型用 React + 手写 CSS，它带来的圆角、字号层级、卡片内边距、按钮高度、信息条底色全部丢失——结构能对上、视觉是两个产物。逐元素抠数值是无底洞，而且改完之后行为仍是手写的，源码再更新一遍又要重对。

正确做法：

1. **原型与源码同技术栈**，把页面和样式文件整块搬过来，组件库版本对齐。源码更新时同步文件就行。
2. **搬之前先摸底三个依赖**，不然会摋在半路：① 私有组件库（企业内部的按钮/列表/下拉封装）——**先试内部 npm 私服，不要默认拿不到**：企业内网通常有私有 registry（看源码仓库 `.npmrc` 里的 `registry=`，形如 `http://npm.<corp>.xyz`），包往往能装。做法是先建一个临时最小工程装一遍、渲染一个组件、跑通 build，用结果定路线——**装得上就整块搬，视觉 100% 一致**；装不上才退回「统计用到了哪些、逐个找开源同源组件替代或写薄封装」。实测私服可访问、私有 UI 库和原生 SDK 都能装，直接省掉整轮适配层；不验证就按「拿不到」去做适配层，等于自己找活干；② 原生 Bridge（扫码、复制、保存图片、打开外部 App、拨号）浏览器没有——列清单写 mock 层，调用时装成功并给提示；③ 内网接口、登录态、环境变量——换成 mock 数据。
3. **重构窗口是代码量小的时候**。几页的时候改成本最低，几十页再改就是重做。

判别信号：用户说「样式完全是两个产物」「有源码怎么还做成这样」——不要再发「逐项对齐样式值」的指令了，直接提重构。抠样式的指令发出去，agent 会给你一张改了二十个色值的对照表，页面看着还是不像。

**现成的复刻提示词在维他命课件里，先拿再改，别现编**：`/root/notes/vitamin-course/08 用 AI复刻已有系统前端页面.md` 收了四种方法的完整模板（能拿到代码 / 只有截图 / 有 Figma 稿 / **用浏览器自动化读页面再复刻**，最后一种最贴合）。模板里的硬红线值得原样继承：浏览器里已登录的页面是唯一视觉真源、只允许浏览观察而禁止保存/提交/删除/导出、不许擅自现代化而保留原控件密度与视觉风格、图标用真实资源或内联 SVG 禁用 emoji 顶替、禁止把整张参考截图当背景图、完成后在同视口对比且明显一致就停。改造时**只换技术栈段和「本次任务信息」**，并必须额外加两节：① **本轮明确不动的部分**（逐条列出之前已经调过的设计改动，否则它会照线上把已有改动推平）；② 本轮范围只限指定页面。用户会直接担心「这个提示词会不会把我们之前调好的覆盖了」。

### 只读取证：只出事实，不出改造方案

用户会让你「去源码核对一下现在到底是什么逻辑」。这类任务的产出边界很窄，越界会被当场打断（用户原话：“这个我们只是取证，我们又不是开发，管怎么修改干嘛”“我只是要取证这块前端的处理逻辑到底是什么，告诉我，让我能懂就行了”）。

- **产出两层就够**：① 现状是什么（带 `文件:行号` 和代码原文，不转述）② 这在产品上意味着什么问题。**到此为止**——怎么改、改到哪一层是研发的事，写出来就是越界。
- **用业务语言讲，不堆技术细节**：说「点进去什么都没显示」而不是「`router-view` 挂在 `v-if=hasAccount` 里面」。用户要的是能听懂，不是能评审代码。
- **汇报前先分清条件挂在哪一层——用户描述的现象和代码实际行为常常差一层**。用户说「这个 tab 不显示」，实际可能是「tab 还在，但整块内容区被一个前置判断拦住了」，影响范围比他以为的大得多（实例：没账号的导购连任务和销售都进不去）。必须看清 `v-if` 挂在**容器壳**上（整块内容消失、所有入口一起废）还是**内容块**上（只影响这一块）。不确认就答，会把大问题报成小问题。
- **判断条件过粗（只看数组空不空，导致多种原因不可区分）、某处硬编码未抽象（换渠道要改 N 处）** 这类发现，如实列成事实即可，不顺手附改造清单。
- 指令里要写死：「只读不改；不许猜，找不到就说找不到并写明搜了什么关键词、看了哪些文件；代码原文要贴，不许转述」。不写死，agent 会交一份掺着建议和推断的报告。
- **跨分支核对是常态**：同一功能在 master 与版本分支上可能存在差异（甚至文档里写了要改、代码并没改）。两个分支都要读并说明差异，别只看当前分支就下结论。

### 口径条目 ↔ 存量源码核实（把业务口述的口径用代码坐实）

对象不是 PRD↔代码，而是「口径字典 / 业务口径里的一句话」是否与**存量生产源码**相符。这类核实最容易把方向搞反。

**判「不一致」前先分辨三种落点，不许一律判口径错：**

| 差异落点 | 判据 | 结论怎么写 |
|---|---|---|
| 口径写错 | 机制、来源、归属确实与代码相反 | 不一致，给出代码证据并改口径 |
| 本期新增 | 存量没有，但 PRD 的版本记录/列定义里有 | 「存量无、本期新增，数据源在 CMS 库内，实现待开发」——**不是口径错误** |
| 存量有、本期不要 | 代码里有，PRD 已明确砍掉 | 记为存量遗留，别拿去论证口径 |

实操判据：动手前先翻 PRD 版本记录和列定义（如「列表由 8 列恢复到 17 列」），凡是本期加列/加功能的，拿存量源码里的「查无此列」当口径错，回写时会把第②③类写反。典型误判：前端后端都没有导出接口 → 若 PRD 里有导出需求，结论是「存量无、本期新增」；列表返回 VO 缺某列同理。

**机制类结论以「数据怎么进来」为主线**：回调推送 / 定时拉取 / 手工导入 / 查询时回填，这四种常常混在同一句口径里。写「定时任务对接外部系统拉取」而实际是服务商 webhook 回调 + MQ 异步入库、CMS 侧定时任务只做库内自转（库↔ES 对齐、过期清理），这种方向性错误只有把链路逐跳追出来才看得见——从回调入口、事件枚举、MQ 生产/消费，一直追到落表与索引。

**只认代码证据，不认命名推断**：每条结论带 `文件:行号`；搜不到就写「代码内未找到」并说明搜过哪些关键词、看了哪些文件。定时任务的 cron 频率常配置在代码之外（调度管理台），写「代码内未找到，需在管理台查」，禁止猜数值。中文路径下 grep 会出假阴性，命中 0 时先换工具（PowerShell Select-String / Glob）再下「不存在」的结论。

**派生发现单独成节，不要混进口径修订**：核实时暴露的「PRD 放在 A 行的字段其实是源码里 B 行的属性」「存量菜单名与 PRD 菜单名不同」这类，属产品待确认，另开一节列给用户拍板；和口径修订混在一起改，拍板项会被当成已定结论落进文档。

**派核实指令前先自验仓库路径**：指令里写死的源码工作区（哪台机器、哪个目录、内销还是外销仓库）必须先确认，照抄看板或记忆里的路径会把整轮活干到错的仓库。让 agent 在阶段一先回报「本次取证对象是哪个仓库、哪一端（内销/外销）」，不对立刻停。

**分阶段门禁 + 定式交付表**是这类活的最佳形状：阶段一「定位表」（模块｜文件:行号｜作用｜置信度），阶段二「同步任务参数表」+「字段来源表」，阶段三报告 + 可直接替换口径条目的成段草稿；每阶段结束必须停、等确认再往下，红线写死只读/不改文档/不猜/不做全库扫描。一次梭哈会把定位错误带到整份报告里。追链路的具体顺序（页面→接口→BFF→领域服务→存储→写入方）与可直接复用的三阶段指令模板见 `references/data-lineage-tracing.md`。

**报告是产出物，不是临时文件。** 项目里若已有「任务结束前必须删除 .tmp 临时文件」这类规则，指令里必须同时写明报告的归档路径并注明「属产出物、不列入临时清理范围」——不点名就会被顺带清掉，而 agent 仍然会回报「已生成 + MD5 校验通过」。

**agent 说文件已生成不算验收。** 报告在对方机器上时，拿它把「结论摘要 / 待拍板清单 / 口径替换草稿」贴到聊天，或让它 commit 后给出提交号自己拉下来核；只收到路径与 MD5 通过就宣布完成，等于拿自报当结果。

### 结构回滚不是单文件操作

`git checkout <commit> -- config/menus.ts` 回滚菜单后，下游文件里对被删模块的判断会编译报错（`TS2367: 类型 '"a" | "b"' 与 '"c"' 没有重叠`——典型是资源表构建器还在按旧的模块 key 分支）。资源表若由 `menus.ts` 程序化生成，回滚菜单后资源表会自动跟上，但**回滚后必须 build 一次再宣布完成**；`tsc` 会把所有连带点列出来。

回滚前先确认回滚范围：`git log --oneline <好提交>..HEAD -- <相关文件>` 看这段时间到底动过哪几个文件，只回滚被错误改动带的文件，别把期间的正当改进（如资源表改成程序化生成）也一起回退。

### 全局审计的批量修复打包（2026-08-28 实测——一轮 Codex 清完 14 项）

双审计（功能+UI）合并后**不要逐项发指令**——打包成一条编号指令（P0-1/P0-2/P1-3.../UI-严重/UI-建议），每项含文件:行号+对策，末尾统一 build/compileall+自检报告管道。实测一轮 14 项全过。原则：
- 审计确认"已通过"的方面在指令里显式写"不要动"——防 Codex 顺手改坏
- 防臆造条款：外部组件（如飞书 collapsible_panel）"查证不到就走保守降级，不臆造字段"——本次 Codex 正确降级为 500 字平铺
- 并发竞态修法（通用）：状态检查+commit 改条件更新占位 `UPDATE ... WHERE status IN (...)` 检查 rowcount=0 → 409
- 僵尸状态修法（通用）：状态可因进程崩溃永久卡死时，入口检测 updated_at 超 N 分钟自动复位 + 异常兜底置失败
- 用户验收会推翻实现：删除规则上线后被纠正"已推送=凭证不可删"——**验收反馈是需求变更，快速出修正指令**（改动量极小时单条指令也值得）

### 指令文件序号规范（forge-scrm prompt/ 目录）

指令文件必须 `NN-名称-指令.md` 连续序号（01~25 已用，新增续号）。曾犯：从 16 号起丢序号产生 8 个散文件，用户纠正后统一 rename 归位。**创建新指令文件前先 ls prompt/ 看最大序号，续号不重开。**

### 指令写错方向被用户抓到后的处理（2026-08-28 实测）

给 Codex 的修复指令方向反了（把用户已拍板"下掉审核"的需求当成缺口去"放开审核"），用户在 Codex 开跑前抓到。处理流程：
1. **先核对再重写**：grep PRD/变更说明/后端代码三方，确认真实口径（本次发现后端 schema 早已有有效期字段、"人工新建直接生效"早实现——D1 判定整个作废）
2. **重写整份指令**（不是打补丁），被推翻的项显式写"作废/撤回"+原因，防止 Codex 从旧审计报告里又捡回来
3. **拍板口径升级为回写授权**：反复被误判的口径（审核默认通过）一次性授权回写 context SSOT，消灭陷阱源头——但 context 授权范围必须逐文件逐段列白名单
4. Codex 未 push 的本地改动直接作废重来，成本为零（未 commit 就没有沉没成本）

### 模型分层排活与接力（2026-08-19 额度血泪）

审计/返修/铺标注这类大活**不要一开始全丢给 Sol**——Sol 强但烧得快（实测 3 小时烧完一天额度：双审计 + 双返修 + ERP 采购标注）。正确分层：

| 任务类型 | 模型 | 原因 |
|---|---|---|
| 关键审计 / 复杂返修 / 架构判断 | Sol（高质量重任务） | 质量导向，但要看额度 —— 只上关键大活 |
| 收口 / 批量标注 / 自检 / 复核 / 格式化 | Luna 或普通跑量 | 省额度，指令拆清 + 验收标准写全可替代 Sol |
| 备用兜底 / 小灶 | 中转(awesomeai 等) / 本地模型 | 主额度耗尽时接住未完成任务 |

- **接力会产生同一任务两份自检报告**（先发首版 + 收口版）——这是正常现象不是重复提交。Codex 计划用 Sol，额度烧完被用户切 Luna 接力，同一部署常有多份报告（如 ERP 采购 18:06 首版 + 18:18 更新版；WMS 返修 18:27 + 18:29）。**查报告时认最新时间戳那版，不误判重复，也不重复派活。**
- **进度压缩**：Sol 烧完后剩余 P0 优先跑（P0 必须清零，P1/P2 留待），把"没干完"收敛成"至少把最关键的干完"。
- 模型分层属排活方法论，进 skill 不进 memory（用户自己管额度记忆）。

### 跨模块共性发现（6 模块审计后——返修优先级最高）

1. 跨系统契约缺失（商机/合同/业绩都缺 ERP 订单/事件契约）——先定 SSOT 边界
2. 字段清单 SSOT 落地不完整（全部模块有"Demo 用了清单没定义"的字段）
3. 用例推演覆盖不足（全缺异常/逆向/跨系统路径）
4. 金额口径不清（商机预计/合同签署/ERP 订单三处关系未收口）
5. 状态模型混淆（同步处理状态 vs 业务生命周期状态）

## 状态机推演：不只是 forward path

**2026-07-12 踩坑：** 盘点/报损/调拨的审核流只实现了 happy path（提交→审核通过→完成），漏掉了逆向分支（驳回→回退到草稿→重新编辑）。根因是 `用例数据推演` 只跑了正向路径，没推演逆向。

**实现任何状态机前必须验证：**
1. 正向路径：每个状态可达
2. 逆向路径：每个 reject/rollback 回到合法的可编辑状态
3. 重新提交：回退后表单可编辑
4. 所有状态转换都有对应的 UI 按钮
5. 审核类按钮由角色控制（supervisor only）

Codex 无法检测这类缺失——它只比较代码和 PRD 文本，不会发现"PRD 本身漏了逆向路径"。需要人工推演。

## 前端 UI 标准审计（配合 UI-DESIGN.md 落地——2026-08-28 forge-scrm 实测）

当用户抱怨"Codex 做的 UI 很丑/不协调/随意"时，按两步走：

1. **先立标准再审计**——项目通常只有 theme.ts（视觉 token）没有 UI 规范文档。先起草《UI 标准》段落（间距 8px 栅格五档/Drawer 宽度三档 480-640-720/Modal 520-720/状态色板唯一来源 statusTagColor()/按钮层级 primary 每视图≤1+行内禁 primary+danger 只给不可逆+操作列 size=small/所有 Table 必设 emptyText/页面骨架），再按标准全站走查。
2. **标准解耦存放**：标准正文放 `frontend/UI-DESIGN.md`（唯一维护处），AGENTS.md 只加指针小节（不复制正文）——单一来源，与 CLAUDE.md→AGENTS.md 指向模式一致。
3. **分级输出**：【严重】（不可逆操作无确认拦截、行内 primary 滥用）优先修；【建议】（emptyText 缺失、任意间距值）抽共享常量批量修（如 tableEmpty.ts + AST 扫描补齐 25 处）。
4. 审计可交给 delegate_task 子代理（只回分级清单不进主上下文），功能审计与 UI 审计并行两个子代理。

### UI 规范库 ↔ 代码实际值取证（规范落地审计，2026-10 实测）

当要优化的对象是**设计规范库本身**（Token 基线 / 组件清单 / 布局规则）而不是代码时，做法是反向取证：拿代码里实际在用的值去衡量规范覆盖度。四条硬口径：

1. **全量频次，不许抽样**：每个数值类都要给「取值 + 出现次数 + 文件:行号」。只贴一个例子就下结论的交付直接退回——规范审计的价值全在频次分布上，单点无法判断是普遍用法还是孤例。
2. **统计前先归一化**：色值要先展开简写、统一小写、去掉函数内空格（`#fff`→`#ffffff`、`rgba(0,0,0,.04)` 与 `rgba(0, 0, 0, 0.04)` 合并），否则同一颜色被算成多个值，去重数和 Top 榜全是假的。归一化前后各给一次数字，并列出被合并的组。
3. **要求它交「取证方法说明」**：扫哪些目录、用什么正则、频次怎么计数。口径看得懂才能判断结论可信；口径含糊的时候，数字好看也不当验收依据。
4. **只报现状，不许夹整改建议**：这一轮的红线是「不写建议」。审计层混进方案会让后续拍板被带着走。

**组件覆盖核对的两个口径陷阱（踩过）**：

- **只认 `export function` 会漏掉真正在复用的 UI 单元**：大量 B 端项目靠 CSS 类 + 原生元素复用（`.cms-input`/`.tool-table` 这类），组件清单必须再做一轮「CSS 类级组件」——按可复用 UI 语义筛、要求跨两个以上文件使用、状态修饰类归到父类。只扫 React 导出会把规范缺口的主体遮住。
- **页面级组件不算「组件规范缺口」**：pages 下的页面全部列进缺口等于把清单淹了，页面对应的是「页面模板」那一层规范，需要单独核对。

**命名对不上 ≠ 规范过期**：规范写 `AppHeader`、代码里叫 `Header` 时，正解是**把规范侧改成实际名字**，不是删条目、也不是让代码改名。审计报告里这类要单独标「命名不一致，需规范侧对齐」。

**结论方向：规范窄于代码现实时，反向回填而不是反向改造**。当审计显示规范只覆盖了一小块、代码自己长出了一套（典型：规范写 1 条阴影、代码 18 条；规范 4 档圆角、代码另有 4/6/7px 各二三十处；语义色、间距细则整块空白），正确处置顺序是：先补空白类（语义色 / 阴影 / 圆角 / 间距），再把漂移值收敛成规范值，最后才谈改代码。直接发「让代码对齐现有规范」的指令 = 把大量既有实现判成错误，返工量不可控。

**口径未定的阶段不要提前铺开下一阶段（防返工）**：审计分阶段做时，若后续阶段要引入外部基准（如设计稿导出数据）才定口径，先停在前一阶段并**把已产出的中间结果落成文件存进仓库**（不提交也可以）——只留在 agent 对话里的结论，会话一关就白跑。用户自己会说「等外部数据回来再做，不然可能返工」，这时不要为了赶进度先做差异化口径的下一轮。

## 全栈代码验收抽验（2026-08-24 forge-scrm 85 API 实测）

当 AI（Claude Code/Codex）生成了**完整前后端系统**（FastAPI + React）而非单页原型，验收不用逐行读，用**四类抽验**覆盖关键风险：

1. **端点清单抽验**：`grep -n '@router\|def ' backend/app/routers/*.py` —— 按模块核对端点是否覆盖 PRD 功能清单；重点看**状态流转端点**是否成链（如脚本：generate→create→update→versions→diff→submit→review→mark-used→discard，一个都不能少）和**回写/反哺**类双写端点（writeback_material + writeback_topic 分开才算完成 R7）。
2. **安全抽验**：`grep -c 'bcrypt\|jwt' app/core/security.py`（>0）；`grep -rn 'sk-[a-zA-Z0-9]\{20,\}'` 应 0 命中；`.env` 确认被 .gitignore 排除（`git ls-files | grep '\.env$'` 应为空，只留 .env.example）。
3. **范围红线抽验**：`grep -n` 一期不该出现的功能关键词（自动采集/定时任务/语义去重/扫码登录/版本表）在 services/ 应 0 业务实现——只在 models 或注释里预留结构。
4. **状态机落位**：核心字段清单的 enum 与代码 enums.py 一致；关键业务状态（如脚本四态 待审核/已通过/已使用/已废弃）在 service 与 model 双处可 grep 到。

配套纪律（本会话血泪）：
- **命令简化**：多关键字组合 grep 会被安全拦截（`BLOCKED (hardline): command parser limit`）——拆成单条简单命令逐项验证，别用超长复合命令。
- **Agent 自报 ≠ 交付**：Claude 自检报告说"43/45 验收通过"后，git pull 发现仓库无新提交——代码还在 Mac 本地。**先让用户 push，pull 到 VPS 副本后再抽验**；抽验 grep 的是 VPS 副本的实际代码，不是报告文字。
- **抽验看端点名 + summary 注释**：FastAPI 的 `summary="..."` 常直接标注业务规则（如"标记已使用（R15/D4：仅已通过可标记）"），grep 端点时一并抓到，等于同时验证了规则落位。
- **技术决策先行**：开发指令里把待澄清项（同步/异步、CSV 模板、惰性过期、存储位置、JWT 有效期）先给默认决策让 AI 执行，它自检报告里的"遗留风险"才能收敛成真问题清单而非"待确认"堆积。
