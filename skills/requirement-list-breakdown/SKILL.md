# 在线需求表 · 功能点拆解

## 何时用
- 用户把在线需求表（WPS/飞书表格）截图发来，说"帮我补充下""现在要写 X 这条需求的了"
- 要把一条需求拆成"1级菜单 → 5级功能点"填进他正在维护的表

## 先确认表头，别凭印象列列名

真实表头是这七列（从左到右）：

```
所在端 | 1级菜单 | 2级菜单 | 3级菜单 | 4级功能点 | 5级功能点 | 功能点描述
```

左侧另有需求层的大列（需求人 / 提出时间 / 期望完成时间 / 需求名称 / 主要场景 / 需求价值），这些是他自己填的，你只供右侧拆解。

**动笔前先用 vision 把表头逐字读出来**，不要拿"1级菜单/2级菜单/3级菜单/4级菜单/5级菜单"当表头——4、5 级叫**功能点**，且最后一列叫**功能点描述**，写错列名他没法直接粘。

## 铁律 1：粒度到功能点，不到字段

**一个 4级功能点占一行，字段名全写在该行的「功能点描述」里，用顿号隔开。**

- ✅ `列表页 | 新增列表展示字段 | 首次添加时间、最新添加时间、所属门店、导购ID、好友标签、备注…`
- ❌ 把每个字段拆成一行（"新增门店列""新增导购ID列""新增首次添加时间列"…）——他会直接说"太细了，不要到字段分行"

**这与字段清单 TSV 的粒度正好相反**：字段清单 TSV 要求每字段独立成行、禁止折叠；需求 list 要求按功能点聚合、字段写在描述里。别把上一个任务的习惯带过来。

## 铁律 2：菜单层级别自造，去项目里查真实菜单树

1-3 级菜单必须是系统里真实存在的路径。来源优先级：

1. `01-全局背景信息/参考资料/CMS知识宝典*.md` 的「菜单结构总览」章节（一级模块 + 二级菜单 + 页面 ID）
2. 原型源码的菜单配置（如 `99-产品原型prototype/src/config/menus.ts`）——这是唯一的运行时真相，知识宝典过期时以它为准
3. 页面采集记录（`.../02-页面采集/<模块>/P-XXX-*.md`，含菜单路径与列字段）

原型菜单常与知识宝典不一致（同一能力在不同版本被挪过位置），**两者冲突时以原型源码为准，并把这个差异告诉用户**。

**用户原表里的菜单名也要核，别照抄**：他维护的表是历史累积的，层级和名字都可能过时。逐字比对 `menus.ts` 的 `label`（**含大小写**——原型里是 `whats管理工具`，不是 `Whats管理工具`），不一致就改并说明理由。典型错法是把页面内的操作当成菜单层写：原表写 `触达计划 > 计划创建/编辑`，原型实际是 `触达计划 > 计划列表`，而"新建/编辑计划"只是列表页上的按钮。

**菜单层级有硬上限**：外销 CMS 的菜单模型是 `Module(顶部) → MenuGroup(左侧) → MenuLeaf(左侧)`，`MenuLeaf` 没有 `children`，所以**菜单最多 3 级**。写"这条需求在哪"时，`受众圈选`（向导第 3 步）、`行为`（页面内页签）这类**页面内结构不是菜单层**，但需求表需要一个位置容器，就顺次填进 3/4/5 级——这是表的结构约定，不代表菜单真有那么深。落笔前先想清楚每级填什么，评审时会被问"为什么这组只到两级"，要能答上来。

**判断某一层是不是真层级（而非引用入口）**：看页面 URL 的路径前缀。内销"自动打标"在 `/main/qywx/qywx/label/autoMark`，"标签库管理"在 `/main/vsnow/gadgets/customer-base-management`——前缀不同说明后者是从别的模块**引用**挂进来的，上面那层"工具中心 > 企业微信管理"只是入口，不算层级。别照抄看起来的深度。

## 铁律 3：字段来源先查接口文档，别猜"接口有没有"

`01-全局背景信息/参考资料/接口分析/01-接口文档地图.md` 里有按「接口名 × 字段名」组织的全量字段表，能直接回答"这个字段接口返回了吗"。

- 接口已返回 → 写"取接口 `xxxName`，接口已返回，仅需前端展示"（开发一看就知道零成本）
- 接口没有 → 明确说"接口无此字段，需服务端统计/新增"
- **可信度自检**：该文档的证据列写着「从 JSON 示例注释提取」——字段存在这件事可信，但**中文字段含义可能不准**。遇到语义含糊的字段（如 `addTime` 备注写"账号添加时间"，但可能是好友添加时间）标"待技术方确认实际语义"，不要直接当成用户要的那个含义写进需求。

## 铁律 4：筛选项 ≠ 列表字段，不一一对应

用户会明确反对"加了一列就配一个筛选"。筛选项按**业务真会用到的**挑，其余靠导出后在 Excel 里自己筛。

- 列表字段可以很多，筛选项保持克制（常用的是：时间区间、组织/门店、标签）
- 现有筛选项保留不动，只列**新增**的
- 给建议时先给最小集，让他往上加；一次给一长串会被打回"好多筛选条件啊"

## 铁律 5：导出类功能点必须写清范围和边界

一行功能点描述里要包含：导出范围 / 导出字段 / 格式 / 上限 / 权限。

- **范围写"导出当前筛选条件下的全部结果，含当前页，不受分页限制"**。绝不要写"非当前页"——它读起来是"不含当前页"，正好相反，用户会当场问"我筛选完导出，当前页数据不应该也在里面吗"。
- 上限、大数据量处理（同步下载 vs 异步任务）、导出权限这三条**标待确认**，别替开发决定。

## 铁律 6：不写"不支持"的功能点

"列头排序不支持"这类**明确的否定项不进需求表**——它不是功能点，占一行只会让开发误会要做什么。用户原话："不写，免得误会"。这类边界口头讲，或放评审时的说明里。

## 铁律 7：待确认写在描述里，不单开行

"口径待业务确认""待技术方确认"直接写进该功能点的描述末尾，不要为待确认项单独占一行。

## 交付形式：默认发文件，他说"聊天框发我"就贴原文

他要把内容粘进在线表，**聊天里贴出的 TSV 会显示成一片文本、不是表格**（用户会说"你发我的不是表格形式呢"）。

- 默认落一个 `.tsv`（制表符分隔、UTF-8），用 `MEDIA:/绝对路径` 发给他，打开就是分好列的表格，可整块复制
- 文件名带上范围：`<模块>-功能点拆解-精简.tsv`
- **交付通道听他的**：他说"直接在聊天框发我，我来复制""我要填 Excel，甚至可以让本地 agent 转 tsv"时，就把 TSV 贴进代码块——他要的是能直接复制的原文，不是附件
- 出"总的需求 list"时，需求层的大列（需求人 / 期望完成时间 / 需求名称+链接 / 主要场景 / 需求价值 / 所在端）要**逐行重复填满**，一个功能点一行，他粘进 Excel 后合并单元格即可；不要只给右侧菜单功能点让他自己对

## 迭代节奏：他是否定式收敛，不是一次给全

这类表他会连续否几轮（太细 → 筛选太多 → 口径不对 → 表述有歧义）。预判：

1. **第一版给粗粒度**（功能点级），不要一上来就拆字段
2. 他砍的时候**不要争**，按他给的边界重出一版，并在回复里说明"相比上一版改了什么"
3. **他说"不用进 list"的东西就别再往里塞**——比如交互规范（表头内嵌搜索、回车搜索、清空重置）他明确说"等后面出原型的时候这样就行"
4. 每轮只回答"改了什么 + 还有什么要他定"，不重述整张表

## 相关但不同的产物

- **字段清单 TSV（13 列）**：字段级、每字段一行、禁折叠 → 用 `field-list-tsv`
- **需求 list 功能点拆解（7 列）**：功能点级、字段写在描述里 → 本技能
- **PRD / 评审档**：讲页面、规则、验收 → 用 `prd-doc-authoring` 一类
