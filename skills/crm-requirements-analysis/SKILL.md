# 需求分析与 AI 产物验收方法论（用户定稿 2026-09-14）

## 需求分析 ≠ 出产品方案

需求分析是**决策过程**：拆解→排序→取舍→定本期范围，产出的是**分析报告/优先级清单**，不是 PRD。**范围锁死后才进入 字段清单→业务PRD→DemoPRD 流程**。范围没定就写方案 = 返工。

### 七步法
1. 拆子需求：按"解决什么/给谁/哪个业务环节"拆，**不按技术拆**。
2. 分类定性：核心链路(没它闭环断)/增值/支撑。
3. 四维估：价值/成本/风险/依赖（或 RICE）。
4. 找依赖串联：哪些是另一些的前置，排不出先后即没理清。
5. 取舍分期：定本期做哪些、二期哪些、砍/延哪些，砍要有理由。
6. 列待确认：需求矛盾/口径/优先级冲突，列出来问业务，不许猜、不许自行定。
7. 产出分析报告：表 = 子需求|价值|成本|依赖|优先级(本期/二期/砍)|理由 + 待确认清单。

## 新增判定铁律（最怕"已有能力评估成新开发"）

标"新增/新开发"前必须过**两关**，两关都过才算新增：
1. 生产环境 DOM 确证该能力不存在（Cursor/抓包已抓该模块/页面，找不到对应功能/字段/路由）；
2. 跨系统确认也不存在（相邻系统如 VK/v消息/销冠 能否复用/对接），别只查一个系统。
有一处已存在/可复用 → 一律标"增强/补指标/对接复用"，不标"新开发"。

### 铁律：以真实生产系统为准
- **需求池文档没提 ≠ 系统没有**。判断以生产系统实测(DOM/BI board/页面)为准，不以需求文档为准。
- 已有能力按"补指标/增强"评估，只有真实系统里确实没有的才算新开发。
- 核心翻转范例：报表线上已接 BI 看板(board 编号可证) → 从"从零做"改"添加指标"做；已有框架补指标、没有的才新增。

## 填在线需求 list 的功能点拆解表

用户在在线表里维护需求 list，每行按 `所在端 / 1级菜单 / 2级菜单 / 3级菜单 / 4级功能点 / 5级功能点 / 功能点描述` 拆功能。**先让他发表头或读图确认列名**——别按自己想象的列（"4级菜单""5级功能点及描述"）去拼，列名不对整份没法粘。

### 粒度：一行一个功能点组，字段清单写进描述列
**不要一个字段一行。** 一次任务里会连续被纠正三轮：
1. 拆到字段分行 → "太细了，不要到字段分行"：合并成"新增列表展示字段"一行，字段用顿号列在描述里。
2. 给每个字段配一个筛选项 → "这样就是新增列表的字段都要在筛选上体现了"：**列表字段 ≠ 筛选项**，不是加了一列就得加一个筛选。
3. 筛选项给了三个 → "好多筛选条件啊"：**能少不多，通常只留 1 个**。

判断逻辑：筛选项只解决"系统里不筛就导不出来"的问题；导出到 Excel 后业务能自己筛的门店、标签、次数，一律不进系统筛选。所以筛选区常常只加一个时间区间（作用是限制导出范围）。

### 时间筛选别做"类型下拉 + 一个区间"
列表里同时有两个时间列（如首次添加时间、最新添加时间）时，用一个下拉只能选其一——读者会问"两个都想筛呢"。要么两个独立区间（可 AND），要么按上条只留最常用的那一个。省版面不能牺牲能不能筛。

### 先查接口文档再定字段，别凭字段名猜
项目通常带 `01-全局背景信息/参考资料/接口分析/01-接口文档地图.md`（按「接口名」搜，一行一字段，含字段名/示例值/中文含义/证据）。用途：判断"这个字段接口已经有了、只需前端展示"还是"根本没这个字段、要服务端新做"——两者工作量差很远，写进拆解表能直接省掉一轮评审追问。
**可信度要看证据列**：标着「从JSON示例注释提取」的，字段存在可信、中文字义未必准，涉及关键口径仍要标"待技术方确认"。

### 先问清数据的流向，再定范围
同一个页面，"我们做功能"和"我们落表、别人取数展示"是两种完全不同的范围。做报表类需求前必须问：**谁生产数据、谁取数、谁做页面**。答错会把"我们只做接口/落表"写成"做整页功能"，凭空多出十几条功能点。

### 交付形态：给 .tsv 文件，不要聊天里贴 TSV 文本
他要"能快速复制的"表格时，**在聊天里贴制表符文本不算表格**（"你发我的不是表格形式呢"）。产出 `.tsv` 用 MEDIA 发文件，WPS/Excel 打开自动分列，他直接框选复制进在线表。

### 待确认要落在行里，别只在回复里说
字段口径没定的（数据源不明、统计口径待业务确认、单次导出上限、导出权限），写进「功能点描述」列并标"待确认"——评审时这些恰恰是会被逐条追问的。**但只标真正需要对方答的**，属于数据方和业务之间对口径的（如"新增好友数"算首次还是算所有添加动作），不进我们的功能点。

## AI 产物验收铁律（判断 agent 真吸收还是复读）

- **带证据的自我修正 = 真吸收**：如 v2 报告"我原来 X 判断被生产证据推翻、现改成 Y"。
- **复读骨架/空口"完成/读完了/消化了" = 没吸收**。别接这些空口，让它拿产出/证据证明。
- **三态汇报**【已完成/待确认/未做】+ 贴 commit/hash/远端 HEAD 证据。
- 自报不可信，**以生产系统/远端实测为准**（曾：agent 报"迁移完成"实际没 commit/push，报"推送成功"实际是空口）。
- 教训：agent 把已完成的事用"要不要继续/搁置"待办口吻复述 = 制造假信号误导决策，要立三态纪律。
- 实例：已有能力评估成新开发是最贵的错——既白烧研发又错过便宜的"补/增强"路。
