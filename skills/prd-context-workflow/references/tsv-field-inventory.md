# TSV 字段清单方法论（字段事实源的标准做法）

> 来源：维生素 AI 课程「项目实战篇」（QS-ERP / QS-JXC 进销存项目实战），2026-09-07 深度解读。
> 适用：任何要用 AI 产出 PRD/字段清单的 B 端项目。核心 = **字段清单用 TSV，不用 md 表格、不用 Excel；初稿/详细稿分层；字段事实/业务规则/页面交互三层分离。**

## 一、为什么用 TSV 做字段清单（不用 Excel、不用 md 表）

TSV = Tab-Separated Values（制表符分隔值），纯文本，每列 Tab 隔开。老师原话逻辑：**"用 TSV 是为了方便快速编辑和确认，让 AI 能帮你做预测和走查确认，不要用 Excel。"**

三大理由：
1. **纯文本 → AI 能直接读写**（Excel 是二进制，AI 处理费劲）
2. **字段多时比 Markdown 表格更好维护**（md 表字段一多就乱、对不齐）
3. **配合 AI IDE 的预测性自动补全** → 填一列自动预测下一行（Cursor 装 TSV 插件后效率高）

## 二、字段清单分两版：初稿 → 详细稿

**初稿（5 列）——先确认"有哪些字段"：**
```
字段所属分组 | 字段名称 | 字段类型 | 字段来源 | 字段说明/描述
```

**详细稿（13 列）——再定义"字段在产品上怎么表现"：**
```
字段所属分组 | 字段名称 | 字段类型 | 字段来源 | 必填性 | 新增页 | 编辑页 |
列表展示 | 可筛选 | 详情展示 | 字段说明/描述 | 取值说明 | 备注
```

**为什么分两版**：先确认"有哪些字段"（初稿快、问题早暴露），再定义"每个字段完整规格"（详细稿）。一步到位容易乱。

**铁律**：
- **详细稿确认后 = 字段唯一事实源**；初稿只留作过程记录，不再更新维护
- **只保留 TSV 一份，绝不维护对应的 Markdown 副本**——否则出现"字段清单.tsv + .md 两份、不知道哪份最新"的灾难

## 三、TSV 该放什么、不该放什么

**✅ 放（字段本身的稳定信息）**：字段分组 / 字段名称 / 字段类型 / 字段来源 / 必填条件 / 取值格式枚举 / 字段说明 / 字段级约束 / 计算或回写说明

**❌ 不放（属于页面交互，进前端 Demo PRD）**：查询区位置、控件占几列、placeholder、下拉列表样式、远程搜索触发、加载中/空结果/失败反馈、错误提示位置、页面布局按钮排列

## 四、三层分离（TSV 方法论的核心）

同一个"采购数量"：
| 层 | 内容 | 放哪 |
|---|---|---|
| 字段事实 | 整数、>0、来源用户填写 | 字段清单 TSV |
| 业务约束 | 提交审核时每个明细行必填；审核后不可改 | 业务 PRD |
| 页面交互 | 用 NumberInput；失焦校验；错误定位到明细行 | 前端 Demo PRD |

三层不是重复，是分别回答：**字段是什么 / 业务怎么限制 / 页面怎么让用户完成操作**。

## 五、字段清单逐步丰富（6 步）

1. 找竞品/参考系统做参照起点
2. 手动填初稿骨架（5-10 个字段起）
3. 让 AI 辅助补全（预测补全）
4. **人工走查**（查编造字段/类型/取值，标记已确认 vs 候选）
5. 让 AI 输出详细稿（13 列）
6. **再次人工走查**

## 六、版本迭代法（已有模块加需求时）

不覆盖第一版：在 `03-产品设计/` 下新建版本目录（如 `20260803第一版` → `20260820第二版`）。第一版保留作基线，第二版放本轮新内容；给 AI 明确上下文范围（默认读第二版），防版本边界混。

## 七、词条/字段库的分层结构（多语言/多系统场景，2026-09-07 用户设计）

当字段/词条要跨系统复用时，结构：
```
业务 BU（空间）        ← 管业务边界 + 权限
  └─ 系统/应用          ← key 在此层唯一
      ├─ 默认源语言
      └─ 目标翻译语言
         └─ key（应用内唯一，中文名可重复）
```
关键约束：**key 在应用层唯一**（不是全局/空间）；**中文名（原文文本）可重复**——同一句中文在不同 key/场景下译文/定义可不同，语义靠 key 区分场景。落地难点：**key 的来源与命名治理**（谁建、命名规范、防语义重叠）——比"key 唯一"本身更难。

## 八、给 AI 下任务的结构（先给边界，再给任务）

```
输入材料：本次要读取哪些背景/流程/字段/相关单据PRD
当前任务：本次只输出 XXX（业务PRD / 页面骨架 / Demo PRD 之一）
权威边界：字段以TSV为准，业务规则以业务PRD为准，页面交互以Demo PRD为准；
         发现冲突先列出，不自行补成已确认事实
输出要求：说明产出了什么，影响哪些下游文件
```
**一次只让 AI 输出一个层次**，不要同时生成字段/规则/页面/原型。

## 九、与现有 Forge 项目的关系

forge 四项目（wms/erp/crm/scrm）现有字段清单**全是 `.md` 表格**（已接近详细稿列结构）。理论升级点 = 载体改 TSV + 初稿/详细稿分层 + 只留 TSV 不维护 md 副本。**用户已定：工作日不改造 forge 项目**，此方法论先用于公司 CMS + 娜美。
