# PRD 优先 + Context 回写工作流

> 适用于任何需要新增业务单据的项目。先定义地基规则,AI 按规则生成 PRD,评审后回写修正,最后前端实现。

## 文档基线化（现状重写，2026-08-04 实战——接手已有代码项目、文档过时时的标准流程）

**触发场景**：用户拉取一个已开发完成的仓库（如 lophy-jarvis-voice），要求"补填 context 和 PRD"——此时 context 是历史规划态（写"待开发/待融合"），实际代码早已实现。**不能按规划态补文档，要先摸现状再按现状重写**。

**流程**（git clone → 摸现状 → 用户定口径 → 重写 → commit）：

1. **git clone + 全面摸现状**（不假设文档对）：
   - `git log --oneline`（权威变更时间线，先看这个）
   - `package.json`（技术栈真实版本，别信 AGENTS.md 里过时的技术栈描述——本次 AGENTS.md 写"React Router HashRouter"但 package.json 无 react-router，实际是单页条件渲染）
   - `find src -type f`（模块地图以实际代码为准）
   - 读现有 context/ 和 prd-docs/（识别哪些是"规划态"哪些是"实现态"）
   - 看 server/ 后端代码（契约以代码为准，别凭记忆）
   - `git status --short` 确认工作区干净

2. **先问用户文档口径**（关键决策，别自作主张）：
   - "按当前最终版整理"（文档描述真实现状，历史规划单独存档）vs "按规划目标整理"（继续作为阶段项目）
   - 本次用户选：**按当前最终版整理；融合规划归入历史路线；语音功能暂无迭代计划**
   - 选型影响整个文档体系的方向，必须先确认

3. **重写 context 体系**（本次产出 01-07）：
   - 01 业务背景与项目范围：能力清单全标 ✅（已完成），明确"不做"清单，历史规划（如融合）单独 § 存档
   - 02 功能清单与模块地图：以实际 src/ 文件树为准画模块地图
   - 03 核心业务流程：参数与实际代码对齐（VAD 阈值、超时、批次大小）
   - 04 现状与边界（新增）：AI 开工前必读的状态锚点——一句话现状、版本状态、能做什么/不能做什么、技术债、决策记录、高频陷阱
   - 05 接口与数据契约（新增）：后端权威契约（端点/方法/请求响应/认证），前端适配
   - 06 技术架构与部署（新增）：整体架构图、技术栈、部署流程、配置位置、资源限制
   - 07 版本与回滚规范（新增）：git 基线铁律、versions/ 快照机制、回滚流程、打包规范

4. **PRD 目录组织（用户 2026-08-04 定）**：
   ```
   prd-docs/
   ├── robin-主PRD-v1.2.md              ← 主 PRD（当前最终版基线，根目录）
   ├── robin-验收清单-v1.0.md           ← 验收清单（根目录）
   ├── robin-prd-v1.1-历史融合规划-存档.md ← 旧版归档（改名标记，不删）
   ├── 语音模式/README.md               ← 语音模式迭代 PRD 分目录
   └── 文字模式/README.md               ← 文字模式迭代 PRD 分目录
   ```
   **规则**：主 PRD 放根目录描述整体基线；后续各模式迭代 PRD 按模式分别放入对应文件夹（文件名 `robin-voice-iter-v{n}.md` / `robin-text-iter-v{n}.md`）；迭代 PRD 只写本轮改动，完成后回写主 PRD 状态。

5. **验收清单**（新增，与主 PRD 配套）：
   - 部署后快速验收（构建/部署/功能标记 grep/浏览器冒烟）
   - 分模块详细验收（登录/文字/语音/记忆/后端服务）
   - 语音流式指标判定表（chunk×/流式命中×/源/预览×）
   - 回归清单 + 已知限制（区分"限制"与"缺陷"）

6. **commit + push**：
   - commit 备注写清变更大纲（本次：context 01-07 重写 + 主PRD v1.2 + 验收清单 + prd-docs 分目录）
   - **VPS 上 git push 到 GitHub 会失败**（无 https 凭据：`fatal: could not read Username`）——VPS 只做 commit，push 要么走 SSH key（见 vps-git-push-setup），要么把改动打包发给用户在 Mac 本地 push，要么让用户在 Mac 操作

**踩过的坑（0804 新增）**：
- 别信 AGENTS.md 的技术栈描述，以 package.json + 实际代码为准（本次 AGENTS 写 React Router，实际无）
- 文档"能力清单"标注过时的 ⬜ 待开发项会误导后续 AI——按现状重写时全部改为 ✅ 或移入"不做"清单
- 旧 PRD 用 `mv` 改名加"-历史-存档"后缀，不删除（git 保留重命名历史，diff 更干净）
- 用户中途要求改目录结构（如本次"分语音/文字两个文件夹"）——先做，再 commit，一次到位

## 问卷/待确认清单回收后的回写纪律（2026-08-24 forge-scrm 实战）

**触发场景**：业务问卷或待确认问题清单（如发给姐夫/客户的问题）回收后，需要把答复落进文档体系，标记从"待确认"变为"已确认"，并让规则表/主PRD/draft 三处一致。

**回写流程**（一次 commit 完成，别分多次）：
1. **先 grep 全部 `待确认`/`⚠️` 标记**：`grep -rn '待确认\|⚠️' context/ prd-docs/ --include='*.md'`——拿到所有待确认点的完整分布，逐处回写，防漏（本次 7 项分散在 context/02/04/05/06 + 主PRD §10 + draft 共 6 文件）。
2. **规则表新增编号**：新确认的规则进全局规则表（如 R9/R10/R11），原"待确认"行改为"✅ + 确认结论 + 来源编号"（如 R9 脚本默认基于选题，4.1 确认：选题为主、独立为辅）。
3. **文件头状态同步**：每个被改的 context 文件头部 `> 状态：` 行从"⚠️ 待确认"改成"✅ 已确认（日期回写）"。
4. **主PRD 的待确认清单改"已回收"**：保留原问题表但要加"姐夫回复"和"落位"两列（指向 context 文件 §），让 PRD 与 context 可追踪。**不要直接删问题**——留痕供评审追溯。
5. **draft 标记全部回收**：发给对方的原始问题文档头部改为"✅ 全部回收（日期）"，加回复记录表（#/问题/回复/状态）。
6. **一次 commit + push，备注列全 7 项结论摘要**。VPS push 失败时先 `git pull --rebase`（远端可能有 Mac 的新提交，本会话 notes-vault 就撞过一次）。

**注意**：残留未回复项（如设备 6.8）保留 ⚠️ 并注明"二期再确认、不阻塞"，不要假装全绿。

## PRD 套件产出模式（2026-08-24 forge-scrm 定稿实战）

业务地基（context 六件套）定稿后，产出整套 PRD 的标准结构：

```text
prd-docs/
├── 主PRD.md               # 总纲：概述/In-Out Scope/用户故事/流程/状态机/验收/待确认
├── 核心字段清单.md        # MySQL schema 前身：13+ 实体表，每实体含 PK/必填/唯一/外键/索引
├── mvp验收清单.md         # 编号用例（M01..M38 + S01..S03），按模块分组，覆盖正常+边界+异常
├── modules/
│   ├── 01-资料库PRD.md     # 每模块 8-9 功能、独立状态机、权限矩阵、验收用例
│   ├── 02-选题库PRD.md
│   ├── 03-脚本库PRD.md     # 该模块核心规则单独展开（如版本历史机制）
│   ├── 04-数据分析PRD.md
│   └── 05-权限与账号PRD.md
└── templates/
    └── prd-template.md    # 模块 PRD 统一模板，后续模块按此填充
```

模块 PRD 标准结构（写进 templates/prd-template.md 供复用）：模块概述 → 功能清单(In/Out) → 交互流程(Mermaid LR) → 关键规则(引用 context R 编号) → 状态机(Mermaid) → 数据字段(引用 context/05 SSOT，不重复定义) → 权限矩阵(两级角色) → 验收标准(勾选式) → 待确认事项。

**产出纪律**：
- 字段/状态/枚举一律引用 context 编号（R1-R11、context/05），**绝不新造**；如确需新增必须标"新增建议，待确认"；
- 主PRD §10 待确认清单改为"已回收"表（问题/姐夫回复/落位三列），**不删问题留痕**；
- 验收清单编号体系：`M##`(模块用例) + `S##`(跨模块系统用例)，每模块末尾给汇总（用例数/通过数）；
- 字段清单就是建表依据，直接可交后端开发（本会话交付 Opus 用）。

## 文档产物分工：第一版 Hermes 亲自写（2026-08-24 用户拍板）

**触发场景**：用户说"文本型产物应该你给指令让 codex 来跑"之后又改口"还是你写吧，第一版你写靠谱点，毕竟有充足的上下文"。

**规则**：**PRD/字段清单/验收清单第一版由 Hermes 亲自写**——因为判断层持有完整上下文（问卷回复、业务推演、state 机、SSOT），直接产出最准、不会跑偏；Codex/Workbuddy 用于**批量/迭代**（第二版起、多文档重复劳动、按模板填充）。用户原话："第一版你写靠谱点，毕竟有充足的上下文"——这调和了本 skill 旧表述"Workbuddy 管 PRD 生成"：分工 = 判断层出第一版 + Agent 跑批量迭代，不是一刀切全交 agent。

**配套**：Hermes 亲自写时若上下文接近满，先读完关键 context 文件（实体关系/字段 SSOT）再开写，避免写到一半发现引用错误；一次 commit 含全部套件（模板+模块+清单），备注列清结构。

## 文档审计指令模式（2026-08-24 forge-scrm 实战）

PRD 套件产出后、进入开发前，用 Codex 做一轮全量**只读**审计（用户拍板"审计一遍"）。指令要点（五段式）：
- **审计范围**：全部 context/ + prd-docs/（主PRD/模块PRD/字段清单/验收清单）+ templates/ + draft/ + AGENTS.md——16+ 文件全查，不含糊；
- **六维度**：①一致性（模块 PRD 字段/状态/枚举/规则 vs context；主PRD vs modules；context/03 实体 vs 字段清单表/关系；context/06 权限矩阵 vs 各模块权限段；mvp验收用例 vs 主PRD §8；7+1 项已确认结论是否全部回写，逐条核对）②引用完整性（R 编号/章节号/字段名/枚举值是否真实存在）③状态机一致性（context/04 vs 各模块 PRD，状态名/流转/派生态无出入）④结构规范性（是否按 prd-template 9 段）⑤缺口（modules §9 待确认是否归档 draft、requirements 结论有无遗漏、NIS 一致性、AGENTS.md 规则转述是否准确）⑥笔误（错别字/Mermaid 语法/编号跳号重复/表格缺列）；
- **分级**：P0（事实冲突/规则矛盾/会导致开发做错，必须修）/ P1（引用错误/结构缺失/状态不一致，应该修）/ P2（笔误/表述不清/优化，建议修）；每条含位置+问题+建议修法；
- **红线**：纯只读不修改任何文件、不 commit/push/部署、不臆造 context 不存在的内容（拿不准标"需人工确认"）、不新增文档；
- **输出**：完整报告在回复中（不写入项目文件），必含"7+1 项确认 vs 回写位置核对表"逐条标 ✅/❌；另附自检报告上传 ai-reports 管道；
- **后续**：报告回传 → Hermes 核对 P0 逐条修复回写 context/PRD → 再进入开发（开发前门禁）。

## 项目规则文件体系（AGENTS.md / CLAUDE.md / .cursor/rules，2026-08-24 用户定稿）

多 Agent 协作项目（Codex/Cursor/Claude Code/反gravity 共用）的规则文件分层：
- **AGENTS.md = 唯一权威规则主体**：项目是什么、文档权威层级、目录速查、关键业务规则（R 编号）、状态机、字段 SSOT 位置、技术栈方向、工作流程铁律、红线禁止、当前状态。所有 agent 共享这一份；
- **CLAUDE.md = 只做入口索引**：一行指明"读 AGENTS.md"并声明"新增/更新规则写入 AGENTS.md，不要写本文件"——避免同一条规则多处维护产生不同版本（单一来源哲学）；
- **.cursor/rules/*.mdc = IDE 行为规范**（编码纪律：先思考再动手/以前为先/精准修改/目标驱动），与项目知识分开；
- **用户偏好：不要把"不同 agent 各自的职责分工"写进 AGENTS.md**（用户原话："不用补进去，反而会有点限制，我们自己知道怎么用就行，灵活点"）——分工是会话级知识，写死会僵化派工，灵活应变优先；
- **交付文件内容也是单代码块**：把 AGENTS.md/CLAUDE.md 等文件内容发给用户复制时，整段放一个代码块（见 a2a-instruction-format 的 Copyability gate 扩展）。

|:---:|------|------|
| 1 | PM 定义 scope | 复用在具 context/ 文件(04功能清单/05编码规则/07边界/08术语) |
| 2 | AI 生成 PRD 初稿 | 主PRD + 字段清单(SSOT) + Demo 列表页 + Demo 新增编辑页 |
| 3 | PM 走查 | 检查单号规则/术语一致性/状态机/SSOT 矛盾 |
| 4 | PM 回写 context | 新单号前缀写入 context/05,新模块写入 context/04 |
| 5 | AI 同步修正 | 字段清单 + Demo + Changelog 对齐(不重生成,只改矛盾处) |
| 6 | PM git commit | 反重力做 git 操作,VPS 只 pull |
| 7 | 确定 UI 框架 | 新 B 端系统必须用组件库,禁止 Tailwind 纯手搓。React→AntDesign/Sha/Xdcn/UI, Vue→VbenAdmin/ElementPlus |
| 8 | 前端实现 | 参照 PRD 套件,用确定的组件库开发表单和列表 |

## 走查红线

```
- 单号前缀是否在 context/05 中存在(不在则先回写)
- 术语是否对齐 context/08(商品非药品、模块名对齐 context/04)
- 字段清单是否为 SSOT(Demo 只引用不重复定义枚举)
- 状态机是否简化(执行层不设审核态,仅草稿→已报价)
- 新单据与上下游是否"零联动"(一期不做跨模块引用)
```

## 字段清单载体的升级方向：用 TSV（2026-09-07 沉淀）

现有 forge 项目的字段清单是 `.md` 表格；维生素实战篇给出一条更优做法——**字段清单用 TSV 维护**（纯文本 AI 可读写 / 字段多时比 md 表好维护 / 配 AI IDE 预测补全），**初稿(5列)/详细稿(13列)分两版**，详细稿确认后为字段唯一事实源，**只留 TSV 不维护 md 副本**；字段事实/业务规则/页面交互**三层分离**。完整方法论（含初稿详细稿列定义、6步丰富法、版本迭代法、多系统词条库 key 分层、给 AI 的下任务结构）见 `references/tsv-field-inventory.md`。跨系统/多语言词条库结构、key 应用层唯一、中文名可重复 —— 同见该参考文件。

## PRD 粒度规范：细但不啰嗦（2026-09-21 定稿）

用户要的 PRD 颗粒度是「**该有的结构得有、字符不能太简单、但不许灌水**」——不是越长越好，是**章节齐全 + 每章有判定标准 + 无废话**。做 PRD 产出/评审/约束 AI 时按此规格。

### 关键区分：规范 vs 参照
用户反复强调要「**规范**」不要「**参照**」（被纠正两次）：参照靠 agent 悟、得自己判断「够不够细」;规范是硬约束——**每件产出物含什么/禁什么/不达标怎么拦写死**，agent 机械照做、不靠理解力。**约束娜美/本地 agent/Cursor/Codex 的 PRD 产出时，必须给可勾选的硬规格，不是给一个写得很好的样例让它模仿。** 样例 → 它会抄形不抄神、还是判不了细不细。

### 必含章节（九章，缺一返工）
概述/背景 → 功能清单(每功能ID+作用+本期归属) → 流程(主+异常分支,谁触发/下步是什么) → 业务规则(逐条编号R##,条件→结果,含状态流转/数量口径/权限) → 交互规则(按钮/控件行为+校验时机+错误反馈+编辑权限) → 字段说明(类型/必填/来源/只读/快照/计算) → 页面路径(URL/路由+入口+跳转关系) → 异常/边界(并发/重复/缺数/越权) → 验收标准(逐条输入条件→预期结果,可测)。

### 每章「够不够细」三问（任一不过=该章返工）
1. **边界清了没**：谁能用/不能用、能做什么/不能、什么状态允许/禁止
2. **条件全了没**：规则写「什么条件下触发→结果→不满足怎么办」，不只写正向
3. **能在钉子上钉死没**：字段/状态/按钮/路径都有具体名/ID/取值，不用「相关信息」「适当提示」这类代词

### 啰嗦判定（这些话 AI 须删）
每字段补「当…则…」防御说明 / 「系统将自动处理」空承诺 / 与本期无关的公司背景行业分析 / 同规则在章节间重复定义 / 状态机上没有的死状态 / 「后续版本考虑」模糊承诺。**细 ≠ 长：用表格编号判据充实，不用散文堆防御性说明。**

### 验收标准写法（能测才算数）
❌「状态流转正常」✅「对『已完成』订单点『创建入库单』→ 入口不展示」。每条验收=输入条件→预期结果，研发按它自测、测试按它拆用例。

## 踩过的坑

- **PRD 定位错了浪费前端三轮**: 供应商报价模块第1版PRD定位为"采购员录入报价"→用户纠正为"供应商报价工作台"→重写context→重写PRD→重写前端。根因：PRD出完没先让用户确认"这个模块谁用?做什么?"就出了前端指令。铁律：PRD→用户确认定位→再前端。
- 让 AI 在 Demo 里给询价单号手工填 → 与实际需要的"系统自动生成"矛盾。必须在评审阶段发现并修正
- context 修改后 VPS 无 SSH key 无法 push → 发 md 文件让用户替换本地
- 字段清单 SSOT 标注"待回写"残留 → 走查时 grep "待回写\|手工填" 验证清理
- **供应商报价模块教训**: PRD 目录名从 `供应商报价单` 改为 `供应商报价工作台`,BJ前缀从 context/05 删除(供应商报价不产生独立单号),流程图需同步更新 product-structure 和 system-interaction diagram
- **Agent 工具分工**: Workbuddy 管 PRD 生成,反重力管前端编码,不交叉
- **超期规则反转需同步全套文档**: 供应商报价\"超期不阻断\"改为\"超期禁止报价\"后,需同步:主PRD §8.4 + 验收V10 + 字段清单状态说明 + Demo两页(列表操作列+报价页表单锁死) + Changelog。只改一处会导致前端实现和PRD不一致,反重力白跑一轮
- **登录系统上下文同步**: 新增登录功能后,需回写 context/04(用户登录与权限→简易登录+两角色分流) + 主PRD Out Scope(供应商身份来源从\"假设已认证\"改为\"来自登录用户名\")。PRD和前端实现必须和context描述一致
- **流程图更新触发条件**: 但凡新增一个\"模块节点\"(如供应商报价工作台),必须同步更新 docs/flow/flowchart.md 中的产品结构图(Mermaid)和系统交互流程图。避免 PRD 和项目文档的分歧随时间扩大
- **Ant Design 表单兼容性**: 反重力对 ProForm 子组件支持不稳定,改用 antd 原生 Form.Item。迁移分三阶段:基础档案→采购管理→全量
