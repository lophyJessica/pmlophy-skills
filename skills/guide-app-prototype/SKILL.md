# 导购端原型（V销冠 guide-app）

## 仓库与技术栈

- 仓库：guide-app（VPS `\root/repos/guide-app`，公司机 `E:\\projects\\guide-app`）。原型目录 `99-产品原型prototype-vue`（Vue 正体）；`99-产品原型prototype` 是旧 React 壳，别往里加页面。
- 栈：Vue 3.5 + Vite 7 + Pinia + `@vivo/vos-ui@4.1.1-alpha.3.46`（主组件库，私有包，内网源 npm.vmic.xyz 可装）+ Vant 4.9（辅助）+ `@vivo/h5sdk`。
- VOS 组件（FosButton / nx-search / nx-tabs / nx-list / nx-pull-refresh / nx-icon / nx-empty）一个不许替换——换通用组件视觉全错；唯一可 mock 的是平台能力层（JS Bridge → useBridgeMock）。
- 生产源码参照：公司机 `E:\\projects\\源码管理\\外销\\前端\\global-guide`（origin/1.8.0）；仓库内只读快照 `01-全局背景信息/参考资料/源码/global-guide`。本机跑副本无登录态（接口 40140026），只能看布局不做验收。
- **仓库内那份快照是老分支**：package.json version 1.0.0、9 条路由、views 只有 couponDetail / home / myPage / notFound.vue / task / userManager、**没有 sales 模块**。它只够做「外销现状」对账，不能当复刻的对照基准（见下节）。
- 真实现没有页内导航栏组件：标题由 `router.afterEach` 写 `document.title`、顶部栏由容器 App 提供——原型侧 NavBar 是按设计稿补建的，源码里没有可抄的。
- **线上 `/project/guide-app/` 部署的是 React 旧壳，不是 Vue 版**：目录里只有 index.html + assets 两个文件（无源码），挂载点 `id="root"`（Vue 版 index.html 是 `id="app"`），bundle 里能 grep 到 React `createElement`、grep 不到 Vue/vue-router 特征。`deploy-all.sh` 里没有 guide-app 映射，它当初是手动部署的，所以线上与备份目录都没有历史部署包。要恢复可编辑源码只能走 git 或仓库压缩包，**不要指望从线上取回 Vue 版**；判断线上是哪一版就用上面三条特征（挂载点 id、createElement、vue 特征串），不看标题文字。

## 本地构建：pnpm，家里跑不了

- 包管理是 **pnpm**（`pnpm-lock.yaml`，lockfileVersion 9.0），不是 npm。公司机实测 Node 24.18 + pnpm 9.4 可用（engines 要求 `node >= 20.19` 且 `.npmrc` 带 `engine-strict=true`）。
- `.npmrc` 里 `registry=http://npm.vmic.xyz`，`@vivo/vos-ui` 是**私有包**——外网/家里装不了，`pnpm install` 只能在公司网络里跑。**「build 验证」这一步天然要排到公司**，在家别硬试，也别拿「build 没过」当代码问题去改。
- `pnpm-workspace.yaml` 是坏文件：只有 `allowBuilds` 三项、**没有 `packages` 字段**，pnpm 9 看到它就把目录当 workspace 根，直接报 `ERROR packages field missing or empty`。单包项目不需要它，**删掉即可**（`allowBuilds` 是 pnpm 10 语法，pnpm 9 认的是 `onlyBuiltDependencies`，留着无效）。
- 删/改 workspace 文件后 pnpm 会提示重建 node_modules（配置记在 `node_modules/.modules.yaml`，对不上就重建）——这是改配置的必然结果，不是删文件的副作用；**不要按 n 跳过**，否则 node_modules 仍是旧配置装的，后面 build 会出说不清的问题。

- `f46a652`「全量代码提交」引入 `99-产品原型prototype-vue`；`origin/main` 至少到 `4ee4283`（10-29）。

## 第一步永远是读路由清单

`src/router/index.ts` 是页面唯一清单源：`meta.homeTab`（底部 Tab 一级页）+ `meta.title`（导航栏标题）+ `meta.sourcePath`。改外壳/补页面前先 grep 它列全页面，别凭 views 目录猜。

## 按外销源码对照复刻：先定基准，再动手

用户说「按源码对照复刻」时，**第一步不是开比，是确认拿哪份源码当基准**——仓库里同时存在两套外销源码，规模差一个模块量级：

| 基准 | version | 路由 | views 下 .vue | 含 sales 模块 |
|---|---|---|---|---|
| 仓库内快照 `01-全局背景信息/参考资料/源码/global-guide` | 1.0.0 | 9 | 6（task / userManager / myPage / couponDetail / home / notFound） | 无 |
| **`code-source` 仓库 → `外销/前端/global-guide`（VPS 镜像 `/root/repos/code-source`）** | **1.0.0** | **18** | **21** | **有** |
| 公司机 `E:\\projects\\源码管理\\外销\\前端\\global-guide` origin/1.8.0 | 活跃分支 | 18 | 21 | 有 |
| 原型 `99-产品原型prototype-vue` | — | 17 | 20（多 sales 8 页：orderList / orderDetail / orderListSearch / activityList / activityShare / setFollow / verify / components/publicDialog） | 有 |

**判据只有路由条数 + views 大小，不认 version**：快照与 code-source 那份 package.json 都写 1.0.0，靠版本号分不出来，只有 `grep -c "path:" src/router/index.ts`（9 对 18）和有没有 `src/views/sales/` 能分。

`code-source` 是纯源码库（不含原型、不含对标交付件），用户 push 后 VPS 侧 `git pull` 即可拿到基准，不必等公司机拷贝。

检查顺序（缺一即停在问用户）：

1. `grep -c "path:" src/router/index.ts` + `find src -name '*.vue' | wc -l` 定路由数与规模；**不靠 version 判新旧**。
2. `find src -name '*.vue'` 两边列清单做集合差，不要凭目录名或上一轮交接里的计数下结论——交接数字是症状不是账本，实测对不上就按实测报并说明差在哪。
3. 原型里有、基准源码里没有的模块（典型是 sales 8 页），**不许自行删页也不许自行保留**：这是「规格差异」不是「遗漏」，作为阻塞问题交用户拍板（这版设计要不要跟源码走）。
4. 基准源码只在用户本机时，先要用户 commit+push 或拷过来，VPS 镜像查不到未推分支；不要拿快照硬对，会把 1.8.0 的页面误判成「多余」。

对照粒度：逐文件比 `<template>` 结构、组件引用、层级、交互与字段，mock 按真实业务形态造；逐页过，不许跳页。

### 逐页对照先用脚本量差异，再人判读（不要逐页肉眼读）

对 19 个业务页两两配 `difflib.SequenceMatcher` 拿 opcode 块，再按块内是否命中 mock 标记正则分成两类——**mock 化差异**（`lan.` / `useAppStore` / `storeToRefs` / `mock` / `useBridgeMock` / `dsBridge` / `vchatAPI` / `useCurrentInstance` / `from '@/api`）与**真缺陷**。基准量级：147 块里 mock 化占了 95 块，真正的缺陷只有 52 块中的十几条——不做这步会拿几十条预期内差异去骚扰 agent，也会把真缺陷埋在噪音里。做法与判据见 `references/prototype-vs-source-alignment.md`。

两条判断先做在派活之前：

1. **等价架构不算缺页**：源码 `views/home/index.vue` 是四 Tab 容器（keep-alive 包 userManager、底部 iframe-footer 导航、把 `lan/baseInfo/hasAuthorize/accountListData` 以 props 下发给子页）。原型把这套职责搬进了 `App.vue`（NavBar + TabBar + keep-alive + 空账号态），子页改从 store 取值——**不要新建 home/index.vue 去对拷**，只核对 Tab 顺序与 active 态、空账号态文案 `workNoAccount` 与 `@/images/empty.png`。真正缺的是 `notFound.vue` 与 catch-all 路由。
2. **组件替换是硬缺陷，要全库扫**：原型是最容易在这里破规矩的地方（曾把源码的 VOS `Loading` 写成 `van-loading`）。核法＝在原型 views 里 `grep -rn '<van-'`，与源码同名文件的 import 对比，凡源码用 VOS 组件而原型换了 Vant/原生标签的，逐条改回。

指令里要点名「先读本清单再动手」并把已对齐的页面列成禁改清单（本仓已有 5 页差异块为 0：`couponDetail/components/noticeInfo.vue`、`couponDetail/components/userForm.vue`、`sales/activityShare.vue`、`sales/orderListSearch.vue`、`sales/setFollower.vue`），否则 agent 会把对齐的页面重写一遍。

拷图片那一步要在指令里预先写好裁决法：原型 SVG 多带 UTF-8 BOM（`EF BB BF`），与源码比 md5 必然不同、看着像冲突，实际剥离 BOM 后逐字节一致。写成「同名图先剥 BOM 与行尾再比，一致就按源码覆盖，不算冲突；剥完仍不同才停下问」——只写「同名不同就停」会让 agent 在 8 个 tabbar 图标上整轮卡住等确认。

## 一致性判定与走样归因（用户说「原型跟源码不一致」时先跑这步）

用户要的是「原型与源码一致」，不是「接近」。报差异必须按三层收敛，只报第一层的数字会把人吓去大改：

1. **全量 diff 块**（含 script）——最虚。`lan` 字典整块换成硬编码中文、`vchat`→`useBridgeMock`、`@/api`→`@/mock` 都会把整段算成 replace。
2. **剔除 mock 化块后**——比第一层可信，仍含 script 段位移。
3. **只比 `<template>` 与 `<style>` 段**——这才是「结构/视觉是否一致」的真实口径。实测同一版本三层的数字是 147 / 46 / 17，模板层那 17 块里真正实质的只有 2 处（原型自加的状态类、mock 字段名与源码不同），其余全是换行与缩进。**给用户报一致性只报第三层 + 逐条列实质差异**，不要报第一层块数。

走样归因（用户说「以前做得很接近，后来不知道改了什么」）：不猜，逐提交跑同一统计，差异最小的当黄金版本、跳升的那次当退化点。

```
git log --format=%H|%ad|%s --reverse <当前HEAD> -- 99-产品原型prototype-vue/src/views
```

对每个提交 `git show <commit>:<path>` 取 19 个业务页，按第三层口径算模板+样式差异块。实测：`f46a652`「全量代码提交」10 块（黄金版本）→ `8a6a526`「NavBar 小程序外壳统一」20 块（退化点：外壳改造顺带动了页面）→ 当前 17 块。给用户这张表，而不是「我看了下大致一致」——他要的是定位到哪次改坏的。

**页面标题盘点走 titleKey，不搜中文字符串**：源码标题不写死，路由是 `meta: { title, titleKey }`，真实文案 = `store.lan[titleKey]`（线上来自 `langGet` 接口，本地 `src/store/workbench.ts` 只是兜底字典，两者可能不同）。按 key 查字典再比原型的 `meta.title`；搜源码里的中文搜不到，不等于线上不显示。master 基准实测 5 处不一致：`/taskList` 私聊任务 vs 任务列表、`/orderList` 订单管理 vs 订单列表、`/orderListSearch` 订单管理 vs 搜索订单、`/activityShare` 分享给用户 vs 活动分享、`/verify` 取货码核销 vs 扫码核销。

**基准版本开工前一定要问准**：用户口径里的版本是「1802」这类补丁版本号，master 不是复刻基准。对着 master 比出来的每一条差异都建在错基准上，改多少轮都对不齐——这不是 agent 不努力，是参照物错了。第一句问「这次对的是哪个版本分支」，并要用户把那一版源码放进 `code-source` push 上来，VPS 侧 `git pull` 后再跑对照。

**用户取源码分支的规则（照此核对，别自己另立）**：master 是最新就用 master，master 不是最新就取「未合并进 master 的最新分支」。code-source 里那份 `外销/前端/global-guide` 就是按这条取的，可能就是 1802——不要仅凭「我以为它叫 master」下结论。

**三源冲突时先问图是哪来的，不判「研发没实现」**：同一处文案会同时存在三个可能的值——分支代码（含 `langGet` 下发）、设计稿、真机。三者不一致时先问用户「这张图是设计稿还是真机截图」，答案决定结论：

- **设计稿 ≠ 代码** → 研发实现偏离设计，记进差异清单交研发；原型跟谁由用户定（跟真机＝复刻现状，跟设计稿＝目标形态，改的东西完全不同）。
- **真机 ≠ 分支代码** → 说明线上跑的版本比手上的分支还新，此时**不能把任何不一致判成「研发没实现」**，整个对照基准要重新取；先记下这条，别再继续按旧分支出结论。
- 自己先搜一遍全库该文案（`grep -rn` 中文），搜不到时不要急着说「线上不显示」——走接口下发的值代码里本来就没有，只有真机能证。

**报告说「已完成」但工作区干净＝改动不在这个仓库**：agent 报 `ai-reports/xxx.md` 已落盘、改了 N 个文件，而 `git status --short` 为空时，先接受「这份仓库没被改过」这个事实，再查是不是开在别的副本/别的机器。不要拿报告去推「改动被谁覆盖了」。

## 设计稿尺寸（px 口径，别混）

- **设计稿逻辑宽 = 1080**；设计稿导出的 PNG 实测 2160px 宽（2 倍图）。标尺寸、写页面 px 一律按 1080 基准。
- **预览/讨论适配时按 375 视口说话**（旧稿习惯是 375×667）。
- 两者靠构建层换算对齐：`postcss.config.cjs` 里 `postcss-px-to-viewport-8-plugin` 的 viewportWidth 按文件路径分流——`node_modules/vant/` 取 375，其余业务文件取 1080。所以业务代码写 1080 基准的 px，Vant 组件本身是 375 基准，最终都转成视口单位。改 viewportWidth 或加新依赖前先看这一行，别把两套基准改成同一个数。
- 固定高度（NavBar 44px）用 `/* px-to-viewport-ignore-next */` 保持物理像素——改样式时别删这两行注释。
- **验收必须在手机视口下看**：业务代码 px 按 1080 基准转成 `vw`，而 `vw` 相对浏览器窗口宽度、不认容器宽度。桌面 Chrome 全屏（1440）打开 `pnpm preview` 会整体放大 1.33 倍，表现成字号失控、Tab 换行堆叠、内容溢出屏幕、卡片只剩一角——**这是视口问题，不是样式被改坏**。验收前 F12 → `Ctrl+Shift+M` 切设备模拟、选 375 宽机型再刷新；拿桌面截图当「页面崩了」去改样式等于白改一轮，且会把 agent 引到错误方向。

## NavBar 公用外壳（已定稿，指令直接抄）

设计稿真源（**容易误判存亡，先读这段**）：`03-产品设计/外销预售V5.1.0/01-PRD套件/前端Demo PRD/assets/UI稿/`（81 张 / 57M）与同级 `assets/交互稿/`（47 张 / 29M）已被用户要求删除。

- 想拿原图：直接读用户本机副本，或从 `origin/main` 对应提交里取（本地那份工作区已删，不要在那里找）；要真正从仓库移除得单独走一次提交。既然可能就在本机，就别拿「已删除」当「找不到」交差。
- **不要再按这个路径当设计稿依据做复刻**——形态口径以下面第 1-5 条的文字规格为准。

形态：
1. 白底，高 44px（375 视口），无底部分隔线、无阴影。
2. 左：黑色细线 chevron「<」返回箭头，无底色无边框；`meta.homeTab===true` 的一级页左侧留白不渲染。

坑：agent 照设计稿自由发挥会做成悬浮方块按钮（56px 黑框）——形态必须由 Hermes 读图后逐属性文字化写进指令，并点名禁掉这个错误形态。

## 内外销导购端差异对比（做对标表时先读）

两套不是同一产品换皮，规模差一个量级：

- **内销** = `qywx-h5`（企业微信里的唯一 H5 应用，v5.0.3），路由 100 条、30+ 页面：AI 助手、AI 话术教练、机型对比、内容库、学习培训、快捷回复、话术、分组群发、回访用户列表、留资线索录入、业绩与服务宝数据、推荐购机活动、素材中心等。
- **外销** = `global-guide`（v 消息里的应用，中文名 **V销冠**，不是「v销管」）。规模看拿的是哪份：仓库内**旧快照**只有 9 条路由 / 6 个视图（我的任务、用户管理、我的、任务列表、任务详情、用户详情、卡券详情 + 404）；活跃分支（`code-source` 那份 / 公司机 origin/1.8.0）是 **18 条路由 / 21 个视图**，多出 sales 模块（订单列表/详情、扫码核销、设置跟进人、活动列表/分享）。做对标前先按上节定基准，拿快照当现状会把「已在源码里实现」误报成「我方规划」。本仓库原型是为外销预售 V5.1.0 设计的**目标形态**，不算现状证据。

对标做法（按成本从低到高）：

1. **源码功能对账**：两边各提取页面/路由/按钮/字段，机器 diff 出「内销有外销无 / 外销有内销无 / 都有但形态不同」三类，人只在差异清单上判读。别手工一格格对。
   - 提取别派子 Agent 逐文件读：内销 qywx-h5 有 31 个 views，子 Agent 会撞轮次上限。用脚本扫 `<template>` 里的中文串（文本节点、placeholder、`:label` 绑定），按路由文件定权威页面清单，落 TSV（页面/子功能项/代码依据），再由人补「功能介绍」。
   - 归类按六个业务域：用户经营与线索 / 内容与素材 / AI 能力 / 任务与执行 / 销售与营销 / 数据与管控。办事处和技术页（侧边栏跳转、加载失败、上报成功、定位授权）不进管理层对比表。
   - 内部基准量级参考：内销 qywx-h5 全量提取约 309 行 / 68 个页面，其中内容与素材 + AI 能力合计过百行，而外销这两块代码里为零——这是给领导看时最有力的结构型结论。
   - 三类不确定性必须在表里显式标：路由被注释（未启用）、文案由接口下发（只能确认结构）、纯技术页（不进对比）。不标就会被当成已核实项。
2. **截图只能来自运行态真系统**：内销在企业微信容器里、外销在 v 消息容器里，都要容器登录态，Playwright 无头抓不了。复现原型截的图**不能当证据**，尤其不能拿去给领导——它证明不了线上实际形态。
3. **表别铺满**：区域 × 功能点的矩阵很容易变成几百格。给管理层看的版本压到 30-40 行、按业务链路分组、每条差异带一句缘由；五地区只在真有地区差异的行填，其余合并写「一致」。
4. 先确认源码版本对应当前线上哪一版，版本对不上则差异结论无效。

## 对比表的字段结构与粒度（用户 1101 定稿）

- **以内销为基准全量铺开**，外销列只回答「有没有」；范围只做导购工作台，不含 CMS。
- 表结构 32 列：基础信息 3 列（页面/功能模块、子功能项（文案/按钮）、功能介绍）+ 五组地区（内销、印度、普外印尼、欧洲西班牙、拉美巴西），每组 5-6 列 = 截图/是否支持该功能/内容是否可配/展示数量/设计规范（宽*高）/差异备注。顶部另附 9 条填写说明（截图要求、功能介绍要求、各地区代表国家选因等）。
- **粒度分两档，别混**：明细版照《商城商详页》样例，一个页面拆 15-30 行子功能项、一条一行；压缩版**一页一行**，功能介绍用顿号穷举该页各子功能项，结论列按「全支持 √ / 有支持有不支持 部分 / 全不支持 ×」汇总。用户对「功能介绍占 10 行、图要跨 10 格合并」的反馈是「不利于观看」，所以压缩版不要再做跨行合并的图——**列结构仍保持 33 列，只填关键几列，其余留空**（用户确认「这两件事不冲突」）。压行前先压一页出样例（附压缩前后对照图）给他看文案读不读得通，认可再全量压。
- 第一列页面名**每行都写、不合并单元格**——合并后不能筛选/透视，且合并逻辑写错会整列丢值。
- 写清两类不确定性：路由被注释（未启用）与文案接口下发（只能确认结构），否则会被当成已核实项。

#### 插图合并（用户点名过两次的老毛病）

- 实际列位：33 列，**第 4 列 `内销-截图`、第 15 列 `印尼-截图`**（第 9 列是印度、第 21 西班牙、第 27 巴西），第 33 列是代码依据。用户口中说「32 列」是不含最后一列。
- **截图列必须按页做单元格合并，图锚定在合并区居中**。判据不是「合并区数量」，是「图不能乱放」。上一轮 agent 为了少建合并区，改成不做合并、按行逐行锚定，结果「用户管理、用户详情截图单元格不合并，图就乱插放」——这是本末倒置。
- 合并分组依据是第 1 列「页面/功能模块」的连续相同值（第 1 列本身不合并，只拿它分组）。
- **动手前先量现状，不凭交接文档描述**：`zip -l <xlsx> | grep xl/media` 看到有媒体文件，不等于表里真有图——实测主表 `openpyxl` 读出 0 张图、0 个合并区，第 4 列只是一个文件名文本，包内那些 media 是孤儿残留。插图前先跑一次 `len(ws._images)` / `len(ws.merged_cells.ranges)` 定真实起点。
- 单元格里同时放文字和图片会互相挤，先问用户文件名文本留不留（建议移到索引 sheet 做对照，截图列只放图）。
- 图与行的对应不要靠文件名顺序猜，用「内销序号 ↔ 外销文件名」映射表；外销截图编号已按内销 1-8 对齐时这层才能直接对上。
- **改文案必须排在插行之前。** 新增一行会把下面所有行号推移，先按现行号改完文案、再插行，内容跟着单元格走不会错；反过来先插行、再按旧行号替换，从新行往下整段错位。指令里把顺序写成 1 改文案 → 2 统一整列 → 3 插行，并注明「插入后行号下移属正常，不许去修正」。

#### 卡券核销的口径（外销特有，别和订单核销混）

- 外销**有**卡券核销能力，但 **V销冠（导购端）没有核销入口**：核销走 V消息 App 的「扫一扫」，落地页是独立 H5，导购端无页面。这是「有能力的点、无页面」的一条，表里要单独占一行，不许并进订单核销那几行——源码里 `/verify` 与 sales 首页的「扫码核销」是**订单/取货码核销**，跟卡券核销是两回事。
- 卡券的发放走 **CMS 触达计划、经渠道下发给用户**，所以「有没有 CMS」决定这个国家有没有卡券生态：印尼有 CMS 填 √；西班牙商城上线但 CMS 未部署、巴西商城与 CMS 都没上，这两国填 ×；**印度特殊**——没部署导购工作台（V销冠），但卡券核销照填 √，因为这个能力不依赖导购端。
- 判断国家支持与否的通用链：CMS 部署 → 才有导购工作台；导购端能力随工作台有无；但走 V消息/平台侧的能力不受这条限制。
- **V消息扫一扫对应内销「企业微信扫一扫」，判「不缺失」并打 √**。外销的扫码能力同样不在导购端，在 V消息 App 内，扫码后跳转独立 H5 落地页——表里这一行若填印尼 ×、备注「外销无此页面」就是错的。它是 V消息 平台能力，14 国通用，**印度也照填 √**（备注「经 V消息扫一扫，无独立页面」）；西班牙/巴西仍随 CMS 为 ×。同一类 V消息 能力（卡券核销、扫一扫）在不同行里的填法必须一致，不要一个打勾一个打叉。

#### 外销图与行的归属：按语义配，不按文件名里的关键词配

两张跟「卡券」有关的图最容易配反，实测就错过一轮：

- **`16-我的.png` → 「卡券-导购信息」行**。内销那页是导购自己的信息页（头像 / 姓名 / 手机号 / 所属门店），对应外销 `/home/myPage`「我的」，不是券详情。

判据：配图前先看该外销页的 `lan` 文案（`store/workbench.ts` 里按 key 查）与内销那行到底在讲什么，名字里都有「卡券」不足以判同。

只按内销页面铺行时，外销这些能力在内销没对应页，就无处可放、图只能躺在硬盘上，表也就不叫「内外销对比」了。用户口径：「外销独有，这才是内外销的对比完全体」。必占行的 7 条：订单列表 / 订单搜索 / 订单详情 / 设置跟进人 / 取货码核销 / 分享活动列表 / 分享给用户。

#### 多版本交付件：先确认改哪一份，再动手

`内外销梳理/` 下同时躺着 `内外销功能对比-32列主表.xlsx`（明细，1136 行）、`内外销功能对比-压缩版.xlsx`（320 行）、`内外销功能对比-明细版.xlsx`、以及压行产物 `内外销功能对比-单行版.xlsx`（69 页 ≈ 69 行）——列名与列序完全相同，用户口头只说「对比表」。派活前必须问准目标文件，并在红线里写死「不许动另外几份」。实测因没确认，整轮分析做在了明细版上，用户要的是压缩版。

**单行版必须另存、不能原地压**：子功能项明细一旦压掉就找不回来，原始多行版要留着当底稿（以后查某个子功能当时怎么评估的还得翻回去）。指令里写死「输出为新文件，源文件一个字节都不许改」。

三份的实况也不同，别串着说：压缩版 A 列 58 个合并区、D 列（内销-截图）58 个且与 A 一一对应、O 列（印尼-截图）0 个；明细版 0 图 0 合并区、D 列只是文件名文本。报任何「现状数字」前先说清是哪份文件、哪个版本取出来的。

#### 用户说的「填反 / 错位」先确认是哪一端

用户报「印度和印尼位置反了、要调换」时，不要一头扎进对调方案。实测现状：印度列 320 行全 ×、备注「不含印度」，印尼列 6 个 √ + 18 个部分，与「印度无 V销冠、印尼有」完全吻合，怎么推理都对不上；真相是 **Excel 本身没错，是导入公司在线文档平台之后错位**。

排除顺序固定三步，问完再谈改法：① 说的是哪份文件（同名交付件不止一份）；② 看的是 Excel 还是导入后的在线文档；③ 分析的是 VPS 镜像还是用户本机在改的那份（镜像可能落后好几轮）。三个问完之前，所有对调推演都是空转。

#### 差异备注写业务语言，不写技术路径

四个差异备注列（印度 14 / 印尼 20 / 西班牙 26 / 巴西 32）里塞了英文路由、组件名、清单行号，业务读不懂（实测 740 行命中）。改法：不出现任何英文、路径、变量名、接口名、行号；一句话不超过 40 字；多条缺点用顿号连写，不编号不加括号注释。改写前先出清单让用户抽查，不要一次性回写几百行。

**主语用国别词、不用「外销」；而且句首连国别词都不必写。** 这几列本身就是国家列，写「外销无 X」会让印尼列、西班牙列、巴西列变成同一句话，看不出是哪个国家没有；但逐句都以「印尼」开头也被用户否掉过——「不需要每一句都是印尼开头，本来就是在印尼这一列下展示的」。列内直接写「无 X」「有 X，但无 Y」即可。

**先算清到底要改几条，别按命中行数派活。** 实测 740 行命中里只有 43 行真的要逐条改：印度按口径整列统一成一句（印度未部署导购工作台），西班牙、巴西各 320 行原文本来就是业务语言（「商城已上线但 CMS 未部署，无导购工作台」），动它反而改坏。派活前把命中行拆成「整列同质 = 统一一句」与「真需逐条」两堆，只派后一堆。

**这类语义改写不要交给 agent，父会话自己写。** 弱模型跑出三类硬伤：① 在国家列写「外销无…」；② 把具体差异压成「外销无部分内销功能」这种零信息量的话；③ 把原文的「可配明细：…可配；X 不可配」误读成外销有无，编出「外销无印度、搜索框可搜索备注名」的病句。正确分工：父会话产出「行号 + 改写后」两列 TSV，agent 按行号整格替换，只做机械动作。验收看它报的逐条替换结果，不看它自述「已优化文案」。

#### 导入公司在线文档（docs.vivo.xyz）错位

Excel 本身没问题、导入后列错位时，先查**两级表头 + 跨列合并**：第一行是分组（印度跨 5 列、普外（印尼）跨 6 列），被导入端拍平或当数据行，整表就往右挪一格。解法是另出一份导入专用版：表头压成单行、列名带国家前缀（印度-截图 / 印尼-截图 …）、去掉表头区的跨列合并；正文里页面列的合并可以保留。先问清错位形态（整列右移 / 表头串到数据行下面），形态不同改法不同。

#### 外销截图列同样要按页合并

第 15 列（印尼-截图）照第 4 列（内销-截图）的做法：按页面合并单元格，一个页面一张图，锚定在合并区居中。**一张图铺在多个单元格上就是缺陷**——分不清这张图对应哪一行。用户点名过两次，指令里要单独写成一条红线。
