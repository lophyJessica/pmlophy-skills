# 产品文档的图文表达

用户判断一份方案/PRD 能不能用，第一顺位不是内容对不对，而是**表达层级够不够高**：

> **文不如表，表不如图，图不如面。** 面 = 可运行的原型/在线系统。

满篇叙述段落 = 不合格，会被直接打回（原话：全是大白话）。

## 交付前的两问自检

1. 有没有**只有文字**的段落能改写成表？能就改，别犹豫。
2. 有没有能画成**图**的流程、状态、条件组合？有就画。

改完再回头看一眼：读者扫表和图能不能在 30 秒内拿到结论；做不到就是图和表选错了。

## 叙述 → 表

把“为什么必须做 X”这类论证改写成多列表。例如：

| 场景 | 包含条件 | 排除条件 | 不做的后果 |
|---|---|---|---|
| 核销提醒 | 订单状态=已预订 | 状态=已核销 | 触达已购用户，引发客诉 |

只改**论证型长段落**，不要把全文硬抳成表格。

## 方案阶段固定六张图

mermaid 直接嵌 md（公司 wiki 支持 md + mermaid，不用另出文件）：

| 图 | 画什么 | 解决什么 |
|---|---|---|
| 端到端流程图 | 业务动作→数据产生→配置→使用→回流；外部环节用虚线反喂 | 读者不知道它在链路哪里 |
| 状态机 | 配置对象生命周期；把“只停用不删除”这类设计决策画出来 | 状态流转靠文字说不清 |
| 单条结构图 | 一条条件/一条记录由哪几段拼成 | 字段为什么这么多 |
| 组合逻辑树 | 多条件怎么交并补（AND / NOT）及优先级 | 组合规则最易理解错 |
| 时序图 | 多角色（业务方/数据/产品/运营/系统/渠道）的先后与交接口 | 读到一半不知谁干什么 |
| 路线图 | 分几期、每期范围与推进条件 | 分期的根据 |

mermaid 避坑：节点文案含括号/斜杠/冒号时**用引号包起来**（`A["业务动作<br/>下单 / 核销"]`），否则解析失败。写完数一下 `^```mermaid` 与 `^``` ` 是否成对。

**产品视角铁律（用户纠：时序图画成代码仓库名/库名被判「太技术了，这是产品经理的图，不是开发的」）**：流程/时序图的参与方一律写**业务角色与系统职责**（业务人员 / CMS / 大数据平台 / 触达计划），**禁止出现代码仓库名、库表名、接口名、请求方式、Dubbo/JDBC 这类实现细节**——技术细节收进图底脚注或注释框。时序图的语言是「谁在什么时候向谁要什么、给回什么」，不是调用栈。待确认的外部环节用橙色/独立色标注参与方并加说明小字。**参与方控制在 5 个以内**：第一版画了 6 泳道被退回「看不懂，太复杂」，简化到 5 个（业务人员/CMS/事件配置/大数据平台/触达计划）后才过——同类内部环节（如 BFF、配置库）合并进所属系统，不单独成泳道。

**交付方式：流程/时序/结构关系类图一律 mermaid 语法贴聊天框，不渲染 PNG（1028 用户定）**——用户自己渲染看、也方便后续改，PNG 渲染烧 token 还难改。只有 UI 线框/展示类长图才走 HTML→PNG（见 ui-wireframe-mockup）。判断标准：图的受众要「理解逻辑」就给 mermaid 源码；要「看长相」才出 PNG。

## 迭代路线要写四层，不是一条箭头

只画「V1→V2→V3」三个盒子等于没写分期。方案要能回答「凭什么现在只做这些」「下一期凭什么能开」：

| 层 | 写什么 | 缺了会怎样 |
|---|---|---|
| 飞轮闭环 | 圈人→触达→用户新行为→沉淀为新事件→看效果→调策略→再圈人；**用虚线或旁注标出本期只闭合哪一段** | 读者看不出「越用越好用」靠什么成立 |
| 中转站 | 事件与用途之间的中间产物（分群/人群包）：是什么、在飞轮哪个位置、静态快照 vs 每次重算各自适合什么 | 下一期最该做的东西根本没被设计出来 |
| 各期准入矩阵 | 维度 × 期次横向拉平（范围/入口/触发方式/准入条件/验收方式），一列一期 | 「推进条件」只写一句话，评审无法判断能不能开 |
| 设想场景全表 | 场景 / 用到什么数据 / 业务价值 / 前提与待确认 / 归哪期 | 设想散在正文里越扩越乱，也没有对应的待确认项 |

全表里每条设想都要带「前提或待确认」，不让设想裸奔；未定稿的统一标「设想，非现有能力」。

**升版别把前版的论证层压没**：重写方案时最容易蒸发的是「为什么这么分期」这层（飞轮、中转站、准入条件），因为它不像字段和结论那样显眼。升版前先列出前版的论证层，逐条确认还在——已确认结论不能被遗忘，已想清的设计也不能。

## 没真实截图时：HTML 线框

功能未开发就没截图，**不允许空着、也不允许拿不相干的截图凑数**（用户会当场识破并要求重做）。

- 一个 HTML 放多张线框面板（列表页 / 弹窗 / 带页签的交互页），浏览器直开能看。
- 用 HTML+CSS 盒子画，**不手写 SVG**——坐标错一处整张图就歪。
- 风格抄项目已有的线框：浅灰底、白卡片圆角、slate 色盘、monospace 标签（参考 `01-全局背景信息/flow/compliance-wireframe.html`）。
- 线框里要写**关键设计决策旁注**（“为什么这个入口放配置中心”“为什么这个按钮必须有”），线框的价值一半在旁注。
- 正文明说：**功能未开发，此处为线框示意，原型出来后再补真实截图**。不假装是截图。

### 交付方式：HTML 直接贴聊天框，不要只给文件路径

用户要求「**出了图直接在聊天框发我，我来复制**」。线框/代码类产物：

- 把完整 HTML **贴进聊天框的代码块**，他自己存成 `.html` 双击打开。
- **不要只说「文件在 /xxx/yyy.html」**——他要拿去给领导看，路径对他没用。
- 文件照常落盘留档，但交付动作是「贴出来」。

### 给领导审核的「变更标记型」UI 图

在**已有功能上加东西**（加筛选、加列、加按钮）时，领导要的不是完整原型，是「**改了哪些**」：

- **灰 = 现有项，蓝 = 新增项**。每个新增项旁边挂一个蓝色「新增」小角标（`#415FFF` 底 + 白字 + 圆角小胶囊），新增的表格列用浅蓝底 + 蓝色列头。扫一眼就知道这次动了什么。
- **一页把三件事画全**：筛选区（含新增筛选项）、列表（含新增列，配 2 行示例数据）、右上角新增按钮。拆成多页反而看不出关系。
- **示例数据用真实业务语境的假值**（真实国家/门店名、导购工号、手机号打码），别用 `xxx`/`test`——领导看不出这是真需求。
- 图下方配一条黄底「看图要点」，把**最容易误解的那条设计决策**写在最前面。
- **交互类改动（如导出）另出一张小图**：点按钮 → 确认弹窗，弹窗里写明范围/字段/格式，以及**待确认项**（上限、同步还是异步、权限）。待确认项直接摆在图上，评审时当场就能拍。
- 「简略」的含义：领导审的是结构和有无遗漏，不是像素。不用响应式、不用接数据。

## 有真实截图时：先筛，再放

从仓库的验收/审计截图库取图（`08-相关资料/产品审计/*/验收截图`、`08-相关资料/审计报告/截图`）。

- **只放有真实数据的截图**：空表、KPI 全是「—」、图表显示「查询无数据」的图，放上去比不放更露怯——读者会以为系统没跑起来。先确认画面里真有数据行/柱子/数字。
- **带人工标注的审计截图不能用**：红框、箭头、批注是审计过程留痕，不是产品展示。
- **一次筛完，别逐张看**：把候选缩略图拼成一张 contact sheet（网格 + 角标编号 + 文件名），一次问出「哪些有数据、哪些带标注」，比逐张渲染看图快一个量级。
- 一页放几张：**2 张是清晰度上限**，3 张并排必然「结构可辨、细节不可读」。多图必须等高（统一 H、宽度按比例），否则说明文字基线不齐。

## 别人给的原图：原样复用，不要重画

领导/评审方说「用我之前那张图，**不要改动**」时，重画等于「动了」，是要被打回的。

- 从源 PPTX/PDF **高 DPI 渲染**（300dpi，150 发虚）→ 按非白像素外接框**只裁纸边**（`ImageChops.difference` + `getbbox`，留 14px 白边）→ 整张等比放入。图形本身一个像素不动。
- 源页面上方有标题/说明文字时，按行统计墨迹找「全白行段」，取最后一段之后当图顶，自动裁掉上方文字。
- **先定位原图在哪一页**：把源文件全部页面渲染成缩略图总览，一次问出「哪页有这个图形」，别逐页看。
- **同一张图有多个版本时必须问用户是哪一版**：源文件里常并存「完整版」和「精简版」（差一列指标之类），缩略图看不出差别，自己挑就是赌。用文字描述两版差异让用户选。
- 放入后页面标题用自己的，交付时明说「只裁了纸边，图形没动」。

## 手画的图表要能自证

- **柱状图必须有 Y 轴刻度线**，否则读者无法核验柱高比例，只能信你写的数字。
- **分组柱图的月份标签按「柱组中心」对齐**，不是按第一根柱。
- 结论里的倍数/比例**逐项算过再写**：拿 A 均值比 B 单月，会写出「5 倍以上」而实际最低只有 4 倍。

## 图里的数据不许编

线框/示意图里的数字一律用示意值，**不能写得像真实业务数据**。真实统计另起表列并标出处；找不到出处就删或写“待确认”。

## 缺口与待补充项：显性化，并写清「卡在哪」

材料里数据没到位的指标，不要混在叙述段落里，也不要只写「暂无数据」：

- **整块用一个对比色分区**（橙色系，与主色蓝拉开），块内逐项一张小卡，每张卡都挂同色「待补充」标签——扫一眼就知道哪几项是空的。
- **每一项必须写清卡在哪**，只写「还没数」等于没写。四类分法够用：卡时间（工具还没上线）/ 卡埋点 / 卡数源（上游只有 A/I 口，缺 P/L 转化）/ 卡采集（功能已上线但数据没采）。
- **分清「让读者补数」还是「读者推别人给数」**。产品侧算不出来的指标，责任在研发/大数据——交付时要明说「你要做的不是补数字，是推动数源和口径」，否则读者会问「这块是要我补充吗？还是漏了？」。
- **结论条写成预期管理**（「工具上线快于指标可测，Q4 与 XX 对齐后回填」），而不是道歉或留白。
- 可选：给每项标上责任方（找研发 / 找大数据），评审对齐场景下加上更省事。

## 对外口径

可能发给别人或在评审现场展示的文档（PRD / 方案 / 台账 / 报告）：

- **不得出现内部昵称**（路飞 / 罗宾 / 杰西卡 / 娜美），一律用真实姓名——对方不知道路飞是谁。
- 写完扫一遍：`grep -n "路飞\|罗宾\|杰西卡\|娜美" <文件>`；同一批要外发的文档**一起扫**，别只改手上这份。
- **agent 代号不能当作者署名**：版本记录/修改记录的「修改人」列若写的是 agent 代号，改成「—」，但**不许删整行**——行里的版本号和「改了什么」要留着，否则修订史断掉。
- 不替别的部门派活、不写“由 XX 中心牵头”；口径不明的数据不背书，宁可删。

## 图之上还有一层：视（视频）

用户把表达层级推到 **「文不如表，表不如图，图不如视」**。视频只用在**过程/时序/状态推进**上——静态图和文字都说不清「先发生什么、后发生什么、满足什么条件才变」。典型案例：事件标签（用户行为→规则→标签）。

### 做法：写动效网页再逐帧录，不碰视频生成模型

所谓 AI 做视频，本质是「用写代码的能力产出动效网页，再截帧拼成视频」。Mac/VPS 都能跑，二十来分钟出片：

1. 单文件 HTML，暴露 `renderFrame(sec)`，所有动画由这个纯函数按秒数决定。**不能用 CSS transition / requestAnimationFrame**，否则截帧时间点不可控。
2. Playwright 循环：`evaluate(renderFrame, t)` + `screenshot`，30fps。
3. `ffmpeg -framerate 30 -i frames/f_%05d.png -c:v libx264 -crf 18 -pix_fmt yuv420p -movflags +faststart out.mp4`
4. 1920×1080、20 秒 ≈ 600 帧，单机一分钟内出片。

坑：
- Playwright 报浏览器不存在时，改用系统已有 chromium 的 `executable_path`，别硬下新版。
- 进度量要允许「超冲」（如 pRaw 上限 1.08），否则最后一个节点永远停在半透明，末帧看着没点亮。
- 画面上的数字必须真算（时间跨度、计数），不要用 `done*1.05` 这种凑数，用户会核对。

### 数字要能从画面上的证据推出来

视频里每一层的派生数字（规则命中值、累计次数、圈人人数）都必须**由同一份基准事件表算出来**，不能各画各的。做法：先立一份 7 条左右的基准事件（时间 + 事件类型 + 商品 + 来源），当作全场唯一依据，后面每条规则、每个属性过滤、每个圈人数字都标明它引用了其中哪几条。

反例（自己踩过、被下游 agent 当场挑出）：规则卡写「近 7 天浏览 X500 ≥2 次」，时间轴上却只画了 1 次 X500 浏览——规则和证据各写各的，观众一核对就发现对不上。判据：拿时间轴上的事件数亲自算一遍，能算出规则卡上那个数字，才算自洽。

圈人数字同样要闭合：`标签命中 1532 − 剔除已购 246 = 圈出 1286`，渠道拆分 `WhatsApp 842 + 邮件 444 = 1286` 不多不少。

### 属性筛选要在画面上留下证据

讲「为什么命中」时，五个属性不能只是排一排文字。每个属性生效的瞬间要在时间轴上**真的把不符合的事件筛掉**（节点变暗 / 打删除线 / 扫过时间窗竖线），观众才看见它在过滤什么。最后一项用完才解锁「5/5 满足 → 产出标签」的出口，未满足前出口保持锁定——这比另做一段反例更能表达「缺一个就不算」。

### 派活给 agent 做这类视频：先交分镜

让 agent 做动效视频时，Checkpoint 卡在**分镜方案**，不要让它直接写码。分镜要它交：总时长与帧数、各阶段的时间区间、每阶段画面出现什么元素、以及它自己的数据自洽校验。分镜阶段发现「数字对不上」「阶段之间没有变形承接」，改方案比改代码便宜一个量级。

派活指令必写三条红线：不许用视频生成模型（全程代码实现）；参考实现只读、不许改；不许碰服务和配置。另加一条正面要求「每个阶段切换必须是同一画面持续变形，不要切场景或淡入淡出换页」——否则会收到一版 PPT 式轮播。

### 讲「机制」不是讲「流程」

第一版只画了行为时间轴，被判 **「这就是用户地图，不是事件标签」** —— 差的是后面三层：

| 层 | 画什么 | 缺了会怎样 |
|---|---|---|
| 行为层 | 事件按时间轴依次点亮 | 只是日志流水，任何埋点都能拉出来 |
| 规则层 | 每条规则由几个**属性**拼成：事件来源 / 关联商品 / 时间窗口 / 统计口径 / 触发阈值 | 「为什么会被命中」讲不出来 |
| 判定层 | 多属性是 **AND**，全部满足才命中，画面上要有 3/3、5/5 的进度感 | 看着像随手打的标 |
| 结论层 | 命中的规则才沉淀成标签，标签再用于圈人、触达 | 停在概念，接不上业务 |

两组硬要求：
- **每个属性格子都必须有具体值**。「统计方式 = 累计次数」这种只有枚举没有值的写法会被当场判「没看懂」，改成「统计口径 = 按用户累计次数」+「触发阈值 = ≥ 2 次」，名和值分开放。
- **别在同一画面塞状态型语义**。「曾命中 · 已下单移除」会被追问「既然命中了为什么还要移除」。要么一开始就不命中（规则改成「当前仍未下单」），要么单独做一段讲标签失效，别混在主线里。

## 与相邻 skill 的关系

- `prd-doc-authoring` 管评审 PRD 的规格（章节、字段表、整页红框截图、base64 发布）；本 skill 管**表达层级与对外口径**，两者叠加。
- `pm-project-context-setup` 管项目目录体系；方案还在草稿/未评审时放 `00-草稿对话/<需求名>/`，不要放进 `03-产品设计/`。
