# UI 线框图（给评审 / 领导看）

## 何时用

- “快速出几个图，我要先给领导审核下 UI 图，简略就行”
- “红色圈出的这几条，帮我出个图”
- PRD / 需求评审前，要让人看到页面长什么样、改动落在哪里

**不是原型**。原型是可交互的 React 工程，这个是给人看的一张静态图，内容是版式 + 字段 + 标权。

## 产物形式

**直接给 PNG 长图，不给 HTML。** 用户明确要求过：「下次给我图，不要 html 了，这样更方便」。HTML 只是中转产物（留档、下轮好改），发出去的是 PNG 附件：`MEDIA:/绝对路径/xxx.png`。**不要把 HTML 源码贴进聊天框**，也不要让他自己复制存文件。

同一个场景的多个画面**合并成一张长图**——用户原话「这样连贯些…可读性高」，比拆成多张小图好用。HTML 仍然要写（内联 CSS、无外部依赖、无 CDN、无构建），因为下一轮改还得改它。

## 版式铁律

一节 `<div class="frame">` = 一张图。每节结构固定：

1. `<h2>`：图 N ｜ 完整路径，如 `图 1 ｜ 权限中心 → 用户行为（列表页）`——领导和开发都是先看“这是哪个页面”
2. `.sub`：一句话说清这页在讲什么
3. `.win`：浏览器窗口壳（`.win-bar` 面包屑 + `.body` 正文），画成窗口比画成漂浮卡片更像真页面
4. `.anno`：图下黄色条写「看图要点」，编号列出——不要让人自己从图里找结论

**新增项必须一眼可辨。** 领导看的就是“改了什么”，不标出来他要一行行比对：

- 零散项（筛选项、按钮）→ 蓝色圆角小标签 `新增`
- 表格列 → 新增列的 `th` 用浅蓝底 + 蓝字，`td` 用极浅蓝底；现有列全部保持灰字
- 配置弹窗的模块 → 小节标题后面挂一个 `新增` 标签

**待确认项单独一块**：虚线框 + `▼ 待确认（不卡开发，影响交互）`，编号列出要拍板的点。绝不混在正文里。

**一图讲一件事，一轮 3–4 张。** 覆盖任务的完整链，典型四段：

```
图 1  入口 + 列表页（这东西加在哪、列表长什么样）
图 2  配置详情（弹窗，分几块）
图 3  使用（业务在哪个流程里用到它）
图 4  使用结果（提交后它变成什么样子）
```

只出“配置”不出“使用”，用户会直接说“还少了使用页面的展示”。

这几段**最终合在一张长图里**（同一个 HTML 内多个 `.frame` 竖排，每帧 `margin-bottom:26px`），一并发出——不是 3–4 个文件。

**配色**：品牌蓝 `#415FFF`、浅蓝底 `#EDF0FF`、小屏灰 `#f5f5f7`、正文 `#334155`、次要文字 `#94a3b8`；告警 / 待确认用 `#f59e0b` + `#fffbeb`。样式起点用 `templates/wireframe-base.html`，复制后往里填 `.frame` 就行。

## 出 PNG

Chromium 装一次（装到 `/root/.agent-browser/browsers/chrome-<版本>/chrome`，注意不在 `chrome-linux64/` 子目录里）：

```
agent-browser install        # npm 报 EBADENGINE 可忽略，它还会装成功
```

**必须套内存隔离再跑 Chrome**。这机器上 Chrome 和 Hermes 网关在同一个 cgroup，直接跑会把网关 OOM 杀掉（一天被杀 6 次，用户因此要求停用 Chrome）。用 `systemd-run` 给它独立 cgroup，爆也只爆它自己：

```
systemd-run --scope -p MemoryMax=700M -p MemorySwapMax=0 --unit=shot-$$ /root/.agent-browser/browsers/chrome-<版本>/chrome --headless=new --no-sandbox --disable-gpu --hide-scrollbars --force-device-scale-factor=2 --window-size=1450,3000 --screenshot=/绝对路径/out.png file:///绝对路径/x.html
```

- `--force-device-scale-factor=2` 出 2 倍图，贴进 PPT 不糊
- **一次截整篇（长图）**，不要把每个 `.frame` 拆开单独截
- 窗口高度先给足（3000 起步）——`--screenshot` 会按 window-size 补齐空高，所以截完必须裁
- **裁剪与截断检测一起做**：PIL 转灰度，从底部往上扫第一条「非空行」（该行里像素值 <240 的超过 3 个即算非空），裁到 `内容底 + 36px`；同时看**底部留白**——**< 40px 说明内容被切掉了**，把 window-size 调高重截，不要直接发
- 渲染完顺手 `free -m` 看一眼，确认没把内存吃光
- stderr 里的 dbus / GLib / UPower 报错无害，不要重试

**HTML 线框只能走 headless Chrome 渲染**：LibreOffice 的 HTML 导入不解析 flex 布局，渲出来是坏的。浏览器没装就先把浏览器装上，不要换手段降级——用户等的是图。

## 系统图 / 时序图 / 流程图（用户点名要时）

- 跨系统链路（谁调谁、返回什么、哪步异步）用**泳道时序图**：参与方横排，实线同步、虚线返回/异步。用户会直接点名「我需要系统流程图（时序图）」，按他要的形态出，**不要拿「流程图更好读」去替换他的要求**。
- **先定受众，再定颗粒度。** 交付给产品/业务的时序图只出现系统级参与方（业务人员 / 我们的系统 / 外部平台 / 下游使用方），每行写「谁向谁要什么、给回什么」；接口名、请求方式、库表名、服务模块名（cms-admin、BFF、MySQL 这类）一律不出现——画成源码级泳道会被打回「我们是产品经理梳理的时序图，不是开发的」。源码级泳道只给自己取证用，不交付。
- **规模：≤5 个参与方、三段、≤18 步。** 每步一句话，注释只留真正会误解的 3–5 条。参与方或步骤超了就重排成「主链 + 待确认」，不要靠加列硬塞——塞满的图会被一句「看不懂，太复杂了」废掉。
- **下游参与方必须有证据。** 链路末端接哪个系统（触达、导出、报表）先查文档或源码，没证据就标「待确认」或直接砍掉，不许凭业务想象接一个；同一个词在不同模块含义不同（列表页「导出」是导出行明细，人群「导出」是名单交付下游），混用会把两件事画成一条链。
- 业务侧走的那条链用**竖向流程图**：阶段色块（前置外部依赖橙 / 配置蓝 / 使用绿 / 固化紫）+ 节点编号 + 判断分支左右两盒（是/否）+ 底部橙色虚线「待确认」块。
- **默认交付 mermaid 源码，不渲图**：用户原话「不要做图片给我，给我 mermaid 语法就行，我去渲染看，这样能省 token，而且你也好修改」。时序图给 `sequenceDiagram`（`autonumber` + `rect rgb()` 分段 + `Note over` 挂待确认），业务流程图给 `flowchart TD`（`classDef` 区分业务/系统/大数据/外部依赖，`subgraph` 当阶段块，虚线 `-.->` 表示外部前置）——各一个代码块，跟他聊得上、他随时能改。写完数一遍 ```mermaid 与 ``` 是否成对；节点文案含括号/斜杠/冒号时用引号包住。
- **只有用户点名要图才走 HTML + headless Chrome 截 PNG**（评审、PPT、给领导看）；那种情况两张图分两个文件，不要塞进一张长图——单图过高超出窗口，读者也分不清哪张讲系统、哪张讲业务。
- 一律用 **JS 数据数组驱动**（`rows=[...]` → 累加 y → 追加 DOM），不手写绝对坐标：改一行文案不用重算版面。箭头三段 y 分开设（线 `y+20`、三角 `y+15`、文字 `y`）；标签白底压在生命线上正常，**压住另一条标签才是错**，同一行只放一条消息。
- 出完**分区校验**：先整图问一遍（列头是否重叠、有无裁切、底部注释是否完整），再用 `vision_analyze` 的 `region` 裁中段放大看箭头与文字。只问一次整图，模型一律回“整体良好”，局部问题看不见。
- 绘制参数、两套数据结构、验收步骤见 `references/系统图绘制与验收.md`；裁底部白边用 `scripts/trim_bottom_whitespace.py`。

## 交互版 HTML 的验收：跑断言，不读代码

线框 HTML 被要求「加上所有交互效果」后，agent 自报“已实现”不算数，**读它的 JS 源码也不算数**——源码里写了 `addEventListener` 和一堆 `showToast` 时，读代码会把“弹了个提示”当成真实现。做法：把 HTML 落到本机，`browser_exec` 打开 `file://`，用一段 JS 断言逐项实测，按「真能用 / 看似能用实际是假 / 没做」三段出清单，每条带实测值。

高频降级项（逐条都要断言）：

| 断言 | 假实现的样子 |
|---|---|
| 点整行是否打开详情 | 只有“查看详情”文字绑了 click |
| Esc / 点遮罩是否关闭弹层 | 只关了筛选菜单或别的弹窗 |
| 点排序表头后行顺序是否变 | 表头点开的是筛选菜单，压根没排序 |
| 点第 2 页后行内容是否变 | 只换了页码高亮 |
| 切每页条数后行数是否变 | 只弹 toast |
| 搜无结果是否出现空态元素 | 行全隐藏，没有空态 |
| 顶部“筛选后的数据”提示条是否随筛选显隐 | 常驻显示 |
| 页面里有几份列表 | 列表态 + 抽屉态各写一份，点详情只是滚到下面那张 |

**交互形态先查项目规范，不自己发明**：列表筛选、抽屉、批量操作这类有既定规范（项目里通常在 UI 规范库，如 `07-UI规范库/03-组件与交互规则.md`）。规范里没有的形态（右侧筛选面板、按门店分组多选、chip 回显）画得再顺也会被退回；规范没覆盖就先问用户要允许的形式，再动笔。

## 列表改版类：字段进列表还是进抽屉

把「账号视角列表」改成「好友视角列表 + 详情抽屉」这类需求，图的表面是排版，实际是**字段分配**；分配没定就画，每版都会被退回（该在列表的没显示、该在抽屉的没显示）。

1. **先算总数再谈布局**：`现有系统列数 + 本次新增字段数`，逐个点名列出来再动手。用户口述的字段分类和字段清单对不上时（说新增了「好友数」而清单记的是「导购ID」）**当场指出差异让他选**，不要自己挑一个往下做。
2. **先按属性分类**（账号 / 导购 / 好友 这类实体归属），再定列：分类决定哪些字段该进列表、哪些该收进抽屉，分类错则列怎么排都是错的。
3. **划分判据**：列表只放「一屏上要横向比较、据此做判断」的字段（名称/标签/归属人/时间/次数/一眼可见的状态）；抽屉放「定位到某一条才看」的字段（账号标识、授权、同步时间、组织与门店）。用户质疑「列表上不还是会重复展示 X 吗」时，用这个判据回答，而不是删列或增列。
4. **字段名用真实系统原文**：以页面采集（`全局背景信息/参考资料/中文/02-页面采集/<pageId>-<页面>.md`）为准，不做口语化缩写（「Whats账号删除状态」不能写成「账号删除状态」）。
5. **同名字段必须点破区别**：列表里的「所属导购」与抽屉里的「账号所属导购」是两个实体上的字段，不写一句解释就是设计歧义。
6. **分屏渲染让 agent 读表**，不要让它从中文指令里归纳字段名和枚举：字段落位映射表（属性分类 / 列表列序 / 抽屉分组 / 枚举 / 空值）的格式与写法见 `field-list-tsv` 的「页面落位映射表」一节。
7. **列表与抽屉字段互斥，不重复展示。** 抽屉只放列表没有的字段；名称、状态这类需要在抽屉里有归属感的字段写成标题区锚点（主标题放名称、副标题放状态标签），不占分组字段行。「抽屉是完整档案」是错的说法——照它实现出来的抽屉会把 17 个字段全列一遍，用户当场反问「怎么抽屉变成全量的字段了」。

## 坑

- **输入是截图时，先把图里的内容逐格读全再动笔**，特别是表格的菜单列和功能点列；政策 / 口径文字常被单元格边界截断，读到半句就标出来问，不要自己补完整。
- **同一页里把联动关系画出来**：如果配置页有个开关影响使用页的行为（比如“不允许限制时间范围” → 圈人时时间框置灰），使用页就把那个控件画成置灰虚线并注明原因。这是评审时最有说服力的一张图。
- **不要把表格 / 清单用空格对齐画进聊天框**——手机上列全歪，用户会直接说「发表格的可读性太差了」。表格类内容一律出文件（xlsx / tsv）当附件发；图就发 PNG。
- **一图一态**：列表态与抽屉/弹窗详情态不要并排画在同一画布——读者会把它当成表格下面又跟了一块，直接说「没看懂」。抽屉要靠点击才出现，图上标清「点击某行 → 右侧滑出」的切换关系；真要一张长图里给两种态，就成对编号（图 2a 列表态 → 图 2b 点击后的抽屉态）并写链。
- **同名字段必须点破区别**：表格列「所属导购」与抽屉里「账号所属导购」这类同族命名，不写一句解释就是设计歧义——在黄条注释里逐条说明各自口径。
- **不许自造派生列，聚合列先问再做**：把两个真实字段拼成一个更“好懂”的列（「Whats账号删除状态」+「数据同步时间」→「账号可用状态」）会被当场否掉——用户一句「为什么会有这个字段」就没有第二个答案。列表字段只能是「现有系统页面采集」+「本次新增清单」的并集；确实要聚合，先把「仅一对多才需要聚合」这个前提写进待确认块再问。
- **不要依赖 CDN、不要用需要构建的框架**：他要能离线双击打开，也要能自己复制粘贴到任意环境。
