# PM 入职接盘流程

> 你拿到的不一定是白纸。先摸清已有资产,再定自己做什么。

## 标准三步

1. **要代码仓库** — 先 git clone,看 README/package.json/路由结构。全栈可能已经写了页面。
2. **要项目文档** — docs/ 目录、需求说明书、设计说明书、演示脚本。前 PM 可能留了全套。
3. **要演示账号** — 有测试账号就登录跑一遍,没账号就 `npm run dev` 本地起。

## 正确姿势

```text
老板说"接这个项目" →
  1. 要代码仓库地址(git clone)
  2. 要 docs/ 压缩包
  3. 要演示账号/本地启动方式
  4. 读完再定:我做什么,不做什么
  5. 复盘缺失——前PM留了什么(REQ/ARCH/API)?缺了什么(PRD/交互图)?
```

**反模式:** 拿到几份文档就假设是白纸项目,开始设计交互原型(其实全栈已经画了43个页面)。

## 补充: 接盘后5步审计(入职第一周)

按顺序摸清项目全貌,不跳步:

| # | 审计项 | 方法 |
|---|--------|------|
| 1 | **文档资产** | docs/ 目录 + 外部需求说明书/设计说明书 → 出资产清单 |
| 2 | **代码资产** | git log → README → package.json → 路由 → 页面数 |
| 3 | **集成资产** | SPD/接口/字段映射 → 出对接进度表(已接入/缺口/待办) |
| 4 | **需求资产** | REQ追溯矩阵 → 识别P阶段缺口(P4算法层通常是重灾区) |
| 5 | **缺失清单** | PRD?交互图?系统交互图?用户任务流程图?功能列表(业务视角)? → 这就是你的第一份交付物 |

## 代码资产审计：先列全部分支，当前分支不等于全部仓库

用**当前检出分支**的代码去判断「某功能有没有实现」，是接盘阶段最常见的误判。功能常在新版本分支上开发，主干还停在老版本，于是在主干上搜一遍关键词全部落空，就直接得出"这个能力还没做"的结论——而用户下一句就是「我们不是有源码吗」。

实测形态：某导购端仓库 master 上只有卡券核销页，搜「预售/订单/核销」全落空；`git branch -r` 一列，`origin/1.8.0` 上躺着完整八个页面（销售工作台、订单列表、订单搜索、订单详情、分享活动列表/详情、设置跟进人、取货码核销）+ 公共弹窗组件 + 两套 mock 数据，连主页底部导航的销售入口都改好了。

做法：

1. `git branch -r` 列全部分支，按版本号 / 特性名找候选（`v1.8.0`、`1.8.0`、`presale`、`feature-xxx` 这类）。版本号往往来自需求文档的版本命名，不是仓库的默认命名。
2. **只读查看，不切分支**（工作区保持干净，免得污染用户正在用的检出）：
   ```bash
   git ls-tree -r --name-only origin/1.8.0 | grep -i '<模块关键词>'
   git show origin/1.8.0:src/views/sales/orderList.vue
   ```
3. 确认所有分支都没有，才可以说"没有实现"，并在回话里写明扫了哪些分支。

配套判据：**关键词搜不到，先怀疑命名，再怀疑分支，最后才怀疑没做**。用页面/目录清单（全量列文件）比关键词匹配可靠——某功能的页面可能叫 `orderList`、`workbench`，一个"预售"字都不带。

## 跳系统嵌入：找不到实现时，先查是不是 iframe 嵌了别的系统

判断「某业务功能在本系统有没有实现」之前，先排除一种结构：**本系统只提供壳，业务页面在外部系统**。实测形态：后台系统的销售/预售菜单点进去，页面是 iframe 加载的商城后台（`shopIframe/index.vue` 按 `pageId` 查一张 URL_MAP，拼出商城域名塞进 iframe），本系统只管菜单、登录态、语言切换（postMessage）。

误导点：本系统后端里搜不到对应的 Controller / 接口，很容易判成「功能没开发」。真相是数据在外部系统，本系统天然没有这套接口。

识别做法：

1. 搜 `iframe`、`src=`、`<embed>`、外链域名，看有没有嵌入外部系统的容器页。
2. 读容器页的映射表（`URL_MAP` / `pageMap` 这类），把 `pageId → 外部路径` 全列出来，比猜菜单名准。
3. **路由名不等于菜单文案**，真实菜单多在 i18n 的 `layout.js` 里：实测 `remark-list` 的菜单叫「评论列表」、`shop-list` 叫「实物商品」、`gift-management` 是「赠品活动管理」不是「赠品管理」。先按映射表把三者对齐再回报。
4. 结论写成「本系统只提供入口，业务页面在 X 系统的 Y 路径」，并说清本系统负责什么（菜单 / 权限 / 登录态 / 参数传递）——这直接决定后续原型该画个壳还是画完整业务界面。

## 源码优先于 PRD：要复刻/补齐原型时，别让 Agent 去读 PRD 套件

找到源码后，**照源码出结构清单**（页面、路由、字段、交互、组件、mock 数据结构），不要去读 PRD 套件。源码是唯一真源；PRD 只是当时的意向——它可能对应另一个版本、后期又改过、或者实现细节压根没同步。让 Agent 先读四份 PRD 再动手，既烧 token 又会被旧设计带偏，用户会直接反问「为什么要读 PRD 套件，我们不是有源码吗」。

PRD 只在三种情况下才翻：①该模块源码缺失（未开发 / 在别的仓库 / 别的分支）；②需要业务意图或权限口径而代码里看不出来；③要判定某功能是否属于本期范围。

另一个高频陷阱：**文档里的 UI 稿目录名、版本号，比代码更能定位分支**。PRD 套件叫「v1.8.0 外销预售功能」、需求 PDF 叫「外销预售 180 版本」，那个 `1.8.0` 就是去找分支的钥匙，不是当前 `master`。
