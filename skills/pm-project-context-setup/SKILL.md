# PM 项目上下文搭建

基于 PM Vitamin 课程「三层六步工作流」方法论的标准化项目搭建流程。核心目标：把业务背景、系统架构、规则约束结构化地塞进 AI 的上下文，让同一个 AI 产出的 PRD 质量从"不能用"变成"可作起点"。

## 方法论速查

| 层级 | 步骤 | 产出物 |
|------|------|--------|
| **宏观层** | ①业务上下文 → ②系统骨架 → ③场景流程推演 | 项目背景、上下游系统、功能模块清单、入库/出库流程详解 |
| **中观层** | ④字段清单+规则 → ⑤用例推演 | 字段清单（**用 TSV**，初稿5列→详细稿13列）、业务规则、高频用例数据 |
| **微观层** | ⑥页面实现+原型 | 前端 Demo PRD、前端代码 |

## 标准目录结构

```
project-name/
├── AGENTS.md                  ← AI 入职指南
├── CLAUDE.md                  ← 指向 AGENTS.md 的路标（仅指针，不存实质内容）
├── 01-項目背景/               ← context/ 对等目录
│   ├── 00-背景信息索引.md
│   ├── 01-项目背景.md
│   ├── 02-上下游关联系统.md
│   ├── 03-主要功能模块和清单.md
│   └── 04-入库流程详解.md
├── 02-PRD 文档/               ← PRD 工作区
├── 03-参考模版/               ← template/
├── 04-参考資料/               ← reference/
├── 05-常用提示/               ← prompt/
├── 06-前端原型 Demo/          ← prototypes/
└── 00-草稿对话/               ← drafts/
```

## 工作流：Hermes + Cursor 协同

**阶段一：Hermes 搭骨架（本阶段）**

1. 确认项目性质（定制项目 vs 标准化产品、单一客户 vs 多客户、单仓 vs 多仓）
2. 创建目录结构 + 写 AGENTS.md
3. 写 `01-项目背景.md`（项目起因、目标、角色、范围、NIS）
4. 将背景文件发给用户确认

**阶段二：Cursor 生成，Hermes 审核**

5. 用户将 AGENTS.md + 01-项目背景.md 导入 Cursor 项目
6. 在 Cursor 中用 Sonnet 5 High 生成 02-04 三份文件
7. 用户将 Cursor 输出发回 Hermes
8. Hermes 做质量审核：Mermaid 语法、业务逻辑自洽、交叉引用准确

**阶段三：验证**

9. 让 AI 做"有上下文 vs 无上下文"对比测试——同一道题，喂文件前和喂文件后各写一段需求背景概述

## 审核清单

每次生成或修改上下文文件后，逐项检查：

- [ ] 项目性质一致：定制项目不说"多家客户"，标准化产品不说"XX公司"
- [ ] 仓库数量一致：单仓的项目不出现"多仓库支持"
- [ ] 模块范围一致：NIS 的功能不在"覆盖模块"里出现
- [ ] 角色职责一致：NIS 的功能不在角色职责里出现（如调拨 NIS → 主管职责不能有"审批调拨"）
- [ ] Mermaid 语法正确（flowchart 节点用 `{}` 表示判断，sequence 用 `alt/else` 分支）
- [ ] 交叉引用路径正确（文件名和编号匹配）
- [ ] 量化数据有来源（45分钟→15分钟 要有"三雄极光反馈"之类的出处）
- [ ] 待确认 vs NIS 不混用（技术不确定标【待确认】，范围排除标 NIS）

## 路径注意

用户在 Mac 本地用 Cursor，Hermes 在 VPS 上。给 Cursor 的指令要用 Mac 本地路径（如 `01-項目背景/`），不能用 VPS 路径（`/root/notes/projects/`）。发送修改后的文件时，直接贴完整内容或给修改片段，不要假设文件在 VPS 上就能被用户拿到。

## 需求池/台账类目录：状态是列，不是目录

需求池这类「一张表跟踪多条需求」的数据，**按状态分文件夹是反模式**：

- 状态会变（预研未排期 → V1.8.0 → 已上线），每变一次就要搬文件 → git 历史断裂、外部引用失效
- 版本目录和状态目录混在同一层（`V1.9.0/` 是版本，`已上线/` 是状态），语义不齐
- 状态已经写在文件名（`-P2-需求接受`）和 README 表格列里，文件夹再分一次 = 同一事实存三份
- 几十个 md 若只是把表字段逐条复制出来（无增量信息），就是"把筛选器做成目录"，纯增熵

正解：**一张 TSV 当唯一事实源**（类 Excel、可 diff 可筛选），状态/优先级/版本/归属全是列。目录只留 `README.md`（规则）+ `需求池.tsv`（全量）+ 按需的 `需求拆分/`（针对单条需求的深度分析产物）。

**要分清两类东西**，混在一起就会觉得目录很重：

| | 是什么 | 形式 |
|---|---|---|
| 需求池 | 状态跟踪表 | TSV，一行一条 |
| 需求分析产物 | 针对某条需求深挖的文档 | md，放需求拆分/ 或 03-产品设计 |

**刷新需求池的标准动作**（在线抓取指令写法见 `intranet-data-capture` skill）：Cursor 只读导出在线表 → 覆盖 TSV → 在 `导出说明.md` 补一节「本轮差异」（日期、总条数、新增/减少多少、表头有没有变）。

**跨版本对账一律用单号做唯一键**（VR 号/工单号），不要用需求名：名称在不同来源里空格、【】、标点、前缀都不一致，按名称前缀匹配会把大量老需求误判成「新增」；只有无单号的新需求才退回按名称识别。父单号消失不一定是丢失——在线表常把父需求拆成多条子需求独立成行。

**表头会漂移**：导出前先让 agent 报「实际几列 + 逐列列名 + 与历史列结构的差异」，别假设列数不变（实际遇到过 18 列变 19 列、新增一列、另有一列改名）。

**优先级口径**：需求池的优先级列 = 产品定义的优先级，以此为准；需求原文里业务方另写的优先级，**仅当一条需求包含多个子需求时**才参考。统一大写 `P`（`p1/p2/p3` 混用要规范化）；`P2 / 0630调整为P1` 这类调整记录保留原样，别改成单一值丢掉历史。

**旧版归档而不是删**：目录改造时旧数据用 `git mv` 整包进 `_archive/<名称>-<日期>/`，不用 `git rm`。git 会把整目录移动识别成 100% rename，历史完整可回溯。

## 方案类文档的形态：图 > 表 > 文

用户对纯叙述方案的反馈原文：**"缺少页面截图和流程图，全是大白话，文不如表，表不如图？"** 。产品方案、迭代计划、PRD 交出去前逐段自查：

| 层级 | 承载什么 | 判据 |
|---|---|---|
| 图 | 流程、状态、时序、页面结构、条件组合逻辑 | 有"先干什么再干什么""在哪些状态之间流转""界面上长什么样" |
| 表 | 对照、字段、规则、验收、待确认 | 并列同类项且每项属性一致 |
| 文 | 只在图和表都不合适时 | 大段连续叙述 = 没想清楚，回去拆成表 |

方案稿至少配：端到端流程图（业务动作→系统环节→结果）、状态机（对象有生命周期时，并把"不做删除只做停用"这类取舍理由写在一起）、时序图（跨多方的数据流）、条件组合逻辑树（多条 AND/NOT 叠加时）、迭代路线图。

**功能没开发、没有真实截图时**：画 HTML/CSS 线框（比手写 SVG 好维护），一个 HTML 放多张面板，每张标清是哪个页面、每个字段是什么；并在文中声明"这是线框不是截图，原型做出来再补真实截图"——不拿线框冒充截图，也不因为没截图就不给页面。

**给评审/同事看的文档，人名写真实姓名**，不写助手圈里的昵称——昵称在评审场合等于无人认领的占位符。

**升版时前版已确认的结论要逐条回收**：重写或升级方案（v3→v4）时，前版里已谈定、带出处、带对接人的结论最容易蒸发（如"大数据按需求开表"这个已确认机制、现成的内销表结构），漏掉会在评审被问"数据怎么来"而答不出。做法：升版前列出前版「已确认」清单（谁确认的 + 出处章节），逐条比对新版是否还在，不在的要么补回、要么在修改记录写明为何删。**已确认结论只能被推翻，不能被遗忘。**

**待确认项不替对方填默认值**：前版写"取值未知"的，新版不能升级成自己猜的枚举值，否则等于替对接方签了结论。

## 删文档/清目录前的三查

清理冗余目录（提示词合集、旧版本指令等）前，按顺序查这三样，缺一样都可能删出问题：

1. **活引用**：全库 grep 目录名，**排除历史报告里的旧路径文字**（自检报告写的"依据：`05-提示词合集/prompt/x.md`"是历史记录，不是活引用，不用改）
2. **别处备份**：这套模板/规范是否在其他仓库也有一份（`grep -rl "<特征标题>" /root/repos`）；有备份才能安心删
3. **索引与目录树**：根 `README.md` 的目录树、其他 README 里的"先读 XX 目录"说明，跟着删或改编号

删除用 `git rm -r` 保留历史。**删完必须核验真实条数**：`git diff-tree --no-commit-id --name-status -r <commit> | awk '{print $1}' | sort | uniq -c`——手写 `ls dir/*.md` 只算顶层，会漏子目录（曾报 19 个实际 48 个）。

**「删内容」不等于删文件夹**。用户说「把 X 里的内容删了」「太冗余了」时，删的是**里面的文件**，目录结构（含各级子目录）保留。动手前先把「删什么 / 留什么」列成清单等用户点头，禁止按自己的理解扩大范围——曾把「删内容」执行成整目录 `git rm -r`，被要求恢复。

保留目录时注意 git 不跟踪空目录：每个空目录放一个 `.gitkeep` 占位，否则对方 pull 下来目录会消失。

## 常见陷阱

| 陷阱 | 表现 | 预防 |
|------|------|------|
| 口径污染 | 写的时候按标准化产品写的，后来发现是定制项目，残留"多家客户""多仓库"等表述 | 步骤1先确认项目性质，写完 01 后全量扫描其他文件 |
| 角色越界 | 主管职责里有 NIS 功能（调拨审批出现在无调拨的项目里） | 每改一次 NIS，同步检查角色职责表 |
| 路径错乱 | 给 Cursor 的指令用了 VPS 路径，用户无法执行 | 所有 Cursor 指令用 Mac 本地路径 |
| 表头断裂 | Cursor 生成的 Markdown 表格偶尔多出 `|`（如 `|||`） | 审核时检查表格列数是否一致 |
| 字段清单双份 | 同时维护 `.tsv` 和 `.md` 字段清单 → 不知道哪份最新 | 只用 TSV 一份当字段唯一事实源；md 表字段一多就乱、且 AI 不易处理；详见 references/tsv-field-list-methodology.md |
| 图语法错误 | Mermaid 关键字写错或括号不匹配 | 审核时模拟走一遍图的每个分支 |
| 项目框架新旧并存 | 升级框架时新增 00~09 目录但旧目录(context/prompt/prd-docs/front-prototype)没被吸收 → 语义重复两套并存 | 升级必须用**独立分支**承载，旧目录 git mv 进新家；见 references/qs-jxc-layered-framework.md |
| 双 agent 并行同仓库 | Codex 合并+反重力产物在同一工作副本抢 git/路径 | 并行必须用隔离克隆；未 commit 的两个副本要收口到一个主副本再单条 commit，不两处分别 commit/push |
| 游离目录 `docs/` | 全景图、OKR、培训材料、竞品调研、旧汇报都塞进 `docs/`，不在 00~09+99 体系内，最后变成一个杂物间 | 项目里**不建 `docs/`**（QS-JXC 就压根没有这一层）。调研进 `02-需求调研/`、架构图与流程进 `01-全局背景信息/flow/`、参考材料进 `08-相关资料/参考数据/`、过程草稿进 `00-草稿对话/`；拆除时 `git mv` 逐个归位，再删空目录，同步改根 README 目录树 |
| 未定稿的方案混进 `03-产品设计/` | 需求还停在“需求提出”、还有十条待确认，却和已带完整 PRD 套件的模块并列，让人误以为已评审 | 判断标准看需求池状态与待确认余量：**未评审/未定稿一律进 `00-草稿对话/<需求名>/`，评审通过后再升 `02-需求调研` 或 `03-产品设计`** |
| 插章节把 Mermaid 围栏吃掉 | 用 patch 在代码块前插新章节时，`old_string` 若包到 `````mermaid`` 开头行，替换后围栏就不成对，图变成正文（表现为 `participant`/节点行裸在正文里） | 插完立刻验：`grep -c '^```' doc.md` 必须是偶数、`grep -c '^```mermaid'` 等于图数，再扫有无裸露的 `participant`/`sequenceDiagram` 行；图块标题与图本身要保持相邻 |
