# QS-JXC 分层项目框架（把产品项目对齐到它）

来源：维他命 QS-JXC-Project（github.com/TopVitamin/QS-JXC-Project）+ 4 篇实战课程文档。适用于把已存在的产品项目（如 forge-crm）升级为这套分层框架，或新建项目直接搭这套骨架。

## 框架结构（01~99）
```
00-草稿对话 / 01-全局背景信息 / 02-需求调研 / 03-产品设计 / 04-常用模版 / 05-提示词合集 /
06-产品方法论 / 07-UI规范库 / 08-相关资料 / 99-产品原型prototype
+ AGENTS.md(权威源分层) + README(框架地图) + .cursor/rules + CI
```
- `03-产品设计` **按日期版本分目录**（`<日期>-<版本说明>/`），第一版留基线，迭代进新版目录，不覆盖第一版。每版本下：字段清单 TSV(初稿+详细稿) + 系统架构与流程 + 每模块 = 主PRD + 页面骨架(可选) + 前端Demo_PRD合集(列表/新增编辑/详情) + `annotations/`。
  - **页面骨架"可选"到什么程度可省（2026-09 定口径）**：不画骨架，光靠 DemoPRD 就能在脑内清楚看到页面组织/层级/跳转关系、走查不乱的，可省；反之（页面多、页面间关系复杂、或多人评审需一张结构图托底）才补。它是"必要时的脚手架"，作用是“看得清页面级结构"，不承担 UI 细节。
- `99-产品原型prototype/` = 前端 Demo（npm 根）+ prototype-annotation。

## 展示项目结构时：线框图 + 标注（用户偏好 2026-09）
给 README/文档补\"项目结构\"时，用户要的是**ASCII 线框结构图 + 分层逻辑标注**，不是只给目录表格。做法：先用代码块画一棵 `├─/└─` 目录树（每行 `目录名 ── 一句话职责`，关键路径带缩进展开），再在树下方用要点标注\"分层逻辑\"——01~03 从上到下（全局约束→调研→版本设计，03 按日期-版本迭代/第一版留基线）、04~07 资产库（模板/提示词/方法论/UI 规范，不混业务事实）、99 收尾原型槽位（刻意放最后非 09 笔误）、文档主链路（架构/流程→TSV→业务PRD→骨架→DemoPRD→原型→回归）。线框让一屏看懂骨架，与目录表互补不互替。
1. **单一事实源分层**：每类信息只认一个权威源，不互相覆盖（"不使用一份文档覆盖所有问题"）——解耦的根基，不是目录好看。
2. **约束集中编号化**：全局规则(01)、UI规范(07)、默认字段校验规范，都是集中、编号、有权威源的，不散落。
3. **变更沿权威源单向传播**：改哪层先改该层权威源，再沿依赖往下游传播，不反向发明——防错骨架。
4. **模板+提示词让产出同构**：04 模板 + 05 提示词保证每次产出结构一致、可复用、可比。
5. **"待确认/不臆造/诚实边界"是对 AI 幻觉的结构性对抗**：冲突先列证据→未确认标待确认→用户拍板→再同步；README 明标"未实现/旧规划状态/不补空壳"。

## 04-常用模版 = 产出执行索引（README 是 AI 第一个入口）
执行顺序带验证关卡：Step①业务上下文→②系统骨架(Mermaid ER)→③场景流程推演(⛔关卡1:流程走不通回①②)→④字段清单+主PRD(⛔写顺序约束:先字段后PRD；简单型不写主PRD)→⑤用例数据推演(⛔关卡2:数据跑不通回④③)→⑥前端Demo PRD+原型。区分标准型/简单型文档集。

## 07-UI规范库 = spec-manifest 驱动
`spec-manifest.json` 是唯一索引：design_principles(设计方向) + confirmed_dimensions(顶栏54/侧栏200/控件32…) + **page_templates(每种页面类型要读哪几份规范：list 读 01,02,03,04,07；modal_form 读 01,02,03,04,08…) + 页面→spec 映射 + ai_task_templates**。8份编号规范：01系统约束与Token基线(避`bg-brand-6/10`透明度坑)/02页面模板与实例映射/03组件交互/04状态权限异常/05AI协作IO模板/06模块契约与原型复刻/07单据复刻/08轻量弹窗。补 UI 标准时就按 manifest 的页面类型→规范映射来配，别只有 README。

**⚠️ 07 要按目标项目的实际代码适配，不能照抄 QS-JXC**：token/组件/尺寸必须读目标前端真实实现（如 `src/index.css` 的 CSS 变量 + `components/ui/*` 既有封装）来固化，不搬 QS-JXC 的 Arco 色板（技术栈不同：shadcn/Tailwind v4 vs Arco）。forge-crm 实际：主色 `--primary 221.2 83.2% 53.3%`(蓝≈#2563eb)、slate 灰阶中性层、0.5rem 圆角、14px 正文、页面底色 210 40% 98%；语义层固化为 主按钮 `bg-blue-600/700/800`、次级 `bg-slate-100`、危险 `bg-red-500`、信息工具条 `bg-blue-50 text-blue-700`。**建 07 前先读一遍真实 index.css + 代表性页面(App/列表/表单)把布局样板也固化成 02 页面模板**，禁止散写 HEX 与 Tailwind v4 透明度修饰符（对 CSS 变量做 opacity 易静默失效）。

## 来源：4 篇实战课程如何长出这套结构（用户问"结构从哪来/怎么分层"时讲）
同一链路（宏观走查→字段初稿→详细稿→业务PRD→页面骨架→DemoPRD→原型→走查回写）在 4 篇重复走 4-5 遍，每篇沉淀一层：①实战篇1 = **目录结构来源**（第3节标准结构 context/template/prompt/prd/prototypes/drafts/reference + 背景宏观→中观→微观 + 字段初稿5列/详细稿13列 + 8步搭建法）；②实战篇2 = **工作流方法论**（每产物只负责一类问题/三层分开/一次只输出一个层次/先给边界再给任务/需求变化找真正修改入口）+ **版本目录迭代法**（03 按 日期-版本 并存，第一版留基线）；③实战篇3 = **沉淀三形式**：模板(04)/Prompt(05)/Skill(06)——把重复劳动收口成固定资产；④沉淀方法论=**完整链路+三层约束拆分+变更表+交付前最小检查**。故 04/05/06 三个目录存在的根因 = "同一件事重复多遍又望每次一致 → 沉淀成资产"。`99-产品原型prototype` 是刻意放在最后的原型槽位（不是 09 笔误）。

## 认真解读整个项目结构时（用户要通读，不是抽样）
用户要"认真解读一个项目的结构"时，只读 README/AGENTS + 抽几个文件就自称读完会被打回（该 session 即被打断"每一个项目文件夹都读了吗？"）。正确做法：①先 `find <root> -type f` 拉全文件清单按顶层分组；②逐文件夹读承载约束/标准的正文（01全局/04模板索引/05规则/06方法论+踩坑/07 manifest+规范），产物的结构以模板为准不必逐字读每个模块 PRD；③汇报时**诚实标注覆盖面**——哪些正文读了、哪些只读了结构清单，不下"全读"结论。

## 权威源分层（AGENTS.md 核心）
按信息职责取值，不用一份文档覆盖所有问题：
- 跨模块口径 → `01-全局背景信息`；跨角色流程→业务流程；跨单据处理→系统单据流程。
- 字段名称/类型/来源/枚举/字段级约束 → **字段清单详细稿 TSV**（确认后唯一源）。
- 模块内状态/动作/业务规则/回写/异常 → **业务 PRD**。
- 页面结构/控件/显隐/校验时机/反馈 → **前端 Demo PRD** + `07-UI规范库`，不反向从 Mock 发明业务规则。
- 冲突先列文件证据+影响范围；未确认标"待确认"，用户拍板后再同步权威源与下游。

## 三层分开（每层各管各，别揉一起）
同一字段分三层写：字段事实=TSV（"采购数量是整数，>0，用户填"）/ 业务规则=业务PRD（"提交审核时每明细行必填，审核后不可改"）/ 页面交互=DemoPRD（"NumberInput，失焦校验，错误定位到行"）。三层是答三个问题，不是重复。

## 变更传播方向表
| 变化 | 第一修改入口 | 后续检查 |
|---|---|---|
| 字段名称/类型/来源/枚举/字段级约束 | 字段清单详细稿 TSV | 业务PRD、骨架、DemoPRD、原型 |
| 状态/动作/业务规则/业务结果 | 业务 PRD(必要时回流程) | 字段清单、所有页面产物 |

## TSV 字段清单
初稿5列：字段所属分组/字段名称/字段类型/字段来源/字段说明。
详细稿13列：初稿 + 必填性/新增页/编辑页/列表展示/可筛选/详情展示/取值说明/备注。
确认后以**详细稿 TSV 为唯一源**，不维护 Markdown 字段表副本（两份并存必出"哪份最新"疑问）。

**初稿/详细稿共存期，初稿什么时候"退休"（2026-09 定口径）**：不是详细稿生成**立即**废弃，而是以**一次走查通过**为门槛——初稿(5列)= 确认范围，详细稿(13列)= 定规格/唯一源；但详细稿刚生成时可能还有"待确认项"没核完（如枚举、边界），走查验收把待确认都厘清后，初稿才退休/存档——留作历史演进记录，不再被引用。

**多单据/多子对象用 `===== 大分组 =====` 分隔行塞进同一个 TSV**（用户要求采纳的结构）：一个大 TSV 里用 `===== 单据名 =====` 切出多个模块（如 `===== 采购订单 ===== / ===== 采购入库单 =====`），表头只出现一次在文件首行，模块内用 A 列"字段所属分组"做二级分类（单据头/基本信息、单据体/商品明细）。目录按 `<模块>的字段清单/<模块>模块字段清单（初稿|详细稿）.tsv`。转换时**只转干净的 `字段：描述` 条目为 4 列表格（字段|展示/输入类型|业务说明|约束与备注），枚举/短语类（无冒号或一整串字段名）保持原样不硬塞表格**——强制把所有 `- ` 变表格会产生垃圾行。要"字段说明"以表格形态显示，运行时 `countMarkdownItems` 还必须统计表格行（它默认只数 `- ` 列表行，见 SKILL.md），否则面板字段 tab 显示 0 项。

## 把一个已有项目按 3 层缺口对齐到这套框架（forge-crm 0913test 已跑通）
骨架 00~99 + 01全局 + 04/05/06 导入通常先做；对已搭骨架但标准未满的项目，闭环这三个缺口（按价值序）：
1. **07-UI规范库**（断链最重）：只有 README 占位 = UI 权威源缺失。按 spec-manifest（页面类型→规范映射）+ 8 份编号规范建，token 读目标前端真实实现。
2. **AGENTS.md 补强**：加"AI 协作四段式（输入材料/当前任务/权威边界/输出要求）+ 一次只输出一个层次 + 三层约束拆分（字段TSV/业务PRD/页面Demo）"与"分类型验证门（文档/字段/前端，build≠运行态）"。
3. **03-产品设计 日期版本化**：`git mv <首版目录> <日期>-<版本说明>`，保历史；以后迭代建新版本目录。配置/编译产物若引用旧路径，rebase 后要用 `--output` 重编译到真源一次。
做完 07+AGENTS+版本化，框架即与 QS-JXC 对齐（07 管 UI、AGENTS 管协作流程、03 管版本）。

## 把已有项目迁移进该框架的坑
1. **必须在真源上做，不在半镜像/Hermes 侧拷贝**：VPS 的 `/root/repos/forge-*` 常是 Mac 工作区的半镜像（缺 docs/drafts/prototypes/reference 等目录）。在 VPS 上 git mv 到新骨架、推分支后，Mac 真源上旧目录因从未被 VPS 跟踪而残留为 untracked → 新骨架与旧目录并存 = 大量语义重复。**框架合并要在 Mac 真源执行（本地 agent），VPS 只当骨架参考**。
2. **先 git 审计再动**：checkout 分支后 `git status --short` 区分 tracked vs untracked；untracked 的草稿/资料/原型目录不会被分支切换清理，要单独吸收，不静默丢弃。
3. **`git mv src dst` 到已存在的空目录会嵌套**：dst 已是(空)目录时产出 `dst/src` 而非改名。renaming 前先 `rmdir` 空目标，或 rename 到不存在的路径；事后展平用 `git mv sub/* .` + `rmdir sub`。
4. **`cp -rn src/dir dest`（dest 为已存在目录）会再套一层**：产出 `dest/src/*`。要合并内容时逐项 cp，别整目录 cp。
5. **AGENTS.md 是受保护文件**：Hermes 文件工具直接拒写（审批超时即拦，不静默通过）。重写它需用户明确批准；批准前先把草稿给用户看。**审批要在工具弹窗上点同意才算**——用户在聊天里说"批了/可以"到不了审批关卡，弹窗超时就静默拦（且超时后立即重试仍被拦，别连点）。流程：先把要加的整段内容列成草稿给用户过目 → 用户同意后再发一次写入补丁 → 用户在弹窗出现时点掉。保护文件的重写这类'把框架标准反哺进项目文档'的活，用户明确要 Hermes 亲自做、不交本地 agent（Codex/反gravity 对 AGENTS 类受保护文档式结构和边界吃不准）。
6. **每条给 agent 的指令（包括框架/文档合并类）末尾都要带自检报告上传通道**：用户会查漏。若本次改动无代码/无部署，仍要落盘报告并 curl 上传 ai-reports。
7. **同一个分支多个 agent（Codex/反gravity/用户 Mac）都在推，push 常被拒 non-fast-forward**：本地 commit 时远端已前进（如另一个 agent 先推了）。别慌别乱 rebase reset——`git fetch origin <branch>` → 看 `git log HEAD..origin/<branch>` 确认自己只差一条 → `git rebase origin/<branch>`（新文件冲突概率低）→ 再 push。改标注/content 的真实编译产物（annotation.bundle.json）与 markdown 源会与另一个 agent 的改动冲突，rebase 后要用 `--output` 重编译一次当前真源再推，别沿用旧 bundle。
