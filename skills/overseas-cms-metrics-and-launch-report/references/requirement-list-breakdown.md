# 需求「功能点拆解」写进在线需求 list（外销 CMS）

用户会把需求整理进一张在线表（也叫需求 list），列固定为：

```
所在端 | 1级菜单 | 2级菜单 | 3级菜单 | 4级功能点 | 5级功能点 | 功能点描述
```

## 粒度：一行一个功能块，不拆到字段

- **不要每个字段占一行**。用户会直接打回："太细了，不要到字段分行"。
- 参照表里已有的行：一个页面通常 3 行左右（筛选条件 / 列表页 / 导出）。字段全部塞进「功能点描述」一格里，用顿号连起来。
- **"不支持"的项不写**。它不是功能点，占行反而引起误会（用户原话："免得误会"）——口头说明或会后对齐即可，尤其像"列头排序不支持"这种。
- 交付形态：聊天里发 **TSV 代码块**（他粘进 WPS 会自动分列），需要时同时给 `.tsv` 文件。纯 TSV 文本他说"不是表格形式"，给文件时要说明"用 WPS 打开就是表格"。

## 菜单层级只能来自真实系统，不能编

一级/二级/三级菜单必须与生产一致，来源两处：

1. `01-全局背景信息/参考资料/CMS知识宝典_V3.0.md` 的「菜单结构总览」——6 个一级模块（触达计划 / 数据报表 / 工具中心 / 组织架构 / 权限中心 / 配置中心）+ 各自子菜单 + pageId
2. 原型 `99-产品原型prototype/src/config/menus.ts`——modules → groups → children，带 path 与 implemented 标志

新功能挂哪个一级菜单**先跟用户确认**。他会拿内销对照（"内销 CMS 是放在用户标签同一个层级下的"），内销取证在 `03-产品设计/私域2.0一期/内销事件标签竞品分析.md`（内销：工具中心 > 企业微信管理 > 标签管理 > 标签库管理 / 自动打标，两个同级）。注意"营销与转化 > 新机营销"是**标签分类**不是菜单，别混。

## 字段级依据来自接口文档，并说明其可信度

`01-全局背景信息/参考资料/接口分析/01-接口文档地图.md` 按接口名列出返回字段（如「管理后台-分页查询好友列表」下有 `storeName` / `employeeId` / `addTime` 等）。

- 关键局限：多数行的证据列写着「**从JSON示例注释提取**」——字段存在可信，**中文含义来自 JSON 注释、可能不准**。例如 `addTime` 标"账号添加时间"，到底是好友首次添加时间还是账号本身的时间，必须再确认。
- 这个区分直接决定工作量：接口里已有的字段 = "接口已返回，仅需前端展示"；找不到的 = 需服务端新增。落笔前先分清，别把已有字段写成"新增"。

## 报表类需求先问清"谁做页面"

报表常常**不是 CMS 自研功能**：页面由数据方内嵌，数据从 **CMS 服务端某张表**取。此时我方工作量在**字段设计与落表**，不在页面。

- **不要因为"要落表"就单独立项**。用户会驳回："取数据，又不改字段值，而且为什么要在功能点里单独立项？"字段本来就在取数链路里，功能点只写"列表页新增 X 字段"。
- **列表字段与筛选项不是一一对应**：加一列不等于加一个筛选。筛选项按业务真用得上的挑；"每个字段都配一个筛选"会被反弹（"好多筛选条件啊"）。导出到 Excel 后业务自己能筛的，系统里不必做。
- 只有**限制导出量**的筛选（时间区间）才必须在系统里做。

## 每个新增字段都要能答口径

至少回答：取值来源（哪个接口/哪张表）、口径定义、更新时机、是否可空。有歧义的标"待确认"并写明找谁，例如：

- **首次添加时间 vs 最新添加时间必须成对**：Meta 会自动删好友再自动加回来，只留一个时间字段会把"删了又加"误判成新好友（重复打扰）或看不出重加。接口只有 `addTime`，其语义待确认；"首次添加时间"通常需服务端在首次入库时写入且**此后不更新**。
- **业务口径未定的指标，不在功能点里替业务签结论**。"新增好友数"到底算首次还是算所有添加动作，是数据方与业务对齐的事——我们只需保证两个字段都在，他们怎么定都算得出来。

## 交互措辞自查：别写出自相矛盾的设计

写完"时间类型下拉（首次/最新）"这类描述后回读一遍：列表里两列同时展示、筛选却只能选一个，业务会问"两个都想筛呢"。**两个独立区间筛选更清楚**，不要为了省版面把两个维度压成一个下拉。用户会直接质疑（"还是或者的关系，不矛盾么"）。
