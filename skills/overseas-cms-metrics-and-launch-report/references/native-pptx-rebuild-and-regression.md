# PPTX 报告：贴图改原生页 + 回归验证

报告里凡是「长期还要改」的页面，一律不用原稿整页抠图贴入。贴图会失真、改不了数、一重排页码引用全断。

## 贴图 vs 原生：判断标准

| 页面类型 | 处理 | 理由 |
|---|---|---|
| 数据表、分国家看数、能力清单、架构图 | 必须原生 | 要改数、要加行、要迭代 |
| 流程图、形态示意（公域五步、预售形态） | 可原生，长期用就别贴 | 改动频率低但一改就得回原稿重导 |
| 封面 | 保留贴图 | 纯视觉，不承载内容 |

用户原话可用作判据：「主要是要长期用，所以原生化」。

## 生成器入库是原生化前提

把生成脚本放进仓库（如 `08-相关资料/参考数据/上线报告/gen1104/`），路径改成相对仓库，不留在 `/root/gen1104` 之类仓库外目录。理由：agent 要在 Mac 上改这份脚本，路径写死在仓库外的机器上它根本跑不起来。

脚本内部纪律：

- 模块清单写成函数开头的数据结构（每层一个元组：层名、模块列表、模块三元组含名称/说明/类型），画图代码只读数据循环生成。加模块＝改数据，不是改绘图代码。
- 页脚、页码统一由 `header()` 一类封装生成，别在每页手写，否则改一页漏一页。
- 换页序、插页之后，正文里所有「见 Pxx」的交叉引用会静默失效。**正文里的页码引用改成按页标题指代**（「见「归因」页」），只有脚注和交叉表可以保留页码。

## 逐页回归验证（验收 agent 改动的唯一可靠口径）

agent 说「只改了三页」不算证据。判据是逐页 slide XML 的 md5 对比：

```bash
# 用基线提交的脚本生成对照稿
cd <repo>/gen1104
git show <base-commit>:"<path>/gen1104/gen_full.py" > _old.py
# 把输出文件名改成 _base.pptx，避免覆盖交付件
sed -i 's|out = str(PARENT / "<交付件>.pptx")|out = str(HERE / "_base.pptx")|' _old.py
python _old.py
```

```python
import zipfile, hashlib
def sl(p):
    z = zipfile.ZipFile(p)
    return {n: hashlib.md5(z.read(n)).hexdigest() for n in z.namelist()
            if n.startswith('ppt/slides/slide') and n.endswith('.xml')}
a, b = sl('_base.pptx'), sl('<交付件>.pptx')
print('差异页:', sorted(k for k in a if a[k] != b.get(k)))
```

期望输出：只有目标页在差异列表里，其余页字节级一致。页数也必须打印出来核对。

**必须自己独立跑一遍**。agent 的自证报告可以参考，但不能作为验收依据——同一脚本、同一基线，两边结果一致才算过。

## 多页批量原生化：一次给全量指令

用户会直接要「给我一个全量的指令」——逐页下指令等于让他在 agent 和助手之间当传话筒，一轮只推进一页。做法：一次把剩余所有页列清（页号 ← 原稿页号），分成几部分写进同一份指令，验收只留一个总 Checkpoint。

下指令前必须做两件事，否则会写出执行不了的红线：

1. **全册 `<p:pic>` 普查，别凭记忆断言哪几页是贴图。** 生成器里 `keep_original()` 的调用点未必和你记住的一致——实测自己断言「只剩封面是图片」，实际另有两页也是，agent 当场报上来，那条红线成了自相矛盾的验收项。普查法：

   ```python
   import zipfile
   z = zipfile.ZipFile('x.pptx')
   for i in range(1, 26):
       c = z.read(f'ppt/slides/slide{i}.xml').decode().count('<p:pic>')
       if c: print(f'P{i}: {c}')
   ```

   把真实清单写进指令，「除封面外不得再有 `<p:pic>`」才立得住。

2. **先渲染原稿对应页看形态，再写形态要求。** 「数据页应该有表格」是推断不是事实——实测原稿那两页一个是柱状图 + 右侧卡片、一个是 2×3 卡片，通篇没有行列结构。指令里写「表格列数与行数必须与原稿一致」，agent 要么违令造一张表、要么停下来问，两条都白费一轮。正确写法是把渲染图上看到的结构描述出来（「柱状图 + 4 张卡 + 底部对比框」「2×3 六卡」），它照着画。

指令里的计数（「规划模块只能是我列的 N 个」）落笔前数一遍。列了 4 个却写 5 个，agent 会按清单做、然后在验收时把这条当作待拍板项报回来。

## 原稿里与当前口径冲突的内容：删，并在交付说明里点明

整页搬运改成原生页时，原稿底部常留着与新口径打架的小字——如「规划预留：策略中心、营销画布后期扩展位」（而策略中心已建成、营销画布已变成层内规划块）、「后台五模块视图（开发视角）」（与五层架构是重复的两种切法）。处置：**删掉，并在交付说明里单列一条写明「删了哪两行、为什么删」**，让用户一句话就能反转。默默保留会让新页自相矛盾，默默删掉他会以为漏搬。

## 逐字 diff 的过滤启发式会误报

核对「与原稿逐字一致」时要剔掉每页 `header()` 自带的章节标签与页脚。**用固定全串过滤**（`02 产品与现有能力`、`外销 CMS 用户运营系统 · 2026.10.23 上线报告 NN / 25`），不要用「以某词开头就丢弃」这类启发式——实测原稿里以「外销」开头的正常正文行被当成页脚剔掉，凭空报出两处 insert，白查一轮。

## 原生化的附带检查

- 改完的页 `ppt/slides/slideNN.xml` 里不应再有 `<p:pic>`（可 grep `<p:pic` 确认），且不应有 `<a:tbl>` 如果这页原本是卡片布局。
- 交付前逐页渲染成 PNG 用视觉核一遍版式：卡片对齐、文字不溢出、卡片不重叠、脚注不压页脚。只跑脚本不看图＝没核。
- 内容与原稿的一致性用字符级 diff 核（去空白后比正文），差异应该只剩 `header()` 自带的章节标记和页脚。

## 中间产物不进版本库

抠图用的 `cut_*.png`、渲染出的 `cover_*.png`、`preview/` 目录都是脚本每次运行重写的构建产物，不进库。

坑：`.gitignore` 只对**未跟踪**文件生效。已经提交过的 PNG 加 `.gitignore` 无效，工作区照样天天脏。必须先移出索引：

```bash
git rm --cached gen1104/*.png   # 只移出索引，本地文件保留
git add gen1104/.gitignore && git commit
```

移出后必须验证脚本不依赖它们：把 PNG 全移到 /tmp（不硬删），连跑两遍生成器，确认能重新生成且两遍产物字节级一致。这一步不能跳，否则移出库就是埋雷。

## 环境坑

- **python-pptx 装不上**：PEP 668 拦住系统级安装，用 `pip install --user --break-system-packages python-pptx`，装在用户目录不动系统包。之后一律用该解释器跑脚本。
- **soffice 转 PDF 静默失败**：受限沙箱下 `--convert-to` 报成功但 PDF 时间戳不更新，容易误判「页面没变」。转换后必须先确认 PDF 时间戳变了再渲染；偶发 `DeploymentException` 时加 `-env:UserInstallation=file:///tmp/lo_prof` 并提权。
- **add_picture 的宽高必须传 `Inches(x)`**，传裸数字会被当成 EMU（约 0），页面贴出来是白页。抠图 PNG 若是特殊 color mode，先 `convert("RGB")` 再贴，否则也可能是白页。
