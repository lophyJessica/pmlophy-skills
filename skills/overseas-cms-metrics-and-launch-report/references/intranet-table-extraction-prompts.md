# 内网在线表抓取指令（Cursor 内置浏览器 → 结构化导出）

公司内网文档（在线表格/知识库）这里进不去，只能让用户公司电脑上的 Cursor 用内置浏览器只读抓。运营数据、需求池、指标表都走这条路。

## 指令骨架

```plaintext
@Browser <完整URL>

Context:
执行位置：公司电脑，该链接已在 Cursor 内置浏览器中打开（已登录内网）。
任务：只读导出这张表，不写文件、不做 git 操作，结果直接贴聊天。
只处理当前工作表（sheetIndex=N，即「<页签名>」表），不抓其他页签。

Request:
第一步：先读表头，不要先读数据
第二步：按实际表头逐行抓全量数据
第三步：不做任何加工

Output format / 红线禁止 / Checkpoint
```

## 七条硬规则

**1. `@Browser <url>` 打头，Context 里补一句"链接已在内置浏览器打开"**——不写这句它会自己开新标签页、还可能撞登录态。

**2. `?sheetIndex=N` 是"第 N 个工作表"，不是"全部"。** 任务写"整表导出"时指的是**这一张表的全部行**，不是整本簿。为"抓全"把参数删掉，会跑去抓别的产品线的表——用户会直接纠回来。

**3. 先让它报同簿页签清单**（几乎零成本），并写进 Checkpoint。这一句经常直接回答"数据只有到 N 月吗"——同簿往往按月留快照（`2026年0512/0601/0701/0801/0901/1015`）。

**4. 先读表头，再按实际表头抓数据——绝不把自己记的列清单当权威。** 按历史记忆写死列名会漏列且无从发现：曾按记忆列了 18 列，实际已是 19 列（多了「是否维护」），而那份记忆本身只写了 13 个列名。
正确做法：让它先抄实际表头（多层合并表头记成「上层-下层」）、**与你给的历史列清单逐条比对并报告增删改名**，确认后再按实际表头逐行抓。

**5. 长文本列要点名**（「主要场景 / 需求价值 / 产品分析 / 进度跟踪」这类），明写"必须完整读取，不得截断、不得概括、不得省略"，否则拿到的是摘要残本。

**6. 规范化写死：** 空单元格写「空」；单元格内换行合并成一行用「 / 」；链接保留完整 URL；记下每行实际行号；不去重、不合并、不排序、不改写。若原表是公式（率类），取单元格**显示值**。

**7. 双层输出。** 完整版（全列 + 长文本）写进项目目录归档；另向聊天贴一份**精简清单**（约 10 列 + 长文本截断到 60 字），全量长文本贴不动也不该灌进上下文。两份分工在 Context 里说清。

## 红线必写两条

- **只读**：不得修改、编辑、提交、评审任何在线数据。
- **禁止任何 git 操作**（`git add/commit/push` 一律不做）；需要"不落盘"时再加"不得生成文件、不写磁盘"。公司侧要减少 git 痕迹，不写这句它会顺手 commit。

## Checkpoint 必问五项

几个页签（同簿清单）／表头实际几列／每页签抓到几行、合计／**与历史列清单相比的增删改名**／文件绝对路径与字节数。

## 落盘后的反向验算（必做）

率类字段和绝对值对一遍：`阅读率 × 发送成功 ≈ 阅读人数`。本轮正是靠这个发现原表错误：某国阅读人数与另一国完全相同，而按它自己的 25.81% × 2345 万反推应是 605 万。
**处置**：原值保留不改（它是事实源快照），在归档文件末尾单列「数据异常说明」；报告引用时只用自洽那一侧（只说阅读率、不引用该国的绝对人数）。

## 常见追问的处理

- 用户问"这个表是不是可以统计到"——先用已有字段算一遍它能支撑哪些结论（渠道效果排序、覆盖 vs 实际使用、未上线原因），能答就不用再抓。
- 补历史时段单独发一条只读历史页签的指令，并要求**逐个判断该页签是「单月值」还是「年初至今累计值」**（看表外的时间范围文字）。单月与累计混在一张趋势图里就是造假。
