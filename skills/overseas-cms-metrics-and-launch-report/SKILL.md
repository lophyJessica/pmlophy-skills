# 外销 CMS 运营指标 与 上线报告

## 触发场景
- "外销/海外 CMS 运营要看哪些指标"、"整理运营指标"
- "做上线报告/上线复盘 PPT"

**改已有 pptx（加页 / 删页 / 改数 / 删页）之前，先跳读本 skill 的「结构级核验」与「删页」两节、以及 `references/pptx-generation-qa.md`。** 这几节里的坑（孤立部件撞名、部件名≠页码、页码假阳性、明细改了合计没改）都是重复踩过的，凭手感重做一遍会原样再错一回。

## 目录页：单维度，一行一句
目录每行 = **序号 + 章节名 + 一句话**，共一个维度。三个反复被退回的写法：
- 右侧再挂一列关键词/标签 → 那就是「两个维度」，连同章节名一共三层信息，退。
- 那一句里用逗号并列两个主题（「A，还要 B」「A 与 B」）→ 看着是一行，实际是两个主题，退。
- 那一句写成章内条目/页面清单（「包含 X、Y、Z 三块」）→ 那是内容清单不是主题句，退。
那一句要说的只有一件事：**这一章讲什么观点**。改稿时只动这一句，不要顺手给目录加维度。

## 先取一手料：运营盘点文档与上线国家清单

写上线报告的「功能使用情况」与「上线国家」两页之前，**先读运营盘点**，不要从代码或配置倒推。一手料的位置：

- 在线：`26年Q1-Q3运营盘点`（vivo 文档）
- 抓取产物：`cms-project/08-相关资料/产品审计/26年Q1-Q3运营盘点/`（原文 md、10 张表的 markdown、37 行国家运营状态 TSV、抓取自检；2 张示例图需人工另存）
- 口径与结论汇总：笔记库 `工作面试/外销运营盘点与上线国家口径-1104.md`

文档已明确：覆盖 13 国，7 国全部未使用（台缅柬港新肯埃），2 国部分未使用（孟加拉、越南）；私域覆盖 3 国（印尼、马来、孟加拉），只用授权绑定、未用下发导购任务。

**己知的坑（我自己在 11-05 踩过一次，引得用户白担心）**：不能让「文档写马来授权 66 / 印尼 39，页面实抓是马来 39 / 印尼 65，两组像是写反了」这种结论上桌。实情是文档表 2 的列序为泰国、马来、印尼、孟加拉…，**马来 88 个号授权 39、印尼 290 个号授权 66**，与页面实抓完全对得上（印尼 65 对 66，差 1 是时点差异）。**列序看错就会把两国数据对调**，进而编出一个不存在的「串位」问题。

真正未闭环的只有一条：**马来好友数**，文档 14,617 vs 页面实抓 12,928，差 1,689（印尼方向相反，文档 46,280 低于实抓 49,405，属正常增长）。且「好友数」至少三个口径并存（文档好友数 / 账号列表账号下好友数合计 / 好友列表关系行数），报告里只能用一个、其余标来源。

**核对顺序固定**：先拿表头原文逐列对齐 → 再回行里 grep 该数 → 最后才说谁对谁错。不要拿 agent 的结构化提取稿当权威（它会串位），也不要凭一次比对就宣布文档有错。

## 铁律 0：先确认业务形态，别套模板
必问三项（口径不同、指标侧重不同）：
1. 定位：官网内容站 / 独立站电商 / 海外经销商内容门户？
2. 覆盖规模：多少国家、多少渠道（公域几个、私域几个）
3. 内容承载：产品页 / 资讯 / 促销 / 技术资料

## 北极星
**有效商机数**（询盘 / 留资 / 合格线索），按 **国家 × 渠道** 拆。
- PV/UV/发文数/曝光 = 过程指标，不能当北极星（虚荣指标）
- 解释给非产品同学：开餐厅只看"今天卖出多少份饭"；减肥只看体重体脂
- **C 端私域不适用"商机数"**：C 端没人用=资产归零，北极星换成「月活跃私域用户数(MAU)」；活动率(MAU÷私域总用户) 作为健康尺，两个一起看（规模+健康），只追 MAU 会被僵尸粉灌水，只看活动率会漏掉盘子太小
- 用户把"带来多少私域用户"当北极星时，必须加硬度：**有效私域客户 = 有真实联系方式 + 至少一次有效互动/询盘**，否则人数涨了生意没涨
- **怎么讲给不懂的人**：不要重复念定义。直接问"只能给老板报一个数证明这件事成了，你报哪个"——他自己说出的那个就是北极星，再说"其余都是围着它转的过程数"。用一次日常类比（开餐厅/减肥）就够，别堆框架

## 维度组织（比指标清单本身更重要）
- 国家数 × 渠道数 = N 个格子（如 14国×6渠道=84）
- **禁止全站平均**：总数上涨可能掩盖某国某渠道在塌
- 日常只看**异常告警/阈值**，按大区（欧洲/北美/东南亚/中东）看，不逐格人工审

## 公域 vs 私域，考核点不同
| | 公域（获客型） | 私域（经营型） |
|---|---|---|
| 主指标 | 曝光、进站UV、线索数、单线索成本 | 留资量、线索合格率、首响时长、复访/复购 |
| 内容侧 | 收录数、核心词排名、单条内容引流 | 落地页转化率、跳失、CTA点击 |
| 抓手 | 关键词/选题/落地页 | 内容分层/客户旅程/催单节奏 |

## 五组必盯指标
1. **覆盖**：每国内容就绪度、SKU内容覆盖率（已上线完整内容÷应上线）、语种全字段完整度
2. **触达（公域）**：各渠道 曝光→进站→留资 链路转化、Top/Bottom内容、SEO（收录/自然流量占比/死链）
3. **承接（私域）**：留资→合格线索质量率、询盘首响时长（跨时区最易崩）、复访/复购
4. **质量合规（外销最易出事）**：合规命中数（各国广告法/认证/禁售逐国不同）、与ERP数据一致性（价格/币种/单位/规格）、机翻未校量
5. **健康效率**：内容上架时长、待审积压、发布成功率、上游同步成功率与字段冲突数

## 埋点前提（不解决则全部无效）
一条询盘必须可追溯：**渠道 ← 国家站 ← 内容**（UTM/来源字段/专属落地页）。归因不通=多渠道数据一锅粥，无法优化。

## 收口：只盯 8 个 KPI
有效商机数(国家×渠道)、各国内容就绪度、渠道链路转化、单线索成本(分渠道)、私域首响+线索合格率、合规/一致性问题数、本地化完成度、站内搜索无结果率

## 活动率口径铁律（私域必吵的一环）
分子="有效行为"，分母=私域用户总数（去重、有真实联系方式），周期定死（日/周/月，主体看月）。三条最容易注水，必须堵：
1. **送达≠活动**：推送成功、发出去一条消息都不算活动，那是我们发了、他没动
2. **分母用"累计注册"会虚高**，要用去重有效用户
3. **必须拆**：新增活动率 vs 存量活动率（拉新质量 vs 养客质量）、按私域渠道拆（邮件/WhatsApp/社群活动定义不同，不能混算）、按国家拆

配一排上下家：留存（次日/7/30）→ 触达（到达/打开/点击）→ 转化（私域→下单/客单价/复购）→ 风险（沉默用户占比 90天无活动=漏水口）。

**「留存用户数」≠「好友数」，做报表/汇报前先把口径钉死**：同一份业务材料里，需求原文写"好友 2 万"、季报写"留存用户 5.96 万"，看着差一倍——它们可能是同一件事的不同快照（需求提出时的旧值 vs 后来的新值），也可能是两套统计口径。WhatsApp 的 Meta 机制是黑盒，好友会被系统反复删掉再加回来，短期看数会 2 万→1.6 万→2 万+ 上下跳。**用到这类数必须问清三件：哪个口径、统计截止时点、是否含删除重加的重复计数**；说不清就只当"时点值"报，不当"净增"用，也不写进需要纵向对比的表格。

## 导购工作台（导购-好友）私域指标
- **分母必须是「(导购, 好友) 关系对」**，不是好友去重人数、也不是导购人数——否则同一好友被多人添加会重复算，指标飘
- 三档口径，别混：**触达率**（周期内有任何消息，群发广告也算，会灌水）→ **互动率**（好友有回复，双向才算）：**深度互动**（≥3 轮 或 连续 N 天）
- 必配：响应时效（好友发言→导购回复中位时长，跨时区最易崩）、沉默关系占比、**活跃导购占比**、头部/腰部/尾部产出分布（警惕全靠两三个头部撑）
- 北极星建议：**月度有效互动的(导购,好友) 关系对数**（规模） + **互动率**（健康），两个一起看
- 必堵的坑：群发算互动 → 互动率虚高；只追互动率不看转化 → 聊得热闹不下单

## 多任务并行：**顺序由用户定，单线程推进**

用户手里同时压着"事件标签 / 私域 X.0 / 上线 PPT"几条线时，**不要替他重排顺序、也不要趁排队空档顺手推进另一条**。他会明确说"这个先不要动，按顺序走，一个完结后再执行另一个任务"——照做，其余全部冻结。

允许做的只有两件：①按他给的顺序推进当前这一条；②他问"接下来是什么节奏"时，把各条线的当前状态和目标列清，顺序仍由他拍。

**派并行子 Agent 前，先盘点用户在这条线上是不是已经有自己的稿子。** 为"省时间"一次 fan-out 几份交付物，若其中一条主题用户本人已经写过方案（仓库里就有 v1/v2、还标着"已拍板"），子 Agent 的产出必然与他的口径冲突、直接作废——省下的时间又赔回去。先 `find`/`grep` 一遍该主题下的既有文档，命中就改为"以他的稿为权威，我只补缺口"，并把缺口列给他确认，再决定要不要派活。

事件标签/标签体系这类既需要**跨系统事实**（对方系统有没有这个能力、字段叫什么、找谁确认）又已被用户自己推进过的主题，尤其不要靠子 Agent 凭空设三期路线——产物看着完整、实则与已拍板范围不符，是最典型的白干。

依赖关系只作为**口头建议**在他征求意见时给出（标签体系定不死，报表的活动率/互动率就算不出来；上线 PPT 的口径要等前面几条定稿才圆）——不要因为存在依赖就自行串线开工。

上线报告 PPT 的范围口径不因排序而变：**不是某个单模块（如某次预售）的专题**，而是全系统 0→1 至当前版本的全景；没拿到发版史时可先做骨架，但不把某个模块的上线当成整份报告。

## 找"剩余 N 条需求"：去需求池的拆分说明，不在 PRD 套件里

用户会问"XX 2.0 剩下的那 N 条需求你查到了吗"——**答案通常不在已交付的 PRD 套件里**（那里只有已经做掉的），而在 `02-需求调研/需求池/` 里那条**母需求文档的拆分说明**：

1. 先按关键词捞母需求文件。`预研未排期/` 与 `无版本/` 下常有同一件事的新旧两份，取最新那份（旧大包往往更全但编号更早）。
2. 读文末的「拆分说明 / 拆分逻辑」——常会写"某几个模块**未在在线需求池单独成行、本次不建文件**"。把这几个模块逐个列出来，就是剩余项；**数一遍和用户说的 N 对上再回话**。
3. 再对照一期 PRD 套件里的功能清单/版本记录，确认"一期做掉的是哪几条"（如 P0 三项），避免把已完成的算进剩余。
4. 每条剩余的**成文程度要分清**：有的在旧大包里已有描述，有的只有名字。**只有名字的，绝不凭名字编需求分析**——原始需求在内部需求系统（VAPD 之类）里，外网进不去；直接告诉用户"需要这几条的原始描述（截图/导出）"，并列出"哪几条已有材料、哪几条缺"，让他一次性补齐。

## 项目资料获取：私有仓库 release → 只读拉取

**动手宣称"项目里没有 X"之前，先把同级目录全部 ls 一遍。** 一个业务系统常拆成多个独立仓库（管理后台 `cms-project` + 导购端 `guide-app` 各自一套 00-08+99 结构，各自有原型源码），只搜其中一个就下结论"没有导购端资料"，会漏掉整套项目、并当场被用户纠正（"不是有 guide-app 项目吗"）。查资料先 `ls -d /root/repos/*/ /root/repos/*/*/`，再按关键词 find。

**其次查分支**：同一仓库的旧分支上可能有整块功能（实测预售前端全在 `origin/1.8.0`，主分支一个文件都没有）。只扫当前 checkout 分支就断言"前端还没做"，会得出完全相反的结论。做法：`git branch -r` 列出所有远程分支，再 `git ls-tree` / `git show <branch>:<path>` 只读比对页面目录差异。

**最后查 iframe / 外部系统嵌入**——这是最容易漏的一类：功能页面可能根本不在本仓库，本仓库只有一个通用壳。判据是搜 `iframe`、`pageId`、`URL_MAP`、`postMessage` 这类词，命中一个通用容器页（如 `views/shopIframe/index.vue` 按 `pageId` 查映射拼外部地址）就说明：**菜单、登录态、语言切换在本系统，业务表格和表单全在对方系统**。后果很实际——本系统后端也就不会有对应接口，去后端仓库翻 Controller 永远是空的。实测 CMS 后台的预售、商品、赠品、评论四个模块全走这条路，页面在商城后台 `shopadmin-*/spa/*`，原型要复刻得去那个系统的界面上取。

三类全查完才能下结论：主分支→其他分支→外部系统嵌入。顺序反了会在"没找到→换仓库→还是没找到"里空转好几轮。

公司项目资料常在公司侧 VPS，不在这里。链路：**公司侧打包 → 私有 GitHub release（tag 带时间戳）→ 这里只读拉取分析**，不回写公司侧。
- `git clone`（SSH key）只拿**仓库树**；release 的 asset（zip/tar.gz）**必须用 GitHub Token 调 `/repos/{o}/{r}/releases/assets/{id}` + `Accept: application/octet-stream`** 才下得动，私有仓库用 SSH 拿不到 asset
- 无 gh/无 token 时先 `git ls-remote` 确认可达，再向用户要**只读、单仓库、短期** fine-grained token；**token 一旦出现在聊天里，下载完立刻提醒撤销重建**，本地副本用完删除
- 包解开后先做**文件级盘点**（顶层目录/模块/文档数/关键文件清单）再承诺分析，不要凭印象说"我看了"
- **文件到了先验文件头再解析**：`file <f>` + `head -c 16 <f> | xxd`。若显示 `%TSD-Header-###%`（`file` 报 `data`），是公司 DLP 加密壳——PDF 库报 `no objects found`、pptx 报 `File is not a zip file`，**任何解析器都读不了**，因为文件不是坏、是加密。此时不要反复换解析库。**首选解法：让他在公司电脑上解密后重新提交/推送**（解密后文件头变回 `%PDF-` 或 `PK`，直接可读；实测 xlsx/pdf/pptx 解密后全部能正常解析）；截图、口述、贴文字是次选。提醒他：加密与存储位置无关，推到 GitHub 仍是加密壳，解密必须在客户端做。
- **用户在聊天里发文件时，先查缓存再说话**：收到的文件落在 `/root/.hermes/cache/documents/`。**不要凭印象断言"通道收不到文件"**——文本类附件（.md 等）能正常到达，实测 30KB 的整库导出 md 就在缓存里。**先查，没有再说没有**；用户说"发你了"而你没看到内容时同理，先找文件，不要先归因到通道——文件已经收到却去解释通道，是最招人烦的跑题（被当场纠正过）。
- 只有**部分大体积二进制**（Excel/PPT）可能退化成 `type=post` 富文本卡片，正文取不出，日志里只落一行 `text='[Rich text message]'`（adapter 的 `FALLBACK_POST_TEXT` 占位符）。**看到这个占位符**才说明该格式真走不了聊天，别再猜"是不是加密"或让用户重发；此时改走 **GitHub 私有仓库 push**（助手能 SSH clone）或云文档链接。

## 上线报告 PPT：先定范围与体例（别急着套骨架）

**铁律 0：动手前先问清两件事，否则整份白写**
1. **范围**：是**全系统**（0→1 到当前版本，含全部迭代史），还是**单个模块/单次上线**？用户说"上线报告"时很可能指**全系统全景**——不要默认成你手头正好在看的那个模块
2. **迭代史口径**："迭代到 N 版"是**发版次数**还是**版本号**（v1.9.0 / v5.1.0 这类）？口径不同，时间轴写法完全不同

**迭代史的材料来源（最常见的缺口）**：产品设计包里**没有发版史**——只有模块级 PRD、字段清单、零散几份历史版本文档。真正的迭代史在**发版记录 / 上线审批单 / 需求池 / 历史上的上线报告**里。
- 缺这块时：先做"系统全景 + 0→1 阶段划分 + 指标体系 + 架构机制"，**时间轴留空并明确告诉用户缺什么**，不要编版本内容
- 让用户提供历史上线报告，比让他导出工单列表更省事

**体例优先（照它写，不自创格式）**：拿到历史报告后三步走——①**先摸体例**（章节结构、颗粒度、口径、措辞风格）②从各版里抽「版本号 + 日期 + 交付内容」拼时间轴 ③按同一体例产出，缺口处标注问用户。要文件时**最早一份 + 最近一份 + 中间几份**就够摸清演变。

**拿到一份「对味的同类报告」要照着改时（兄弟产品/兄弟部门的同主题报告）：先做结构对照，再给三档方案，只问一次。**

1. **结构对照**：用 python-pptx 把两边逐页标题打印出来（只取每页首段文本），列成两栏对照，点出「我们缺哪几块 / 我们多哪几块」。别用肉眼翻 PDF 估。
2. **三档改造方案**，连同工时与风险一起报，让他选：
   - **轻改**：保留现有骨架，只补对方有而我们缺的几页（改动小、风险低，但对方的产品观借不到）
   - **中改**：前段按对方重排（业务结果 → 逐国归因 → 问题与责任人 → 短期计划），后段保留我们的能力与架构，把重叠的几页压并
   - **全按对方体例重做**：等于推翻已定稿内容，只在他明确说「重来」时选
3. **只问一次**。他选完就往下做，不要再回来确认方向；方案里要显式标出「哪些页不动」——他点名不动的页（如「产品架构页不用改」）要单列一行，生成脚本里也不许碰它。
4. **复用兄弟材料的某几页**（如某份历史 PDF 的第 6～9 页）：先用 `pymupdf` 把那几页原文 `get_text()` 提出来，按原文事实改写表述，不要凭印象转述；提完之后在方案里写清「用了哪几页、用在哪几页」。
5. **「和 X 报告格式保持一致」是三种不同的事，开工前一次问清**：①**版式**（字体、字号层级、配色、内页排法）；②**章节结构与叙事打法**（结果先行 / 附件产品设计）；③**只对齐模板元素**（封面、页眉页脚、页码、分隔页）。他说「格式」「那种结构」时往往指②，而回答「版式怎么换」会被当场打回。给三档让他点一个，别追问第二轮。
6. **改造初期可以用「前段重做版式、后段抠图整页贴」过渡，但交付版必须把贴图页原生化。** 用户会直接点出来：「我们不应该在 1104 版本上做贴图，会失真」。贴图是技术债：改不了一个数、加不了一个模块、缩小后小字投影发糊、改一处得回原稿改再重贴——实测两次反噬（架构图要加延展模块只能在图外另起一排；数据要更新只能整页换掉）。
   - **数据页、表格页、能力明细页一律原生画**（`table()` / `rect()` / `text()`），它们会被反复改数。
   - **核心图（产品架构）也要原生重画**：它要承载新增/规划模块，贴图做不到。工作量大，单独排一轮。
   - **贴图只留给真正不改的示意图**（流程五步、系统形态、封面），并在交付说明里写明哪几页是贴图、为什么。
   - **生成器必须入库**：`base.py` + `gen_*.py` 连同原稿 PDF 一起提交到仓库，路径改成基于 `__file__` 的仓库相对路径（缺 PDF 时脚本内自动 `soffice --convert-to pdf`）。否则脚本只在助手本机，同事与外包 agent 都改不了页，所有修改卡在一个人手上。
   - 早期抠图阶段的坑仍适用：
   - **clip 左右各多放 ~8pt、上下多放 ~5pt**，卡太紧会把最右一列模块和底部注释行裁掉（实测第 13 页架构图右缘被切）。
   - **`add_picture` 的宽高必须传 `Inches(...)`，传裸数字会被当成 EMU**：`width=13.333, height=7.5` 写进 XML 变成 `cx="13" cy="7"`（近似为 0），渲染出来是一张纯白页，而 `shape.width` 读回仍是 13×7——只看形状列表根本发现不了。自检办法：渲染首页取像素主色（纯白即失败），或解包看 `<a:ext cx=...>` 是否等于 英寸×914400。贴完封面/整页图必跑一次，否则交到用户手里才发现封面是白页。
   - **页面里承诺过的视觉元素必须真的落到版面上**：文案写了「红标＝外部依赖 / 蓝标＝我们能推进 / 橙标＝两边都要动」，那这些格子就得上色（`table()` 加 `cell_color` / `cell_bold` 参数，按 `(row, col)` 覆盖 `run.font.color.rgb`）；同理图例、状态圆点、已建/在建/规划三色。**没有渲染器就把那句说明删掉**——只写说明不落色，用户一眼就会问「哪里有红标」。

**批量原生化时一次给全量指令，不要一页一轮。** 用户会直接要「给我一个全量的指令」——逐页派活等于让他在 agent 和助手之间当传话筒。一次把剩余所有页列清（页号 ← 原稿页号），按部分写进同一份指令，验收只留一个总 Checkpoint。写指令前先做两件事：① 跑全册 `<p:pic>` 普查，把真实的贴图页清单列进去（凭记忆断言「只剩封面是图片」会写出一条自相矛盾的红线）；② 先渲染原稿对应页看清形态再写形态要求（「数据页应该有表格」是推断，实际可能是柱状图 + 卡片，据此下的「表格行列数与原稿一致」根本执行不了）。指令里的计数（「只能是我列的 N 个」）落笔前数一遍。细节见 `references/native-pptx-rebuild-and-regression.md`。

### 多版本演进链上的回归检查（拿旧版点评来审新版时）

上级会把**旧版的点评**甩过来，让你自查新版有没有同样的问题，而中间通常还有一版「按点评整改过」的稿子。此时判断标准不是**「当前版有没有重犯旧版的毛病」**，而是**「有没有把中间版已经整改好的地方改回去」**——直接拿旧版点评逐条对新版，会把中间版早已解决的问题误报成遗漏，白改一遍还改错方向。

做法：

1. **先把版本链和每版的整改记录列清**，用 python-pptx 逐页打「标题 + 正文首段」对位，按点评一条条落到具体页，别凭印象说「新版没做」。被点评过的那几条，在中间版里通常已经换了形态（内销对比表、数据页的「说明了什么·下一步怎么用」总结块）——这些当前版若是整页继承原稿，就没退化。
2. **当前版由「重写页 + 原稿抠图整页贴」混合构成时，风险全在重写页**。抠图页是像素复制，必然继承中间版内容，可豁免核对；逐页查一遍重写的结构页即可。
3. **重写结构页要照抄中间版该页的字段要素与句式，不要重新设计。** 实测重写最容易退化成三种形态：一维目录被加上第二个维度（右侧关键词标签，正是被批过的「一句话下面两个维度」）；「业务要…→产品给了…」的对照句被压成两列干表、还丢了页底收口句；四块能力的「是什么 / 给谁用 / 现在到哪了」三要素被删剩一列。
4. **结论分三栏报**，不要笼统说「N 条未解决」——那既误导对方，也暴露没做对位核实：
   - **已不是问题**：旧版点评在中间版就整改过、当前版继承住了，逐条点明现在落在哪一页的哪个形态。
   - **刚修掉**：这轮自查新发现、已当场改完的（典型：重排导致的页码交叉引用失效、承诺了颜色却没上色）。
   - **仍存在、待用户拍**：附一句现状 + 一个建议改法，让他二选一，别替他决定。
   若前一轮自己报过某条「未解决」后来发现报错了，**在这一栏开头明说撤回**，并给正确的出处；含糊过去会让整份审计失信。
5. **审计顺带要做机械错扫描**，这类不需要业务判断、但投影时最抓眼，且往往正是重排/重写引入的：正文页码交叉引用、目录与正文段落是否一致、承诺的颜色/图例是否落版。**没有数据支撑的那一类缺口（比如要求写「哪些国家近期没有计划」而原稿里根本没这个信息）如实报缺，不要为了凑齐点评条目去编。**
6. **旧点评与中间版拍板相矛盾时，列出来让他拍，不自行回退。** 实测：老板批过「讲能力就直接放能力，不要放数据」，而中间版拍板要求能力页写「是什么 / 给谁用 / 现在到哪了」，第三列天然带数字。提建议（把数字换成状态词）可以，**但动手前要问他一句**——他很可能回「按之前口径，不做新数据更新」。这类冲突不在我能单方面裁决的范围：把「哪条点评 / 哪一版拍板 / 建议怎么折中」三行并排列给他，比自作主张安全。

**排版落地的坑（生成的页必查，别等用户发现）**：
- **交付前必须逐页渲图用视觉核，不许抽样。** 用户会直接下硬话「注意排版，检查一遍，不要出现挤压、重叠这种，逐一对比过来，你阅读过再给我」。做法成链：`soffice --headless --convert-to pdf` → `pymupdf` 按 100~110 dpi 每页出一张 PNG → 每一张送视觉逐个问「有无重叠/挤压/越界/压页脚」。**新画的页 100% 要看；从原稿抠图整页贴的页可豁免**（像素复制，版式不可能变），但要在交付说明里讲清哪些页豁免、为什么。程序扫 `shapes` 越界只能抓「超出画布」，抓不到「两个框互相压」和「行高被撑开压到页脚」——视觉这一遍不能省。
- **章节标签（kicker）文本框按中文标签长度给宽，别按英文习惯给 1.2"。** 「02 我们面对的是什么」这种 10 字标签在 1.2" 框里会被挤成两行、上半截压到标题线上。给到 4.2" 一行放得下；标签是短文本，框宽了不影响排版。
- **表格行高被长文本撑开时，改列宽比例，不要硬压行高。** python-pptx 设的 `row_h` 只是下限，任一单元格换行就会把该行撑高——结果是行高不匀、总高溢出压页脚。正确修法是**给长文本那列更多宽度让它单行**（如 `col_w=[1, 1.28]`），配合字号略降；只调 `row_h` 会在 LibreOffice 与 PowerPoint 里表现不一致。
- **多栏卡片禁手动累加 y 坐标**：`yy += 固定值` 遇长条目就叠字。改成**一个文本框装多段落**（`paragraphs` + `space_after`），自动换行不会压。
- **表格行高先算再画**：`起点 y + 表头高 + 行数 × 行高` 必须 ≤ 页脚上沿（7.5" 页约 6.95"），超了末行会压页脚。稠密表（6 行以上）行高降到 0.70"、字号 9.5pt。
- **重排页序后，页码与章节标签必须用脚本重挂，不能手改。** 生成器里页序＝代码块顺序，把块搬完后手改 `page=` 必错位。做法：正则扫全文件按出现顺序把 `page=` / `newpage=` 统一重编为 2..N，再按页码区间映射章节标签（如 3–10→「01 结果与归因」；11–22→「02 产品与现有能力」；23–24→「03 …」；25→「04 未来三年」）。改完用 python-pptx 逐页打「章节标签 + 标题」核一遍——章节标签串了页是最容易被看出来的错。
- **正文里的交叉引用也会一起失效，重排后必须扫。** 页面正文常写着「口径见 P23 累计期间看数」「见 P13」这类指向，重排后 P23 可能早已变成别的页（实测累计页从 23 挪到 7 后，第 3 页底部还写着「见 P23」）。扫法：逐页取文本（含表格单元格）正则 `P\s?(\d{1,2})`，把命中页码解析成对应的实际页标题，人工核一遍是否指对；改完再扫一次确认零残留。
- **越界自检写成脚本**：遍历 `shapes` 算 `left+width`、`top+height` 对页尺寸（13.334 × 7.52）比，报出越界形状数，目标 0；再按上面的逐页视觉核走一遍。
- **交付说明要报「查了什么、修了什么」，不是「已检查」**。逐页看时发现的每处问题写成一行「第 N 页 + 问题 + 怎么改的」，用户才认这份检查真做过；笼统一句「排版已检查」等于没查。

**没有量化目标时，达成页改成定性对照，不编数字。** 上线报告通常拿不到国家维度的目标值——此时把「目标 vs 达成」那页做成**左右两列：左＝业务预期（需求方口径，逐条），右＝本次实际交付（逐条一一对应）**，底部一句收口「预期到结果的转化卡在落地条件上，不在系统能力上」，并在讲法备注里约定口径：被问目标就答「本次没有下发国家维度量化目标，只有业务预期」。引用到页上的数只能用报告后页已有的数（部署国数、授权号数、好友数），不新造。

## 上线报告被绑 OKR 时怎么办（两层写，别对抗）

公司把上线报告和 OKR 挂钩时，用户会不爽（"上线报告应该是说明产品的矩阵和能力，不知道为什么要跟 OKR 做绑定来解读"）。**他是对的，但别顺着抱怨走**——这份报告实际服务于两拨人、两套语言：

| 读者 | 要什么 | 该放什么 |
|:--|:--|:--|
| 听产品的 | 这套东西**有什么、能干什么** | 产品矩阵与能力：模块全景、关键能力、迭代史、成效 |
| 管人的 | 人力投进去**换回了什么** | 一条 OKR 对齐章节：这三件事各支撑哪个 O、达成情况 |

**写法**：主体（大头）照"产品矩阵与能力"展开；OKR 收成一章（小头），一句话挂一个 O，**不硬凑、不为了对齐 O 去夸大未做成的事**。这样两边都不打架，也不用为它耗神。

**前置动作**：先问用户「这三件事分别挂在哪条 OKR 上」——OKR 原文往往在绩效系统里，产品文档里没有；没拿到就不自己编 O 的名字。

**要数直接要季度 OKR 表**（Excel，每季度一份，通常在项目仓库的 `docs/OKR总览/` 下）：里面 O/KR 权重、进度百分比、信心指数、任务负责人、"完成情况/检查分析/改善/计划"四栏都齐。季度 O 进度和 KR 进度可以直接填进报告（这是硬数据，能放心讲）；**年度 KR 的指标当前值往往不在这张表里**，仍要单独找数据方确认口径。读表时注意：同一 O 的多条 KR 会跨行展开，用 openpyxl 按行取值比按单元格定位稳。

## 审一份已有上线报告初稿：先给病灶，别在烂稿上打补丁

用户说"整理的上线报告我看了不满意"时，**别只问"哪里不满意"**（他往往说不准），先按这张表自检初稿，把病灶点出来再给改法：

| 病灶 | 症状 | 改法 |
|:--|:--|:--|
| 主线错位 | 按 Q1/Q2/Q3 串，同一模块在多个季度各讲一次，读者拼不出完整能力 | 按模块把能力讲完整，时间线降为背景 |
| 矩阵缺席 | 能力全景排在末尾，还标着"待重画" | 前置到第 2-3 页，一页看懂 |
| OKR 开头 | 每章先报 O 的进度百分比，读起来像 KPI 复盘 | OKR 收成一页附录 |
| 占位符满页 | "待补"散落各页、KR 对照表大半为空 | 汇报版清零：能查的查、查不到的改口径或删行 |
| 写作者痕迹 | 出处标注（【PDF】L204-223、【Q1】O17）留在正文 | 汇报版全删，出处只留底稿 |
| 只有动作 | 讲了做了什么，没讲沉淀了什么 | 补"资产"页：国家/渠道/关系对/标签/组织 |

改完的骨架（产品视角）：一页纸结论 → 定位与痛点 → 产品矩阵全景 → 能力逐个讲（是什么/解决什么/关键数据/现状）→ 规模化复制 → 数据成效 → 沉淀资产 → 问题与不足（坦诚反而加分）→ 下一步 → 附 OKR 对照。

**动手前先问两件事**：①这份初稿是谁做的（自己/别的 AI/前手）——决定"在它上面改"还是"重新起"；②汇报对象与时长——决定总页数与详略。不问就写，写完必返工。

## 上级给了修改意见：按「五类病灶」改造，不要逐条打补丁

领导/上级看完材料给的意见常是这五条（原话：内容都没错、都是对的，但整个材料不够振奋人心，也体现不了未来 3/5 年的中长期视角）。**这五条指向同一个病根：材料是"我们做了什么"的盘点，不是"这平台值多少钱"的叙事。** 逐条对应改造：

| 意见 | 改造动作 |
|:--|:--|
| 全是文字，读起来成本太高 | ①章节标题换成有观点的陈述句；②要点类页改矩阵/对照表；③「怎么跑」类页改**编号流程图**，不要五段文字；④**问题/风险类页改问题卡矩阵**（见下「全是文字怎么改」） |
| 没想象空间、没讲生态玩法、都是能力堆叠 | **新增一页「平台生态：谁在上面、怎么长出来」**：上游（数据方 / MDM / 活动平台 / 外部服务商）、中间平台、下游（导购端 / 商城 / 服务）、角色分层（总部 / 国家运营 / 代理 / 门店 / 导购 / 消费者）。核心论点一句话：**每加一个国家不用重做、每接一个渠道只配一条** |
| 数据要精炼、要更新 | **先找讲同一件事的重复页去重**（典型：对比页与累计页都在说「渠道之间差 20 倍」——只留在最合适的一页，其余改成单一结论），再把散在多页的数字抽成**一页「数字看板」**（规模 / 渠道效率 / 覆盖 / 资产各一到两个数），细节页放后面；同时把口径刷新到最新时点。**「精炼」去掉的是重复，不是页数——页数可以不变** |
| 分章节后标题要体现主题、每章讲透 | 章节标题从流程词（为什么做 / 产品是什么 / 做了什么 / 怎么用 / 效果如何）换成**带判断的句子**（"海外缺一个用户运营底座，我们把它建起来了""不是六个功能，是一个平台：谁在上面、怎么长"） |
| 不够振奋人心、缺 3/5 年中长期视角 | **新增一页「未来三年：从工具到平台到生态」**：今年工具化（跑通触达与预售）→ 明年平台化（数据与策略沉淀、第三方服务商接入）→ 后几年生态化（代理与第三方基于平台自建玩法） |

**动手顺序**：先出**「新目录 + 新增的那两页」样板**给定方向，认可了再全量改——直接重排几十页，方向不对就是全白干。但**只问一次**：用户回「自由发挥，你定」之后就别再回来确认方向（他常这么说——产品口径归他、执行归你），直接改完交付。反复问"要不要先出样板"会被当成磨蹭。

**改完的交付说明必须自带证据**：老页改动数（逐页文本 MD5 比对，目标「0 处」）+ 页脚逐个校验 + 新页渲染成图逐张看过。用户嘴上说怕脚本改错，能安抚他的只有这种可核验的数字，不是「我已经检查过了」。

**改造做到一半被问进度，逐条如实报，绝不笼统回「都做了」**。五条是一批下发、分批落地的，上级迟早逐条对账。正确回法是把五条摊开，每条标明「已处理 / 没动 / 做了一半」各附一句现状——用户问「这几个点都做了对应处理了吗」时，答"四条里做完两条、两条没动"远比含糊过去安全，他也才知道还要不要往下推。同时**主动列出「还欠哪几条」**，别等他一条条问出来。

**分批交付时两轮产物分清、脚本分开**：第一轮是「加页」（新增生态坐标 / AIPL / 未来三年这类），第二轮是「改已有页」（长文字图形化 / 数据精炼 / 目录重做、章节标题）。脚本分开写（`add_xxx_pages.py` → `polish_pages.py`），别混成一个——第一轮脚本是「从 v1 生成 v2」，第二轮再跑会覆盖 v2 加过的页。两轮的验证目标也不同：第一轮证「老页一字未动」，第二轮证「改动页恰好等于计划改的那几页」。具体做法见 `references/pptx-generation-qa.md` 第 15 节。

**向上级要参考物**：他夸"某某画的图有水平"时，把那张原图要过来当标杆（聊天里的缩略图太糊，看不出细节，别凭缩略图揣测样式）。

**上级指定"用我之前那种 X 图，不要改动"时——去找原图复用，不要自绘。** 这类话通常指公司自己战略/规划材料里的现成图（"房子图"＝屋顶＋柱子＋主体＋地基那种能力架构；"线框图"＝泳道式业务流程），**不是让你照风格重画一张**。重画就等于改动，评审必被打回。三步：

1. **先定是哪张**。同一主题会有好几张候选（年度规划 PPT 的分层架构页、上一份上线报告的产品架构页/产品定义页），**同一份材料里还会并排放着多个版本**（一版是"图 + 上方说明文字"、目标列更全；另一版是"纯图"、少了最右那一列）。一次性都渲染出来比对再回话，别一头扎进最像的那张；**取信息更全的那版**，并在交付说明里主动写明"我用的是哪版、为什么换版"，给他一次否决的机会。用缩略图总览快速定位，见 `references/pptx-generation-qa.md` 第 16 节。
2. **确认原图讲的是不是同一个产品**。相邻产品的同名图不能直接搬（官网商城的"房子图"≠ CMS 的房子图；触达平台的架构页又是第三张）。候选列给用户让他点一个——"用哪张"的决定权在产品经理，猜错整页白做。
3. **原样复用**：把该页按 150–170 dpi 渲染、裁内容区做 PNG 直接放进页里（保留原配色与层级），标题/副标题套报告的统一样式。脱敏版的防伪底纹会一起带过来，先说明。

**原图要单独占一页时（原有架构页保留不动，再新增一页放领导原图）**：

- **位置按叙事层级定，不按页序方便定**：顶层依据类（支撑策略、业务蓝图）放在「业务规划」页之后、「产品回应」之前；页面级架构图则贴在已有的产品架构页附近。放完告诉他插在第几页后、后续页如何顺移，给他一次否决的机会。
- **整页插图按可用高度定宽，不按宽度铺满**：`h = 脚注上沿 - 分隔线下沿`（实测 1.05"→6.90" 得 5.85"），`w = h * 16/9`，水平居中 `left = (13.333 - w) / 2`。按宽度铺满 12.5" 会把高度顶出页脚区。
- **版式从相邻页搬，不手搓**：标题文本框位置、字号字色字体（从相邻页对应 `run.font` 读出来复用）、左上斜角装饰块、标题下分隔线，全部沿用同一套。装饰形状用 `new_slide.shapes._spTree.append(copy.deepcopy(shape._element))` 复制过来。
- **插页后页码有两类改动，只做一类就漏**：插入点**之后**的页，页码数字 +1 且总数 +1；插入点**之前**的页只有总数变、数字不动（实测第一遍只改了后段，前 5 页的「N / 28」全留着）。交叉引用同理只给 `n >= 插入位置` 的 `Pnn` +1。改完全文扫一遍旧总数确认零残留。
- **原图分辨率要交代清楚**：用户从文档/PPT 截来的图常只有 800–1000 px 宽，铺到 10 英寸约 77–100 dpi，投影看小字会糊。先如实告诉他这个限制、问有没有原图；没有就用并说明「讲解时配合口头说明」。别默默塞进去让他到会上才发现。

**"多加一些系统截图"先摸项目仓库，别让他重新截。** 验收截图、审计截图、竞品截图通常已经成批躺在项目里（按目录统计张数与取材路径见 `references/pptx-generation-qa.md` 第 16.2 节）。**挑图必须先过一遍「有没有数据」**——空态截图（「查询无数据」、只有筛选区没有表格行）和带人工标注框的走查截图都不上台；一次把所有候选拼成缩略图总览交给视觉工具逐张判「有数据 / 无数据」，比一张张看快得多（筛选问法与并排版式见同一文档 §16.4、§11.3）。

### 「全是文字」怎么改：三类页三种形态

| 页的类型 | 改成的形态 |
|:--|:--|
| 章节标题 / 目录 | 章节名 + **一句话**（那句话是观点，不是章节内的页目录，也不加关键词标签——见下「目录页重做」） |
| 问题 / 风险 / 现状盘点 | **问题卡矩阵**：每张卡 = 分类 + **责任归属彩色标签** + 一句结论 + 原因 + 下一步 |
| 计划 / 排期 | 主线卡（3 张横排，深色标题条）+ 底线卡（2 张并排，左侧黄色色条），底部一句评价标准收口 |

**目录页重做**：每章一行，结构只许 `序号 + 章节名 + 一句话`。那句写的是**这一章的观点**，不是它包含哪几页——把章节内的页名罗列进去（「归因、证据、问题与短期推进计划」）就是把目录写成了内容清单，正是被批过的「一句话讲透的 AI 话」。**不许再加第四列关键词标签**：一个大标题下面挂两个维度（名称 + 说明 + 标签），用户会直接说「你这里有两个维度的话，不太对」。四条说明必须各自单行不折行，超了就砍字，不要缩字号。**卡片的视觉权重必须一致，不要高亮其中一张**——高亮那张会被读成"当前章节"或"最重要章节"，而目录本身没有这个语义。

目录与后文必须对得上：章节名改了、页序重排了，回来核一遍「目录写的四段 = 正文实际四段」，并查正文里有没有还在引用旧页码或旧章节名的句子。

**说明句不许出现逗号并列的两个主题。** 把两条主题拼一句（「五层架构一页看懂，四块能力串成一条主链路」）会被圈出来问「为什么不是一句话了？」——这就是被批过的「一个大标题下面两个维度」的目录版。改成单一主谓（「系统边界一页看清」「从工具到平台到生态」「能力到位但结果没跟上」），交付前逐条自查：有没有逗号并列两个主题、是否单行。

**问题卡矩阵的「责任归属标签」是这页的核心价值**：右上角一枚小色片写「外部依赖 / 我们自己的 / 外部 + 我们」，左侧色条同色——红＝外部依赖、品牌蓝＝自己能推进、橙＝混合。这类页的真正目的不是罗列问题，而是**提前对齐「哪些不归我们」的预期**，所以归属必须视觉化，不能只埋在正文里。混合项要单独给色，别并入红色——归成"全是外部"会被追问，归成"全是我们的"等于自己揽锅。

### 「没讲生态玩法」的正解：先找公司自己的战略框架图，别自建一套生态页

这条意见**最容易被答成自造一个「上游/中间平台/下游/角色分层」的生态页**——词都对，但和公司讲战略用的那套语言对不上，评审时反而显得是产品组自己的发明。

正解是**先翻公司自己的战略/规划材料**（年度规划 PPT、业务支撑策略图这类），里面通常已经有一张把整个盘子说清的框架图，直接拿它当坐标系：

- 典型结构：服务战略 → 使命 → 长期命题（2–4 条）→ 产品矩阵（3–5 块）→ 产品策略/用户旅程（AIPL）→ 目标牵引（终极目标 vs 当年关键目标）
- **先问「本产品在这张图里占哪几块」，再决定高亮范围——不要默认把它缩成最小的一格。** 原图的标签是**部门分工视角**（如「私域：CMS」只写在触达中心那一格里），而产品经理对自己产品范围的界定往往更宽：他会指着产品矩阵说"你看这几块不都是 cms 的么"。此时"把那一格高亮出来"就是错的——那一格只是四分之一。正确形态是**整块产品矩阵作为一个整体呈现**（四块外面套一个体系外框），**不要拆成四张卡片逐块讲**，也不要在其中一块上加高亮
- 收口句写成链路关系，不写功能罗列：「四块合起来才是一个完整产品：认识用户 → 找到用户 → 成交 → 留住」

**长期命题那一行照抄公司的，不要换成自己的说法**——它是公司级考核语言（全球化/系统成熟度、满意度 NPS、品牌忠诚度/活跃），后面「未来三年」页正好用它收口。

### 再补一页 AIPL 对照，回答"CMS 到底管哪一段"

生态坐标页说清"在哪儿"，再用一页 AIPL 说清"管哪段"。四列横排，**每列三段固定结构**：能力来自谁 / 这一段是什么 / **CMS 在这里干什么**；本产品所在那列用品牌深色高亮并标「本报告主角」。

- A 用户是谁 → 用户运营中心提供人群标签
- I 更多客人 → **CMS（公域四渠道 + 私域 WhatsApp）**
- P 更多转化 → 官网商城 app / 预售
- L 更多复购 → 导购私域工作台

好处：把"能力堆叠"直接改写成"我在链条里承担哪一环、上下游是谁"，也顺势解释了这份报告为什么不覆盖 A/P/L 的功能细节。

## 领导要求「金字塔写法」时：结论先行，之后每页都得是前面某个论点的证据

金字塔落在这类报告上只有一条硬标准：**结论页之后，任何一页只要在「往回讲背景」，结构就破了**。典型破法是结果段讲完（结论 → 交付 vs 预期 → 归因 → 问题与责任 → 短期计划）之后，又接回背景 / 痛点 / 定位 / 能力 / 架构 / 路标——领导翻到那里会想「结论不是给过了吗，怎么又从头讲」；而这类内容本该是开场的铺垫。

改法（优先最小改动，别推倒重排）：

- 结论页拆两页：一页给结论，一页给「支撑这个结论的三个论点」清单。
- 背景 / 痛点 / 定位三类前置成开场（情境 → 冲突 → 问题 → 结论），或明确降级为支撑材料。
- 产品架构、路标、能力明细保持原位，标注为支撑材料即可，不必重排。

**动手前先问一句「有没有现成框架」。** 上级若已给过备注和页序框架，照填就行——自己再设计一套金字塔结构属于加戏，用户会直接说「其实是我们搞复杂化了」。

**先问清这份报告是谁写哪一段。** 上线报告常被拆开写：领导拿产品侧规划与后续章节，产品只补前面的「结果相关」部分。没问就整份重做，等于把领导要写的那几页也替他包了，白干一轮。定分工后再决定动全部页还是只动前段；改的时候先看现有稿里哪些页属于别人的段落，别顺手改。

**先问有没有现成框架、再问这份报告谁写哪段、最后才问金字塔结构要不要调——三个问题一次问完**，不要写完一版才发现方向不对。

## 归因最多一页，别占三页

上线报告的主体是「交付了什么、到什么程度」，归因只是解释。用户会当场点出「阐述的归因太多了」。

把「交付 vs 预期」「逐国归因」「当前问题与解决方案」压缩成一页表：每项一行写「未达成什么 / 原因 / 责任归属」，被追问再翻细页。**「交付 vs 预期」那张对照表要保留**——它讲的是结果不是归因，压掉它反而丢了最硬的一页。

## 每个数字都要有口径登记（交付前必做）

做一张数字登记表，图报告里每个数各占一行：**数字 / 口径定义 / 数据来源 / 统计时点 / 是否已验证**。现成表头与逐项填写要点见 `templates/数字口径登记表.md`，复制改就行。没有口径的，要么补口径、要么从报告里删掉——留在页上等人问是最被动的。用户会直接说「很多是没正确口径的」。

一定会被问的四类：

| 类 | 要问清的 |
|---|---|
| 比率类 | 分母是发送数还是发送成功数；去重不去重 |
| 存量类 | 是留存数还是导入数；截止哪天；平台反复删加好友带来的自然涨落 |
| 账号类 | 已授权账号数 ≠ 实际在用人数，两个口径并存时必须点名区别 |
| 多文件并存 | 单月口径与累计口径不能相加、不能混画一条趋势 |

**拿到「合计 + 分项」两套数，先自己加一遍再落笔。** 分项加起来不等于合计时，多数是对方笔误，当场发回去确认；不要默默挑一个用，更不要拿这个差值去推一个听起来合理的业务解释——那会白推一轮，而且推出来的结论是错的。

## 行内通行体例（前手产品的历史报告，最值得照抄）
拿到公司里上一任/相邻团队做的历史上线报告，优先照它的骨架，别自创。一份成熟的外销 CMS 阶段性报告是这个顺序：
**系统建设背景 → 定位与目标（痛点分「运营/导购/用户」三层，每层再分「工具层缺能力 / 策略层缺方法」）→ 产品架构图（前台入口 / 能力层 / 后台支撑）→ 三阶段路标（业务路线与产品路线并排）→ 已建设能力 → 各国家已有功能 → 业务玩法（逐流程截图）→ 业务效果（案例 + 内外销对比）→ 路标更新（已完成/进行中）→ 致谢**

三个可直接复用的手法：
1. **已建能力着色**：架构图不重画，用颜色标记「已建/在建/规划」，标清统计截止月份。判定口径写进页脚——绿=已上线且至少一个国家在用；黄=代码完成或在验收、尚未全量；灰=只有方案没有排期。**未上线的需求一律算黄不算绿**，否则后面验收会被打回。
   - **颜色词写在文案里 ≠ 版面上有颜色**。文案把要点写成「公域触达（绿）」，若生成器还是统一的浅色卡片，渲染出来就是同一片蓝，用户会立刻问"三色没标出来？"。状态类页面必须有**专门的状态矩阵渲染器**（行 = 业务线，列 = 已上线/在建/规划，每格色底 + 左侧色条 + 顶部图例 + 页脚判定口径），见 `references/pptx-generation-qa.md` 的状态矩阵一节。
2. **国家 × 功能矩阵**：行是国家、列是功能，格子里 √ / ❎。比文字描述更快看出哪个国家缺什么，也顺手暴露「某国没有官方号/没有富媒体」这类缺项。
3. **业务玩法逐流程截图**：一个玩法一页（如授权→分配→转发→会话→核销），照操作顺序配后台截图。不懂业务的人也能看懂，比讲架构有效。

**第二种可参照体例：兄弟产品的上线报告（如欧洲商城那份）——业务结果先行，产品设计当附件**：结果页（一页纸结论 + 逐国目标/实际/归因表）→ 当前问题与解决方案（每条挂责任方）→ 短期运营计划（动作 + 节奏 + 衡量）→ 附件「产品设计方案」（一条主链路 → 差异怎么落到配置 → 合规与税制怎么分层 → 选型 A/B/C 为什么这么选 → 生命周期逐段）。它与上面那份 CMS 历史报告的区别是：**把「没达成」和「运营计划」摆在最前面**，产品能力退到后半当附件——适合给管理层看、且这次交付结果不及预期时用。两种体例都在行内出现过，**选哪种由用户拍**，别自己合并成四不像。

**选了这一种，就得守它的段序和页序——只换前几页的标题不改后段顺序，等于没换体例。** 用户会直接点出来："前几页归因运营侧问题没做好，产品能力是跟得上运营提的需求，但是产品的真实使用情况没达标，然后直接后面都是产品的介绍。" 合格的四段骨架：

| 段 | 章节名 | 放什么 | 不许放 |
|:--|:--|:--|:--|
| 01 | 结果与归因 | 一页纸结论 → 交付 vs 预期对照 → 归因 → **使用证据（数据页）** → 问题与解决方案（挂责任方）→ 短期运营计划 | 产品能力介绍 |
| 02 | 产品与现有能力 | 背景 → 痛点 → 定位 → 产品回应 → 四块能力 → 一条主链路 → 渠道/私域/预售能力明细 | 网站级效果数 |
| 03 | 架构与后续规划 | 产品架构 → 三阶段路标（业务线与产品线一一对应） | 效果数据 |
| 04 | 未来三年 | 工具化 → 平台化 → 生态化，底部压数据口径说明 | 现状盘点 |

两条最容易犯的结构错，犯了下场就是被打回重排：

1. **效果数据页不许夹在产品段中间。** 首战数据、累计看数、私域资产这类页，默认排在原稿末尾很容易被顺延进「产品与现有能力」段——它们讲的是"用起来没有"，属于结果段，必须**前移到归因页之后当证据**。判断法：一页只要回答"跑了多少、效果如何"，就归 01 段，不归 02 段。
2. **归因页写成「情况 × 国家与地区 × 运营侧卡点 × 该推进的人」，不要只写国家分档。** 只按「已跑出数据 / 已上线未使用 / 部分部署 / 未上线」分档，读起来是客观盘点，答不到"为什么没达标、谁该动"。四列分别落到：建好但没启用（卡点在导购与门店未关联、号没分配到人）、只用了最小范围（如仅上卡券）、**零投放（CMS 已部署但商城未上线，线下预售无处承接；渠道侧该国的富媒体 / WhatsApp / 短信均不支持）**、在跑但效率不达标（圈选含不适配机型、模板审批滞后、内容缺本地化），页底一句收口"部署不等于使用，落差在部署之后有没有人推"。

**归因里的每一条"为什么没达成"都要能指回原文，别顺手补一个听起来合理的原因。** 数字要溯源，因果更要溯源：原稿里若只有"某国零投放"和"商城没上线"，就只能写这两句；写成"合同 / 物流 / 财税未完成"这种外部条件，用户下一句就是"这信息你从哪拿到的"，答不上来整页的可信度就没了。查法：把国家名丢进原稿全文搜（`柬埔寨`、`肯尼亚`），看它出现在哪几页、原文怎么措辞，照原文口径落笔。交付说明里也要点出哪些页是提炼/推演、哪些是原文搬运，让他知道该核哪几处。

**溯源要查整条版本链，别只查手上这一版。** 被问「这条有依据吗」时，措辞可能本来就在更早的原稿里（实测「合同、物流、财税条件未完成」在 1025、1027 的「运营侧｜未同步」清单里都有，是你们自己的原稿口径，不是我编的）。只查当前版或只查某一份 md 就答「文档里没有这句」，会把自己的正确改动说成错误、还顺带否定原稿，用户一眼看穿。做法：`python-pptx` 把 1025 / 1027 / 当前版对应页的原文各打一遍再比对；确认是原稿口径后，**处置权交回用户**——保留当原稿口径、删掉、或加「待业务确认」脚注，三选一由他拍，不自作主张。真正该改的只是「把原稿的泛化表述挪成对具体国家的归因」这类我自己新增的推断。


补充：内部黑话（季度 OKR 编号、AIPL 以外自造缩写）首次出现要给中文解释；面向全员汇报时，少用内部术语，多讲「为什么做、做成了什么、对业务意味着什么」。

**禁止自造编号体系**：不要给需求编 R1–R8、P0-1 这类代号再在正文里交叉引用。业务看不懂，作者自己隔几天也会忘——用户原话是"给业务都看不懂 R1 是什么，我也会忘记"。全文用需求本名（"私域数据分析报表""导购打标"），只在全景表里保留一列序号 + 业务系统原编号（如 VAPD #1）。批量替换后要回读一遍，检查有无"名字 名字"重复、"名字"和后接词粘连成句读不通的情况。

**架构／分层页每一层要穷举，别拿一个例子当全部**：写"用户入口"层时，司内（运营后台、导购工作台 V消息/V销冠）和司外（官网商城 PC 与官网 APP、H5 活动页、领券页）都要点到——只写"消费者在 H5 领券核销"会被业务当场纠正"怎么就 H5，商城 app 也可以的"。凡是要用括号举例的层，先把该层的主要载体列全再落笔；拿不准就去翻架构文档或问用户，不要凭印象收窄。

## 用户要「产品架构图」时：改造现有页，别新增页

报告里已经有「产品矩阵/分层」页和「底层支撑」页时，再插一张架构图必然撞车。正确做法是把这两页各自升级成图，**页数不变**，靠视角分工错开：

| 页 | 视角 | 画什么 |
|:--|:--|:--|
| 产品矩阵/分层页 | 业务视角 | 五层堆叠（用户入口 → 渠道触达 → 活动转化 → 数据与工具 → 底层能力），层间加向下箭头 |
| 底层支撑页 | 系统视角 | 中心辐射：CMS 居中，左侧入口「访问 →」、右侧六渠道「下发 →」、下方外部依赖「↑ 调用」，底部一句边界 |

同一批模块在两页出现不算重复，只要**一问不同**：一页回答"业务上分几层"，一页回答"技术上依赖谁、边界在哪"——后者正是协同方和领导最关心的。

**分层页不是给每层写一行长句**。五条从上到下的色带，每条里塞一句用顿号连起来的模块名，渲染出来只是"五条带字的色块"，用户会直接问"这块做成架构图会不会更直观"。正确做法是**每层内部拆成模块小方块**（对齐公司历史报告的"能力中心 + 下挂模块"写法）：用户入口 6 块（后台/导购端/商城/H5/领券页…）、渠道触达 6 块（公域 4 一块色、私域 2 另一块色，一眼数得出"4 公域 + 2 私域"）、活动转化 4 块、数据与工具按中心拆（洞察/策略/工具/数据中心，每块下挂能力）、底层能力 4 块。层与层之间加向下箭头（上层做业务、下层做支撑）。

两个渲染坑：①底部结论条别直接取 `bullets[0]`（那是要点第一条，不是结论），用写死的四句式（每层管什么），否则会抽出牛头不对马嘴的一句话并在句尾留孤字；②箭头用 `MSO_SHAPE.DOWN_ARROW` 且要够粗够深（宽 ≥0.24"、色值比层底色深两档），浅灰小三角投影时几乎看不见。

**标题的名词要和图形形态一致**：画的是一维层叠栈就别叫「产品矩阵」，改成「产品架构」；矩阵意味着两个维度交叉。

**架构图必须把连接关系画出来**：只摆一堆方块，评审会直接判"像清单、不像架构图"。左右用带方向的箭头并标动词（访问 / 下发 / 调用），下方依赖用「一条横向总线 + 一根上行箭头」接入中心块，比逐个连七根线干净得多。

**架构页的页序：放在「产品段」的第一页，别压到末尾。** 用户会直接说「产品架构的优先级应该上移，提到最高处，这是老板们喜欢看的」。默认排在产品段末尾是错的——归因段（结论 → 交付对照 → 归因 → 使用证据 → 问题与责任 → 短期计划）讲完，紧接下一页就给全局架构，老板一眼看到系统全貌，再往后才是背景/痛点/定位/能力明细。但**不要越过结果段**：那一段是他定的「为什么没达成」，插进架构图会打断归因。挪完必须全篇重编页码与章节标签（架构进了产品段，原「03 架构与后续规划」就只剩路标，章节名要改成「03 后续规划」）。

**架构图的「延展性」不能只标一两处，要和后面的规划页对齐。** 架构图被批「这是产品现状，架构应当具备延展性」时，靠几个黄块应付会被追问「就两个是不是太少了」。正确做法是把「三阶段路标」和「未来三年」里承诺的每件事，逐个回到架构图上找它落在哪个模块：找得到就标成延展（洞察 / 策略 / 工具 / 数据中心、底层的全球租户、私域的两块导购号，都是典型的第二批），**一个都找不到的，说明那是规划新增的能力、图上根本没有这个位**——例如「私域好友运营」「事件标签中心」「营销画布」「多国复制模板」。

**「标已有的」和「加没有的」是两件事，只做前一件会被打回。** 用户说「不是增加拓展能力吗」时，指的是要在图上真的**长出新模块**，而不是给现有方块画圈。落地做法：把架构图略微缩小让出底部条带（约 4.1" 高即可，原 4.67"），在下方加一行标题「规划新增的延展能力」+ 三到四张浅黄底、橙色虚线的卡片，每张写「模块名 + 属于第几年 + 一句话说明」，与未来三年页逐条对应。这样一张图上同时有「现有五层架构」「已有的延展位」「规划新增的能力」三层信息。

**不要在规划里没有出处的地方硬加模块**：每张新增卡片都要能指回规划页的原话（第二年的私域 2.0 / 事件标签，第三年的四块互联 / 14 国复制），凭感觉往图上塞「活动转化要扩展」这类没有规划依据的标注，会在汇报时被问「这块规划里说了吗」。

**在整页贴图上叠加标注（不重画原图）的坐标换算法**：源 pptx 里取模块形状的 `left/top/width/height`（EMU，除以 914400 得英寸），按 PDF `clip` 的比例映射到贴图矩形：

```python
fx = lambda x_in: (x_in * 72 - clip.x0) / (clip.x1 - clip.x0)
fy = lambda y_in: (y_in * 72 - clip.y0) / (clip.y1 - clip.y0)
左 = 图左 + fx(b.left/914400) * 图宽
宽 = (fx((b.left+b.width)/914400) - fx(b.left/914400)) * 图宽
```

三个配套的坑：①**模块的文字标签与外框常是两个形状**（文字是独立 TEXT_BOX、色块是 AUTO_SHAPE），按「文字框中心点落在哪个色块内」配对，否则框会套在错位置或套在标签上；②**同一个中心点会同时落在「模块方块」和「整层底板」上，必须取包含该中心的面积最小的色块**——取第一个命中会拿到层底板，框出来就是整层一圈，读起来像「渠道触达整层是延展」，而层里的短信、邮件明明是已建成的，用户当场就会说「怎么还是整层框」；③**用虚线（`line.dash_style = MSO_LINE_DASH_STYLE.DASH`）而非实线，并按原框内缩约 0.025"**：相邻模块的实线描边只要一贴边就连成一整圈，虚线加内缩才能让「逐个模块」看得出来；描边只画线不填充（`fill.background()`），填充会把模块里的字盖掉。

**原图自带的旧图例要盖掉重写**：先用白块覆盖旧图例区域、再在同一位置写短图例（如「虚线＝延展能力」），明细说明放页首结论句里——图例拉长会顶出页面右缘被裁。

**叠加完必须渲染回看，逐个数框**：视觉核时问的问题要具体到「橙色虚线框标在哪几个模块上？是模块级还是整层？」，只问「有没有标出来」会得到「有的」这种没信息量的回答，而实际框错了层级。

**外部依赖清单别自己枚举，去项目里的架构文档对账。** 项目常有 `docs/flow/<系统>-product-architecture-*.md`（业务架构 + 系统架构两节，Mermaid 源 + 同目录 HTML 浏览版），它的「基础支撑层」就是权威清单。自己凭印象列会漏东西也会归类错：漏了通道类（短信/邮件/富媒体）、漏了内部平台（V消息），还把**业务侧平台（活动/卡券平台）混进"外部依赖"**——业务侧平台应单列一行，和延后项放一起。顶部那句"调用 N 个公共能力"里的 N 必须等于实际框数。

**多列布局生成后，拿渲染图数一遍每列的框数，和数据源条数比对。** 右侧一列条数多时很容易越过下边界、被下方区块盖住，视觉上"少了一个"——本次六个渠道只显示出五个，就是因为右列第 6 个落在依赖区标题下面。判断方法：渲染页拿去逐列数框，比数据少就是布局重叠（把该列框高压紧、或把下方区块整体下移），不是漏画；PPT 文本结构里其实六条都在，只查文本查不出来。

## 上线范围页：「为什么某些市场不上」要单独成一页

多市场上线必然有取舍（系统铺了 14 国、某个能力只在 7 国开）。读者第一个问题一定是「为什么不给我这个国家」。别把这答案塞进功能页当一句脚注，而是单独出一页：

1. 核心一句话给**交集公式**，让取舍显得是规则而不是拍脑袋：如「线下预售 = 商城预售能力 ∩ CMS 已部署，两个条件缺一不可」。
2. 三类清单分开列：上线（逐个点名）/ 待确认（写明触发条件，如「CMS 后续部署则跟随上线」）/ 不上线（**每一国配一句具体原因**：没有商城、没有触达能力、系统未部署）。
3. 结尾补一段**后续开通路径**（已具备的直接配置 / 缺能力的要发版 / 新市场要重新部署），把「以后怎么才能上」一并答掉。
4. 若线上与线下范围口径不同（线上覆盖所有有商城的国家），单独一句说清，别合并成一句话。

这页的作用是**一次答完所有国家**，避免会上被逐国追问、也避免"是不是漏了某国"的质疑。数据要先跟用户核一遍口径再落笔。

## 全员汇报 ≠ 管理层汇报：三类内容不许上全员页

同一份报告，受众不同，红线不同。用户会当场挑出来（"过期了还要在上面提醒过期的用意是什么呢"），判断标准是：**这页对听的人有没有价值、会不会反过来伤到团队**。

| 不许上全员页 | 为什么 | 该放哪 |
|:--|:--|:--|
| "已过期 / 逾期 / 待确认"这类排期失控措辞 | 对非相关听众零价值，只留下"这团队交付不力"的印象 | 与管理层单独沟通的材料、复盘会 |
| **未与需求提出人确认的优先级结论**（P0/P1/P2、"需求接受"） | 摆上全员页等于替产品签了需求接受结论，而业务侧还没确认——用户原话："你这样放上去，就代表我对于需求的接受结论了啊，这块还没和需求提出人确认呢" | 内部评审材料 |
| 需求提出人姓名 | 点名把责任压到个人，且尚未与本人确认 | 内部材料；全员页只写"业务侧 / 某中心提出" |
| **替别的部门派活**（"Q4 由 XX 中心牵头统一口径""建议 XX 团队…"） | 产品在全员场合无权给别的部门安排工作，这句话一出口就是越权，当场树敌 | 会后单独沟通；报告里只写"下一步与 XX 对齐口径" |
| **把口径不明的数字当结论用**（如"私域贡献约 15% 销量"） | 数字一上页就要替它接住所有追问，而它连统计时间、范围、归因方式都没定 | 只讲能核实的资产量（留存用户数、导购数）；贡献类改成"暂无统一归因口径，本报告不纳入" |

替代写法：全员页按**价值分组**讲（能算账 / 能自动 / 能分层），不按优先级分组；结尾讲"下一步：与业务一起定排期，先出功能清单和 PRD"，不承诺时间。

一句话自检：**这页写出去，是替用户挣分，还是替他背锅？** 背锅的移到别的材料。

## 报告「有没有数据支撑」：先做数据分布盘点，再判断缺口

用户会直接问「我们的上线报告是不是缺少数据支撑？」——**不要凭印象答「有」或「没有」**。先把每页的数字捞出来，用分布说话：

```python
# /root/venv-ppt/bin/python（该 venv 已装 python-pptx）
from pptx import Presentation; import re
for i, s in enumerate(Presentation("x.pptx").slides, 1):
    t = " ".join(sh.text_frame.text for sh in s.shapes if sh.has_text_frame)
    print(i, re.findall(r"\d[\d,\.]*\s*(?:%|万|亿|个|条|家|国|台|人)?", t)[:12])
```

能捞出业务数字的算「有数页」，只剩职责/流程措辞的是「无数据页」——这份分布表本身就是答案的骨架（典型：28 页里只有 8 页带数，且集中在痛点、首战、私域资产、OKR 四处）。

缺口按四类对，别泛泛说「数据不够」：

| 类 | 缺的表现 | 补法 |
|---|---|---|
| 规模 | 全篇没有「累计触达 N 人 / 发了 N 条」 | 从触达报表拉月度汇总 |
| 效果漏斗 | 只有一个比率（如阅读率），没有 发送→送达→打开→点击→转化 | 取决于埋点深度，先问报表侧支持到哪层 |
| 私域漏斗 | 只有留存存量，没有 导入→留存→互动→转化 | 导入数业务侧有，互动/转化要数据方 |
| 目标对照 | KR / 年度指标大半表格空着 | 找 OKR 系统或数据方 |

判断口径：全员汇报讲清「做了什么、能干什么」就够，不必堆数。但**「覆盖 N 国」只有国家名单、没有各国触达量，等于只是部署了**——这类「有名单没量」的地方必须补，会上必被追问。另外，**自己写在页上的「还没有数」就是在自曝**，宁可改口径或删行。

**同一指标出现两个版本时先核口径再落笔**：用户会拿另一份材料里的同名图表来对（内销 vs 外销阅读率连小数位都不同），说明两张图来源或统计区间不同。别自己择一、别求平均，先问「这份是哪版的、统计区间是哪几个月」，确认后再统一全文并 grep 复核。

## 数字溯源：每个数都要能指到源文件

用户会抽查任意一个数字（"这数据你从哪得来的"）。出不了出处就不能上页。

- 交付前给每个数字记下来源（哪份需求文档 / 哪张 OKR 表 / 哪行原文），被问时一次性回显文件名+原话，不要边翻边答。
- **一个数只能有一个口径来源**。两份文档打架时（A 处"共存账号 17 个（印马合计）"、B 处"某国试点 15 个"），**不要用"其中……"把两个来源缝进一句话**——那等于造出第三个数，还会把归属挂错。选权威源（业务需求原文 > 前手 AI 初稿），另一个降级为"待核对"或删。
- **时间跨度和汇总数自己算一遍**。照抄前手文案会把它的错一起带下去（前手写"九个月"，实际 2025.09→2026.10 是 14 个月）。凡出现"N 个月 / N 年 / 合计 N"，用日期现算。
- **但算准了也未必该写**：用户会明确叫停"不要写 14 个月"。月份数容易和听众心里的口径打架（从组织成立算起？还是产品实际开发周期？），而且不加分。**安全写法是只写起止节点与规模**（2025.09 启动 → 2026.10 上线、14 国 / 6 渠道），不写月份数；凡全篇出现"N 个月 / N 年"，先问要不要留，别默认保留。改的时候记得封面数字块、时间线页标题、时间线正文、结尾页四处会各写一遍。
- **用户口述的汇总数，按分项加一遍再落笔**。他说"合计 118"而分项是 66+40+2=108 时，当场把加总结果发给他要确认，别默默挑一个用——他会回一句"写错了"就解决；不核就把错数带上页。同理，国家/渠道这类清单要数个数再对照他说的总数（13 个具名 + 1 个部分部署 = 14 国，正好对上）。
- **累加前先验"这个指标能不能加"**：列名带"人数"的字段未必是去重人数。用常识反推一遍——某国"发送成功人数"3,337 万，而该国总人口才 3,400 万，必然含重复，它是**跨计划跨时间的累计人次**。这类数字用于汇报时必须写"人次 / 次"并注明"同一用户可能被多次触达"，不能写成"触达了 N 亿用户"；成功率这类比率只有在分子分母同口径时才成立，否则一起废掉。拿不准就先找数据方确认计数方式，宁可标"口径待确认"也不要裸用。
- **自己推理出来的数量词同样要溯源，这类最容易漏**。过程解释句里顺口写的"没有这一步后面三个国家上不了线"、"两大痛点"、"三类角色"，往往既没有源文件也不是用户给的，纯属落笔时的印象。写之前问一句「这个数字出自哪份材料」：答不上就删数字改定性（"每进一个国家都要重做一遍"），或换成有据的清单。交付前把所有 `N 个 / N 条 / N 项` 连同类名词一起 grep 出来（`grep -oE "[0-9一二三四五六七八九十]+ ?个?[国家渠道项条]"`），逐条对来源——前手文案里的数字和用户口述的数字都有人替你查了，唯独自己写的没人查。
- **实体清单也要跟当前业务清单对账，不只是数字**。前手稿的 KR 对照表里会挂着规划清单里的国家/系统，而用户最新给的部署清单里可能根本没有它（典型：某国只在"规划里的普外国家"出现、备注写着"无进展记录"）。照抄等于替一个不存在的事实占一页。逐个实体问出处，答不上就**正文和文末待补清单两处一起删**——这两处经常各写一遍，只删一处留尾巴；删完把该行改成"其余以业务给定清单为准"。
- **溯源 grep 先限定范围**：PRD/评审文档常内嵌 base64 截图（`![...](data:image/png;base64,…)`），在这些文件上 `grep -rn <关键字>` 会把上百 KB 的 base64 灌进上下文、还只能看到首尾。先 `grep -rl` 只列命中文件，再对命中文件 `sed -n '<行号>p'` 精读；或排除含 `data:image` 的文件后再搜。
- **被问"这数据你从哪得来的"时，先验证再回答，并给原文而非自己的复述**：声称某个数字出自某份 PDF/PPT 前，先把文件打开确认它真在那里。PDF 用 `pymupdf` 逐页 `get_text()` 搜；PPTX 要搜三处——`ppt/slides/*.xml` 的文本节点、`ppt/charts/*.xml`、`ppt/embeddings/*`（内嵌 Excel），只看 `shapes`/`table` 会漏。回答时附上页码、原文标题和同页附注，不要把自己写过的那句话当成出处。
- **搜数字必须用固定串（`grep -F` 或 `data.find(b"11.86")`），不能用裸正则**：`11.86` 里那个点会匹配任意字符，`7.96` 能命中 `7096`、`7,96` 之类的无关文本，产生一大堆假阳性——曾据此误以为找到了出处。搜不到时用 `grep -rlaF` 做一次全包扫描（含二进制），能确认"这份材料里确实没有这个数"就不必再猜。用户能给你一份与仓库全部材料都对不上的图表，这是正常的——直接说"这份不是我手里任何一份材料里的，它从哪来的"，不要挑一个"可能来源"凑答案。

## 终稿交付前逐页体检：三类机械错最容易漏

内容写完不等于能交。逐页扫一遍，这三类错跟业务无关、纯交付质量，但投影时最抓眼：

**① 浮点精度泄漏进单元格**。表格里的比率是脚本算出来的，没做取整就会写出 `66.069999999999993` 这种值。不用人工翻页找，把全部数字抓出来筛长小数即可：

```python
# 任何数值型单元格 / 文本里的数字都扫
import re
bad = re.findall(r'\d+\.\d{4,}', blob)   # 四位以上小数基本都是未取整
```

统一取两位小数。比率类（成功率 / 阅读率）固定保留两位，不要一页 15.72 下一页 15.9。

**② 分类清单加起来不等于总数**。典型：「上线 7 + 没有商城 6 + 能力不足 2 = 15」，而全篇口径是 14 国——因为其中一国根本不在总数里（未部署），被错归类进去了。**每个分组页都要自己加一遍，与全篇口径对账**；对不上不是改数字，是改分类归属（把「未部署」从「能力不足」里拆出来单列，或标题改成「其他国家」）。领导会在会上当场加这个和。

**③ 同一件事在不同页两种说法**。实测：「短信渠道建成但外销目前没有实际使用」vs「短信 1 国，只有印尼用过 1 次（4 人）」。差 4 个人也是矛盾。用关键词全文扫一遍同一话题的表述：

```bash
# 交给能读 pptx 文本的环境，按关键词找同话题多处表述
grep -n '没有实际使用\|未使用\|未启用\|从未'
```

改法是往一致的一端靠（「基本未使用，仅某国试发 1 次」），不是删掉其中一句。

这三类都不需要业务知识，但要**主动查**——作者自己写的，不会被业务方替查。

**结构级核验：页数不能数 slide 文件数，占位符不能数关键词。**

- **页数**：`ls ppt/slides/slide*.xml | wc -l` 会数出比实际多的值——多次删页改出来的文件里会残留孤立 slide（实测放映序列 25 页，slides 目录下却有 27 个 slide 文件，多出的两个既不在序列也不被引用）。正确读法：`ppt/presentation.xml` 里 `<p:sldIdLst>` 的 rId 个数才是放映页数，再用 `ppt/_rels/presentation.xml.rels` 把 rId 映射到 `slideN.xml` 核对顺序。孤立文件会让部分读取工具（含自写的遍历脚本）误报页数，改完 pptx 后必查这一项。
- **加页会撞上孤立部件，保存出重复 zip 条目（实测会真写坏文件）**：`add_slide` 按「当前页数 + 1」给新部件命名，序号正好等于包里某个孤立部件时，写出的 zip 会有两条同名条目，被跳过的那页会变成别的页的复制件，PowerPoint 打开可能弹修复。先枚举包里全部 `ppt/slides/slideN.xml` 与 `sldIdLst` 比对，找出孤立部件（既不在放映序列、也不该再被用到的历史遗留页）。
  - **回避法（孤立页可能还被别处引用时用）**：新页**显式命名成 `slide{max+1}.xml`**，不依赖默认命名；孤立部件原样留着。
  - **清理法（更彻底，能一次解决后患，优先用它）**：孤立页往往还被 `ppt/_rels/presentation.xml.rels` 挂着 `<Relationship Target="slides/slideNN.xml">`，只是 `sldIdLst` 里没有——python-pptx 一访问 `.slides` 就按位置重编号，活页撞上孤立页的编号，保存必出 `UserWarning: Duplicate name`。用 zipfile 重打包，**三处一起删**：① `ppt/slides/slideNN.xml` 及其 `_rels/slideNN.xml.rels`；② `[Content_Types].xml` 里对应的 `<Override PartName=...>`；③ `presentation.xml.rels` 里 `Target="slides/slideNN.xml"` 的 Relationship 条目。**只删文件不删 rels 关系，包会指向不存在的部件，更难查。** 清完用 lxml 解析这三个 XML 验合法性，再用 python-pptx 打开保存一次，确认无警告、包内无重复条目、slide 数等于放映页数、部件编号连续。
  - 无论哪种做法，保存后都要 `zipfile.ZipFile(f).namelist()` 查重名（必须为空），并核对 `[Content_Types].xml` 已登记新部件。
- **内存重编号不是磁盘状态**：python-pptx 首次访问 `prs.slides` 会按页序惰性重编部件名，读出来的 partname 与磁盘上可能不一致（实测：内存显示新页是 `slide9.xml`，磁盘上其实是 `slide34.xml`）。判文件健康只看磁盘：解包比对 `sldIdLst` 顺序 + 各页真实部件名 + zip 无重复条目三项。
- **页码校验的假阳性**：全页扫 `\d+\s*/\s*\d+` 会误抓正文日期（`10/21`、`10/15`）和与相邻数字粘连的文本（`8 / 27` 后面紧跟 `14` 拼成 `8 / 2714`），据此报「页码异常」是假警报。校验要精确到形状：定位页脚形状后读值，或只认完整匹配 `^\d+\s*/\s*{total}$` 的 run；封面无页码属正常，不当异常报。
- **加页会让所有外部页码引用集体过期**：页码顺延后，引用具体页码的外部文档（待补数据清单、归档说明 README、验收清单）全部失效。先算映射（新增第 N 页 → 原 N 及其后全部 +1），逐份更新，改完 grep 旧页码残留，并用解包读 XML 的方式（按 `sldIdLst` 顺序定位）交叉验证一遍，不要信工具报的页号。
- **占位符**：`grep -c '待补'` 会把正文叙述里的“某数据仍待补”也算进去（实测数出 9 处，真正的 `[待补：xxx]` 占位只有 7 处，多出的 2 处是正文文字）。核验占位用带方括号冒号的固定串，并同时报两个数（占位符 N 处 + 正文提及 M 处），否则会把正文叙述误判成“多出两处没填”。
- **文本核验不能裸 grep slide XML**：直接 `grep '7.21' ppt/slides/*.xml` 会命中**几何坐标与样式属性值**（实测：三个 slide 报命中，解析 `<a:t>` 文本节点后该串零残留，命中的全是形状的 off/ext 数值）。文本核验必须解析 XML 取文本节点：
  ```python
  A='{http://schemas.openxmlformats.org/drawingml/2006/main}t'
  texts=[e.text for e in ET.parse(f).iter(A) if e.text]
  ```
  图表里的数另走 `ppt/charts/*.xml` 的 `<c:v>`。裸 grep 只配用来**快速定位可疑页**，不能当"还有残留"的证据。
- **页码正则要容忍空格**：页脚实际写成 `24 / 28`（斜杠两侧带空格），`\d+/\d+` 无空格版会全篇漏检、误报"29 页全部缺页码"。用 `^\d+\s*/\s*{total}$` 精确匹配整段 run，封面无页码属正常。

改这三类错时一律用字符串级手术（解包 XML 改文本再重打包），不要整份重新生成：改完拿全稿逐 run（`<a:t>` 与图表 `<c:v>`）跟改前备份逐项比，证“变化恰好是计划改动的那几处、其余页零变化”；另跑一遍字号 `sz` 属性分布对比，证“未引入新字号”。三项都交，才算这份二进制改干净了。

### 删页：页数对了不代表删对了

删页是最容易「看起来成功」的破坏性操作——删错页时页数照样对，删掉的可能是关键内容页而该删的还留着。三项一起验，缺一项都可能交出一个内容全错的版本：

1. **字节数变化要合理**：删一页通常少几十 KB。若只少几十字节、或新文件大小接近另一个历史版本，说明读的根本不是你以为的那份源文件。
2. **关键图片还在不在**：`zipfile` 数 `ppt/media/` 的条目数与各自字节数，跟改前逐个比。大图（领导原图、系统截图）丢了会让字节数掉一大截，这是最灵敏的信号。
3. **逐页打印标题**：改完立刻 `enumerate(prs.slides, 1)` 打印每页首段文本，确认删掉的正是标题匹配的那一页，而不是相邻页。按「第 N 页」下标的操作一律先换算成标题确认，脚本里把待删页的标题打出来再删。

另外：**页码数字与分母总数是两套替换，要全篇一趟改完**。只对位移之后的页改数字、忘了前面几页的分母，会留下 `3 / 29` 与 `4 / 27` 并存。

## 用户说「这块不一致了」：先核数据，再解释——不要替他的直觉找理由

用户提出的质疑本身不一定成立（他原话："我表明的不一定对啊，你思考好呢"）。他指着一页说"数字打架"时，**第一步是把两个数按维度拆开逐项核**，而不是顺着他的判断先编一个合理解释。

反面实例：标题写"107 个授权号"、卡片写"108 名导购"，用户说"不一致"。为了圆场臆测了一句"号数少于人头数属正常"——核完发现印尼 66=66、孟加拉 2=2 完全相等，只有马来 40→39 差 1，说明两者大概率就是同一口径，真实情况只是"马来少授权了 1 个号"，根本不存在"号≠人"这回事。

规矩：
1. 两个数按维度拆成表（国家 × 两个口径 × 差值），看差在哪一格、差多少。
2. **差值为 0 的格子说明两个口径高度重合**，此时不要再用"口径不同"搪塞；只有全部格子都差、且差得不成比例，才谈得上口径差异。
3. 对真实差异只给一句事实（"马来少授权 1 个号"），成因没确认就标"待业务确认"，不要顺手补一个听起来合理的原因。
4. 一旦发现自己的上一版解释没有依据，**明说"这是臆测，撤回"**，再给正确版本——不要在两个版本之间含糊过去。

处置优先选「把这组数从标题层拿掉」：两个口径的数字并列在标题里必然被追问，挪进正文卡片并标清单位就不扎眼。

## 一次上线横跨多个系统：版本号按系统分列，子端不另立版本

一份"上线"常常是好几个系统同时发版。写版本时**逐个系统点名各自的版本**，读者（尤其业务）才知道这次动了哪几个系统：

- ✅ `预售由两个系统一起交付——外销商城 V5.1.0 + CMS v1.8.0`
- ❌ 只写一个版本号（"V5.1.0 上线"），会让人以为另一个系统没动
- ❌ 把系统内部的子端当成独立系统（"CMS v1.8.0（导购端 v1.8.0）"）——导购端是 CMS 里的一部分、代码同属一个版本，单列会造出一个不存在的系统。用户会直接纠正"导购端是在 CMS 中的，代码在一起"

同一件事在 roadmap（季度排期表）和上线报告里版本叫法可能不同（排期表写 `【v1.8.0】预售系统建设`，上线报告封面写 `V5.1.0（导购端 V1.8.0）`）。对不上时先问"这两个号是什么关系"，别自己合号或择一——用户答"外销商城 5.1.0、CMS 1.8.0"后才好落笔。确认后全文替换并 grep 复核：路标页、预售页、能力全景、Q4 计划四处通常各写一遍。

## 能力全景的「规划中」列：从用户的 roadmap 取，别自己设想

状态矩阵的灰色列经常空着，看起来像"没规划"。用户会发来季度排期甘特图说"这是 roadmap，可以稍微补充下这个家底"——**规划列照它填**：把 Q4 的 TBD 项（"事件圈人 11 月待定""预售付定金 12 月待定""短信供应商切换 12 月待定"）按业务线归到对应行，比自拟场景准得多，也顺手校正了前面的版本口径。

**填了带时间的规划项，页脚判定口径必须同步改**：原来写"灰＝只有方案、无排期"，一旦灰格里是"11 月待定"这句就自相矛盾——改成"灰＝已列入规划、排期待定（roadmap 标注 TBD）"。图例、表头、页脚三处要一起演。

## 拿到多时点数据：做「变化」，不要只报最新一个点

业务会陆续给数据（先 8 月、再 9 月）。**只把最新时点填进页面，等于扔掉最有说服力的部分**——要做成前后对比：

- 同一指标两期并列 + 净变化（导购 37 → 108，一个月净增 71；印尼留存 1.6 万 → 4.6 万；国家 7 → 14，单月新增 7 个）。这类"一个月铺了 7 个国家、导购翻三倍"的说法，比任何一个单点数字都硬。
- **分项缺一个时点就不硬凑合计**（某月只给了导入量、没给留存），逐国并列即可，不要自己造一个"上月总计"。
- 增长旁边仍要保留口径注解：是留存数还是导入数、统计截止哪一天；Meta 会反复删加好友，涨跌不全是运营结果。

## 指标状态变了，全文的「N 项」要一起改

任一 KR 指标一拿到数，"六项待补"这类计数立刻过期，而它通常散落在多处（OKR 页、季度计划页、文末待补数据清单）。**改完用 `grep` 把「N 项 / N 条待补」全捞一遍同步**——同一份报告里一处说六项、一处说五项，评审时比没数更尴尬。

## 用户纠正技术事实、但与项目文档冲突时：先联网核实，别急着改

用户凭直觉纠正一个供应商/技术事实（"X 是短信服务商，跟 WhatsApp 有什么关系"），而项目文档恰好写着相反（"X 是 WhatsApp 底层服务商"）——**两边都别盲信**，先查第三方事实再落笔。

实例：牛信云既卖国际短信，又是 Meta 官方授权的 BSP（企业不能直接调 WhatsApp API，必须经 BSP 接入），所以"它是短信服务商"和"它是 WhatsApp 接入方"同时成立——文档没错，用户的直觉只是不完整。核实后回头讲清接入链路（企业 → BSP → Meta），他往往一句"我理解错了，按你的来"。反过来若文档确实错了（把短信供应商写成 WhatsApp 服务商），要连文档一起纠正，别只改页面。

**术语改名让用户一句话定**：把「富媒体短信」自作主张统一成「富媒体」，会被一句"就叫富媒体短信吧"打回。术语、编号、称呼全部由他定；等他定了再全文替换 + grep 复核。

## 需求 list 的功能点拆解（交付形态与粒度）

除了 PPT 和方案档，用户还会把需求整理进一张在线表（列：所在端 / 1级菜单 / 2级菜单 / 3级菜单 / 4级功能点 / 5级功能点 / 功能点描述）。粒度、菜单层级来源、接口字段依据、报表类需求的归属判定、字段口径写法，全部见 `references/requirement-list-breakdown.md`——**动手前先读它**，最常被打回的两点是「一行一个字段太细」和「把已有接口字段写成新增」。

## 交付节奏：攒问题 → 一次性改 → 一次性发

用户逐页审稿时会连续抛问题。**不要每提一条就改一版发一版**——他会叫停："你先不要改一下发我下，等全部问题确认清楚，再一次性改了发我呢"。

- 开一份 `修改清单.md` 放交付目录，分三块：**已改**（页码 / 问题 / 处理）、**待用户拍板**（给建议 + 选项）、**待补数据**（数据 / 用在哪页 / 找谁）。
- 每收到一条反馈就记进去（用 patch 追加表格行，别整篇重写）；回话只给"记下了 + 一句处理建议 + 要他选的选项"，不附文件。
- 等他说"就这些 / 可以改了"，再一次改完、一次交付。

## 交付形态：先出逐页文案，再出真 PPT

**改已有 pptx 一律先复制一份带日期后缀的工作底稿，原文件一字不动。** 命令就两步：`cp 原名.pptx 原名-v4-<MMDD>.pptx` 然后 `md5sum` 两份核对一致再开工。用户会明确要求「不要在这个上面直接改，复制一份名称 XX 结尾」——照做，并在交付说明里写清「底稿是哪个、原文件没动」。后续所有脚本只读写底稿，回到旧版只需换回文件名。

汇报 PPT 先交一份**逐页文案 md**，每页固定五段：页面标题 / 核心一句话 / 要点 3–7 条 / 需要的数据与图表 / 讲法备注。用户能直接改文字、能在评审前自己讲一遍，改稿成本远低于改版式；文案定稿后再排版。页数按受众定（全员汇报压在 30 页内），宁砍不水。

文案过了目，再真出 `.pptx`：用 python-pptx **按同一份 md 生成**（解析 `## 第N页` 段落，文案改一处 PPT 重跑一次，绝不手工在 PPT 里改字）。交付前必做渲染自检，而不是生成完就发——具体环境、生成器结构、自动缩字号、渲染+视觉检查闭环见 `references/pptx-generation-qa.md`；要把文字页升级成**真图表或真界面截图**（含从已有 PPTX 里扒截图的提取与版式几何），见同一文档第 11 节。

**版式不是自由设计——先扒公司现成的同类 PPT 当品牌母版。** 自己设计出来的"干净版"一定会被否（用户原话："上线报告没有按照这种 ppt 的排版格式来吗？"）。公司里已经有一份对味的同类报告时，先量它的主色、字体、字号、封面图、标题位置，再改造生成器，具体量法与卡片式版式见 `references/brand-deck-extraction.md`。

拆页规则：一页要点超过 5 条、或单条超过约 120 字，就**拆成两页**（例如"季度进度"一页、"年度指标缺口"一页），不要靠缩字号硬塞。拆完总页数仍要在受众上限内（全员汇报 ≤30 页）。拆页后总页数会变，页脚里的"页码 / 总页数"和后续页的 md 编号要同步改，别留在旧的 26/27。

**时间线页只写阶段，不写日期流水**：一条要点挂一个日期＋版本号的写法，投影时必然被读成"数字很混乱"（用户原话）。压成三段式（如"打底座通公域 / 建私域 / 上预售"），整页只保留 3 个时间区间 + 3–4 个关键数字（几国、几渠道、上线日）；版本号（v1.4.0 / v1.5.0 / v5.1.0）与小里程碑全部移到附录或口头补充——全员听众关心"什么时候做了什么"，不关心版本号。

## 把用户已拍板的方案补成「方案 + 迭代计划」交付档

用户自己写过 v1/v2 方案（还标着"已拍板"）时，**别重写方案**——只补他缺的两半：

1. **可开发的一半**：配置页字段（列表列 + 新建弹窗分块 + 校验规则）、交互（在哪一步、条件结构长什么样、条数上限）、权限（谁能配 vs 谁能用，配置权通常只给总部避免各国口径分裂）、验收清单（每条可判定，别写"体验流畅"）。
2. **规划的一半**：飞轮闭环 + 分阶段（V1 已定 / V2 扩场景 / V3 智能化）+ 设想场景表（每行标"归入哪一阶段"与"前提待确认"）+ 下一阶段的**推进条件**（由数据触发还是由排期推动）。

**只交第 1 半会被打回**——原话是"我要的是……产品方案和迭代计划"。落地设计写得再细，缺迭代路线就不叫方案。

**待确认清单不要平铺**，按「卡开发 / 待拍板 / 不卡」三档重排，每档标找谁。他拿这份去见对方时能直接说"这四条不给，开发就停"；平铺 11 条等于没有优先级。自己已经给出方案的那几条，要标成"本文已给方案，待拍板"，别混进真待确认里。

**交付位置写进项目仓库**：`docs/<主题>/` 下，和用户自己的 v1/v2 放一起（他会在那儿找，不会去本地交付目录翻）。写完只报绝对路径 + `git status` 未提交状态，commit/push 由他自己做。

**结论要给"真风险在哪"**：技术量小的需求，风险通常在外部依赖（对方系统的表能不能按时出、状态字段能不能区分关键取值）。开头或结尾点明"这两件不定，代码写完也验证不了"，比罗列工作量有用。

**交付前做人称与署名清理（外传档必做）**：评审档、方案档会发给同事和其他部门，人格化代号一律不留。
1. 版本/修改记录的「修改人」列不写 AI/助手代号——改真实姓名或「—」，但**保留版本行和修改内容**（评审要看哪版改了什么），只改署名不动结论与口径。
2. 文档里的内部昵称换实名，评审人认不出昵称是谁。
3. 内部方法论类文档里的角色代号统一成可读角色名（如「个人 Agent（AI 指令官）」）——**不要删整句**，那是工作流说明，删了主语句子就不成立。
4. 改完 `grep -rn <名字>` 全项目扫一遍：这类称呼常散落在方案稿、调研问卷、PRD 版本记录、旧稿多处，只改手上那份必留尾巴。

## 画「覆盖矩阵」时，列取全篇口径的国家清单，不取数据源那份清单

矩阵的数据源（某张触达/使用情况表）往往只含**真正有业务数据**的国家，而封面、路标页、正文写的是**部署口径**的更大数字。直接照数据源画，页面上就会突然少一个国家——用户会当场指出来（"这里为什么是 13 国了呢"）。

规矩：
1. **先定全篇国家口径**（如 13 个正常部署 + 1 个部分部署 = 14），矩阵列数必须等于它。
2. 数据源里没有的国家，**补一列全灰**，并在原因区单列一条说明（"仅上卡券，未接触达渠道"），不要默默省略。
3. 补齐后重算单元格宽度重新排布，防止最后一列被右侧面板挤出去（见下条渲染核对）。
4. 同理适用于渠道、模块等任何"矩阵的一维"：一维的取值集合永远跟全篇口径走，不跟数据源走。

## 只有一段月份的数据时，先看同一份在线表还有没有历史页签

用户会问"这块数据只有到 6 月份的吗"——答案常常不是"只有"，而是"你只抓了当前那一个页签"。在线表格常按月留快照页签（`2026年0512 / 0601 / 0701 / 0801 / 0901 / 1015` 这种命名），一份就补齐整条趋势。

- 抓任何 sheet 前，**先报同簿的页签清单**（这一步几乎零成本），并写进 Checkpoint。
- 补历史页签时，**必须逐个确认它是「单月值」还是「年初至今累计值」**（看表外的时间范围文字），两者混在一张趋势图里就是造假；若某页签与其他页签数值完全相同，指出它可能是副本。
- 跨月趋势只能和**同口径**的另一条线比。内销/外销这类对比若两边月份范围对不齐，就拆成两半讲（左：同期对比；右：本方自趋势），不要硬塞进同一坐标轴。
- **表格外的文字也要抓**：时间范围、口径说明、“私域试点计划（某国 N 个号、已授权 M 个、X 个好友）”这类长备注常写在数据区下方，里面埋着表内没有的关键数字。只抓表格会把它们丢掉。
- 抓取指令的具体写法（`@Browser` 开头、`sheetIndex` 语义、先读表头再按实际表头抓、双层输出、禁止 git、落盘后反向验算抓原表错误）见 `references/intranet-table-extraction-prompts.md`。

### 累计口径 vs 单月口径：仓库里那份先是哪种，先验再说

这类运营统计表常见的坑不是「只有一个月」，而是**两种口径同时存在、被当成同一种用**。典型：在线文档每个月一张 sheet、每张都是「2026/01/08 到当月 1 号」的**年初至今累计值**（看表外那行时间范围文字就知道，不是看 sheet 名）；而仓库里存的某份「月度统计」是**当月单月值**。拿单月值去讲增长趋势、或拿累计值当单月增量，都是假的。

规矩：

1. **先问口径再看数据**，两句话问清：“这张表是单月值还是年初至今累计？”和“每个月一张 sheet 还是全期一张？”
2. **建任何新数据文件之前，先 `ls` 一遍目录里已有什么**。已有同名/近名文件时先判断它是什么口径，**不要默认它就是你要的**，也不要直接覆盖。
3. **发现已有文件口径不对，改名 + 在文件头加口径声明，不要默默留着也不要删**：改成 `单月口径-xxx（仅统计当月，非累计）.tsv`，头四行写明“本表为单月口径…与在线文档的累计口径不同…累计数据看 xxx”。留在库里不标注，下一次还会被自己和别人误用。
4. **累计注释按“一期一个文件”组织**：目录 `累计快照/` 下 `累计至YYYYMMDD.tsv`，每期一份，结构固定为行=渠道（上线情况/使用情况两行）、列=国家，分期冻结不回头改历史。
5. **上线情况行只能从在线文档拿**（BI 看板只有使用数据、没有上线状态），使用情况行才走 BI 明细汇总；两行来源不同时，在文件头把来源分开写清。

### 国家列取全篇部署口径，不取数据源里有数据的那些国

BI 明细里只会出现真正有投放的国家（实测富媒体 5 国、WhatsApp 3 国、邮件 5 国），而统计表的列要跟全篇口径走（实测 13 国部署）。做法：先定国家清单再建表，没数据的国家格填 `——`，不要因为没数据就不给列——少一列会被当成“漏了一个国家”。

### BI 明细汇总对不上在线文档时，先当在线文档有错

两边逐格对一遍，差异通常分两类：

- **明显笔误**：某国某个数跟另一个国家一模一样（实测菲律宾阅读人数 = 印尼阅读人数，同一个数被复制过去了），这种直接采用 BI 算出来的值。
- **系统性偏小**：某国计划数、发送数、成功数、阅读数全面低于 BI，不是取整误差，而是统计口径或时间边界不同。这类**不要自己择一，也不要求平均**——问一句“这张表当时是从哪个报表、什么口径取的”，确认不了就以 BI 为唯一数据源重出，并在交付说明里列出差值。

汇总时**国家字段为空的行必须单列开**（实测一笔 340 万发送量国家为空），不要默默算进总数、也不要随便归属到某国：单独占一列「待归属（国家为空）」或单独标注，并写清来源日期，让用户拍板归属。

**重算前先验证自己没漏国家**：用明细按日期区间汇总后，把各国数值加总跟全期总数对一遍；对不上先查是否有空国家、拼写差异（`马来西亚` vs `马来`）、以及日期字段是否带时间戳。


## 改完一个数，跑一遍全篇数字残留扫描

同一个业务数（好友数、导购数、完成率）会散落在多页：封面、私域工作台、资产页、私域 2.0、KR 对照，**任何一处没同步都是会上被问的点**。给 python-pptx 写个小探针，改完就扫：

```python
# /root/venv-ppt/bin/python
KEYS = ["59,609", "60,920", "107", "108 名", "11.9%", "12.2%"]
for i, s in enumerate(Presentation(f).slides, 1):
    blob = " ".join(sh.text_frame.text for sh in s.shapes if sh.has_text_frame)
    hits = [k for k in KEYS if k in blob]
    if hits: print(i, hits)
    if "旧值" in blob and "新值" in blob: print(i, "⚠ 同页并存新旧值")
```

两种要抓的病灶：①老值还有残留（说明某页漏改）；②同一页新旧值并存（说明只改了一半，读者会看成"数字打架"）。扫完再改，比人眼翻 29 页可靠。

**③ 明细口径改了、合计口径没跟着改（最隐蔽的一类，报告内部自相矛盾）。** 同一指标常有两个数据源：矩阵汇总表（按国家分组的快照，某渠道可能只覆盖 3 国）和明细表（逐条记录，同一渠道实际有 5 国）。给邮件卡按明细改成「5 国」之后，四渠道合计若还沿用矩阵那个 3 国的邮件数，两个口径就在同一份报告里打架——差的那两国（埃及、缅甸）恰好就是有人会去加的。

规矩：**改任何一处渠道口径，把全文所有引用该渠道的合计重算一遍。** 做法是从明细表逐行加总取新值，不要沿用汇总表的旧值；改完给出「逐国明细 → 渠道合计 → 多渠道总计」的三级算式贴在交付说明里，让用户能自己加一遍。选定一个数据源后全文统一，不再混用——混用比全用旧值更糟，因为它看起来是新的。

**分渠道的剔除规则要对称，但允许按数据性质不对称。** 明细里会有无国家标注的行（测试投放、跨区投放）：某渠道剔了、另一渠道没剔，会被问"为什么不一致"。判断依据是**这行是否已被该渠道在页面上展示的总数包含**——已包含就保持不剔（否则合计和该渠道卡片对不上），是纯测试数据则剔除，并在口径页写明剔了什么。

### 按月快照 Excel（渠道 × 国家 × 六期）的定稿格式与配色

用户要的是「每期一张 sheet、渠道分块、指标分行、13 国横铺」，不是长表。已定稿的结构：`说明与口径` + 六期 sheet（2026-05-31 / 06-30 / 07-31 / 08-31 / 09-30 / 10-31）+ `明细长表`。

**配色必须沿用已有版本，不要自己换**（本次擅自换成蓝色系被打回，用户原话「怎么改了样式，不是黄色的列吗？和之前的保持同步呢」）：渠道块标题 `FDE9D9` 浅橙 / 表头 `F4B183` 橙 / 指标名列与合计行 `FCE4D6` 浅橙 / 未上线国家列 `FFF2CC` 浅黄。未上线国家在「上线情况」行与数据行都要铺浅黄，合计不计入。

每个渠道块固定四行头：块标题 → 指标+13国+待归属 表头 → 上线情况行（写上线月份，未上线写「未上线」+浅黄）→ 指标行（富媒体 8 项含点击、WhatsApp 6 项无点击、邮件 8 项、短信 4 项）→ 发送人数合计行。

**三个抓数后必须核对并写进说明页的坑**：

1. **「国家」下拉 ≠ 上线国家**：它反映的是该时间范围内**实际有投放记录**的国家。实测富媒体国家数 3→3→4→4→4→5，而菲律宾 2025-12 就上线、富媒体到 2026-07 才有量，越南 2026-08 上线、富媒体到 2026-10 才出现。表格里已上线却为「—」的国家属正常，不是数据缺失，必须在说明页举例写清，否则会被当成漏抓。
2. **待归属六期恒定不涨**：富媒体恒 3,403,847、邮件恒 57。累计口径不可能不动——根因是这批国家为空的记录**没有「发送日期」字段，日期筛选对它们不生效**，被原样带出。占富媒体总量 0.46%，不影响结论但要在说明页标注。
3. **埃及邮件 139 万发送、0 成功**：量级与 0 成功率并存，不像真实业务，报告引用前先向供应商/短信中心核实邮箱数据源。短信渠道六期恒为「印尼 1 条计划 4 人」，是残留脏数据，不能当业务事实讲。

**跨期校验加一条**：同一国家同一渠道的累计发送人数必须单调不减（5/31 ≤ 6/30 ≤ … ≤ 10/31），出现回退一定是抓数或口径错，不许当成业务波动抹平。

**期次写法（用户 2026-11-05 纠正）**：这类表是累计口径，期次列一律写**完整区间** `2026/01/08 ~ 2026-05-31`，不写 `2026-05-31`——只写单日期会被当成「那一个月的数」。Excel 的 sheet 名同步用 `截至2026-05-31`，不用裸日期。

**列宽与小数字号（踩过）**：上亿的数（如富媒体累计发送 740,934,490）在列宽 11 时 Excel 直接显示 `########`，会被误认为空数据。国别列宽给 **≥16**，明细长表数值列 14~16。

**同一份数据出两个形态**：Excel 矩阵版给人看（保留颜色、合并、上线情况行）；TSV 长表版给程序/分析用（一行一个「区间 × 渠道 × 国家」，空值为空串、比率为小数）。矩阵直接转 TSV 会把合并与样式全丢掉、还变成大堆空格，不要那么干。

**趋势图：不能把四个渠道画进一张图。** 实测富媒体累计 7.41 亿、邮件 2314 万、WhatsApp 23 万、短信 4 人，量级差六个数量级，同图会把小渠道压成底边一条直线。正确做法：**每渠道单独一张「柱（发送人数）+ 折线（成功率/阅读率，副轴）」组合图**；另加一张只有百分比量纲的三渠道成功率对比折线；**短信量级太小直接不出图**，在说明里写清原因。副轴在 openpyxl 里要显式设 `axPos="r"`，默认是左侧会盖住主轴。

**累计相减求单月：只能当参考，不能当交付。** 相邻两期同起点的累计值相减确实能得单月量（实测与直接拓展单月完全一致、差值 0），但它有两个硬伤：①**计划数相减无意义**（计划 id 按期去重，跨月计划会重复/漏算）；②无法自证是否被 BI 中途重算过。要单月就**直接拓展单月区间**（日期筛选填该月 1 日到末日，国家筛选仍用「使用全部」），并做一项强自检：**Σ月度单月值 必须等于 累计至最大值 的对应值，误差 0**。

**单月趋势出现断崖先当真实业务波动，但要标注释。** 实测富媒体 6~10 月单月：1.22 亿 → 2.13 亿 → 3395 万 → 8940 万 → 8550 万，7 月一个尖峰、8 月回落。直接拓展核实差值 0，说明真如此（集中大促后的回落）。出图时在尖峰点标一句，否则看图的人会以为是数据异常。

## 上线报告的五段结构（2026-10-22 用户定义的叙事版）

用户要求把上线报告改成这个顺序，**顺序不能换**：

1. **需求背景**（当初为什么要做——缺口、现状数据）
2. **需求内容**（提了什么、本期范围是什么）
3. **需求价值**（预期价值，需求方口径）
4. **价值达成情况**（实际做到什么程度）
5. **附件：产品功能实现**（交付清单/功能对照，放最后当附件）

**这份报告的叙事目的**：清楚呈现「**需求已提、产品功能已交付、价值未达成**」——把「价值没达成」与「需求/功能交付」分开讲，价值缺口归因到落地与运营侧（用户原话：“主要是体现我需求做了，产品功能提供了，但是价值没达成，运营的锅”）。

**写第 4 段的三条硬要求**：
1. **必须带可核数据**（功能使用次数/使用率、触达计划数与触达量、覆盖率）——只写「价值未达成」会被反问“依据呢”，有数据这页才立得住；
2. **归因要有落点**：哪些是使用侧的原因（没人用/用得少）、哪些是执行侧（执行频率/覆盖度），用数据分开写，不要写成情绪结论；
3. **数据从哪来**：常在生产环境的数据报表页（内网、需登录态）——让 Cursor 内置浏览器只读抓取，不自己估数。

**开场先定数据需求**：动手写前先把「要哪几类数、从哪张报表抓」定下来，否则写到一半发现不够还得重抓（用户会主动说“明天需要收集数据”）。

**第 4 段的五种“拿得住”的证据形态（实战验证，写之前先看有没有这些）**：

1. **使用量差几个数量级**——四个渠道能力都交付，但累计发送量从几亿到个位数，一句「能力交付与使用量差 4 个数量级，主因在使用侧」就是最硬的归因句（比任何形容词都硬）。小到个位数的渠道定性写“上线后未投用”，不写“失败”。
2. **成功率与阅读率反向**——高成功率的渠道可能没人读（邮件），最该用的渠道（按阅读率排第一）使用量最小；这页直接把“能力没问题、选择与执行有问题”讲通了。
3. **累计 vs 近 30 天两期并列**——同一指标累计值明显低于近期值 = 通道/配置在改善。写法：两期并列 + 净变化（pct 点），比单点数字有说服力。
4. **失败归因（发送状态归因页签）**——**先跨计划汇总再算占比**：页签是行级明细（一行 = 某计划下某明细状态），**行内占比不能相加**，要按「明细状态」求和人数后自己算占比。常见结果：**“无回执”往往是最大项**，而不是“统一频控”——没汇总就下结论会把归因写错。归因分两层写：通道侧事实（无回执 / 短信中心无数据 / ID 转 clientId 失败）+ 策略侧事实（统一频控，可调）。
5. **覆盖 ≠ 使用**——单开一页：部署 N 国，但**有触达量的只有其中少数几国**，且同一渠道在不同国家成功率可能差两三倍。这类差异归因到各国运营执行，不讲成能力差异。

**“按国家拆”不用重新抓数**：运营计划统计表本来就带「战区」「国家」列，抓下来的 TSV 直接按国家 group by 求和即可（发送/成功/阅读），再算成功率与阅读率——比回看板逐国筛一遍快得多，也不引入新口径。

**KPI 口径说明必须随数一起抄**：各渠道的“发送人数”口径不同（富媒体过滤“系统个性化开关关闭”；邮件过滤未绑定邮箱；WhatsApp/短信还会叠加未登录、未绑定手机号），“阅读人数”指进入消息详情页。不写口径直接上页，评审一句“这数怎么算的”就卡住。


## 交付状态与截图取材：写之前先把「已上线 / 今日上线 / 策划中」钉死

上线报告最容易出、也最伤的一类错，是**把还没上线的功能写进「已交付」，并拿它的原型设计稿当已上线系统的界面图**。用户会当场点破：「用户行为还没上线，还在策划阶段」「你的产品功能截图都用的是我们本次做的策划中的产品设计图」。

动手前定三态，逐条列给用户确认，**不要自己判**：

| 态 | 含义 | 能放哪 |
|:--|:--|:--|
| 已上线 | 代码上线且至少一个国家在用 | 需求内容 / 交付清单 / 产品设计方案截图页 |
| 今日上线 | 当天首日上线，无数据 | 交付清单（标日期）；**只列上线后观察指标，不下达成度结论** |
| 策划中 / 评审中 | 只有 PRD/原型，未开发 | **只能进「后续规划」页**，状态写「策划/评审中，未上线」；不计入交付、不作价值达成依据 |

- **截图取材**：产品设计方案页**只放线上系统的界面截图**（生产/验收留存，含真实菜单与数据）；策划中的原型稿、线框图**单独成页或干脆不放**，绝不与已上线界面混排——混排等于对外宣称这些已经交付。
- **同一功能在「交付清单」和「价值达成」两处会各写一遍**，改状态时两处一起改（功能清单表 + 交付能力表），并 grep「已上线 / 已交付」全篇复核。
- 交付清单顶部写一句判定口径（"代码完成且至少一国在用 = 已上线；只有方案或未验收的一律不计"），评审被追问时这句话就是依据。

## 国家口径与「近期没有计划」：权威源是《26年Q1-Q3运营盘点》

国家维度的事实不再从 1025/1027 旧稿推导，改以公司文档《26年Q1-Q3 运营盘点》（`docs.vivo.xyz/i/<id>`，需内网登录，按渠道组织：触达计划 / 卡券 / whatsapp私域，带国家矩阵表）为准。让 Cursor 内置浏览器只读抓取即可。

**口径钉死：14 国 = 13 国 + 印度。印度长期只做线下运营，所以统计表里写「覆盖 13 个国家/地区」不包含它**。报告写 14 国时在页脚注明这个构成，否则会上必被追问。

文档给出的三类事实（2026-11 实测抓取）：

| 分类 | 国家 | 原文口径 |
|---|---|---|
| 全部未使用（7 国） | 中国台湾、缅甸、柬埔寨、中国香港、新加坡、肯尼亚、埃及 | 「覆盖13个国家/地区，但有7个国家/地区全部未使用」 |
| 部分未使用（2 国） | 孟加拉、越南 | 「2个国家/地区部分未使用」 |
| 近期没有计划 | 越南、中国台湾（短信）；孟加拉（私域） | 「短信中心反馈：使用人少，质量差，暂不建设」；孟加拉「将暂停孟加拉授权，直到 Q4 底开始灰度切换」 |
| 渠道条件不具备 | 泰国、菲律宾、缅甸（WhatsApp）；孟加拉（富媒体） | 「未上线（泰国不用 whats）」「未上线（菲律宾主流社媒不是 whats）」「未上线（CMS 未对接）」「未上线（短信中心反馈：目前手机版本不支持）」 |

**「未上线（原因）」不等于「近期没有计划」。** 只有原文写「暂不建设」「暂停…直到 Q4」的才能归入第三类；写「不用 / 不是 / 未对接 / 手机不支持」的是**客观条件不具备**，两者混成一类，汇报时一句「凭什么归这里」就答不上。归因页就把它们拆成两行（「近期没有计划」+「渠道条件不具备」）；老板只要三类时，把「渠道条件不具备」当作第四行补充，不要硬塞进三类里。

**「暂不建设」就等于「近期没有计划」，不要跟用户争这个同义问题，也不要在页脚加口径注**——用户原话「没什么可争执的」。直接按老板要的第三类说法落页。

**私域授权进度是最硬的运营侧证据，优先用它替掉笼统说法**：马来 39/88、印尼 66/290、孟加拉 2/30（原文另有「授权进度相对较落后」）。比「导购缺可用号」这种描述有力得多。

**授权进度这类「号数/授权数」必须按原文表格的列序取值，不要用 agent 整理的提取表。** 同一份文档里，Cursor 输出的结构化提取稿把马来与印尼的数字整段串了位（写成马来 66/290、印尼 39/88，与原文表 2 的列序正好相反）。判法：拿表格还原稿（原文 Markdown）的列头顺序逐个对位，再回原文行 grep 该数字，看它前面紧跟的是哪一国；两个来源冲突时**永远以原文表格列序为准**，提取稿只当作已归类的线索。

**数字格式异常先还原，别急着判数据错。** 看到「发送人数：5,7005492」这种千分位错位的值，先还原成 57,005,492 再验逻辑（57,005,492 > 成功 13,884,216 > 阅读 1,914,920，且 1,914,920 ÷ 13,884,216 = 13.79% 与原文阅读率一致），否则会把好数据误判成「成功数大于发送数、逻辑不成立」，被用户当场纠正。

**真正的串位靠两个信号抓**：①同一张表里两个不同国家出现完全相同的长数字；②用该行自己的比率反算对不上（实测菲律宾「阅读人数 3,336,781」与印尼同值，而 23,440,552 × 25.81% ≈ 6,050,000，差近一倍——这个数是印尼的，被复制过去了）。命中任一条就标「待业务核」，**不要自己择一或改数**，也先别把该组数据搬上页。

**别指望从这份文档拿季度维度**：它按渠道组织，没有「按国家 × Q1/Q2/Q3」的动作表。一开始就要求 agent 输出三列季度动作，结果全是「页面上无此项」，白抓一轮——要季度维度得换材料。软文里的数字也照原样带错（实测「发送人数：5,7005492」千分位错位），引用时标注原文如此。

**改归因页之前必须拿到全量文件并逐行核——聊天里的精简清单不算数据到手。** 实测 agent 本地落了 37 行提取表、聊天里只贴了 27 行样例；拿样例直接改页面，漏掉的那几行恰好就是会把国家归错类的原文（「暂不建设」与「未上线（原因）」混成一类）。固定顺序：**要全量 → `git pull` 拉下来逐行核 → 先报「原稿哪些对、哪些错」 → 再动手改页 → 交付时说明改了哪几处、依据是原文哪句**。跳过这步会被问「能不能先拿信息后，你再动手？」，而且改完整轮作废。

## 证据链必须随版落盘（每个新版产出后立刻做，不能等被问）

用户会直接批评："我们输出这些 PPT 前做的证据链材料都找不到了，或者说没沉淀好，这是不对的。"真正的问题不是没材料（1025 待补数据清单、BI 明细 TSV、累计快照、口径字典都在仓库里），而是**材料挂在旧版本上、新版没有逐页账**。

规矩：每交一版 pptx，同目录同步交一份 `<版本>-证据链.md`，四块内容：

1. **逐页来源表**：页号 / 标题 / 来源 / 状态。状态只设三种：`原文搬运`（整页贴图或逐字照搬，标原稿页码）、`重绘有出处`（版面新做，文字指回原页）、`推导`（无原文、需业务侧确认）。推导项必须单列清单，上会前逐个拍。
2. **关键数字溯源索引**：数字 / 出现页 / 数据文件路径。BL 明细、累计快照、口径字典都给绝对相对路径，别只写"BI 看板"。
3. **未闭环清单**：把旧版待补清单里仍未拿到数据的条目，按新页码重新挂一遍（页码会因重排而变化，直接沿用旧清单必错）。
4. **口径文件索引**：术语字典、口径差异说明、明细数据目录。

生成器里页序＝代码块顺序，来源映射可以脚本抽：`grep "keep_original(" 生成器.py` 得到「原稿页号 → 新版页号」对照，重绘页再逐个手填来源（这是必须人工定的一步，按页标题对原稿）。同时更新同目录 README 的版本索引，让下一个人一进目录就知道哪个是当前版、证据在哪个文件。

**同一份报告的多个版本会并存**（1024/1025/1027/1104 同时躺在目录里），证据链文件名带版本号，不要写成 `证据链.md`，否则下一版一覆盖就又把旧的弄丢了。

## 上线报告 PPT 骨架（从0到上线全生命周期）
1 项目概览（背景/定位/目标）
2 需求（业务方/场景/已确认清单）
3 方案与设计（架构/信息架构/关键流程/外销特有：多语言多站点权限）
4 迭代历程（时间线里程碑/每期交付/关键决策与回退——重头）
5 技术实现
6 测试与验收（特性测试/用例评审/回归/bug 数）
7 上线与运营（发布流程/数据迁移/回滚预案/监控）
8 成效与后续（有数据才放/遗留/二期）

**红线**：只放能从 PRD/测试/验收客观推出的结论，不编用户数/运营数据，避免被一问穿帮。
