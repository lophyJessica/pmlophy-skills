# Frontend UI Audit Loop（前端 UI 审计-修复-部署闭环）

## Overview

用户（路飞）的 forge 系项目用 Codex/Cursor 等 AI agent 做前端改动，杰西卡（Hermes）负责出指令、核验、部署通道。本 skill 固化这条链路里反复踩坑后沉淀的做法：**指令怎么写、代码怎么核验、部署怎么把关、实测怎么定位**。

**开工前先加载本 skill，别做到一半被用户问「不是有个 skill 吗」**：凡是 UI 审计、规范整治、前端交付核验类任务，第一动作是 `skill_view` 本 skill 加 `pm-deliverable-audit`（分维度对照 + 阻塞/中等/低分级），再动手写指令。凭印象直接写，必然漏掉 skill 里已经沉淀的步骤（指令入目录按 NN 编号、逐文件行号清单、分批顺序），然后被当场纠。

**「复刻提示词模板在哪」这类问题也算，不要先去文件系统里翻**：本 skill 已有 `templates/legacy-clone-prompt.md` 和课件原文路径，逐盘搜 /root/notes 之类属于白做功；实测先搜了文件系统、被用户纠一次，回到 skill 里发现早就存着。

## 设计稿对齐（数值白箱法：量取一次，写死指令）

agent 拿设计稿做 UI 却反复走样（胶囊做大、箭头漏渲染、状态栏细节错）时，不要一轮轮「再看图理解」——那是让它每次重新估尺寸，每轮都不一样。正确做法是**父会话逐像素量取标准值一次，把数值白箱化写进指令**，agent 只做填空：

1. 父会话用 vision_analyze 带精确提问逐项量取设计稿（问题要具体到「多少 px、什么字重、相对屏幕宽度比例」，摘要式提问量不出数值）；设计稿是 2x/3x 样机时先用原图像素尺寸折算逻辑 pt。
2. 把规格写成「组件 — 属性: 值」的逐行清单放进指令（如：导航栏高 44px；胶囊 87×32px 圆角 16px 描边 0.5-1px #E5E5E5；箭头单 chevron 笔画 2px 圆头 9×15px；标题 17px/600/#111）。
3. 指令红线写「逐值照做，不做自行估算；只改这些数值与缺失元素，不改结构」。
4. 验收拿用户实测截图与规格逐值对，差值超过 2px 即打回。

**agent 自检表与用户实测冲突时，要求运行时证据，不接受再次自报**：自检表连续与实测对不上时，下一轮指令要求它交「console 输出 / computed style 读数」这类运行时证据（如 `typeof route.meta.homeTab` 在目标路由下的实际值），同时交判断代码片段。只报「已修复」不算交付。

**前提是 agent 的代码要能被父会话读到——分居两机时先解决可见性**：agent 在用户机器上改、父会话（VPS）只能靠 `git pull` 读代码，agent 不 push 时父会话完全靠截图猜，诊断成本翻倍。长任务收尾必须让用户验收满意后让 agent push 一次基线，中途诊断轮不能 push 也要说明「本轮结论基于截图+汇报」。

## 铁律（违反 = 返工）

1. **审核字样红线（用户 0828+0830 定稿）**：前端永不展示任何"审核/抽查/待审核/转审核"字样、状态徽章、菜单入口或操作按钮。审核能力仅后端预留（review_status 等字段保留），路由与组件文件保留但从导航隐藏。写进每条前端指令的红线。涉审核 UI 的缺口项一律搁置，在自检报告标注"按审核字样隐藏口径搁置"。
2. **指令五段式 + 部署通道**：Context/Request/Output format/红线禁止/Checkpoint。管道命令（rsync/curl 上传）必须逐字写进指令，不能只引用 AGENTS.md。指令文件存项目的提示词目录——**目录名各项目不同，不要照搬**：cms-project 是 `05-提示词合集/`，forge 系是 `prompt/`，动手前先 `ls` 看现有最大编号再续号，空目录从 `01` 起。`NN-名称-指令.md` 格式严格续号。写完 commit + push，别只在聊天里发一遍，否则下次没人找得到。
3. **"已部署"不可信**：agent 自报 ≠ 部署。核验先 `git pull` 实锤代码，再 grep dist bundle 内容特征，再验远端。**报告里整段粘贴的「改后代码」同样不可信**——它贴的是它打算写的内容，磁盘上的文件可能一个字没变；只认 `git pull` 后当场 `grep` 出来的实际文件内容。agent 用自带 git 面板提交时还会静默漏文件（面板只勾了部分改动），表现为连续几轮报告都说改完了、远端仍是旧内容；此时改走命令行 `git add -A` 一把全收，别再用它的面板。工作区有多个 agent 并行时反过来，必须逐文件显式路径 add（见并行一节）。
4. **先核验后部署，用户拍板**：用户认可后才执行 deploy；不认可则 `git reset` 回滚零残留。多 agent 并行改动可合并为一个 commit，但必须先全部核验。
5. **报告代传兜底**：Codex 沙箱 DNS 不解析项目域名 → 报告留 check-reports/ 由杰西卡 VPS 代传管道，禁止重试。

## 核验清单（部署前逐项 grep 实锤）

```bash
# 1. 代码实锤（不信报告）
git pull && git log --oneline <prev>..HEAD
grep -n "<新功能关键代码>" <改动文件>

# 2. bundle 特征（部署后）
curl -sk https://<域名>/ | grep -o 'index-[A-Za-z0-9-]*\.js'   # 确认新 hash 上线
curl -sk https://<域名>/assets/<新hash>.js | grep -c "<关键字符串>"  # 特征进产物

# 3. 红线扫描（前端零命中，注释/枚举定义除外）
grep -rn "审核\|抽查" frontend/src/pages/ | grep -v "//"

# 4. 历史报告/指令里的旧路径是存档不改；活指针(AGENTS.md等)必须同步
```

## 单一来源模式（UI token / 样式 / 规范）

- UI 标准唯一维护处 = 仓库根目录 `UI-DESIGN.md`，AGENTS.md 只留指针。
- 跨页共享样式（如筛选区卡片）必须在 theme.ts 定义**单一 token**（如 `FILTER_CARD_STYLE`），所有页面引用，禁止页面自写平行样式。
- 全站批量改时：一条指令覆盖全部页面清单（逐文件列行号），防止"改了这页忘了那页"。

## 复刻件的规范对齐边界（用户纠正过一次，别再抬标准）

复刻原型是**给评审看的演示件，不是上线系统**。用户原话：「没必要那么严谨吧，我们只是复刻一个…支撑原型评审的演示的使用」。

**做到这一步就停**：

- 只对齐能让页面「看着像那么回事」的几处：主色、正文色档位、按钮圆角、语义色（成功/错误/警告各一个值）。改完这三四类就算齐。
- **不做**：全量色板补齐（设计稿上百个颜色不要逐个写进规范）、组件清单补到设计稿数量、逐值对设计稿出完整 gap 对照表。取证做到能回答「差在哪几类」即可。

**判断两套颜色体系是否脱钩，看档位不看单值**：拿设计稿的语义色档位（如正文 80/60/40/20 四档）对照代码实际用的透明度列表——代码里出现档位外的值（0.65/0.45/0.35 这些）就是两套体系，别逐个值纠结谁对。这种情况下规范文档往往把代码现状抄了下来，而不是设计稿口径。

**但“规范按设计稿写”与“代码归并到哪个值”是两件事，别混**：规范文档该记设计稿口径（正文就那四档）；而代码侧做归并时，**语义色 base 的基准取项目现状高频色，不取设计稿值**（见下文「语义色基准由用户拍板」）。一边是“规范怎么写”，一边是“代码收敛到哪个值”，二者不矛盾——“把所有绿都改成设计稿那个黄绿”是项目级换肤，不属于规范整治。

**用户说「先不着急」就是不要开工**：这类规范对齐属于随时可做的收尾活，不要因为手上有取证材料就自己推下去。

## UI 规范整治：先审计，再按数据定范围

整治样式前先出一份全量取值分布审计（颜色/圆角/字号/字重/间距/边框/阴影/组件），**不要凭印象列一张手写映射表就开工**——手写的往往只覆盖颜色和圆角，漏掉阴影、字重、间距。

**判读审计数据的三个关键指标（比"有多少个取值"重要得多）**：

1. **一次性取值占比**：某个维度里「只出现 1 次」的值占多大比例。实测一个原型 204 个色值里 109 个只出现一次（占一半）、真正高频的只有 16 个——说明大头是随手写的噪音，归并掉几乎没有视觉风险，这部分可以当第一刀。只看"204 个颜色"会高估工作量。
2. **组件文件数 vs 路由页面数**：两者差距悬殊就是"没有公共组件层"。实测 7 个组件对 19 个页面时，分页在项目里有七套独立实现、各写各的样式，才会出现"有的页面正常、有的页面文字折行"。这类问题的修法不是逐个补 CSS，是抽公共组件。
3. **四角独立写法列表**：`border-radius` 出现 `0 8px 0 8px` 与 `0 6px 0 8px` 并存 = 同一类形状写了两个值，纯手误；这类矛盾值一眼就能定位。

**中文逐字折行是布局约束缺失，不是样式丑**：单选框选项被压成「激/活」竖排、分页按钮「上一页」折成两行——根因是 flex 子项没 `white-space: nowrap`（父容器 `flex-wrap: wrap` 时被压窄），或固定宽高的图标按钮里塞了文字（如 `width:32px;height:32px` 的 `.pager-btn` 既当图标按钮又当文字按钮）。**先归因再修**：加一行 nowrap / 给文字版加个宽度自适应的变体，修一个类名全站生效；不要逐页调 padding。

**数据量撑不起控件时控件该隐身**：总条数不超过一页仍渲染每页条数选择器 + 页码 + 上下页，这些控件全是死的。条件渲染缺失，与样式无关，单列一条。

**反过来，要让分页控件可见可验收，mock 条数必须大于默认 pageSize**：抽完公共分页组件后如果各页 mock 都只有一页，控件全部隐身，等于没法验收，只能靠读代码判断对错。做法不是去找一个天然多页的页面，是直接把 mock 补到能翻第二页（用户原话「加 mock 数据不就好了吗」）。**这条对每个接分页的页面都成立：mock 条数 > 默认 pageSize，至少两页**，并写进 mock 文件顶部注释当规范。补 mock 的边界：① 数据要像真的业务数据（真实活动名/国家/埋点名），不许 `test001`、`aaa`、`111` 这类占位值——评审会看到，一眼假；② 状态铺开（草稿/审批中/已通过/已下发/已结束/超时/驳回），不要全启用；③ 时间散在近两个月，倒序排列时看着自然；④ 原有边界样本（属性数为 0 那条、按钮置灰那条）原样保留，别为凑数改掉。

**走 IndexedDB 种子的列表，补 mock 后必须 bump 种子版本号并清站点数据**：这类数据不是直接从 mock 数组读，是先灌进 IndexedDB，刷新只读库不重灌。种子版本号（如 `PLANS_SEED_VERSION`）不变，加了数据也看不见，会被误判成「补的 mock 没生效」。交付说明里要写明「本次 bump 了种子版本，测之前先清站点数据」；自己实测时也要先 `indexedDB.deleteDatabase('<库名>')` 再重载。

**抽公共分页组件的标准形态（可直接复用）**：① 只有一条判据 `total <= pageSize` → 仅渲染「共 N 条」，容器高度与右对齐保持不变，否则列表底部会跳一下；② 多页时从左到右：共 N 条 → 每页 10/20/50/100 → 上下页 → 可选页码 → 可选跳页，跳页与页码做成可选 prop（各页原始设计不一致，统一反而算改需求）；③ 上下页用图标按钮，**32×32 定宽定高里不要再塞「上一页/下一页」文字**——那是折行的根因；④ 跳页值夹到 `[1, totalPages]`，Enter 与 blur 都提交；⑤ 抽完逐页说明「每页条数档位有没有变」：本项目从 10/20/30/40/50/100 统一成 10/20/50/100 属行为变更，必须主动报给用户，不能当纯重构交付。

**分批顺序按风险递增，不要一次性梭哈**：① 一次性取值归并 + 野值归位 + 阴影收敛（几乎无视觉变化，低风险）→ ② 高频 token 对齐设计稿（会真的改变观感，需逐页看）→ ③ 抽公共组件（改结构，与①②撞文件，必须排在最后）。间距体系建议不动——改了整页布局会变，收益抵不上风险，在规范里承认它存在即可。抽组件前先出一份方案（抽哪几个、按什么顺序、每个改哪些页面）给用户拍板，不要直接开抽——十九个页面共用几个组件属于结构级重构，边抽边想必成半成品。

**阴影必须先归并，颜色归并必须显式排除 `box-shadow` 属性**：审计里"非标黑透明度有几十种"这个数字大半是虚的——`rgba(0,0,0,0.12)`、`0.18` 这类值绝大多数来自阴影，不是文字色。若把颜色和阴影一起按档位归并，阴影会被压重、卡片层次直接塌。指令里写死这条边界：颜色步骤只处理 `color` / `background` / `border` / `fill`，`box-shadow` 里的颜色一律不碰，由阴影步骤单独收敛。**验收同理：档位外的值先查它是不是阴影自己的颜色**——`grep 'rgba(0, 0, 0, [0-9.]+)'` 全量数出来的残余值，先看数量对不对得上某类阴影的实例数（实测 8 个 `0.12` 恰好等于 B 类阴影的 8 处），对得上就是阴影颜色，不是漏改的脏值。直接按「档位外一律不达标」判会误伤，也会让 agent 去改本该保留的东西。

**四角写法是 `border-radius` 里容易误伤的坑**：`border-radius: 2px 2px 0 0` 这类多值写法会被单值正则一起匹配到。归并清单必须显式排除多值写法，并在指令里点名本轮不处理哪些（表格顶角、50%、999px 等），否则 agent 会把它们压成单值，圆角形状直接变。

**逐文件待改数表是最有效的防漏手段**：把「文件 → 待改处数」列成表并给出合计，要求 agent 交付时逐文件核数字。只写"全部 .tsx/.css"必然漏页。加上"合计 N 处，改完核数一个不差"这句才算闭环。

**表里的数字必须自己重跑命令数出来，不许拿第一次 grep 的输出目测**。第一批统计用的正则往往比"真正要改的形态"宽（没锚分号、会连多值写法一起匹配），逐文件数就会偏；而对照表一旦偏了，agent 照着核反而得出"我漏改了"的错误结论，白返工一轮。做法：写完清单再跑一条更严的正则复核——单值改动用 `border-radius: *(2px|5px|7px);`（结尾锚分号）而不是 `border-radius: *[0-9]+px`，多值写法单独一条命令数，两条合计对得上才写进指令。

**缺计数器/必填星号这类「内销同款」小件，按规范库落，不靠 agent 每次』看图参考』**：用户会把内销截图当参照（如输入框计数器 0/20、必填红色星号），agent 每轮「参考图实现」必然走样。正确做法是把这类小件固化进仓库 UI 规范库（表单节：星号颜色 #f5222d、提示/占位 12px 同级、计数器右下；规范库中文档为准），指令里只引用规范路径 + 要求自检表加对应核对行——规范库是唯一真源，图只用在第一次提炼时。

## 多 agent 同工作区并行：先禁止，再谈隔离

**首选是不并行。** 一个 git 工作区同一时刻只许一个 agent 写源码——要真并行就各自 clone / 独立 worktree，产出回主干前人工合。实测撞车：Agent A 改完一批 CSS 并 `git add`，Agent B 同时在同工作区读同一批文件并整体写回，结果暂存文件全变 `MM`（暂存区是 A 的快照，工作区已被 B 改写），A 提交的 commit 虽然干净，**工作区里 A 的改动可能已被抹掉**，后面谁再提交就是倒退。还多出几个没人认领的改动，无法归因。

**`git add` 不是隔离手段，只是快照。** 它冻结 commit 的内容，挡不住后一个 agent 改工作区。别把「我提交的是 add 时刻快照」当成隔离成功——要验的是「上一刀的目标值现在还在不在」，而不是「commit 里的 diff 长什么样」。

审计类（只写 md）和改源码类可以并行；两个都写源码的必须串行。

**「我在 VPS 上改、agent 在用户机器上改同一个文件」是最容易漏掉的一种撞车**：两边都已写进文件、都未提交，谁先 push 谁成功，另一个直接 non-fast-forward，`stash pop` 还会 `both modified` 冲突。分派文档类任务给 agent 之后，VPS 侧不要同时动同一份文件；已经撞上了，先让用户那边 commit + push（他的改动通常更完整，因为按完整指令跑过），VPS 侧 `git stash drop` 丢弃自己那份，再逐条 grep 核对内容是不是真覆盖齐全，不要反过来让用户丢他那份。指令抬头要同时标「执行者 + 工作区」，只写工作区不够——用户手上同时开着 Cursor / ZCode / 反重力，粘错窗口是常事（实测把给 Cursor 的指令给了 ZCode，两个工具在同一份源码上撞车）。

**并行已发生后的善后顺序**：① 让人把还在跑的 agent 全停掉（只有用户能停别人的会话）——若那个 agent 的任务本身是对的、停不得，就让它跑完再动，中间谁都别碰 cms；② 只留一个 agent 做只读清点——`git log --oneline -6` / `git status --short` / `git stash list` / `git diff --cached --name-only` / `git diff --stat`，全程禁 add/commit/checkout/reset/stash；③ 清点结果 push 上来，自己 pull 核，**不要根据三方汇报拼事实**；④ 确认那个 commit 干净后立刻 `git push` 固定成果（push 不动工作区、不影响还在跑的那个 agent），再回头处理工作区那堆改动。顺序反了会把可回退的点一起搞丢。

**判断工作区是「回退」还是「在已提交版本上又加一层」，看行数比，不要逐行 diff**：已提交版本改了 N 处，工作区 `git diff --stat` 显示 M 处——M ≈ N 且方向相反 = 前一刀的改动被覆盖回退了，是灾难；M 远小于 N = 只是又叠了一层同类替换，已有成果没被破坏。实测 N=407、M=60，一眼就能定性，省一轮逐行比对。

**撞车后别再补截图取证**：工作区代码此时已经改过一轮，此刻截的「before」不是改前。要真改前基线只能 `git show <已提交第一刀>^` 取代码另起 worktree 再截。不做这一步，整组改前改后对比是假的，表现为 agent 反复调 Chrome headless（路由写错、profile 冲突、页面没渲染）却始终得不到有效对比——那是前提已经错了，不是截图工具的问题。

并行无法避免时的取数纪律：

- 每批改动完成后**立即逐文件 `git add` 显式路径清单**，逐个列全。禁用 `git add -A` / `git add .` / 通配符。
- add 完必须贴 `git diff --cached --name-only`，证明暂存区恰好是预期那几个文件；数量对不上就停下查，别继续提交。曾出现「归档提交只带 4 个文件」却没先确认上一批 12 个还在不在暂存区的情况，无法判断隔离到底做成没做成。
- 明确排除不入库的：`dist/` build 产物、`_tmp_` 前缀的脚本与中间数据、基线 txt。
- 提交前先收拾一次：`_tmp_` 脚本删、可复用扫描脚本改名正式化留下、截图合并到 `08-相关资料/审计报告/<任务名>-截图/` 并带「改前-/改后-」前缀。

**替换量的自证法（很强的一招）**：`git diff --cached --stat` 的 insertions 与 deletions 应严格相等，且总数等于各类替换处数之和。实测 344（颜色）+ 23（阴影）+ 40（圆角）= 407/407。相等且对得上，说明每处都是原地换值、没夹带整行重写或格式漂移；不等就说明混进了别的改动。

**交付要报「收敛了多少」，不只报「改了多少处」**：替换 407 处听着治完了，但如果改后色值仍有 164 种（改前 204），说明真正收敛的只占两成，颜色体系还是乱的。指令的 Output format 里要同时要「改前唯一取值数 / 改后唯一取值数 / 替换处数」三个数，验收时看的是后值降了多少，不是前值改了多少。保守规则（如非标 hex 一律不自动归并）一定会让步，交付时必须写明「哪一大块没动、留给下一刀」，否则用户会以为这部分治完了。

**指令自身的验收判据与红线不能打架**：红线写「36px 圆角本轮不动」，验收判据却写「圆角单值只剩 4/6/8/12 四种」——agent 按红线执行没动 36px，判据就判不合格，白返一轮。写完指令回查一遍：凡列在「不动/豁免」里的值，验收判据里要显式排除；做不到就删掉那条判据。

**上一刀产出的「未处理清单」不能直接当下一刀的输入，它会失真**。实测一份上百行的未处理色值清单里，某色值标了 4 处，在当前代码里 grep 是 0 处——行号对应到的其实是另一个值。生成清单的 agent 可能按旧版本文件记行号，或同一行里有多个色值。做法：每刀开工前用**当前代码重扫一遍**，清单只当「大概有哪些类」，每个色值以 grep 实况为准；指令里要求 agent 交付时报「该值在当前代码里的实际处数」，禁止沿用上一刀清单的行号。

**下一刀的分级判据是「改了会不会被看见」，不是「出现次数多少」**：同一批里混进两类风险会毁掉验收。

- 低风险（可与前刀同性质、一批走）：极浅背景的近似值（`#fafbff` / `#fafbfe` / `#f7f8fa` / `#f5f6fa` / `#f3f5ff` 十几种，肉眼分不出）、边框灰的近似值、`#000` / `#333` / `#999` 这类简写文字色归到既有档位。归并后几乎无感。
- 高风险（单独一批，逐页看）：语义色 base 本身换了色相。实测绿色同时存在青绿与黄绿两个 base（前者十几处、后者一两处），统一会明显变色，连带它的一串透明变体（`rgba(旧绿rgb, x)`）也要跟着换。
- 一句话判据：**改动前后色相/明度肉眼可辨 = 高风险批；只在近似值之间微调 = 低风险批**。混一起交付，就既有无感改动又有感改动，无法判断该放行还是打回。

**语义色基准由用户拍板，默认取项目现状高频色，不要设计稿色**：多套色系混装时（实测绿色同时有六种：项目青绿十七处、antd 绿两处、色板黄绿三处、深绿一处），先把每种的处数扫出来，把「基准选谁」单独抛给用户，别自己替他在「对齐设计稿」和「保留现状」之间选。用户实测口径是「以项目现有高频色为基准，不要 Figma 的」——理由：设计稿那套换过去等于整个系统的绿偏黄，是另一个项目级的活。**深色值要豁免**：深绿 `#087f5b`、深红 `#cf1322` 这类只有一处、用于深色文字的值，归并到浅色 base 会掉可读性，列入保留不动。

**扫语义色必须同时扫 hex 和 rgb 分量写法，只扫一种必漏**：`#f5a623` 和 `rgba(245, 166, 35, 0.14)` 是同一个颜色的两种写法，映射表只列 `rgba(230, 162, 60, x)` 就会漏掉另一个橙色的分量写法（实测漏一处，被 agent 的执行结果反衬出来）。做法：先全量捞出非黑非白非主色的 rgba，逐个人肉认出它属于哪个语义色——

```bash
grep -rhoE 'rgba\([0-9]+, [0-9]+, [0-9]+, [0-9.]+\)' --include=*.css --include=*.tsx . | grep -vE 'rgba\((0, 0, 0|255, 255, 255|65, 95, 255)' | sort | uniq -c | sort -rn
```

**替换范围要写「属性 + 字面量形态」，只写 CSS 属性会漏掉 JSX 内联样式的同一类值**：`color: #999;`（CSS 文件）和 `style={{ color: '#999' }}`（TSX 内联，驼峰属性名 + 引号包裹）是同一个语义，但正则 `color: *(#999);` 只命中前者。实测一份映射表把 CSS 字面量覆盖全了，两处 JSX 内联的 `#999` 原封不动漏过去，还是 agent 自己列在未处理清单里才暴露的。做法：每条映射规则的 grep 同时给两种形态——CSS `属性: 值;` 与 TSX `属性: '<值>'`；交付时要求报「该值还剩几处、各在什么形态里」，剩余不为 0 必须逐条说明为什么不在本轮范围。`background` / `border` / `fontSize` / `borderRadius` / `boxShadow` 在 tsx 里同样是驼峰内联写法，归并这些属性时一并纳入。

**第二重自证：改后基准色的增量应等于各少数派之和**：这是跟「insertions=deletions」独立的另一条验证线。实测 `#2ba471` 17→24（+7）= 3+2+2，`#d94152` 14→28（+14）= 8+4+2，`#d98c16` 5→11（+6）= 2+2+1+1，四组全对上，替换就不可能漏也不会多。指令里要求 agent 报「基准色改前改后处数」，验收时用这条核。

**预期处数写错会让正确的 agent 白停一轮**：给 agent 的「预期处数」是它的停下判据，写错它就报差异停住（实测浅背景把 31 写成 29、文字简写把 14 写成 7，两处都是分项相加时算错、合计漏改）。生成动作固定成：写分项列表 → 逐项相加 → 与合计核一遍 → 再跑一次真实 grep 对。分项对了而合计写错，是最容易犯也最容易漏查的。

**改前改后截图必须同尺寸，否则对比是假的**：实测一组里混了 1440×900 的视口截图和 1826×1916 的整页截图，尺寸不同的两张放进一组根本无法对比；更糟的是视口图常是撞车后截的，标着「改前」其实是改后。验法：读 PNG 头拿宽高——

```bash
python3 -c "import struct;d=open('x.png','rb').read(33);print(struct.unpack('>II',d[16:24]))"
```

一组图逐个打印尺寸，不一致的直接剔除。弱信号：整页图同页改前改后字节数应很接近（纯值替换实测只差几百字节），差几十 KB 的多半是视口图或页面没渲染完整。

## 原型里「看着合理」的结构化字段，多半是按下标循环造出来的假数据

权限/菜单/资源这类配置表格，字段值如果是从数组下标轮转出来的，评审一眼就能拆穿。实测一份「菜单资源管理」表里 keepAlive / requireAuth / icon 三列，源头是 `ROUTE_META_PRESETS[index % 4]`——只有四组预设按条目顺序循环分配，「计划审批」因此拿到 `keepAlive:true, icon:'edit'`，跟它是审批列表页毫无关系。同一张表「页面路径」整列显示 `--`，因为数据结构 `ResourceMetadata` 里压根没有 `path` 字段，渲染层只能填占位符。

**判据：结构类字段（路由路径、资源类型、权限元数据、图标、是否缓存）必须逐条有来源，不能由循环、随机或默认值生成。** 出现以下任一迹象就该整表重做，别打补丁：

- 数据文件里有 `PRESETS` / `DEFAULT_META` 数组，用 `index % n` 或 `i % n` 取值；
- 某列在所有行都是同一个占位符（`--`、`-`、空）；
- 资源树混进非菜单节点：从列表页按钮进入的表单页（创建/编辑）被当成菜单项、Demo/示例页挂在正式资源树下、同名节点在两个层级各出现一次。

**修法以菜单定义文件为唯一真源，不是路由表**（这条曾被写反，直接导致一整轮返工）：菜单/资源树/权限项的结构真源是 `src/config/menus.ts` 这类**侧栏菜单定义**（MODULES → MenuGroup → MenuLeaf 三层），不是 `App.tsx` 的路由表。

**但这条只管「原型内部怎么推导资源树」，不能拿它当「真实系统的信息架构长什么样」的基准。** 两件事必须分开：内部一致性看 `menus.ts`；「真系统里有没有这个分组、它挂在哪一级」只能看真系统。拿自己原型的菜单定义去写了指令让 agent 改结构，改完会被当场推翻——实测真实系统跟原型差出十处：触达计划下只有「触达计划」一个分组、压根没有「白名单」和「标签管理」两个分组；权限中心是**顶部一级**而不是组织架构下的分组；配置中心反而是权限中心下的分组；一级导航顺位也不同；还凭空多出一个原型自带的 Demo 示例一级菜单。

判据很简单：**这个结构的证据是「今天在真系统 DOM 里看到的」，还是「从我自己的产物里读出来的」？后者不算证据。** 历史盘点文档同样不能当基准——它可能已因写错被删，拿已作废的数据去改结构，下游（资源表、路由、页面归属）跟着整套返工。拿不到真系统访问时，就把取证当独立一步派出去（抓法见 skill `intranet-data-capture` 「菜单 / 信息架构：只认实时 DOM」一节），结构清单到手了再谈改哪个文件。

**结构类改动要先把连带面盘出来再报价**：菜单层级一变，`menus.ts`、路由、资源表种子版本、页面归属四处一起动，而页面内容本身不动。跟用户谈范围时说清这四层，别只说「改个菜单文件」。两者的区别是致命的：路由表记录的是「代码挂了哪些路径」，混着大量历史别名（`/main/channel/channel/agentManage`、`/main/content/content/engage/*`、`/main/promotion/*`），且**不体现菜单层级**——按路由表推，结果必然是别名路径、叶子漏一半、分组被压平。菜单定义里写的是短路径（`/org/agents`、`/auth/resources`、`/report/whatsapp`），别名只出现在侧栏高亮回落的兼容映射里。

开工前的核实动作：`grep -n` 出候选文件，把菜单定义的模块/分组/叶子三层各有多少条数出来，与路由表对照——数量对不上（如菜单里有 27 个叶子，按路由推导只出 3 条）说明真源选错了，此时不许下指令。映射规则：模块 → 一级资源；MenuGroup 有 children → 分组资源；MenuLeaf → 菜单资源（`path` 直接用叶子自己的 path）；MenuGroup 无 children 但有 path（如「活动管理」「私域分析报表」）→ 本身就是菜单。

同时加 `resourceType: 'menu' | 'button' | 'group'` 区分——菜单、按钮级操作、纯分组在权限系统里语义完全不同，全标「菜单」等于把权限粒度做错。从列表页按钮进入的表单页（创建/编辑）是 button 不是 menu，它们不出现在侧栏，但权限系统确实要控「谁能点新建」。对不上任何菜单项的资源**列出来问用户，不许按名字猜路径**；`keepAlive`/`requireAuth` 按页面性质定（列表页 true、表单页 false）；`icon` 用侧栏实际那个，菜单定义里没写就留空，**不许统一填同一个值凑数**。

**同名资源必须能区分**：菜单结构里天然有重名——模块名与分组名相同（触达计划 › 触达计划）、同一分组名在两个层级各出现一次（配置管理既是触达计划下的分组，又是配置中心下的菜单）。让 agent 补一列 `code`（menuKey）并在展示层加层级标注（`触达计划（模块）`／`触达计划（分组）`），数据层 `name` 不动。验收前自己扫一遍全表的重名组，别等用户配权限时看不出该选哪条。

**验收看的是「每行都能说出这个值从哪来」，不是「表格填满了」**：交付要求逐条列出资源名／类型／path／各元数据值 + 依据，末尾必须有「路由表里找不到对应项的资源清单」这一项——写「无」也行，但不能没有。

## 用户框出的那块就是问题范围，不要放大成整个模块重做

用户发截图 + 红框 + 一句「这个问题怎么还存在呢」时，**框选范围就是问题范围**。把一次报障理解成「整张表/整个模块的结构对齐」去重做，会连着做几轮都碰不到他框的那两个字段，他下一句就是「不还是这个问题么」——返工和信任都赔进去。

- 红框圈了 A、B 两个字段，就只处理这两个字段；红框外的结构问题（数据来源造假、层级压平、叶子漏半）是另一件事，单独列出来问他要不要一起改，不要顺手并进同一轮。
- 用户在多选项里挑了一个（如「三，权限中心的」）时，**这个选项是边界不是起点**——不要把「这个页面的某字段不对」扩展成「这个页面整张表重做」。
- 红框里的元素如果**没有系统画的圆形序号角标/虚线框**，说明那是用户用截图工具手画的标记线，只在指位置。不要据此判断标注功能出了 bug——先确认页面上 `.vpa-badge` / `.vpa-anchored` 的实际数量是 0 还是非 0 再下结论。
- 看不准框选处到底哪里不对时，**直接问那一处**（「这条选中『激活』，你觉得哪里不对」）。问一句的成本远低于猜错重做一张表。

## 取证任务只出行为结论，不出修复方案

用户说「取证」「查一下现在是怎么处理的」「我只是想搞清楚这块逻辑」时，交付物是**用大白话讲清现状行为 + 一行结论**，不含「应该怎么改」。这是产品经理视角的只读取证，不是开发视角的方案设计。

- 只报三件事：什么条件下走哪条分支、各分支的页面表现、哪些情况代码没有区分。按场景顺序讲（进来先做什么 → 拿不到什么 → 落到哪句提示），不要抛函数名和字段名当结论。
- **不要顺手写修复指令或改造建议**：会被当场怼回来「我们又不是开发，管怎么修改干嘛」。要改的时候他会明说换个问题，那时才进设计。
- 涉及多层的判断（容器鉴权 / 身份鉴权 / 数据授权），把每一层单独列出来，再说清代码实际把哪几层合并成了同一个判断——这是取证最有价值的产出，比逐行贴代码有用。
- 结论要给**准确定义**，不是复述用户原话：用户说「Tab 不展示了」，实测可能是「Tab 都在、内容区被统一拦掉」。这一句差别决定他后面怎么跟研发对齐，含糊过去等于白取证。
- 真机截图是最强证据：用户发来自己账号进系统的截图，能直接确认某一分支的真实表现，比自己读十行代码更快定案。

## 数据模型扩了枚举值，所有消费该枚举的地方都要同步扩

给某类对象加档位（资源类型从「菜单/按钮」扩成「菜单/按钮/分组」）时，改了列表和数据不等于改完——**详情表单、筛选器、徽章渲染各自有一份独立的取值列表**。实测资源表已按三档渲染，点开某条资源的详情，资源类型 radio 仍然只有菜单/按钮两项，分组型资源两个都没选中，用户一眼看出没做完。

- 改枚举前先让 agent grep 字段名和各档位的硬编码字面量，**列出每一个消费处**（表格列、详情表单 radio、筛选下拉、状态徽章、导出），逐处确认是否要跟着扩。
- 验收不是「列表看着对」，是**每种取值各打开一次详情**：选中项正确、保存后重新打开值没变。只看列表会漏掉表单那一侧。

## 复刻老系统：先拿布局骨架，同栈搬源码优于跨栈重画

复刻类最贵的返工，是字段一个个都对上了、页面还是「两个产物」。问题不在字段层，在更高的两层。

**第一步拿布局骨架，不拿字段**：整页是单栏卡片还是左右分栏、列表是表格还是纵向树、行高多少、缩进多少、操作入口在行内还是顶部按钮、有没有搜索框和分页。实测菜单资源管理——真实系统是单栏卡片 + 一整棵纵向菜单树（无搜索、无分页、无表头、无左右分栏，默认全部收起，选中行才在行末出四个图标），原型做成左树右表单两栏，字段全对也是两套设计。骨架证据只能来自真系统截图/DOM，顺序反了整页重做。

**样式值从源码或计算样式抠，不从截图估**：截图能估出的字号圆角只能当草图，交付前必须回到源码样式文件或 `getComputedStyle` 取值。

**第二次因为「不像」返工，就停止抠元素，改提同栈重构**：源系统是 Vue3 + Vant + 内部组件库时，用 React 手写 CSS 复刻等于拿另一套组件库重画——卡片圆角、按钮高度、字号层级、赠品条底色全是组件库带来的，一个个抠完源码一更新又要再对一遍。用户原话判据是「有源码还会做成这样」。改走同栈搬源码要处理两类依赖：内部组件库和 App 原生桥（扫码/剪贴板/相册/拨号，写 mock 层 + Toast 提示）。动手前先出一轮摸底——依赖清单与版本、组件替换难度、桥调用清单、页面按「纯展示/需 mock/需自写组件」分类、目录结构与分步计划——再定搬的边界，不要直接开搬。

**摸底之后第一个动作是验内部组件库能不能真装上，不要先按「装不上」去设计适配层**：公司内网通常有私有 npm 源（`http://npm.vmic.xyz` 这类），内部组件库在公共 registry 是 404、在内网源能正常下载。做法：建一个一次性最小工程（`_dep-check`），`.npmrc` 指内网源，装框架 + 组件库各一个版本，渲染一个内部组件跑一次 build——能过就是同栈搬源码、视觉完全一致、一行适配层都不用写；装不上才走开源同源库等价替换 + 薄封装。跳过这一步直接按「私有包拿不到」去写适配层，等于自找几十个组件的样式差异。装上之后还要补内部组件库缺失的 TypeScript 声明（本地 shims），否则 `vue-tsc` 过不去。

**装上之后一个组件都不许换——指令里那句「不能用的用开源组件替代」是整轮样式返工的根源**：组件库能装却仍被替换成开源同源库（内部 `FosButton`/`nx-search`/`nx-list` → `van-button`/`van-search`/`van-list`），DOM 结构、默认尺寸、Tab 收缩策略、按钮内边距全部变了，CSS 单位换算再准也不是同一个东西，用户判据是「有源码还做成这样」。写指令时把替代这条**整个删掉**，改成「内部组件一律用原件，不许用开源库替代；某个组件确实用不了，停下来报，由我决定」。装不上才写替代清单。

诊断这类「样式对不上」时，先查实际渲染的是谁，不要先怀疑单位换算：浏览器里数内部组件的 DOM/class 命中数（实测全是 `0`，页面上只有 `button.van-button`），命中 0 就证明替换已发生，此时 PostCSS `cqw` 换算对不对、全局样式搬没搬全都是次要问题——那两条实测都是对的，主因就是替换。取证顺序固定为：内部组件 DOM 命中数 → PostCSS 实渲值 vs 理论值 → 全局样式文件对照 → 逐元素差异归因。

**组件库替换这条路走到「还是不像」时，改走「把源码跑起来照真实渲染复刻」**：源码依赖内网接口、私有包、App 登录态，公司机往往能跑；跑得起来就直接看真实页面，抓 DOM 结构、class 名、computed style 当基线，原型照最终像素复刻，不再纠缠中间层用哪个组件。先单独派一轮「能不能跑起来」的探路指令（检查 Node/pnpm 版本、`.npmrc` 指向、dev server 端口与代理、需要哪些环境变量，用 worktree 或复制副本到临时目录装依赖起服务，内置浏览器打开看是白屏还是能进），跑得起来再定后面的路，跑不起来才回组件替换那条线。探路指令要写死「不许改源码仓库、不许切分支、临时目录验完留着」。

**验证用的临时工程验完就必须清掉，否则会跟着正式仓库一起提交**：`_dep-check` 这类一次性工程直接建在项目目录下时，`git add -A` 会把十几二十个文件一起收进去。验收通过当场做三件：`git rm -r --cached _dep-check`、写进 `.gitignore`、本地目录删掉。推到远端后再发现就得多一个提交收尾，且包内容变脏。

**同栈搬源码的工程参数一律锁定到源码版本，不要用 `^`**：`package.json` 里框架和组件库写完整版本号（如 `vue 3.5.22`、`vant 4.9.21`、内部组件库 `4.1.1-alpha.3.46`），带 `^` 装出的小版本差异会让全部样式漂移，而这类漂移在「一个个对组件」阶段根本查不出来。PostCSS 的 px 转 viewport 是**双基准**：业务源码按设计稿宽度（实测 1080）、Vant 组件按 375，两个都要配，只配一个会让开源组件整体尺寸错位。骨架验收标准是「一个内部组件 + 一个开源组件同页渲染 + build 通过」，两个都出来再往里搬页面。

**搬源码时把设计变量也从源码抠出来当基线**：主色、卡片圆角（实测 36px）、按钮圆角（1000px）、标题/正文/辅助三级字号（48/36/32）、页面边距（48px）这些是 px 转 viewport 的换算基础，写在 `styles/tokens.scss` 里；源码 reset 样式里引用的图标（如 `load.svg`）要一起搬，否则 reset 加载就报 404。

**不要假设原型里那块表单就是真实系统的形态**：真实系统只有树、看不到表单时，先确认表单入口（新增资源弹窗？行内图标？）再照做，别把原型自己那套承载方式当基准保留下来。

**局部截图只能证明被截到的那部分，不能据此推断整页布局**：用户发来两张只截了左侧菜单树的图，据此判定「真实系统是单栏、没有右侧表单」，实际 DOM 里是左树右表单的双栏（`.resourse-container` / `.menu-container` / `.form-container`），而用户那句「完全对不上」指的是样式不像、不是结构不对。遇到只拍到局部的图，先问一句「右边是什么」，或让 agent 抓整页 DOM/全屏截图，别拿半张图当架构基准——判断错了会把一个纯样式任务写成结构重构指令，白跑一轮。

**复刻指令直接用维他命课程那份现成模板**：`/root/notes/vitamin-course/08 用 AI复刻已有系统前端页面.md` 的方法四（浏览器自动化读取已有系统再复刻），完整 React 版模板已存本 skill `templates/legacy-clone-prompt.md`，不要每次从零手写。套用时必须按本项目改四处：

1. **浏览器指代**：原文写 Chrome，本项目环境改为「Cursor 内置浏览器」——它复用已登录态，是办公机访问测试/生产环境的唯一入口。
2. **范围白名单**：只点名本轮要复刻的那一个页面，其余一律不因页面存在菜单/按钮而扩展。
3. **不许动清单（防覆盖既有设计改动的门禁）**：原型里与真实系统「有意不一致」的部分要逐条列进红线段落，例如私域 2.0 把标签管理从权限中心挪到触达计划下、销售管理模块、Demo 示例的去留。不加这份清单，agent 对齐真实系统时会把这些设计改动一起「修回去」，等于把几轮需求白做。发现不一致时只记录、不许改，交回来由用户拍板。
4. **禁止静默简化**：加一句「取不到的如实标注在该处，不许静默删掉或做成简版」，并在 Output format 里单要一项「哪些确实取不到、尝试了什么」。agent 的默认行为是把「没取到证据」当成「可以简化」——iframe 跨域读不到 DOM、点开下拉时执行上下文被销毁，它就直接交一版字段减半的东西，还自己在遗留清单里标成「Demo 简化」。用户一句「为什么要做简化」就得整页返工。取证不全时要它停、要它问，不是要它自己决定缩水。

**「只许浏览不许改数据」不等于「只能看不能点」**：这条限制的边界是——可以展开收起、切 Tab、翻页、筛选、打开弹窗看结构；不许保存、提交、删除、导出、退出登录、切换账号。写指令时把两侧都写出来，只写「不得执行修改操作」容易被读成整页只读，agent 会因此拿不到展开后的层级结构。

**移动端 H5 原型要在桌面浏览器里模拟手机视口，不是直接全宽铺开**：设计稿宽度（实测 1080）靠 PostCSS px 转 viewport 换算，浏览器给多宽就按多宽算，桌面打开会按 960/1440 这类窗口宽度换算，元素比例整体错掉、看着像另一个系统。做法：外层容器 `max-width: 375px` 居中、两侧淡灰留白；容器内独立滚动，底部 TabBar 固定在容器底部而不是窗口底部；窗口宽度小于 375 时取消 max-width 直接铺满（方便真机访问）。

**用 `cqw` 代替 `vw` 时必须给容器声明 `container-type`，否则等于没改**：`cqw` 相对最近的容器查询容器计算，容器没声明 `container-type: inline-size` 就退回浏览器视口，还是按窗口宽度换算。agent 交付里写「180px 已变成 16.67cqw」只证明替换动作做了，不证明生效。验收读一句：`getComputedStyle(document.querySelector('.mobile-viewport')).containerType` 必须返回 `inline-size`；另一眼判据是打开页面看字号是否整体偏大——没有容器约束时 16cqw 在宽窗口下会算出上百像素。

**手机容器的包裹范围要把所有路由盖住，不只是首页**：容器常被写在首页那一层组件里，后续新增的独立路由（列表、详情、核销、活动这些）挂到外层就全宽铺开，用户看到的是「筛选栏横排、卡片一行排完」的桌面后台形态，一句「这不是移动端」又要返工。做法：容器往上一层提到 App 根组件、只包一次 `router-view`，不按页面逐个包；验收时把每个路由逐个打开看宽度是不是都和首页一致。

**容器生效与否看比例，不看「看着像」**：同一批元素在 375px 容器里的实渲像素应与源码设计稿等比（实测 180px 设计稿 → 约 62.5px）；差一个量级就是 cqw 没生效，TabBar 写死 `calc(180px + ...)` 时在无容器约束下会算出近三倍高。

**复刻移动端原型时文案一律直接写中文，不接语言包**：源码那套 `workLan[key]` 多语言字典搬过来只会让文案取错值（真机显示「用户」，字典里那个 key 的值是「用户管理」），每次对齐文案还多查一层。用户口径就是「不要管语言包，现在全用中文」——Tab 名、按钮、空态提示全部字面量写死。

## 表格：翻页列宽跳动 = 没设 `table-layout: fixed`

用户说「翻到第二页表头列间距不一样、页面跳一下」，根因几乎总是 `table-layout` 还是默认的 `auto`——列宽按**当前页内容**算，第二页文字长短不同就重排。

**先全项目扫三类表格的实际布局，别只看报问题的那一页**：

```bash
grep -rn "table-layout" --include=*.css .          # 哪些表格设了、哪些漏了
# 再定位每条的所属选择器（别只看行号）：
for l in $(grep -rn "table-layout" --include=*.css . | cut -d: -f2); do :; done
```

实测同一个项目里 `.approval-table` / `.org-table` 都写了 fixed，唯独 `.permission-table` 漏了——用它的是用户行为、权限用户、权限中心、受众条件明细、行为编辑属性表等六处，全部会跳。

**光加 `table-layout: fixed` 不够，必须同时补 `<colgroup>` 百分比列宽**，否则 fixed 下所有列平分，本来宽的「数据源表」被压成和「属性数」一样宽，比原来更糟。做法：每处先数清列数、按内容长短定百分比、**每页合计必须等于 100%**，交付时逐页报「列数 / 比例 / 合计」。长文本列（编码、路径、表名）配 `overflow: hidden; text-overflow: ellipsis; white-space: nowrap` 兜底。

**验收用 `th.offsetWidth` 跨页对比，不要看截图**：

```js
[...document.querySelectorAll('.permission-table th')].map(t => t.offsetWidth)
```

翻第 1 / 2 / 3 页各读一次，三个数组必须完全相同（实测 `[103,167,142,309,103,77,90,167,129]` 三页一致才算过）。只看截图看不出 1~2px 的差。

## 禁用态：`disabled` 属性只管点不动，视觉置灰要另外写

用户说「按钮要置灰，不可点击那种样式」时，只加 `disabled={条件}` 是不够的——`.link-btn` 这类链接按钮通常**一条 `:disabled` 样式都没有**，按钮确实点不动了，但颜色还是主题蓝，看着跟可点的一模一样。

```css
.link-btn:disabled,
.link-btn.danger:disabled {
  color: rgba(0, 0, 0, 0.25);
  cursor: not-allowed;
  background: transparent;
}
```

同时把已有 hover 规则写成 `.link-btn:not(:disabled):hover`，否则禁用态悬停还会变蓝。

**验收读 computed 值对比，两侧都要读**：禁用按钮 `color` 应为 `rgba(0,0,0,0.25)`、`cursor` 为 `not-allowed`；可点按钮应为主题色 + `pointer`。只报禁用侧不算验过——不比就无法证明「能看出来区别」。

## 浮层/角标贴边：先考虑挂到元素另一侧，而不是往视口里挤

角标、tooltip、popover 定位写成 `Math.min(window.innerWidth - 28, rect.right + 4)` 时，元素一靠右，浮层就被夹到视口最边缘贴着边框，用户说「快看不到了」。

**正确顺序是「换边 → 才夹」**：右侧放不下就挂到元素左侧（`rect.left - 宽度`），左侧也放不下才回退到视口内固定值，最后统一夹到 `[4, innerWidth - 32]`。只夹不换边，等于把浮层从元素旁硬拽到屏幕边，位置语义就丢了。

**验收：遍历所有浮层读 `getBoundingClientRect()`，统计 `left < 2 || right > innerWidth - 2` 的个数，必须为 0**；再抽三处（右侧靠边 / 中间 / 左侧宽块）报角标坐标与元素坐标的相对关系（`1327 = 1355 - 28` 这类算式最直观）。

## 项目内运行时与 skill 资产是双份，改完必须回写

`annotation-kit/runtime.js` 这类运行时在项目里有一份、在 skill 库 `assets/` 下有权威版。**在项目里改完修好的逻辑，不回写 skill 资产，下次同步会把旧逻辑又带回项目**，同一个 bug 修第二遍。

回写流程：`cp` 项目版 → skill 资产 → `wc -l` 两边行数 → `git diff --stat` 应只显示这一处预期增量 → commit（备注写明同步了哪几处改动）→ push。push 后**立刻在聊天里告知提交号并要用户 `git pull --rebase`**，否则他在另一台机器上 push 会因非快进而被拒。

## React/antd DOM 调试技巧（fiber 层）

当"源码/bundle 都对，但 DOM 渲染不对"时，逐层实锤：

1. 源码 grep → 2. bundle 里查变量引用（**注意：minified 共享常量被 Rollup 提升，字面量不会出现在使用点附近，grep 使用点附近的字面量是无效检查**）→ 3. 服务端确认上线 hash → 4. Playwright 读 DOM + React fiber：

```js
// 读 fiber props（React 私有 key）
const fk = Object.keys(el).find(k => k.startsWith('__reactFiber$'));
const styleInProps = el[fk]?.memoizedProps?.style;  // fiber 有 + DOM 无 = commit 层被劫持/丢失
// 元素 API 身份检查（决定性一招）
el.style instanceof CSSStyleDeclaration  // false = style 被替换成普通对象！
```

实战案例（0831 forge-scrm）：7/8 列表页筛选卡片正常、唯独 /scripts 无 style。源码/bundle/部署全对，fiber props 有样式，DOM attribute 为 null，最终 `el.style.setProperty is not a function` 实锤——**该元素 style 被替换成普通 JS 对象**，React 写进了假对象，DOM 永远不更新。修复方向 = 找出劫持点（全仓搜 `defineProperty`、`.style =` 赋值），或每渲染新建对象 `{...TOKEN}` + 稳定 `key` 强制重挂。

排查教训：
- ❌ grep bundle 里"使用点附近的字面量"判断样式缺失（Rollup 提升导致误判）
- ❌ 归因浏览器/CDN 缓存（需 Playwright 全新 context 复现才算数）
- ✅ 疑似缓存时，先用 Playwright 无缓存登录态复现，复现了才排除缓存
- ✅ hook `CSSStyleDeclaration.prototype` 不会触发如果元素 style 被替换成普通对象——先查原型身份

- Context 必须带：已完成排查清单（防 agent 重复走弯路）+ 文件行号证据
- Request 逐项列改动文件+行号；范围红线（"禁止修改 backend/""禁动其他正常页"）
- Checkpoint 要求：改动文件清单 + 每项验证方式 + build/tsc 证明 + 红线复扫结果 + 遗留风险
- 沙箱网络受限：报告留 check-reports/，禁重试上传，由杰西卡代传
- **大批量统计给脚本文件，不给内联管道**：像"跑八类取值分布"这种活，把命令写成一个 `.sh`（每段前面 echo 分隔标题），指令里只让它 `bash 脚本.sh > 输出.txt`，再照输出填表。反过来把带多层引号嵌套的 `grep | sed | sort` 管道链直接写进指令，agent 会卡在转义上原地打转十几轮——不是它能力问题，是 shell 嵌套引号本身不可靠。同理禁止让它用 `node -e` / `sh -c` 现场拼命令。
- **统计脚本里的正则要能说明自己在数什么**：`grep 'border[a-z-]*: *[0-9]+px'` 会把 `border-radius` 一起算进边框宽度，得出"边框有 13 档"的假数据。写完先自查一遍正则会不会串属性，串了就拆成两条并显式 `grep -v radius`。
- **一条指令只做一件事；多余的需求宁可另发一条新指令，也不要合并进已在跑的指令**：用户经常同时开多个 agent（Qoder / Cursor / WorkBuddy）各跑一条指令，他拿到指令的第一时间就贴出去了——事后往上追加需求（如「哦对了还要加个字段」）要**另发一条独立补丁指令**（开头标明给哪个 agent + 哪台机器 + 与前一条什么关系），禁止悄悄改写原指令或把新需求折进别的任务。用户明确开口让合并时才合并。补丁指令应单点、小范围（只加一列、只改一处），验收标准独立可 grep。
- **多轮迭代要主动维护「待跑指令队列」**：连续跑几轮后用户会说「我现在不知道要跑哪些指令了」。每轮交付收口时必须用一句话交代状态——「已提交 X，待跑 Y 和 Z，Y 先」；积压超过两条就重排一次完整清单，顺序规则是「先把手上未提交的改动提交成基线，再逐条指令」，别让用户自己拼上下文。
- **命令块的 `cd` 必须按用户当前那台机器写路径，不要混平台**：同一项目在公司机（Windows）是 `E:\projects\<name>`、个人机（Mac）是 `~/个人文件/WorkSpace/vivo/<name>`。用户会直接整段粘贴，给错平台就是第一条命令就报「找不到路径」（实测被当场指「那个 cd 是你给我的」）。同一个会话里用户可能在公司机和 Mac 之间切，每次给命令前先确认他此刻在哪台机上；不确定就用一句「公司机：…；Mac：…」并列写开。
- **收尾固定给完整 git 命令块，不要让用户自己判断 git 操作**：用户实测口径是「这种并行跑的 git 我不操作了，跑完我告诉你，你给我 git 指令，我直接用就行」。所以交付后不要只给 commit message。命令块要整段可粘：`cd <工作区>` → `git status --short` → 逐文件显式 `git add`（禁 `-A`／通配符）→ `git diff --cached --stat` → `commit -m` → `git pull --rebase` → `git push origin main` → `git log --oneline -3`。并写明闸门：「--stat 里应出现 A、B、C，出现 D 就先撤出暂存」。agent 常把临时文件和备份文件（`*_backup.pptx` 这类）一起提交，这道闸门是唯一能挡住它的地方。
- **指令正文里直接要求 agent 改完就 `git add` + `commit` 到本地分支，push 由用户或杰西卡做**。agent 默认口径是「不 commit、不 push」，结果是每轮交付都要多绕一次「报告说改了、远端还是旧字节数、搜不到新内容」，再补一条提交命令。在 Request 末尾加一句「改完 commit，不 push」，这一轮就省掉了。验收时一律以 `git pull` 后的字节数/内容特征为准，不信报告。

## 公司机的透明加密会把二进制文件变成打不开的密文

办公机装了透明加密 / 数据防泄漏类软件时，**只要用 Office 打开过 .pptx / .xlsx / .docx，文件就会被就地加密**（不必编辑、不必另存），随后跟着 commit 一起推上来。表现：VPS 上字节数明显变小、`unzip` 报 `End-of-central-directory signature not found`、`file` 显示 `data` 而不是 `Microsoft PowerPoint 2007+`。

**判据看文件头，不看大小**：

```bash
file "<文件路径>"                  # 正常应报 Microsoft PowerPoint 2007+ / Zip archive
head -c 8 "<文件路径>" | xxd       # 正常是 504b 0304（PK..）；出现 %TSD-Header 之类就是密文
```

- **修法**：从上一个正常提交恢复（`git show <上一个好提交>:"<路径>" > "<路径>"`），恢复后重新验页数 / 图片数 / 关键文本三样，再提交覆盖。不要试图解密。
- **预防**：二进制产物固定在 Mac 上改，公司机只读不打开；交付前用 `file` 过一遍本轮提交的二进制文件。
- **别当用户操作失误**：用户什么都没做，是加密软件后台改的，报原因时要说清这一点，别让他以为自己存错了。

## 部署到共享域名的子路径（pmlophy.com/project/&lt;name&gt;/）

共享域名下一个项目一个子路径，`rsync` 覆盖前有两步不能省：

1. **先比对线上独有的目录**。`rsync --delete` 会删掉目标里源没有的一切。项目常有 `dist/` 之外的上线物（如 `annotation-kit/` 标注运行时），一旦被删，页面还能开、但功能整块消失，且从首页返回值看是 200，很容易误判成功。

```bash
comm -23 <(ls <线上目录> | sort) <(ls <dist目录> | sort)   # 输出非空 = 有东西会被删
```

输出非空就把那些目录先补进源，或在 rsync 里加 `--exclude`。

2. **先备份再覆盖**：`cp -a <线上目录> /root/backups/<name>-web-$(date +%Y%m%d%H%M%S)`，回退时整目录替回即可。

部署动作与验证顺序：`npm run build`（确认产物 hash 与仓库 dist 一致）→ 备份 → 改 `dist/index.html` 里的缓存版本参数（`v=<日期+字母>`，纯值替换部署时它是不变的，不 bump 用户看到的还是旧缓存）→ `rsync -a --delete` → 验证三件：首页 HTTP 200、线上引用的是新 hash、新 bundle 里 grep 得到本轮改进去的特征色值。

**部署序列里 `git checkout -- dist/index.html` 必须排在 `git pull` 之前，不是之后**：`dist/index.html` 被 git 跟踪（虽然 `dist/assets/*.js` 被 ignore），bump 完 `v=` 它就变成未提交修改；上一次部署留下的脏改动会让这次的 `git pull --rebase` 直接失败（`cannot pull with rebase: You have unstaged changes`）。固定顺序：`git checkout -- <项目>/dist/index.html` → `git pull --rebase` → `npm run build` → 备份 → sed 改 `v=` → `rsync -a --delete` → curl 验证。如果哪天要提交 dist（比如被当成发布产物管理），就单独一次 commit 说明理由，不要让它长期半脏。

**pull 的失败必须让它可见，否则会拿旧代码部署上线**：`git pull -q --rebase 2>&1 | tail -2` 这类写法分不清成功与失败——没有输出和「Already up to date」都只显示一两行，被 tail 一截就看不出是报错。实测漏判一次，结果用旧代码 build 并 rsync 上线，用户打开看到的还是上一版。做法：pull 之后 `git log --oneline -1` 打印当前 HEAD 并核对是不是远端最新，或写成 `git pull --rebase || { echo PULL_FAILED; exit 1; }`。build 之前必须确认 pull 真成功，不能默认它成功。

**VPS 侧的 remote 长期保持 SSH，不要为了一次 push 临时改成 https 再「复原」**：VPS 上没有 https 凭据，origin 一旦是 `https://github.com/...`，之后每条 `git pull` 都报 `could not read Username for 'https://github.com': No such device or address`，而这个失败很容易被 `-q ... | tail -2` 吞掉，接着照样 build + rsync，上线的就是上一版代码（真实踩过：pull 失败后部署，页面还是旧的）。做法：VPS 上 origin 固定写 `git@github.com:<user>/<repo>.git`，拉取时带 `GIT_SSH_COMMAND="ssh -i <key> -o StrictHostKeyChecking=no"`；确实需要临时换协议时新建一个 remote 名（如 `https-tmp`）用完删掉，不要动 origin。

**部署后功能验证不能靠"首页能开"**。整块功能（标注、侧栏入口等）由子路径下的运行时脚本提供，首页 200 不代表它在。浏览器实测：脚本清单里应出现该运行时、页面无 console 报错、功能入口元素存在且宽高非 0。

## 静态 HTML 原型/线框图：交互是真是假必须逐条点，不能读代码判断

用户收到 agent 改完的「交互版」单文件 HTML（内联脚本）说「加上交互了，你看看」时，**不要读代码判断实现与否，直接开无头浏览器一条条点**。假交互和真交互在代码上长得一样：addEventListener 齐全、toast 也弹，但用户点下去什么都没发生。

打开方式（中文文件名/路径必须编码，否则 file:// 打不开）：

```python
import urllib.parse
new_tab("file://" + urllib.parse.quote("/root/.../中文-线框.html")); wait_for_load()
```

一次 js 调用跑完整组断言，结果一次性拿回：搜索后**可见行数** → 点表头看**行顺序**变没变（排序）→ 点第 2 页看**行内容**变没变（分页）→ 切每页条数看**可见行数**是否跟着 10/20/50 变 → 点整行与点「查看详情」分别看抽屉 class/标题 → 派发 `keydown Escape` 和点遮罩看抽屉有没有关 → 数 `document.querySelectorAll('[data-table]').length` 看是不是只有一份表格 → 读提示条/空态/标记条元素在不在。

**假交互的典型形态（命中即打回，都实测见过）**：

- 抽屉不是弹层：页面里有两份表格、`.drawer` 是 `position:absolute` 挂在第二份上，点「查看详情」只是 `scrollIntoView` 滚到下半部分——用户看到的是「表格下面又跟了一块」。
- 分页只换 `active` 类 + `showToast('演示')`，行不动、条数不变。
- 「排序」箭头其实是筛选触发器，点开的是下拉菜单，行序永远不变。
- 筛选提示条（「当前列表为筛选后的数据」）常驻，筛选清空后也不消失。
- 搜不到时全行 `hidden`、没有空态元素，页面一片空白。
- 只有「查看详情」那几个字可点，点整行没反应。
- Esc 只关了筛选菜单和弹窗，抽屉不关；遮罩压根没绑点击。
- 状态点没有 `title`/tooltip，hover 无说明；「数据未同步」行没有降透明度。

**报给用户分三档，不要给「交互基本实现」这种结论**：真能用（逐条点名）／假的（写成可复现动作，如「点第 2 页行不动」）／没做。他拿这三档决定返修范围，含糊结论等于让他自己去点一遍。

**返修指令这样写**：把实测出的每条原样搬进 Context「现状问题（已实测，必须全部修掉）」，Checkpoint 写成「我会逐条点：……」并列成可复现动作，红线加一句「任何一条做不到或被降级成 toast，直接说明，不要假装实现」。**结构问题要单独点出来**：两个状态并排画在一张长图上时，光加脚本改不掉，必须要求「合成一份列表 + 一个 fixed 抽屉 + 遮罩」。

## 截图当交付证据时的三条纪律

交付物里的截图（评审材料、验收图、对比图）是给别人看的证据，不是给自己看的日志。三条踩过的坑：

1. **空表格的图等于没截：优先打开「有数据的编辑态」，不要用新建态**。新建弹窗里表格区常是空态（“暂无数据，先选择数据源”），红框圈出来只有一个表头加一句空提示，证明不了新增的列或控件。凡是证明「表格/列表里有什么」的图，走编辑已存在记录的路径（列表行点「编辑」，弹窗自带 mock 数据），脚本里备一个 `open_xxx_edit_modal()` 与新建态分开用。
2. **用视觉模型读成品图逐项核，不要只看「文件生成了」**。脚本自检只能证明文件存在，证明不了图里是当前形态。出图后把图喂给视觉模型，按「该出现的元素在不在、不该出现的文字还在不在」逐条问（这一列是不是下拉、默认值是不是 X、那句旧说明文案还在不在）。
3. **截图脚本要能只重出指定图**。整批重跑会让所有图字节变化（顶栏时钟实时渲染）、产物体积重复膨胀、git 改动面失真。给脚本加一个环境变量过滤 filename（如 `SHOTS_ONLY="07-属性表"`），小改只重出受影响那几张，交付前再确认没有被漏掉的关联图。

**按文件回退前，先看这批文件里有没有「与冲突无关、但你还依赖的改动」**：`git checkout <commit> -- <files>` 是把整个文件退到那个提交，同一文件里后来加的环境适配、平台路径兼容会一起消失（典型：给截图脚本加的自定义浏览器路径 env 被退没，重跑时报「找不到 Chrome」，白跑两轮）。回退后先跑一次冒烟（脚本能不能起来、能不能出一张图），不要等跑完整流程才发现。

## 部署后实测分工

- 杰西卡：服务端 curl 验 bundle hash + 特征 + 服务状态
- 用户：浏览器实测（注意强刷/无痕）；截图发回时杰西卡负责"看图描述"（用户视障）
- 遗留风险分级：可接受（记账后续优化）vs 阻塞（必须修后重部署）

### 验证原型标注是否生效（查错选择器会误判成功能丢了）

标注运行时（VPA）的 DOM 特征与直觉相反，按下面的顺序查，否则会把"本来就没进入标注模式"误判成"部署把标注弄坏了"：

1. 入口**不是 button**。查 `document.querySelectorAll('button')` 找不到标注入口是正常的——入口是 `.vpa-floating-entries` 容器里的 `.vpa-entry` 元素。查这三个：`.vpa-floating-entries`、`.vpa-entry`、`.vpa-root`。
2. **preview 模式下角标本来就是 0**。`.vpa-badge` 数量为 0 不代表坏了，必须 `document.querySelector('.vpa-entry').click()` 进入标注模式后再数，这时角标才渲染，且数量应等于当前屏幕状态分组下的块数。
3. 判定功能在不在，看这三件：`document.scripts` 里有 `annotation-kit/runtime.js`、`fetch('.../annotation-kit/annotation.bundle.json')` 返回 200 且条数正确、`.vpa-floating-entries` 的 `getBoundingClientRect()` 宽高非 0。
4. 页面主体文字很少（几百字）而根节点 HTML 很长，通常是 IndexedDB 种子数据尚未灌完就查了；等 4–6 秒重测，别据此判定页面坏了。

### 配置项不生效，先核对运行时版本，别查配置

标注这类"config + 运行时脚本"分离的功能，config 里配了新字段（如 `screenState`）但页面毫无变化时，**第一动作是核对运行时版本，而不是怀疑配置写错**。实测项目里那份 `annotation-kit/runtime.js` 是 1498 行的旧版，压根没有屏幕状态逻辑，config 配了等于没配；skill 库里的权威版本 1524 行才有。验法：

```bash
wc -l <项目>/public/annotation-kit/runtime.js
grep -c "screenState" <项目>/public/annotation-kit/runtime.js   # 0 = 旧版
diff -u <项目版> <skill库权威版> | head -60                   # 先看 diff 再覆盖
```

diff 只落在预期的那几处（本例四处：加屏幕状态判定、去掉来源行渲染、改角标测量遍历）就说明项目没做过别的定制，可以整体覆盖；diff 里出现项目特有的逻辑就不能覆盖，要手工移植。

### 虚线框的判定依据是「挂上角标」，不是「元素有锚点属性」

CSS 若写成 `body.vpa-mode-annotate [data-anno] { outline: dashed }`，那凡是源码里留着 `data-anno` 的元素都会进标注模式就画框——**即使对应标注块已经删掉**，页面上就出现一批点了没内容的空框。实测删掉一批超范围标注后，源码里还残留 12 个锚点，全部变成空框。

正确做法是运行时在角标真正挂载成功后给该元素加标记 class（如 `vpa-anchored`），每次测量前先清空再加，CSS 只认这个 class。这样锚点留不留都不会出空框。

排查手法：源码锚点集合与 bundle 实际引用的锚点集合做差集，差出来的就是会画空框的：

```bash
comm -23 <(grep -rhoE 'data-anno="[^"]+"' src/ | sed 's/.*="//;s/"//' | sort -u) <(bundle 里被引用的锚点 | sort -u)
```

**面板里出现「来源：xxx.md#7.1」这类行，也是同一类「展示层漏了过滤」**：来源只该进 config 的 `sourceRefs`，不该渲染到面板（开发看不到那些 md，评审也用不到）。既有 md 正文里的 `> 来源：` 行要一起清，光改 runtime 不够——两处都没了才算清干净。

### 页面头部（面包屑 + 标题）不统一，是全局结构问题不是单页 bug

单页出现面包屑写错（如把「权限中心」硬编码在别的模块的页里）时不要只改那一页，先全量扫一遍有多少页有面包屑、用的什么 class：

```bash
grep -rn "crumb" --include=*.tsx pages/ | grep -E "span|h1|div"
```

实测 17 个页面只有 4 个有面包屑，且各写各的用 4 套 class；有的页面连 `<h1>` 都没有，标题是个 13px 的 div。修法不是逐页补，是抽一个 `PageHeader` 组件（传页面名 + 所属模块，内部按菜单树自动算层级路径），所有页面统一调用。

**面包屑的正确形态是两行：路径小字 + 标题大字**。三个词同字号同颜色字重排一行，看不出哪个是当前页（用户判为 bug 并要求改）；改成一行为路径（12px、常规字重、`rgba(0,0,0,0.4)`）、下一行为 `h1` 标题（20px、字重 600、`rgba(0,0,0,0.8)`），两者间距 6–8px。

**标题字号必须显式写死，不能依赖继承**：页面容器的 `h1` 规则常是从别的页复制来的（实测 `.permission-page__top h1` 是 13px/700），直接改结构后标题会被父容器压成 13px，看起来像没生效。给页面自己的 `.行为前缀__breadcrumb h1` 写完整字号字重颜色，并在浏览器里读 `getComputedStyle` 校验 `fontSize` / `fontWeight` / `color` 三个值，不只看截图。

**菜单结构里常有「分组名 = 模块名」的重复层**（触达计划 › 触达计划 › 计划列表），照菜单直接拼会拼成两级同名。规则：分组名与模块名相同时省略中间那级。
