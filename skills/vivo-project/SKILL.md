**下面三条是「原方案」的成立依据——留着不是用来坚持，是用来解释「当初为什么这么放」（评审一定会问）：**

1. **需求原文的位置要求**：需求池第 14 条要求预售标签挂在**标签管理**的标签树「营销与转化 > 新机营销」下（新增独立的预售含核销标签），而标签管理在本系统归属**权限中心**（生产路径 `/main/content/tag-management`）。后来把「预售标签」重构为「用户行为」（静态标签承载不了自定义数据源/属性），**形态和名字改了、归属没改**——改得越少，跟需求方沟通成本越低。
2. **同类能力、同类权限**：用户行为与标签管理都是「定义维度」的配置资产，权限约束一致（配置仅总部产品/运营可增删改，国家运营只读）。
3. **不照搬内销位置**：内销把标签/行为放在「工具中心 > 标签管理」（与自动打标同级），外销的标签管理本来就在权限中心，照搬会出现「标签在权限中心、行为在工具中心」的分裂。

推论（配置与使用分离，回答「那使用入口呢」）：**配置在权限中心，使用（圈人）在触达计划的受众筛选区块**——与内销「定义在标签库、使用在人群/触达」同构。

**内销最值得引用的一条架构点**：条件不写在计划里，而是沉淀成可复用的人群资产（人群洞察 → 新建人群，有「人群名称」「适用场景」，触达计划只「选择人群」引用；引导语写着「人群洞察是触达的核心」）。推论：**行为定义要做成一套、两处可引用**（触发侧 + 圈人侧都出自同一个行为库）——本期只做圈人侧，但结构上要能被计划外引用，别绑死在计划里，否则二期做触发型时会出现两套定义、两套 JSON 语义。

**外销命名定稿（用户拍板）**：模块统一叫 **「用户行为」**，不用「事件标签」「时间标签」这类叫法；页面动作是「新建行为 / 编辑用户行为」。但技术词「事件表」「事件编码」**保留**（要跟大数据那边的说法对齐）。

**命名统一要连目录名和文件名一起改**，不只是文档正文（用户原话「那个文件夹都改成叫『用户行为』吧，后面统一名称都叫『用户行为』」）。做法：`git mv` 逐个改名（保留历史），改完 **`grep -rn '<旧路径>'` 扫全仓库引用**，再 `rmdir` 空目录。注意**版本记录/变更日志里的旧叫法要留着**（那是“改了什么”的留痕），只有正文和文件名要新叫法。

**外销范围定稿 = B 方案（用户拍板）**：V1 只接预售一条行为，**保持精简**，覆盖业务场景够用即可（原话：「前期没必要那么重」）。

- **只补两项**（对齐内销后确认是刚需）：① 「允许限制时间范围」（允许 / 不允许，决定圈人侧时间框能不能用）② 「行为属性」的表结构（序号 / 字段名称 / 字段描述 / 字段类型 / 是否可限制组织权限）
- **不补**（外销 V1 用不上）：行为触达时机（DELAY/BEFORE/AT_ONCE）、数据更新时间、行为使用范围、行为有效时间
- **保留自有字段**：行为编码（英文小写+下划线、全局唯一、创建后不可改）、状态（启用 / 停用，只停用不物理删除）
- UI 线框在 `/root/deliverables/20261019/用户行为-UI线框-配置与使用.html`（4 图：配置入口 / 配置详情 / 使用-受众圈选 / 使用结果-明细页）

**菜单层级硬上限 = 3 级**（用户提供的事实，决定所有菜单归属方案）：数据模型是 `Module(顶部) → MenuGroup(左侧组) → MenuLeaf(左侧叶子)`，**MenuLeaf 没有 children**，所以 4 级物理上做不出来。已实测在用的最深结构是 3 级：`触达计划 > 触达计划 > 计划列表/计划审批`。

推论（提菜单归属方案时必须先算层数）：
- 内销实际 **3 级**、外销 **2 级**（权限中心>标签管理）——外销没有「企业微信管理」这层壳，两边层数本来就不一样。「对齐内销」时**不能照搬内销的层数**，要先想清映射到外销是几级。

- 页面内的步骤/页签（如触达计划 6 步向导、受众圈选内的页签）**不受菜单层级限制**，别把两类混在一起算。

2. 评审 PRD 里三节（不是两节）——**凡是"不说清就会被反问、且答案不在文档里"的，都该有对应小节**：`1.5 内外销对标与本期取舍`（取舍表 + 对外话术）、`2.3.4 架构约束（开发须知）`（把底子写成开发能照做的条目）、`2.4.1 模块归属说明`（引用块，写在首个页面节标题下方：为什么这个功能放在这个模块下）。

**判断差异的主线（1021 用户定，位置与能力差异都回到这条线判断）**

> 用户标签、用户行为本质上都是**「圈人的原料」**，服务的链路是：**对齐圈人颗粒度 → 锁定人群（人群资产）→ 洞察（人群分析）→ 触达（计划下发）**。内销的说法是「人群洞察是触达的核心，先洞察再触达」，而其**前置条件是颗粒度先对齐**——颗粒度不一致，人群锁不住、洞察没有可比口径。

三条判断原则：

1. **原料类能力按「它服务哪条链路」归位，不按系统的管理属性归位。** 权限中心是管菜单资源与权限的域；把圈人的原料放进去 = 语义错位（运营要圈人得跑去权限中心找标签）。这是大领导说「没道理」的根因，比「内销放工具中心所以我们也放」更经得起追问。
2. **两侧链路要等价，不等价要能说出等价物。** 内销多一层「人群资产」，外销把条件直接写在计划里 → **链路等价、中间资产缺失**，讲成**阶段差异**（外销 V3 规划「行为条件保存为可复用人群包」），而不是「我们没做」。
3. **与链路无关的差异（菜单命名、报表命名）单独走命名统一**，不套链路判断。已知命名差异：内销「运营报表」= 外销「数据报表」、内销「组织管理」= 外销「组织架构」；「触达计划」「工具中心」同名一致。**命名不一致最容易被当成「两个系统不一样」，评审要主动说明。**

**「对齐圈人颗粒度」的抓手是一张维度对照表**（10 维：组织范围 / 用户范围入口池 / 用户关系条件 / 标签条件 / 行为条件 / DMP标签 / 固定条件 / 对象层级(人·群) / 触发条件 / 人群资产），逐条标「一致 / 差异 / 阶段差异 + 缘由」，结语点出「主干（标签+行为）已一致或对齐中，差异集中在 DMP、固定条件分层、用户关系、群维度四项」。**外销比内销多的项也要写进去**（如「导入门店」），只列缺的会漏掉自己更强的地方。表与外销实测现状见 `references/内销触达计划与人群洞察架构.md`。

**差异矩阵每条必须标「差异性质」**——这是决定"要不要现在做"的唯一依据：

| 性质 | 含义 | 处理 |
|---|---|---|
| **形态差异** | 界面长什么样、编排方式、在哪一步、指标几层 | 可后补，**不进 V1** |
| **能力差异** | 有/无某个能力（触发型、DMP 接入、打标链路） | 排期解决，写进迭代路线 |
| **架构差异** | 数据与语义的底层结构（条件存哪、定义绑不绑计划） | **只有这类必须在 V1 处理** |

**「底子 vs 面子」是回应用户"怕底子没扎好、后面改得多"的标准切法**：

- **底子（V1 必做，不做就返工）**：① **定义中枢化**——计划的条件只存"行为的引用 + 属性条件值快照"，不复制定义本体；② **条件集可独立存取**（有自己的标识、能序列化），界面上仍留在计划内的受众筛选区块；③ **三个语义在定义层定死**（主体是人还是设备 / 时间一律按行为发生字段 / 保存即快照，后续改定义不影响历史计划）。
- **面子（V1 明确不做，后补不疼）**：人群资产界面（列表/命名/复用选择器）、触发型引擎、画布式编排与判断节点、DMP 标签接入、行为用于自动打标。
- **讲法（对外口径）**：对齐内销的是**能力骨架**（定义中枢 → 条件模型 → 可复用人群），**不是它的界面形态**；差异理由是外销按国家与战区运营、条件写在计划内是既有业务习惯。备选方案（V1 就带最小人群资产）**并列在评审里比较，不塞进 V1 范围**。
- **架构约束要写成开发可执行的条目**（放进评审 PRD 的「开发须知」节，不能只写在分析文档里）——否则开发按传统做法把条件内联进计划表，二期做人群库时要迁移。

## 四、账号对应好友列表 P-TOL-005（高频改动点）

现有 10 列：账号所属国家、区号、账号对应手机号、授权状态、账号所属导购/工号、Whats好友名称、好友手机号、账号删除状态、数据同步时间、操作。
筛选：手机号、导购姓名/工号、好友名称。

接口「管理后台-分页查询好友列表」**已返回但页面未展示**：`storeName/storeCode`、`employeeId/employeeName/employeeCode`、`remark`、`addTime`（备注=账号添加时间）、`assignTime`、`preStoreName/preEmployeeCode`。
**接口没有**：好友首次添加时间、好友标签、会话次数。

**列表视角混合是这页的结构性问题（用户会拿截图来问怎么优化）**：一行 = 一个 WhatsApp 好友，但表头里混了**账号维度**的列（账号所属国家 / 区号 / 账号对应手机号 / 授权状态 / 账号所属导购工号）——同一个账号下的 N 个好友会把这几列重复 N 遍；国家、区号、账号删除状态这类值还会整列恒定（全「印尼」/全「+62」/全「未删除」）。诊断一句话：**表头把「账号」的属性和「好友」的属性平铺在同一层，视角不一致**。

三个优化方向（给用户选，别直接开工）：

| 方向 | 做法 | 代价 |
|---|---|---|
| **A 账号为主、好友为辅**（推荐） | 一级行 = 一个账号（手机号/国家/区号/授权状态/所属导购/**好友数**/同步时间），展开看该账号下好友 | 列表长度大降；但导出与权限跟随账号维度 |
| B 保留平铺、列降噪 | 账号维度列合并单元格或收进悬浮；恒定值列（国家/区号/删除状态）改由筛选体现，默认不占列 | 改动小；信息密度仍高 |
| C 双视图切换 | 默认账号视图，可切回好友视角 | 两种口径要同时维护 |

### 账号—好友列表优化（1023 用户拍板）

- **方向 A（主从视图）拍板，原话“不留尾巴，彻底杜绝”**：一级行 = 一个账号（账号手机号/国家/区号/授权状态/所属导购/好友数/同步时间），展开看该账号下的好友。
- **导出：按好友维度平铺**（用户定）；但“同一好友被多个账号加过时导多行”这件事**需业务确认有没有实际场景**——先让 Cursor 只读抓数核实，再落文档。
- **8 个新增字段的维度归属（1023 分好，写文档/线框必用）**：账号维度 3 个 = 导购私域账号 / 所属门店 / 导购ID；**「账号—好友」关系对维度 5 个** = 首次添加时间 / 最新添加时间 / 好友标签 / 备注 / 导购主动发起会话次数。**结论：没有一个属于纯好友维度**——同一好友被多个账号加过时这 5 个值可不同，所以“按好友维度导出平铺”必须定取哪一条。

**账号:好友手机号 = 1:N；同一好友可被多个导购账号添加——这是 WhatsApp 社交软件的正常形态，不是脏数据/重复数据（1023 用户纠正 + 运营汤翠琴确认）**。用户原话：“国外用 WhatsApp，导购也是 WhatsApp 账号，导购 A 加你为好友，导购 B 也可以加你为好友，这是正常的，毕竟是社交软件，本质都是账号互加”。运营口径：“这种统计的时候每个导购都算 1”。**措辞纪律**：写文档时用「同一好友可被多个导购账号添加」，归到「关系对维度」，**不要叫“跨账号重复”或归为数据质量问题**。推论：① 导出按好友维度平铺、**不做好友去重**——同一好友被两个导购加过就出两行（正常结果，不是例外）；② 列表优化（方向 A 主从视图）的定位是**视角分层**（一级行=一个导购账号，展开看它加了哪些好友），不是“去重”；③ 所有“好友数”类指标必须写明口径（关系对 vs 好友去重），报表按关系对走。**不要再靠抓全量列表验证这件事**——直接问业务/研发一句即可。

**业务场景句（需求原文口径，写方案/评审直接引）：**「用户通过线上或线下联系导购 WhatsApp Business 后」→ 导购加用户为好友，形成「账号—好友」关系。术语统一用**导购的 WhatsApp Business 账号**（对应字段「导购私域账号」）；**接入形态（Business App / Business API）未经用户确认，文档里不写具体形态**，只写“已授权接入 vivo 后台、可管控聊天记录、达到国内企微效果”。

**导购账号管控链路（1023 用户补的架构事实，写方案/评审必用）**：vivo 通过 **WhatsApp Business**（1023 用户术语：不叫“商务授权”）把导购的账号接入 vivo 后台，由此**管控聊天记录**（可监管、可合规审计）——**达到国内企微的效果**。这条是外销私域工作台存在的根据，也解释了列表里为什么有「授权状态」「账号所属导购/工号」这些账号维度字段。评审被问“为什么能管控导购的消息”时用这句答。

**该页仍待定的一件**：① 本次优化与一期需求（新增筛选 / 8 个字段 / 导出）**是否合并成一次改**（别改两遍同一页）。导出维度（好友维度平铺、每导购算 1）与 1:N 口径已定，不再是待确认项。

**该页一期需求的去留：用户 1022 定「保持不砍」（原话：加比砍的成本更高），优化项排到评审后**。不要再主动提议砍掉或把优化塞进发版范围；改动与同源需求**合并成一次**。

## 六、需求 list / 功能点拆解规范

在线需求 list 的列：`需求人 提出时间 期望完成时间 需求名称 主要场景 需求价值 所在端 1级菜单 2级菜单 3级菜单 4级功能点 5级功能点 功能点描述`。

- **粒度要粗**：一行一个功能点，**不要按字段分行**（用户明确反对）
- **不写「不支持」的项**（如列头排序不支持），免得误会
- 导出必须写「**导出当前筛选条件下的全部结果，含当前页，不受分页限制**」——写「非当前页」会被理解成不含当前页
- 列表字段 ≠ 筛选项，不要一加字段就加筛选
- **不要从「原型现状」反推需求行**：需求 list 只写需求方提的。曾把原型里既有的「人数预估」当成需求写成一行，被追问「这个预估是你臆想的？」才发现需求原文根本没提。从现有系统看到的东西 ≠ 需求，别自己立项。
- **改 TSV/Excel 的脚本，先 `print(head)` 再动手**：曾按错列下标（把第 10/11 列当成第 5/6 列）跑改写脚本，脚本“成功”但 **0 行改动、静默没生效**。列数多时先打印列头 + 逐行打印定位列，再写替换逻辑；改完回读校验（grep 旧值应为 0、grep 新值应有命中、总行数对）。
- **交付时附「需求 list ↔ 原型图」对照表**：用户会要求「把需求 list 和原型对应好」。出一份 xlsx：Sheet1 = 需求行 × 对应原型图 + 看图说明；Sheet2 = 反查每张图归哪几行 + 状态（已出/作废）。**一张图可对多行**（“配置详情”弹窗一图管基础信息/数据源/使用限制/行为属性四行），**一行也可对多图**（筛选条件 = 列表页 + 交互细节图）。把「共用图」「配套图」显式写出来用户才不绕；**没有独立需求行的画面**（如明细页）先挂在相关行下当配套图；但用户可能要求**单列一行**——明细页最终就是单列的（`触达计划 | 新建/编辑计划 | 明细 | 行为 | 条件明细展示`），他开口就加，别坚持「不造行」。
- **需求 list 有两份在并行维护，交付前必须核对差异**：用户在**他公司的 Excel**上改（真正交付口径），我在 VPS 的 TSV 上改（我的工作稿）。两边会分叉且互相不知道——曾出现用户已把 2 级菜单改成「新建/编辑计划」并新增「明细」行，我这份还是「计划列表」且没有明细行；反过来我这边有「筛选条件」行、他表里没有。**规矩**：① 每轮基于需求 list 出 PRD / 线框 / 对照表**之前**，先让用户发一张**当前 Excel 截图**，逐行比对后再动手；② 我改完 TSV 要显式列出「我这份 vs 你那份」的差异清单让用户拍板，不要默认已同步；③ 最终口径以用户的 Excel 为准，TSV 只是工作稿；④ **用户 Excel 里「数据报表 │ 私域分析报表」那一行是给领导知晓用的，不是本期开发范围**——他明确说「我这边留着，你不用管」。所以**不要把它当成本期范围差异报给用户、也不要往评审 PRD 里加**，我这份功能清单保持本期口径（好友列表 3 + 用户行为 7 + 触达计划 2 = 12 行）即可。

**二期（跟进版本）7 条需求的「分析档」产出规范**（用户会先过内容、再让本地 agent 跑全量）：

- **结构**：开篇总览表（序号 / 需求名 / 原文优先级 / 涉及端 / 主要依赖 / 建议排期段）+ 逐条七段（① 原文摘要照抄不改写 ② 业务场景与价值 ③ **现状核查带生产源码 `文件:行号`** ④ 实现方案按端给 MVP ⑤ 前置依赖（外部：大数据表 / VK 订单 / 合规；内部：哪些能力要先做）⑥ 优先级建议 + 理由 ⑦ 待确认）+ 结尾「整体判断」（建议先做 / 建议合并 / 建议暂缓，每条带理由）。

- **不接受的回复**：“#5–#8 沿用旧评估、不复核源码”——直接退回，至少要求相关度高的条目复核。
- **原文绑定句必须先回原文定位再下结论**：“此功能和 X 一起上”这类句子往往只写在**某个子项**（如 4a）底下，不是整条——1022 复核搭出来一条：分析档写“4a 和 4b 都跟预售一起上”属过度解读，回查原文后发现那句只在 4a 下，4b 并未被绑。改法：只对确实被绑的子项写绑定，其余写独立排期，并把“能否先行”列成待确认挂需求方。
- **复核回收后由我分层处置，不照单全改**：① 结构性前提（上游能力未交付 / 外部数据源未接入）→ **我回写分析档的依赖节**（权威源），再让方案稿同步——“只写在草稿里等于没写”；② 口径错误（原文被过度解读）→ 回原文核实后改权威源；③ 机械可修（外引路径 / 过期时间 / 名称不一致）→ 我一次性改掉，不占 bot 轮次；④ 已由我处理过的→**明确告知对方不用补**，防重复劳动与二次口径漂移。
- **时效与内部证据要在文档头部交代**：原文“期望上线时间”过期就在总览 TSV 与正文里逐条标「已过期，需重排」；分析档引用的源码行号/证据档是**内部件该有的**，在头部加一行「内部证据文件」说明来源类型就行——否则外部复核方会把它当“无出处”报上来（属误报，不要因此去删证据链）。

## 八、我犯过的坑（别重犯）

1. **删除类指令**：用户说「删内容」只删文件、保留目录结构，不等于删文件夹。动手前先复述「删什么、留什么」。
2. **数据口径**：曾把 13 国当 14 国、把 107 授权号与 108 导购并列造成矛盾、把「非当前页」写反。凡涉及数字先回原文核对。
3. **过度设计**：曾建议为「服务端数据表」单独功能点立项、把报表指标口径往 CMS 范围里塞——都被驳回。取数不改字段值就不需要立项；报表指标口径是大数据对业务的事。
4. **不要替用户圆场**：他说「这块不一致了」时，先独立核验数据，不要顺着他给的解释编理由。
5. **历史文档里的菜单路径和步骤号会过时，一律以原型源码为准**。曾发现方案文档写着「配置中心 → 事件配置」、「触达计划第 2 步」，而原型实测分别是`权限中心`和`第 3 步`——旧口径已散落在文档和线框 HTML 标题里。**要引用菜单路径/步骤序号时，先读 `src/config/menus.ts` 和对应页面组件核对，别从旧文档抄**。发现旧口径就对用户列出来，等确认后一次性改完所有落点（文档 + 线框标题 + 功能点 TSV）。

6. **领导认可过的既有图不要重画，只能原图搬入**。上线报告的「产品架构」「产品定义」要用凌桥当初画的图（支撑策略图 / 产品定义页），他会拿原图逐字比对，重画必被驳回（原话：「直接用我之前那种房子图以及线框图，不要改动；不然凌哥不给通过」）。做法：源 pptx 300dpi 渲染 → `ImageChops.difference` 求非白外接框 → **只裁四周空白边** → 等比缩放放入。同一张图可能有多个版本（26 年规划 P12 带红色「26 年关键目标牵引」列，P29 没有），**以用户圈选的那一版为准**。

7. **拿不准口径就先写下理解再动手**。比如「不要用时间标签」→ 我理解为模块名统一「用户行为」、技术词「事件表/事件编码」保留，先写出来让他确认；比改错一轮划算。同类的还有「删内容」≠ 删文件夹。

8. **视觉模型读中文表格会认错字，关键口径不能只靠截图 OCR**。曾把用户表格里的「受众圈选」读成「受众筛选」，并据此报了个假差异，被用户当场纠正（“你图像识别的模型有问题”）。规则：① 用 `vision_analyze` 读截图只当**辅助**，涉菜单名/字段名/状态值这类**关键字符串**，必须回源码或原文件核对（如 `src/config/menus.ts`、`ChannelStepForm.tsx`）；② 向用户报「差异」前先自问“这是我实测到的，还是我 OCR 到的”，OCR 到的就标不确定、别当结论；③ 合并单元格多的表格 OCR 容易漏行（曾漏报一行，用户回“我没截出来，是有的”）。
   ④ **带颜色高亮的表格截图（名单、对接人表、配置矩阵）另有专门做法**：颜色归属靠像素扫描（PIL）定，不靠模型叙述；人名逐格裁切放大 4x 拼成带编号的图再一次识别；行标签单独裁左列读。完整步骤与坑见 skill `web-article-reading` 的 `references/table-screenshot-ocr.md`。**三次 OCR 结果一致 ≠ 正确**——同一个模型会犯同一个错，用户说“名字对不上是你读的不准”时以用户为准。

9. **绝不把「我设计的」当成「原型现状」写进交付物**。这是本项目最贵的一类错误：写需求 list / 线框 / PRD 时，把自己推导出来的设计（数字拆分、交互行为、校验规则）写成了陈述现状，用户一看就发现“原型里根本不是这样”。**规矩**：写任何一条描述前先问自己“这是需求原文/原型代码里读到的，还是我推的”——推的必须显式标注（“本期新增”“建议”），或干脆先问用户。引用原型事实时**带上文件行号**（如 `ChannelStepForm.tsx:145`），让用户能当场核。

10. **回答「真系统里有 X」前先分清证据是哪一层，绝不拿低层当高层说**。手上关于真系统的证据只有三类，可信度依次递减：① 我实测过的真系统截图或线上页面；② 我们**复刻原型**里的代码（`99-产品原型prototype/`，当年照生产端复刻，但**不等于生产端**）；③ 复刻原型里的**注释**声称「对应生产端 xxxComp」（是原型作者的话，我没核实）。用户会直接追问「你说的原型里有，是指 99 原型这个目录下的代码吗？」——被问到了就如实说是哪一层，并明说「我不能证明真系统有」。含糊说「原型里有」会被当场戳穿。手上真系统截图只有 `08-相关资料/产品审计/外销预售V5.1.0/验收截图/v2-engage-*.png` 四张（选渠道弹窗 / 计划列表 / 日期选择 / 提交结果），**都停在向导之前，拍不到步骤条**——要坐实「触达计划 6 步」「第 6 步预览」这类事，只能让用户在真系统点一次，或问负责该模块的同事，别把复刻当权威。

11. **同一口径的改动会跨多个交付物，且用户自己也未必定得下来——先确认「定没定」，再决定改不改。** 一个字段名（如「首次添加时间 / 首次添加日期」）可能在几轮内被来回改好几次，而它散落在四处：评审 PRD（`.md`）、需求 list（TSV + 导购用 xlsx）、线框（HTML 源 + 已发出的 PNG）。规矩：① 用户说「**先按 X 来，不阻塞**」「稍等我确认下」= **X 只是占位，不是定稿**，照用即可，但别在文档里加粗强调、也别当成已定；② 每轮真改，**先把四处落点列出来一次改完**（PRD 全文 `replace_all`、需求 list TSV、xlsx 重生成、受影响的线框图重出），别只改手边那一份；③ 改完回读校验：`grep 旧值` 应为 0、`grep 新值` 应有命中、TSV 行数不变；④ 同一口径反复变超过两次时，先问一句「这条定了吗，要不要先跟需求方对一下」再动手。

12. **「有几版 / 有几个文件」这类问题，必须全盘 `find`，不能只数手边目录、更不能凭会话记忆答**。曾答「上线报告共 3 版」，用户回「我那边显示 7」——实际是 **3 个正式版 + 2 个回滚备份 + 2 个更早的稿**（更早的稿不在 `deliverables/`，而在另一个仓库的 `share/` 目录）。规矩：① 被问数量先跑 `find / -iname "*<关键词>*" -not -path "*/proc/*" -not -path "*/sys/*"` 扫全盘，再按类分组列给用户（正式 / 备份 / 更早稿）；② 交付物会被脚本反复重写，**同一个文件在不同时间页数可能不同**（曾出现 v2 被后续脚本覆盖，页数从 32 变 35）——报页数/字节数前重新读文件，别用早先读到的值；③ 会话中间若发生过网关重启，**跨断点的“做过几版”记忆一律不可信**，直接回磁盘数。

- **不撞车的判据是“文件清单是否重叠”，不是“谁先谁后”**：把两边要动的文件各列一遍，不重叠就不会冲突（各自提交后 `git pull --rebase` 即可）；重叠的文件（常见的 `index.css`、共享组件、`App.tsx` 路由）要么避开——**在增量指令里显式写“不要动这几个文件”**，要么那批改动先 push 再并行。
- **出图/截图类任务必须用“装了最新原型改动”的那台**：原型页面本身没同步时出图，出出来的是旧形态，“图全对但全是错的”——这类要排在同步之后。
- **公司机导出的文件可能被企业透明加密**：文件头是 `%TSD-Header-###%` 而不是 `%PDF-`（或 Office/zip 的可识别头），VPS 上任何工具都打不开，也**不要去研究怎么解密**。可行路径只有三条：① 让用户在公司机上**截图发来**（图片不走加密）；② 让用户把正文贴出来；③ 从 **git 历史**取回上一版同源包（`git cat-file -p <blob> > x.zip`）——先跟用户确认是不是同一份内容。**④ 让用户把文档导出成图片压缩包发飞书**——实测可行（120 张 PNG 的 zip 直接能收，落到 `/root/.hermes/cache/documents/`）；收到后**存 VPS 仓库外**（如 `/root/presale-180/`），别塞进 `cms-project` 把刚瘦下来的仓库又撑大。诊断做法：`file <f>` + `head -c 200 <f> | xxd` 看头部，再下结论；别拿扩展名当格式。
- **产物与自检报告的上传通道是「每项目一份」，不是全局配置**：写在项目根的 `.agents/rules/antigravity-rules.md`「产物自动流转管道」节。`AGENTS.md` 里只有「报告存 `08-相关资料/审计报告/`」和 git 地址，**没有上传地址**，别去那儿找。
  **当前定稿通道 = 杰西卡（用户的公司 VPS 侧 agent「娜美」已废弃，通道与审查都归杰西卡）**，命令与契约：
  ```
  curl.exe -X POST -H "X-Jarvis-User: ai-reports" -F "file=@本地路径\报告.md" https://pmlophy.com/p/jarvis/file/upload
  ```
  三个要点：请求头 `X-Jarvis-User: ai-reports`、**表单字段名 `file`**（服务端 `req.multipart()` 取值，所以必须 `-F`，不能用 `--data-binary`）、成功返回 JSON 且带落盘路径才算送达（落在 `/var/lib/jarvis/files/ai-reports/`）。旧写法 `-X POST --data-binary ... http://10.103.183.179:8083/upload/x` 是娜美的公司内网端口，**已废弃，不要再用**。
  推论：① **改通道要逐项目改这份文件**，且我和用户的仓库副本各存一份（`cms-project`、`cms-src/` 下的克隆）都要同步——三份内容必须一致；② **上传目的地决定了谁来审**——传到哪台，就触发那台的审查 cron；③ 公司电脑上可能另有**用户级全局 rules**，仓库里看不到，换通道前先让用户确认并截图。
- 评审批次记录只改署名，保留版本行与修改内容
- **给领导看的 UI 图，直接给 PNG，不给 HTML**（2026-10-20 用户定：「下次给我图，不要 html 了，这样更方便」）。同一场景的多个画面**合并成一张长图**（用户：「这样连贯些…可读性高」）。写 HTML 只当中转，出图后**发 PNG 附件**；HTML 源文件留在 `/root/deliverables/` 供后续改。

**出图分工（1020 起，用户定）**：出线框图/原型图**默认不归本 VPS Hermes**。用户原话：「后面出线框图给本地 agent，或者网页版 chat 出就行，除非紧急」——本 VPS 可用内存只剩 ~900MB，网关自己占 550MB，还要留余量给会话。

| 场景 | 谁出 |
|---|---|
| 常规线框图 / 原型图 / 长图 | **本地 agent（Cursor / 反重力）或网页版 chat** |
| 紧急（用户当场等图） | 本 VPS 出，但**必须套 `systemd-run` 限内存**，禁止裸跑 Chrome |
| **给 agent 当对照用的形态参照图**（配 `参考-*.png` 放进仓库让它自己打开对照） | **本机直接出最快**——走 agent 浏览器的 `browser_exec`（见下），不受 Chrome OOM 限制 |

转交出去时要把话说到位：2 倍图（宽 1450px）、分几块、怎么拼成长图、全中文、只用真实数据不编造、每个线框下带「看图要点」。

**出 PNG 的完整流程**（VPS 已装 Chromium，但**直接跑 Chrome 会把网关 OOM 杀掉**——曾一天被杀 6 次，用户要求停 Chrome。必须先套内存隔离）：

```
systemd-run --scope -p MemoryMax=700M -p MemorySwapMax=0 --unit=shot-$$ /root/.agent-browser/browsers/chrome-155.0.8059.84/chrome --headless=new --no-sandbox --disable-gpu --hide-scrollbars --force-device-scale-factor=2 --window-size=1450,3000 --screenshot=/绝对路径/out.png file:///绝对路径/x.html
```

- `systemd-run -p MemoryMax=700M` 把 Chrome 关进**独立 cgroup**，爆也只爆它自己，不连累网关（约 980MB 可用内存下实测安全，渲染完内存无异常）。
- 窗口高度先给足（如 3000），渲染后用 Pillow **从底部往上扫第一条非空行**裁掉多余白边再发；同时看底部留白，**< 40px 说明被截断**，要把窗口调更高重渲。
- 多图合长图 = 多个 `<div class="frame">` 竖排在同一 HTML 里（每帧 `margin-bottom:26px` 即可）。
- **LibreOffice 渲 HTML 会把 flex 布局渲坏，别用 soffice 转。**
- 线框 HTML 写法：新增项用蓝色小标签标出、现有项灰字，领导一眼看出改了哪些；每个线框下加一条黄色「看图要点」把业务理由写上（如「首次添加时间与最新添加时间必须同时存在」）
- **线框 HTML 的拆分/合并按用户当次所说**：他会一会儿要「拆成多个独立文件」（说「分开啊，不要反正一个html中」）、一会儿要「合到一个 html」——照当次指令办，别固定成一种。

**用 agent 浏览器（`browser_exec`）把 HTML 出成 PNG——本机首选路径，不必碰 `systemd-run`**：写 HTML → `new_tab("file:///绝对路径/x.html")` → `cdp('Emulation.setDeviceMetricsOverride', width=<比内容宽>, height=<给足>, deviceScaleFactor=2, mobile=False)` → `capture_screenshot()`。两个坑：① **视口必须比内容宽**（内容 1440px 就给 1560px），否则右侧一列直接被裁掉，PNG 看着“完整”其实缺内容；② 截图存的是临时路径，出完要 `cp` 进仓库目标目录再核字节数。
**参照图交付前两件自检（缺一个，agent 就会照着错的做）**：① 用 `js()` 数一遍要素，如 `js("document.querySelectorAll('th .v').length")`，确认该有的标记数量对得上（曾漏给第一列加筛选小三角，图里就少一个）；② 用 `vision_analyze` 读一遍成品图逐项核（标记是否齐全、控件样式对不对——单选面板画成方框勾选就是错的、有没有被裁切），不对就改 HTML 重渲。

## 九之三、并行派活（外部 agent）与目录边界铁律

**外部 agent（grok bot 这类多机器人团队）的派活判据**——它无内置浏览器、无公司内网登录态、网络非内网，所以只接：**输入自包含（文件或粘贴）、输出为文档或代码、不需登录态与内网**的任务。需内网截图 / DOM 取证 / 访问本地仓库的活一律交 Cursor（公司 ThinkPad）。

- **输入要显式列文件清单**：它的沙箱只能读指定盘（如 C 盘）——先把材料复制到它能读的目录，指令里写**精确绝对路径 + 只读 + 只处理其中哪一节**。写「参考项目里的文档」它读不到，会自己编。
- **成套派活模板（多 bot 并行）**：一个 bot 一条需求 / 一个页面，统一八节（①原文摘要 ②用户场景 ③功能点拆解 ④交互草案 ⑤字段草案 ⑥依赖与前置 ⑦待确认（写明问谁） ⑧验收清单），Checkpoint 先交 ①③⑦ 三节确认口径。
- **另留一个复核岗 bot**：只挑毛病、不写方案——按六类找（无出处的事实 / 自相矛盾 / 遗漏边界 / 依赖漏项 / 优先级理由站不住 / 术语不一致），产出「位置 + 问题 + 依据 + 严重度 + 建议」。
- **回收后由我统一过一遍**（术语、重复字段、依赖冲突），别让 N 个 bot 各写各的直接入库。
- **红线模板**：不编造系统实现 / 接口字段 / 表名；不引用给定文件以外的信息（含模型通识）；不给排期工时；不输出代码；不执行任何 git 命令。

**目录边界铁律（误删事故后定，写进每一条涉及 clone / 新建 / 移动目录的指令）**：

> 只在 `<目标目录>` 内操作；**禁止删除、移动、重命名该目录以外的任何文件与目录**。

本地 agent 越界清理的后果是整个项目目录消失。**恢复顺序**：① 先查 Windows 回收站（最快的整目录还原）；② 从 GitHub 重 clone——VPS `/root/repos/` 下每个仓库都能拿到远端地址与最新提交 hash，可直接报给用户；③ 生产源码目录（`E:\projects\源码管理`）从公司 GitLab 重 clone。
**动手恢复前先自查本地有无未 push 的改动**（拿用户本地状态对比 VPS 镜像的 HEAD）：有就先捞内容再重置。「另一个磁盘有备份」是常见情形，所以先问清有无备份，再决定走哪条。

## 十一、工作日报写作口径（1020 用户定稿）

**先想清楚日报是给谁的**：读者是领导与绩效留痕。它只回答三个问题——**交付了什么、完成到什么程度、明天往哪走**。它是工作产出汇报，**不是工作日志**；不记录「我怎么做的」「谁说的」「用了什么工具」。用户把口头稿改完后的原话：「别只存啊，要先会，先懂，再存」——**写完先对照下面的规则自查，再落盘**。

**十条禁令与要求**

1. **不出现「领导」字样**。改版依据只说「按意见改版」，不写「按领导 5 条意见」。
2. **不出现内部文档体系分层名**。`PRD套件`／`评审PRD`／`业务PRD`／`Demo PRD`／`字段清单TSV` 一律换成业务口径说法：「产品方案」「页面交互说明」「需求清单」。日报读者不需要知道我们内部怎么分层。
3. **只写产出，不写做法**。删掉「沿用哪张图」「新增了哪 3 页」「用什么方法做的」这类过程描述；一个 D 子项压到 1–2 条即可。
4. **不写交代不了的原因**。如「原型标注未做」就到此为止，不补「因为原型里还没有用户行为页面」。能力缺口不在日报里展开。
5. **产出物写全称**。「上线报告」→「上线报告PPT」；「触达计划」→「触达计划数据报表」。
6. **C（检查）结论先行**。先说完成度（「已完成初稿」「今日未推进」），再谈其余；不要把指标罗列在前面。
7. **A（明日计划）要往前推**，不停在收尾动作。用户会把「报告补完数据后提交」换成「开展私域2.0 二期 7 条原始需求的分析」。
8. **全程不出现 AI／工具名**（AI、Codex、Cursor、Hermes 等）。
9. **变更要外归因**。自己发起的变化写成依据外部要求，如「好友列表筛选改为表头筛选（按交互规范要求）」。
10. **格式与发送**：标题 `【MMDD 刘龙飞工作日报】`；章节 P（计划）／D（执行）／C（检查）／A（改进 & 明日计划）；条目用 `1、`（不用 `1.`）；D 下分 `D1.` `D2.`；**P 承接前一天的 A，前一天计划了没做的如实进当天 C**。发飞书时**纯文字**——无 md 符号、无代码块、不发表格；**标题行与正文之间空一行**（用户 1022 订正：“我的是标题换行”——只有标题后要空行，**正文条目之间不要空行**，别把正文也撑开）。
    - **交稿前必做 P↔C 回扣检查**：当天 P 段的**每一条**都要在 C 段找到对应结论——做了写完成度，**没做的必须明写「今日未推进」**。曾漏掉 P 里「继续分析私域2.0剩余7条需求」，用户一眼看出「检查中少了私域2.0 7条需求分析没进展」。漏写未完成项 = 读者会默认它做完了，等于智报进度。（同一条只检查“前一天 A→今天 C”，会漏掉“今天 P→今天 C”。）

**三条高层原则（上面十条都是它们的推论，拿不准时回到这里判断）**

11. **不写「因为 X 要求、所以我做了 Y」这种因果句**。一旦把事项绑到指令来源上，事情没问题时显得没主见（“领导说啥你干啥”），出了错就把指令发出人一起拖进来担责。日报只写**做了什么、达到什么进度**；改版依据最多写到「按意见」为止，再往前一步都不要写。用户原话：「也不要写什么领导要求，然后我做了什么，这会没头脑，如果出现了错误，那领导还要跟你一起去担责咯」。
12. **术语必须让领导看得懂**。内部黑话（锚点、数据源表、评审PRD、角标）一律换成大白话；领导看不懂的词等于没写，而且会显得在推内部细节。用户原话：「包括你那个什么锚点，他知道是什么吗？完全不知道，写了没用，而且还会挨骂」。
13. **粒度对齐「交付 / 进度」，不是事项流水账**。不把一天从头到尾拆细列出来，领导不关心过程颗粒；一条 D 能说清“交付了 X、完成到 Y 程度”就够，多余的动作描述删掉。
14. **宽窄分两层：主线写宽，结果写窄**（用户 1020 定稿表述：「窄是我的阶段性结果，宽是我在做的工作内容主线」）。
   - **宽 = 工作内容主线**：D 的小节标题（`D1.` `D2.` `D3.`）就是主线——概括自己负责的工作块（外销预售180版本上线报告 / 外销事件标签 / 私域2.0需求整理），**跨天稳定延续**，不随当天做了什么而变。A 里的条目写的也是主线的推进方向，所以同样写宽（「补齐私域2.0一期剩余的策划内容」）。
   - **窄 = 阶段性结果**：D 主线下的编号条目、以及 C 里的每一条，都是一个具体可验收的结果。「完成」的主语锁在具体交付物上，程度也限定（初稿／部分／全部）。**不能写「上线报告已完成」或「私域2.0一期已完成」**。
   - 自检法：看 D 的小节标题是不是“一段战线”（跨天不换），看每条编号是不是“一个能拿出手的东西”（能指给领导看）。两个都对，粒度就对了。用户原话：「能写宽的不要写窄…比如后面可能还会出现完成了什么，那完成一定要精准，不要范围铺的很大」。
15. **整理类工作一律不进日报，日报只认交付物进度**。仓库瘦身、目录改名、规范修订、补 README、删过程稿、脚本归位——这些都是「怎么整理的」，没人在乎。领导只问一件事：**那个交付物到百分之多少了**。用户原话：「没人在乎你怎么整理prd的，只在乎你prd进度多少了，百分之50还是百分百」。
   - 判断法：这件事能不能变成一个具体交付物的完成度数字？能→进日报；不能（或只是让后续更顺）→不进。
   - 曾把「评审PRD 按需求块重组 / 字段清单补建 / 流程图重写」这三件当作产出物变化想补进当日 C 段，被否：这些都属“怎么整理”，而当日 C 段已有的「私域2.0一期产品方案与页面交互说明已产出」已经盖住了进度，不用再拆。

**输出前自查清单**：数一遍有无「领导」字样 → 有无内部文档分层名 → D 里还剩多少过程描述 → C 是否结论先行 → A 是否只剩余收尾 → 有无 AI/工具名 → 格式与纯文字 → **宽窄自检**：D 的小节标题是否跨天稳定（宽＝工作主线），每条编号是否是一个能指给领导看的具体结果（窄＝阶段性结果）。用户 1021 再次强调的原话：「以交付为主，往宽了说，向窄了收」。

**落盘口径**：用户改定后发回来的版本**即为定稿**，逐字落盘，**不要拿自己那版覆盖**。写完先自查再落盘（用户原话「别只存啊，要先会，先懂，再存」）。

**校验必须能失败，自证式的检查等于没检查**：把用户原文写进文件、再把文件读回来跟同一段原文 `difflib` 比对，两边同源，差异恒为 0——这种“全绿”没有信息量，用户一眼就会追问「怎么会 diff 为 0 呢」。**正确做法：`git diff <上一版提交> <定稿提交> -- <文件>`**，逐行看差异、并逐条对回用户这次到底改了什么（应只剩下用户明确改的那几处，多一处就是自己改过头）；再顺带确认没有多余回退（用户可能给的是一份早先的粘稿，见下）。
**用户可能粘回早先那版**：用户发来的“定稿”内容有时是复制了更早的消息（少了之前加的条目），而口头上说的是格式要求。**不要默默按最后一次粘的覆盖**：先拿新旧两版逐条比出差异（哪几条被去掉/回退），把差异列给用户一句“确认要这版内容吗”，得到确认再落盘；只对格式（换行、空行）的要求，就只改格式、内容保留最新那版。

**触发前提**：本规则在 `vivo-project` skill 内——写工作日报/PDCA 日报前**必须先载入本 skill**再动笔，不要凭印象直接写。

## 十一节附：需求准入与业务结果铁律（2026-10-23 用户定）

业务方提需求时，不能只给一句功能描述或一句“要上线”。至少要同时给出：

1. **业务数据**：现状规模、基线、涉及国家/渠道/用户量，不能只凭感觉判断问题大小。
2. **ROI 或收益口径**：预期带来什么收益，如何计算，不能只说“提升运营能力”。
3. **计划与目标**：上线时间、面客时间、运营负责人、目标值、使用计划和验收节点。
4. **前置条件**：人员、代理、合同、物流、财税、渠道、流量、内容等是否准备完成。
5. **结果复盘**：上线后必须对比原定目标与实际结果，区分产品交付、国家使用、运营投入、外部依赖和通道问题。

产品评审时要把“需求目标 → 产品能力 → 上线条件 → 业务结果”串起来；缺数据、ROI、计划或目标的需求，标为业务输入不完整，不能直接把结果责任全部归到产品。

## 十一节附：不飘不脑补铁律（2026-10-22 用户定，原话“有不清晰和歧义的，不要飘逸和脑补，需要澄清的就列出来，否则我要担责的”）

产出（分析档 / 方案 / PRD / 给 agent 的指令）中凡遇到**不清晰或有歧义**的地方：

1. **默认动作是“列澄清项”，不是“给一个看起来合理的结论”。** 每条澄清项写清：不确定的是什么、会影响哪个结论、要问谁。
2. **确需先往下走时，假设必须显式标记**：「口径假设（<日期> <谁拍>）：…，待需求澄清」——不能写成事实句，不能悄悄当成已定口径。
3. **区分三类写法**（对应追责）：事实（带出处）/ 推断（标“推断”）/ 假设（标“假设+待澄清”）。三者不得混写。
4. **给外部 agent 的指令同样加这条红线**：遇歧义停下列清单回来问，不许自行判断往下做。
5. 自检：交付前问一句“这里面有几处是我猜的？”——答不出具体条数，就是没做到。
6. **不把“和某人确认过”当依据写进文档（2026-10-22 用户定）**：方案/PRD/日报里不写“与某同事已确认”，除非那是需求方的正式拍板（且用户指定要写）。设计依据只写**事实性来源**（如“参考内销的事件与标签设计”）与**目的**（如“满足业务灵活配置圈人”）。理由：把依据绑到具体人身上，事情顺时显得没主见、出问题时把人拖进来自然。
7. **内外销对标只看功能与交互，不碰技术实现（2026-10-22 用户定）**：用户是产品经理不是开发，拿内销源码对标时**只对功能面与交互面**（菜单位置与菜单结构、列表列与操作、表单字段与校验、配置界面形态与示例值）。**不要写“需后端才能对齐机制/口径”这类依赖**——后端只作可选佐证（评审时开发问“技术上怎么实现”，有内销案例可引）。产出用“内销长什么样 / 外销怎么做 / 差在哪 / 要不要对齐”四列形态对照表，不写实现细节。
8. **内外销对标取证口径**（菜单位置、用户行为列表形态、触达计划与人群洞察链路、事件 vs 标签的答复口径、对标写法）见 `references/neixiao-benchmark-evidence.md`。取证只能靠用户机器上的 Cursor 内置浏览器（内销源码独立只读、不外传）；**没取到就写“未观察到”，绝不可写成“内销没有”**。
9. **澄清项要收敛分类，不是倒垃圾（2026-10-22 用户评“澄清项不能太夸张了吧”）**：一份方案里堆上百条澄清项 = **没做判断**。按「谁能答 / 不答的后果」分三类：
   - **A 必须外部答**（需求方 / 大数据 / 其他团队）——只留“不答就做不了、或判不了验收”的；每份需求最多 3 条，超出先合并同类项、按优先级排。**评审会只过 A**。
   - **B 设计选择**（自己就能拍的：入口位置、列表列、文案）——单独成表，给建议 + 理由，标注待产品拍板。
   - **C 开发实现**（接口怎么调、表怎么建、并发怎么处理）——给“开发确认”清单，不占产品澄清位。
   - 另把两类**从澄清项里剔出去**：材料缺口（图未转录等）→ “补材料清单”；现状核查（要查代码/环境）→ 核查项。三者性质不同，混在一起只会虚高条数。
   - 每条必须四列齐：不确定的是什么 / 会影响哪些结论（写“改了结论怎么变”，不是堆编号）/ 问谁（**具体人或角色，不许“待指定”**）/ 优先级（带理由）。
   - **外部 agent 产出的澄清项同理**：回收后先按上面分三类，不要照单接收；会上只拍 A 类，其余书面分发。

**删旧产物时别按分组名整份删**（1020 事故）：清 旧字段清单时，看到第一列分组写「报表维度/报表指标」就判定整份是报表的、不属本期 → 删了。**实际 64 行里 21 行属本期**（好友列表-会话分析字段 8、好友列表-筛选区 2、触达明细 11），而「用户行为」整套字段旧稿里根本没有、必须新做。

判断法——逐个分组标三态，不是二分：

| 状态 | 处理 |
|---|---|
| 已废弃 / 已移出本期 | 删 |
| **本期相关但口径已变**（如好友列表从「顶部筛选区」变「表头筛选」） | **重做**，不能删 |
| **本期新立项、旧稿没有的** | **新建** |

所以正确动作是「**重做整个 02-字段清单/**」，不是「删掉它」。删之前把每个分组的行数打出来（`cut -f1 | sort | uniq -c`），一眼能看出哪些分组还活着。

自检三件套：① 列宽集合 == {13}（详细稿）/ {5}（初稿）；② 需求 list 里的字段全部在册；③ 评审 PRD 里提到的字段全部收录。

**Demo PRD 的固定 11 章**（重做时直接照旧文件抄骨架最快）：版本记录 / 页面概述 / 页面布局（ASCII 框图）/ 筛选条件（或字段）/ 操作按钮 / 交互说明（表格：序号丨操作丨结果）/ Mock 数据示例 / 异常处理 / 关联文档 / 变更日志。一个模块可一个文件覆盖多页（如「受众圈选与明细」合一）。

**业务背景 / 业务价值的写法**（用户会直接贴需求原文让你重写这两节）

- 背景要**实据**：先写现状数据（账号数 / 好友数 / 门店数 / 导购数），再**逐条列系统缺口**，缺口措辞用需求原文。
- 结构改成**「缺口 ↔ 本期能力」一一对应**，不要平铺一长串问题（如“用户行为对应缺口 2；好友列表对应缺口 1、3”）。
- 价值分两层：**定性价值（需求方原文，逐条照抄）+ 经营价值（表格）**，不自己另编一套。
- 运营计划单独成节（配合哪个新品、后续追踪频率）。
- **需求原文里的数据是有时点的**（如「线上共存账号 17 个、好友约 2 万」是需求提出时，与后续实测差十倍）——引用时带上时点（“截至需求提出时”），别和实测数据混在一句里；两个数要不要都留先问用户。

**重做 ≠ 缝补**：用户换口径时要求**整套重做**（“不要再缝缝补补了”），不是逐文件改。重做后**正文零残留**：`grep` 旧口径关键词**只应命中「版本记录」与「变更日志」**（保留历史留痕是对的），正文命中就是漏改。

**交付前两项自检（必跑）**

1. **序号核验**：业务规则表 / 页面表 / 字段表的序号都要**每表从 1 重排**。做法：正则切 `^#{2,4} \d+\.\d+` 分节 → 每节抓 `^\|\s*(\d+)\s*\|` → 断言等于 `1..n`，逐表打印。曾插入新行没重排，出现两个第 11 条。

**评审 PRD 的多需求块结构：按块平行拆，不按职能穿插**（用户 1020 定）

**`.gitkeep` 与空目录**：

- `.gitkeep` **只对真空目录有意义**——Git 只记录文件不记录空目录，空目录要靠它占位。目录里已有别的文件时它纯属多余，可删。
- 用户判定：**只有明确要保留的归档目录才补 `.gitkeep`**（如 `05-提示词合集/`），其余空目录一律不留——「将来真往里放文件时 Git 会自动重建整个路径，不用提前占位」。
- **⚠ `rmdir` 会向上递归**：删掉一批空子目录后，父目录变空会被连带清除。曾因此把 `05-提示词合集/` 整个删掉（它在那批子目录移除后也成了空目录），而且同一条命令里后面的 `.gitkeep` 写入因目录已消失而失败，**提交后目录从仓库消失，只能再补一个提交恢复**。正确顺序：**先把要保留的上层目录和 `.gitkeep` 建好并提交，再删下层空目录**。
- 同理，`git mv` 大目录后会留下空壳（如 `docs/` 解散后磁盘上还留着空的 `docs/flow/`），git 已不跟踪但要手动 `rmdir` 清掉，否则用户翻目录时会以为文件没了。

**清理自己的中间件时把生成脚本留下**：`/tmp` 里的一次性渲染目录/脚本、`*.bak-*`、`__pycache__` 可以清，但 `gen_ppt_brand.py` / `polish_pages.py` 这类**交付物生成脚本要留**——PPT 后续还要补数据，删了就改不动了。清完把关键交付物逐个 `[ -f ]` 核一遍。

- **标注在跑时冻结 PRD 正文（顺序铁律）**：原型标注的内容是**逐字搬 PRD「页面说明」列**的，标注指令跑的过程中改 PRD 会让标注与文档对不上——要改 PRD 口径（删外引、修过期句）就**排在标注跑完之后**。文档层与原型层可以并行，但**前提是不碰同一份文件**；一旦都碰 PRD 就串行。正确的即时反应是“我这边先按住文档层不动”，不是赶着改。
- **形态类改动要排在出图之前，图是最后一环**：整页红框图会被评审 PRD 引用，图里的形态错了等于白出。凡“改形态”的任务（筛选交互、列与字段、菜单结构），**先改代码 → 截图确认形态 → 再出图**；一旦图先出、形态后改，全部图重跑。同理，**标注跑完才出图**（`capture_orm.py` 靠 data-anno 锚点定位）。
- **菜单/导航类改动 = 全部整页图重出**：整页红框图带左侧菜单，菜单位置一变，已出的所有图里的菜单就过时了。判断影响面时直接把“重出全部图（含已交付的）”算进去，一次指令里做完，别分批——省下的那轮时间会被“图与系统不一致”在评审时吃掉。
- **参照图不要被内嵌进发布版**：为给 agent 对照而放进 `04-评审PRD/images/` 的形态参照图（`参考-*.png`）不属于 PRD 引用的图，生成 base64 发布版时要排除（内嵌脚本按 md 里的图片引用走，只要 PRD 正文没引用它就安全；指令里仍要写明“参照图不参与内嵌”）。

**标注交付的验收清单（1022 实操，按这套一次过）**

1. **角标数 = PRD「页面和操作」表的行数**：本项目 4 页共 11 个角标（2.4.1 三条 / 2.4.2 四条 / 2.4.3 三条 / 2.4.4 一条）。验收直接读 `04-评审PRD/annotations/annotation.config.json`——**「来源需求」数组条数 == 「角标」数组条数 == 目标页 PRD 行数**，三个数对上才进下一轮；config 的来源字段每条能回溯到 PRD 行号，是复核标记是否与文档对得上的把手。
2. **锚点验收看 diff，不看自报**：`git show HEAD -- '*.tsx'` 里被删的行应该是「同一行又加回 data-anno」这种形态；出现整段业务逻辑被删就是越界。弹窗类角标的锚点走弹窗组件透传（本项目在 `BusinessModal` 上加了 props 透传），所以页面文件里 grep 不到全部锚点，**别据此判缺失**。
3. **六个 Tab 名逐字核**：全部 / 页面内容 / 交互说明 / 业务规则 / 字段说明 / 待确认——运行时旧版会把空的「待确认」显示成「待办 0」，属要修的文案 bug。
4. **拖拽类交互 agent 自测不了**：它驱动不了用 pointer 事件的悬浮容器，交付里会写「未能验证」——这类必须让用户人工拖一次，别把自报当已验。
5. **截图两项自检**：`find <目录> -type f -size 0` 必须为空；同批同用途的图跑 `md5sum` 去重（出现过同一张图两个文件名、自检 md 只引用其中一个）。
6. **标注完成后才派红框图指令**：`capture_orm.py` 靠 data-anno 锚点定位，锚点没挂完就跑只会出区域小图。

**发版前的三项校验（1022 实操补充）**

1. **「自包含」还要查一类外引：正文里的仓库内路径引用**——不只是黑名单词（TSV/详细稿/权威源/角标）。写 PRD 分析节时很容易顺手写「事实依据见 `08-相关资料/…/预估人数-证据档.md`」，交付前把带路径的句子改成内嵌表述（把依据写进正文），`grep -n '08-相关资料\|03-产品设计\|\.md'` 扫一遍。
2. **字段清单章节别当成缺项去补**：本项目每页节后面已经自带「XX-字段清单」小节，先 `grep -n '字段清单' <prd.md>` 再下结论。
3. **流程图已升到 V3.1（1022）**：方向放开为 `flowchart TD` / `flowchart LR` **按内容选**（线性步骤用 TD，分支回流多用 LR，同一套件内统一）；新增第 6 节渲染风格（灰白极简：浅灰填充 + 1px 浅灰描边 + 直角矩形 + 菱形判断 + 小矩形分支标签 + 细线小三角箭头，不加图标/阴影/圆角/编号/图例）；产物为 **mermaid 源码（权威）+ 渲染 PNG**（给人看时出 PNG，不发 HTML）。引用旧「统一 LR、不用 TD」的说法已作废。

**产出纪律：临时的进度/节奏清单不要落成项目文件（1022 用户定）**——“你记着就行，完成后勾一下”；项目仓库里只留正式交付物。要跟踪就放在我自己的对话/看板里，不要往 `03-产品设计` 或 `04-评审PRD` 里写 `发版进度清单.md` 这类文件（写了会被要求删）。
**但它必须有一个用户能再找到的落点**：只在聊天里给过、不落任何文件，几天后用户一定会说“我要之前那个清单，翻记录没找到”（聊天流里翻不到）。所以：① 每次给出这类清单，同时在 `/root/deliverables/`（**仓库外**）留一份 `.md`，回复里直接发 `MEDIA:` 附件；② 或把条目拆进看板 `dashboard.md`（我能随时读回）。**原则：仓库里不留，但不能只活在聊天里。**
**看板是待办的唯一落点，且要随进度勾销**：用户会隔几天说“拉一下任务清单看完成度”——那时直接读 `dashboard.md`，把 `- [ ]` 逐条按实情改成 `- [x]`（含“无需执行”的注明原因），push 后再回报，**不要重复答一份已经完成的清单**。

**PRD 与原型冲突的裁决（1022 原型标注时 Cursor 报了 3 处不一致）**：

1. **以已确认口径（原型/用户拍板）为准，由我回写 PRD**——不让 agent 停下等改文档（评审 PRD 正文修改权在我这边，agent 只读）；同时给 agent 一段可粘贴的口径答复（逐条编号、放一个 plaintext 代码块）。
2. **状态文案类统一到用户拍板的口径**：一期用户行为状态统一「启用 / 停用」，PRD 里残留的「已停用」属待回写的旧措辞。
3. **原型里不存在的界面不写进 PRD**：用户行为无独立详情页 → PRD 里“只展示列表与详情”的“详情”要删。
4. 回写后在「修改记录」补一行，不重构其他章节。

## 十三、补原型页面的前端指令（补图链路的第 ① 步）

链路第 ① 步 = 让本地 agent 把缺的页面补进 `99-产品原型prototype/`。原型技术栈、文件地图、向导步骤索引、指令骨架与红线清单见 `references/原型补页指令与代码地图.md`。

要点：

- **先核需求 list 再写指令**：每轮出 PRD / 线框 / 指令前，先要一张用户当前 Excel 截图逐行比对（见第六节）。
- **指令写五段式放一个 plaintext 代码块**（Context / Request / Output format / 红线禁止 / Checkpoint），开头写明执行位置（`cms-project/99-产品原型prototype/`，跑在用户本机而非 VPS）。
- **页面内容全部从 Demo PRD / 评审 PRD 逐字搬**，mock 数据照 Demo 的 Mock 示例抄，不做任何自己的设计。
- **分 Checkpoint 停下**：一批页面先做先截图，确认后再做下一批。
- **红线里必须写**：不新建项目、不装依赖、不引 UI 库、不动范围外页面、不删既有 UI（取舍权在用户）、不做登录/权限实现、不 commit/不 push/不部署；**删掉的东西先注释保留，不要物理删除**（不写就直接删，已删实现虽能从 `HEAD` 取回，但白多一轮）。
- **交付后必须 push 才能验收**：截图只验外观，命名/字段/条件结构要 pull 下来读代码核；只拿 agent 的自报当真会被用户当场退回（“不合格”）。省略这一步的结果是用户自己逐屏比对，然后回来说「不合格」，白跑一轮。**凡是「已删除 / 已移除 / 已改名」这类声明，必须 grep 代码确认它真的不在（或真的改了）**——报告说删了而代码里还在、说改好了而代码里没动，是常见偏差；以代码为准，把偏差单独列给用户并给回退/补做指令。
- **写指令时就把三条验收硬要求写进去**（1021 当场交付不合格后补的，效果显著）：① 对照表**每项带生产源码 `文件:行号` + 原文摘录**，没行号的不收（等于没做完）；② 交付前**逐项自查清单**：区块数量与顺序 / 每块字段 / 控件类型与默认值 / 所有枚举的**中文展示文案** / 按钮文案 / 右侧预览 / 页脚按钮；③ 每个区块出**生产端 × 原型端同屏并排对比图**（不要各截各的）。
- **枚举值不得当文案、按钮不得自创**：复刻曾把渠道直接显示为 `EMAIL / SMS / SMART_SMS`，而生产是 邮件 / 短信 / 富媒体短信；弹窗标题也不对（生产是「请选择触达渠道」，原型写成「新建触达计划」）、按钮 确定 ≠ 生产 提交。所以：凡从源码抄枚举，一律取源码里的中文展示文案；且要**同类问题全扫一遍**（筛选下拉、列表渠道列、状态列、触发类型/推送方式、WhatsApp 三模式文案），别只改手边那一个。
- **告一段落的前置：先确认页面结构已按生产源码对齐**。若还没对齐（不知道生产端到底是不是向导、区块叫什么），先走 `references/生产源码对齐复刻原型.md`，否则补出来的页面会建在错误结构上、白做。
- **口径不明处写「本轮不许动」并在聊天里单独问用户**：比如「明细页是新增一块还是替换原有渠道字段核对」「现有的人数预估这块砍不砍」——让 agent 自己决定就会造出我没设计过的现状描述。
- **agent 看不到你在聊天里贴的图，引用形态必须有图或有逐条文字描述**：指令里写「参照内销导购管理的表头筛选形态」而手边又没截图 = 它只能猜，**必然做错**（1022 实例：让它按内销形态做表头筛选，它做成了顶部筛选区，白跑一轮）。做法：① 先自己按规则出一张**形态参照图 PNG 放进仓库**（如 `04-评审PRD/images/参考-表头筛选形态.png`），指令里写**文件路径**让它打开对照（它能读仓库里的图片文件，读不到聊天消息里的图）；② 把规则出处（Demo PRD 的对应小节 + 交互规则段）逐条抄进指令兜底；③ 参照图里把「禁止做法」也写上（如「不要把筛选做成表格顶部的一排筛选控件」）。
- 指令存 `05-提示词合集/NN-名称.md`（编号即版本）；**先给用户看，用户点头再 push**。
- **指令的交付方式是「聊天整段发」，不是发文件**（用户原话「指令不要发文件，直接聊天发就好，老规矩啊」）。做法：正文写一两句说明 + 一个 plaintext 代码块整段贴，用户自己复制给 Cursor；**不要**把指令做成附件（MEDIA/文件），也没让存就不要往 `05-提示词合集/` 里写文件——这个目录是有意留空的，只在用户明确说存的时候才写。
- **补完页面要重新部署才能出图**：原型补页落地后，先 `npm run build` 再发到 VPS（评审用的红框图、标注都依赖线上可跑的原型）。部署命令、nginx 配置块、验收三件套见 `references/原型部署到VPS.md`。
- **在 Mac 上出图要现装依赖**（公司机装过、Mac 通常没有，属首次环境准备）：`pip install playwright pillow` ＋ `python3 -m playwright install chromium`；指令里把这两条写在最前面，别让 agent 卡在 import 报错上。
- **路径改了，出图指令里的 `--page-map` 也要跟着改**：形如 `--page-map "/engage/behaviors/modal=/engage/behaviors"`——虚拟路由（弹窗态）靠它映射到真实可访问路径，只改代码不改这里，弹窗那几张图会直接出不来。
