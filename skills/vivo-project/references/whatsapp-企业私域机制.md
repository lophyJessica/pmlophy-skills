# WhatsApp 企业私域机制（Meta 官方文档核实，可直接引用）

用于回答「导购的 WhatsApp 到底怎么接进 vivo、好友数为什么会掉、系统能不能替导购加好友」这类问题。**依据只取 Meta for Developers 官方文档，不取博客。** 引用时区分：**事实**（官方原文）/ **推断**（我方判断）/ **待确认**。

## 一、三条接入路径

| 路径 | 是什么 | 关键限制（事实） |
|---|---|---|
| WhatsApp Business App | 手机 App，手动聊 | 无 API；联系人 = 手机通讯录 |
| Cloud API（Business Platform） | Meta 托管官方 API，经 Solution Partner / Tech Provider 接入 | 号码注册后**该号不能再用 WhatsApp App**；需模板审核 + opt-in + 24 小时客服窗口 |
| **Coexistence**（官方叫 Onboard WhatsApp Business app users） | 同一个 Business App 号码同时接 Cloud API | App 与 API 消息双向镜像；吞吐固定 20 mps；群聊/广播列表/语音视频**不同步**，广播列表接入后被禁用 |

## 二、企业能拿到的数据（Coexistence 订阅的四个 webhook）

| webhook | 内容 | 限制 |
|---|---|---|
| `history` | 历史消息 | **仅最近 6 个月**（原文：All chat messages in the most recent 6 months can be synchronized） |
| `smb_app_state_sync` | 联系人全量 + 后续增删改 | 来自**手机通讯录**；动作只有 `add` / `remove`；字段 `contact_change_timestamp` 是可用时间戳 |
| `smb_message_echoes` | 导购在 App / 支持的伴侣设备上发出的消息 | 不支持的客户端发的消息不触发 webhook |
| `account_update` | 账号生命周期与断连 | 见下节枚举 |

明确不同步：群聊、消失消息、一次性查看、实时位置、语音视频通话、Business 工具、消息工具、业务资料、Channels。成本：App 内发消息免费；走 Cloud API 按 Cloud API 计费。

## 三、好友数波动的六个可解释机制（回答「meta 黑盒导致好友被删了又加回来」）

1. **联系人源头是导购手机通讯录**：导购删通讯录就发 `remove`，加回来就发 `add`。不是 Meta 无缘无故删。
2. **设备不活跃会断连**：`account_update` 的 `PARTNER_REMOVED.reason` 枚举含 `PRIMARY_INACTIVITY`（主设备约 14 天）、`COMPANION_INACTIVITY`（伴侣设备约 30 天）；断开后同步停止，重连再全量同步。
3. **导购换机 / 重新注册**：`USER_RE_REGISTERED` / `CHANGE_NUMBER`。
4. **号码被注册回消费者版 WhatsApp**：`BUSINESS_DOWNGRADE`，接入关系直接失效。
5. **6 个月窗口**：更早的会话不进企业侧，界面若按「有消息即为好友」判定，老好友会“消失”。
6. **用户侧**：删聊天、拉黑、换号，企业侧同样表现为联系人消失。

推论（写方案用）：**好友指标必须先定口径**——按通讯录同步结果、按有过消息往来的 wa_id、还是按首加时间；口径不定，页面怎么改都会继续对不上号。

## 四、能不能主动加好友 / 主动触达

- **不能加好友**：Cloud API 没有添加联系人的接口。企业侧联系人是通讯录同步来的或用户先来消息产生的。
- **主动触达两个前提**：① 用户 opt-in；② 用户来消息或来电后开 **24 小时客服窗口**，窗口内可发自由格式消息，窗口外**只能发已审核模板消息**；用户再发消息会重置 24 小时。
- 导购在 Business App 里直接发消息**不受** 24 小时窗口限制（窗口约束只对 Cloud API 发送）；但该消息只在 `smb_message_echoes` 里回传。

## 五、对需求的直接影响

| 需求类型 | 结论 |
|---|---|
| 「按订单号自动分配好友」 | 系统只能出**待添加清单 + 提醒**，不能替导购加好友——方案表述必须改成清单，不能写“自动归属” |
| 「好友列表状态 / 好友数统计」 | 波动可用通讯录同步 + 断连 + 6 个月窗口解释；先定口径再谈页面 |
| 「成为好友第 N 天」类触发 | 可选的起算点有三个：通讯录 `add` 的时间戳、首条消息时间、首次双向会话（原文口径）——要业务拍 |
| 「导购直发/转发 + 永不打扰过滤」 | 走 App 侧发送成本最低（免费、不受窗口限制），过滤挂在那里最省事；走 Cloud API 才涉及 opt-in / 模板 / 窗口 |

## 六、剩下的待确认（问 BSP / 牛信 或实测）

1. vivo 实际用的是**纯 App / 纯 API / Coexistence** 哪一种——决定能不能拿到联系人，也决定好友列表数据源是否成立。
2. 牛信是否已订阅 `smb_app_state_sync`；若已订阅，历史 `remove` 事件本身就是“波动来自通讯录删除”的直接证据，不必再猜。
3. 20 mps 固定吞吐是否够用，超限排队与重试策略。
4. 是否使用 `username` / business-scoped user ID（webhook 可能不含手机号），影响我方用户标识设计。

## 七、供应商依赖的处置纪律（不写成「请供应商支持」）

牛信是 BSP 供应商，**不一定会为我方单个需求专门处理或回补 `remove` 事件**。凡依赖第三方供应商给能力/给数据的项，按三档走，别一上来就写「请某某支持」：

1. **先确认我方实际能收到什么**——标准事件（`smb_app_state_sync` / `history` / `smb_message_echoes` / `account_update`）是标准订阅，先查自己后台有没有，能自查的不求人。
2. 收不到时评估：**我方按标准订阅直连**，或由供应商转发。**标准事件不需要供应商做定制开发**，这条要分清——「定制」和「开通」是两件事。
3. 两条都不行，才把相应口径（如「按通讯录删除统计好友数」）**降级为推断，不写进验收**。

结论口径：这类项记为**待确认与风险，不作为开工前置条件**。功能按「通讯录同步结果 / 有过消息往来」双口径都能算的方式设计，事件数据到了再校准——不要因为供应商没动静就让需求停摆。
