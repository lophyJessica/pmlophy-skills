# 交付级 Excel 的结构、配图与在线表格落地

做好一张要发出去给人看的 Excel（大表分组合并、嵌页截图、导进在线表格协作），比写数据难的是排版与落地。本 skill 只管这些，数据口径归各自的业务 skill。

## 一、先问清落地形态，再动手排版

排版方案取决于最终在哪看，问错了白做一遍：

| 落地形态 | 约束 |
|---|---|
| 本地 Excel / WPS | 随便做，筛选、合并、多 sheet 都行 |
| 在线表格（飞书、腾讯文档、docs.vivo.xyz 这类） | 嵌入图能不能留要先实测；合并块导入后可能散开；多 sheet 可能不被接受 |
| 只发文件给别人看 | 图必须嵌入，不能外链，否则对方打开是空的 |

**动手前先实测目标文件的真实状态，不要用镜像或历史版本判断。** 同一份对比表往往同时存在明细版和压缩版两个文件，用户手上那份还可能已被别人改过；VPS / 父会话里的副本不等于他本地那份。开工第一条指令就是让它读回：表头逐列、各列合并区数、嵌图数、关键列的已有内容，再定方案。按镜像算出来的「现状」会整段作废，甚至会得出「印度和印尼填反了」这类假结论，连带白改一轮。

**多 sheet 是高频误判点**：用户说「这块会作为一个 sheet 放进在线表格」时，默认意思是**只能有一个 sheet**，别自作主张加「明细版」「索引」之类的辅助 sheet。但反过来也别压过头——用户说「把数据放进一个 sheet」可能只是指「数据也要进表、别只给图」，随后又会要「图表一个 sheet、数据一个 sheet」。**开工前把 sheet 清单（几个、各放什么）复述一遍让用户点头**，比做完再返工便宜。

**派活前四条硬核实，缺一条不下指令。** 这类表的返工几乎全部来自「以为的现状」与「实际现状」不符，而核实只要几分钟：① 把图目录的文件名实际列一遍，不要按你想象的命名规则写匹配代码；② 读回表里页面分组的真实结构——同名页面有没有被拆成两段、截图清单里的页在表里是不是根本没出现；③ 插图锚定写法先在本机插一行验证并读回锚点，确认图真落在格子里；④ 行高列宽按图比例反算成精确值并核对到像素。四样做完再发指令，一轮能过；留到执行后再发现，就是一路「补一张图、改一次锚点、重压一次行」地返工，用户最终会以「我们 skill 是失败的」收场。

## 二、合并单元格做分组

同一维度重复几十行的表（比如一个页面 30 行功能），用纵向合并把重复值收成一格，视觉上自然分组，比给每行标序号清楚得多。

- **按真实分组边界合并，不能按「相邻且同值」简单合并**。同名的两段可能中间夹着别的组，按相邻同值合会跨段错位。合并前先按业务键把行分组，逐组确认起止行号。
- **值只保留在左上角**，合并前先断言左上角有值，合完再读回校验一次。
- **合并后自动筛选必然失效**。要么去掉筛选免得留个点了没反应的按钮，要么另存一版不合并的明细表（但先看第一节的单 sheet 约束）。
- 单格合并（1 行的组）在序列化时会被省略，是视觉等价，不算丢。

通用形态：`主键列（整组合并）→ 分组列（组内合并）→ 明细列（逐行独立）`。

## 三、嵌图：尺寸、锚定、溢出

- **图片必须嵌入（base64/blip），不能外链**，否则发出去打不开。
- **「图根本没插进单元格」＝锚定方式选错了，不是缩放算错。** openpyxl 默认用 `OneCellAnchor`（锚在某个单元格左上角 + 固定像素尺寸），图永远浮在表格上方：压住右边一列、跨过好几行，行列怎么调都对不上边框。要让图边界与单元格边框重合，必须用 `TwoCellAnchor` 从单元格左上锚到右下，Excel 才会按这个范围拉伸：

```python
from openpyxl.drawing.spreadsheet_drawing import TwoCellAnchor, AnchorMarker
a = TwoCellAnchor()
a._from = AnchorMarker(col=14, row=r-1, colOff=0, rowOff=0)   # O 列第 r 行，索引从 0 起
a.to    = AnchorMarker(col=15, row=r,   colOff=0, rowOff=0)    # 到下一列下一行＝正好一格
img.anchor = a
ws.add_image(img, f"O{r}")
```

  锚定范围本身就是图的大小，所以**行高列宽必须先设到位**，否则锚出来的格子是错的。
- **列宽全是全表统一的、不能逐行改，所以行高也必须统一。** 压成一页一行、每行放一张 750×1624 手机长截图时：先定一个够用的统一行高，再反算截图列宽 —— 列宽（字符）≈ 行高（pt）× 0.088。实测行高 320pt 配列宽 28 字符 = 427×205px，比例差 4%，图会被横向拉伸一点（肉眼看不出，但既然验收口径是「完全与单元格契合」，就不要留这个误差）。精确反算：列宽 px = 字符数 × 7 + 5；行高 pt = 列宽px × 0.75 × 图高 ÷ 图宽。750×1624 的图配 28.625 字符列宽 → 205.4px → 行高 333.5pt，像素尺寸 205×445，与图等比无变形。333.5pt 也够放下约 18 条子功能项。逐行设不同行高会让同一列里的图比例全对不上。
- **插行、删行会打断图片与行的对应关系，锚点必须手动搬。** openpyxl 的 `insert_rows` / `delete_rows` 只移动单元格，不动图片：插一行，后面所有锚点仍指着原来的行号，整列图整体错开一格；删一行，被删行那一格的图还留在画布上盖住下一行。做法是先记下每张图的 `(img, anchor._from.row, anchor.to.row)`，再改行，最后把所有 `from_row` 在插入/删除点之后的图统一 `row ± 1`（`from` 和 `to` 两个都要改）；删除时同时把落在被删行那一格的图从 `ws._images` 里摘掉。实测一次插行要搬 50 张、删行要搬 55 张，漏搬不报错，只是图和内容错位。属性名是 `anchor.to`，不是 `anchor._to`。
- **复制单元格样式用 `copy(s._style)`，不要 `d.alignment = s.alignment`。** 后者在 openpyxl 里抛 `TypeError: unhashable type: 'StyleProxy'`——对齐、字体读出来是代理对象，必须深拷贝后再赋。
- **同一页面名在表里出现两段时，压行会产出两行内容完全相同的行。** 主表把一页拆成两组功能、中间又夹着别的页面时，「按连续相同值分组」得到两个组，但回填按页面名取值，两组拿到的是同一份合并内容——看着像重复数据，其实只多了一行。核实办法：把两行的第 2、3 列原文打出来逐字比，一字不差就是真重复、删一行；内容不同才是两个功能组，该改名分开保留。同一页面因渠道不同要拆成两行时（如素材详情的朋友圈版 / 社群版各一张图），拆行同样要按上一条搬锚点。
- 锚点定在对应分组的主单元格，**水平居中于该列、垂直居中于该组的高度**。
- **图片与表行的对应关系靠映射表，不靠文件名猜。** 表里的页面名和截图文件名通常不是同一套命名（表里「销售-vivo+销售工具」、图是 `03-销售.png`；「我的待办」对 `05-我的任务.png`；「任务中心」对 `07-任务列表.png`）。写「文件名去掉序号后必须与页面名完全相等」这类严格规则会大面积静默失败——实测 8 张只插上 2 张，脚本不报错，只是少插。正确做法：父会话先出一张「页面名 → 图文件名」的显式映射表写进指令，agent 只照表插；表外页面一律留空，不许拿相近文件名凑。核对方式：读回文件统计**每个截图列各有几张图**（不是总图片数），只有 2 张那种一眼就看出来。
- 统一图宽（如 130px）等比缩放，并算好对应的 pt 高度（px ÷ 1.333 ≈ pt）。
- **插得好不好看，取决于「这一格是不是为图调过」**。标杆表里的嵌图之所以规整，是三个动作：行高按图单独抬过、列宽配好留出左右边距、等比缩放并锚定在那一格内居中——不是工具差异。如果一组占 5-20 行合并，先算合并区总行高够不够图，不够就抬（每行大约要 70pt 才能放下一张手机长截图），而不是把图压小到看不清。
- **尺寸算法（按合并区反算，不写死图宽）**：
  1. 可用宽 = 列宽字符数 × 7 × 0.9（px）；可用高 = 合并区各行行高之和（pt）× 1.333 × 0.9（px）。
  2. 按原图宽高比分别算出「限宽后高」与「限高后宽」，**取两者中使图完全落入格内的那一组**。
  3. 错定在合并区左上单元格（`ws['D5']` 这类），用偏移量把图水平居中；**图高向下取整**，避免小数向上越过合并区底部。
  4. 算出来图太小（宽 < 80px，看不清内容）就不要继续缩，反推需要多少行高并抬高该组行——宁可行高不统一，也不能图看不清。

**行高不够时抬行高，不要缩图宽。** 这是本类任务最容易做错的一处：某组只有 2 行、行高 20pt、总高 40pt，却要塞 97.5pt 的图——缩到最小 60px 宽后图仍高于 40pt，只能往下漫，**溢出部分直接盖住下一组的内容**。正确做法是把该组所有行行高抬到「需要高度 ÷ 行数」（2 行组每行 49pt）。组越小越要抬，行数多的组用基础行高就够，别整表拉高。

配图自检必须断言：
- 嵌入图片数 == 应有数
- 每张图锚定行落在对应分组的行范围内
- **每张图底部不越出所属分组（越界数 == 0）**
- 图片 md5 与源文件一致（确认没被压缩或替换）
- 图宽是否被实现悄悄改过
- **锚点数 ≠ 图片内容去重数是正常的**。同一路由的不同状态页（同一页的多个 tab、容器页与其默认子页）截出来内容一样，会存成多份相同图片——实测 61 个锚点只对应 57 份不同内容。判「有没有缺图」要按**每个分组块内是否存在锚点**来查，不能按图片内容唯一数查，否则会把正常情况误报成少图。
- **锚定行不等于块首行**。图常因为垂直居中而锚在块内某一中间行。审计判「锚定行是否落在该组的行范围内」，用块首行精确匹配会大量误判成「这页没图」。
- **图高向下取整不要四舍五入**。块高 98pt、图算出来 98.25pt 时，`round` 会让图比块高，垂直居中偏移变成负数、图顶出块外；`floor` 才稳。
- **人工给的图必须进保护名单，否则下一轮就没了。** 用户手工截的、或者他临时提供替换的图，要连同「文件名 + 字节数 + SHA」一起写进生成/重截脚本的跳过名单，并在覆盖前快照。只靠「这次记得不覆盖」不行——重跑一次自动截图就把它冲掉，而且很难当场发现。
- **合并区数量不是验收标准。** 为了让「合并区域数保持不变」而放弃按页合并、改成逐行锚定，结果是图乱插放、跟相邻列对不齐——这是倒果为因。合并数变多是正常的；验收看的是图落不落在该组内、有没有溢出。
- **全表行高要统一。** 给部分行多插了图就把那几行抬到 100pt+，整张表看起来参差不齐。要么全表统一行高、图缩到能放下，要么按列统一；不允许个别行特别高。
- **改生成脚本重新生成，不要手工编辑 xlsx。** 合并区、行高、图片锚定都是脚本算出来的，手工改一处很容易把相邻组的合并拆掉。脚本不在手上就先让上游 agent 把生成器交回来。

## 四、列宽：不设宽度会看到一排井号

数字列设了千分位后，9 位数需要约 15 字符宽。列宽按 11 给，会在 Excel 里渲染成 `########`——数据没错，但用户会以为某几格没数据。

开工时按最长值估一遍：`最长字符数（含千分位逗号）+ 2`。百分比列 10-12，长文本列（说明、备注、代码依据）45-60 并开自动换行。

## 五、导入在线表格（docs.vivo.xyz 类）

- **嵌入图片实测能随 xlsx 导入保留**，但浮动对象与外部链接会丢。
- 合并块导入后**必须实测是否散开**：散开的话主键值会重复出现几十次，视觉分组就没了。
- 列宽、行高、图宽缩放通常会有出入，导入后要重新看一眼图是否变形。
- **两级表头（分组行 + 列名行）叠跨列合并，是导入后整体错位的头号原因**：第一行「印度」跨 5 列、「普外（印尼）」跨 6 列，导入端把分组行拍平或当成数据行，整表就往右挪一格。解法是另出一份导入专用版：表头压成单行、列名带分组前缀（印度-截图 / 印尼-截图 …）、去掉表头区的跨列合并；正文里页面列的纵向合并可以保留。用户报「列错位 / 两边填反了」时先分清是 Excel 本身错还是导入后错——大概率是后者，先去查表头合并，不要动数据。
- 上线前先做小样本导入（挑行数最多、行数最少各一个）验一遍，别全量做完才发现形态不对。

## 六、自检的固定做法

**先确认 openpyxl 装在哪个解释器里再写脚本**：这台 VPS 上系统 `python3` 没有 openpyxl，可用的是 Hermes 自带环境 `/usr/local/lib/hermes-agent/venv/bin/python`（实测 openpyxl 3.1.5）。生成脚本落 scratch 目录、输出落交付目录，用这一条命令跑：`/usr/local/lib/hermes-agent/venv/bin/python <脚本>`；写成 `python3 xxx.py` 会当场报 `ModuleNotFoundError: No module named 'openpyxl'`，别误判成没装。

agent 自报「成功 61 张 / 全部通过」不算验收，必须读回文件断言：

**用户丢回一句「这做的啥啊」时，先读回文件逐列核对，不要先自辩也不要直接重做。** 他的不满可能指向某一块（截图列空着、某列没填），而定稿本身可能全对。做法：openpyxl 打开他发回的那份，报行数/列数/合并区数/行高列宽，再挑一个代表行把 33 列逐列打出来，对照规则逐项判「对/不对」，然后拿这份事实问他具体哪一块不对。实测一轮里压行结果实际全对（70 行 69 页、0 合并区、行高 320、列宽 28.6、「包含：」+换行格式、各国结论按汇总规则算对），空的只是两列截图——直接重做就是白损一轮。

0. **两边都在改同一张 xlsx 时，用逐格文本 diff 判断真实差异，别凭「文件变过」就断定冲突要重做。** 用户会在公司机上改同一份表再 push，而你这边也有未提交的改动，git 合不了二进制。做法：`git show <远端提交>:<路径> > /tmp/his.xlsx`，两边 openpyxl 读回逐格比 `str(a or '').strip() != str(b or '').strip()`，把差异格按「行号 / 列号 / 我这边 / 他那边的原文」逐条打印。实测 74 行 33 列的两版只差 1 格（他把一句备注加了「外销」两字），手工合并即可，不必整份重做、也不必让他重发。反过来，diff 出几十格才说明真分叉，这时停下来问以哪版为准。别先入为主地认为「他改过 = 我的版本作废」。
1. 用 openpyxl / zipfile 读回，报行数、列数、合并区域数、嵌图数、锚定行范围、越界数。
2. 与源数据逐格比对，声明「除某列外其余 N 列零差异」。
3. 生成与校验**同一条命令连跑**：公司 DLP 会对 xlsx 做异步透明加密（文件头变 `%TSD-Header-###%`），本机打开无感知但外发会失败，且加密时机不确定。判断是否被加密看**文件头前两字节是否为 `PK`**，不要只看能否打开。TSV 不受影响——真要外发又来不及解密，就发 TSV 或截图压缩包。

## 七、并行跑多个版本时

同一台机器开两个会话分别生成不同版本（如明细版 + 压缩版）是可行的，前提：

- **输出文件名写死在各自指令里且互不相同**，否则互相覆盖。
- **两边都不许回写共同的源文件**（如主表 TSV），谁回写谁就把对方读到的数据改了。
- 图片等只读资源不许改、不许移。
- 同机并行生成带几十张大图的 xlsx 会抢内存和 IO，串行更稳；非要并行就接受偶发超时。

## 八、图表页：组合图、数据标签、轴显示

交付级图表的标准是「不看图例也能读出数」：柱顶有数值、两轴有标题、横轴是真实分类名。openpyxl 生成的图默认三条全不满足，而且全程不报错，代码里看不出任何异常。

**① 分类轴要显式改成文本引用。** `chart.set_categories(Reference(...))` 写出来的是 `<c:cat><c:numRef>`。分类本身是文字（月份、国家、统计区间）时，Excel 按数字引用去取值，横轴渲染成空白或 1/2/3。修法：构造完图表后逐系列改 `s.cat = AxDataSource(strRef=StrRef(f="'表名'!$A$2:$A$11"))`。

**② 只改 strRef 还不够，必须把值缓存进图表。** Excel 打开时不主动计算跨表引用，引用本身是对的但显示仍为空白。要把分类文字与数值都写进 `strCache` / `numCache`：

```python
s.cat = AxDataSource(strRef=StrRef(f=cat_range, strCache=StrData(
    ptCount=n, pt=[StrVal(idx=i, v=str(v)) for i, v in enumerate(cats)])))
s.val = NumDataSource(numRef=NumRef(f=val_range, numCache=NumData(
    formatCode="#,##0", ptCount=n,
    pt=[NumVal(idx=i, v=v) for i, v in enumerate(vals)])))
```

注意 `s.val` 要的是 `NumDataSource` 包装的 `NumRef`，直接赋 `NumRef` 会抛 TypeError。

**③ 数据标签不加就没有数值。** 设 `chart.dLbls = DataLabelList()`、`showVal=True`、`numFmt`、`position="outEnd"`，并显式关掉 `showSerName` / `showCatName` / `showLegendKey`，否则标签上会拖一串系列名。折线图用 `position="t"`。

**④ 组合图副轴三件套都要设**：`y_axis.axId=200`、`y_axis.crosses="max"`、`y_axis.axPos="r"`。缺 `axPos` 副轴会叠在左边跟主轴重合。

**⑤ 量级差一个数量级以上的系列不要同图。**同一张柱图里放 7 亿和 4，小的会被压成贴底的直线。按渠道 / 按分组各出一张，另外单出一张「同量纲的比率对比折线」把各分组放到一起。

**⑥ 不要给每个系列都开标签。**10 个分类 × 3 个系列 = 30 个标签会糊成一片。柱标数值，折线靠右轴读数；只有纯比率的对比图才给折线点标百分比。

**⑦ 图源数据与被展示的矩阵分开写。**图表引用的是「月份 × 指标」这类行列结构，跟给人看的「分组块 × 指标行 × 月份列」不是一回事。在数据 sheet 下部（或单独一块）留图源区并标「勿删」，别让图直接引用展示区——展示区加一行数据，图就错位。

**⑧ 没法本地渲染验证时就读 XML 断言。**服务器上 LibreOffice 转换可能因环境原因失败（连一份已知完好的旧表都报 `source file could not be loaded` 时，就是它自己环境坏了，别当成自己的文件坏了），不等它也能验：解压 xlsx 读 `xl/charts/chartN.xml`，断言图表数对、每个 `<c:cat>` 下是 `strRef` 而不是 `numRef`、存在 `strCache` / `numCache`、`<dLbls>` 存在且 `showVal=1`、分类点数等于数据期数。**断言时按不带前缀的标签名 grep（`strRef` / `strCache` / `dLbls`），不要写 `<c:strRef>`**——命名空间前缀在不同序列化路径下会变，带前缀统计出来全是 0，会把配好的图误判成「一个标签都没设」。XML 全对但用户那边仍显示异常，再要截图看实际渲染。

**⑨ 系列名要自己给，`titles_from_data=False` 时图例是空的。** 手工构造 `Reference` 加数据（尤其副轴折线、多系列对比图）时不传 `tx`，图例就落成「系列1 / 系列2 / 列 D」，用户看不出哪条是成功率、哪条是阅读率。加完数据立刻补 `from openpyxl.chart.series import SeriesLabel; s.tx = SeriesLabel(v="发送成功率")`。校验方式：读 XML 里 `<ser>` 段存在 `<tx><v>…</v></tx>`，数量等于系列数。

## 九、行粒度：先问同行怎么做，再定自己多细

盘点类、对比类大表最容易掉进的坑不是缺内容，是**粒度没跟对方对齐**。同一件事，写成 1136 行“每个按钮一行”或者写成 320 行“一组一行”，都能说清，但两份表摆在一起看的人会默认它们可比，粒度过细的那份就显得不做取舍。

**开工前先问一句：领导手上有没有别的团队做的同类表？有就要一份来看。** 如果对方用 84 行覆盖一个完整 App，而你用 1000+ 行，就要另外出一版与其粒度对齐——不是推翻细粒度那版，是并存：

- **明细版**：全量底档，可追溯。谁追问某个具体入口，都能找到并指回源码位置。
- **压缩版**：给领导或跨部门看，对齐同行粒度，一屏能看全一个模块。

压缩版的行法固定三列：主键列（整组纵向合并）→ **分组列（区块名，组内合并）** → **明细列（穷举该区块下所有原子项，顿号串联）**。

三条硬规矩：

- **明细列只穷举，不加业务价值句、不写「该区块解决什么」。** 价值句反复就那么几种写法，很快又变成满页重复；而穷举天然不重复。
- **穷举的排版用单元格内换行，不要用顿号串成一句**：首行写「包含：」，之后每个子功能项单独一行，单元格设自动换行 + 垂直居中。顿号串联会把该列拉得很宽；换行则列宽不变、由行高吃下（用户口径：「每一个换行即可，这样不会拉宽表格」）。早前「不加包含：前缀」的写法已被这条覆盖，不要再照那句做。
- **单个区块的原子项上限 6 个**，超了就再拆一层。塞不进去说明该拆，不要硬塞。
- **不新增列**。区块名占现成的分组列，列数保持不变；用户对列数敏感。

实测两组数字可以用来说服用户接受双版本：明细版 1136 行的明细列只有 47 种写法（同组 30 行同一句），压缩版 320 行有 311 种（97%）。**合并单元格只能遮住重复的观感，信息量并未增加；压缩版是真的把每块写成了不同内容。**

区块内各项结论不一致时，结论列填「部分」（多出一个取值就要写进填表说明），差异列以「其中 X 有、Y 无」开头并保留原各项备注。**不要把明细塞进按口径就该空着的列**（如设计规范、展示数量）——那两列以后要靠它们填真数据，借来装别的就废了。

**一页多行 + 一页一张图，图就必然要跨 N 行合并，用户对它的反馈是「不利于观看」。** 此时的正解不是继续调合并方式，而是把该页压成一行。压行后两列各司其职，**不能把子功能项名称塞进功能介绍列、让子功能项列空着**（实测这么干被当场退回一句「第二列，子功能项呢？」）：子功能项列放该页所有子功能项名称逐行列出，功能介绍列放各行原有的功能介绍原文逐行列出，两列都必须有内容；结论列按「全支持 √ / 有支持有不支持 部分 / 全不支持 ×」汇总、差异列去重后串成一段、设计规范与展示数量留空。**列结构保持不变，只填关键几列，其余空着**——用户确认过这两件事不冲突。压行是不可逆的破坏性操作，先压一页做样例（附压缩前后对照图）给用户看合并后的文案读不读得通，认可再全量压。

**压行与改文案的顺序不能颠倒**：按现行行号改完备注、统一口径列之后，再压行；先压行会让后面所有行号错位，改文案的清单全部作废。

**判「内销无此能力」不能只看截图清单里有没有同名页面。** 内销常把多个模块做在同一页的 Tab 或宫格里——销售工具页内部就包含订单管理、活动管理、优惠券，清单里却只有「销售-vivo+销售工具」一条。只按页面名对不上就标成「外销独有、内销无对应」，会被业务当场否掉（用户原话：「vivo+销售工具中里包含了订单管理，活动管理，优惠券等」）。判独有必须回到内销源码看那一页的模块清单，或直接问用户，不要凭清单缺项下结论。

**逐行有值的明细列（代码依据、字段出处、备注）压行后要合并该页所有取值，不能只取首行。** 按首行取会把后面每行的出处全丢掉，用户一眼就能看出「路由也不准」。做法：该页各行的值去重后换行列出，或明确标注「仅保留首行出处」。

**压行后新插的行要单独补第 2、3 列。** 压行是按页面名回填子功能项与功能介绍的，而在多行版里新插入的行（比如新补的一条能力）在里面没有子功能项可匹配，压完就是空的。压行落盘后必须扫一遍「第 2 列或第 3 列为空的页」，逐行补上它本来就该有的那一句，不要默认空着是正常的。

**子功能项与功能介绍写「基准侧」的功能，另一侧的差异一律进差异备注列。** 对比表的两列主描述是给基准系统（本例的内销）看的，外销怎么变写在国家列的差异备注里。把外销的功能写进功能介绍、内销列却打了勾，评审会当场发现「写的是外销功能却两边都支持」，前后对不上。判据：B/C 里出现的每个元素（页签、筛选、字段、按钮）都能在内销那张截图上找到。

**B/C 照截图读事实，但只写「能做什么」，不写「长什么样」。** 写之前把该行对应那张 H5 截图抽出来读一遍（页签、筛选条、卡片字段、按钮文案），目的是确认能力清单，不是把看到的东西都填进去。判据：写进 B/C 的每一项必须是**功能动作**（筛选、搜索、派发、核销、发给客户、查看使用条件），版面元素一律不写——「待处理带数量角标」「商品图与秒杀角标」「商品名称与规格」这类是展示细节，不是功能（用户原话：「这些都没有意义，不是功能是如何展示而已」）。正确颗粒度：`按全部、待处理、已完成筛选订单，展示商品、规格、金额、赠品与自提方式，可联系客户与核销订单`。

**同一页面在表里占多行时，各写自己那一块，不要重复页面级描述。** 内销把一个页面拆成「导购信息」「导购信息（引导与门店）」两行、外销却只有同一个我的页时，两行备注都会以「我的页…」开头重复讲同一件事，用户会要求「统一下，不要在两个单元格描述」。做法：页面级共性（如「我的页只读展示所属门店」）只留在第一行，后续几行只写本行独有的差异项（选择门店弹窗、门店搜索、未找到门店反馈、授权指引）。同一格内部同理——三句都以「我的页」开头要合并成一段。

**改文案前先文字对齐，不要直接动文件。** 用户对「改一版发他看」的循环耐受度很低，会直接说「复杂了，先不要动手，文字发我对齐后再动手改文件」。做法：把该批行的「子功能项 / 功能介绍 / 差异备注」三列以纯文本逐行列在聊天里，等他逐条点头（他常会把你给的文本原样发回来、只改一两处措辞——那就是定稿），再一次性写入。写入后读回打印这几行给他确认，不要只报「已改 N 行」。

## 十、差异备注列：写给人看，不是写给代码看

- **国家列的主语必须是国别词，不能写「外销」。**「外销」是所有国家的统称；西班牙列写「外销无 X」、巴西列也写「外销无 X」，看表的人分不出是哪个国家没有。印度列写印度、印尼列写印尼。
- **在哪个国家的列下，就不必每句重复国别词。** 句首直接写「无筛选弹窗，也无左侧标签分类栏」，读的人看列名就知道归属；通篇「印尼…印尼…」是噪音。
- **不许把具体差异压成「外销无部分内销功能」这类空话。** 弱模型做改写时倾向把长句压成一句结论，信息全丢，改完不如不改。判据：改写后必须还能读出「没有的是哪几项」。
- **原文里的「可配明细：X 可配 / Y 不可配」是内销侧的内容可配说明，不是外销差异。** 把它读成「外销有无该项」是本类改写最常见的错，会把「不可配」写成「外销无」。
- **技术内容一律删掉**：路由、路径、变量名、接口名、组件名、清单行号一个不留，只留业务结论，一条 20-50 字。
- **改写量先数一遍再派活。** 整列套同一句说明的国家（未上线国家常见）根本不用逐条改，统一一句话即可；真正需要逐条改的往往只占全量的百分之几。按总行数派活会白跑几百条。
- **需要理解业务语义的改写不要交给弱模型。** 能读懂「可配明细」「外销是统称不是国家」这类判断的活，由父会话自己改完、产出「行号 + 定稿文案」的 TSV，agent 只做按行号整格替换，一个字都不许自己发挥。

## 十一、文件体积与仓库治理

带嵌图的 xlsx 很容易变成几十兆，一旦进 git 就会拖垮整个仓库。交付前先量体积、压图片，别等用户说「文件太大了」。

**体积来源与压缩效果（80 张 750×1624 / 1152×2376 手机长截图实测）**：

| 方案 | 80 张合计 | 说明 |
|---|---|---|
| 原始 PNG | 33.5 MB | 平均 428 KB/张 |
| **PNG 256 色调色板** | **5.8 MB** | 分辨率不变，UI 截图肉眼无差，**首选** |
| 缩到 600 宽 + JPEG q88 | 6.6 MB | 降了分辨率，不划算 |
| JPEG q85 原尺寸 | 12.4 MB | 文字边缘有伪影，且比调色板 PNG 更大 |

**但先问验收口径，口径不同最优解不同**：

| 用户口径 | 做法 | 实测 |
|---|---|---|
| 只要求发得出去 | PNG 256 色量化 | 33.5MB → 5.8MB |
| **「点开是正常的图，不点开也能知道长什么样」** | **像素尺寸不降，只把 PNG 转 JPEG q90** | 35.8MB → 16MB（87 张） |
| 已被上一版压坏（「压缩的太多了」「都挤成一团」） | 从 git 历史捞回原图重嵌 | 见本节末 |

要求「点开放大是原图」时，只有一条路：**保持原始像素、只换编码格式**。量化调色板或统一 resize 都会让文字发糊、比例被压，用户一眼看出「挤成一团」——他要的是缩略能认、放大是原图，不是小体积。JPEG q90/q92/q95 分别 16.1/17.4/21.4MB，q90 是拐点，再往上体积涨得快、肉眼看不出差别。压缩之前若已有量化版在表里，先确认原图还在不在（可能在 git 历史里，见本节末）。

结论分场景：**只要体积、不在乎放大清晰度 → PNG 量化；要「点开是原图」→ 原像素 JPEG q90**。UI 截图是纯色加细文字，同像素下 JPEG 确实比量化 PNG 大，但量化 PNG 放大后文字是花的，不符合后一种口径。

```python
q = pil.convert("RGBA").quantize(colors=256, method=PILImage.FASTOCTREE)  # RGBA 必须用 FASTOCTREE
buf = io.BytesIO(); q.save(buf, "PNG", optimize=True)
ni = XLImage(buf); ni.anchor = old.anchor; ni.width, ni.height = old.width, old.height
```

压缩后要读回断言图片数不变、锚点不变、行数不变（只换字节，不动结构）。整表 32.7MB → 5.5MB 后飞书聊天框能直接发，不用绕 git 或网盘。

**量化两个必踩的报错**：`quantize(colors=256, method=MEDIANCUT)` 对 RGBA 图会报 `ValueError: Fast Octree (method == 2) and libimagequant (method == 3) are the only valid methods for quantizing RGBA images`；而先 `convert("RGB")` 再量化仍可能报到 `ValueError: transparency for P must be an integer or bytes`（原图的 `info['transparency']` 被继承下来）。两种都直接用 `convert("RGB")` + `FASTOCTREE`，或量化后 `q.info.pop('transparency', None)` 再存。

**表里图的尺寸往往不止一种，压之前先统一。** 同一张表可能混着 1152×2376、750×1624、甚至 1152×4727（两倍高的超长页）。单元格只能迁就一种比例，所以先把全部图等比缩放/拉伸到同一个尺寸再插，否则怎么调列宽行高都有一半图变形。统一前先统计一次分布（`Counter(Image.open(...).size)`）并把结果告诉用户：超长图压成普通比例会纵向压扁一倍、内容看不清，这类要单独问怎么办（放大行高、裁切、还是留着不管），不要默默压掉。

**git 侧：xlsx 是二进制，每次提交都存整份快照。** 同一张大表改十几轮、每轮提交一次，`.git` 会直接膨胀到几百兆（实测 216MB，仓库目录 287MB），用户那边 `git pull` 会失败。三条处置：

1. **交付物优先走聊天框或网盘，不要反复提交进 git**；确实要多端同步，就只提交**压缩后**的版本。
2. 先用 `git rev-list --objects --all | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' | awk '$1=="blob"{print $3, $4}' | sort -rn | head` 找出历史里最大的对象，看清楚是哪些文件在吃体积，再决定清什么。
3. 治本用 `git filter-repo` 从历史里剔除大文件。**先在 mirror 副本上试跑**（`git clone --mirror` → `git filter-repo --path-glob '*.xlsx' --invert-paths --force`），确认体积和内容再动正本；实测 187MB → 33MB。代价必须提前说清：**所有提交号都会变，别人本机那份要删掉重新 clone，未 push 的改动会丢**。

**正本瘦身的完整落地顺序（实测仓库 491MB→225MB、.git 224MB→74M）**，顺序错了会丢文件：

1. 先 `tar czf` 整仓备份（含 `.git`）——filter-repo 不可逆；
2. 提交工作区所有改动，保证干净；
3. **把要保留的 xlsx 先复制到仓库外**（`cp 内外销梳理/*.xlsx /tmp/keep/`）。`--invert-paths` 会把它从**所有**提交里剔除、包括 HEAD，跑完工作区里这些文件直接消失；
4. `git filter-repo --path-glob '*.xlsx' --path-glob '*.xls' --path '.tmp-mock/' --path '.qoder/' --invert-paths --force`；
5. **origin 会被自动移除**（脚本会打 NOTICE），要重新 `git remote add origin git@github.com:<user>/<repo>.git`；
6. 把 xlsx 复制回原位，单独提交一次——这一份快照就是新的唯一历史；
7. `git push --force origin main`；
8. push 后 `.git` 会因新对象涨回去（实测 33M→82M），跑 `git gc --aggressive --prune=now` 压回 74M。

顺带两条同批清理：第三方 AI IDE 自动生成的代码知识库（`.qoder/` 这类，几百个 md）可以直接删——用户不是开发，不会去读代码级技术文档，下次打开 IDE 会自动重建；散在仓库根目录的过程数据（tsv、清单、映射表）用 `git mv` 归档到子目录，不要直接删，那是梳理过程的证据。

**源图宽高比与目标格子不一致会拉伸。** 反算出格子尺寸后，先比一下格子比与源图比：732×1624 的格子和 1152×2376 的图差约 5%，锚定铺满就会横向拉伸。要么按格子比例重裁/重缩图片，要么明确告诉用户「会拉伸约 N%，可接受吗」，不要默认他看不出来。

**多比例图混在同一列、又要求不变形时，换 `OneCellAnchor` 等比居中留白。** `TwoCellAnchor` 的锚定范围就是显示尺寸，必然拉伸填满——表里同时有 0.485 和 0.462 两种比例的图时，不管行高列宽怎么配，总有一半变形。此时用单点锚定 + 显式显示尺寸：

```python
from openpyxl.drawing.spreadsheet_drawing import OneCellAnchor, AnchorMarker
from openpyxl.drawing.xdr import XDRPositiveSize2D
sc = min(Wpx*0.98/w, Hpx*0.98/h)          # Wpx/Hpx = 单元格像素宽高
ax = OneCellAnchor()
ax._from = AnchorMarker(col=c-1, row=r-1,
                        colOff=int((Wpx-w*sc)/2*9525),   # 1px = 9525 EMU
                        rowOff=int((Hpx-h*sc)/2*9525))
ax.ext = XDRPositiveSize2D(int(w*sc*9525), int(h*sc*9525))
img.anchor = ax
```

这样每张图按自身比例缩到格内最大、居中、四周留白，**代价是留白**——「正好塞满」和「绝不变形」在不统一图比例的前提下不可兼得，二选一前先问用户要哪个（他要「不点开也能认出、点开是原图」时选不变量 + 留白）。

**重嵌图片必须先安全读到原始字节，否则会一次丢掉全部图片。** `ws._images` 的图对象在「从 BytesIO 加载」场景下调 `im._data()` 会抛 `ValueError: I/O operation on closed file`；若循环里捕获后继续、而 `ws._images = []` 已执行，保存出来是**零张图、0MB** 的文件，原有图全没了（实测 87 张一次归零）。**出了这件事不要在原地重试**：清空已经写进文件了，直接 `cp` 改图前那份 `.bak` 覆盖回目标文件，再从 zip 重新取字节做一遍。改成从 zip 直接读：

```python
import zipfile
from xml.etree import ElementTree as ET
z  = zipfile.ZipFile(path)
rt = ET.fromstring(z.read("xl/drawings/_rels/drawing1.xml.rels"))
rid2media = {r.get('Id'): r.get('Target').replace('../media/','xl/media/').lstrip('/')
             for r in rt if 'image' in r.get('Type','')}
xt = ET.fromstring(z.read("xl/drawings/drawing1.xml"))
for anc in xt:                                   # from(row,col) + blip r:embed
    fr   = anc.find(XDR+'from');  blip = anc.find('.//'+A+'blip')
    row  = int(fr.find(XDR+'row').text); col = int(fr.find(XDR+'col').text)
    raw  = z.read(rid2media[blip.get(R+'embed')])   # 原始字节，直接拿去重嵌
```

media 路径读出来带前导 `/`（`/xl/media/image1.png`），`z.read()` 会 KeyError，必须 `lstrip('/')`。另外 f-string 里不能含反斜杠，`f"{...{'png' if raw[:4]==b'\x89PNG' else 'jpg'}}"` 会 `SyntaxError`，把判断挪到 f-string 外面。

**原图被自己压坏了可以从 git 历史捞回来。** `git show <提交>:<路径> > /tmp/orig.xlsx` 拿到当时的完整快照（哪怕后来提交的都是压缩版），再按「页面名 + 列」建索引与新表匹配、把原图按位置换回去；新加的、旧快照里没有的行，用原始截图文件单独补。硬盘上的 `.bak` 备份通常只剩压缩后的版本，git 历史才是真原图。
