# 字段清单 TSV 详细稿（13列标准）

## 何时用
- md 字段清单 → TSV 转换（forge 系字段清单统一用 TSV，不维护 md 副本）
- 新写字段清单、补字段空列、PRD↔TSV 双向对账
- 用户说"字段清单""TSV""字段对齐""字段命名"

## 铁律 1：每字段独立成行，禁止折叠/合并（用户 0927 严厉纠正）
**每个字段占一行**，跨系统标识符（crmCustomerId 等）、同步元数据、审计字段全部独立成行。
- ❌ 错：把 crmCustomerId/erpCustomerId/snapshotVersion 等 4 个字段"收进关联客户的备注"——用户原话"把四个字段合成一个字段，瞎搞""你又不是备注字段，有效字段啊"。
- ✅ 对：`关联客户`一行、`CRM客户标识（crmCustomerId）`单独一行、`ERP客户标识（erpCustomerId）`单独一行……每一个都是有效字段，各占一行。
- 推论：折叠会丢字段（审计曾抓出商机 ERP 订单同步 5 字段、客户 13 个同步元数据字段因此整体丢失）。

## 铁律 2：字段名 = 中文名（英文名），中英文都要（用户 0927 定）
字段名称列格式：`中文名（英文名）`，如 `商机编号（opportunityNo）`。英文名字段是数据流转/数据库用，中文是展示，二者都要，不能只留一个。英文名规则：
- **时间类固定 `xxxTime`，禁 `xxxAt`**（用户：createdAt 是设计缺陷，约定 createdTime）——创建时间→createdTime、阶段变更时间→stageChangedTime、最近跟进时间→lastFollowUpTime
- 名称→xxxName、编号→xxxNo、状态→xxxStatus、Id→xxxId、驼峰拼接
- 源 md 已有英文标识（crmCustomerId/poolType/voidType）直接用，不重新翻译
- "关联客户（customerId）"表达"通过 id 关联"的语义
- 翻译不确定的字段：驼峰直译 + 备注列标"英文名待确认"，不阻塞
- 项目若已有确认过的 TSV（如线索详细稿），以其命名风格为参照标准

## 铁律 3：13 列固定表头
`字段所属分组 | 字段名称 | 字段类型 | 字段来源 | 字段说明 | 必填性 | 新增页 | 编辑页 | 列表展示 | 可筛选 | 详情展示 | 取值说明 | 备注`

## 铁律 4：字段类型 = 控件语义混合，用标准值不用"单选(枚举)"
类型取值：**文本 / 数字 / 日期 / 日期时间 / 单选 / 多行文本 / 级联选择 / 对象集合 / 整数**。枚举值放"取值说明"列，不放类型列（审计红线：`单选(枚举)` 不是标准类型值，下游字符串匹配会出两套类型）。

## 铁律 5：权威层级（PRD↔TSV 互补用）
0. **真实系统页面采集 = 字段名与枚举值的第一权威**（`全局背景信息/参考资料/中文/02-页面采集/<pageId>-<页面>.md`，线上系统的只读记录）。TSV、主PRD、Demo 与它冲突时以采集为准，并列出回写清单——Demo 里带旧字段名、旧枚举很常见（把「Whats账号删除状态」简写成「账号删除状态」、把「待授权」写成「未授权」），照抄就会一路错到原型和评审档。
1. **TSV = 字段定义权威**（类型/来源/必填性/名称；与采集冲突时按第 0 条处理）
2. **主PRD = 业务规则权威**（取值规则/约束/枚举/必填依据）
3. **Demo 页PRD = 页面交互权威**（新增/编辑控件、筛选、详情展示）
4. **前端原型/annotations = 实际实现参照**（Demo 与原型冲突时以实际原型为准）
5. **全局背景信息 = 兜底权威**（地基，单据命名/编码规则；用户 0927："全局背景信息是的，因为是依据地基搭建起来的，地基作为权威没问题，作为兜底"）
- **用例数据推演不是补充来源**（用户明确排除：只是数据样例，不权威）
- **用户口述与页面采集冲突时，摆计数证据再落盘**：同一个字段用户可能几轮给出不同枚举（先「已授权/待授权」、再「未授权/已授权」、最后「已授权/待授权/--」）。既不要默认最后一句就是最新真值，也不要默认采集一定压过用户口径——把采集里的实际计数摆出来（「截图 11 行里已授权 2 次、待授权 9 次、未授权 0 次，你要哪个」），让他选；定稿后**同一步把 TSV 改掉，并在交付里留一条「口径分歧记录」**（产品口径 vs 真实系统取值），否则下一轮又有人按旧口径重做一遍。

## 页面落位映射表（字段 → 列表 / 抽屉 / 枚举）

13 列字段清单回答「字段是什么」；列表改版、抽屉式详情这类页面级重构还要多一张**落位映射表**，回答「这个字段显示在哪、什么枚举、空值怎么表示」。

给渲染型 agent（Cursor / Codex / 反重力）下指令时，让它**读这张表机械渲染，不要从中文指令里自己归纳字段名和枚举**。同一份 17 字段的分配，用文字描述会每版丢几项、改几个名（把「Whats账号删除状态」写成「账号删除状态」、把「所属导购/工号」写成「所导购」），用表渲染则没有发挥空间；返工三四轮后正确的处置就是回头补这张表，而不是把指令再写细一点。

8 列表头，与字段清单同层放（`02-字段清单/`），文件名带页面名：

`序号 | 属性分类 | 字段名 | 列表列序 | 抽屉分组 | 枚举或格式 | 空值表现 | 使用说明`

- **属性分类先定**（账号 / 导购 / 好友 这类实体归属）：它决定哪些字段进列表（好友视角横向比较用）、哪些收进抽屉（账号与组织维度，定位到单条才看）。分类错，后面列怎么排都是错的。
- **列表列序留空 = 不进列表**：把「列表放哪些列」变成数据，而不是每版重新讨论一次文本结论。
- **列表与抽屉互斥，两边不重复**：列序有值 = 只在列表；留空 = 只在抽屉。**不要写「抽屉是完整档案」**——agent 会照做，把列表字段在抽屉里再列一遍，用户会直接问「怎么抽屉变成全量的字段了」。名称、状态这类抽屉里也要露出的字段，指定为标题区锚点（主标题放名称、副标题放状态标签），在列序列留空并在使用说明写「抽屉标题区展示，不单列一行」。
- **操作列不是字段**：写明列表 N 列里有几列是字段、哪一列是操作，否则 agent 会把操作算成第 N+1 个字段，或把 8 个字段做成 9 个。
- **枚举列写全，含空值态**：三态就写三态（`已授权｜待授权｜--`），把 `--` 当成显式状态写进去，agent 才不会只实现两态。
- **0 不是空值，不能用同一个符号表达**：`库存 0` 是「售罄」这种有效事实，`-` / `--` 表示「没有这个数据」。混用的代价是演示时「卖光了」被读成「这字段没数据」。实现口径：只在 `null`/`undefined` 显示横线（判空写 `x == null`，**不要写 `x === 0`**），取字符串前先判空防崩 `(x ?? '').trim()`。
- **真实页面显示横线时要反查含义**：看到某列是 `-`，先分清它代表 0、无记录、还是无权限，**在没取证前不许反推成「这个字段 0 就显示横线」**，否则会把一个未证实的猜测固化进字段口径。
- **聚合类数值写清口径**（如「好友数按导购聚合，同一导购各行相同，且不等于列表条数」），否则 agent 按行编出看起来自相矛盾的假数。
- **禁止自造派生列**：字段只能来自「现有系统页面采集」+「本次新增清单」的并集。把两个真实字段拼成一个更“好懂”的聚合列（如把「Whats账号删除状态」+「数据同步时间」拼成「账号可用状态」）会被当场否掉——用户反问「为什么会有这个字段」时没有第二个答案。要做聚合先问，别先做。
- **交付要 agent 出三列核对表**（字段名 / 位置 / 枚举）逐行对这张表，少一行算不合格。这是低成本发现漏字段的唯一位置。

## 转换流程（md → TSV）
1. 读源 md，按 `## 分组标题` 分块，表格行映射 13 列
2. 每字段独立成行（铁律1），不做任何折叠
3. 字段名转`中文（英文）`格式（铁律2），类型推断（铁律4）
4. 类型推断是纯规则，边缘必错（编号/状态/金额类）——**必须人工或 agent 审计类型列**，别信脚本规则
5. 每个模块 TSV 生成后走 Codex 只读审计（13列校验/类型明细/字段覆盖/技术字段独立行核对）→ 本地 agent（用户 Mac 上的 Codex）修复 → 我验收。

## 互补对账流程（PRD ↔ TSV，双向）
- **正向（PRD 补 TSV）**：主PRD 有 TSV 没有的字段/规则冲突 → 以 PRD 业务规则为准修正 TSV 对应列（按铁律5 层级）
- **反向（TSV 补 PRD）**：主PRD 缺 TSV 字段 → 在主PRD 补"字段定义/对象字段总览"章节，从 TSV 投影全字段（中文+英文+类型+必填+来源+说明），保证 PRD 独立可读
- 用例推演可以当"校验样例"（验证字段够不够用），不当字段补充来源
- 输出对账说明到 `audit-reviews/`，逐字段标核对结论（一致/修正/补充）

### 对账执行纪律（0927 线索/商机样板验收后定稿）
- **修正必须有来源依据 + 标"待确认"**：每处 TSV 修正，备注列标来源（具体到 `前端Demo_PRD合集/xxx.md#章节号` 或 `annotations/pages/xxx.md#区块`）+ 标"待确认"。无依据的必填/取值/展示不准硬补，标"未定义/待确认"。这是对账指令的核心红线——样板里 Codex 正是每条修正都带来源才被验收。
- **样板先行，验收后再铺开**：先做 1-2 个模块（如线索+商机）走完整对账流程，用户验收格式/补法无误后，再给其余模块出同一套对账指令铺开（指令内写"沿用样板模块的流程与红线、勿动样板已完成的文件"）。一次给 7 模块全做，方向错了全部返工。
- 对账只改"可对账列"（必填性/新增/编辑/列表/筛选/详情/取值/备注），**禁止动字段名称/类型/英文名**（以 TSV 为准）——样板验收确认字段定义列是 TSV 权威，对账只补页面事实。
- **字段数量先对账再谈布局**：动手划列表/抽屉之前先算总数并逐个点名，做法与判据见下面「页面落位映射表」节第 1 条。
- **验收时序**：agent 在用户 Mac 本地改（报告路径在 ~/个人文件/forge-crm），我 VPS 端**先 git pull 发现没新 commit 不代表没改**——要等用户 push 后才有得核。用户说"我 push 过了"再拉；拉到后核 `git show --stat HEAD` 确认改动文件集合符合预期（每批 = N个TSV + N个主PRD + N份报告，无第 4 类文件），再跑 13列/空列/字段名/类型 脚本校验，最后 `git diff --name-only | grep -iE "Demo|annotations|全局背景|用例"` 确认红线文件未动。
- **验收脚本化**：逐行 `split('\t')` 校验 ①首行列数=13 ②每行列数等宽 ③空列统计（除刻意留待确认外应为 0）④字段名含中文+（英文）且无 xxxAt 残留 ⑤类型值在标准集合内。全部通过才可答复验收通过。

  **优先用 awk 一行跑完，别为此开 python**（本机 python 会触发审核，用户明确偏好不用）：

  ```bash
  awk -F'\t' '{print NF}' 字段清单_详细稿.tsv | sort | uniq -c
  ```

  输出只应有一行「N 行 13」；出现两种数字就是有行缺列或多列。查组内重名字段：

  ```bash
  awk -F'\t' '$1=="商品管理"{print $2}' 字段清单_详细稿.tsv | sort | uniq -d
  ```

  无输出=无重复。这两条够替代 90% 的脚本校验，且人眼直接能判。

## 外部系统引用（只读）页面的行怎么填

服务宝商品、第三方商品、外部中台数据这类**CMS 只引用不维护**的页面，字段行最容易从别的模块套模板套错。判据：

- **新增页 / 编辑页 一律为「否」**。模板是从可维护模块抄过来的，常留着「是 / 是」，跟真实页面「没有新建没有编辑」直接矛盾。每加一批外部引用字段，逐行核这两列。
- **列表展示 = 是，可筛选 = 按真实页面那几个筛选框来**。别按「这个字段大概能筛」填；筛不筛只认页面上的输入框/页签。页签切换本质是按某字段筛选（如状态三页签 ⇒ 状态字段可筛选=是）。
- **字段来源统一「外部系统引用」，必填性「选填」**，取值说明写「来自对应主数据；以系统实际数据为准」。
- **同一概念自查别撞车**：可维护模块已有「库存」（用户填写、默认 999999），外部页的「可用库存」是另一行，务必在字段说明里写清区别，否则后面有人当重复项删掉。

### 待确认条目怎么挂、怎么关

- 挂的时候**写下禁止动作**，不只写「未取证」：「待确认：枚举未取证，**不得自行假定**」「原型暂沿用既有页面的币种符号，未取证」。否则下一位 agent 会自己编一个值填上。
- 关闭时把**证据值原样写进取值说明**，并在备注标出处与日期：「已取证值：服务宝商品」「已取证：金额保留两位小数，币种符号 ฿（泰铢）」。写明「已取证」和写明「待确认」一样重要——**只有可核的才能升级成事实**，部分取证就写「除已取证值外其余待中台确认」，不要因为拿到一个样本就把整条判成已确认。
- **取证结论必须带视角限定**：写清是哪个国家/组织账号、什么环境、什么时间看到的。多地区系统的同一字段值随所选国家变化（币种、上下架状态、可用库存都是），写「已取证：฿ 1000.00」等于埋雷，应写「已取证（泰国视角）：金额两位小数、符号 ฿；其它国家未取证」，备注里再写死「币种按国家而定，不得写成全局泰铢」。**样本值 ≠ 全局口径**，把单点观测写成系统事实是最容易被业务当场推翻的一种错。

## 字段清单放哪一层：独立层 vs 按单据聚合（2026-10 定）

同一批 TSV，两种组织方式都有人用，**先认清当前项目是哪种，再谈要不要改**：

| 组织方式 | 长什么样 | 谁在用 | 适合规模 |
|:--|:--|:--|:--|
| ① 独立字段清单层 | `03-产品设计/字段清单/<模块>/*.tsv`，与 `需求文档与规则/<模块>/` **镜像对应** | forge-crm；外部课件（维他命 QS-JXC 把它做成 `字段清单/` + `需求文档与规则/` 两个顶层文件夹、层级对齐） | 模块多、单据多的大型项目——字段事实集中成库、改字段先改它 |
| ② 按单据聚合 | 单据文件夹内平铺：`<单据>/<单据>-字段清单-初稿.tsv` + `详细稿.tsv` + 主PRD + Demo×3 + 拍板记录 + 澄清清单 + 评审PRD | SC-JXC（顺诚进销存） | 小规模（如 4 档案 + 1 单据） |

**判据：规模决定，不靠"哪个体面"。** ①的收益在"很多模块时字段库集中、与需求文档层级镜像"；到不了那个规模，拆两层是纯仪式——而且**实操/教学是"每步就地往该单据落一件"**（澄清→拍板→初稿→详细稿→主PRD→Demo→评审），拆成两个文件夹后每步都要在两个目录间跳着找上一步产出，讲起来更绕。

**方法论要求的分层 ≠ 文件夹分层。** 字段事实（TSV）／业务规则（主PRD）／页面交互（Demo）三层，靠**文件名+角色**已经分得很清，权威排序照常可用。用户被外部课件的"两个文件夹层级正好对应"吸引时：先讲清收益主要在规模，再给轻量替代——**不改文件夹，只在权威排序段把"字段清单 TSV 是唯一事实源，改字段先改它"讲透，或在目录树里把 TSV 标成权威层**；最后让用户拍板。真要拆，必须同步 `AGENTS.md`、`03-产品设计/说明.md`、课件里的目录树、两只交付 zip，先备份再动。

**对比外部项目结构时，别把"我们还没跑"说成"我们没有"**（用户纠正："我们只是还没用原型标注的 skill，不是说没有自动化标注吧？"）。列"多了/少了"之前先分清三类：**能力确实没有** / **能力有但本项目还没启用**（如原型标注 skill 尚未在 SC-JXC 跑过）/ **同样产物放在别的目录**（外部放 `03-产品设计/annotations/`，我们放 `99-产品原型/标注/`）。第二、三类不是差距，说成缺口会被当场纠正。
