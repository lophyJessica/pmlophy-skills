# Forge PRD 生成流程

## 核心规则

1. **context 先修再出 PRD。** 出 PRD 前问自己：context/04 模块描述对吗？context/05 编码前缀对吗？PRD 定位一旦错了，前端 4 轮迭代都救不回来。
2. **PRD 经用户确认后才可出前端指令。** 不要在用户审 PRD 前给前端 agent 发指令。
3. **Agent 禁止 git commit/push。** Git 只在反重力/Cursor IDE 中由用户操作。

## 完整产出流程（2026-09-01 用户核对定稿——权威顺序，不可跳过）

```
① context（业务事实地基：背景/边界/术语/功能模块/上下游/编码/场景/约束）
② AGENTS.md（工作规范：提炼 context 关键约束，定产出标准）
③ 调研（pm-research）+ 双向铁人论证（把"嘴上要的功能"逼成"真正要解决的问题"）
④ 确认结果回写 context（SSOT）——回复后立即回写再更新 PRD
⑤ PRD 套件一次性整套输出 ★
⑥ 用户确认 PRD 套件（未确认前禁止出前端指令）
⑦ 前端开发（AI 按 Demo PRD 写页面，页面反过来校验 Demo PRD，双向锁定）
```

**关键认知（用户纠正过的坑）：**
- **字段清单 / 功能清单 / 用例推演 / 状态机 / 流程，都是 PRD 套件内部的文件，不是套件之前的独立步骤。** 不要写成"先单独写字段/功能/用例，再输出套件"——它们是套件的一部分，套件一次整套输出。
- **Demo PRD 必有**：列表页 / 新增页 / 主PRD 等。这是"先 PRD 再原型"的核心——AI 按 Demo PRD 写页面，页面反过来校验 Demo PRD。
- AGENTS.md 是第②步（context 后、调研前），但它本身基于 context 写（把 context 关键约束提炼进去）。

**PRD 套件 = 必须项 + 场景项（0831 定稿，0902 补业务规则规格，喂 agent 前先讲清，别让它无脑写全套）：**
- **必须项（每套都有）**：主PRD + 字段清单 + 功能清单 + 业务流程 + Demo PRD
- **场景项（按场景/模块判断，不是整个系统一刀切）**：
  - **系统流程（时序图）**：仅当**涉及上下游系统交互**时必有；本系统内单纯数据录入不需要（无跨系统可画）
  - **业务规则规格**：复杂业务 / 上下游强关联 / 状态机·校验·计算复杂才写；简单业务写"不适用"
  - **用例数据推演、状态机推演**：业务系统模块要，工具类/纯查询模块简配（写"不适用"及原因）
  - **业务规则规格 vs 用例推演的分工**：规则规格管"规则是什么"（状态机流转表/校验/权限/计算逻辑，静态定义）；用例推演管"规则怎么跑对"（带数字验证/状态快照/走查清单，动态验证）。复杂业务两者都要，简单业务都可简配。

**判断是否业务系统的 4 问**（中 2 个以上 = 业务系统，要推演；全否 = 工具类，简配）：
1. 有没有状态机（多态流转）？
2. 数据要不要跨实体流转（非单表增删改查）？
3. 有没有计算/公式规则？
4. 是否多角色多步骤协作？
（例：采购订单要推演[状态机+跨实体+计算+多角色]；"商品分类管理"配置页不用[单表+无状态+无计算]。同一系统里业务模块和工具模块并存，按模块判断。）

- 状态多 → 套件内必写状态机推演；纯查询/管理类可简配（状态机写"不适用"及原因）。

## 字段清单载体 = TSV（2026-09-07 用户定稿；完整方法论见 notes-vault `AI项目/2026-09-07 TSV字段清单方法论-维生素实战篇.md`）

**用户研读维生素"项目实战篇"4 篇后拍板：字段清单用 TSV 载体，不用 md 表格。** forge 旧字段清单是 .md（已接近详细稿列结构），迁移时改载体即可。

**为什么 TSV**：
- 纯文本 → AI 能直接读写（Excel 二进制 AI 处理费劲）
- 字段多时比 md 表好维护（md 表字段一多就对不齐、乱）
- 配合 AI IDE（Cursor）预测性自动补全——填一列预测下一行，编辑效率高

**两版分层维护**：
- **初稿 5 列**（先确认"有哪些字段"）：`字段所属分组 | 字段名称 | 字段类型 | 字段来源 | 字段说明/描述`
- **详细稿 13 列**（再定义"字段在产品上怎么表现"）：初稿 5 列 + `必填性 | 新增页 | 编辑页 | 列表展示 | 可筛选 | 详情展示 | 取值说明 | 备注`
- 先确认字段范围（初稿快、问题早暴露）再定完整规格（详细稿）——不一步到位

**铁律**：
- **只保留 TSV 一份，绝不并维护对应的 md 字段清单副本**——两份都能改 = "哪份最新"灾难（曾出现 `字段清单.tsv` + `.md` 并存）
- 详细稿确认后 = 字段唯一事实源；初稿只留作过程记录，不再更新维护
- TSV 不放页面细节（查询区位置/控件占列/placeholder/下拉样式/错误提示位置 → 进前端 Demo PRD）

**三层分开，别混着写**（TSV 方法论核心）：
- **字段事实**（类型整数/>0/来源用户填写）→ 字段清单 TSV
- **业务约束**（提交审核时每明细行必填/审核后不可改）→ 业务 PRD
- **页面交互**（用 NumberInput/失焦校验/错误定位到明细行）→ 前端 Demo PRD
- 三层分别回答：字段是什么 / 业务怎么限制 / 页面怎么让用户完成操作——不是重复

**喂 agent 时**：字段名称/类型/来源/枚举/字段级约束以 TSV 为准（权威边界），业务规则以业务 PRD 为准，页面交互以 Demo PRD 为准——让 AI 把 TSV 当字段事实源，不重复定义不越界。

### TSV 转换规则（md → 13列详细稿，2026-09 用户多轮纠正定稿）

旧 md 字段清单转 TSV 详细稿时（不是从零产出，是从已有 md 迁移）：

- **每个字段独立成行，禁止折叠/合并/收进备注。** 跨系统标识（crmCustomerId/erpProductId）、同步元数据、审计字段都是有效字段，必须占自己的 TSV 行。曾把 crmCustomerId 等 4 个字段"收进关联客户备注" = 把 4 个字段合成 1 个，用户斥为"瞎搞"——备注只写补充说明，不承载字段本体。
- **字段名 = 中文名（英文名）双名制**：`商机编号（opportunityNo）`。源文件已有英文标识直接用源英文（crmCustomerId/poolType）；源没有的按驼峰翻译。这是给人看的文档标准，不是代码——代码还要注释，文档更要中英对照。
- **英文名命名规范**：时间类用 `xxxTime`（创建时间→createdTime，不是 createdAt）；名称 xxxName、编号 xxxNo、状态 xxxStatus、Id xxxId；"关联客户（customerId）"表达"通过ID关联"的语义。拿不准的驼峰直译 + 备注标"英文名待确认"，不阻塞转换。
- **字段类型从取值说明/控件推断**：Textarea→多行文本；NumberInput/正数/金额→数字；DatePicker/YYYY-MM→日期；枚举（`A=B` 分隔）→单选（枚举放取值说明列）；控件写 Select 的→单选。类型值统一用：文本/数字/日期/日期时间/单选/多行文本/级联选择/对象集合/整数，**不用"单选(枚举)"这种复合标签**。
- **源 md 缺列的列留空**（如新增页/编辑页源表没有），不脑补页面规则；后续从 Demo PRD/PRD 补，补不上的标"未定义/待确认"。
- 转换后中英文名、类型、行数用脚本核验（每个字段名应含英文括号、无重复行、13列等宽）。
- 审计先行：转换完先让 Codex 只读审计（列数/类型/字段覆盖/技术字段收敛/源版本），按审计报告修复后再交付。

### PRD ↔ TSV 双向互补对账（2026-09 用户定颗粒度）

字段清单不是孤立文件——TSV 和 PRD 是**同一事实的不同切面，互补对账**，不是单向填空列：

- **权威关系**：TSV=字段定义权威（名称/类型/来源/必填）；主PRD=业务规则权威（取值/约束/枚举）；Demo页PRD=页面交互权威（新增/编辑控件/筛选/详情）；前端原型 annotations=实际实现参照；**全局背景信息=兜底权威**（单据命名/编码规则/功能地图，地基优先）。
- **用例数据推演不作字段补充来源**——只是数据样例，不权威（用户明确排除）。
- **双向**：正向=主PRD 的字段规则与 TSV 冲突时以 PRD 业务规则修正 TSV；反向=主PRD 缺 TSV 已定义字段时，在主PRD 补"字段定义/对象字段总览"章节（从 TSV 投影全字段中文名+英文名+类型+必填+来源+简短说明），保证 PRD 可独立阅读。
- **产出对账说明**：每个字段的核对结论（一致/修正/补充）落 audit-reviews/，不只改文件不留痕。
- **先样板后铺开**：先做 1-2 个模块（如线索+商机）验收补法，再推其他模块——7 模块全做错方向返工成本高。
- 权威源变更注意：Demo PRD 里写"以 XX 字段清单为唯一权威源"指的是当时的 md 文件；md 被 TSV 取代后此引用自动失效，实际权威=TSV，不必纠结历史引用。

### 03-产品设计 目录对齐 JXC 标准（2026-09 重构定稿）

版本目录下对齐 QS-JXC 的标准三目录（forge-crm 已重构，新模块照此）：
```
<日期版本目录>/
├── 字段清单/               按模块分目录：{模块}/{模块}字段清单（初稿|详细稿）.tsv，md 全转 TSV 后删（不破不立）
├── 系统架构和流程/         三件套：系统架构说明.md + 业务流程合集.md + 系统单据流程合集.md
└── 需求文档与规则/         模块单层（领域级模块不再套第二层）：{模块}/{annotations, 前端Demo_PRD合集, 主PRD, 页面骨架}
```
- 每个模块：annotations/ + 前端Demo_PRD合集/（Demo 全移入）+ 主PRD + 页面骨架；决策定稿/评审PRD 不入模块目录（评审PRD 归平级"评审PRD/"目录）。
- JXC 源项目：github.com/TopVitamin/QS-JXC-Project（真项目，对照标准用它而不是凭课程笔记猜）。
- 字段清单 md→TSV 转换完成后**删除 md**（不破不立，只留 TSV 一份）；删前先过 Codex 只读审计确认 TSV 完整承接。
- 目录重构用 `git mv` 保历史；批量移动后 `git add -A` 让 git 识别 rename，核验 HEAD~1 vs HEAD 文件数差=有意删除数（无意外丢失）。

**字段清单逐步丰富 6 步**：找参照系统 → 手填初稿骨架（5-10 字段起）→ AI 辅助补全（预测）→ 人工走查（查编造字段/类型/取值，标已确认 vs 候选）→ AI 出详细稿 → 再人工走查。

**配套：版本目录迭代法**（已有模块加需求不覆盖旧版）：`03-产品设计/` 下建 `2026XXXX-第N版` 版本目录放本轮新内容，第一版保留作基线对照，防版本边界混。

## PRD 前置检查清单

出 PRD 前必须逐项确认：

- [ ] 谁用这个页面？（采购员？供应商？仓管？管理员？）
- [ ] 供应商侧 → 独立布局（无 ERP 侧边栏）、数据隔离
- [ ] 采购员侧 → ERP 主布局 + 侧边栏
- [ ] 需要独立编码前缀吗？（执行层单据有，辅助记录/供应商侧通常无）
- [ ] context/04 模块名与实际业务对齐
- [ ] context/05 前缀表是否需要增删
- [ ] docs/flow/flowchart.md 是否需要更新
- [ ] 超期/过期逻辑定稿（宽松仍可操作 vs 硬阻断禁止操作）
- [ ] 登录/权限是否影响本模块（供应商身份来自登录？需角色分流？）

## UI 组件库铁律

**禁止 Tailwind 手搓组件。** 新 B 端系统初始化时必须先问组件库：

| 技术栈 | 组件库 |
|------|------|
| React | Ant Design + ProComponents 或 Shadcn/UI 或 Arco Design |
| Vue | Vben Admin(Shadcn/UI 核心 + 可插拔 Ant Design Vue / Element Plus) |

改造策略：先换一个基础档案模块验证 → 基础资料全推 → 业务模块 → 全量。

### Ant Design 迁移已知坑
- **ProForm 子组件不可用**：反重力无法生成 ProFormText/ProFormSelect,改用 antd 原生 `Form.Item + Input`.
- **表单居中**：反重力加 max-w 容器→删掉,antd Form 默认全宽.
- **列表页**：ProTable 支持良好,一步到位.

### 三系统 UI 矩阵(2026-07 定版)
| 项目 | 技术栈 | 设计风格 |
|------|------|------|
| forge-erp | React + Ant Design + ProComponents | 稳重企业级 |
| forge-wms | Vue 3 + Vben Admin(Element Plus) | 清新蓝白 |
| forge-crm | React + Shadcn/UI | 现代极简 |

## 内置/默认能力必须对用户可见可选（2026-08-26 forge-scrm 实测）

**教训**：系统"内置默认提示词"（代码常量 DEFAULT_SYSTEM_PROMPT）用户完全看不到——生成页下拉只显示数据库模板（空=暂无数据），用户不知道内置是什么、也不知道生成效果受它影响（"内置了但看不到"=黑盒）。用户两次反馈：①"用户不知道内置模板是什么"→ P0 补管理页展示；②"内置意义不大，全部放进提示词模板中"→ 演进为全模板化（内置 seed 进模板表，可编辑可删；生成页 Radio 内置/自定义显式选择；自定义提示词一键存模板）。

**规则**：PRD/产品设计阶段就检查"默认值/内置项"是否对用户可见——凡影响输出质量的配置（提示词/规则/阈值/模板），必须：① 管理页可见可管（列表+编辑+删除，删除保护=每类型至少留一条）；② 使用入口显式可选（单选/下拉，不让用户面对"空下拉"）；③ 兜底逻辑防空库（模板库空时回退内置常量，不报错）。一句话：**黑盒配置 = 必然返工的 P0**。

## 上下文累积教训

1. **供应商报价模块三版才定稿**：PRD 定位错三次——采购员侧→供应商侧→超期阻断策略→登录绑定。根源：先出 PRD 再修 context。正确顺序：先修 context 再出 PRD，用户点头后才写前端。
2. **多 agent 并行改 UI 时不编译**：只改不 build，最后统一 build。

## 问卷调研 → 确认回写 → PRD 套件（forge-scrm 2026-08-24 定型，可复用于新项目）

### 1. 问卷回复回收纪律
- **两轮确认机制**：第一轮 = 问卷阻塞项（矛盾/缺口，必须澄清）；第二轮 = 模块 PRD 的"待确认事项"整理后再访。每轮回复都做三重存档：**问题原文 + 回复摘要表 + 回复原文（姐夫原话）**，都放 `draft/待确认问题-*.md`，并注明"摘要与原文不一致以原文为准"。设备等口头确认（无原文文件）的标注来源（如"2026-08-24 用户口头确认"）。
- **回复后立即回写 context**（SSOT），再更新主PRD/模块PRD——回写位置可参考主PRD §10 的"落位"列。
- **派修复指令前必须确认待确认项全部回收**，否则 agent 会把已确认内容按"待确认"处理导致返工/git 冲突（见 a2a-agent-orchestration 的冲突坑）。

### 1.5 防止 git 冲突的并发控制（2026-08-24 血泪教训，用户明确"最烦 git 冲突"）
**同一文件同一时间只允许一个修改者。** 冲突根源：Codex 审计修复（改 draft）+ 用户补录姐夫回复（也改 draft）并行，两边基于不同版本，一合就撞。

强制规则：
1. **发任何修复/审计指令前**，先想清"这份指令会改哪些文件"，并在指令里显式列出**文件锁清单**："以下文件被本任务锁定，其他工作（补录回复/手改文档）暂不要动"；
2. **回复回收与审计修复必须串行**：要么先让所有回复回收完再派审计修复，要么审计修复先跑完再收回复——绝不同时进行同批文件；
3. **用户补录内容时**（如"我补充过了"），先检查相应文件是否被其他 agent 锁定/有未推送改动，若有则让用户先决定顺序；
4. **发现冲突苗头就预警**：用户给出"第二轮回复"这类会在 draft 落地的内容时，主动说"这个会和 Codex 正在修的 XX 文件撞车，建议先等它跑完"；
5. **Agent 自报 ≠ 已交付**：Codex 只上传自检报告，文档改动必须用户 commit+push 后从 GitHub pull 才能验证——验收前先 `git pull` 确认改动真的到了。

### 1.6 交付修改后的文件 = 直接贴完整内容（2026-08-24 用户两次纠偏，重要）
用户说"把修改后的文件发我 / 补全下 / 改好发我"时——**直接把整个文件的完整内容贴进聊天框（一个代码块），不要给 git 命令、不要指路径、不要让他自己操作**。

翻车实录（本会话）：用户要修改后的 draft 文件 → 我给了 `git checkout --theirs` + `git stash drop` 命令 → 用户怒"直接聊天框发，听不懂吗？"。另一次 AGENTS.md 交付没包单代码块 → "要在一个代码块中"。

规则：
1. 改完文件后 `read_file` 取最终内容 → 整个文件放一个 ```代码块``` → 直接发给用户复制覆盖；
2. 单代码块、块外不夹说明文字、内部不嵌套反引号；
3. git 提交是用户/Mac 侧自己的事（或我 VPS 代做），交付物本身必须聊天框可见；
4. 同理适用于要转发给第三方的文本（问姐夫的话术、AGENTS.md、CLAUDE.md、指令）——直接贴，别指路。

### 2. PRD 套件结构（主PRD 定稿后的展开物）

prd-docs/mvp验收清单.md            # 可勾选用例：模块分组 M01-M38 + 系统级 S01-S03；Must/Should 分组（Should 非阻塞）

关键设计：字段 SSOT 在 context/05，字段清单是展开版；MVP 验收拆 Must/Should 组（"希望有"≠必须验收，别把 Should 混进全过门禁）。

### 2.1 双轨节奏（2026-08-24 用户定，重要）
**原型可以超前，PRD 和文档必须同步跟上。** 交付物是原型，PRD 套件才是迭代的最可靠依据。
- 前端/原型是"快速轨道"：先跑起来看清效果、验证交互（可以用 Cursor/Claude/反gravity 快速做）
- PRD 套件是"同步轨道"：原型每超前一块，文档必须补位（主PRD/字段清单/Demo PRD/规则规格）
- 节奏：原型超前 → 按前端实际页面回写 Demo PRD（不凭空设计）→ 规则/字段进 context + 字段清单 → 形成可迭代基线
- 禁止"原型跑远了文档还停在旧版"——迭代依据永远是文档，不是原型代码
- **这是 forge 系列（erp/wms/crm/scrm）的统一节奏**，不是 scrm 新发明——所有项目都这样跑，不要等用户提醒（2026-08-24 被用户指出"生疏了"）

**AI 时代顺序（2026-08-24 用户定）：先 PRD 再原型，不是先原型再 PRD。**
- 以前（人写代码）：原型贵 → 先原型验证 → 再补 PRD（文档后置）
- 现在（AI 写代码）：PRD 便宜 → 先出完整 PRD 套件（含 Demo PRD）→ AI 按文档直接产出原型
- 新项目开场必须配齐：context 地基 + 主PRD + 模块套件（含 Demo PRD）→ 才让 AI 写原型
- 教训：forge-scrm 开场只出了主PRD 就上原型，原型 PRD（Demo）漏了，靠 Opus 底子好才没翻车——这是流程失误，不是运气
- **原型 PRD（Demo PRD）不是可选项**：它是"先 PRD 再原型"的核心——AI 按 Demo PRD 写页面，页面反过来校验 Demo PRD，双向锁定

### 2.2 模块套件完整构成（对齐 forge-erp 采购入库单 / forge-scrm 选题库样板）
每个业务模块 = 一个目录（prd-docs/modules/{模块}/），含：
| 文件 | 只管什么 | 禁止写什么 |
|---|---|---|
| {模块}主PRD.md | 背景、范围、定位、场景、规则摘要、验收 | 重复定义字段 |
| {模块}字段清单.md | 字段唯一定义（SSOT 展开） | 页面布局 |
| {模块}_业务规则规格.md | 状态机、校验、权限、计算规则 | 重复写字段 |
| {模块}_业务流程推演.md | 动态沙盘：步骤+真实示例 | 与用例推演重复 |
| {模块}_用例数据推演.md | 带数字验证：公式、状态快照、走查清单 | UI 控件规格 |
| {模块}_Demo_列表页.md / _Demo_*页.md | 页面结构、控件、交互、Mock（对照 frontend/src 实际页面！） | 字段枚举、计算规则 |
必须文件：主PRD + 字段清单 + Demo PRD（按实际页面数）；有状态机的模块补规则规格+用例推演；纯查询/管理类可简配（不写推演类）。
生成时参照：同类型样板套件（如选题库）+ frontend/src 实际页面——Demo PRD 禁止凭空设计页面。

### 2.3 模块套件 = 每模块一个文件夹（8 份文档，2026-08-24 对齐 forge-erp 采购入库单样板）

**大模块不再用单文件 `modules/0X-*.md`，改为文件夹套件**（对齐 forge-erp `prd-docs/采购管理/采购入库单/` 的 8 件套）：

├── {模块}_业务流程推演.md        # 动态沙盘：分步 + 真实示例数据

### 2.4 实测反馈 → 先回写 PRD → 再出开发指令（2026-08-24 用户要求）

用户实测 Demo/线上系统后提的新需求（本会话案例：业务方向/专业方向"即建即用+二级联动"、菜单默认折叠、登录后进首页），**必须先把需求补进 PRD（更新对应模块套件 + 全局布局文档），用户确认后再出开发指令**——用户原话"把 prd 修正下后再出指令"。跳过 PRD 直接改代码=重复"PRD 定位错了前端 4 轮救不回来"的老坑。

### 2.5 全仓改名/角色词替换 = 语义化替换，不是机械替换（2026-08-24 实测）

项目/系统改名或清理敏感称谓（如"姐夫新媒体运营系统"→"Forge 新媒体运营系统"、"姐夫"→角色词）时：

- **先 grep -rc 摸底分布**：按文件统计出现次数，标出前端用户可见文案（Login/MainLayout 等硬编码标题）与文档分布，拿给用户确认替换边界（如 requirements/ 调研历史、check-reports 过程文件是否也换）；
- **按角色语义分两类替换**（同一称谓在不同句子角色不同，不能一刀切）：
  - 指"产品使用者/操作者/管理员" → 换角色词（如"操盘手"）
  - 指"调研对象/回复人"（原文引用"XX 原话"）→ 换"调研者"
  - 拿不准的选最通顺的，并在报告中列出语义判断供用户复核；
- 替换命令给 agent 时，要求"全仓扫描 + 语义判断 + 结尾 grep 残留=0 验证"，明确文件名不改（历史文件名保留原名）、代码标识符不动、只改文案与文档内容；
- 用户偏好（2026-08-24 确认）：**全仓都替换，不留历史特例**（A 类选项——requirements/check-reports 也换，保持仓库干净）。

### 3. 审计 - 修复循环（27 项分级法）
- **审计指令**：六维度（一致性/引用完整性/状态机/结构规范/缺口/笔误），发现按 P0（事实冲突/规则矛盾，会导致开发做错）/P1（引用错误/结构缺失）/P2（笔误/表述）分级；要求输出"7+1 确认项 vs 回写位置核对表"。
- **修复指令**：把审计发现逐项列成清单，每项"定位文件 → 修改 → 验证"；先定范围决策（如脚本审核一期做"审核入口"、权限一期基础隔离）再让 agent 动手；红线"新增字段必须标'新增建议，待确认'并回写 SSOT"。
- **验收**：agent 自报 ≠ 已交付——它只上传自检报告到 ai-reports 管道，**文档改动必须用户 commit+push 后从 GitHub pull 才能验证**。抽验 P0 不看全部，看每个决策点的实际落位（grep 关键句）。
- **审计/修复报告归档**：审计报告在对话输出（不写项目文件）；自检报告走 ai-reports 管道 + check-reports/ 目录。

### 3.5 多轮回写 = 决策编号（D1-Dn）映射 + 按编号抽验（2026-08-24 实测两轮）

多轮确认回复（如第二轮 9 项）回写时，用**决策编号**而非自然语言描述，让 agent 和验收都可机械核对：

- **指令里先列"已确认的业务决策 D1-Dn"段**：每条一句话（如"D5 自动采集整体降级为预留，MVP 以手动录入+CSV 导入为主"），标注对范围/状态机/字段的影响方向；再按文件列回写点，每处标注对应决策编号（如"context/01 In Scope：采集改手动（D5）"）。
- **agent 自检报告要求 D1-Dn 落位统计表**：每项标 ✅已回写/❌遗漏 + 落位文件——避免它笼统说"已处理"。
- **验收按编号 grep 抽验**：拿 D1-Dn 逐条 `grep -n "关键句" context/XX` 验证真实落位（如 D4 脚本"已使用"→ grep context/04 状态机 + 核心字段清单 enum），不信任自检报告的"全部 ✅"。
- 这种模式同样用于"范围调整类"回写（审计修完一轮后再回写新确认），与审计修复指令区分开、**串行执行**（见 §1.5 文件锁）。

## 给 AI 产出 PRD：给规范，不给参照样例（2026-09 用户定）

用户明确：让 agent 产出 PRD 时，要的是**可执行的规范（硬约束：含什么/禁什么/不达标怎么拦写死），不是参照（样例文档）**——参照靠 agent 自己比对、自己悟，容易走样；规范是机械照做。做法：把规范当标准注入 agent 指令/上下文，不要丢一份样板 PRD 让它"照着写"。

**单文档颗粒度标准（简版参考，详细规范见 `/root/notes/PRD套件产出规格规范_v1.1.md`）**：
- 九章必齐：概述/功能清单/流程/业务规则/交互规则/字段说明/页面路径/异常边界/验收标准。缺章节 = 不够颗粒度。只读页须写明哪些章节"不适用及原因"，不能直接删。
- 每章三问判据：①边界清不清 ②条件全不全（正向+异常，不满足怎么办）③能不能钉死（具体名/ID/取值）。
- 啰嗦边界：防御性"当…则"、空承诺、跨章节重复、死状态、模糊承诺 → 删。**细 ≠ 长**，用表格/编号判据充实，不用散文堆。
- 用户表述要点："该有的结构得有，字符也不能太简单，要说明交互规则、业务规则、流程、功能清单、页面路径"但"不要做得十分啰嗦"。

供应商侧模块 ≠ ERP 内部模块：

| 编码前缀 | 有 | 无 |
