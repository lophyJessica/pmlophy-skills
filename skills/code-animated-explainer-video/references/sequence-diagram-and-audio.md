# 系统时序片配方 + 音轨音效做法

概念讲解片讲「逻辑怎么运转」，时序片讲「系统之间怎么配合」。这份给的是后者的画面结构与声音层做法。

## 一、时序片画面结构

### 布局

横向排 N 条泳道（每列等宽，均分画布宽度），纵向是时间往下推。

```
标题栏 Y 0–70      画面时间进度右上角
泳道标题 Y 76–128  每列一个色带胶囊，写参与方真名
消息区 Y 176–876   可滚动层，消息按出现顺序往下排
解说带 Y 914–1020  固定，主舞台元素不许下探
```

1920 宽放 5 条泳道合适（每条约 330px，够放消息文字标签）。超过 6 条就要缩文字，或者拆成两条片子。

### 消息渲染规则

每条消息是一个绝对定位的行，行高固定（68px 左右够放箭头 + 一行标签）。按 `t` 算进度 `p = clamp((t - m.t) / m.dur, 0, 1)`：

- **箭头线**从发送方泳道中心向接收方生长，宽度 = 距离 × p
- **箭头头**在 p > 0.15 时出现，方向由收发方左右关系决定
- **文字标签**在 p > 0.35 时淡入（箭头先到、字后出现，比同时出现清楚）
- **请求用实线、返回用虚线**——不靠颜色区分，线型是最省认知的编码
- **自述型消息**（CMS 内部逻辑这类，不发往任何一方）画成居中的虚线胶囊，不要假装成箭头

### 历史消息必须保留（最容易做错的一条）

时序图的价值就在累积感：观众要能看到「前面已经走过这几步，现在走到这一步」。

**不要**在消息播完后把它淡出到不可见。做法是分三档压暗而不是消失：

```js
const fade = t > m.t + m.dur + 8 ? 0.42 : (t > m.t + m.dur ? 0.78 : 1);
```

只有当前消息是全亮，刚播完的降到 0.78，更早的压到 0.42 但仍可读。整屏通常能同时看到 5~7 条消息，这才是时序图的样子。

### 滚动用连续插值，不要按条跳

按消息序号整数跳会一顿一顿。用「当前消息序号 + 消息内进度」当浮点索引：

```js
const floatIdx = curIdx + inMsg * 0.85;
const offset = clamp(floatIdx * MSG_H + 30 - AREA_H * 0.40, 0, maxOff);
```

当前消息稳定停在可视区 40% 高度处，上面留历史、下面留预期空间。

### 泳道高亮

只高亮「当前这条消息的收发双方」，其余压到 0.5 透明度。别把所有走过的泳道都留着亮——观众会失去「现在是谁跟谁说」的焦点。

## 二、音轨：分段 TTS 贴到时间轴

逐条旁白单独合成，再按起止秒贴到长音轨上。关键是每段都要卡在自己的时间窗口内。

```python
# 1 逐条调 TTS（本机 http://127.0.0.1:8866/tts?text=<urlencode>&rate=-24）
#    rate=-24 是语速参数（豆包 V3 audio_params.speech_rate，-50~100）
#    对约 4 字/秒（用户拍板的语速基准），默认不传为原速（约 5.3 字/秒，讲解太快）
# 2 ffprobe 量每段实际时长
win  = e - s - 0.6            # 留 0.6 秒尾部气口，不要顶满
rate = 1.0 if d <= win else min(1.18, d / win)
# 3 超窗口的用 atempo 微调，超过 1.18 就回去精简文案
# 4 adelay 到各自起始秒 → amix → apad 补齐总时长
```

```python
filters.append(f"[{i}:a]adelay={ms}|{ms}[a{i}]")
filters.append("".join(labels) + f"amix=inputs={n}:normalize=0,apad[aout]")
filters.append("[aout]asplit[out]")
```

规则：

- **atempo 上限 1.18**。再快就是在逼观众赶节奏，宁可精简文案。写文案时先按字数估，长句注定塞不进短窗口。
- **窗口按「音频时长 + 0.6s」设计，不是按内容重要性分配**。音频 4 秒的文案给 3 秒窗口，只能加速或砍内容。
- **amix 之后必须 apad**，否则音轨会在最后一段结束处截断（例如 240 秒的片子出成 231 秒）。
- 合成完 `ffprobe` 验总时长必须严格等于片子时长。

## 三、音效：ffmpeg 合成电子音，逐点写死

不需要素材库，`sine` 滤镜能造出干净的电子音：

```bash
# 短促提示音（带衰减尾巴）
ffmpeg -y -f lavfi -i "sine=frequency=880:duration=0.26,volume=0.30,afade=t=out:st=0.16:d=0.10" -t 0.26 ding.wav
# 下滑音（个数骨架）：先造正弦再改采样率
ffmpeg -y -f lavfi -i "sine=frequency=880:duration=0.30" -af "asetrate=44100*0.5,aresample=44100" turn_down.wav
```

音色分工（每类一个频率，观众能听出含义）：

| 事件 | 频率 | 时长 | 说明 |
|---|---|---|---|
| 请求发出 | 880Hz | 260ms | 短促「叮」 |
| 返回消息 | 1046Hz | 260ms | 略高，与请求区分 |
| 阶段开始 | 660Hz | 220ms | 轻过渡 |
| 收尾转折 | 523Hz | 520ms | 长音，收束全片 |

时间点从消息数组里直接推导，不要手写第二份时间表——两份表必然不同步。

## 四、混音：旁白优先

旁白 1.0、音效 0.35，音效压到能感觉到的程度就够了，绝不能盖住人声：

```bash
ffmpeg -y -i video.mp4 -i voice.m4a -i sfx.m4a \
  -filter_complex "[1:a]volume=1.0[v];[2:a]volume=0.35[s];[v][s]amix=inputs=2:normalize=0:duration=first[aout]" \
  -map 0:v -map "[aout]" -c:v copy -c:a aac -b:a 128k -t <DUR> out.mp4
```

`-c:v copy` 直接复用已渲染的视频流，不重编码画面，几秒出片。

出两条：带旁白版、纯音效版（用户可能要自己在剪映里换配音或调字幕）。

## 五、TTS 服务参数与升级纪律

本机 `/opt/jarvis-tts.py` 只有 `text` 与新增的 `rate` 两个查询参数（`clean()` 会把标点全替换为空格，长句停顿感来自自己控制分段，不在标点上）。

改这个全局服务前：**先备份（`.bak-<tag>`）、改动保持向后兼容（新能力用新增的查询参数，默认行为不变）**，重启前先确认没有别的调用方正在使用（这类服务是被多方共用的：罗宾的旁白、其他 agent 的音效生成都可能连着）——重启几十秒的断服会打断正在跑的生成任务。

重启后用一条最短请求验证（如 `?text=测试&rate=-24`，解毒 ffprobe 时长与实际相符即说明 rate 生效），非默认路径也要测。

## 六、渲染加速：按核数分片并行

单浏览器顺序渲染是 100 帧/分钟的量级，7200 帧要一个多小时。可以分片并行，但有三个约束：

```python
workers = max(1, min(2, os.cpu_count() or 1))   # 并行数不超过核数
# 把缺失帧切成 workers 段连续区间，每段用独立浏览器实例
await asyncio.gather(*[render_chunk(p, s, e, f"W{j+1}") for j,(s,e) in enumerate(segs)])
```

1 **并行数 = 核数**。2 核开 4 路只会互相抢占 CPU，比串行还慢。先 `nproc` 再定。
2 **每片切连续区间**，片内严格单调递增渲染。乱序渲染会让 Chromium 对被 `scale()` 的图层重新栅格化，阶段交界处出现 1px 亚像素差（肉眼不可见但会污染跳帧一致性校验）。
3 **只补缺失帧**：进入渲染前先扫帧目录，`os.path.exists` 过滤出缺的再排分片。中断过的任务能原地续上，不用白烧前面那几十分钟。

## 七、这个组合的实际耗时参考

240 秒 / 7200 帧 / 1920×1080 / 2 核 VPS：

- 动效页 + 截图脚本 + 文案：一轮写完
- TTS 21 段：约 2 分钟
- 全量截图：单浏览器 60~75 分钟，2 路并行约 30 分钟
- 合成 + 混音：1~2 分钟

长任务一律后台跑并挂完成通知（`background=True, notify=True`），别在前台干等——期间可以继续写混音脚本或做别的事。取消时用 `process_manage(action='kill', session_id=...)`，不要用 `pkill -f`（会连执行它的 shell 一起杀掉）。

## 八、画面已渲染后的改动：只重做对应层，不要重跑帧

成片之后最常见的改动是字幕文案、旁白语速、音效音量、最后的混音配比。这些都在画面层之外，**改完只需重新对应的层再重跑一遍混音（几秒），不要动渲染**——重跑几千帧是几十分钟级别的大代价。

- **字幕文案改**：改 HTML 里的文案数组，对应起止秒变动时同步更新同条文案窗口，然后重跑帧。这属于画面层，还是重渲；但把文案数组先在开写前定死（见八条清单第 8 条）就能避掉，投产后再改代价大。字幕有同步改文案时旁白也要重生成，两层共用同一组起止秒，只改一层必然就错位。
- **语速调整**：本机 TTS 加 `?rate=-24`（约 4 字/秒，用户拍板的标准）重新生成 21 段旁白 → 重新贴时间轴混音，字幕与旁白同续。画面、音效、字幕全不动。
- **音效和混音**：直接改 `build_sfx.py` 的音效点位或 `mix.py` 的音量配比重跑，几秒。

**反例：语速问题重渲画面**——语速太快是旁白层的事，重跑帧解决不了，还担几十分钟成本。遇到「画面太慢/太快」「字幕太啰嗦」这类问题，先判断它属于哪层（画面 / 旁白 / 字幕 / 音效 / 混音），再在那一层内改。

## 九、成片归档与改片的层级判断

成片与全套源码入库 GitHub lophyJessica/video-source，目录约定：`<主题>/<版本-制作者>/`（index.html + shot.py + build_voice.py + build_sfx.py + 两版 mp4）。同一主题的多个版本各自设目录（如 20s-robin、300s-robin、system-seq-240s），不把版本号或工具名写进文件名——靠目录隔离，同名脚本不同目录不相撞。

用户报「某条片子要改」时，第一动作是确认两件事：①要改的属于哪一层（画面 / 旁白 / 字幕 / 音效 / 混音），②用户的源文件在哪台机器上（他 Mac 本地视频目录 / VPS 渲染目录 / video-source 仓）——三处都可能存在同一仙子的不同版本，先找最新那份再动手；能只改非画面层就绝不重渲，重渲几千帧是几十分钟级代价，永远是最后手段。
