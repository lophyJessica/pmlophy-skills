# 用代码做动效讲解视频

把「文字讲不清、静态图也讲不清」的过程做成视频：时间轴、状态流转、条件逐层筛选、因果链。典型请求是「把 X 概念做成一段视频」「图不如视」。

**核心认知：这不是文生视频。** 视频是写一个动效网页、把状态与时序用代码写准，再逐帧录下来拼成 MP4。所以画面能拖参数、能一步步演示，靠的是代码不是视频模型。这个认知要主动讲给用户，否则他会以为需要视频生成工具。

## 三步流水线

1 **动效页**：单个 HTML，CSS/JS 手写动效，暴露 `window.renderFrame(t)`（t 为秒）。
2 **逐帧截图**：Playwright 按固定 fps 循环调 `renderFrame(t)` 再 `screenshot()`。
3 **合成**：ffmpeg 把帧序列拼成 MP4。

```python
# 截图脚本骨架（playwright async）
FPS, DUR = 30, 20.0
exec = "/root/.cache/ms-playwright/chromium-<ver>/chrome-linux/chrome"
await pg.goto("file:///abs/path/index.html")
for i in range(int(FPS*DUR)):
    await pg.evaluate("(t)=>window.renderFrame(t)", i/FPS)
    await pg.screenshot(path=f"{OUT}/f_{i:05d}.png")
```

```bash
ffmpeg -y -framerate 30 -i frames/f_%05d.png -c:v libx264 -preset medium \
  -crf 18 -pix_fmt yuv420p -movflags +faststart out.mp4
```

1920×1080 / 30fps / 20 秒 ≈ 600 帧，截图 40~60 秒，成片 500~700KB。

## renderFrame 必须是 t 的纯函数（这条错了整条流水线白做）

所有元素的状态只由传入的 `t` 决定，不依赖任何上一帧的累积变量、不依赖 `setTimeout` / `requestAnimationFrame`。原因：逐帧截图是**随机访问**，不是实时播放；有内部状态的动画一截图就乱。

配套写法：

- 每个阶段用 `clamp((t - start)/dur, 0, 1)` 算出 0~1 的进度再插值
- 需要“轴推到末端后末端节点才完全点亮”这类效果时，允许进度**超冲**（`clamp(..., 0, 1.08)`），显示值再 `Math.min(p,1)` 截住——否则末元素的 opacity 永远到不了 1，成片里它一直是暗的
- 元素一次性生成好再按 t 改 `style`，不要在 renderFrame 里反复 createElement

## 用户对这类视频的硬要求（别自己发明）

- **禁止 PPT 式翻页**：不许把静态图一页页截出来轮播配音。要求带动效、能讲清对应概念。
- **真数字、可自洽**：所有数字必须从同一组事实源推导得出，不能一处写“≥2 次”另一处时间轴上只画了 1 次。用户会逐条对账。
- **同一画面持续变形优于切场景**：时间轴等基准元素常驻，后续阶段回头在它上面标出证据，观众能一直追溯。
- **每帧都要承载信息**：不要“AI 生成”式空镜头或氛围页。
- **解说带 + 旁白是标配，不是可选**：只给画面等于逼观众用眼睛追动效，一快就跟丢。底部留一条固定解说带（字号要大，观众可能在手机上看，位置固定不遮主画面），实时跟随写"现在在干什么、为什么"；再挂一条 TTS 旁白，语速放慢、句子间留停顿。旁白比字幕更口语、更完整。
- **文案用因果句式**：只写"筛掉 1 条"是在描述现象，写"因为来源是导购端，所以筛掉 1 条"才让人懂为什么。规则判定这类核心逻辑走完整三段式——因为（依据）、触发了（规则）、命中了（结论）。
- **动效节奏底线：任何动效不许 1 秒内做完就切走**。单段动效 1.2~1.5 秒起步，阶段结尾留 0.5~1.5 秒静止，让眼睛跟上。
- **音效层不能省**：只有画面和旁白是半成品。节点点亮给短促「叮」（多个节点音调依次升高），连线给滑音，命中上扬/未命中下沉，阶段切换给轻过渡音，锁定→解锁用两个对比强烈的音（全片最关键的听觉锚点）。BGM 压到最低只管铺底，绝不能盖过旁白。音效在指令里**逐点写死时间与素材**，不让 agent 自由发挥——不给规格它要么不做要么乱贴。
- **文字层两种形态**：固定解说带（位置固定、好读、观众知道看哪）承载主线；关键节点（命中结论、组合通过、解锁）闪一条弹幕做强调。弹幕别全程飘，信息一多就乱。
- **不用专业术语**：观众是业务口的人，数学/工程术语一律换成大白话。「算子」改成「关系」，「二元算子」改成「两个条件之间的关系」，「一元算子」改成「作用在单个条件上的取反」。画面能写「且：两个都要满足」就不要只写一个「且」符号。术语是讲者的舒适区，不是听者的。
- **对象用真名，不用编号**：「标签一」「标签二」「步骤一」这类编号是内部排序，观众记不住，还要多背一套对应关系。导航、标题、方块一律用真名（「X500 高意向」「深度兴趣」「已购客户」）。确实需要标顺序时，编号放真名前面当小字，主视觉必须是真名。

## 语速、字幕、画面三者的时长基准（量化，别凭感觉）

这三段必须用同一个基准算，否则一定错位：要么画面动作做完了字幕还在，要么字幕念完了画面没动。

**语速基准：4 字/秒**（约 240 字/分钟），用户拍板的标准。中文讲解的舒适区。

实测对照（同一段 38 字文案）：TTS 默认输出 7.22 秒 = **5.26 字/秒**，念稿可以、讲解太快；`atempo=0.85` 得 4.45 字/秒（仍偏快）；`atempo=0.76` 得 **3.98 字/秒**（9.55 秒）——对齐 4 字/秒就用这个。atempo 是变速不变调，不会把人声变机器人。

更干净的做法：让 TTS 本身说慢（豆包 V3 的 `audio_params.speech_rate`，范围 -50~100，4 字/秒约 **-24**），而不是事后 atempo 压——压多次会掉音质。本机 `/opt/jarvis-tts.py` 已支持 `?rate=-24` 参数（默认 0 不变，不影响其他调用方）。

**字幕停留 = 字数 ÷ 4 + 1.5 秒**

- 22 字 → 念完 5.5 秒 → 窗口给 7 秒
- 只给 5.5 秒，观众刚读完就切走；给到 10 秒以上，画面在等字幕，节奏就散了

**弹幕 / 解说带切换点 = 语音开始点**：出现与语音起始同帧，消失取语音结束 + 1.5 秒。二者不许各走一套时间轴，同一段文案共用一组起止秒。

**画面动作时长 = 字幕停留时长**。

三条一起校验：取任一段，`朗读时长（字数÷4） ≤ 字幕窗口 ≤ 动画动作时长`。

反查信号：某条文案的窗口若是它朗读时长的两三倍，说明总时长定长了——回退去压内容或重排分段，**不是把语速提上来填满窗口**。语速被拉快就把拉长时长的意义抵消了。

## 时长按内容量算，不是先定时长再往里塞

先定内容，再按时长算：单个机制（一条规则的属性拆解 + 结论）60 秒打底；多个并列对象（三个标签、两条链路对比）再加它们之间的组合关系，120 秒起步。

先拍一个短时长再往里挤，结果只能是每个动作 0.5 秒过一遍，观众看完什么也没记住。**超长的成本远低于信息密度过高的成本**——宁可 2 分钟讲透一件事，不要 60 秒塞四件事。

## 信息密度做减法，一屏只讲一件事

讲解视频的通病是用信息量冒充专业度：同一份数据在节点卡、明细表、统计卡里重复三遍，观众眼睛不知道往哪放。一屏塞三个重点等于零个。

- 一屏只讲一件事，其余元素压暗或干脆不放
- 同一数据不许在多处重复呈现，选一个位置
- 和主线无关的统计（各类事件计数、商品款数、渠道占比）不要上屏
- 放不下的细节留给静态评审页；视频只承担"讲懂"，不承担"显得专业"

判断标准：这一屏要让观众记住的唯一一件事是什么——答不上来就是堆多了。

## 概念讲解片 ≠ 产品界面演示片（最容易做歪的地方）

AI 做这类视频最典型的失败：把逻辑图伪装成产品界面——左侧用户档案面板、底部明细表、右侧统计卡、顶部流程导航条一应俱全。看着专业，但**现实里不存在这种页面**，用户第一反应是「这界面适用于谁？」，答不上来就废了。

两者目标根本不同：

- 产品界面要**完整**：有人要反复操作，每块区域都得有信息
- 概念讲解要**克制**：观众只看一遍，画面里每个元素必须服务"这一秒想让他理解什么"

两条干净的路，别走中间：要么纯抽象图形讲逻辑（观众知道是示意图），要么老老实实录真实产品操作界面。中间形态两头都输。

**操作演示是第三种形态，可以长也可以密**：按「我改配置 → 系统给什么反馈」的操作路径组织（新建标签→配属性→看命中范围怎么缩→预览→发布→到下游调用），信息密反而是优势，因为每步都是新东西。这种三分钟都合理。判断用哪种：讲**逻辑怎么运转**用概念片，讲**系统怎么响应**用操作演示。

## 三类视频，开写前先定是哪一类

同一个功能通常能拆成三条片，分别回答不同问题，别混成一条：

| 类型 | 回答什么 | 画面 | 硬要求 |
|---|---|---|---|
| 概念讲解 | 这是什么、逻辑怎么设计 | 抽象图形、时间轴、条件链 | 克制，一屏一事 |
| 系统时序 | 背后靠什么运转 | 多条泳道 + 时间轴，消息从 A 走到 B | 不出现接口名、请求方式、中间件名，只讲谁向谁要什么、给回什么 |
| 交互演示 | 人具体怎么操作 | 单页面 + 状态变化 | 演清点击后哪块变了、数据从哪来 |

三者覆盖三个层面，放一起就是完整叙事：先懂概念，再看清背后，最后学操作。同一系列片共用一套底色、配色、动效节奏，观众会感知为「完整设计过的」而不是三段零散视频。

做时序片之前必须先把系统边界理清：几个参与方、各自负责什么、哪些同步哪些异步。没定就开写，做出来必错，返工比不做好。

## 交互演示片：用真实原型驱动，不要用代码重画页面

交互片的工作量比概念片和时序片大一个量级——页面布局、组件、表单、弹窗、各步状态全都要对。**绝不要用代码把页面重画一遍**：重画一定走样（照着手抄和直接用原件是两回事），工作量还翻十倍。

正确路线是反过来：用 Playwright 自动操作**真实原型页面**，每一步截图或录屏，叠上标注层（高亮当前操作区、点击位置、解说带）再合成。

- 页面就是真页面，不存在走样问题
- 省掉重画页面的大头工作量
- 原型改了重跑一遍，视频自动跟着更新（传统剪辑做不到这点）
- 如果项目已做过原型复刻，等于把现成资产直接变现

真正的工作量在交互链路的推导：每一步点哪里、页面变成什么、数据从哪来、点错了或网络异常怎么显示、哪些是主路径哪些是异常分支。这不是画图能替代的。

控制工作量的三条：只演主路径 + 一到两个关键异常（提交失败、空状态），不要试图覆盖所有分支；把一个模块拆成多条 2–3 分钟短片而不是一条长片；页面状态复用原型已有的 mock 数据，不另造。

## 开工前必填八条（一条没定别开写）

这类活的返工成本极高：改一个设定就要重写文案、改代码、重跑几千帧。而这八条任意一条在开写前改只要一句话，落进渲染就是几小时。

1 **给谁看**——评审要逻辑正确、运营要规模与效果、研发要实现细节。受众不定，结尾必然写错（给运营停在"1 人命中"毫无说服力）
2 **讲哪个概念、边界在哪**——错了最贵，要连文案带画面重写
3 **多长**——按内容量算，不是拍数字再塞
4 **术语口径**——有没有不能用专业词的地方
5 **对象怎么称呼**——真名还是编号
6 **数据基准**——唯一数字来源 + 派生值清单 + 白名单 + 验算等式
7 **分几段、每段讲什么**——结构先定死，再算帧数
8 **文案全文**——全部写完，起止秒与动画逐条对齐

八条全勾才允许开始写 index.html。完整清单见笔记库 `AI项目/视频任务开工前必填清单.md`。

**时序片的具体配方**（泳道坐标、消息渲染、历史消息保留、滚动插值）以及**音轨与音效的落地做法**（分段 TTS 贴时间轴、ffmpeg 合成电子音、混音配比）见 `references/sequence-diagram-and-audio.md`。其中最容易做错的一条：消息播完后要压暗保留，不能淡出消失——时序图的累积感就靠这个。

## 文案从原型标注里取，不要重新写

如果项目已经做过原型复刻和原型标注，视频解说词直接取标注里的交互说明、业务规则、字段说明——那是评审过的口径，源头上就不会和文档矛盾。

手工重写一遍解说词的代价：每条都要人拍板，一轮一轮返工（十八条文案改三轮不稀奇），而且很容易出现视频和标注说法不一致。

链条是：**原型复刻（真界面）→ 原型标注（交互/规则/字段说明）→ 视频文案（弹幕/解说带）**。标注是多细，视频几乎就是白送。反过来说，接需求时问一句「这个功能评审要出什么」，就直接决定了标注要写多细。

## 受众决定内容落点

- **领导/评审**：要逻辑对不对、机制说不说得通
- **运营**：只关心圈出多少人（越多越喜欢）、触达成功率、转化效果、单位成本。给他讲「属性一二三四五逐层筛」，他只会问最后圈了多少
- **研发**：实现细节（接口、数据源、性能）

做技术向的算法透明演示，结尾停在"1 人命中"对运营毫无说服力，必须落到业务价值：圈出多少人、渠道怎么分、预估能触达多少。开写前先问清给谁看。

## 概念本身必须准确（比画得好不好优先一万倍）

讲解片最严重的错误不是画面难看，是把概念讲错——观众会拿片子当依据，错的东西会被当真。开写前先把概念的边界跟用户对齐，不确定就问。

常见逻辑关系只有三种，不许自创第四种：

- **且**：连接两个条件，两个都要满足
- **或**：连接两个条件，满足其中一个就行
- **非**：作用在**单个**条件上，把它反过来算

禁止把「且」和「非」合并成一个叫「且非」的算子。看起来很顺，但它是把两个不同层级的东西粘在一起，观众会以为系统里有第四种关系。正确画法是把「非」单独一步，套在那个条件外面，让它先变成「非 X」，再作为一个整体参与前面的「且」运算。

**多层级组合要分层画**：一个机制常有两层组合（如「条件→中间物」是一层，「中间物→最终结果」是另一层，且两层的可用关系还不一样）。这两层必须视觉上能区分——不同色系（一层一色）、不同形状（圆角胶囊 vs 直角方块）、各自挂带「第 1 层 / 第 2 层」的标签。混在一起观众会以为是一层。

「或」最容易被误解成「全部都要满足才算过」。画并联电路，一支灭一支亮主干照样导通，下面再写一句「或关系下有分支没满足，不代表不通过」——这是「或」和「且」的关键差别，不点明等于没讲。

## 内容结构：四段式（讲清一个机制的最小骨架）

以“规则引擎类”概念（如事件标签、风控规则、评分模型）为例：

1 **过程铺开**：把原始事实按时间/顺序排开（时间轴节点依次点亮），右上角计数递增
2 **逐条判定**：规则逐条判断命中与否，命中的高亮、未命中的变灰并写明原因（“0 / 需 1”），同时回指时间轴上的证据节点，用连线连过去
3 **机制展开（核心，占最长时间）**：把一条规则拆成若干属性（事件来源 / 关联对象 / 时间窗口 / 统计口径 / 触发阈值），逐个变“满足”，**每一步都在时间轴上筛掉不符合的元素**，让人看到这个属性具体在过滤什么；配“已满足 n/N”进度条，全部满足才解锁出口
4 **结果与用途**：结论沉淀到对象上，再接下游用法（圈出多少人群、走什么渠道），数字要能从前面推出

“缺一个就不算”这类否定逻辑，用**出口锁住 → 满足后解锁**来表现，比另做一个反例干净。

## 视觉默认值

深色渐变（`#06080c` → `#141c28`）+ 极淡网格；主色青 `#5ee7df`；失效/被筛掉的灰 `#3a4a5e`；锁定态暗琥珀色，且只在这一处用。这套观感用户认可，可以直接作为起点。

## 出片前审查：文案时间轴必须逐条对齐动画时间轴

解说文案按平均时长估算分配，会和动画动作错位：画面已经在筛第五个属性，字幕还在讲第四个，观众对不上号。所有文案的起止秒必须等于对应动画动作的起止秒，逐条核对，不许估算。排完文案后回到动画时间表，一条一条比对。

审片抽这几帧：每个阶段起点、每个筛选动作完成点、每个结论点亮那一帧，以及**全片最后一帧**。核对三件事——元素是否重叠/出画、数字是否与事实源一致、字幕文字是否对应当下动作。

**判定数字错误前先抽末帧定值**：滚动计数的中间帧会显示任何中间值（实测两次把滚动中间态 542/193 误判成数据错误，末帧才落在正确终值）。看到圈人/统计数字对不上时，先取 `ffmpeg -ss <接近末尾>` 的帧确认最终值，再下结论；中间态不是错误。

**读数字要裁区域放大，不能整图一次识读**：数字密集区（圈人卡、计算条）用 `vision_analyze` 的 region 裁剪到只有那一块再读，整图读会把相邻数字串位。列表/表格列顺序拿不准时回 HTML 源码 grep 核对，不靠一次识读断言。

## 交付：配一段文字摘要，不要只丢一个 mp4

视频没法搜、没法跳，看的人不知道值不值得花两分钟。嵌入 wiki / 知识库时，同一个页面里放三样：文字摘要（三到五条要点）、视频、原始文档。不想看视频的人照旧读文字，不会因为“只能看视频”而跳过整块内容。

摘要写法：这段讲了三件事——①…… ②…… ③……。让扫一眼的人能判断要不要细看。

入库时成品控制在 10MB 以内最好（超30MB 上传卡、观众也打不开），大文件就降码率或压时长。

**只交最终完整版，不发过程版。** 用户要的“成片”只有一个定义：带旁白的完整版。纯画面版、修正版、加 -fix 后缀的版本一律自己留着当底档，不要一并发出去让他挑（原话：「给我的产物只需要一个完整版，不需要过程版也给我」）。中间产物多了他会自己分不清哪个是最终版。

## 出厂前的三项硬校验（缺一项就等于发了个废片）

交付前必须跑完这三项，任何一项不过都先修再发：

1. **音轨存在且响度正常**。`ffprobe -show_entries stream=codec_type` 确认有 audio 流；`ffmpeg -i f.mp4 -vn -af volumedetect -f null /dev/null` 看 mean/max。人声成片用 `loudnorm=I=-16:TP=-1.5:LRA=11` 归一，只挂音效的版本 mean≈-28dB 就够。**实测踩过：mean -43.5dB（带旁白版）与 -52dB（音效版）在手机/笔记本上等于没声音**，用户只会说“声音太小太小根本听不见”；此外还出现过整条无音频流的“无旁白版”。
2. **解码完整性**：`ffmpeg -v error -i f.mp4 -map 0:v -f null - 2>&1 | wc -l` 必须是 0。有几百上千行 NAL 报错的文件是坏的，播放时表现为**画面和文案对不上、开头几秒跳到中段某一步**——先怀疑文件损坏，不要去改内容/顺序重排。同批次里干净的那条可以当对照（同一条流水线出来的片子不会只有一条内容错）。
3. **首帧与末帧肉眼确认**：抽首帧看是不是片子第 ① 步，抽末帧看是不是终态；数字类再用 region 裁剪放大读值。

三项都过再发。用户报“画面和文字不符”时，先按上面第 2 条解码错误数定位，再谈内容。

### 响度归一化必须写进混音脚本，不是出厂前临时补

补一次不算修好：手工对成片做 loudnorm 之后，只要流水线重跑一遍（改文案、重渲帧），音频就退回原样——用户会说“声音又是 bug，太低了”，而根因跟上一轮一模一样。

判据：`grep -nE 'loudnorm|volume=' <混音脚本>`。混音链里只有 `amix=...` 和 `volume=1.0` 就是缺这一级。TTS 分轨本身很轻（实测 voice 轨 mean ≈ -38dB），原样合轨必然整片偏轻。

修在源头：把归一化挂在该脚本最后一次合轨的 `filter_complex` 末尾，之后所有重渲自动带。

```bash
# 合轨时直接带上
amix=inputs=2:...,apad=whole_dur=<DUR>,atrim=0:<DUR>,loudnorm=I=-16:TP=-1.5:LRA=11[mixout]
```

### 已出片只修音频：重封装，不要重渲视频

画面没问题、只是声音小的时候，**绝不要重跑几千帧**（半小时到几小时）。视频流原样 copy、只换音轨：

```bash
# 1) 先测混音成品，拿 measured_* （可选，只影响精度）
ffmpeg -i audio_final.wav -af loudnorm=I=-16:TP=-1.5:LRA=11:print_format=json -f null - 2>&1 | tail -14
# 2) 归一化音轨
ffmpeg -i audio_final.wav -af "loudnorm=I=-16:TP=-1.5:LRA=11:measured_I=..:measured_TP=..:measured_LRA=..:measured_thresh=..:offset=..:linear=false" -ar 44100 -ac 2 audio_fix.wav
# 3) 视频流 copy + 换音轨（秒级）
ffmpeg -y -i old.mp4 -i audio_fix.wav -map 0:v:0 -map 1:a:0 -c:v copy -c:a aac -b:a 192k -movflags +faststart -shortest fixed.mp4
```

重封装后仍要跑三项硬校验（解码 0 错误、`I` 在 -17~-15 LUFS、True peak ≤ -1.5 dBFS），因为 `-c:a aac` 是二次编码。

### 声音小的定位顺序（别一上来就调增益）

1. 全片 `volumedetect` + `ebur128` 看 **mean 与 integrated（I）**：I ≈ -36 LUFS 就是整片轻，不是某段。
2. 分轨量 voice / sfx / audio_final 各跑一次 volumedetect。**voice 轨自己就 -38dB 说明问题在混音缺归一化**，不在编码、也不在 TTS 音色选错。
3. 分段抽样（每 30 秒取 8 秒）确认全片轻还是局部轻；全片 -35~-60dB = 缺增益级，不是某处衰减点错。
4. 再看流：`ffprobe -show_entries stream=codec_type` 有没有 audio 流、几条。

## 交付的两条通道：入库优先，传机次选

**成片一律先入 `video-source` 仓库**（`<主题>/<版本>/`，如 `event-tag/300s-robin/`），文件名带日期与定稿标识（`eventtag-300s-voice-final-1109.mp4`）。用户在任意机器上 `git pull` 就能拿到，不受 Tailscale 中继速度和他开不开机影响。传 Mac 只是「他今天就要看」时的快捷通道，不是唯一交付方式。

- 仓库约定**单个 mp4 ≤ 20MB**（超了就上 LFS，不值得为几 MB 折腾）。超一点点时最省事的减法不是降画质，是**音频重封装到 128k**：`ffmpeg -y -i in.mp4 -map 0:v:0 -map 1:a… -c:v copy -c:a aac -b:a 128k out.mp4` ——视频流 copy 不动，21MB 掉到 19MB，响度不受影响（重封装后仍要跑一遍三项硬校验）。
- **README 的片目表要写清哪条是定稿、成品文件路径、md5、时长、响度**。一个目录里堆着四五个历史版本时，唯一能分辨「哪个是最终版」的就是这张表和 md5，只写「成品」两个字下一个人一定拿错。
- 历史版本会持续长大（每条 300s 片子四个版本 ≈ 70MB），片子多了以后只保留定稿入库，历史版留在本地当底档。

## 把成片送到用户机（Tailscale + scp，别让他自己敲命令）

```bash
scp -i ~/.ssh/id_ed25519_forge -o IdentitiesOnly=yes \
  a.mp4 b.mp4 liulongfei@<mac-tailscale-ip>:~/video-robin/
ssh -i ~/.ssh/id_ed25519_forge liulongfei@<mac-tailscale-ip> 'md5 -r ~/video-robin/*.mp4'
```

- 用户的 Mac 收件目录固定 `~/video-robin`，不要另建目录也不要问放哪。
- **必须 `-i <key> -o IdentitiesOnly=yes`**：私钥文件名不是默认的 `id_ed25519` 时不显式指定，ssh 根本不会把它递上去，现象是 `Permission denied (publickey)` ——此时先查本机 `~/.ssh/*.pub` 与远端 `~/.ssh/authorized_keys`，不要急着重装 sshd 或换用户。
- 传完两端各跑一次 md5 逐条比对再报完成；只报“已传输”不算交付。
- **大文件用 `rsync --partial` 而不是 `scp`**：scp 断线从头再来，而这条链路本身很慢（实测 18MB 走 Tailscale 中继约 5 分钟，约 58KB/s）。续传写法：

```bash
rsync -av --partial --progress -e "ssh -i ~/.ssh/id_ed25519_forge -o BatchMode=yes" \
  fixed.mp4 liulongfei@<mac-tailscale-ip>:~/video-robin/
```

- **对方合盖/休眠会让 SSH 直接超时，表现像“网络问题”其实不是**：先 `tailscale status` 看对端是不是 `offline, last seen ...`、是不是在 `relay "xxx"` 中继；对端 offline 就停手等对方开机，不要反复重试也不要怀疑密钥。判据：`tailscale ping` 同样 timed out 而本机其他服务正常。
- **重传时先保持 `-fixed` 文件名**，两端 md5 对齐后再在远端覆盖成正式文件名，避免传到一半把旧版冲掉。
- Mac 侧只开 Tailscale 不等于能连：macOS 的「远程登录」默认关闭，需要用户在 系统设置→通用→共享 里打开；公钥没加入 `~/.ssh/authorized_keys` 同样连不上。走不通时的备用通道：把文件放到静态站目录，给一条可直接粘贴的 `curl -O` 循环命令（文件仍要核 Content-Length 或 md5）。


## 环境坑

- **`PYTHONPATH` 被上一层进程占用了，会让所有 python 都加载到错版本的包**：报 `ModuleNotFoundError: No module named 'greenlet._greenlet'`（或任何 `_xxx` C 扩展找不到）时，不是包没装，是 `PYTHONPATH` 指向了另一个解释器的 site-packages。验证与重跑用：`env -u PYTHONPATH <install venv>/bin/python shot.py`。Hermes 本体升级后 venv 被重建，旧解释器的包目录还留在环境变量里，这个坑会反复出现。
- **Playwright 的浏览器版本常与本机缓存不一致**：报 `Executable doesn't exist at .../chrome-headless-shell-<ver>` 时不要去下载（国内慢），先 `ls ~/.cache/ms-playwright/` 看已有版本，用 `executable_path=` 指过去，并补 `--no-sandbox --disable-dev-shm-usage`（容器/VPS 必需）。
- **中断长渲染时别用 `pkill -f <关键词>`**：执行这条命令的 shell 自身命令行里就含那个关键词，pkill 会把自己一起杀掉（现象是命令返回 exit -15 / -9，后面什么都没输出）。用工具层的 `process_manage(action='kill', session_id=...)` 精确杀掉那个后台会话；必须在 shell 里杀时，把关键词拆开拼接（`P="s""hot.py"`）避免自匹配。
- **重跑先补缺帧，不要盲目 `rm -rf frames`**：按帧号 `os.path.exists` 扫一遍只渲染缺失的，中断过的任务能原地续上。只有改了动效页逻辑（画面全部失效）才需要清空重来。
- **被杀掉的 ffmpeg 留下的成品 mp4 是坏的**（无 moov atom，`ffprobe` 读不出时长，报 Invalid data），和帧损坏是两回事：帧文件都在、画面不用重渲，直接把那条 ffmpeg 合成命令重跑一遍即修。混音配比前先对成品跑 `ffprobe -show_entries format=duration` 验能读出时长，再拿它去配。
- **渲染速度由核数决定，`nproc` 先看再定并行度**：2 核机器单浏览器顺序渲染约 100 帧/分钟（7200 帧要一个多小时），开 2 路能压到一半；但并行数超过核数只会互相抢。分片必须切**连续区间**、每片内部严格单调顺序渲染——乱序会让 Chromium 重栅格化，阶段交界处出现亚像素差。
- **并行度没有通用值，先看机器再定**：VPS 2 核只能开 2 路（开 4 路反而更慢）；Mac M1 Max 10 核可开 4–6 路，7200 帧约十分钟。**这类渲染本来就该整条放在 Mac 上跑**（写代码+渲染+出片一条龙，不用两头搬文件），VPS 只适合写代码和审片。
- **渲染这步要放在核数多的机器上**，不要习惯性地在本机跑。它是纯 CPU 密集活，和写代码、审片可以拆开：本地机器（如 10 核 Mac）跑渲染，服务器只负责写代码和审片，同一脚本两边差四五倍。两头搬文件那点麻烦，远小于多等半小时。
- 成片发出去前抽 2~3 帧看一眼（末帧尤其重要）：末元素是否点亮、汇总数字是否与实际一致。

## 时长量化表（与上一节配套）

| 内容量 | 合理时长 |
|---|---|
| 单个机制、一条链路 | 60–90s |
| 两三个分支或多个条件逐个拆 | 120–180s |
| 多个实体组合、两层逻辑、且或非全覆盖 | 240–300s |

粗算：一个概念要点（一个条件、一条分支、一次判定）2.5–3 秒画面 + 3–5 秒消化停顿，约 6–8 秒；分镜阶段一条解说文案占 12–16 秒（含念完 + 留白），文案条数 × 13 秒 ≈ 总时长。用户说「太快」= 时长不够，不是语速问题。

## 数字纪律与逻辑自洽（两条被用户当场否决过的）

- **禁止用人为倍率造规模**：`基准 7 条 ×100 = 700 人` 即使标注「折算」也算编造。要么用单样本实况值，要么明写「结构示意，非真实规模」。改版时先核旧数字——上一版剔除 246 人、这一版 124 人，两版都自称自洽，观众一算就卡住。
- **让基准数据天生卡在边界上**：把某条记录放进 168h 滚动窗口外 2 小时 40 分，那个「时间窗口」属性才有真实过滤动作，比堆参数有力得多。
- **状态推导出来的东西要跟着状态变**：演「规则失效 → 结果移除」时，结果物要用 `RULES.filter(r => r.hit)` 生成，别全量建好再逐个隐藏——实测出过规则写「已下单移除」、标签卡还挂着「需人工跟进」的自相矛盾。

## 两个易漏的实现坑

- **`DUR` 必须与页面最后一个动画的结束秒数对齐**：给页面加内容忘了改 DUR，成片末尾直接被截断像没播完；DUR 过长则多出几秒静止。改完内容先抽 `<DUR-0.5>` 秒的末帧确认已是终态。
- **属性面板要「属性名 + 具体值」**：写「统计方式 = 累计次数」像没填（枚举不是数值）。每格都要是「统计口径→按用户累计次数」「触发阈值→≥2 次」这种，多条组合要显式演「全部满足才命中（5/5）」。
- **f-string 里不能出现反斜杠**：`f"{...b'\x89PNG'...}"` 直接 SyntaxError，魔数判断先算成变量。
- **成品别盲保留**：帧序列是中间产物，几十 G；成片 md5 与 git 仓里那份核对一致后即可删帧（本次清出 6.4G）。

## 时间轴必须按旁白真实时长排（本类活返工最多的根因）

先定总时长再往里塞文案，必然留下一堆死空白：实测一条 240 秒片子，20 段旁白加起只讲了 108 秒，**132 秒是空的**，每段之间静 5–11 秒。用户的描述会是「开场说完后一直停了好几秒才有动画和声音」——不要辩解是「留白消化时间」，5 秒以上就已是缺陷。

正确做法：

1. **逐段量真实语音时长**：`ffprobe -show_entries format=duration -of csv=p=0 audio/vNN.mp3`，槽位 = 语音时长 + **1.5 秒气口**，全片总时长 = 所有槽位之和（不是先拍 240 再往下分）。
2. **改文案就改时长，改时长就重排整条时间线**：TTS 重新合成那一段 → 该段变长/变短 → 后面所有 MSG/SUBS/PHASES 的秒数全要重算 → 必须重渲。所以**文案要在开工渲染前定稿**；否则每改一句话就是一轮全量重渲。
3. **重排要脚本化、一次改全**：建一份分段线性映射（旧窗口 `[s_i,e_i]` → 新窗口），用它统一重写 index.html 里的 MSG.t（dur 同时夹到本槽位上限）、SUBS、PHASES，以及 shot.py 的 `DUR`、build_voice.py 的 `DUR` 和每条时间、mix.py 的 `-t`。手改十几个数字必错且漏。重排前先 `cp` 备份这几个源文件，改坏了能回滚。
4. **交付前量空白**：`ffmpeg -i f.mp4 -vn -af "silencedetect=noise=-45dB:d=2" -f null -` 看 `silence_duration`，最长应 ≤ 约 2 秒（气口量级）；出现 4 秒以上就说明时间轴还是按老时长铺的。

重排脚本已封装：`scripts/retime_timeline.py`（填 BASE / OLD_WINDOWS / PHASE_BOUNDS 后跑一次，自动重写 index.html 的 MSG·SUBS·PHASES 与 build_voice.py / shot.py / mix.py 的时长）。跑之前先 `cp` 备份这四个文件。

**总时长与时间码不许在画面里写死。** 页面上 `const DUR = 240` 与 `progTag.textContent = t+'s / 240.0s'` 这种硬编码，重排到 143 秒后右上角还在显示「/ 240.0s」，用户会以为没剪。一律改成从 `DUR` 常量算，改一处全片跟随。

**屏幕文案进场前逐条 grep 源文件核对完整性**。画面里出现半句话（如结尾少四个字）多数不是 CSS 裁切，而是写源文件时就写漏了——`grep -n '<半句>' index.html` 对上原文一眼就能确认，不要先去调字号/宽度。

**业务上下文要写进文案本身。** 只说「配受众」不够，要写清这一步发生在哪：「在触达计划里做受众筛选：块间 且/或/非 → 组间 …」。改一条屏幕文案时，解说带和 TTS 旁白同步改（旁白重新合成那一句），三处口径不许分叉。

## 交付时清掉被取代的旧文件

把新成片传到用户机后，**在同一条命令里删掉上一版**（`ssh … 'rm -f ~/video-robin/<旧文件名>'`）。他的收件目录里躺着 240s 旧版和 143s 新版时，他打开的是哪个全凭运气，而这属于「过程中的糊涂」不该丢给他。传完 `ls` 一次目录给他看，列表里只该有当前有效的成片。

## 派给别的 agent 时

这类任务很适合交给子 agent / 网页端助手做，但指令里必须写死：禁止 PPT 式翻页、renderFrame 必须是 t 的纯函数、基准数据自洽、一屏一个重点、文案与动画逐条对齐，以及“先交分镜再写代码”的 Checkpoint。分镜里要求它列出每个阶段的时间区间与画面元素，人核过再放行——否则容易得到一版漂亮但对不上账的东西。

自检要求也要写进指令，让它自己验，而不是嘴上说"已验证"：

1 **跳帧一致性**：取 8~10 个采样点，顺序渲染一遍、乱序反向跳帧再渲一遍，各自算 SHA-256 比对。这是像素级验证，比读 DOM 属性严格，抗锯齿差异都能发现。
2 **阶段交界零重叠**：每个交界处取前后各一帧，用 `getBoundingClientRect()` 两两算交集面积，必须为 0。
3 **状态单调性**：被筛掉的元素在后续所有阶段不许重新点亮，扫全片验证违规次数为 0。
4 **文案时序**：逐条核对字幕实际切换时刻与设定值，误差不超过 1 帧。

写完先交 4 张关键节点单帧预览确认布局，再跑全量。几千帧一上来就全量渲染，布局没定就白跑一遍。
